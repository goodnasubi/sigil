# 並行実行時の直列化・遅延劣化の調査と配備条件（Issue #781）

## 1. 概要

sigil-aegis-waf 第4段（Issue #7、PR #8）の計測において、検査追加時間 p95 ≤ 2 ms の目標が同時数 1 でのみ達成され、同時数 2 以上で未達（同時数 2: 53.7%、同時数 4: 1.4%、同時数 8: 1.1%）となる現象が報告された（Issue #781）。「Sigil の実行系が実行時呼び出しを直列化している疑い」について、計測要因と実行系要因の切り分けを行い、根本原因の特定と代替配備条件の検証を実施した。

## 2. 計測側要因の切り分け

1. **Python 3.13 計測ハーネス（`bench_stage4.py`）**:
   - `ThreadPoolExecutor(max_workers=concurrency)` による並行クライアント送信を検証した。後述のとおり、配備条件を `SIGIL_WORKERS=1` とした場合は同時数 2・4・8 のいずれでも 99.6%〜99.9% が 2 ms 以内に収まり p95 ≤ 2 ms を達成した。したがって、計測ハーネス自身がボトルネックや直列化の原因ではない。
2. **ループバック上流（`shield-preface` / モック）**:
   - 応答遅延はマイクロ秒単位であり、直列化の主因ではない。
3. **固定 PROXY v2 送信元 / レート制限（`Lock<Limiter>`）**:
   - `aegis_http.sigil` の `admit` 内の `Lock<Limiter>` をバイパスして計測した場合でも、複数ワーカー時の遅延（同時数 2 で平均 3.14 ms）は改善しなかった。レート制限ロックの競合が主因ではない。

## 3. 実行系本体の要因特定

### 3.1 レーン C2（ネイティブ生成系・スレッド実行）の検証

`src/codegen/func/task.rs` の `worker_run_body` および `src/native.rs` を精査した。
- `worker_run_body` では、`sched_next_task` でタスク枠を取得した後は `call_indirect` を排他ロックの外側で実行しており、コード生成系がタスクの実行自体を直列化するロックを保持している事実はない。
- `tests/worker_sched_355.rs` のバリア同期テスト（`two_workers_execute_at_the_same_time`）が示すとおり、複数のワーカー OS スレッドは実際に同時に CPU コア上で並列実行されている。

### 3.2 レーン D2（標準ライブラリ実行系）における競合の特定

複数ワーカー稼働時のプロファイリング（strace）により、8 要求の処理中に 70,000 回を超える `sys_futex` システムコール（秒間換算約 350,000 回）が発生し、激しいロック競合とコンテキストスイッチが発生していることが判明した。

原因は標準ライブラリ（レーン D2）の以下の 2 点にある:

1. **メモリアロケータの単一グローバルロック（`src/stdlib/os_alloc.sigil`）**:
   - 確保器は状態ページの末尾（`LOCK_AT = 4088`）にある単一のロック語を `atomic_cas_i64` で取得し、競合時は `futex(FUTEX_WAIT_PRIVATE, 2)` で待機、解放時に `futex(FUTEX_WAKE_PRIVATE, 1)` を発行する。
   - aegis-waf の要求検査中には文字列・バイト列・リストの確保および解放が頻発する。さらに、時間予算管理で呼ばれる `clock.monotonic_nanos()` も 1 回の呼び出しごとに 16 バイトの `timespec` を `raw.alloc` / `raw.free` している。
   - 複数ワーカーが同時に検査を実行すると、`LOCK_AT` に対する CAS 衝突が頻発し、大量の futex システムコールによるカーネル遷移とスレッド停止が発生する。
2. **スケジューラの単一ロックと thundering herd（`src/stdlib/os_sched.sigil`）**:
   - スケジューラ全体が単一の `S_MUTEX` で保護されている。
   - アイドル状態のワーカーは `sched_idle` → `wait_event` で `S_EVENT` の futex 待機に入るが、タスクの起床・完了・I/O 到着のたびに `notify()` が `futex(S_EVENT, FUTEX_WAKE, 2147483647)`（ブロードキャスト起床）を発行する。
   - これにより、全待機ワーカーが一斉に起床して `S_MUTEX` を奪い合う。また、`wait_event` が排他を解除してから `sys_futex` を呼ぶわずかな間に他スレッドが `notify()` を呼ぶと世代番号が不一致となり、`futex` が `-1 EAGAIN` を返して即座にループする。この結果、空きワーカーが実質的なビジーループ（futex スピン）に陥り、CPU コアを占有して検査中のワーカーを飢餓状態にする。

これら 2 つのグローバルロック競合により、複数ワーカー実行時には CPU 時間の過半がロック待機・カーネル遷移に奪われ、実効処理時間が 0.8 ms から 3〜4 ms へと大幅に膨張していた。これが「並行時の直列化・遅延劣化」の実体である。

## 4. 代替の配備条件と実測結果

### 4.1 代替配備条件: `SIGIL_WORKERS=1`

Sigil のネイティブ実行系は、環境変数 `SIGIL_WORKERS=1` を指定すると単一ワーカー・協調的非同期イベントループモードで動作する。

このモードにおける動作とコストの内訳は以下のとおりである:

1. **削減されるオーバーヘッド（ワーカー間競合の排除）**:
   - `S_MUTEX`（スケジューラ）および `LOCK_AT`（メモリアロケータ）に対する**ワーカー同士の排他競合・CAS 衝突が完全に排除**される。
   - `notify()` のブロードキャスト起床に伴う複数ワーカーの同時起床競合（thundering herd）や、世代不一致による `futex` の `EAGAIN` 返却に伴う空転スピンが解消される。
   - アイドルワーカーの激しい futex ループによる CPU 資源の浪費がなくなり、CPU が要求検査処理に専念できるようになる。
2. **残るオーバーヘッド（I/O スレッド間通知・システムコールコスト）**:
   - `src/stdlib/os_sched.sigil` の `notify()` はワーカー数によらず `FUTEX_WAKE_PRIVATE` システムコールを発行するため、スケジューリング境界でのシステムコール呼び出しコスト自体は残る（ただし他ワーカーが存在しないため競合は起きない）。
   - ネットワーク I/O 使用時には `io_enter()` により独立した I/O スレッド（`io_loop`）が動作しており、実行可能タスクがない場合の `wait_event()` による `futex` 待機と、I/O 完了時の I/O スレッドからの `futex` 起床は引き続き発生する。
   - したがって、待機・起床機構そのものがゼロになるのではなく、**複数ワーカー間の激しい排他競合・スピンが解消され、I/O スレッドと単一ワーカー間の必要最小限の通知コストに抑えられる**ことが性能向上の理由である。

### 4.4 配備推奨

aegis-waf やゲートウェイ等の I/O 集中型ネットワークプロキシの配備にあたっては、以下の構成を推奨する:
- 各インスタンスは `SIGIL_WORKERS=1` で起動する。
- 複数 CPU コアを活用したスケールアウトは、同一インスタンス内の複数ワーカーではなく、**CPU コア数分のプロセスを起動するプロセス並列**（Linux `SO_REUSEPORT` または前段リバースプロキシによるプロセス間負荷分散）により行う。

## 5. レーン D2（標準ライブラリ）への今後の改善提案

Sigil 実行系のマルチワーカー並行処理のスケーラビリティを向上させるため、レーン D2 側で以下の改修が推奨される:
1. `std.os.alloc`: 単一ロック `LOCK_AT` を廃止し、スレッドローカルキャッシュ（アリーナ）を導入する。
2. `std.os.clock`: `monotonic_nanos()` で毎回 `raw.alloc`/`raw.free` を呼ぶのをやめ、スタック領域またはスレッドローカル領域で timespec を取得する。
3. `std.os.sched`: `notify()` の `INT_MAX` ブロードキャストをワーカー 1 台のみの起床（`futex_wake(1)`）に改めるか、ワークスティーリング型スケジューラへ再設計する。
