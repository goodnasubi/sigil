# 0054 P6 の OS 本体

- **状態**　提案（typesafe-ai 正式判定済み）
- **日付**　2026-11-21（JST）
- **起草**　Codex Cloud
- **関連**　[Issue #641](https://github.com/goodnasubi/sigil/issues/641)

## 背景と前提

[ADR 0005](0005-long-term-goals.md) 決定 2 の P6（G7）では、Sigil で書いた OS 本体を、ESXi のゲストと実機の両方で起動する。実機の範囲に組み込み OS を含める。最初の CPU アーキテクチャは x86-64 とする。P0 と [ADR 0003](0003-ownership-and-borrowing.md) の改訂（ADR 0005 決定 3）は完了済み。P5 も [ADR 0053](0053-p5-container-management.md) の最終段 P5-5 が [sigil-container PR #14](https://github.com/goodnasubi/sigil-container/pull/14) のマージにより完了した。

## 決定 1　対象とプラットフォームの境界

最初の受入対象は **UEFI の x86-64 ESXi VM** とする。カーネルの共有部分には、起動情報と機器操作の型付き契約を設ける。起動情報はメモリ領域と予約領域などを表し、機器操作は検出済みの機器・割り込み・バッファに対する能力を明示する。機器の発見・設定やハードウェア固有の処理は、対象ごとのプラットフォーム層に置く。初期の契約は ESXi の受入試験に使う操作で決め、組み込み実機への移植で契約を確かめる。

ESXi 固有の構成に閉じた案は起動を早く試せるが、実機への移植で依存の切り分けが必要になる。Cloud Hypervisor のような KVM 系を先行させる案は virtio を使う小さな機器構成を試せるが、ADR 0005 の受入順を変える。ESXi と KVM 系を同時に進める案は、最初の起動に要る契約とデバイス実装を増やす。ESXi を先行しつつ、KVM 系は同じ境界で検証できる後続対象として対応表に残す。

## 決定 2　実行環境なしのネイティブ出力

x86-64 の静的 ELF カーネルと、最初の起動用の UEFI ローダーを分ける。ローダーが ELF を読み、カーネルのメモリ領域を準備し、UEFI のブートサービス終了後に合意済みの入口へ制御を渡す。入口の ABI、スタック、CPU 初期状態、起動情報の版・所有権・寿命を起動契約に記録する。カーネルはホスト OS の ABI、Linux システムコール、ホストの起動コード、動的リンカや外部ランタイムに依存せず、自身の初期化に必要な最小コードを同梱する。ELF をローダーと分けることで、同じカーネル入口を別の起動経路からも検証できる。

出力先は明示的に選ぶ。[ADR 0014](0014-core-and-os-split.md) の `targets bare` は利用可能な機能の制約であり、出力選択には使わない。[ADR 0015](0015-m5-native-output.md) の Linux 向け静的 ELF は既存の出力先とし、P6 の検証には実際のブートを要求する。

## 決定 3　標準ライブラリの分割

| 層 | 依存・利用範囲 |
|---|---|
| 確保に依存しない核 | スカラー値、`Option`、`Result` など。OS と確保器への依存を持たず、初期ブートから使用できる。 |
| 確保に依存する核 | `List` や `String` など。確保に依存しない核と、出力先が供給する確保器の契約に依存する。OS サービスへの依存を持たず、カーネルでは確保器の初期化後に使う。 |
| OS サービス層 | 核の上でファイルや通信などのサービスを使う。ADR 0014 の `std.os` の対象制約を継承する。 |

既存の `std.core` が OS 非依存で確保を使えるという意味と、ホスト上の既存 API を保つ。確保と解放は [ADR 0004](0004-effects.md) の効果規則を継承する。依存の向きはビルドで検査する。確保に依存しない核に確保器の参照が残る場合や、既存 API を保つために層をまたぐ循環依存が必要になる場合は、分割の単位を後続 ADR で再検討する。

## 決定 4　信頼基盤とプラットフォーム層

既存の信頼基盤に加わるのは、ローダーと起動時の引き渡し、CPU 初期化、割り込み、ページ表、MMIO や DMA など、通常の検査では安全性を示せない原始操作、およびそれに不可欠なランタイム部品に限る。ドライバの状態管理やキュー処理、カーネルの資源配分など、通常の検査で表せる部分は、型付きの境界を介して `trust none` で実装する。機器の範囲やバッファの所有権・寿命などの前提を境界の契約で示す。

[ADR 0016](0016-trust-base-declaration.md) に従い、使用する原始操作を `raw.*` の表に登録し、型、効果、検査できる `requires` と安全の前提を示す。呼び出すモジュールは `trust base` を宣言し、外部モジュールは正確なモジュール名による `--trust-base` の許可を要する。必要な箇所に限り `unchecked` の前提を記し、境界の `requires`・`ensures` と併せて `sigil spec` でレビューできるようにする。信頼基盤を増やす差分は許可リストと CI で可視化する。形式検証に備えて、原始操作とローダーの仮定を個別に列挙できる大きさに保つ。

## 決定 5　効果カテゴリの追加

追加候補は、機器 I/O、割り込み制御、アドレス空間操作とする。型付き契約が必要になった段で、カテゴリ名、対象、権限を表す型、宣言と推論の規則、否定例と検証方法を個別の ADR に記録し、承認後に標準ライブラリまたはプラットフォーム層へ追加する。ADR 0004・0005 に従い、利用者によるカテゴリ追加は禁止する。

機器操作を許す場合は P6 用の明示した出力プロファイルと能力の境界に閉じる。[ADR 0028](0028-task-suspend-on-bare.md) の一般の `bare` で使える効果の条件を維持する。機器操作を既存の `state` や `effects none` に割り当てることは許さない。各段の実装は必要な効果の ADR を前提とする。

## 決定 6　実装の置き場所と依存版

言語、標準ライブラリ、P6 の仕様は `sigil` に置く。OS 本体、対象ごとのプラットフォーム層、OS のビルドと起動試験は所有者が作成・命名する別の OS 用リポジトリに置く。リポジトリの作成は所有者が行い、作成されるまで P6 の実装に着手しない。

[ADR 0044](0044-p4-scope.md) 決定 4 に沿い、起草時の `sigil` 基準を完全 SHA `a283bf54607d96e4c1aa27755a2cf2c9ea7a8ce8` に固定する。依存版の取得は当該 SHA をチェックアウトし、`Cargo.lock` を使う `cargo build --locked --release` で行う。P6 の出力に必要な処理系や標準ライブラリの変更は、契約と検証を伴う別の変更で整え、各実装段が依存する SHA を依存更新で明示する。起草基準の SHA で利用できるネイティブ出力は Linux 用である。

## 決定 7　実装段と完了条件

各段は成果物と検証記録を保存する。記録には依存する `sigil` の SHA、対象機器とファームウェア・ハイパーバイザーの構成、起動・試験の手順と観測結果を含める。

| 段 | 成果物と完了の確かめ方 |
|---|---|
| P6-1 出力と起動契約 | 確保不要の Sigil プログラムを静的 ELF として出力し、UEFI ローダーで起動する。ELF に動的リンカ・未解決の外部参照がなく、ビルドの依存と生成コードにホスト ABI の利用がないことを確認する。生成コードと同梱ランタイムに確保器の参照がないことも確認する。ESXi VM でブートサービス終了後にカーネルの入口へ到達し、起動情報の版と検査結果を観測する。対象外形式や不正な起動情報は停止として観測する。 |
| P6-2 ESXi の最小カーネル | ESXi VM で起動し、予約領域を除くページ管理と割り込みを初期化し、確保器を起動して Sigil の確保依存の核を使う。予約領域を配らないこと、資源不足の扱い、割り込みの受信を試験する。通常モジュールからの原始操作は処理系が拒否し、許可された前提は `sigil spec` に出ることを確認する。 |
| P6-3 ESXi の最小機器 | ESXi のサポート対象の仮想機器と版を各 1 構成に固定する。準仮想化ストレージの試験用ディスクで既知データの読み書き、準仮想化ネットワークで試験相手との送受信を再現する。範囲外の要求や機器未提供時は拒否を確認する。 |
| P6-4 組み込み実機 | x86-64 の組み込み実機を 1 構成選び、機種、起動設定、必要な機器を固定する。実機のファームウェアから起動し、共有のカーネル境界を通じてメモリ初期化、割り込み、機器 1 種への入出力を観測する。実機での起動と試験結果を記録する。 |

P6 はこの表の成果物と確認結果がそろい、次の対応表に対象・構成・検証結果を反映した時点で完了とする。ADR 起草の完了は、対象の選び方、出力、ライブラリ分割、信頼基盤とプラットフォーム層、効果の追加、実装段と各段の完了条件が書かれた本 ADR の PR 作成で確認する。Issue #641 の完了には、後続の agy による別系統レビューの承認、CI の成功、マージを要する。

### 対応表

| 対象 | P6 の到達範囲 | 起草時の状態 |
|---|---|---|
| ESXi x86-64 UEFI VM | 起動・最小カーネル・指定構成のストレージとネットワーク | 未対応（P6-1〜P6-3） |
| x86-64 組み込み実機 | 指定した 1 構成の起動・基本機器の動作 | 未対応（P6-4） |
| Cloud Hypervisor 等の KVM 系・virtio | 共有境界を用いる移植候補 | 未対応 |
| 非 x86-64、別のファームウェア、他の機器・機種 | 今回の受入対象外 | 未対応 |
| 汎用 OS のアプリ互換、包括的な機器対応、GUI | 今回の受入対象外 | 未対応 |
| 自動運転向け safety monitor、実車適用、機能安全認証 | 長期方針 | 未対応 |

## 決定 8　自動運転への適用

自動運転は長期方針とし、最初の適用候補は独立した safety monitor とする。AI の判断を型付きの入力として受け、鮮度や範囲、許可された動作を検証し、条件外の出力を拒否して上位の監督部へ通知する。操作の最終権限は監督部が持つ。導入条件となる時間の上限、隔離、安全状態、認証対象はシステムの安全要求とともに別 ADR で決める。VM 上の動作確認は P6 の検証に用い、実車や機能安全への適用は [自動運転 OS の調査](../research/autonomous-driving-os.md) §6.2–6.3 に沿って後続で評価する。実機の設計には [Issue #464](https://github.com/goodnasubi/sigil/issues/464) の The Embedded Rust Book 日本語訳を参照する。
