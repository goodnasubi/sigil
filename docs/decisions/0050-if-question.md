# 0050: 制御構造の条件・対象式における `?` の早期リターン

- **状態** — 提案（2026-11-18 JST）
- **関連** — [Issue #602](https://github.com/goodnasubi/sigil/issues/602)、[Issue #606](https://github.com/goodnasubi/sigil/issues/606)

## 背景

#602 の固定版 `d78779a` では、`Result<Bool, E>` を返す呼び出しに `?` を付けて `if` の条件にすると、ネイティブ実行が segfault（終了コード 139）した。評価器は報告例の期待値である偽側の値を返した。成功値を先に `let` で束縛する形では両方が期待どおりに動いた。誤った分岐や値も報告されている。所有者は 2026-11-18 17:48 JST に ADR を起点に修正する方針を決めた。

## 現行実装の切り分け

- C1 の `lower/expr.rs::try_expr` は対象を一度評価して容器を一時に保存し、タグで分岐する。失敗側は戻り値を設定し、`early_return` で局所の破棄を逆順に出して共通の終端に進む。成功側は容器内のフィールドを指すオペランドを返す。
- `lower/stmt.rs` の `if_stmt` と `While` は条件を lower した後、`flush_temps` で容器を含む一時値を破棄してから `Term::Branch` を出す。条件のオペランドが容器を参照したままなら、生存期間の食い違いが SIR に入る。先に `let` で束縛する形では、破棄より前に値を独立した局所へ取り出す。`match_` は対象のパターン検査と束縛を行い、この箇所に `if`／`while` と同じ破棄順序は見当たらない。
- C1 の評価器では `ir_eval/mod.rs` の `Drop` が対象を `Val::Empty` にし、`value.rs::with_val` は辿れないフィールドに `Empty` を返す。`expr.rs::read_bool` は `Val::Bool(true)` だけを真と扱う。報告例は偽を期待するため、この経路でも期待値と一致し得る。真を返すケースも評価器で期待値を確認する必要がある。
- C2 の `codegen/func/stmt.rs` は集約値の破棄でスロットをゼロにしてから破棄処理を呼び、後続の分岐で `val` を通して条件を読む。破棄済み容器を参照する SIR がネイティブで異常な読み取りになる経路を説明できる。ここまでの切り分けは main `507db2b` のソース読解に基づく。報告の終了コードは固定版の観測であり、現行版での各経路の実測と正常な SIR に対する C2 固有の残差確認は実装段で行う。

## 選択肢

- **C1 からの恒久修正**。分岐が読む値を破棄より先に取り出す。共通の SIR を正し、同じ仕様を両方で実行できる。破棄順と失敗時の後始末を確かめる必要がある。
- **C2 だけで補正**。変更箇所をネイティブに絞れる。評価器にも届く寿命の誤りが SIR に残り、同じ規則をコード生成側で補うことになる。
- **当面はビルド時に診断して拒否**。影響する形を確実に検出できれば異常実行を防げる。型の通る式の一部がネイティブで使えなくなり、評価器との差と回避用の束縛が残る。

## 決定

現行の型検査が許す `if`／`else if`、`while` の条件と `match` 文／式の対象に、既存の `?` の意味を適用する。条件は `Bool`、`match` の対象は成功値を既存のパターン規則で照合する。到達した `?` の対象は一度だけ評価する。`Ok(v)` と `Some(v)` では `v` で式の評価を続ける。`Err(e)` と `None` では既存の破棄規則に従い、その関数から同じエラーまたは `None` を返す。残りの式、分岐先、ループ本体、パターン照合には進まない。`while` の条件は反復の先頭で再評価し、既存の評価順と短絡を保つ。

C1 からの恒久修正を採用する。分岐に必要な `Bool` を生存中に独立した値へ取り出し、条件の一時値を従来の境界で逆順に破棄した後、その値で分岐する。失敗時は既存の早期リターン経路で、所有する値を一度ずつ処理する。確認できた欠陥に変更を絞り、`match` は同じ試験で意味を確認する。C2 の変更は、正しい SIR を渡しても差が残った場合に限る。

### 判断の記録

[ADR 0001](0001-vision-and-scope.md) の「AI が書き、人間は仕様をレビューする」とメモリ安全性、[ADR 0017](0017-run-on-sir-evaluator.md) の実行方式の一致、所有者の恒久修正方針を評価軸とした。既存の型規則を維持し、共通の SIR で値の生存期間を保証することで、同じ仕様を両方で検証できる。

## 突き合わせの追加

`tests/common/mod.rs` の `run`／`run_with` を通す新規統合試験を追加する。期待値を明示し、テスト入口で分岐・照合結果と早期リターンの内容を比較可能な値に表す。正常な実行の終了状態も既存の比較処理で確かめる。

- 報告の偽側を含む直接形と `let` 束縛の対照で、`Ok(true)` の真側、`Ok(false)` の偽側、`Err(e)` の値と後続処理の不実行を確かめる。`else if` と、短絡で `?` に到達しない場合も確認する。
- `while` では真から偽へ変わるまでの再評価と反復回数、途中の失敗による早期リターンを確かめる。`match` 文／式では成功値で選ぶ腕と、失敗時に照合に進まないことを確かめる。`Option` の `Some`／`None` も検証する。
- 破棄が観察できる事例は既存の破棄記録を使い、分岐前の一時値と失敗時の局所の破棄順を確認する。`scripts/native-report.sh` が集計する TSV で、識別可能な試験入口ごとに実行比較の `checked` 行があり、飛ばしが増えていないことを試験の成功と併せて確認する。比較件数の下限と飛ばしの上限は現行の CI 設定を用いる。

## 影響

文法・型規則・公開される `sigil spec` の出力を維持する。条件と対象式の既存の意味を両方の実行方式で保証できるようにし、報告形における束縛への書き換えを不要にする。
