## 確定した方式（判断の手順による）

閾値・単位は ADR 0037／0020／0032／0018 のどこにも規定が無かったため、判断の手順（理念→typesafe-ai 正式判定）で確定した。

- 判定: typesafe-ai（jev-1.13.0）正式判定、2026-11-22。計画案（下記）が確率 1.0・confidence 1.0 で選択された。代替案（30回／60秒、300回／60秒、100回／30秒、100回／300秒、成功でリセット）はいずれも 0.0。
- 入出力の記録: `typesafe-659-ratelimit-20261122-{input,output}.json`（開発記録側に保管）

確定値:

| 項目 | 値 |
|---|---|
| 計数の対象 | 認証必須経路での認証失敗のみ（固定401になる試行） |
| キー | 検証器（サービス）全体。接続・経路・トークンを区別しない |
| ウィンドウ | 最初の失敗で開始する固定ウィンドウ 60 秒 |
| 上限 | ウィンドウ内で失敗 100 回まで。101 回目以降は検証を行わず 429 |
| 成功の扱い | 数えない。成功してもカウンタはリセットしない |
| 設定面 | 閾値は `web.sigil` 内の定数。環境変数等の設定面は広げない |
| 状態の置き場所 | 検証器生成時に作る `SyncShared<Lock<…>>`（プロセス内のみ。再起動でリセット） |

キーを検証器全体にせざるを得ない理由: 要求型（`HttpRequest`／`AppRequest`）に接続元アドレスが無く、署名検証前の未検証クレームは ADR 0037 決定3によりキーにできず、提示トークン文字列をキーにしても総当たりには効かないため。

## 429 応答

- 状態コード 429、本文は固定文 `too many requests`（理由別の差は出さない）
- 見出し: `Content-Type: text/plain; charset=utf-8`、`Retry-After: <ウィンドウ残り秒>`、`Cache-Control: no-store`
- 鍵・トークン・未検証クレームは応答に含めない
- あわせて `Router` の振り分けは、検証器のエラー応答のうち状態コード 429 のものだけを通し、それ以外は従来どおり破棄して固定401に置き換えるよう変更した。計画当初案は「検証器の応答をそのまま返す」だったが、利用者定義の検証器が返した任意のエラー応答（診断情報を含む本文など）を隠す既存の性質（`tests/web_router_478.rs` で検証済み）と両立しないため、429 のみに絞る形へ実施時に修正した
- 利用者定義の検証器が返した 429 は、そのまま（本文・見出し込みで）通す。意図した挙動で、`tests/bearer_ratelimit_659.rs` の `custom_verifier_429_passes_through_eval` で確認している。429 以外の診断情報の隠蔽には例外を作らない
- 時計が取得できない場合は従来どおり固定401で、制限の判定も記録もしない
- 壁時計が巻き戻ったとき（`now < rate_start`）はウィンドウの外として扱い、新しいウィンドウを開く（2026-11-22 の Claude レビュー指摘への対応）。巻き戻しをウィンドウ内とみなすと制限が巻き戻し分だけ長く続くため

## レビュー指摘への対応（2026-11-22、Claude レビュー）

PR #667 への Claude（Claude 系統）の条件つき承認（要対応 2 件）への対応。

1. 壁時計の巻き戻し: `bearer_rate_limited` と `bearer_rate_note_failure` で `now < rate_start` をウィンドウの外として扱い、新しいウィンドウを開くよう変更。試験 `clock_rewind_opens_new_window_native` を追加（差替え時計で 100 回失敗後に 1 時間戻し、401 が続くことを確認）。
2. 実サーバー経路での共有: 検証器は `into_verifier` で一度だけ作られ、`SyncShared<Lock<BearerRate>>` を持つ。実サービスの `serve`（`examples/06-service/main.sigil`）はその Router を `SyncShared` で共有し、接続ごとに clone した持ち手で振り分けるため、状態は接続をまたいで一つ。試験 `shared_rate_limit_across_connections_native` を追加（`serve_two` ドライバで二つの接続をソケットで受け、合計 100 回の失敗後に 429 になることを確認）。
3. その他の提案（ブロックしない）は記録へ反映: 並行要求による上限超過（ソフトな上限）、ロック破損時の fail-open、固定ウィンドウ境界での最大 200 回を「残る限界」へ追加。利用者定義の検証器の 429 の素通しは意図した挙動として本記録の「429 応答」へ明記し、試験 `custom_verifier_429_passes_through_eval` を追加。

## 残る限界（受容として記録）

- 全体カウンタのため、攻撃時には正規利用者の認証も最大60秒止まりうる。キー単位の制限が可能になるまでの最低限の対策として受容する
- 判定と記録が別々のロックのため、同時に飛んでくる要求が `gate` を通過した後に失敗を記録する分、100 回を並行数の分だけ超えうる。ソフトな上限として受容する
- ロックが壊れたときは制限しない（fail-open）。`intent` に書かれているとおり
- 固定ウィンドウの境界では、短時間に最大 200 回の失敗が通りうる（ウィンドウ末尾の 100 回と次の先頭の 100 回）。判定済みの方式のため受容する
- 有効なトークンの再使用そのものは止められない（失敗として数えられない）。個別失効は ADR 0037 で後続 ADR の対象
- 状態はプロセス内メモリのみで、再起動でリセットされる（永続化しない）
- 接続元単位の制限は、要求型への接続元情報の追加（契約変更級）が前提になるため別 Issue 候補
