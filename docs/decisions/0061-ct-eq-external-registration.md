# 0061: 外部モジュールの定数時間検査（ct_eq）の登録方法

- **状態**: 提案（正式判定は未実施・問いを ADR 内に記録）。実装・マージ・外部公開の承認を意味しない。
- **日付**: 2026-11-24（JST）
- **対象**: [Issue #727](https://github.com/goodnasubi/sigil/issues/727)、レーン E。起草のみで、実装は含まない。

## 背景

Sigil では、暗号処理や秘密の照合におけるタイミング攻撃耐性を担保するため、3 層の定数時間検証（[ADR 0020](0020-p1-security-addendum.md) 決定 1、[ADR 0024](0024-crypto-primitives.md) 決定 3）を定めている:
1. **対象表と漏れ検査**: 定数時間であるべき関数を `CT_FUNCTIONS` に明示し、包括基準（`ct_` 接頭辞、`Secret` を含むシグネチャ、`std.crypto` の関数）に当たる関数の載せ忘れを防ぐ。
2. **静的検査（`ct_rules_static`）**: lowering 後の SIR 上で秘密の値（テイント）の流れを追跡し、ADR 0020 の規則 R1〜R6（秘密による条件分岐の禁止、秘密によるインデックス参照の禁止など）への違反を検出する。
3. **CLIF 検査（`ct_rules_clif`）**: Cranelift 最適化後の中間表現で除算命令や予期しない条件分岐の挿入がないことを検証する。

しかし、現行の検査フレームワークは処理系リポジトリ内の `tests/ct_rules.rs` に静的に組み込まれており、検査対象表 `CT_FUNCTIONS` や探査用コーパス `corpus()` は標準ライブラリ（`std.core.bytes.ct_equal` や `std.crypto` など）を前提としている。

そのため、独立リポジトリとして開発される外部モジュール（例: `goodnasubi/sigil-rune-auth`、将来の外部認証・暗号部品、ユーザー定義ライブラリ）が独自に固定長バイト列の照合（例: セッション ID の照合、トークンタグの照合など）を提供する場合、処理系の定数時間検査（静的・CLIF 検査）の対象として外部から登録・検査する手段が存在しない（Issue #727）。

`sigil-rune-auth` 段 1 の試作（Issue #1、固定版 `ba4a5f1b`）では、照合箇所を処理系標準の `ct_eq`（`std.core.bytes.ct_equal`）の直接呼び出しのみに限定することで登録機構の追加を回避したが、外部モジュール側で独自の照合関数を定義したり、外部モジュール全体に対して定数時間検査を適用したいケースに対応するため、処理系として外部モジュールの定数時間検査の登録・実行方法を定める必要がある。

## 決定 1 — 外部照合の登録方式: プロジェクト設定（`Sigil.toml`）によるマニフェスト登録

外部モジュールの定数時間検査の登録方式として、以下の案を検討した:

- **(A) 言語組み込みの属性（`#[constant_time]` / `@ct`）方式**: 言語仕様として関数宣言に属性を付与し、コンパイラ／検査器がソースコードから自動的に定数時間対象を認識する。
- **(B) プロジェクト設定（`Sigil.toml`）によるマニフェスト登録方式**: 各モジュールの設定ファイルに定数時間対象関数および公開引数リストを宣言し、CLI から検査を実行する。
- **(C) 検査器ライブラリの公開と外部テストランナー方式**: `ct_rules` の静的・CLIF 検査エンジンを処理系から切り出してテストヘルパーとして公開し、外部モジュールのテストコード内で対象表を渡して検査を実行する。
- **(D) 標準 `ct_eq` への集約と外部照合の原則禁止（規約方式）**: 外部モジュールでの独自バイト列照合の実装を認めず、定数時間照合は標準ライブラリの `ct_eq` の呼び出しに一元化する。

**決定: (B) プロジェクト設定（`Sigil.toml`）によるマニフェスト登録方式を採用する。**

- **理由**:
  - (A) は言語構文（レーン A1）および AST・型検査器への変更を伴い、仕様変更の範囲が大きい。
  - (B) は言語構文を変更せず、プロジェクト単位（レーン D1）で定数時間対象関数を明示できる。既存の `tests/ct_rules.rs` の `CT_FUNCTIONS` と同じ構造 `(関数名, 公開引数一覧)` を TOML 上で宣言可能であり、概念の整合性が最も高い。
  - (C) は外部モジュールが Rust テスト環境を維持することを前提とするため、純粋な Sigil プロジェクト単体でのテスト完結という方針に合致しない。
  - (D) は直近の回避策として有効であるが、将来的に複合的な照合（例: 構造化データの定数時間比較など）を外部モジュールが提供する余地を塞ぐため、恒久的な仕様としては (B) を登録口として定める。

## 決定 2 — マニフェスト（`Sigil.toml`）の記述仕様

外部モジュールのプロジェクト設定ファイル（`Sigil.toml`）に、定数時間検査対象を指定するセクション `[testing.constant_time]` を設ける。

```toml
[testing.constant_time]
# 定数時間検査の対象とする関数一覧
targets = [
  { name = "rune_auth.verify_session_token", public_args = ["token_len"] },
  { name = "rune_auth.compare_digest", public_args = [] },
]
```

- **テイントの扱い**:
  - `public_args` に指定されていない引数は、すべて「秘密」（secret）として扱う（ADR 0020 / ADR 0024 の原則を踏襲）。
  - 長さ情報（`len`, `is_empty`）は、ADR 0020 に従い自動的に公開情報として扱う。
- **完全性の検証**:
  - 宣言された関数がモジュール内に実在しない場合、または `public_args` に指定された引数名が存在しない場合は、検査時に失敗（エラー）とする（typo やシグネチャ変更による検査漏れを防止）。

## 決定 3 — 検査の実行形態と CLI

定数時間検査は、CLI コマンドから明示的に実行できる形態とする:

1. **CLI コマンド `sigil test --ct`（または `sigil verify --ct`）**:
   - カレントプロジェクトの `Sigil.toml` の `[testing.constant_time]` を読み取り、該当モジュールをコンパイル（SIR lower および Cranelift 最適化）した上で、静的検査（規則 R1〜R6）および CLIF 検査を実行する。
2. **外部モジュールの CI での完結**:
   - 外部モジュールのリポジトリ（例: `goodnasubi/sigil-rune-auth`）の CI において、`sigil test --ct` を実行することで、外部リポジトリ単体で定数時間保証の自動検証を完結させる。
   - Sigil 本体の `tests/ct_rules.rs` は、Sigil 本体の標準ライブラリ（`std.crypto` など）の検証に専念し、外部モジュールの関数を直接抱え込まない。

## 決定 4 — 段階的な移行と実装計画

本方針の導入は、以下の段階（3 つのステップ）で進める:

- **段階 1（初版・直近の運用）: 標準 `ct_eq` の利用規約**
  - 外部モジュール（`sigil-rune-auth` 等）は、照合処理に自前のループ等を用いず、標準ライブラリの `std.core.bytes.ct_equal` / `Secret` を直接呼び出す。
  - 処理系本体の `tests/ct_rules.rs` への外部関数の追加は行わない。
- **段階 2: 検査エンジンの共通化と CLI への統合（本 ADR の実装課題）**
  - 現在 `tests/ct_rules.rs` に密結合している静的データフロー解析（`analyze_with_table`）および CLIF 検査ロジックを、処理系ライブラリ（`src/` 配下）にリファクタリングして再配置する。
  - `Sigil.toml` の解釈と `sigil test --ct` コマンドを実装し、外部モジュール単体で検査を実行可能にする。
- **段階 3: 外部モジュールへの適用と CI 整備**
  - `sigil-rune-auth` などの外部リポジトリの `Sigil.toml` に `[testing.constant_time]` を定義し、CI に `--ct` 検査を導入する。

## 守るべきことと防ぐ脅威

| 分類 | 何から何を守るか | 対策 |
|---|---|---|
| 定数時間性 | 外部モジュール内の照合処理におけるタイミング攻撃 | SIR 上のテイント追跡（R1〜R6）と CLIF 分岐・除算検査を外部モジュールにも適用 |
| 設定ミス・漏れ | 定数時間関数の指定漏れや引数名のタイポ | 実在しない関数名や引数名の指定をエラーとして拒否 |
| リポジトリ境界 | 外部モジュールの検証が Sigil 本体のテストコード変更に依存する問題 | `Sigil.toml` によるマニフェスト登録と CLI 実行により外部単体で完結 |
| 安全の基準線 | 外部モジュールが勝手な基準で定数時間ルールを緩和すること | ADR 0020 の規則 R1〜R6、テイント伝播ルールを同一の検査器で強制 |

## 影響

- 外部モジュールの開発者は、自前で複雑なテストハーネスを書くことなく、`Sigil.toml` に宣言を追加するだけで処理系水準の定数時間保証を得られる。
- Sigil 本体側は、外部モジュールの照合関数を本体のテスト表（`tests/ct_rules.rs`）に抱え込まずに済み、リポジトリ境界の疎結合を保てる。
- 検査ロジックを `tests/` から `src/` 配下へ移管するため、コード配置の整理が必要となる（後続の実装 Issue にて対応）。

## 正式判定の問い（見張り用）

起草セッションには判定 API の認証キー `TYPESAFE_API_KEY` が無く、起草時点では判定を実施できなかった（ADR 0044・0060 と同じ）。そのため問いと評価軸を先に記録し、見張りの判定に委ねる。

評価軸（`state` の冒頭）: ADR 0001・0005・0020（定数時間検査の 3 層）・0024・0058、外部リポジトリとの疎結合、言語仕様の安定性、AI がコードを書き人間は仕様だけをレビューする方針。

- **問い 1 (RegistrationForm)**: 外部モジュールの定数時間検査の登録口をどこに置くか？
  - `manifest`: `Sigil.toml` などのプロジェクト設定ファイルで明示する（採用案）。
  - `attribute`: 言語構文に `#[constant_time]` 等の属性を追加する。
  - `test_api`: 外部モジュールのテストコードから呼ぶ API として公開する。
  - `builtin_only`: 外部モジュールの独自照合は登録せず、標準 `ct_eq` の利用に限定する。
- **問い 2 (ExecutionMode)**: 外部モジュールの定数時間検査をどのように実行するか？
  - `cli_command`: `sigil test --ct` などの CLI コマンドで実行する（採用案）。
  - `compiler_pass`: 通常のコンパイル時（`sigil build`）に常に検証する。
  - `standalone_tool`: 別個の専用ツール（`sigil-ct-check`）として配布する。
