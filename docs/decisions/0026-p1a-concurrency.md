# 0026: 並行処理 P1-a（SIR 評価器での構造化並行処理・性質の手付け・要求の隔離）

- **状態**: 提案（PR 4-1。所有者レビュー待ち）
- **日付**: 2026-11-01
- **対象**: 段階 4（並行処理 P1-a）の範囲、`Sendable`・`Shareable` を手で付ける構文、`task` の API と効果、要求の隔離の細目（[ADR 0018](0018-p1-scope.md) 決定 7 の委任分）、中断点をまたぐ借用と取り消し時の破棄の評価器での実現、評価器のスケジューリング

---

## 背景

並行処理のモデルは [ADR 0007](0007-concurrency-model.md) で決定済みである（中断を効果として扱う構造化並行処理、効果カテゴリ `task.spawn`・`task.suspend`・`task.share`、性質 `Sendable`・`Shareable`、取り消しと破棄の規則）。[ADR 0018](0018-p1-scope.md) 決定 3 は P1 の段階分けを定め、段階 4（P1-a）を「SIR の評価器での並行処理」とし、その最初の PR（4-1）を本 ADR とした。4-1 の範囲は、`Sendable`・`Shareable` を手で付ける構文、`task` の API、要求の隔離の細目である。加えて ADR 0018 決定 7 は、隔離の細目（壊れた `Lock` を待つタスク、止めたタスクの資源の後始末、確保器の整合、停止の経路での漏れ）を本 ADR で必ず決めるとした。[ADR 0016](0016-trust-base-declaration.md) 決定 7 は、性質を手で付ける構文を本 ADR で決めると委ねている。

段階 3（PR 3-7 まで）が完了した時点の処理系の現状は、次のとおりである。

- **効果カテゴリ**: `task.spawn`・`task.suspend`・`task.share` は効果の表（`src/effects.rs`）に登録済みで、`effects` 節に書け、推論と完全一致の検査も働く。ただし、その効果を起こす標準ライブラリの部品が存在しないため、利用者のコードが実際に `task.*` を起こす手段はまだない。
- **性質の判定**: `Sendable`・`Shareable` は性質として登録され、構成要素からの自動導出が働いている（構造体・列挙型はフィールドと中身から、中身を見せない標準の型は型引数から）。型引数の制約（`T: Sendable`）と、置ける位置の関数の型の捕獲検査（[ADR 0022](0022-type-identity-traits-and-function-types.md) 決定 3）にも使われている。手で付ける構文はない。
- **`Addr` を含む標準の型は `Sendable` でない**: `Addr` は `Copyable` だけを持つため、`Addr` をフィールドに持つ `String`・`List`・`Map` は、自動導出では `Sendable`・`Shareable` にならない。これらの型をタスクへ渡すには、手で付ける構文が要る（第一の利用者は標準ライブラリ自身である）。
- **評価器**: SIR の評価器は単一スレッドの解釈実行で、呼び出しは処理系（Rust）の再帰で表されている。入口だけはスタックの確保のために OS スレッドで実行する。タスクの概念はなく、異常停止は実行全体に伝播してプログラムを止める。
- **段階 3 の前提**: 標準ライブラリは Sigil 実装になり、暫定 Rust ランタイムは削除された。[ADR 0025](0025-runtime-replacement.md) 決定 2 は「P1-R の時点では単一スレッド／協調マルチタスク前提であり、確保器の関数はリエントラントにならない」ことを前提に置いている。P1-a の協調実行はこの前提と一致しなければならない。

本 ADR は ADR 0007 を改訂しない。ADR 0007 決定 6 の表の「P1-a の列」を、実装可能な細目に落とすものである。

## 決定 1: P1-a の範囲（評価器に載せるもの・載せないもの）

### 決定

**評価器に載せるもの**:

- `task` の API（決定 3）と、それを起こす効果の推論・完全一致の検査。効果の表はすでに `task.*` を持つので、表自体は変えない（ADR 0007 決定 6 の条件 4 の確かめは、API の登録によって行う）。
- `Sendable`・`Shareable` の導出結果の固定（ADR 0007 決定 2 の表）と、タスクを起動するクロージャの検査（決定 3）。
- 性質を手で付ける構文（決定 2）。
- 評価器でのタスクの実行（範囲・起動・合流・取り消し、決定 5）と、スケジューリング（決定 6）。
- 要求の隔離の評価器での機構（決定 4）。
- テスト用の実行環境の差し替え（実行順の固定と種による攪拌、仮想の時計。ADR 0007 決定 4）。
- 並行処理のサンプル（`examples/` への追加。ADR 0007 の影響では `05-concurrency` としたが、05 は制御構文のサンプルが使用済みのため、空いている番号を使う）。

**評価器に載せないもの**（段階 5 以降）:

- 状態機械への変換と、ネイティブ出力での実行の割り当て（段階 5、P1-b）。評価器ではタスクは解釈実行の状態として表し、関数の変換はしない。
- 複数の OS スレッドによる並列実行、`epoll`、スレッドの作成と原子的な操作の原始操作（PR 5-1 の範囲）。
- WebAssembly・JavaScript の実行の割り当て（P2）。
- HTTP・フレームワークなどの段階 6 の部品。それらの API の形は、本 ADR で固定する `task.*` の効果と API の上に、各段階の ADR で決める。

### 理由

- ADR 0007 決定 6 が前提にした順（P1-a で評価器に単一スレッドの実行割り当てとテスト用の差し替えを加え、P1-b でネイティブに広げる）のとおりである。意味の基準を先に評価器で固定し、P1-b はそれと突き合わせる。段階 3 で標準ライブラリの置き換えに使ったのと同じ進め方である。
- 並列実行を P1-a に入れないことで、スケジューリングは決定的にでき（決定 6）、データ競合の排除は型の検査だけに依存する（タスクが実際に同時に動くことはない）。

## 決定 2: `Sendable`・`Shareable` を手で付ける構文

[ADR 0016](0016-trust-base-declaration.md) 決定 7 の枠組み（付けられるのは信頼基盤のモジュールの型だけ、付ける箇所ごとに前提の文を必須とする）の中で、構文と検査器の扱いを決める。

### 選択肢

- **A: 型の宣言の中に節を置く**: `struct`・`enum` の宣言に `properties` の節を加える。
- **B: 独立した項目として書く**: 型とは別の項目として `properties <型名>: <性質の一覧> "<前提の文>"` を置く。
- **C: `impl` の形で書く**: `impl Sendable for <型名>` のように、トレイトの実装と同じ置き場に書く。

### 決定

**B** を採用する。

```sigil
module std.core
  targets bare, browser, server
  trust base

pub struct String {
  ptr: Addr,
  len: Int,
  cap: Int,
}

properties String: Sendable, Shareable "Addr が指す領域はこの値が所有し、他の値と共有されない。別のタスクへ移しても、同時に複数のタスクから読んでも安全である"
```

- **書式**: `properties <型名>: <性質の名前を `,` で並べたもの> "<前提の文>"`。型名は型引数を書かない（下記のとおり、手付けは無条件に付く）。
- **置ける場所**: 対象の型を宣言したモジュールの中だけとする。前提の文は空にできない（`unchecked` の前提と同じ規則）。
- **付けられる性質**: `Sendable`・`Shareable` の 2 つだけである。他の性質（`Copyable`・`Equatable` など）は書けない（エラーにする）。
- **付けられる型**: そのモジュールが信頼基盤（`trust base`）であり、許可の対象であること。それ以外のモジュールで `properties` を書くとエラーにする。
- **自動導出との組み合わせ**: 手付けは、書かれた性質についての導出を**置き換える**（宣言を正とし、その性質については構成要素を見ない）。書かれていない性質は、従来どおり導出する。導出で付く性質を手付けで取り消すことはできない（付ける方向だけを持つ）。
- **総称型**: 手付けは型引数の値によらず無条件に付く。型引数に依存する性質（例: `List<T>` の中身による違い）は導出で扱い、手付けでは扱わない。`List`・`Map` のように中身が `Addr` であっても要素の型によらず安全だと言える根拠は、前提の文に書く（バッファは値が所有し、要素の性質は要素を出し入れする操作の側の制約で担保される、など）。
- **仕様への表示**: `sigil spec` で、その型の仕様に手付けの行（付けた性質と前提の文）を出す。検査を外した箇所が仕様の読み手に見えることは、ADR 0016 の前提の文の目的である。表示の細かい形式は PR 4-2b で決める（「人間の判断が要る点」の判断 2）。
- **整形**: `sigil fmt` の正規形を持つ（性質の名前の順は、書かれた順ではなく `Sendable`、`Shareable` の固定順に並べ替える）。

### 理由

- B は型宣言の文法を変えない。A は構造体・列挙型・篩型のすべての宣言の形に節の位置を決める必要があり、文法への影響が広い。B は「付ける箇所ごとに前提を書く」という ADR 0016 の要求とも一致する（項目 1 つが付ける箇所 1 つになる）。
- C は、性質がトレイトではない（[ADR 0011](0011-type-system-scope.md) 決定 6）にもかかわらず、読み手にトレイトの実装と混同させる。

### 選ばなかった案と理由

- **A・C**: 上のとおり。
- **導出との矛盾をエラーにする案**: 手付けした性質を導出が否定する構成（`Addr` のフィールドなど）こそが手付けの用途であり、矛盾をエラーにすると使えない。検査を外すこと自体がこの構文の意味であり、安全の担保は前提の文と信頼基盤の許可に置く。

## 決定 3: `task` の API と効果

ADR 0007 決定 1〜3 で骨格が決まっている範囲・起動・合流と、決定 4 の取り消しの部品について、型名とシグネチャと効果を固定する。これらの部品はスケジューラを操作するため Sigil では書けず、検査器と評価器が知る組み込みとして標準ライブラリに登録する（`Shared`・`Cell` と同じ扱い）。P1-b では置き場がネイティブの実行の割り当てに移るが、API と効果は変えない。

### 範囲と起動・合流

| 部品 | シグネチャ | 効果 |
|---|---|---|
| `task.scope` | `fn scope<T>(f: fn(&Scope) -> T) -> T` | `task.suspend, of(f)` |
| `Scope.spawn` | `fn spawn<T>(self: &Scope, g: fn() -> T) -> TaskHandle<T>` | `task.spawn, of(g)` |
| `TaskHandle.join` | `fn join(self: TaskHandle<T>) -> T` | `task.suspend` |
| `task.all_ok` | `fn all_ok<T, E>(gs: List<fn() -> Result<T, E>>) -> Result<List<T>, E>` | `task.spawn, task.suspend, of(gs)` |
| `task.race` | `fn race<T>(gs: List<fn() -> T>) -> T` | `task.spawn, task.suspend, of(gs)` |
| `task.timeout` | `fn timeout<T>(millis: Int, g: fn() -> T) -> Option<T>` | `clock, task.spawn, task.suspend, of(g)` |
| `task.sleep` | `fn sleep(millis: Int) -> ()` | `clock, task.suspend` |
| `task.yield` | `fn yield() -> ()` | `task.suspend` |

- `Scope`・`TaskHandle` は利用者が宣言できない前置きの型とする。`Scope` は借用の引数としてだけ現れ、構造体のフィールド・戻り値・クロージャの捕獲には現れない（書くとエラーにする）。`TaskHandle` は `Sendable`・`Shareable` のどちらも持たない（導出の対象外として性質を持たない登録にする）。このため取っ手を子のタスクへ渡せず、「`join` できるのは範囲の本体（とその呼び出し先）だけ」という ADR 0007 決定 1 の規則 4 は、型の性質によって担保される。
- **起動の検査**: `spawn` に渡すクロージャは脱出するクロージャとして扱い（ADR 0007 決定 1 の規則 3）、借用をとらえていたらエラー、とらえた値の型が `Sendable` でなければエラー、戻り値の型が `Sendable` でなければエラーにする。エラーの種類は新設し、PR 4-2a で `src/error.rs` の所定の手順で加える。
- **時間の長さ**: 当面は `Int` のミリ秒とする。専用の型（`Duration` など）は導入しない（「未決として残す点」）。`task.timeout` の時間切れは `None` で表す（時間切れは異常ではなく通常の分岐であり、専用のエラー型を増やさない）。
- **一覧の効果**: `of(gs)` は、引数が関数の値の一覧であるとき、その要素の関数の効果の和を表す。これは [ADR 0004](0004-effects.md) 規則 4 の `of(f)` を一覧に広げるものであり、ADR 0004 への追記を PR 4-2c で行う。

### 共有の部品

| 部品 | シグネチャ | 効果 |
|---|---|---|
| `task.channel` | `fn channel<T>() -> (Sender<T>, Receiver<T>)` | なし |
| `Sender.send` | `fn send(self: &Sender<T>, value: T) -> ()` | `task.share, task.suspend` |
| `Receiver.recv` | `fn recv(self: &Receiver<T>) -> T` | `task.share, task.suspend` |
| `SyncShared.new` | `fn new(value: T) -> SyncShared<T>` | なし |
| `SyncShared.get` | `fn get(self: &SyncShared<T>) -> T`（`T: Copyable`） | `task.share` |
| `Lock.new` | `fn new(value: T) -> Lock<T>` | なし |
| `Lock.acquire` | `fn acquire(self: &Lock<T>) -> Result<LockGuard<T>, LockBroken>` | `task.share, task.suspend` |
| `Atomic.new` | `fn new(value: T) -> Atomic<T>` | なし |
| `Atomic.load` | `fn load(self: &Atomic<T>) -> T`（`T: Copyable`） | `task.share, task.suspend` |
| `Atomic.store` | `fn store(self: &Atomic<T>, value: T) -> ()` | `task.share` |

- 型名 `Sender`・`Receiver`・`LockGuard`・`LockBroken`・`Atomic` は本 ADR で決める。`SyncShared`・`Lock`・`Channel` の考え方は ADR 0007 決定 2 のとおりで、チャネルは送り口と受け口の型に分ける。
- **性質の導出**: `Sender<T>`・`Receiver<T>` は、`T` が `Sendable` なら `Sendable`、常に `Shareable`。`SyncShared<T>`・`Atomic<T>` は、`T` が `Sendable` かつ `Shareable` なら両方を持つ。`Lock<T>` は、`T` が `Sendable` なら両方を持つ（ADR 0007 決定 2 の表）。これらは中身を見せない標準の型の導出として登録する。
- **チャネル**: 待ち行列は無制限とし、評価器では送信は通常は待たない。ただし効果は出力先によらず一様に `task.suspend` を含む（ADR 0007 決定 3 がチャネルの送受信を中断点と定めているため）。容量を有界にするかは P1-b で再検討する（「未決として残す点」）。送り口と受け口は複製でき、参照で共有される。
- **`LockGuard`**: 取得したタスクだけが持つ値で、中身への読み書きは通常の借用の規則で行い、破棄で解放する。`LockBroken` は、壊れた `Lock`（決定 4）の取得の失敗を表す値とする。

### 理由

- 型名と効果をここで固定しないと、段階 6 の HTTP の API（`net.server` と `task.suspend` の組み合わせ）を決められない（ADR 0018 決定 3 の依存の理由）。
- 部品を組み込みとするのは、段階 2 までの標準ライブラリの追加の作法と同じであり、スケジューラと切り離して Sigil で書く方法がないためである。

## 決定 4: 要求の隔離の細目

[ADR 0018](0018-p1-scope.md) 決定 7 は「要求ごとのタスクの範囲で止める」（案 B）を採用し、細目を本 ADR に委ねた。評価器での機構と、委ねられた 4 点を決める。

### 隔離の機構（評価器）

- 評価器は、実行の単位を**ルートタスク**とする。ルートタスクは、評価器が入口として起動するタスクであり、その中で開かれる範囲と子のタスクはすべてそのルートタスクに属する。
- 異常停止（契約違反・桁あふれ・0 での除算。ADR 0018 決定 7 の範囲）は、発生したルートタスクの境界で捕まえる。そのルートタスクと子のタスクを、取り消しと同じ順序で破棄して終わらせる（決定 5）。異常停止の報告は、従来どおり標準エラーに出す。
- 1 つのルートタスクの異常停止は、他のルートタスクを止めない。評価器が複数のルートタスクを実行できることを、P1-a の完了条件のテストで固定する。
- 範囲の内側の子タスクだけを切り離して止めることはしない。異常停止は、その範囲を含むルートタスク全体を止める（取り消しと同じく、止める単位は範囲の構造に従う）。
- `sigil run` の入口は 1 つのルートタスクであり、その異常停止は従来どおりプログラム全体の異常停止として報告される（P0 からの振る舞いは変えない）。サーバーの部品が要求ごとにルートタスクを起動し、異常停止した要求に 500 を返す形は、段階 6（PR 6-3・6-4）の ADR で決める。
- スタックの枯渇と確保の失敗は、ADR 0018 決定 7 のとおりプロセス全体を止める（ルートタスクの境界で捕まえない）。

### 壊れた `Lock` を待っているタスク

- 異常停止したタスクが `Lock` を持っていた場合、その `Lock` は「壊れた」状態になる（ADR 0018 決定 7）。
- その `Lock` の取得で待っているタスクは、**起こして取得を失敗で返す**（ADR 0018 の推奨どおり）。待たせ続けると、壊れたことが永久に伝わらず、タスクが止まったままになるためである。
- 取得の失敗は `Result<LockGuard<T>, LockBroken>` の `Err(LockBroken)` で表す（決定 3）。壊れた状態を戻す手段は持たない（一度壊れた `Lock` は使い捨てとする。戻せると、壊れた前提で書かれた後始末と矛盾する）。

### 止めたタスクの資源の後始末

- 中断中・実行中のタスクを止めたとき、それが持つ資源（接続・ソケット・ファイルを含むすべての値）は、取り消しと同じ順序で破棄する（決定 5）。
- **破棄の処理は中断しない範囲で I/O をしてよい**。破棄の処理は `task.suspend` を起こせない（ADR 0007 決定 3）ため、相手の応答を待つ丁寧な終了（終了を伝えて待ち合わせること）は破棄では行えない。ソケットを閉じる、確保した領域を返す、といった同期的な後始末だけを破棄で行い、丁寧な終了は破棄の前に明示的な関数で行う。
- トランザクションの途中のデータベースの接続については、破棄で接続を閉じて捨てることができる仕組み（同期的な I/O で閉じられること）を本 ADR で用意する。接続の集まりに戻す前に巻き戻すかどうかは ADR 6-5 で決める。

### 確保器の整合

- タスクを止めるのは、中断点と異常停止の地点に限る。確保器（[ADR 0025](0025-runtime-replacement.md) 決定 3）の関数の中に中断点を置かないことは、効果の完全一致の検査によって担保される（確保器の関数は `task.*` の効果を持つ部品を呼ばないので、その関数の効果に `task.*` は現れない）。
- 確保器の関数の中で契約違反が起きないことは、確保器の前提の文に書く（ADR 0025 の前提の扱いに従う）。
- 異常停止が確保器の関数の実行中に起きた場合、その停止は隔離せず、プロセス全体を止める。評価器は、異常停止の地点が確保器の枠の中にあるかを判定して、この扱いを選ぶ。

### 停止の経路での漏れ

- 止めたタスクの値がすべて破棄されることを、テストで固定する。評価器では、タスクを止めた後にそのタスクの生きた値が残っていないことを、破棄の記録と `SIGIL_RT_LIVE`（生きている塊の数）の仕組みで確かめる（PR 4-2f の完了基準）。

## 決定 5: 中断点をまたぐ借用と、取り消し時の破棄（評価器での実現）

ADR 0007 決定 4 は「同じタスクの中では、中断点をまたぐ借用を許す」「取り消しは中断点でだけ起こり、破棄は早期の戻りと同じ順序」と決めた。評価器での実現方針を定める。

### 実行状態の持ち方

- 評価器のタスクは、**枠（フレーム）の積み重ね**を状態として持つ。枠は、関数・現在の基本ブロックと文の位置・局所の一覧である。現在の評価器の再帰による呼び出しを、この明示的な枠の積み重ねに書き換える（SIR の意味は変えない）。
- 中断が生じるのは、呼び出しの終端（タスクの部品の呼び出し、`join`、チャネルの送受信、`Lock` の取得、原子的な値の読み出し、`sleep`、`yield`）だけである。SIR では式の評価は文の中で完結し、中断点は終端にだけ現れるため、保持すべき状態は枠の単位で足りる。
- 書き換えの前後で既存のすべての事例の結果が変わらないことを、既存のテスト全件と、実行ファイルとの突き合わせ（`native-report.sh` の件数が減らないこと）で固定する。

### 中断点をまたぐ借用

- 評価器で借用は、値そのものではなく**場所**（どのタスクの、どの枠の、どの局所の、どの経路か）として解決される（現在の評価器の場所の解決の仕組みをそのまま使う）。
- 借用の参照先の枠は呼び出し元の枠であり、中断している間もそのタスクの中で生き続ける（呼び出しが終わっていないため破棄されない）。したがって借用は中断をまたいで有効であり、追加の仕組みは要らない。
- タスクをまたぐ借用は存在しない（`spawn` の検査が、借用をとらえたクロージャの起動を禁じているため）。場所が他のタスクの枠を指すことはない。

### 取り消し時の破棄

- 取り消しを要求されたタスクは、次の中断点で止まる（ADR 0007 決定 4）。評価器は、その時点の枠の積み重ねを、内側の枠から外側へ畳む。各枠では、局所を宣言の逆順に破棄する。これは、現在の評価器が異常停止と早期の戻りで行う巻き戻しと同じ手順であり、それを再利用する。
- 取り消された関数の `ensures` は評価しない（戻り値を返していないため。ADR 0007 決定 4）。
- 破棄の実行中は、そのタスクを中断させない（破棄の処理は `task.suspend` を起こせないため、中断点は現れない）。
- 異常停止でタスクを止めるときの破棄も、同じ手順である。これに合わせて、[ADR 0013](0013-termination-stdlib-and-function-values.md) の「異常停止は破棄をしてからプログラムを止める」に、要求のタスクの範囲では「破棄をしてからそのタスクの範囲を止める」と読み替える注記を加える（ADR 0018 決定 7 の予告どおり。反映は PR 4-2f で行う）。

## 決定 6: 評価器のスケジューリング方針

### 選択肢

- **A: 決定的な FIFO**: 実行可能なタスクを実行可能待ち行列で管理する。中断したタスクと、起動されたタスクは末尾に入り、先頭から動かす。
- **B: 種で選ぶ非決定な実行**: 実行可能なタスクから、乱数の種で選んで動かす。再現性は種の記録に依存する。
- **C: 実時間のスケジューリング**: 実際の時計と OS のタイマで動かす。

### 決定

**A** を評価器の既定とする。

- **切り替えの粒度**: タスクの切り替えは中断点でだけ起こる（ADR 0007 決定 5 の進行性の前提と一致する）。中断点に達しないタスクは、次の中断点か終了まで動き続ける。
- **仮想の時計**: 評価器の時計は仮想のものとする。実行可能なタスクがなく、時間待ちのタスクだけが残ったら、時計を最も早い目覚めの時刻まで進める。実時間では待たない。
- **デッドロックの検出**: 実行可能なタスクがなく、時間待ちのタスクもないのに終わっていないタスクが残っていたら、進行できない状態として異常停止で報告する（評価器が止まり続けないため）。
- **`task.yield` だけの空転（ライブロック）の検出（暫定。Issue #191・#193）**: 実行可能なタスクがすべて `task.yield` と読み出し（`Atomic.load`・`SyncShared.get`）だけを繰り返し、共有の状態（読み出し以外のタスク操作・起床・タスクの完了）が変わらず、時間待ちのタスクもいないとき、各タスクの枠の積み重ね全体の局所の中身が連続する 2 回の `task.yield` で同じなら、永久に続くとみなし、デッドロックと同じ異常停止（既存のエラー種別）で報告する。回数の上限は持たない（局所の状態が変わるループ、例えば数を数えながらの `yield` は何回でも続けてよい）。中身を完全には辿れない値（`LockGuard` を持つなど）を持つタスクは対象にしない（検出の取りこぼしはあるが、誤検出はない）。時間待ちのタスクがいる間は検出しない（仮想の時計は実行可能なタスクがなくなるまで進まないため、空転は時計待ちとしては解けない。扱いは未決）。この検出の細目は暫定であり、仕様の出力には現れない。
- **テスト用の差し替え**: 待ち行列からの選択を乱数の種で攪拌できる差し替えと、時計の差し替えを用意する（ADR 0007 決定 4 のテスト用の実行環境）。攪拌しても、許される振る舞いの範囲（順序の違いだけ）は変わらない。
- `sigil run` の既定も同じとする。実時間で待つ実行が要るかは、段階 6 のサーバーの実装で判断し、要れば時計の差し替えとして加える（「人間の判断が要る点」の判断 3）。

### 理由

- 決定的な実行は、テストの再現性と、評価器と実行ファイルの突き合わせの基準になる。AI が書くコードのテストが、実行のたびに違う順序で揺れることを避ける。
- B は、順序の違いで現れる誤りを探す用途には向くが、既定にすると通常のテストまで不安定になる。攪拌はテスト用の差し替えとして用意するのが使い分けとして正しい。
- C は評価器の目的（意味の基準とテスト）に合わない。

## 未決として残す点

- チャネルの待ち行列を有界にするか（容量と、満杯のときの送信の扱い）。P1-b の実行の割り当ての設計と合わせて決める。
- 送り口がすべて破棄された後の受信の扱い（待っている受信をどう解くか）。段階 6 でチャネルの使用実態を見て決める。
- 時間の長さの専用の型（`Duration`）を導入するか。当面は `Int` のミリ秒とする。
- 大域の可変な値を `Shareable` な型に限って許すか（ADR 0007 の未決点のまま）。
- 範囲を越えて生き続けるタスク（切り離されたタスク）を将来も持たないか（ADR 0007 の根拠の限界のまま）。

## 根拠の限界

- 評価器の呼び出しを明示的な枠の積み重ねに書き換える見積もりは、現在の評価器の構造（SIR の基本ブロックと局所）に基づく。書き換えの途中で、式の評価の途中状態を保持しなければならない箇所が見つかれば、決定 5 の実現方法を見直す。
- 決定的な FIFO のスケジューリングは、評価器での意味の固定には向くが、実際のサーバーの負荷の偏りは表さない。P1-b の実行の割り当ての性能は、段階 5・6 で測る。
- 手付けの第一の利用例（`String`・`List`・`Map`）の前提の文が正しいかは、標準ライブラリの実装が「バッファを値が所有し共有しない」ことに依存する。前提が崩れる変更が標準ライブラリに入ると、手付けの正しさも崩れる。これは信頼基盤のレビューで扱う。
