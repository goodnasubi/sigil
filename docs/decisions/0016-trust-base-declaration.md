# 0016: 信頼基盤（`trust base`）の宣言方法と、検査を外した箇所の契約の書き方

- **状態**: 承認（2026-10-26。所有者が決定。）
- **実装**: PR1（構文と表示。#55）と PR2（検査・`--trust-base`・`sigil spec` の 2 行・既存テストの移し替え）で実装済み。`stdlib::RAW_OPS` は空で、テストは `effects::Options.raw_ops` にテスト用の原始操作を足して検査する。`tests/trust_base.rs` に完了条件の表のテストと、`--trust-base` のコマンドラインの事例（`*_cli`）、原始操作の登録の誤り（`raw_op_without_premise_rejected`・`duplicate_raw_op_rejected`）を置いた。

## 背景

検査を外す仕組み（Rust の `unsafe` に相当）について、これまでの ADR は次のことを決めた。

- [ADR 0005](0005-long-term-goals.md) の決定 3:
  - 検査を外せるのは **信頼基盤** のモジュールだけとする。信頼基盤は、標準ライブラリ・ランタイム・処理系が生成するコード・プラットフォーム層からなる。
  - 信頼基盤であることは、モジュールの宣言で明示する。
  - 検査を外した各箇所には、安全である前提を契約として書くことを必須とする。人間はコードを読まないので、この前提が人間に示される唯一の情報になる。
- [ADR 0008](0008-m0-notation.md) の決定 6: モジュールの宣言の `trust none | base` の表記を決めた。宣言できる範囲と契約の書き方は、本 ADR に引き継いだ。
- [ADR 0014](0014-core-and-os-split.md) の決定 5: `trust` と `bare` は独立した 2 つの軸で、互いの規則を免除しない。
- [ADR 0006](0006-p0-scope-and-bootstrap.md) の条件 12 と [ADR 0007](0007-concurrency-model.md) の規則 8:
  - 大域の可変な値は持たない。
  - 標準ライブラリの内部の大域の状態（乱数・実行の割り当て）は信頼基盤の例外とし、タスクをまたいで安全である前提を契約に書く。
- ADR 0007 の「基本の型」: `Sendable`・`Shareable` を検査を外して手で付けるのは、信頼基盤に限る。
- [ADR 0015](0015-m5-native-output.md) の決定 9: 本 ADR は M5 の後、P1 の範囲を決める ADR の前（暫定ランタイムを Sigil に置き換える前）に書く。

M5 は完了した（main `be945bd`）。暫定ランタイムを Sigil の信頼基盤のモジュールに置き換えるには、その前に本 ADR が要る（ADR 0006 の「置き換えの時期」）。

### 現状（main `be945bd`）

- `trust` は構文として読むだけで、検査器での意味はない。
  - `sigil spec` は「信頼基盤: はい / いいえ」を表示する。
  - 複数のファイルを合わせるときは、`trust` も宣言の一致（`ModuleMismatch`）の対象になる。
  - 利用者のファイルも `trust base` と書け、書いても何も変わらない。
- 検査を外す操作は、言語にまだ 1 つもない。
  - 標準ライブラリは Rust の表（`src/stdlib.rs`）で、検査器には `trust base` の仮のモジュール（`std.core`・`std.os`）として読ませている。
  - 本体はインタプリタ・SIR の評価器の組み込みと、Rust の暫定ランタイム（`runtime/core`・`runtime/os`）が持つ。
- モジュールどうしの参照はない。宣言がすべて同じファイルだけを合わせられる。「モジュールの単位」の ADR は未決である（DESIGN.md の 5 章）。
- 文法に大域の宣言はない（項目は `type`・`struct`・`enum`・`fn`・`impl` だけ）。条件 12 は文法で満たしている。
- 検査器には、テスト用の差し込み口（`effects::Options` の `primitives`・`copy_override`）がある。

## 本 ADR で決めないこと

- **原始操作の実際の一覧**（決定 1 の表の中身）: 確保・番地の読み書き・システムコールのどれを、どの型で置くかは、暫定ランタイムを置き換える設計と一緒に P1 の範囲を決める ADR で決める。**[ADR 0018](0018-p1-scope.md) の決定 6** が一覧と実行の方式を決めた。本 ADR は、表の形と、表に載った操作を使う規則だけを決める。
- **モジュールをまたぐ公開の範囲**: 信頼基盤のモジュールの関数のうち、どれを他のモジュールから呼べるかは、「モジュールの単位」の ADR で決める。
- **大域の状態の構文**（決定 5）と、**性質を手で付ける構文**（決定 7）: 規則だけを決め、構文はそれを必要とする P1 の ADR で決める。大域の状態の構文は確保器が要るので、[ADR 0018](0018-p1-scope.md) の決定 8 のとおり ADR 3-1 で決める（本 ADR は P1-b としていたが、前に出す）。性質を手で付ける構文は ADR 4-1 で決める。

## 評価の観点

重要な順に並べる。

1. **人間が仕様だけで前提を知れるか**: 検査の外にある前提が、`sigil spec` に人間が読める形で現れること（ADR 0005）。
2. **検査を外せる範囲が最小で、黙って広がらないか**: コードを書く AI が、同じ変更の中で自分に検査を外す権利を与えられないこと。
3. **通常の検査を弱めないか**: 型・移動・借用・効果の検査が、信頼基盤の中でもできるだけそのまま働くこと。
4. **AI が誤りなく書けるか・実装量**
5. **後の段階で作り直さずに済むか**: P1 のランタイムの置き換え、P6 のプラットフォーム層に、同じ仕組みで足りること。

## 決定 1: 「検査を外す」ことの中身

### 選択肢

- **A: 原始操作の方式**。検査器が安全を示せない操作を、標準ライブラリの表に **原始操作**（名前空間 `raw`）として置く。「検査を外す」とは、原始操作を呼べることだけを指す。型・移動・借用の検査は、信頼基盤の中でも外さない。
- **B: 区間の方式**。`unchecked { ... }` の中では、所有権と借用の検査を止める。
- **C: モジュールの方式**。`trust base` のモジュールでは、所有権と借用の検査をしない。

### 決定

**A** を採用する。

- 原始操作は、標準ライブラリの新しい表 `RAW_OPS` に置く。各行は次の列を持つ。
  - 層（`Layer`。ADR 0014）
  - シグネチャ（`raw.名前(...)` の形）
  - 効果（決定 4）
  - 実行時に検査する `requires`（式で書ける前提）
  - **前提の文**（式で書けない前提。日本語、空にできない）
- 番地を表す型 `Addr` を、核の層の中身を見せない型として置く。`Copyable` で、演算子は持たない。番地の計算も原始操作で行う。
- 原始操作の表の行を足す・変える・消すことは、ADR に記録してから行う。効果のカテゴリを足すときと同じ手続きである（ADR 0005 の決定 3）。
- `raw` は予約名に加える。式の中では原始操作の名前空間を指し、利用者は同じ名前の関数・変数・引数・型を定義できない（ADR 0009 の決定 4 の予約名と同じ扱い）。
- 表の形の例を示す。行の中身は確定ではなく、P1 の範囲を決める ADR で決める。

| 層 | シグネチャ | 効果 | `requires` | 前提の文 |
|---|---|---|---|---|
| 核 | `alloc(size: Int, align: Int) -> Addr` | `none` | `size > 0 && align > 0` | `align` は 2 のべき乗である |
| 核 | `read_int(a: Addr) -> Int` | `none` | `none` | `a` は生きている確保の中の、8 バイトに揃った番地である |
| 核 | `write_int(a: Addr, v: Int)` | `state` | `none` | 同上。`a` を通して読む値が他にない |
| OS | `syscall(n: Int, a: Int, b: Int, c: Int) -> Int` | 宣言に委ねる | `none` | 引数は Linux x86-64 の該当するシステムコールの規約に従う |

### 理由

- 観点 3: A は、通常の規則を 1 つも止めない。仕組みとしては、呼べる操作の集合が信頼基盤の中だけ広がるだけである。Rust の `unsafe` も、借用の検査を止めずに、生のポインタの逆参照と `unsafe fn` の呼び出しを許すだけである。
- 観点 1: 原始操作ごとに表が前提の文を持つので、検査を外した箇所すべてに前提がある状態が、表の単体テストで保てる。
- 観点 5: P1 のランタイムの置き換え（確保・番地の読み書き・システムコール）も、P6 のプラットフォーム層（ポートの入出力・割り込み）も、表に行を足すだけで書ける。

### 選ばなかった案と理由

- **B（区間の方式）**: 区間の中で `Shared`・`Cell` の不変条件が検査されなくなり、検査を外した影響が、区間の外の値にも及ぶ。どの前提が何を守るのかを、仕様の表示で示しにくい。
- **C（モジュールの方式）**: 信頼基盤のモジュール全体が検査の外になり、最小に保つ（ADR 0005）ことに反する。

## 決定 2: 検査を外す関数の印と、前提の書き方

### 選択肢

- **A: 関数の節**。契約節の最後（`effects` の後）に `unchecked "前提の文"` を書いた関数だけが、原始操作を呼べる。
- **B: 式の区間**。`unchecked "前提の文" { ... }` の区間の中だけで原始操作を呼べる。
- **C: 印を置かない**。`trust base` のモジュールの中なら、どこでも原始操作を呼べる。前提は原始操作の表のものだけを使う。

### 決定

**A** を採用する。

- **表記**:
  - `effects` の節の次の行に `unchecked "…"` と書く。文字列は空にできない（`intent` と同じ規則）。
  - `unchecked` は予約語に加える。整形器は、この節を他の契約節と同じ字下げで出す。
  - この節は省ける。他の 4 節と違って、書かないことは「原始操作を呼ばない」を意味する。すべての関数に `unchecked none` を書かせると、原始操作を使わない 99% の関数に読む価値のない行が増えるからである。
- **書ける場所**:
  - `trust base` のモジュールの関数だけが書ける。それ以外で書くとエラー `UncheckedOutsideTrustBase` になる。
  - `impl` の中のメソッドにも書ける。
- **原始操作を呼べる場所**:
  - `unchecked` の節を持つ関数の本体で、直接呼ぶときだけ。それ以外はエラー `RawOutsideUnchecked` になる。
  - クロージャの本体の中では呼べない。クロージャは関数の外へ持ち出されて後で呼ばれうるので、関数の前提の文が守る範囲を越えるからである。
  - 原始操作は、関数の値として取り出せない（変数に入れる・引数に渡すことはできない）。同じく、前提の文が守る範囲の外で呼ばれうるからである。
  - 呼べるかどうかは、原始操作を呼ぶ式を含む関数の定義で決める。`unchecked` のない総称の関数の本体は、`unchecked` の関数から呼ばれても原始操作を呼べない。
  - 契約の式（`requires`・`ensures`・篩型の条件）の中でも呼べない。
- **安全な包みの規則**:
  - `unchecked` の関数は、自分の `requires` が成り立つかぎり、どこから呼ばれても安全でなければならない。
  - 前提の文には、本体の原始操作の前提が `requires` とモジュールの不変条件からなぜ成り立つかを書く。
  - 呼び出し側は、通常の関数と同じに呼ぶ。呼び出し側には印も前提も要らない。
  - 呼び出し側が前提を守る義務を負う関数（Rust の `unsafe fn`）は置かない。人間が、関数をまたいで義務の受け渡しを追う必要が出るからである。P1 で必要になった場合は、「モジュールの単位」の ADR（公開の範囲）と一緒に決める。
- **`requires` と `ensures`**:
  - 通常どおり、実行時に検査する（ADR 0006 の決定 5）。
  - 原始操作の表の `requires` も、呼び出しの入口で実行時に検査する。

例:

```
fn read_first(xs: &Words) -> Int
  intent "整数の並びの先頭の値を読む"
  requires xs.len > 0
  ensures none
  effects none
  unchecked "xs.base は Words.new が確保し、len 個の Int を書いた領域を指す（Words の不変条件）。len > 0 なので先頭は確保の中にある"
{
  return raw.read_int(xs.base);
}
```

### 理由

- 観点 1: 契約は関数の単位で人間に示している（`sigil spec`）。前提の文も同じ単位に置けば、関数の仕様の 1 行として読める。
- 観点 4: 関数の単位なら、前提の文と `requires` が同じ場所に並び、両者の関係（`requires` で何を確かめ、残りを何が守るか）を書きやすい。
- B は箇所の粒度は細かいが、区間の前提と関数の `requires` との関係が仕様の表示で離れる。
- C は、前提の文を書く場所がない。表の前提は操作ごとの一般論で、この関数でそれがなぜ成り立つかを書けないため、ADR 0005 の「各箇所に前提を書く」を満たさない。

### 選ばなかった案と理由

- **B（式の区間）**: 上のとおり。1 つの関数に区間が複数あると、仕様に前提が何行も並び、どの区間のものか分からない。必要になれば、関数を分けて A で書ける。
- **C（印なし）**: 上のとおり。

## 決定 3: `trust base` を宣言できる範囲

### 選択肢

- **A: 誰でも宣言できる**。ソースの宣言だけで決まる。`sigil spec` に出るので、人間のレビューで止める。
- **B: 名前で限る**。`std.` などで始まる名前のモジュールだけが宣言できる。
- **C: 処理系の外で人間が許す**。
  - 処理系に同梱する標準ライブラリ（`std.` で始まるモジュール）は、常に許す。
  - それ以外は、検査・実行・組み立ての呼び出しで、`--trust-base <モジュール名>` に名前を挙げたモジュールだけを許す。オプションは繰り返し書ける。
  - 挙げていないモジュールが `trust base` と宣言すると、エラー `TrustBaseNotAllowed` になる。

### 決定

**C** を採用する。

- ライブラリの関数では、`effects::Options` に `trust_base: Vec<String>`（許すモジュール名の一覧）を加える。`check`・`run`・`build` の各経路は、これを検査器に渡す。
- 利用者のファイルが `std` または `std.` で始まる名前のモジュールを宣言すると、エラー `ReservedModuleName` にする。今は止めていないので、新しく加える検査である。標準ライブラリの名前を使って許可をすり抜けられないようにするためである。標準ライブラリの仮のモジュールは、処理系が内部で読むソースなので対象外とする。
- `sigil spec` は許可を検査しない。宣言を表示するだけである（決定 6）。
- テスト用の原始操作は、`effects::Options` に `raw_ops`（`primitives` と同じ差し込み口）を加えて渡す。本 ADR の時点では標準ライブラリの `RAW_OPS` は空で、テストの中だけで定義する（ADR 0006 の「テスト用の性質・カテゴリ・型はテストの中だけで定義し、標準ライブラリには入れない」）。

### 理由

- 観点 2: コードを書くのは AI である。A では、AI が検査を外す権利を、使うのと同じ変更の中で自分に与えられる。`sigil spec` には出るが、大きな仕様の 1 行を人間が見落とせば通る。B も、名前を選ぶのは AI である。
- C は、許可をソースの外の、小さくめったに変わらない 1 か所（ビルドの呼び出し）に置く。その変更を人間の確認の対象にできる。
- 観点 4: オプション 1 つと検査 1 つで足り、パッケージの設定ファイル（まだない）を先に作らずに済む。

### 選ばなかった案と理由

- **A（誰でも）**、**B（名前で限る）**: 上のとおり。
- **パッケージの設定ファイルに一覧を書く案**: 設定ファイルの形式が未決である（P1 でリリースの単位を決めるときに決める）。そのときに、一覧の置き場所をそこへ移すかを見直す（下の再検証）。

## 決定 4: `unchecked` の関数で残す検査

- **型・移動・借用**: 外さない。`Addr` は `Copyable` な値なので、番地の先の値の所有と借用は検査器に見えない。そこを守るのが前提の文である。
- **契約**: 外さない。実行時に検査する（決定 2）。
- **層と出力先**（ADR 0014）: 外さない。原始操作も層を持つ。OS の層の原始操作（システムコールなど）は、`bare` を含むモジュールからは呼べない（`OsItemInCore`）。条件 10 はそのまま成り立つ。
- **効果**: 原則は外さない（推論と宣言の完全な一致。ADR 0004 の規則 3）。例外は次の 1 つだけである。
  - 原始操作のうち、起こす作用が引数で決まるもの（システムコール）は、表の効果の列を **宣言に委ねる** とする。
  - 宣言に委ねる原始操作を呼ぶ関数に限り、検査は「宣言した効果が、推論した効果をすべて含む」とする。宣言には、推論より多い効果があってよい。
  - 宣言に委ねる原始操作を呼ばない `unchecked` の関数は、完全な一致のままとする。
  - 委ねた効果が正しいことは、前提の文に書く。
  - 宣言が推論より多い（過大な宣言）ことは、検査では誤りにしない。代わりに `sigil spec` が、宣言した効果と推論した効果の差を表示する（決定 6）。人間は、その差が前提の文で説明されているかをレビューする。
- **大域の可変な値の禁止**（条件 12）: 決定 5 のとおり、構文がまだないので外さない。

## 決定 5: 大域の状態（条件 12 の例外）

### 選択肢

- **A: 今、大域の宣言の構文を加える**。`trust base` のモジュールに限り、大域の可変な値を宣言できる。
- **B: 大域の宣言の構文は置かず、静的な領域を原始操作で確保する**。
- **C: 規則だけを決め、構文はそれを使う ADR（P1-b の実行の割り当て・乱数）で決める**。

### 決定

**C** を採用する。次の規則を、構文を決める ADR が従う前提として固定する。

1. 大域の可変な状態を持てるのは、`trust base` のモジュールだけである。通常のモジュールで禁止すること（条件 12）は変えない。
2. 大域の状態を読み書きする関数は、すべて `unchecked` の関数とする。前提の文には、タスクをまたいで安全である理由（ADR 0007 の規則 8）と、スレッドごとの領域に値を隠さないこと（ADR 0007 の根拠の限界）を書く。
3. 大域の状態の値の型は、P1-a で入る `Sendable`・`Shareable` の判定に従う。判定を外して置く場合は、規則 2 の前提の文に理由を書く。

### 理由

- 今、大域の状態を必要とする利用者はいない。乱数と実行の割り当ては P1 で入る。
- 安全の前提の中心になるスレッド間の共有の型（`SyncShared`・`Lock`。ADR 0007）が、まだない。構文をその前に決めると、型の判定と食い違うおそれがある。
- B は、大域の状態を番地の読み書きで表すので、型の検査が働かず、決定 1 の「通常の検査を弱めない」に反する。

## 決定 6: 仕様の表示

`sigil spec` に次を加える。人間は、これを見て検査の外の前提をレビューする。

- `unchecked` の関数の「効果:」の行の次に、2 行を加える。
  - `検査を外す: <前提の文>`
  - `使う原始操作: raw.名前（前提: <表の前提の文>）, ...`。本体から呼ぶ原始操作を、名前の順に重複なく並べる。検査器の解決結果から機械的に作る。
- 宣言に委ねる原始操作を呼ぶ関数（決定 4 の効果の例外）では、さらに 1 行を加える。
  - `推論できない効果: <宣言した効果のうち、本体から推論されなかったもの>`。差がなければ `なし` と出す。
  - これを出すために、`sigil spec` は、この行を持つ関数についてだけ検査器の効果の推論を呼ぶ。検査が失敗したファイルでは、この行を `（検査のエラーのため表示できない）` とする。同じ理由（この行を持つかどうかも分からない）で、`使う原始操作:` の行も同じ placeholder にする。
- モジュールの行の「信頼基盤: はい」に、検査を外す関数の数を添える（`信頼基盤: はい（検査を外す関数 2 個）`）。
- 前提の文が正しいかどうかは、処理系では確かめられない。人間のレビュー（仕様の表示を読むこと）で補う。どの変更でレビューを必須にするかは、許可の運用と一緒に P1 の範囲を決める ADR で決める（「人間の判断が要る点」）。

## 決定 6 の補足: エラーの優先順位

1 つのファイルに複数の違反があるとき、検査器は次の順に調べて、最初の 1 つを報告する（検査器は最初のエラーだけを返す）。

1. `ReservedModuleName`（モジュールの宣言）
2. `TrustBaseNotAllowed`（モジュールの宣言）
3. 関数ごとに、ソースの順で次を調べる。
   1. `UncheckedOutsideTrustBase`（節）
   2. 本体の型・名前の解決。ここで原始操作の呼び出しに `RawOutsideUnchecked` を報告する。層の検査の `OsItemInCore` も、名前の解決の中で、同じ式について `RawOutsideUnchecked` の後に調べる。
   3. 移動・借用の検査
   4. 効果の照合（決定 4 の例外を含む）

`std.x` の名前で `trust base` を宣言し、許可もないファイルは、`ReservedModuleName` を報告する。

## 決定 7: 性質を手で付けること

ADR 0007 の「基本の型」の性質（`Sendable`・`Shareable`）を、検査を外して手で付けることについて決める。

- 付けられるのは、`trust base` のモジュールの型だけである。
- 付ける箇所ごとに、決定 2 と同じく空にできない前提の文を必須とする。
- 構文は、2 つの性質を加える P1-a の ADR で決める。

## 実装の手順

1. **PR1: 構文と表示**
   - 字句と構文: `unchecked` を予約語にし、`raw` を予約名にする。`FnDecl` に `unchecked: Option<String>` と節の行を加える。
   - 予約の衝突を確かめる。リポジトリの Sigil のソース（`examples/` と、テストの中の Sigil のソースの文字列）に、識別子としての `raw`・`unchecked` がないことを確かめ、PR に記録する。main `be945bd` の時点では見つからない（Rust のコードの `raw` という名前は対象外）。
   - 整形器と `sigil spec`。決定 6 のうち、`検査を外す:` の行と、モジュールの行の関数の数。
   - 上の表のうち、`tests/fmt.rs`・`tests/errors.rs`・`tests/spec.rs` の事例。
   - **PR1 だけが入った状態の動き**: `unchecked` の節は構文としては読めるが、検査器は節を持つ関数をすべて `Unsupported`（「`unchecked` の検査は未実装（ADR 0016 の PR2）」）で止める。節を書いたプログラムが、検査なしで通る期間を作らないためである。`raw` は予約名になるが、原始操作の表はまだないので、`raw.x(...)` は今と同じく `UnknownName` になる。`trust base` の許可の検査もまだないので、`trust base` の扱いは今と同じである。
2. **PR2: 検査**
   - `effects::Options` に `trust_base`・`raw_ops` を加え、`stdlib::RAW_OPS`（空）と `Addr` を加える。
   - 決定 2〜4 の検査（`UncheckedOutsideTrustBase`・`TrustBaseNotAllowed`・`ReservedModuleName`・`RawOutsideUnchecked`、効果の例外）。
   - `sigil spec` の `使う原始操作:` と `推論できない効果:` の行（決定 6。検査器の解決結果と効果の推論が要るので PR2 で入れる）。
   - CLI の `--trust-base`。`tests/trust_base.rs`。
   - 既存のテストの移し替え。利用者のソースで `trust base` と書いているテストを洗い出し、PR に一覧を記録する。main `be945bd` では、`tests/m4_core_split.rs` の `core_trust_base_still_rejects`（`trust_base` に名前を挙げて、同じ `OsItemInCore` になること）と、`tests/spec.rs` の `trust base` の事例（`sigil spec` は許可を検査しないので変えない）である。
   - PR1 で入れた `Unsupported` の止めを外す。

## 人間の判断が要る点

- 依存の追加・CI の変更・秘密情報は要らない。
- **所有者の決定（2026-10-26）**: `--trust-base` の許可の運用は、[ADR 0018](0018-p1-scope.md) の「所有者の決定（2026-10-26）」の判断 1（T3: 許可の一覧を 1 つのファイルに置き、`CODEOWNERS` とブランチの保護で所有者のレビューを必須にし、CI で信頼基盤の差分を検出する）と判断 2（S2: レビューを必須にする範囲）で決めた。決める前は、許可の一覧が人間の確認を通るのは、その呼び出しを書いたファイル（CI の設定やビルドの手順）の変更を人間が確認する場合だけだった。
  - 本 ADR の時点では、標準ライブラリの `RAW_OPS` は空である。利用者のプログラムが実際に検査を外す手段はまだないので、運用が決まる前に許可の一覧が広がっても、安全性は損なわれない。

## 根拠の限界と再検証

- 候補の案出しと採点を、同じ者（Claude）が行っており、偏りがありうる。
- 原始操作の表の形は、P1 のランタイムの置き換えと P6 のプラットフォーム層を想像して決めたもので、実際に書いた原始操作で試していない。P1 で、暫定ランタイムの機能（`console`・`fs`・確保）を Sigil で書いたとき、次のどれかに当たったら決定 1・2 を見直す。
  - 前提の文を、関数の単位で書けない箇所が多い。
  - 呼び出し側が前提を守る義務を負う関数がないと書けない。
  - 宣言に委ねる効果の例外が、システムコール以外にも要る。

### 段階 3 完了時の見直し記録（2026-11-01、PR 3-7）

ADR 0018 および ADR 0025 に基づく段階 3（ランタイムの置き換え P1-R、PR 3-2 〜 PR 3-7）の完了に伴い、決定 1・2 の見直しを行った。

1. **前提の文を関数の単位で書けない箇所**:
   - 発生しなかった。標準ライブラリ核（`String`, `List`, `Map`）および OS 依存部分（`Console`, `Path` 等）の Sigil 実装において、メモリ操作およびシステムコール発行（`SYS_write` 等）の事前条件・前提をすべて各関数の `unchecked` 節に過不足なく記述できた。
2. **呼び出し側が前提を守る義務を負う関数（Rust の `unsafe fn` 相当）の必要性**:
   - 不要であった。`unchecked` 関数内部で引数の整合性検査や不変条件の維持を行う安全な包みの規則（決定 2）が完全に機能し、外部呼び出し元に安全性の前提義務を課すことなく完結した。
3. **宣言に委ねる効果の例外**:
   - `raw.syscall` のみで過不足なく成立し、それ以外の原始操作はメモリ読み書き・確保・解放を含め「効果なし（プロセス外から不可視）」として一貫して扱うことができた。

したがって、決定 1（原始操作の方式）および決定 2（関数の `unchecked` 節の方式）の仕様は極めて適切に機能しており、**変更や見直しは不要である**と結論した。

- 決定 3 の許可は、ビルドの呼び出しを AI が書き換えれば効かない。P1 の範囲を決める ADR で、許可の運用（所有者の決定）と、一覧の置き場所（パッケージの設定ファイルに移すか）を決める。許可の運用は [ADR 0018](0018-p1-scope.md) の判断 1・2（T3・S2）で決まった。
- 前提の文の正しさは、処理系では確かめられない。人間のレビューで補う（決定 6）。
- 次を計測する。
  - P1 の完了時に、`unchecked` の関数の数と、原始操作の呼び出しの数を数える。信頼基盤が最小に保たれているかを、ADR 0005 の方針に照らして確かめる。
  - 前提の文のうち、後で誤りが見つかったものの数。
