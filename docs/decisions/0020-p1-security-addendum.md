# 0020: P1 のセキュリティの追補（定数時間・ファジング・公開前のレビュー・DoS の上限）

- **状態**: 承認（2026-10-26。所有者の委任を受けて Claude が決定。）CI の変更・依存の追加・権限の設定に当たる 3 項目（W1〜W3）は **所有者承認（2026-10-26「推奨どおり」）**: W1=C1（定期の実行を CI に加える）、W2=D1（`cargo-fuzz` は加えない）、W3=O2（`CODEOWNERS` に表と上限の既定値だけ）。W1 と W3 は PR 1-7 で実装した。
- **委任の記録**: 所有者は 2026-10-26 の会話で、ADR の起草から決定までの自律的な進行を Claude に委任した（コーディネーター経由の指示）。本 ADR の「承認」はこの委任による。

## 背景

[ADR 0018](0018-p1-scope.md) は、P1 で HTTP サーバー・PostgreSQL の接続・認証・暗号の基本部品を Sigil で書き、サービスをコンテナでリリースすることを決めた。所有者は、暗号を Sigil で実装すること（判断 6a）、PostgreSQL は SCRAM-SHA-256 で平文の通信にすること（判断 6b）、API は HMAC で署名したベアラートークンで認証すること（判断 6c）、TLS は前段で終端すること（判断 5）を決めた。

ADR 0018 は、次のことを決めずに残した。

- 判断 6a の注記: 「定数時間の比較が、Cranelift の最適化の後も定数時間であることは、生成コードを見なければ確かめられない。ADR 6-1 で確かめ方を決める」。
- 外から来る入力（HTTP・PostgreSQL の応答・トークン・言語サーバーの要求）を壊れた形で与えたときの確かめ方。
- サービスを外へ公開してよいかを、誰が何を見て決めるか。
- 1 つの接続や要求が資源を使い切ることへの上限。

本 ADR は ADR 0018 の追補として、これらを P1 の全体の方針として決める。各段階の ADR（6-1・6-3〜6-6 など）は、本 ADR の決定を自分の完了条件に含める。

### 現状（main `f9427f2`）

- **依存**: `Cargo.toml` の依存は、所有者が承認した Cranelift の 4 クレート（`=0.137.0`）だけである。
- **CI**（`.github/workflows/ci.yml`）: `push`（main）と `pull_request` で、`cargo fmt`・`clippy`・`cargo test`・`scripts/native-report.sh`・`runtime/` の検査を走らせる。権限は `contents: read` である。定期の実行（`schedule`）はない。
- **ファジング**: ない。
- **入力の上限**:
  - `src/json.rs`（ADR 0019 の PR1）は、入れ子の深さを `MAX_DEPTH = 128` に限る。
  - 構文解析（`src/parser.rs`）は再帰で下り、入れ子の深さに上限がない。深い入れ子の入力で、スタックを使い切りうる。
- **整数とビット演算**: `Int` は 64 ビットの符号付きで、桁あふれは異常停止である（ADR 0011）。ビット演算（論理積・論理和・排他的論理和・シフト）は、演算子にも標準ライブラリにもない。SHA-256 と定数時間の比較は、ビット演算なしには書けない。
- **時間切れ**: ADR 0007 は `task.timeout` を定めたが、中断点のない長い計算は取り消せない（ADR 0007 の未決点）。
- **異常停止の範囲**: ADR 0018 の決定 7 で、契約違反は要求のタスクの範囲で止め、スタックの枯渇と確保の失敗はプロセス全体を止める。外からの入力でスタックを使い切れると、1 件の要求でサービス全体が止まる。

## 本 ADR で決めないこと

- 暗号の部品・HTTP・PostgreSQL・認証の API の形。各段階の ADR で決める。
- 設定の名前（環境変数の名前など）。ADR 6-4（フレームワーク）で決める。本 ADR は既定値と、上限を超えたときの動きだけを決める。
- TLS と、P1 で作らない機能（ADR 0018 の決定 2 の「行わないこと」）の安全。
- W1〜W3 は所有者が推奨どおりに承認した（2026-10-26）。

## 評価の観点

重要な順に並べる。

1. **秘密が漏れないか**: 鍵・パスワード・署名が、時間・ログ・エラーの応答から漏れないこと。
2. **1 件の悪い入力でサービスが止まらないか**: 壊れた入力・大きな入力・遅い接続で、プロセスが止まったり、資源を使い切ったりしないこと。
3. **確かめ方が仕組みになっているか**: 人の注意に頼らず、テストか検査で毎回確かめられること。
4. **依存と設定を増やさないか**: ADR 0005 の方針（既存言語のライブラリを持ち込まない）と、所有者の承認の要る変更を最小にすること。
5. **段階の順序を崩さないか**: ADR 0018 の段階 0〜7 の依存の関係を変えないこと。

## 決定 1: 暗号の定数時間の実装

### 対象

定数時間で動くことを求める関数（以下 **定数時間の関数**）は、次のとおりとする。どれも ADR 6-1・6-5・6-6 で書く。

| 関数 | 秘密の値 | 公開の値 |
|---|---|---|
| バイト列の比較 `ct_eq(a, b)` | `a`・`b` の中身 | 長さ |
| SHA-256 の圧縮関数 | 入力の塊・内部の状態 | 塊の数 |
| HMAC-SHA256 | 鍵・内部の状態 | 入力の長さ |
| PBKDF2-HMAC-SHA256 | パスワード・途中の値 | 塩・回数・出力の長さ |
| SCRAM の計算（`ClientKey`・`StoredKey`・`ClientProof` の排他的論理和、`ServerSignature` の照合） | パスワードから導いた鍵・署名 | 塩・回数・ナンス |
| ベアラートークンの署名の照合 | 署名の鍵・期待する署名 | トークンの長さ |

- 比較の結果（一致したかどうか）は公開の値とする。比較の後で分岐してよい。
- 同じ SHA-256 をイメージの digest（公開のデータ）にも使う。定数時間の関数を公開のデータに使うことは妨げない。
- 環境変数から読んだ鍵の符号化（base64 など）を解くのは、起動の時に 1 回だけである。これは定数時間の関数の対象から外す（解く時間は、起動の時に 1 回しか観測できない）。
- 定数時間を求めるのはネイティブの出力だけである。SIR の評価器は、読み書きのたびに範囲を確かめるので、定数時間ではない。評価器はテストに使い、サービスを動かすのには使わない。

### 規則（静的な規則）

定数時間の関数の中で、秘密の値（と、秘密の値から計算した値）について、次を禁じる。

- **R1 分岐**: `if`・`match`・くり返しの条件・`&&`・`||` の短絡・早期の `return` の条件にすること。
- **R2 番地**: 一覧の添字・表の鍵・番地の計算に使うこと（表を引く S-box 型の実装を禁じる）。
- **R3 割り算**: `/`・`%` の左右に置くこと（x86-64 の割り算の命令は、値によって時間が変わる）。
- **R4 呼び出し**: 定数時間の関数でない関数に渡すこと。ただし、長さを返す関数（`len`）と、R5 のビット演算は除く。
- **R5 演算**: 使ってよいのは、加算・減算・乗算・ビット演算（論理積・論理和・排他的論理和・シフト・回転）・比較の結果を値として持つこと（分岐に使わない）だけとする。
- **R6 外への出力**: `console` などで出力すること、エラーの文に含めること。

R1 の例外として、桁あふれの検査（ADR 0011）の分岐は許す。この分岐は、正しく動く限り常に同じ側に進み（あふれれば異常停止）、時間は値によらない。SHA-256 の 32 ビットの加算は、64 ビットの `Int` で足してから下位の 32 ビットを取り出せば、あふれない。

### 確かめ方

静的な規則（主）と計測（従）の 2 つで確かめる。合流を止めるのは静的な規則だけとする。

1. **SIR の上の検査**（`tests/ct_rules.rs` の `ct_rules_static`）
   - 定数時間の関数の一覧を、このテストの中の表に置く。表の各行は、関数の名前と、公開の値とする引数の名前を持つ。表にない引数はすべて秘密とする。
   - lowering の後の SIR で、秘密の値の流れを追い、R1〜R6 に当たる使い方を見つけたら失敗にする。
   - **領域を経由する流れ（ADR 6-1 の必須事項）**: 秘密の値を書いた `Bytes`・一覧・構造体の領域から読んだ値は、読んだ位置によらず秘密とする（保守的な規則）。領域の中の位置ごとに区別して追うことはしない。`Secret` の型の中身も秘密とする。これにより、秘密を `Bytes` に一度書いてから読み直す経路で、流れが途切れない。
   - **表への載せ忘れ（ADR 6-1 で決める）**: 定数時間であるべき関数を表に載せ忘れると、検査が働かない。ADR 6-1 で、表に載せることを必須にする関数の決め方を、次のどちらか（または両方）に決める。
     - 命名の約束（例: 名前が `ct_` で始まる関数と、暗号の部品のモジュールの公開の関数）。
     - 公開の API で `Secret` の型を受け取る関数。
     決めた規則に当たるのに表にない関数があれば、`ct_rules_static` を失敗にする。
   - 言語に「秘密」を表す構文は足さない。性質を手で付ける構文は ADR 4-1 で決める（ADR 0018 の決定 8）。そこで構文ができたら、表を構文に移すかを見直す。
   - 違反を 1 つずつ埋め込んだ関数（早期の `return`・表を引く・`%` を使う・定数時間でない関数を呼ぶ）を、テストの中に置く。どれも失敗になることを確かめる。

2. **最適化の後の Cranelift の中間表現の検査**（`ct_rules_clif`）
   - 定数時間の関数ごとに、Cranelift の最適化の前と後の中間表現を比べる。
   - 最適化の後の条件分岐（`brif`・`br_table`）の数が、前の数を超えないこと。異常停止へ進む分岐は数えない。SIR の上の検査で、最適化の前の分岐はすべて公開の値によることを確かめているので、最適化が分岐を足さなければ、出力も規則を守る。
   - 割り算の命令（`sdiv`・`udiv`・`srem`・`urem`）が 1 つもないこと。
   - `select` は、機械語で条件付きの転送（`cmov`）になり、分岐にならない。Cranelift の版を上げたときは、このテストと計測をやり直す。
   - 数を比べるだけでは、最適化が分岐を 1 つ消して別の 1 つを足した場合（分岐の入れ替わり）を見落とす。**ADR 6-1 の検討項目**として、最適化の後の中間表現で、各条件分岐の条件の値の出所を追い、秘密の引数（と、秘密の領域から読んだ値）に由来しないことを確かめる方法を検討する。SIR の上の流れの追跡を中間表現に移すことになり、費用が見合えば数の比較に代えて入れる。入れない場合は、その理由を ADR 6-1 に書く。

3. **計測**（`ct_measure`。`#[ignore]` のテストで、通常の `cargo test` では走らせない）
   - dudect の方法による。固定の入力と乱数の入力の 2 組を交互に並べ、ネイティブで各組 100 万回の時間を測り、Welch の t 値を求める。
   - |t| が 4.5 未満なら、時間の差は見つからなかったとする。
   - 同じ手順で、わざと定数時間でない比較（最初の違うバイトで戻る）を測り、|t| が 4.5 を超えることも確かめる（陽性の対照）。陽性の対照で差が出ないときは、その計測は雑音が大きすぎて意味を持たないとし、記録だけ残す。
   - 時間は、Sigil の計測用のプログラムが単調な時計（ナノ秒）で、まとまった回数ずつ測る。集計は Rust のテストの側で行う。
   - 計測するのは、ADR 6-1 の完了の時、Cranelift の版を上げた時、決定 3 の公開の関門の時である。結果（t 値・回数・計測した機械）は ADR 6-1 に記録する。
   - CI の定期の実行に入れるかは、W1 で所有者に問う。

### 秘密の値の扱い

- ADR 6-1 で、秘密のバイト列を入れる型（例: `Secret`）を設ける。この型は、表示（`Displayable`）を実装しない。また、破棄の時に中身を 0 で上書きしてから解放する。上書きが最適化で消えないことは、`ct_rules_clif` と同じ方法（最適化の後の書き込みの命令の数）で確かめる。
- エラーの文・ログに、鍵・パスワード・`Authorization` の見出しの値を含めない。これを公開の関門（決定 3）の確認の項目にする。
- 署名の鍵（判断 6c）は、32 バイト未満なら起動の時に失敗にする。
- トークンの署名の方式は HMAC-SHA256 に固定する。トークンが方式の名前を持っていても、それを読んで方式を選ばない（`alg` の欄を使う攻撃を防ぐ）。署名を確かめるまでは、トークンの中身（利用者の情報など）を読まない。
- SCRAM の回数（サーバーが送る値）は 4096 以上 10 万以下に限り、外れたら接続を失敗にする。下限は RFC 7677 の推奨に合わせた。上限は、悪いサーバーが接続のたびに大きな計算をさせることを防ぐ。
  - 接続を確立するまでの時間の上限（5 秒、決定 4）は、PBKDF2 の計算を含む。ADR 0007 で、時間切れは中断点でだけ効く。中断点がないと、回数の大きい PBKDF2 は時間切れで止められず、その間、同じ OS スレッドの他のタスクも止まる。
  - そこで、**PBKDF2 のくり返しの中で、決まった回数（例: 1024 回）ごとに `task.yield` を呼ぶことを ADR 6-1 の完了条件にする**。呼ぶ時期はくり返しの回数（公開の値）だけで決まるので、定数時間の規則を破らない（R4 は秘密を渡すことを禁じるもので、引数のない `task.yield` は当たらない）。`task.yield` は段階 4 で入るので、ADR 6-1 が段階 4 より前に合流するときは、段階 4 の後の PR で入れる。
  - ADR 6-5 で、回数が 4096 と 10 万のときの接続の確立の時間を実測し、記録する。10 万で 2.5 秒（接続の時間の上限の半分）を超えるときは、本 ADR を改訂して上限を下げる。

### 前提として要るもの

- **ビット演算**: ADR 2-5（`Bytes`）で、`Int` のビット演算（論理積・論理和・排他的論理和・左右のシフト・回転）と、`Bytes` の 1 バイトの読み書きを入れる。
  - どれも 1 つの Cranelift の命令（`band`・`bor`・`bxor`・`ishl`・`ushr`・`sshr`・`rotl`・`rotr`）になり、分岐を含まないこと。
  - シフトの量は `requires 0 <= n && n < 64` とする。この検査の分岐はシフトの量（公開の値）による。
  - 演算子にするか関数にするかは ADR 2-5 で決める。

### 理由

- 観点 1: 比較で最初の違うバイトで戻ると、何バイト目まで合っているかが応答の時間に出る。署名の照合でこれが起きると、署名を 1 バイトずつ当てられる。
- 観点 3: 計測は機械と負荷で結果が揺れ、CI の共用の機械では偽の失敗が出る。規則の検査は毎回同じ結果になるので、合流の止めにはこちらを使う。ただし、規則は Cranelift の最適化と機械語の性質（`cmov` が分岐にならないこと）を前提にする。この前提を計測が補う。
- 観点 4: 言語に構文を足さず、テストの中の表と SIR の検査で済ませる。

### 選ばなかった案と理由

- **計測だけで確かめる**: 上のとおり、合流の止めにできない。
- **生成した機械語を逆アセンブルして調べる**: 逆アセンブラの依存が要る（観点 4）。Cranelift の中間表現で同じことを確かめられる。
- **型で秘密を表す構文（`secret Int` など）をすぐ足す**: 型検査と効果の検査に広く手が入る。ADR 4-1 の「性質を手で付ける構文」と一緒に決める方が、後戻りしない（観点 5）。

## 決定 2: ファジング

### 対象と、確かめる性質

| 対象 | 実装 | 段階 | 確かめる性質 |
|---|---|---|---|
| JSON の読み取り（`src/json.rs`） | Rust | 1 | 異常停止（`panic`）しない。読めた値は、書き出して読み直すと同じ値になる。深さが `MAX_DEPTH` を超えたらエラーになる |
| 字句解析・構文解析・検査 | Rust | 1 | `panic` しない。スタックを使い切らない。構文解析が通った入力は、`fmt` の出力も構文解析が通り、`fmt` を 2 回かけても変わらない |
| 言語サーバーの枠（`Content-Length`） | Rust | 1（ADR 0019 の PR2 の後） | `panic` しない。壊れた見出しと大きすぎる長さは、決定 4 の上限どおりに扱う |
| HTTP の要求の解釈 | Sigil | 6（6-3） | 下の「Sigil の対象の性質」 |
| フレームワークの JSON の読み取り（Sigil で書く場合） | Sigil | 6（6-4） | 同上。加えて、読めた値の書き出しと読み直しが一致する |
| PostgreSQL のサーバーからの通信文 | Sigil | 6（6-5） | 同上 |
| SCRAM の通信文（`server-first`・`server-final`） | Sigil | 6（6-5） | 同上 |
| ベアラートークンの解釈 | Sigil | 6（6-6） | 同上。署名の合わないトークンは、中身によらず同じ失敗になる |

**Sigil の対象の性質**:

- 解釈の関数は、どの入力にも `Ok` か `Err`（値）を返す。契約違反・桁あふれ・範囲の外の読み書き・スタックの枯渇は、どれも誤り（不具合）とする。外からの入力が悪いことは `Err` で表し、異常停止で表さない。
- 同じ入力について、SIR の評価器とネイティブの出力の結果が一致する（突き合わせ）。評価器は読み書きの範囲を確かめるので、ネイティブで見えない範囲の外の読み書きが、評価器で異常停止として見える。
- 入力の長さや入れ子に比例して深く再帰しない。入れ子を持つ形式（JSON など）は、深さの上限を持つ（決定 4）。

### 方法（依存を加えない自前のファジング）

- 乱数は、自前の小さな生成器（splitmix64 など）で作る。乱数の種を決めれば、同じ入力の列が再現できる。
- 入力の作り方は次の 3 つを組み合わせる。
  - ランダムなバイト列。
  - 種の入力（`tests/fuzz/corpus/<対象>/`）を変異させる。ビットの反転、バイトの挿入・削除、他の種との継ぎ合わせ、塊のくり返し（深い入れ子を作る）、境目の値（0・255・`Int` の最大値・`\r\n`・`\r` だけ・`\n` だけ）を入れる。
  - 形式の文法から組み立てる。Sigil の構文、JSON、HTTP の要求の骨組みを作り、その一部を壊す。
- HTTP の種には、要求の密輸の既知の形を必ず入れる。`Content-Length` と `Transfer-Encoding` の両方を持つもの（CL.TE・TE.CL）、`Transfer-Encoding` の値を崩したもの（大文字・空白・重複。TE.TE）、値の違う `Content-Length` の重複、分割した転送の大きさの行の崩れ。どれも決定 4 の規則どおりに拒まれることを確かめる。
- 誤りを見つけたときは、乱数の種と何番目の入力かを出し、入力を `target/fuzz-failures/<対象>/` に書き出す（スタックの溢れのように、プロセスが止まる誤りの扱いは「構文解析の深さの上限」に書いた）。直した PR で、その入力を小さくして `tests/fuzz/regress/<対象>/` に加え、以後は毎回走らせる。
- **短い実行**（合流を止める）:
  - 通常の `cargo test` の中で、種を固定して、対象ごとに決まった回数だけ走らせる。
  - 回数は、CI で増える時間が全体で 60 秒以内になるように、各 PR で測って決める。時間は、CI の 3 か所の `cargo test`（処理系・`runtime/core`・`runtime/os`）の合計の、PR の前後の差で測る。超えたら回数を減らす（CI の設定は変えない）。
  - 種を固定するので、毎回同じ結果になり、偽の失敗は出ない。
- **長い実行**（新しい誤りを探す）:
  - 同じテストを、環境変数（例: `SIGIL_FUZZ_ITERS`・`SIGIL_FUZZ_SEED`）で回数と種を変えて走らせる。
  - 走らせる場所（手で走らせるか、CI の定期の実行に入れるか）は W1 で所有者に問う。W1 の結論が出るまでは、各段階の対象を加えた PR と、公開の関門（決定 3）の時に、手で 30 分以上走らせ、回数・種・結果を PR に記録する。
- Sigil の対象は、Rust のテストから SIR の評価器で解釈の関数を呼ぶ。ネイティブとの突き合わせは、入力をまとめてファイルで渡し、1 回のビルドと 1 回の実行で多数の入力を処理する。

### 構文解析の深さの上限

**実装の記録（PR 1-6）**: 上限は **128** にした。当初の案の 256 は、2 MiB のスタックの debug ビルドで全段を通せなかった（下の「測ったこと」）。新しい `ErrorKind` は加えない（超えたときの `ErrorKind::TooDeep` はすでにあるので、それを使う）。

- 構文解析の入れ子の深さを 128 に限る（`src/parser.rs` の `MAX_DEPTH`）。超えたら `TooDeep`（構文のエラー）にする。深さは、式・型・パターン・ブロック・単項演算の入れ子と、`.`・`(...)`・`?` の連鎖、二項演算の連鎖、`else if` の連鎖を 1 つにつき 1 段と数える。括弧 1 組は 2 段を使う。
- **利用者向けの制限（数え方）**: 二項演算の連鎖（`a + b + c ...`）、メソッド・呼び出し・`?` の連鎖（`a.f().g()?...`）、`else if` の連鎖も 1 つにつき 1 段と数える。したがって 1 つの式に並べられる項は約 128 まで（129 項目でエラー）。括弧は 1 組で 2 段なので、括弧の入れ子は約 64 組まで。超えたら `TooDeep` で、式を `let` で分けて書く。
- 128 は、既存のファイルの最も深い入れ子（`examples/04-effects/effects.sigil` の 19）の 6 倍以上で、人や AI が書く入れ子には十分である。
- **測ったこと**: 2 MiB のスタックのスレッドで `check` を通すと、単項演算の入れ子は 256 段で溢れた（2.8 MiB を超え、3 MiB 以内で通る）。192 段でも溢れ、160 段と 128 段で通った。そこで 128 を選んだ。上限は「全段が 2 MiB で通る最大の深さ」より小さく取る（debug ビルドが最悪の条件）。
- **完了条件**: 深さがちょうど上限の入力（式の括弧・単項演算・型・ブロック・`match` の入れ子のそれぞれ）が、`check`・`fmt`・lowering・`run`（SIR の評価器）・`build`（ネイティブ）のすべての段を、2 MiB のスタックのスレッドで通るテスト `depth_limit_all_phases`（`tests/depth_limit.rs`）を置いた。上限の 1 つ上は `TooDeep` になることも確かめる。通らない段があれば、その段の再帰をくり返しに直すか、上限を下げる。
- **整形の誤りの修正**: このテストで、整形の固定点の誤りが見つかった。すべての腕が `return` だけの入れ子の `match` 文を、整形が式の `match`（`return match ... ;`）に畳むとき、内側を畳まず外側だけ畳んでいたため、整形が固定点にならず `FmtVerify` になった。内側の `match` も式に畳むように直した（`src/fmt.rs`）。畳んだ式の深さの数え方は文と異なり、上限を超えるときは、落ちずに `FmtVerify` か `TooDeep` のエラーになる（`depth_limit_fmt_fold_is_an_error_not_a_crash`）。
- **スタックの溢れの扱い（決定: 事前の書き出しと固定スタックのスレッドの併用）**: Rust でスタックが溢れると、`catch_unwind` で捕まえられず、プロセスが止まる。次のようにした（`tests/common/fuzz.rs`）。
  - 各入力を、処理する前に `target/fuzz-failures/<対象>/current` に書き出す。止まったら、そのファイルが原因の入力になる。正常に終われば消す。
  - 全体を、決まった大きさ（2 MiB）のスタックのスレッドで回す。テストのスレッドの既定と同じで、主スレッドの 8 MiB より厳しい条件で確かめる。
  - 子プロセスで処理する案は選ばなかった: 入力ごとの起動で短い実行が 60 秒に収まらない。溢れを親が見て書き出す利点は、事前の書き出しで足りる（`current` が残る）。
  - 普通の panic は `catch_unwind` で捕まえ、`target/fuzz-failures/<対象>/fail-<種>-<番号>` に書き出して、種と番号を出して失敗にする。

### 理由

- 観点 2: HTTP と PostgreSQL の解釈は、P1 で外から来る入力を最初に読むコードで、ここの誤りがそのままサービスの停止になる。ADR 0018 の決定 7 で、スタックの枯渇はプロセス全体を止めるので、再帰の深さは特に確かめる。
- 観点 3: 種を固定した短い実行を毎回の `cargo test` に入れれば、CI の設定を変えずに合流を止められる。
- 観点 4: 自前の生成器は数百行で書け、依存も CI の変更も要らない。
- 評価器との突き合わせは、ADR 0018 の決定 6 で評価器が範囲を確かめるようにしたことを、ファジングの判定にそのまま使える。これは、外部のファジングの道具（libFuzzer など）には、Cranelift の出力の網羅の情報を渡せないので、代わりにならない利点である。

### 選ばなかった案と理由

- **`cargo-fuzz`（libFuzzer）を今入れる**: 依存の追加と nightly の Rust が要る。網羅の情報で探す力は強いが、使えるのは Rust の対象（処理系）だけで、P1 で外から来る入力を読む Sigil の対象には使えない。W2 で所有者に問う。
- **性質に基づくテストのクレート（proptest など）**: 依存の追加が要り、自前の生成器に比べて得るものが小さい。
- **ファジングをしない**: 観点 2 を満たせない。

## 決定 3: 外部公開の前のセキュリティレビュー

### 「外部公開」の定義

次のどれかに当たることを外部公開とする。

- Sigil で作ったサービスを、所有者が管理しない網（インターネットなど）から届く場所に置く。
- 実在の利用者のデータ（個人の情報・認証の情報）を扱う。

CI と、手元のコンテナでサンプルのサービスを動かすことは、外部公開に当たらない。リポジトリを公開していることも当たらない。

### 関門と担当

| 関門 | 時期 | 実施 | 承認 | 見るもの |
|---|---|---|---|---|
| G1: 段階の ADR の脅威の節 | ADR 6-1〜6-6 の各 ADR | ADR を書く者（Claude） | ADR のレビュー（通常どおり） | 各 ADR に「脅威と対策」の節を置く。入力・認証・秘密・資源の 4 つについて、何から何を守るか、本 ADR のどの決定で守るかを書く |
| G2: 段階の完了の確認 | PR 6-1・6-3・6-5・6-6 の最後の PR | 実装者 | PR のレビュー | 決定 1 の検査、決定 2 の対象の追加と短い実行、決定 4 の上限のテストが入っていること |
| G3: 公開の前のレビュー | PR 7-1 の後、外部公開の前 | 実装者と別の Claude のセッション（レビュー役） | **所有者**が報告を読み、公開してよいかを決める | 下の確認の項目 |

- G3 は、P1 の完了（PR 7-1）の後、最初に外部公開する前に 1 回行う。その後は、暗号・認証・HTTP・PostgreSQL の解釈のコードを変える版を公開する前に、変わった部分について行う。
- レビュー役は、実装した会話の記録を読まずに、リポジトリと本 ADR だけからレビューする。結果は `docs/security/` の下に、日付と対象の版（コミットの番号）を持つ報告として残す。
- 所有者が承認しない限り、外部公開しない。外部の専門家のレビューを加えるかは、実在の利用者のデータを扱う公開の前に、所有者がその時に決める。

### G3 の確認の項目

1. **定数時間**: `ct_rules_static`・`ct_rules_clif` が通る。直近の計測（`ct_measure`）の結果が記録されており、陽性の対照で差が出ている。
2. **ファジング**: 全対象で長い実行を 1 時間以上走らせ、未解決の誤りがない。
3. **上限**: 決定 4 の表の各行のテストが通る。設定で上限を外せない（無制限の値を受け付けない）。
4. **秘密**: リポジトリと CI の設定に、鍵・パスワードがない（`git log -p` を秘密の形で検索する）。ログとエラーの応答に秘密が出ない。鍵が短いと起動が失敗する。
5. **認証**: フレームワークの経路は、明示して外さない限り認証を求める（既定で拒否）。認証を外した経路の一覧を報告に載せる。
6. **エラーの応答**: 500 の本文は固定の文で、内部の情報（契約違反の文・位置）を含めない。内部の情報は標準エラーにだけ出す（ADR 0018 の決定 7）。
7. **HTTP の解釈の規則**: 決定 4 の「入力の解釈の規則」が守られている。
8. **信頼基盤**: 原始操作の表・`unchecked` の関数・許可の一覧の変更が、ADR 0018 の判断 1・2 のレビューを通っている。
9. **依存**: `Cargo.lock` に、承認した依存（Cranelift の 4 クレートとその依存）のほかがない。Cranelift の版について、RustSec の公開の勧告の一覧に該当がないことを手で確かめる。
10. **イメージ**: イメージの設定で、実行する利用者が root でない数の ID になっている。イメージには実行ファイル 1 つのほかに、シェルなどの実行できるものがない（ADR 6-2 で入れる）。

### 理由

- 観点 1・2: P1 では、AI が書いて AI がレビューしたコードが、初めて外の入力を受ける。人間はコードを読まない（ADR 0005）ので、所有者が判断に使える材料（報告と確認の項目）が要る。
- 実装者と別のセッションにレビューさせるのは、同じ者が書いて確かめる偏りを減らすためである。それでも同じ型の AI であることの偏りは残る（「根拠の限界」）。
- G1・G2 を段階ごとに置くのは、G3 で初めて見つかると、後戻りが大きいからである（観点 5）。

### 選ばなかった案と理由

- **G3 だけを置く**: 上のとおり。
- **G3 に外部の専門家を必須にする**: 費用が見合うかは、公開の規模と扱うデータによる。所有者がその時に決める。

## 決定 4: DoS の上限

### 方針

- 上限は、HTTP のライブラリ・フレームワーク・PostgreSQL の接続の部品が、既定値を持つ。
- 設定で値を変えられるが、上限を外す（無制限にする）値は受け付けない。設定の名前と読み方は ADR 6-4 で決める。
- 起動の時に、接続数と大きさの上限から、最悪の場合のメモリの使用量（下の式）を標準エラーに出す。
- 既定値を変えるときは、本 ADR を改訂する。

### 既定値（HTTP サーバー）

| 上限 | 既定値 | 超えたときの動き |
|---|---|---|
| 要求の行（メソッド・対象・版）の長さ | 8 KiB | 414（対象が長い）か 400 を返して接続を閉じる |
| 見出しの部分の全体の大きさ | 16 KiB | 431 を返して接続を閉じる |
| 見出しの数 | 100 | 431 を返して接続を閉じる |
| 本文の大きさ（`Content-Length` か、分割した転送の合計） | 1 MiB | 413 を返して接続を閉じる。`Content-Length` が上限を超えるときは、本文を読まずに返す |
| 分割した転送の大きさの行の長さ | 1 KiB | 400 を返して接続を閉じる |
| 同時の接続の数 | 256 | 上限にある間は、新しい接続を受け付けない（`accept` を呼ばない）。待ち行列（`listen` の backlog）は 128 |
| 見出しを読み終えるまでの時間 | 10 秒（接続の受け付け、または前の応答の送信の終わりから） | 408 を返して接続を閉じる |
| 本文を読み終えるまでの時間 | 30 秒 | 408 を返して接続を閉じる |
| 要求の処理の時間（ハンドラ） | 30 秒 | 取り消して 503 を返す |
| 応答を送り終えるまでの時間 | 30 秒 | 接続を閉じる |
| 接続を保ったまま待つ時間 | 60 秒 | 接続を閉じる |
| 1 つの接続の要求の数 | 1000 | 応答に `Connection: close` を付けて閉じる |
| URL の問い合わせの欄の数 | 100 | 400 を返す |
| JSON の本文の入れ子の深さ（フレームワーク） | 64 | 400 を返す |
| ベアラートークンの長さ | 4 KiB | 401 を返す |
| 応答の本文の大きさ | 1 MiB | ハンドラの誤りとして、500 を返し、標準エラーに記録する |

- 1 つの接続の要求は 1 件ずつ処理する。応答を送り終えるまで、次の要求を読まない。
- 要求の行は、見出しの部分の全体の大きさに数えない（要求の行は 8 KiB、見出しの部分は 16 KiB の別の上限）。
- 分割した転送の後に付く見出し（トレーラー）は、見出しの部分の全体の大きさと見出しの数に、要求の見出しと合わせて数える。トレーラーの値はハンドラに渡さず捨てる。
- `Expect: 100-continue` は、見出しの上限と本文の大きさ（`Content-Length`）の検査を通ったときだけ、`100 Continue` を送ってから本文を読む。本文の大きさが上限を超えるときは、`100 Continue` を送らずに 413 を返す。`100-continue` 以外の `Expect` は 417 で拒む。
- **前段の前提**: サービスの前には、TLS を終端する中継（逆向きの代理）がある（ADR 0018 の判断 5）。上限と解釈の規則は、前段が要求を正しく区切って転送するとは仮定せず、サービスの側だけで守れるように決めた。前段が付ける見出し（`X-Forwarded-For` など）を信じるかは、ADR 6-4 で決める。既定では信じない。
- 最悪の場合のメモリの使用量は、上限から次の式で見積もる。
  - HTTP: 同時の接続の数 ×（見出しの上限 + 本文の上限 + 応答の本文の上限 + 1 つのタスクの大きさ）= 256 ×（16 KiB + 1 MiB + 1 MiB + S）≈ 516 MiB + 256 × S。
  - PostgreSQL: 接続の集まりの大きさ ×（結果の全体の上限 + 通信文の上限）= 10 ×（16 MiB + 4 MiB）= 200 MiB。
  - 合計は、既定値で約 716 MiB + 256 × S である。S（1 つのタスクのスタックか状態の大きさ）は ADR 5-1 で決まるので、ADR 5-1 で式に値を入れる。
  - この式は、ハンドラが自分で作る値（作業の領域）を含まない。それは利用者のコードに依る。
  - コンテナのメモリの上限は、この合計より大きくする。足りないときは、同時の接続の数か本文の上限を下げる。
- 要求の処理の時間の上限は `task.timeout`（ADR 0007）で実装する。中断点のない長い計算は取り消せないので、この上限は中断点でだけ効く。CPU を長く使う処理を書くときは `task.yield` を挟む。これは ADR 0007 の既知の制限で、G3 の報告に、中断点のない長い計算を持つ経路があるかを書く。

### 既定値（PostgreSQL の接続）

| 上限 | 既定値 | 超えたときの動き |
|---|---|---|
| サーバーからの 1 つの通信文の長さ | 4 MiB | 接続を捨て、問い合わせを失敗にする |
| 1 つの問い合わせの結果の全体の大きさ | 16 MiB | 同上 |
| 接続を確立するまでの時間 | 5 秒 | 失敗にする |
| 問い合わせの時間 | 30 秒 | 接続を捨て（接続の集まりに戻さない）、失敗にする |
| 接続の集まりの大きさ | 10 | — |
| 接続の集まりから接続を得るまで待つ時間 | 5 秒 | 失敗にする（フレームワークは 503 を返す） |
| SCRAM の回数 | 4096 以上 10 万以下 | 接続を失敗にする（決定 1） |

### 既定値（処理系と言語サーバー）

| 上限 | 既定値 | 超えたときの動き |
|---|---|---|
| 構文解析の入れ子の深さ | 128（実装済み） | 構文のエラー（`TooDeep`。決定 2） |
| JSON の入れ子の深さ（`src/json.rs`） | 128（実装済み） | エラー |
| 言語サーバーの `Content-Length` | 64 MiB | 読まずに捨て、エラーの応答を返して続ける。続けられない（枠が崩れた）ときは終了する |
| 言語サーバーの見出しの 1 行の長さ | 1 KiB | 同上 |

### 入力の解釈の規則（ADR 6-3 で必ず入れる）

要求の密輸（前段とサービスで要求の区切りの解釈が食い違うこと）を防ぐため、HTTP の解釈は RFC 9112 の厳しい側に倒す。

- `Content-Length` と `Transfer-Encoding` の両方を持つ要求は、400 で拒む。
- 値の違う `Content-Length` が複数あれば、400 で拒む。
- `Transfer-Encoding` は `chunked` だけを受け付け、それ以外は 501 で拒む。
- 見出しの折り返し（行頭の空白で続ける古い書き方）は 400 で拒む。
- 行の終わりは `\r\n` だけを受け付け、`\n` だけの行と、見出しの名前の前後の空白は 400 で拒む。
- 解釈できない要求の後は、接続を閉じる（続く要求の区切りを信じない）。

### 理由

- 観点 2: 上限がないと、遅い接続（見出しを少しずつ送る）や大きな本文で、接続やメモリを使い切れる。ADR 0018 の決定 7 で確保の失敗はプロセス全体を止めるので、メモリの上限は特に要る。
- 値は、広く使われる HTTP サーバーの既定値と同じ桁にした。P1 のサンプルのサービス（小さな JSON の API）には十分で、足りないときは設定で上げられる。
- 上限を外す値を受け付けないのは、設定の誤り 1 つで守りがなくなることを防ぐためである。

### 選ばなかった案と理由

- **上限を利用者のコードに任せる**: 利用者（AI）が毎回書くことになり、書き忘れが起きる。
- **同時の接続の数の上限を超えたら、受け付けてすぐ閉じる**: 受け付けの処理自体に資源を使う。受け付けを止めれば、カーネルの待ち行列が溢れた分だけ、相手に失敗が返る。

## 所有者承認の項目（W1〜W3）

**所有者承認済み（2026-10-26「推奨どおり」）: W1=C1、W2=D1、W3=O2。** 以下は、選んだ案と選ばなかった案の記録である。実装は W1 が `.github/workflows/fuzz.yml`、W3 が `.github/CODEOWNERS`（`tests/ct_rules.rs` と、上限の既定値の置き場所の予定のパス `src/limits.rs`。ADR 6-3 で置き場所が決まったら合わせる）。fuzz.yml の actions はコミットの SHA で固定し、定数時間の計測（`ct_measure`）は ADR 6-1 でテストが加わるまで飛ばす。

CI の設定の変更・依存の追加・権限の設定は所有者の承認が要る（ADR 0006・0018）。次の 3 つは、承認が出るまで始めない。どれも、承認されなくても本 ADR の他の決定は成り立つ（手で走らせて記録する運用で代える）。

### W1: 定期の長い実行を CI に加えるか（CI の変更）

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| C1 | 新しいワークフロー（`.github/workflows/fuzz.yml`）を加える。1 日 1 回の `schedule` と手動の起動（`workflow_dispatch`）で、ファジングの長い実行（対象ごとに数分、全体で 30 分以内）と、定数時間の計測（`ct_measure`）に加え、release ビルドでの `depth_limit_all_phases`(`cargo test --release --test depth_limit`)も走らせる(debug より最適化でスタックの使い方が変わるため)。権限は `contents: read` だけで、秘密は使わない。計測の結果は記録として出すだけで、ジョブを失敗にしない | 人が忘れても毎日探す。種を日ごとに変えるので、探す範囲が広がる | Actions の実行時間を使う。失敗しても通知を受ける人が要る。共用の機械での計測は雑音が大きい |
| C2 | CI に加えず、決定 2・決定 1 の時期に手で走らせて記録する | CI の設定が増えない | 走らせ忘れる。段階の間に入った誤りが、次の手での実行まで見つからない |
| C3 | 長い実行を、PR ごとの CI に入れる | PR の前に見つかる | すべての PR が数十分遅くなる |

**推奨: C1**。ファジングは長く走らせるほど見つかるもので、PR の時間を延ばさずに走らせ続けられるのは定期の実行である。計測をジョブの失敗にしないのは、共用の機械の雑音で偽の失敗が出るからである。始める時期は PR 1-6 の合流の後とする。

### W2: `cargo-fuzz`（libFuzzer）を加えるか（依存の追加）

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| D1 | 加えない。自前のファジング（決定 2）だけにする | 依存も nightly の Rust も要らない | 網羅の情報で探す力がない。深い分岐の奥の誤りが見つかりにくい |
| D2 | `fuzz/` に別のクレートを置き、`libfuzzer-sys` を依存にする（処理系の本体の依存には入れない）。nightly の Rust で、W1 の定期の実行の中で走らせる | 処理系（JSON・字句・構文）を網羅の情報で探せる | 依存と nightly の Rust が増える。Sigil の対象（HTTP・PostgreSQL）には使えない |
| D3 | 性質に基づくテストのクレート（proptest など）を開発用の依存に加える | 入力の生成と縮小が楽になる | 依存が増える。自前の生成器で足りる |

**推奨: D1**（今は加えない）。P1 で外から来る入力を読むのは Sigil の対象で、libFuzzer はそれに使えない。処理系への入力は、開発者と AI が書くソースと、手元の編集器からの要求で、外から来ない。ただし、自前のファジングで処理系の対象に誤りが続けて見つかる（例: 3 か月で 5 件以上）なら、D2 を改めて問う。

### W3: 暗号・認証・解釈のコードを `CODEOWNERS` に加えるか（権限の設定）

ADR 0018 の判断 1（T3）で、信頼基盤の置き場所を `CODEOWNERS` で所有者に割り当てた。本 ADR の対象のコードは、信頼基盤でない（検査を外さない）ので、そこに含まれない。

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| O1 | 暗号の部品・認証・HTTP と PostgreSQL の解釈の置き場所と、`tests/ct_rules.rs` の表を `CODEOWNERS` に加え、所有者のレビューを必須にする | 定数時間の関数の表から関数を外すなど、守りを弱める変更を所有者が必ず見る | 所有者のレビューの数が増える。段階 6 の PR の多くが対象になる |
| O2 | `tests/ct_rules.rs` の表と、上限の既定値の置き場所だけを加える | 守りを弱める変更に絞って見られる | 解釈のコードの変更は所有者が見ない |
| O3 | 加えない。G2・G3 の関門だけにする | 設定が増えない | 表から関数を外す変更が、AI のレビューだけで合流しうる |

**推奨: O2**。人間はコードを読まない前提（ADR 0005）なので、所有者が見て意味がある変更は、守りの範囲を変えるもの（表と上限の値）である。解釈のコードの正しさは、ファジングと上限のテストが確かめる。加える時期は、PR 1-6（表がまだない場合は PR 6-1）の合流の後とする。

## 根拠の限界と再検証

- 候補の案出しと採点を、同じ者（Claude）が行っており、偏りがありうる。G3 のレビュー役も同じ型の AI で、同じ見落としをしうる。
- 決定 1 の `ct_rules_clif` は、「最適化が分岐を足さない」ことと「`select` が機械語で分岐にならない」ことを前提にしている。Cranelift がこの前提を破る変換をしても、分岐の数が同じなら見落とす（分岐を 1 つ消して別の 1 つを足す場合）。計測がこれを補うが、計測は雑音に弱い。Cranelift の版を上げるたびに計測をやり直す。条件の値の出所を中間表現で追う方法は、ADR 6-1 で検討する（決定 1）。
- 決定 2 の自前のファジングは、網羅の情報を使わない。文法から組み立てる入力の質に頼る。PR 1-6 以降、見つけた誤りの数と、それを見つけた入力の作り方（ランダム・変異・文法）を記録し、どの作り方が効いているかを見直す。
- 決定 4 の既定値は、他の HTTP サーバーの既定値と同じ桁にしただけで、Sigil のサービスで測っていない。PR 6-3・6-5 で、既定値の上限ちょうどの負荷でメモリの使用量を測り、決定 4 の式と比べて記録する。
- 要求の処理の時間の上限は、中断点のない計算に効かない（ADR 0007）。この制限が問題になるか（CPU を長く使う要求があるか）は、P1 のサンプルのサービスでは分からない。
- 次を計測する。
  - ファジングで見つけた誤りの数（対象ごと、短い実行と長い実行の別）。
  - 定数時間の計測の t 値の推移（Cranelift の版ごと）。
  - G3 で見つかった問題の数と、それがどの関門（G1・G2）で見つけられたはずか。
