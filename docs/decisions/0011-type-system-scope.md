# 0011: 型システムの範囲（M1 の前）

- **状態**: 承認（2026-10-25。決定 10 に、関数の値を置ける場所と `let` の別名の効果の規則を追記。所有者の委任を受けて Claude が決定。計測による再検証の条件は末尾を参照）

## 背景

[ADR 0006](0006-p0-scope-and-bootstrap.md) の決定 4 の表は、「型システムの範囲」を M1（名前解決・型検査・効果の推論と一致検査）の前に決める論点としている。型検査器が総称型・篩型・性質（ADR 0006 の決定 3 の条件 1）の範囲を必要とするためである。あわせて、次の ADR がこの ADR に事項を引き継いでいる。

- [ADR 0008](0008-m0-notation.md): 暗黙に複製される型の範囲（`old` の引数）、篩型と基の型の間の変換と定数の扱い、メソッドの受け手の書き方、式の中で型引数を明示する書き方の要否
- [ADR 0009](0009-lexical-and-grammar.md): トレイトと実装の確定、`let` の型注釈とパターンによる分解、複数の制約の書き方、`Int`・`Float` 以外の数値型、`Char`・`Bytes` とそのリテラル、空の組と要素 1 つの組、逆参照の書き方（`*` を持つか、`n: &mut Int` の引数への代入をどう書くか）
- [ADR 0010](0010-fmt-and-m0-addendum.md): 決定 3 で、M0 では書けない（または意味を決めない）構文として、組の要素の参照 `t.0`、逆参照の前置 `*`、`n: &mut Int` の引数への代入 `n = n + 1`、文字リテラル `'a'`、バイト列リテラル `b"..."` を本 ADR に繰り延べた。決定 8 で、整形器が `-> Unit` を名前 `Unit` の型として書かれたとおりに出力し、`-> Unit` の関数の末尾の `return;` を消さないことを記録し、`Unit` の扱いを本 ADR に繰り延べた

前提:

- 書き手は AI。人間は仕様（モジュールの宣言・型の宣言・シグネチャと 4 節）だけをレビューする（[ADR 0001](0001-vision-and-scope.md)、ADR 0008 の決定 7）
- 同じ意味の書き方は一つ（[ADR 0002](0002-syntax-family.md) の規則 1）
- 参照は二級で、ライフタイム注釈を持たない（[ADR 0003](0003-ownership-and-borrowing.md)）。効果は固定カテゴリの宣言と推論結果の完全一致で検査し、関数の引数の効果は `of(f)` で引き継ぐ（[ADR 0004](0004-effects.md)）
- `Sendable`・`Shareable` を型の構成要素から導く（[ADR 0007](0007-concurrency-model.md) の決定 2）。P0 の契約と篩型の範囲は実行時に検査する（ADR 0006 の決定 5）
- 出力先はネイティブ・WebAssembly・JavaScript・実行環境なしのネイティブで、意味は出力先によらず同じにする（[ADR 0005](0005-long-term-goals.md)・ADR 0007 の決定 5）

本 ADR は P0 の型の規則を定める。所有権・借用の検査（M2）と、異常停止を効果に数えるか（別の ADR。M1 の前）は扱わない。

## 評価の観点

各決定に共通で、重要な順に並べる。

1. **仕様として信頼できるか**: シグネチャに現れる型が、実行時の値の性質を偽りなく表すこと。黙って値が変わる（桁あふれで回り込む、暗黙に変換される）ことがないこと。
2. **AI が誤りなく書けるか**: 学習データに多い書き方（Rust・TypeScript）に近く、規則が少なく、検査エラーの直し方が明確なこと。
3. **同じ意味の書き方が一つか**: 型注釈の有無や参照の書き方で、同じ意味の綴りが複数にならないこと。
4. **P0 の実装量と、後から広げられるか**: M1 の型検査器を小さく保ち、P1 以降で機能を足しても既存のプログラムの意味が変わらないこと。

各決定では、選択肢を挙げ、推奨する 1 つを採用し、理由と M1 の実装への影響を記す。

## 決定 1: 基本型と数値

### 選択肢

- **A: `Int`（64 ビットの符号付き整数）と `Float`（IEEE 754 の倍精度）の 2 つ。桁あふれは異常停止**
- **B: A と同じ型で、桁あふれは回り込む（2 の補数で切り捨てる）**（Java・Go）
- **C: 開発時の版は停止、最適化した版は回り込む**（Rust）
- **D: `Int` を任意精度の整数にする**（Python）

### 決定

**A** を採用する。規則:

- 基本型は `Int`・`Float`・`Bool`・`String`・`Unit`（決定 2）。P0 の数値型は `Int` と `Float` だけで、固定幅の整数（8・16・32 ビット、符号なし）は持たない。
- `Int` は 64 ビットの符号付き整数（2 の補数）。`+`・`-`・`*`・前置の `-` の結果が範囲を超えたとき、`/`・`%` の右辺が 0 のとき、`Int` の最小値を `-1` で割ったときは **異常停止** とする（契約違反と同じく回復の対象にしない。ADR 0006 の決定 5）。出力先・最適化の有無によらず同じとする。
- 整数の `/` は 0 の方向に切り捨て、`%` の符号は左辺に従う（Rust・Java・JavaScript と同じ）。
- 整数のリテラルが `Int` の範囲を超えるとコンパイルエラー（M1）とする。最小値（`-9223372036854775808`）は 2 の 63 乗のリテラルを書けないので、標準ライブラリの定数として得る（名前は標準ライブラリの最小部分の ADR で決める）。
- `Float` は IEEE 754 の倍精度で、無限大と NaN を含み、演算は停止しない。`%` は `Float` に使えない。`==`・`<` などは IEEE 754 の比較に従う（NaN はどの値とも等しくない）。
- `Int` と `Float` の間に暗黙の変換はなく、`Int + Float` は型エラーとする。変換は標準ライブラリの関数で行う（サンプルの `to_float`。`Float` から `Int` への変換は、範囲外と NaN を `Option` で返す形とする）。
- 回り込む演算が要る用途（ハッシュ、P6 のハードウェア操作）には、標準ライブラリに名前で区別した関数（回り込む加算など）を後の段階で加える。演算子の意味は変えない。

### 理由

B は桁あふれで値が黙って変わり、`add_tax` の `ensures result >= price` のような契約を偽にしたまま計算が続く（観点 1）。C は版によって意味が変わり、出力先によらず同じ意味にする方針（ADR 0007 の決定 5）に反する。D は観点 1 では最もよいが、値が小さな値型でなくなり（ADR 0003 の規則 1 の暗黙の複製の前提が崩れる）、実行環境なしのネイティブ出力（P6）で固定幅の整数が別に必要になる。JavaScript 出力では 64 ビットの整数を模倣する費用がかかるが、性能は非目標である（DESIGN.md の 4 章）。

### M1 への影響

- 演算子の型の規則（`+`・`-`・`*`・`/` は `Int` どうしか `Float` どうし、`%` は `Int` どうし、比較は同じ型どうし、`&&`・`||`・`!` は `Bool`）と、リテラルの範囲の検査を実装する。整数のリテラルは常に `Int`、小数のリテラルは常に `Float` で、リテラルの型を文脈から決める規則は持たない。
- 停止そのものは M3 のインタプリタと M5 の出力で実装する。停止を効果に数えるかは別の ADR（M1 の前）で決め、本 ADR の規則はその結論によらない。
- 予約名に `Unit` と決定 6 の性質の名前を加える（ADR 0009 の決定 4 の「標準の前置きの型と値」）。

## 決定 2: `Unit` 型

### 選択肢

- **A: 標準の前置きの型 `Unit` を持ち、値も `Unit` と書く。`-> Unit` は正規形の違反とし、整形器が `->` のない形に直す**
- **B: 空の組 `()` を型と値にする**（Rust）
- **C: `Unit` を持ち、`-> Unit` と `->` の省略の両方を認める**
- **D: 戻り値のない関数の型を値として扱わない**（`Result<Unit, E>` のような型を書けない）

### 決定

**A** を採用する。規則:

- `Unit` は値が 1 つだけの型で、その値も `Unit` と書く（Kotlin と同じ）。暗黙に複製され、等しいか比べられる（決定 6）。
- `->` を書かない関数（`fn main()`）と関数の型（`fn(Int)`）の戻り値の型は `Unit` である。呼び出し `f(x)` の式の型も `Unit` になり、`Unit` が求められる位置（`fn(Int)` の引数、型引数が `Unit` の総称型）に渡せる。
- 関数の宣言と関数の型に `-> Unit` と書くのは正規形の違反とし、`sigil fmt` が `->` を取り除く（そのうえで、ADR 0009 の決定 11 の「戻り値のない関数の末尾の `return;`」の規則が働く）。`Unit` は予約名なので、名前解決の前でも `Unit` の指す型は一つに決まり、整形器が構文だけで直せる。
- 型引数としては書く。例: `fn save(path: Path, text: String) -> Result<Unit, IoError>` は `return Ok(Unit);` で成功を返す。

### 理由

B は空の組を型と値の両方に使い、ADR 0009 の決定 8 で `()` を「引数のない関数」の印として使っていることと重なる（観点 2・3）。C は同じ意味の書き方が 2 つになる（観点 3）。D では失敗だけを返す処理（ファイルの書き込みなど）を `Result` で書けない。A は ADR 0009 の決定 11（`|x| { return e; }` を `|x| e` に直す）と同じく、意味が同じ別の綴りを整形器が一つに直す規則である。

### M1 への影響

- `Unit` を標準の前置きに加え、`->` のない関数と関数の型の戻り値の型を `Unit` とする。
- M0 の整形器を直す（`-> Unit` を取り除く。`tests/data/messy.sigil` の `fn h() -> Unit` の期待出力が変わる）。この変更は M1 の着手時に、整形器の変更として別に行う。

## 決定 3: 組と要素の参照（`t.0`）

### 選択肢

- **A: 要素 2 つ以上の組を持ち、要素は分解（`let (a, b) = t;` と `match`）でだけ取り出す。`t.0` は持たない**
- **B: A に `t.0` の形の要素の参照を加える**（Rust）
- **C: 組を持たず、構造体だけにする**

### 決定

**A** を採用する。規則:

- 組の型 `(A, B, ...)` と組の値 `(a, b, ...)` は要素 2 つ以上（ADR 0009 の文法のまま）。空の組は持たず、決定 2 の `Unit` を使う。要素 1 つの組も持たない。
- 要素は `let` の分解（決定 7）か `match` のパターンで取り出す。`t.0` は持たず、M0 のとおり構文エラーのままとする。エラーの説明に「`let (a, b) = t;` で分解する」と示す。
- 組は構造で型が決まる（`(Int, String)` はどこで書いても同じ型）。契約の中で要素を名前で参照したいときは、組ではなく構造体を返す。

### 理由

B は `t.0.1` が字句として小数 `0.1` と読める問題（Rust で知られている）を字句解析に持ち込み、ADR 0009 の決定 5（1 つの値の綴りは 1 つ）の字句の規則を複雑にする。また要素ごとの移動（部分的な移動）が借用検査（M2）の対象を増やす。C は ADR 0007 の `Result<(Page, Page), NetError>` と ADR 0009 の組のパターンを捨てることになる。A の欠点（契約の中で `result.0` と書けない）は、構造体で名前を付けることで補え、その方が仕様として読みやすい（観点 1）。

### M1 への影響

- 組の型の検査と、`let` の分解（構文解析の拡張を含む）を実装する。字句解析は変えない。

## 決定 4: 参照の使い方（逆参照 `*` と `&mut` 引数への代入）

### 選択肢

- **A: 逆参照の演算子を持たない。参照の型の名前は、参照先の値そのものを表す**（Swift の `inout`、Hylo の考え方）
- **B: Rust と同じく前置の `*` で逆参照する**（`*n = *n + 1`。フィールドとメソッドは自動で逆参照する）
- **C: 書き換え用に別の代入の構文を持つ**（`n := n + 1` など）

### 決定

**A** を採用する。規則:

- 型が `&T` または `&mut T` の名前（借用の引数と、借用を返す関数の戻り値を受けた変数）は、式の中では参照先の `T` の値を表す。フィールド・メソッド・演算子・比較は参照先に対して働く（`account.balance`・`a == b` は値を比べる）。
- `T` が暗黙に複製される型（決定 6 の `Copyable`）なら、値の位置で読むと複製される（`n: &Int` のとき `let m = n + 1;`）。そうでない型の値を参照から取り出して移動することはできない（M2 のエラー。`.clone()` を使う）。
- `n: &mut T` の名前への代入 `n = 式;` は、参照先を書き換える（元の値はその地点で破棄される）。フィールドへの代入 `n.f = 式;` も同じく参照先のフィールドを書き換える。`n: &T` への代入とそのフィールドへの代入（`n.f = 式;`）、値で受け取った引数への代入、`mut` のない `let` への代入はコンパイルエラーとする（引数は書き換えられない。書き換えるなら `let mut y = x;` で写す）。`let mut` の変数への代入は束縛し直しである。
- `match` の対象が参照の型（`&T`・`&mut T`、または `Option<&T>` のように参照を中身に持つ値）のとき、パターンで束縛した名前の型は、参照先の中身への同じ種類の参照とする（`a: &Account` に対する `match` の腕の束縛は `&` の参照、`Some(a)` で `Option<&Account>` を分解した `a` は `&Account`）。束縛した名前も上の規則のとおり値として使い、中身を参照から移動することはできない（M2 のエラー）。`Copyable` な中身は、値として読む位置で複製される。
- 参照を別の関数に渡すときも、呼び出しの位置では常に `&x`・`&mut x` と書く（`x` がすでに参照でも同じ。借用のし直しとして扱う）。参照の参照（`&&T`）は存在しない（ADR 0009）。例外はメソッドの受け手で、`xs.push(1)` のように受け手は自動で借用する（決定 6）。
- `&mut T` から `&T` への暗黙の変換はしない。`&mut` の名前を共有で渡すときも、呼び出しの位置で `&n` と書く（`&mut n` を `&T` の引数に渡すのはエラー）。借用の種類が呼び出しの位置に必ず現れ、同じ意味の書き方が一つになる（観点 3）。
- 型が参照の変数を `let mut` で宣言することはできない（参照を別の参照で束縛し直す操作を持たない）。
- 前置の `*` は持たない。式の中の `*` は乗算だけで、前置の位置の `*` は構文エラーのままとし、エラーの説明に「参照はそのまま値として使う」と示す。

### 理由

参照が二級（ADR 0003 の規則 3）なので、参照そのもの（どこを指すか）を値と区別して扱う場面がない。参照を構造体に入れたり、別の参照で束縛し直したりできないためである。B の `*` は、この言語では「書かなければならないが意味の違いを生まない記号」になり、書き忘れと付け過ぎの両方が検査エラーになる（観点 2）。C は代入が 2 種類になる（観点 3）。A では仕様に現れる「読む」「書き換える」（ADR 0003 の規則 7）の意味と、本体の書き方が一致する。呼び出しの位置の `&`・`&mut` は残すので、どの呼び出しが値を書き換えうるかは本体でも読み取れる。

### M1 への影響

- 型検査器が、参照の型の式を参照先の型として扱う（暗黙の逆参照）。名前への代入の左辺が `&mut T` の引数か `let mut` かで意味を分け、それ以外への代入をエラーにする。構文解析は変えない（M0 は名前への代入を受理している）。
- 借用が有効かどうか、値を参照から移動していないかは M2 で検査する。参照を置ける位置（構造体のフィールドに置けないことなど。ADR 0003 の規則 3）も M2 で検査する（ADR 0006 の M2 の完了条件のとおり）。

## 決定 5: 文字とバイト列（リテラルと型）

### 選択肢

- **A: P0 では `Char` 型・`Bytes` 型とそれらのリテラルを持たない。`Bytes` は P1 で標準ライブラリの型として加え、リテラルは持たない。文字の型は持たない**
- **B: P0 に `'a'` の文字と `b"..."` のバイト列のリテラルを加える**（Rust）
- **C: P0 に `Char`・`Bytes` の型だけを加え、リテラルは持たない**

### 決定

**A** を採用する。規則:

- 文字列は `String`（UTF-8）だけで扱う。1 文字を表すときも長さ 1 の `String` とし、文字の型 `Char` は持たない。文字列を文字に分ける関数は、`List<String>` を返す形で標準ライブラリに置く（分け方が符号位置か書記素かは標準ライブラリの ADR で決める）。
- バイト列の型 `Bytes` は、HTTP の本体・ファイルの読み書きに要る P1 の前に、標準ライブラリの型として加える（その時点の ADR で、要素の型と作り方を決める）。リテラル `b"..."` は持たず、`String` からの変換や数の一覧から作る関数で作る。
- `'` と `b"` は ADR 0009 の決定 6 のとおり P0 では字句エラー・構文エラーのままとする。将来加える場合も既存のプログラムの意味は変わらない。

### 理由

`Char` は「1 文字」の定義（符号位置か、人が 1 文字と見る書記素か）が言語によって異なり（Rust の `char` と Swift の `Character`）、AI が他の言語の意味で誤って使いやすい（観点 2）。文字列の関数だけにすれば、文字の扱いは標準ライブラリの関数の説明に集まる。バイト列は P0 のサンプルが使わず、リテラルがなくても作る関数で足りる。リテラルを持たなければ、エスケープの規則（ADR 0009 の決定 6）を 2 種類に増やさずに済む（観点 3・4）。

### M1 への影響

- なし（型と字句を加えない）。

## 決定 6: 総称型と性質（型引数の制約）・メソッド

### 選択肢

- **A: 総称の関数・構造体・列挙型を持つ。型引数の制約は、標準ライブラリが定める固定の性質だけにする。利用者のトレイトは P0 では持たず、型に直接付けるメソッド（`impl 型 { ... }`）だけを持つ**
- **B: A に利用者のトレイト（`trait`・`impl トレイト for 型`）を加える**（Rust の基本部分）
- **C: 総称型を標準ライブラリの型（`List`・`Option` など）の利用だけに限り、利用者は総称の宣言を書けない**

### 決定

**A** を採用する。規則:

- **総称の宣言**: 関数・構造体・列挙型・`impl` は型引数を持てる（`fn len<T>(xs: &List<T>) -> Int`、`enum Tree<T> { ... }`）。型引数の制約は関数と `impl` の型引数にだけ書け、構造体・列挙型の型引数には書けない（M1 のエラー）。
- **性質**: 型引数の制約に書けるのは、次の性質だけとする。性質の基本の宣言（導出の出発点）は標準ライブラリだけが行い、利用者は性質を宣言も付与もできない（ADR 0007 の決定 2 と同じ）。導出は ADR 0006 の条件 1 の仕組みに性質ごとの導出の規則を登録して行う。

  | 性質 | 意味（仕様での訳） | 基本の型 | 構造体・列挙型・組 |
  |---|---|---|---|
  | `Copyable` | 暗黙に複製される | `Int`・`Float`・`Bool`・`Unit` | 組は要素がすべて持てば持つ。構造体・列挙型は持たない |
  | `Equatable` | 等しいか比べられる（`==`・`!=`） | `Int`・`Float`・`Bool`・`Unit`・`String`、`List`・`Option`・`Result` は型引数による | 構成要素がすべて持てば持つ |
  | `Comparable` | 大小を比べられる（`<` など） | `Int`・`Float`・`String` | 持たない |
  | `Numeric` | 数として計算できる（`+`・`-`・`*`・`/`） | `Int`・`Float` | 持たない |
  | `Sendable`・`Shareable` | ADR 0007 の決定 2 のとおり | 同左 | 同左 |

  篩型は、`Numeric` を除き基の型の性質を引き継ぐ（篩型の値の演算の結果は基の型になるため。決定 8）。関数の型とクロージャはどの性質も持たない（`Sendable`・`Shareable` はとらえた値の一覧から導く。ADR 0007）。
- **`Comparable` を導出しない理由**: 組・構造体・`Option` の大小には、要素を前から比べる辞書式の順序のほかに、`None` を先にするか後にするか、フィールドのどれを先に比べるかといった選び方があり、導出した順序が書き手の意図と黙って食い違いうる（観点 1）。大小で並べたいときは `max_by(|a| a.balance)` のように比べる値を関数で明示する。必要が計測で分かれば、辞書式の導出を後から加えても既存のプログラムの意味は変わらない。
- **`Numeric` でできること**: `T: Numeric` は `+`・`-`・`*`・`/` と比較（`Numeric` の型はすべて `Comparable` でもある）だけを許し、総称の関数の中で `T` の 0 や 1 を作る手段（`T.zero()` やリテラルの変換）は持たない。これは意図した制限で、総称の数の関数は値を引数から作る（`sum` のような 0 から始める関数は、標準ライブラリが `Int` 用・`Float` 用を別に定めるか、初期値を引数で受け取る）。0・1 を作る手段は、利用者のトレイト（P1 の前）とあわせて決める。
- **`old` の引数**: ADR 0008 の決定 3 の「暗黙に複製される型」は `Copyable` を持つ型とする。
- **構造体・列挙型を `Copyable` にしない理由**: フィールドを 1 つ足しただけで、その型の値が移動から複製に（または逆に）黙って変わり、`close(account)` のような「受け取る」引数の意味が変わるためである。複製は `.clone()` で明示する（ADR 0003 の規則 1）。
- **複数の制約**: `T: Equatable + Sendable` のように `+` でつなぎ、性質の名前の文字の順に並べ、重複を書かない。並べ方は正規形とし、`sigil fmt` が並べ替える（効果の並べ方。ADR 0008 の決定 8 と同じ扱い）。
- **メソッド**: 型に直接付けるメソッドを `impl 型 { ... }`（総称なら `impl<T> 型<T> { ... }`）に書く。受け手は最初の引数として名前 `self` で書き、型を明示する: `self: Account`（受け取る）・`self: &Account`（読む）・`self: &mut Account`（書き換える）。`self` は ADR 0008 の決定 4 のとおり「その値そのもの」を表す（決定 4 の規則により、参照でも値として使える）。`self` のない関数は型に属する関数で、`Account.open(...)` と呼ぶ（`Port.check` と同じ形）。
  - 呼び出し `x.m(a)` では、受け手を宣言に合わせて自動で借用する（`self: &mut T` なら `x` は `let mut` の変数か `&mut T` の名前でなければならない）。
  - `impl` は型を宣言したモジュールの中にだけ書ける。同じ型のメソッドとフィールドに同じ名前を付けられず、メソッドの多重定義（引数の型による呼び分け）もない。
  - メソッドも 4 節を必須とし、仕様に含める。`impl トレイト for 型` は持たない（下記）。
- **利用者のトレイト**: `trait` と `impl ... for` は予約語のまま P0 では持たない（ADR 0009 の決定 10 の骨格は将来の形として残す）。
- **式の中の型引数**: `f<Int>(x)` のような書き方は持たない（ADR 0008 の決定 1 の C を加えない）。型引数は引数と、求められる型から推論し、決まらなければ `let` の型注釈で決める（決定 7）。

### 理由

B のトレイトは、P0 のサンプルと標準ライブラリの最小部分（`List`・`Option`・`Result`・`String`）に必要がない。等しさ・大小・数の演算を性質として導けば、`min(xs)`・`max_by(...)`・`sum(xs)` の型を書ける。トレイトには一貫性の規則（同じ型に同じトレイトの実装が 2 つあってはならない）、関連型、既定の実装など設計の論点が多く、処理系の経験がない段階で決めると後で変えにくい（観点 4）。利用者の抽象（P1 のフレームワークのハンドラ、直列化など）が必要になる時期に、決定 10 の関数の型の拡張とあわせて決める。C は利用者が汎用のデータ構造を書けず、表現力が足りない。受け手の型を明示するのは、`&self`（Rust）の省略形を持つと仕様での訳（「読む」「書き換える」）を引数と別に定義することになるためで、全引数を同じ形で示せる（観点 1）。

### M1 への影響

- 総称の関数・構造体・列挙型・`impl` の型検査、型引数の制約の検査、6 つの性質の導出（ADR 0006 の条件 1。`Sendable`・`Shareable` は登録と導出だけを M1 で行い、使う検査は P1）。ADR 0006 の条件 1 の M1 のテスト（構造体・列挙型の型について構成要素から導かれること）は、構造的に導出する `Equatable` と `Sendable` で兼ねる（`Copyable`・`Comparable`・`Numeric` は構造体・列挙型に導出しないので、このテストの対象にしない）。
- 構文解析の拡張: `impl` の宣言（いまは予約語として構文エラー）、`self: 型` の受け手、制約の `+`。`sigil fmt` に制約の並べ方を加え、`sigil spec` に `impl` の中のメソッドを含める。
- 標準の前置きの性質の名前を予約名に加える（ADR 0009 の決定 4）。

## 決定 7: 型推論の範囲と `let` の型注釈

### 選択肢

- **A: 関数の中だけで推論する。シグネチャ・フィールド・篩型の基の型は常に明示し、関数の本体の中の型は本体全体の制約から決める。`let` の型注釈は、推論で決まらないときと、篩型と基の型の間を移すときにだけ書く**
- **B: A と同じ推論で、`let` の型注釈を書き手が自由に書ける**（Rust）
- **C: シグネチャも推論する**（Hindley-Milner の全体推論。OCaml・Haskell）

### 決定

**A** を採用する。規則:

- **推論の範囲**: 関数の引数と戻り値の型、構造体のフィールド、列挙型の値の中身、篩型の基の型は、常に書く（ADR 0009 の文法のまま）。関数の本体の中の型（`let` の変数・クロージャの引数と戻り値・総称の呼び出しの型引数）は、その関数の本体全体の制約を解いて決める。後の文の使い方から前の変数の型が決まってよい（`let mut xs = List.new(); xs.push(1);` の `xs` は `List<Int>`）。
- **総称化しない**: `let` で束縛したクロージャは総称にならない（1 つの型に決まる）。
- **推論の順序**: フィールドの参照 `x.f` とメソッドの呼び出し `x.m(...)` は、受け手 `x` の型が決まっていないと名前を解決できない。受け手の型がまだ決まっていないときは、先にその式を囲む文脈（`x` を渡した呼び出しの引数の型、代入先や戻り値の型、それより前の文での `x` の使い方）から `x` の型を決め、それでも決まらなければ、その位置で「`x` の型が決まらない（`let` に型注釈を書く）」エラーにする。フィールドやメソッドの名前から受け手の型を逆に推し量ること（`balance` というフィールドを持つ型を探すなど）はしない。クロージャの引数も同じで、`|a| a.balance` の `a` の型は、クロージャを渡す引数の型（`max_by` の `fn(&T) -> U` の `T`）から先に決める。
- **型注釈**: `let x: T = 式;`・`let mut x: T = 式;` を書ける。型注釈は、外すと型が決まらない場合か、外すと型が変わる場合（篩型を基の型として受ける `let n: Int = port;`、定数を篩型として受ける `let p: Port = 8080;`。決定 8）にだけ書け、外しても同じ型に決まる型注釈はコンパイルエラー（M1）とする。エラーの説明に「型注釈を取り除く」と示す。
- **名前の隠蔽（シャドーイング）は禁止**: 同じ関数の中では、引数・外側のスコープ（クロージャの引数と `match` の腕の束縛を含む）で使われている名前を、`let`・分解・`match` の腕・クロージャの引数で再び束縛することはできない（M1 のエラー。別の名前にする）。兄弟のブロックで同じ名前を使うのは隠蔽ではないので書ける。値を書き換えながら同じ名前で使いたいときは `let mut` を使う。理由は、同じ名前が場所によって別の値を指すと、仕様の読み手と書き手の両方が取り違えやすく、「書き方は一つ」（ADR 0002 の規則 1）にも反するためである。
- **分解**: `let (a, b) = 式;` の形で組を分解できる（`let mut (a, b)` は書けず、要素ごとの `mut` もない）。分解のパターンは束縛・`_`・組の入れ子だけとし、列挙型や構造体の分解は `match` で行う。

### 理由

C は仕様（シグネチャ）が本体から決まることになり、人間がレビューする型が本体の変更で黙って変わる（観点 1）。B は同じ意味の書き方が 2 つ（型注釈の有無）になる（観点 3）。A の型注釈の規則は、効果の宣言の「余分もエラー」（ADR 0004 の規則 3）と同じ考え方で、要否を型検査器が機械的に判定でき、直し方も一つに決まる。注釈の要否が後の文の変更で変わりうる欠点は、検査エラーの説明で直し方を示して補う（再検証の対象。末尾）。

### M1 への影響

- 関数ごとの制約の解決（単一化）と、制約が解けないときのエラー（「`let` に型注釈を書く」と示す）、型注釈の要否の判定（注釈を外して推論し直し、同じ型に決まれば余分とする）を実装する。受け手の型が要るフィールド参照とメソッド呼び出しは、上の推論の順序の規則に従って、文脈の制約を先に解いてから名前を解決する。
- 構文解析の拡張: `let` の型注釈と組の分解（ADR 0009 の決定 7 で M0 では持たないとしたもの）。整形器は `let x: T = ...` を `:` の後に空白 1 つで出力する。

## 決定 8: 篩型の型検査と実行時検査の境界

### 選択肢

- **A: 型検査は条件の式の形と篩型の出入りの型だけを見る。条件が成り立つかは実行時（`T.check`）に検査し、リテラルの定数だけはコンパイル時に条件を評価する。篩型から基の型へは暗黙に移せる**
- **B: A で、篩型から基の型へも明示の変換（`port.value()` など）を要する**
- **C: 条件を静的に証明する（SMT ソルバ）**

### 決定

**A** を採用する。規則:

- **型検査（M1）で見るもの**:
  - 条件の式は `Bool` で、`self` の型は基の型。値として参照できるのは `self` とリテラルだけとする。関数は呼び出しの位置（`len(self)` の `len`）でだけ使え、呼べるのは `effects none` の関数だけとする（関数を値として渡すことはできない）。`old`・`result` は書けない（ADR 0008 の決定 3・4 の位置の規則は M0 で検査済み）。
  - 基の型は、篩型・参照・関数の型を含まない型に限る（篩型の篩型は ADR 0008 の決定 4 のとおり持たない）。`type NonEmptyPath = Path where !empty(self);` のように `Int` 以外も基の型にできる。
  - 篩型は名前で区別する型で、条件が同じでも別の篩型とは別の型である。処理系は `T.check(v: B) -> Option<T>` を生成する（ADR 0008 の決定 5）。
- **篩型から基の型へ**: `T` の値は、`B` が求められる位置にそのまま渡せる（値は変わらず、検査も要らない）。篩型の値への演算・比較・基の型のメソッドは基の型として働き、結果は基の型になる（`port + 1` は `Int`）。この移しは値の位置だけで行い、型の中では行わない（`List<Port>` を `List<Int>` として渡すことはできない）。
- **基の型から篩型へ**: `T.check(v)`（実行時の検査）か、基の型のリテラルの定数（`let p: Port = 8080;`、`Port` の引数に `8080` を渡す）だけで作れる。定数の場合はコンパイル時に条件を評価し、偽ならコンパイルエラーとする。条件の評価には M3 の評価器を使うので、M1 では定数から篩型への変換を型として受理し（エラーにしない）、定数が条件を満たすかの検査を M3 に回す。M1 と M3 の間は、条件を満たさない定数も `sigil check` を通るが、M3 以降はコンパイルエラーになる。P0 のサンプルは使わない。
- **絞り込みをしない**: `if 1 <= n && n <= 65535 { ... }` の中でも `n` は `Int` のままで、`Port` にはならない。条件の静的な証明と、分岐による型の絞り込みは、契約の静的検査と同じ時期（P0 の完了後。ADR 0006 の決定 4）に検討する。
- **境界**: Python から呼ばれる関数の篩型の引数は、境界で `check` と同じ検査を行う（ADR 0001 の追加の決定の影響。P3）。

### 理由

B の明示の変換は、常に成功し値も変えない操作に書き手の手間と書き忘れのエラーを加えるだけである（観点 2）。篩型の値は基の型の値の部分集合なので、基の型として使っても仕様は偽にならない（観点 1）。逆方向は条件が偽になりうるので、`check` で `Option` を返す（外から来た値）か、定数のコンパイル時の評価（偽なら必ずエラー）に限る。C は P0 の契約を実行時検査にした決定（ADR 0006 の決定 5）と同じ理由で P0 に入れない。

### M1 への影響

- 篩型の宣言の検査（条件の型・値として参照できる名前・呼び出しの位置の関数と効果なしの制限・基の型の制限）、`check` の型の生成、篩型から基の型への値の位置での移し、定数から篩型への変換の型としての受理を実装する。定数が条件を満たすかの検査は M3 で加える。
- 範囲の検査そのものは M3 で行う（ADR 0006 の M1・M3 の完了条件のまま）。

## 決定 9: 失敗の型（`Result` と `Option`）

### 選択肢

- **A: `Option<T>` と `Result<T, E>` を標準の前置きの列挙型とし、`?` は同じ種類・同じ失敗の型の間でだけ使う。失敗の型の暗黙の変換は持たない**
- **B: A で、`?` が失敗の型を暗黙に変換する**（Rust の `From`）
- **C: 例外を持つ**

### 決定

**A** を採用する。規則:

- `Option<T>`（`Some(T)`・`None`）と `Result<T, E>`（`Ok(T)`・`Err(E)`）は標準ライブラリの総称の列挙型で、型名を付けずに値を書く（ADR 0009 の決定 9）。`E` に制約はない（失敗の型の性質を持たない）。
- `式?` は、`式` が `Result<U, E>` なら、それを含む関数（またはクロージャ）の戻り値の型が `Result<V, E>`（`E` が同じ型）のときだけ書ける。`Option<U>` なら、戻り値の型が `Option<V>` のときだけ書ける。`Option` と `Result` の間の変換と、失敗の型の変換は、`ok_or`・`map_err` などの関数で明示する（サンプルの `map_err(ConfigError.Io)?`）。
- 中身を持つ列挙型の値（`ConfigError.Io`）は、関数の値（`fn(IoError) -> ConfigError`）として引数に渡せる。
- `match` の腕は、前の腕がすでに覆っている値にしか当たらないとき（`_` や名前だけの腕の後に置いた腕、同じパターンを重ねた腕、前の腕の組み合わせが覆う腕）、**エラー**（`UnreachableArm`）。網羅性の検査（腕が全部の値を覆うか）と同じ行列の仕組みで、腕を上から順に「それまでの腕が覆わない値に当たるか」を調べる。理由: 到達できない腕は書き手の思い違いの印で、残っていても動作は変わらないため、同じ意味の書き方を増やす（ADR 0002 の規則 1）。AI が出力したコードの読み手も、死んだ腕に意味を探してしまう。警告の段階は持たない。
- 例外はない。契約違反・桁あふれ・0 での除算は異常停止で、捕まえられない（効果に数えるかは別の ADR）。標準ライブラリに、`None`・`Err` で停止する取り出しの関数（Rust の `unwrap`・`expect`）を置くかは、異常停止の扱いを決める ADR に合わせて標準ライブラリの最小部分を決めるときに決める。

### 理由

B は失敗の型の変換が `?` の位置に隠れ、どの失敗がどの失敗に変わるかを本体から読めなくなる。また変換の定義にトレイトが要る（決定 6 で P0 に入れない）。C は失敗の経路がシグネチャに現れず、仕様として信頼できない（観点 1）。A はサンプルの書き方のままで動く。

### M1 への影響

- `?` の型の規則、列挙型の値の関数としての型、`match` の網羅性の検査（ADR 0009 の決定 9）と、到達できない腕の検査を実装する。

## 決定 10: 関数の型を置ける位置

決定 6・9 と ADR 0004 の規則 4（`of(f)`）から生じる制限を明記する。

### 選択肢

- **A: 関数の型 `fn(...) -> T` は引数の型としてだけ書ける。クロージャを入れた変数は関数の中でだけ使う**
- **B: 関数の型に効果を書けるようにし（`fn(Int) -> Int effects console` など）、フィールド・戻り値・型引数にも置ける**

### 決定

**A** を採用する。規則:

- `fn(...)` の型は、関数とメソッドの引数の型（の一番外）にだけ書ける。構造体のフィールド、列挙型の値の中身、戻り値の型、型引数（`List<fn(Int) -> Int>`）、`let` の型注釈には書けない（M1 のエラー）。
- 引数の型が関数の型なら、関数の名前（`add_tax`）、列挙型の値（`ConfigError.Io`）、クロージャを渡せる。クロージャの型は内部ではとらえた値の一覧を持つ（ADR 0006 の条件 3）。
- `let add_n = move |y| y + n;` のようにクロージャを変数に入れて、同じ関数の中で呼べる。その呼び出しの効果は、クロージャの本体から推論した効果とする。
- 総称の関数を値として渡すときは、型引数が文脈で決まらなければならない。
- 関数の値を置ける場所は、`let` の束縛、関数の引数、直接の呼び出しだけ。組・`Option`・`Result`・`List`・構造体・列挙型などの入れ物に関数の値を入れること（`(c, 1)`、`Some(c)`）は、型の注釈に書かなくても M1 の型エラーとする。関数の値を呼び出しや分岐の結果として返すこと（`id(c)` など）も同じエラーとする。式が関数の型になれるのは、名前・クロージャ・値の構築子だけ。
- `let` の右辺が関数の名前（引数・`let`・関数）のときは、束縛した名前がその名前の効果を引き継ぐ。引数の別名（`let g = f; g(1)`）の効果は `of(f)` のままで、`effects of(f)` と書く。
- 関数の型の変数は `let mut` で宣言できず、関数の値の再代入（引数への代入を含む）もできない（どちらも M1 の型エラー）。再代入を追わなくても、`let` の束縛が一度きりなので効果が一つに決まる。束縛し直したいときは新しい `let` を書く。
- 上位カテゴリの効果を書くと下位をすべて含む（ADR 0004）。一部の下位しか起こさない本体には、上位ではなく起こす下位を書く（宣言と推論の集合は一致しなければならない）。

### 理由

ADR 0004 の効果の推論は「呼び出した関数の効果の和」で、関数の値の効果は引数として `of(f)` で引き継ぐ形でだけ追跡できる。関数をフィールドや戻り値に置くと、呼び出しの効果を宣言からも推論からも決められない（観点 1）。B はその解決だが、関数の型の表記と効果の部分型の規則（効果の少ない関数を多い関数の位置に渡せるか）を決める必要があり、P0 のサンプルは必要としない。P1 のフレームワーク（ルーティングのハンドラを表に入れる）と P2 の UI（イベント処理）では必要になるので、利用者のトレイト（決定 6）とあわせて P1 の前に決める。

### M1 への影響

- 型の位置の検査（関数の型を置ける位置）と、局所のクロージャの呼び出しの効果の推論を実装する。

## 影響

- **ADR 0006**: 決定 4 の表の「型システムの範囲」の行に、解決したことと本 ADR への参照を加えた。M1 の完了条件に、本 ADR の「M1 の完了条件に加えるもの」を満たすことを加えた。繰り延べた論点のうち P1 の前に決めるもの（利用者のトレイトと関数の型の拡張、`Bytes`）は、P1 の範囲を決める ADR で表に加える。
- **ADR 0010**: 決定 3 の繰り延べの表（`t.0`・`*`・`n = n + 1`・`'a'`・`b"..."`）は本 ADR の決定 3・4・5 で、決定 8 の `-> Unit` は本 ADR の決定 2 で、それぞれ解決した（「未決として残すもの」の `Unit` の項も同じ）。字句と構文の現状（`t.0`・`*`・`'a'`・`b"` がエラーになること）は変えず、エラーの説明だけを本 ADR の書き方に合わせる。ADR 0010 の「未決として残すもの」の効果の名前の検査（決定 12。ADR 0004 の表にないカテゴリ、単独の `browser`、引数にない名前の `of(...)` をどの段階で誤りにするか）は型システムの範囲ではないので、本 ADR では決めず、M1 の前の論点として残る。
- **ADR 0008**: 決定 3 の `old` の引数の型を `Copyable` に、決定 5 の篩型と基の型の変換を本 ADR の決定 8 に、決定 4 のメソッドの受け手を本 ADR の決定 6 に、決定 1 の式の中の型引数を本 ADR の決定 6（持たない）に、それぞれ決めた。
- **ADR 0009**: 「影響」の型システムの範囲への引き継ぎ（トレイトと実装、`let` の型注釈と分解、複数の制約、数値型、`Char`・`Bytes`、空の組と要素 1 つの組、逆参照）は本 ADR で決めた。予約名の一覧に `Unit`・`Copyable`・`Equatable`・`Comparable`・`Numeric`・`Sendable`・`Shareable` を加える。`impl` は予約語のまま、型に直接付けるメソッドの宣言に使う（`for` は引き続き予約だけ）。`self` は ADR 0009 の文法で篩型の条件の中だけに書ける語としていたが、本 ADR の決定 6 により、`impl` の中の関数の最初の引数の名前（メソッドの受け手）とその本体にも使えるよう広げる（意味は ADR 0008 の決定 4 のとおり「その値そのもの」で変わらない）。
- **ADR 0003**: 規則 1 の「小さな値型」は `Copyable` を持つ型（`Int`・`Float`・`Bool`・`Unit`、その組と篩型）である。規則 7 の仕様での訳は、メソッドの受け手 `self: &T` などにもそのまま使う。
- **ADR 0007**: 決定 2 の導出の仕組みに、本 ADR の 4 つの性質を同じ仕組みで並べる。
- **DESIGN.md**: 未決の論点の表の「型システムの範囲」の行を「決定」に直す。
- **examples**: 変更なし。5 つのサンプルは本 ADR の規則のまま型検査を通る見込みである（`sum`・`min`・`max`・`len`・`to_float`・`max_by`・`map`・`parse_int` などの型は標準ライブラリの最小部分で、本 ADR の性質を使って定める）。

## 根拠の限界と再検証

- 各決定の観点 2「AI が誤りなく書けるか」は、一般に知られている傾向（Rust の `*` と自動の逆参照の取り違え、`t.0.1` の字句の問題、他の言語の `char` の意味の違い）に基づく定性的な判断であり、この言語で計測した結果ではない。
- 候補の案出しと採点を同じ者（Claude）が行っており、偏りがありうる。特に「持たない」とした機能（`t.0`・`*`・`Char`・式の中の型引数・利用者のトレイト）は、持たないことで AI が回り道の書き方を増やす可能性を評価していない。
- 桁あふれを停止とする決定は、JavaScript 出力で 64 ビットの整数を模倣する費用を見積もっていない（性能は非目標だが、P2 の IDE の応答に影響しうる）。
- M1 の完了後、ADR 0004 の計測と合わせて次を計測する。結果が本決定と大きく食い違う場合は、この ADR を見直す。
  - `t.0`・前置の `*`・`'a'`・式の中の型引数・`trait` を書こうとした誤りの数（多いものは持つ方向で見直す）
  - `let` の型注釈の要否のエラー（不要な注釈・足りない注釈）の数と、修正の成功率。多ければ型注釈を自由にする（決定 7 の B）ことを検討する
  - 関数の型を置ける位置の制限（決定 10）で書けなかった課題の数
  - 桁あふれによる停止が、テストの中で実際の不具合を見つけた数と、誤って止めた（回り込みを意図していた）数
