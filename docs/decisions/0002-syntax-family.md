# 0002: 構文の基本形

- **状態**: 承認（2026-10-22。所有者の委任を受けて Claude が決定。計測による再検証の条件は末尾を参照）

## 背景

[examples](../../examples/) で、同じプログラムを 3 つの構文候補で書いた。

- **A: S 式**: すべてを括弧の入れ子で表す
- **B: インデント + キーワード**: 固定順のキーワード行と字下げでブロックを表す
- **C: 波括弧 + 契約節**: C 系のシグネチャに契約節を付け、本体を `{}` で囲む

[ADR 0001](0001-vision-and-scope.md) で次の前提が決まったので、それに照らして 1 つを選ぶ。

- 書き手は AI であり、人間は仕様（意図・事前条件・事後条件・効果）だけをレビューする
- フロントエンドからバックエンドまでを 1 言語で書き、Java・React・Node.js を置き換える
- Rust と同等のメモリ安全性を、所有権と借用の静的検査で得る

## 評価の観点

重要な順に並べる。

1. **AI が誤りなく生成・編集できるか**: 書き手は AI なので最も重い。
2. **仕様を機械的に取り出して人間に示せるか**: 人間が見るのは仕様だけである。
3. **所有権・借用を自然に書けるか**: Rust と同等の安全性に必要になる。
4. **正規化できるか**: 同じ意味の書き方が一通りに定まるか。
5. **UI のような深い入れ子を書けるか**: React の置き換えに必要になる。
6. **パーサの作りやすさ**: 処理系を独自に作るので考慮するが、重みは小さい。

## 比較

| 観点 | A: S 式 | B: インデント | C: 波括弧 |
|---|---|---|---|
| 1. AI の生成・編集 | △ 深い入れ子で閉じ括弧の数を誤りやすい。学習データに占める Lisp 系の割合は小さい | △ 差分やパッチで編集するとき、文字列や Markdown に埋め込むときに字下げが崩れると意味が変わる | ◎ TypeScript・Java・Rust など、置き換え対象そのものに近い書き方で、学習データが最も多い |
| 2. 仕様の抽出 | ○ 属性として取り出せる | ○ キーワード行として取り出せる | ○ シグネチャと本体の間の契約節として取り出せる |
| 3. 所有権・借用 | △ `(ref x)` のような形になり冗長 | ○ | ◎ Rust の `&` / `&mut` の書き方をそのまま使え、AI の Rust の知識が生きる |
| 4. 正規化 | ◎ 構文要素が少ない | ○ キーワード順を固定すれば高い | △ 記号や書き方の揺れが多い → 下記の「正規形の強制」で補う |
| 5. 深い入れ子（UI） | △ 括弧がさらに深くなる | △ 字下げが深くなり、崩れの影響が大きい | ○ 波括弧で範囲が明示される |
| 6. パーサ | ◎ | ○ | ○ |

補足として、[examples](../../examples/) のコメントを除いた文字数を数えた（空白・改行を除く）。

| 例 | A | B | C |
|---|---|---|---|
| 01-average | 187 | 179 | 172 |
| 02-read-port | 486 | 462 | 457 |

差は 1 割未満で、記述量は決め手にならない。

## 決定

**C: 波括弧 + 契約節** を採用する。

最も重い観点である「AI が誤りなく生成・編集できるか」と「所有権・借用を自然に書けるか」で優れている。弱点の正規化は、次の規則で補う。

### 採用に伴う規則

1. **正規形の強制**: 言語仕様として、正規形（公式の整形器が出力する形）だけを正しいプログラムとする。正規形でないコードはコンパイルエラーにする。これにより、同じ意味の書き方が一通りに定まる。
2. **契約節は必須・順序固定**: 関数には `intent` → `requires` → `ensures` → `effects` の 4 節を、この順にすべて書く。省略は許さない。
   - 空の節は `none` と書く（例: `ensures none`、`effects none`）。
   - `intent` は空にできない。
3. **仕様の抽出**: シグネチャ（関数名・引数・戻り値の型）と 4 節を合わせたものを「仕様」とし、処理系はこれだけを取り出して人間に示せるようにする。本体（`{ ... }`）は仕様に含めない。
   - **改訂（[ADR 0008](0008-m0-notation.md)）**: 仕様に、モジュールの宣言（出力先・信頼基盤）と型の宣言を加えた。

### Python 連携と JavaScript 出力との関係

ADR 0001 の追加の決定（Python から呼び出せること、ブラウザ向けに JavaScript も出力すること）は、構文の選択を変えない。構文は処理系の入力の形を決めるもので、出力先や連携の方式とは独立しているためである。ただし次の点に留意する。

- 識別子は Python と JavaScript の双方にそのまま対応づけられる形（英数字と `_`）に限ると、束縛の生成で名前を変換せずに済む。識別子の規則を決めるときの条件とする。
- 契約節（`requires` など）は、Python から呼ばれる境界での実行時検査にそのまま使える。仕様を本体から分けて書く C の形は、この用途にも合う。

## 影響

- `examples/` の候補 C を、上の規則（4 節必須・空は `none`）に合わせて書き直す。候補 A・B のファイルは比較の記録として残す。
- 所有権・借用の書き方は Rust に倣う方向で、別の ADR で決める。
- 以下は未決として残す。
  - 総称型の括弧（`<>` と比較演算子の曖昧さを避けるため `[]` にするか）
  - 本体の値の返し方（最後の式を値にするか、`return` を必須にするか）。どちらにしても正規形は一つに定める
  - UI の記述方法（JSX のような専用の記法を持つか）

## 根拠の限界と再検証

- 観点 1 の評価は、一般に知られている傾向（LLM は深い括弧の対応を誤りやすい、字下げは編集時に崩れやすい、学習データは C 系の言語が多い）に基づく定性的な判断であり、この言語の候補で生成エラー率を計測した結果ではない。
- 候補の案出しと採点を同じ者（Claude）が行っており、偏りがありうる。
- 処理系（少なくともパーサ）ができた段階で、3 候補それぞれについて AI に同じ課題を書かせ、構文エラー率と修正の成功率を計測する。その結果が本決定と大きく食い違う場合は、この ADR を見直す。
