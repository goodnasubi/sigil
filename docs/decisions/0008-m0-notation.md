# 0008: M0 の前に決める表記

- **状態**: 承認（2026-10-25。所有者の委任を受けて Claude が決定。計測による再検証の条件は末尾を参照）

## 背景

[ADR 0006](0006-p0-scope-and-bootstrap.md) の決定 4 は、M0（字句解析・構文解析・整形器・仕様の抽出）の前に次の論点を ADR で決めるとした（「P0 の中で、該当する段階の前に決めるもの」の表のうち、時期が「M0 の前」の 3 行）。

1. 総称型の括弧・本体の値の返し方（[ADR 0002](0002-syntax-family.md) が未決として残したもの）
2. サンプルの未確定の表記: `old(...)`、篩型の `where` と `self`、`Port.check`、モジュールの宣言
3. 仕様の表現と、人間への示し方（最小限。`sigil spec` の出力形式）

M0 の完了条件は、4 つのサンプル（`01-average/c-brace.sigil`・`02-read-port/c-brace.sigil`・`03-ownership/ownership.sigil`・`04-effects/effects.sigil`）を本 ADR の表記に直したうえで、すべて構文解析を通ることである。本 ADR は上の 3 行を 8 つの決定に分けて決め、サンプルを直す。

前提:

- 書き手は AI。人間は仕様（シグネチャと 4 節）だけをレビューする（[ADR 0001](0001-vision-and-scope.md)）
- 構文は波括弧 + 契約節。正規形以外はコンパイルエラー（ADR 0002）
- 効果は固定カテゴリの宣言と完全一致検査。出力先ごとに使えるカテゴリを制限する（[ADR 0004](0004-effects.md) の規則 5）
- 信頼基盤のモジュールだけが検査を外せ、そのことをモジュールの宣言で明示する（[ADR 0003](0003-ownership-and-borrowing.md) の改訂、[ADR 0005](0005-long-term-goals.md)）
- P0 の契約は実行時検査のみ。`old(...)` は関数の入口で値を記録する。篩型の範囲は変換の時点で検査する（ADR 0006 の決定 5）
- 並行処理は `async` の構文を持たない（[ADR 0007](0007-concurrency-model.md)）。本 ADR の構文はそれを前提にする

## 評価の観点

各決定に共通で、重要な順に並べる。

1. **AI が誤りなく書けるか**: 学習データに多い書き方（Rust・TypeScript など）に近く、紛らわしい別の意味を持たないこと。
2. **正規形が一意か**: 同じ意味の書き方が一通りに定まり、整形器がそれを機械的に決められること（ADR 0002 の規則 1）。
3. **仕様として人間が読めるか**: 仕様に現れる表記が少なく、日本語に訳して示せること。
4. **機械的に抽出しやすいか**: 構文解析の段階（名前解決や型検査の前）で、仕様の部分を取り出せること。

## 決定 1: 総称型の括弧

### 選択肢

- **A: `<>`、型の位置に限る**: `List<Int>`・`Result<Port, ConfigError>`。式の中で型引数を明示する書き方は P0 では持たない（型推論に任せる）。
- **B: `[]`**: `List[Int]`（Scala・Go・Python の型注釈）。比較演算子との曖昧さがない。
- **C: `<>`、式の中では `::<>`**: Rust と同じ。

### 比較

| 観点 | A: `<>`（型の位置のみ） | B: `[]` | C: `<>` と `::<>` |
|---|---|---|---|
| 1. AI が書けるか | ◎ Rust・TypeScript・Java と同じ | ○ 学習データはあるが、Rust に近い他の部分（`&mut`、`Result`）と混ざると揺れやすい。添字の `xs[0]` と同じ記号になる | ○ `::<>` の付け忘れを誤りやすい |
| 2. 正規形 | ◎ | ◎ | ○ 推論できる場面で `::<>` を書くかどうかの揺れが生じる |
| 3. 人間が読めるか | ○ | ○ | △ `::<>` は読み手に説明が要る |
| 4. 抽出しやすさ | ◎ 型の位置（`:` の後・`->` の後・`type` の右辺・列挙型の値の中身 `Io(IoError)`）は構文で決まるので、`<` を比較演算子と取り違えない | ◎ | ○ |

### 決定

**A** を採用する。`<` `>` を総称型の括弧として読むのは型の位置だけであり、式の中では常に比較演算子である。`>>` は字句解析で 2 つの `>` として扱う（シフト演算子は持たない。必要になれば関数で書く）。式の中で型引数を明示する必要が出たら、型システムの範囲の ADR（M1 の前）で C の追加を検討する。

## 決定 2: 本体の値の返し方

### 選択肢

- **A: 最後の式を値にする**（Rust）
- **B: `return` を必須にする**: 波括弧のブロックは文の並びであり、値を持たない。関数の値は `return` で返す。値を持つ分岐は `match` で書く。
- **C: 両方を許し、整形器が一方に寄せる**

### 比較

| 観点 | A: 最後の式 | B: `return` 必須 | C: 両方 |
|---|---|---|---|
| 1. AI が書けるか | ○ Rust の知識が生きるが、末尾の `;` の有無で意味が変わる（Rust でもよくある誤り） | ◎ TypeScript・Java・Go と同じ。`;` の有無で意味が変わらない | △ |
| 2. 正規形 | ○ 早期の戻りでは `return` も要るので、二通りが残る | ◎ 戻り方が一通り | △ 寄せる規則が要る |
| 3. 人間が読めるか | — 本体は仕様に含まれない | — | — |
| 4. 抽出しやすさ | — | — | — |

### 決定

**B** を採用する。規則:

- 戻り値の型を持つ関数は、すべての経路が `return 式;` で終わる。戻り値のない関数は、末尾に `return;` を書かない（途中で戻るときだけ `return;` を書く）。
- ブロック `{ ... }` は値を持たない。値を持つ分岐は `match` だけで書き、`match` の各腕は `パターン => 式,` の形とする（腕にブロックは書けない）。`return match x { ... };` や `let y = match x { ... };` と書ける。
  - **改訂（[ADR 0009](0009-lexical-and-grammar.md)）**: 上の「腕にブロックは書けない」は値の `match`（式の位置）の規則とし、副作用だけの場合分けのために、文の位置に書く `match`（腕は `パターン => { ... }` のブロック）を加えた。
- `if` と `while` は P0 では文だけとし、値を持たない（`let y = if ... { ... } else { ... };` は書けない）。条件の真偽で値を選ぶときは `match c { true => 式, false => 式 }` と書く。`if` の分岐の中で値を返すときは `return` を書く。`else if` は書け、`if` の後の `else` は省略できる。
- 脱出するクロージャ（ADR 0003 の規則 5。`s.spawn(g)` に渡すものなど）は、とらえる値を移動することを `move` で示す（`move || 式`、`move |x| 式`）。非脱出のクロージャには `move` を書かない。`move` の要否の検査は M2 で行う。
- クロージャは、本体が式一つなら `|x| 式` と書き、ブロックにするなら中で `return` を書く。`|x| { return 式; }` は正規形ではなく、整形器が `|x| 式` に直す。
- `match` の対象と `if`・`while` の条件の式の中には、構造体の値（`Account { ... }`）を括弧なしで書けない（Rust と同じ。`match x {` の `{` を構造体の値の始まりと取り違えないため）。

## 決定 3: 事後条件で呼び出し前の値を参照する表記

### 選択肢

- **A: `old(式)`**（Eiffel・Dafny）
- **B: `式@pre`**（OCL）、または `\old(式)`（JML）
- **C: 呼び出し前の値に名前を付ける節**: `ensures` の前に `let before = account.balance` のような束縛を書く。

### 比較

| 観点 | A: `old(式)` | B: `@pre` / `\old` | C: 名前を付ける |
|---|---|---|---|
| 1. AI が書けるか | ◎ 契約を持つ言語で最も広く使われる | △ 学習データが少なく、記号が他の言語にない | ○ ただし 4 節の固定順（ADR 0002 の規則 2）に節が 1 つ増える |
| 2. 正規形 | ◎ | ○ | △ 名前の付け方が自由になる |
| 3. 人間が読めるか | ◎ 英語の語の意味（以前の）から分かる | △ | ○ |
| 4. 抽出しやすさ | ◎ 関数呼び出しの形で構文解析でき、`old` を予約語にすれば構文解析の段階で区別できる | ○ | ○ |

### 決定

**A: `old(式)`** を採用し、examples/03 の仮の表記を確定とする。規則:

- `old` は予約語とし、`ensures` 節の中でだけ書ける。他の場所で使うと構文エラーにする。
- 引数の式は、関数の入口の時点の値として評価する（ADR 0006 の決定 5）。中に `result` と `old` を書けない。
- 引数の式の型は、暗黙に複製される型（`Int` など）に限る。入口で値を記録するときに所有権の移動を起こさないためである。どの型が該当するかは型システムの範囲の ADR（M1 の前）で決め、P0 では検査を M1 で行う。
- 人間向けの仕様（決定 7）でも、M0 では他の式と同じくソースの表記のまま示す。

## 決定 4: 篩型（値の条件で型を絞る型）の表記

### 選択肢

- **A: `type 名前 = 基の型 where 条件;`、対象の値を `self` で参照する**（現在のサンプル）
- **B: 名前付きの束縛**: `type Port = { n: Int | 1 <= n && n <= 65535 };`（Liquid Haskell・F\*）
- **C: 契約節に寄せる**: `type Port = Int requires 1 <= self && self <= 65535;`

### 比較

| 観点 | A: `where` + `self` | B: 名前付きの束縛 | C: `requires` に寄せる |
|---|---|---|---|
| 1. AI が書けるか | ○ 英語として自然。Rust の `where`（総称型の制約）と混同しうる → 下の規則で `where` を篩型専用にする | △ 学習データが少なく、`|` がクロージャの記号と重なる | △ `requires` は関数の事前条件として覚えており、型に付くと意味の取り違えが起きやすい |
| 2. 正規形 | ◎ 対象の名前が `self` に固定される | △ 束縛の名前が自由になる | ◎ |
| 3. 人間が読めるか | ◎ 「Int のうち、条件を満たすもの」と訳せる | ○ | ○ |
| 4. 抽出しやすさ | ◎ | ○ | ◎ |

### 決定

**A** を採用し、サンプルの表記を確定とする。規則:

- `where` は篩型の条件にだけ使う。総称型の制約は ADR 0007 の例のとおり `T: Sendable` の形で型引数の位置に書き、`where` 節は持たない。
- `self` は条件の中で対象の値を表す。メソッドの受け手の書き方は型システムの範囲の ADR で決めるが、`self` を使う場合も「その値そのもの」という同じ意味にする。
- 条件は効果を持たない式に限り（`effects none` の関数だけを呼べる）、参照できるのは `self` と定数だけとする。違反の検査は M1 で行う。
- 基の型に篩型を重ねること（篩型の篩型）は P0 では許さない。

## 決定 5: 境界での検査の表記

篩型への変換（`Int` から `Port` へ）の表記を決める。P0 では変換の時点で実行時に条件を検査する（ADR 0006 の決定 5）。

### 選択肢

- **A: `Port.check(n, エラー)`**: 処理系が篩型ごとに生成する関数。条件が偽ならエラーの値を `Err` で返し、`Result<Port, E>` を返す（現在のサンプル）。
- **B: `Port.check(n)`**: 処理系が篩型ごとに生成する関数。`Option<Port>` を返す。失敗を `Result` にするときは標準の `ok_or` を続ける。
- **C: `n as Port`**: 変換の演算子。条件が偽なら契約違反として停止する。

### 比較

| 観点 | A: `check(n, e)` | B: `check(n)` + `ok_or` | C: `as` |
|---|---|---|---|
| 1. AI が書けるか | ○ 引数の 2 つ目が何かを覚える必要がある | ◎ `Option` と `ok_or` は Rust と同じ。生成される関数の形が単純 | △ 失敗の扱いが「停止」になることを見落としやすい。外から来た値の検査では停止でなく `Result` で返すべき場面が多い |
| 2. 正規形 | ○ | ○ | ○ |
| 3. 人間が読めるか | — 本体の表記で、仕様に現れない | — | — |
| 4. 抽出しやすさ | ○ | ◎ 生成する関数の型が篩型によらず同じ形 | ○ |

観点 2 の「正規形」は、整形器が決める構文の範囲（空白・改行・字下げ・節や要素の並び）に限る。B では `Port.check(n).ok_or(e)` と `match Port.check(n) { Some(p) => Ok(p), None => Err(e) }` の二通りを書けるが、これは意味が同じ別の式であり、整形器が書き換える対象ではない（A でも `match` で書き分けられ、C でも停止する変換を関数で包める）。同じ意味の別の式を一通りに絞ることは正規形の対象外とし、3 案とも ○ とした。

### 決定

**B** を採用する。規則:

- `check` は篩型の予約名とする。篩型に `check` という名前の関数を利用者が定義することはできない。
- 篩型 `T`（基の型 `B`）ごとに、処理系が `T.check(v: B) -> Option<T>` を生成する。条件が真なら `Some`、偽なら `None` を返す。効果は持たない（条件が効果を持たないため。決定 4）。
- 基の型から篩型への暗黙の変換は持たない。篩型の値は `check` を通してだけ作れる。
- 篩型から基の型への変換（`Port` を `Int` として使うこと）と、定数の篩型への変換（`8080` を `Port` として書くこと）の扱いは、型システムの範囲の ADR（M1 の前）で決める。P0 のサンプルはどちらも使わない。

## 決定 6: モジュールの宣言

モジュールの単位（ファイルとモジュールの対応、他のモジュールの参照）は ADR 0006 の表どおり M1 の前に決める。ここでは宣言の表記と、そこに書く出力先・信頼基盤の指定を決める。

### 選択肢

- **A: ファイルの先頭の宣言に節を並べる**: 関数の契約節と同じく、固定順の節を必ず書く。

  ```
  module examples.read_port
    targets server
    trust none
  ```

- **B: 別の設定ファイル**: パッケージの設定ファイル（Cargo.toml のようなもの）にモジュールごとの出力先と信頼基盤を書く。
- **C: 注釈**: `@target(server) @trusted module examples.read_port;`

### 比較

| 観点 | A: 先頭の宣言 | B: 設定ファイル | C: 注釈 |
|---|---|---|---|
| 1. AI が書けるか | ◎ 関数の契約節と同じ規則（固定順・省略不可・空は `none`）で、覚えることが増えない | △ 2 つのファイルを合わせて直す必要があり、片方の更新を忘れやすい | ○ 注釈の有無と順序で揺れる |
| 2. 正規形 | ◎ | ○ | △ 注釈を省略したときの既定値が暗黙になる |
| 3. 人間が読めるか | ◎ 仕様の先頭に「出力先」「信頼基盤か」として示せる | △ 仕様と別の場所にある | ○ |
| 4. 抽出しやすさ | ◎ ファイル 1 つの構文解析で取り出せる | △ | ○ |

### 決定

**A** を採用する。規則:

- 各ファイルの先頭（コメントの後）に、`module` の宣言をちょうど 1 つ書く。モジュール名は識別子を `.` でつないだもの。ファイルの位置とモジュール名の対応は、モジュールの単位の ADR（M1 の前）で決める。
- 宣言には `targets` → `trust` の 2 節を、この順にすべて書く（ADR 0002 の規則 2 と同じ考え方）。
- `targets` は出力先を並べる。P0 で書けるのは `server`（ネイティブ）と `browser`（WebAssembly・JavaScript）で、両方なら `targets browser, server` と書く。並べ方は効果の並べ方（決定 8）と同じく文字の順（ASCII の順）とし、規則を一つにする。ADR 0004 の規則 5 の検査はこの宣言に対して行う（M1）。実行環境なしのネイティブ（ADR 0005）など出力先の語は、効果のカテゴリと同じく ADR に記録してから加える。**追記（[ADR 0014](0014-core-and-os-split.md)）**: 出力先の語に `bare`（実行環境なし。`sigil spec` では「実行環境なし」）を加えた。P0 で書けるのは `bare`・`browser`・`server` の 3 つで、並べ方は文字の順（`bare` < `browser` < `server`）。
- `trust` は `none`（通常のモジュール）または `base`（信頼基盤のモジュール。検査を外す箇所を持てる）。`trust base` を宣言できるモジュールの範囲と、検査を外した箇所の契約の書き方は、[ADR 0016](0016-trust-base-declaration.md) で決めた（許可は `--trust-base`、前提は `unchecked` の節。決定 2・3）。
- 宣言は仕様に含める（決定 7）。
- M0 では、`module` の宣言の欠落・2 つ以上の宣言・節の欠落や順序違反・`targets` の重複や並びの違反を構文エラー（正規形の違反）とする。`ensures` 以外での `old` も構文エラーとする（決定 3）。

## 決定 7: 仕様の表現と、人間への示し方（M0 の最小限）

### 選択肢

- **A: 本体を除いたソースをそのまま出す**: シグネチャと 4 節、型の宣言を Sigil の表記のまま示す。
- **B: 日本語の定型文に訳して出す**: 引数の受け渡し方（ADR 0003 の規則 7）、効果のカテゴリ（ADR 0004 の影響）、モジュールの宣言（決定 6）を訳し、条件の式（`old` を含む）はソースの表記のまま示す。
- **C: 機械向けの形式（JSON）だけを出し、表示は別の道具に任せる**

### 比較

| 観点 | A: ソースのまま | B: 日本語の定型文 | C: JSON |
|---|---|---|---|
| 1. AI が書けるか | — 出力であり、AI は書かない | — | — |
| 2. 正規形 | ◎ | ◎ 出力は仕様から一意に決まる | ◎ |
| 3. 人間が読めるか | △ `&mut` などの意味を読み手が知る必要がある | ◎ ADR 0003・0004 が定めた訳をそのまま使う | × |
| 4. 抽出しやすさ | ◎ | ○ 訳は構文だけで決まる（型の情報を使わない） | ◎ |

### 決定

**B** を採用する。`sigil spec` は M0 では次の形のテキストを出す。条件の式（`requires`・`ensures`・篩型の条件。中の `old(...)` と `result` を含む）は訳さず、ソースの表記のまま示す（式の訳し方は IDE を作る P2 で改めて決める）。機械向けの形式は、言語サーバー（M6）の前に決める（[ADR 0019](0019-m6-machine-spec-and-language-server.md) の決定 1 で決めた）。

```
モジュール examples.ownership
  出力先: ブラウザ, サーバー
  信頼基盤: いいえ

関数 deposit
  意図: 口座に入金する
  引数: account を書き換える（Account）、amount を受け取る（Int）
  戻り値: なし
  事前条件: amount > 0
  事後条件: account.balance == old(account.balance) + amount
  効果: なし
```

- 仕様の範囲は、ADR 0002 の規則 3 の「シグネチャと 4 節」に、モジュールの宣言と型の宣言を加えたものとする。出力の順序はソースの順とし、モジュールの宣言、型の宣言（構造体・列挙型・篩型。本体を持たないので全体を示す）、関数の仕様を並べる。関数の本体は含めない。
- 引数は ADR 0003 の規則 7 の訳を、次の差分付きで使う: 型を括弧で付記する（「x を書き換える（T）」）。`x: T` の注記「呼び出し後、呼び出し側では使えない」は省く。暗黙に複製される型（`Int` など）では当てはまらず、M0 には型の情報がないためである。M1 で型の情報を使って注記を戻すかを決める。
- `none` の節は「なし」と示す。効果は ADR 0004 の訳（`fs.read` →「ファイルを読む」など）で示し、`of(f)` は「f の効果」と示す。
- 各サンプルの期待出力のファイルは、M0 の実装で作る。

## 決定 8: 効果の並べ方（正規形）

サンプルを直す中で、`effects` 節の並べ方が決まっていないことが分かった（`fs.read, console` と `console, fs.read`、`fs` と `fs.read, fs.write` が同じ意味になる）。ADR 0002 の規則 1 により一通りに定める。

### 選択肢

- **A: 文字の順（ASCII の順）、下位がそろったら上位に畳む**: `of(...)` を引数の順に先に置き、カテゴリを文字の順に並べる。あるカテゴリの下位がすべて並んだら上位の 1 語にする（`fs.read, fs.write` → `fs`）。
- **B: 文字の順、畳まない**: 並べ方は A と同じ。上位は書かず、常に最下位のカテゴリで書く（`fs` → `fs.read, fs.write`）。
- **C: ADR 0004 の表の順**: 並べ方を表の順とする（畳み方は A と同じ）。

### 比較

| 観点 | A: 文字の順・畳む | B: 文字の順・畳まない | C: 表の順 |
|---|---|---|---|
| 1. AI が書けるか | ○ 文字の順は表を覚えずに再現できる。畳む規則が 1 つ増える | ○ | △ 表の順を覚える必要がある |
| 2. 正規形 | ◎ | ◎ | ◎ |
| 3. 人間が読めるか | ◎ 短い。ADR 0004 の「上位は下位をすべて含む」と合う | ○ 長くなるが、下位が増えたときに意味が黙って広がらない | ○ |
| 4. 抽出しやすさ | ◎ | ◎ | ◎ |

### 決定

**A** を採用する。規則:

- `of(...)` を引数の順に先に並べ、次にカテゴリを文字の順（ASCII の順）に並べる。
- ADR 0004 の表に下位が 2 つ以上ある上位語（`fs`・`net`・`task`）は、表にある下位がすべて並んだら上位の 1 語に畳む（`fs.read, fs.write` → `fs`、`task.share, task.spawn, task.suspend` → `task`）。下位が 1 つだけのカテゴリ（`browser.storage`）は畳まずそのまま書き、表にない上位語（`browser`）は効果として書けない。畳んでいない形は正規形の違反とする。
  - 理由: 下位が 1 つだけの上位語に畳むと、`browser` のように出力先の語と同じ綴りの語が効果として現れて紛らわしく、短くもならないため。
- 重複と、上位と下位の併記（`fs, fs.read`）は正規形の違反とする。
- 下位のカテゴリが後で加わると、上位の意味が広がる（ADR 0004 の規則 1 のとおり）。そのときは、畳んで書いていた宣言が完全一致の検査（ADR 0004 の規則 3）で引き続き正しいかを、カテゴリを加える ADR で確かめる。

## サンプルの修正

本 ADR の表記で次のとおり直した。いずれも M0 の構文解析の対象のファイル（採用構文 C）だけで、候補 A・B のファイルは比較の記録として変えない。

| サンプル | 修正 |
|---|---|
| すべて | 先頭に `module` の宣言を加えた（`01`・`03`: `targets browser, server`、`02`・`04`: `fs.read` を使うので `targets server`。すべて `trust none`） |
| `02-read-port` | `Port.check(n, ConfigError.OutOfRange(n))` を `Port.check(n).ok_or(ConfigError.OutOfRange(n))` に直した |
| `03-ownership` | `old(...)` が仮の表記であるという注記を、確定の表記の説明に直した |
| `05-control`（新規） | 決定 2 の規則（文としての `if`・`while`、値を選ぶ `match`、`move` 付きクロージャ）を確かめる最小の例を加えた |
| `04-effects` | `effects fs.read, console` を `effects console, fs.read` に直した（効果の並べ方）。ブラウザ向けモジュールのエラー例を、`targets browser` の宣言で書いた |

構文解析の前提で次を確かめた。

- 総称型の `<>` は型の位置（`:`・`->` の後、`type` の右辺、列挙型の値の中身）にだけ現れ、式の中の `<`・`<=` と取り違えない（`type Port = Int where 1 <= self ...` の `where` より後は式）。`Shared<Cell<Int>>` の `>>` は 2 つの `>` として読む。
- 値を返す関数はすべて `return` で終わり、戻り値のない関数（`deposit`・`main`・`count_up`）は末尾に `return;` を持たない。式一つのクロージャ（`|a| a.balance`）とブロックのクロージャ（ADR 0007 の例の `task.scope(|s| { ... return ...; })`）は決定 2 の規則に合う。
- `match` の対象（`parse_int(trim(text))`）と `if`・`while` の条件は構造体の値を含まない。`if` と `while` は文としてだけ現れる（`05-control`）。
- `old` は `ensures` の中にだけ現れ、引数は `Int` である。

## 影響

- **ADR 0006**: 決定 4 の表の「M0 の前」の 3 行を解決済みとし、本 ADR を参照する。「モジュールの単位と出力先の指定」は、単位を M1 の前に決める点が残る。M0 の完了条件に、`module` の宣言と `old` の位置のエラー（決定 6）、`05-control` を加え、`sigil spec` の条件を決定 7（仕様の範囲と引数の訳）に揃える。あわせて、表に新しい論点「字句と文法の全体仕様」を加える（本 ADR では決めない）。
- **仕様の範囲（ADR 0002 の規則 3）**: 仕様は「シグネチャと 4 節」に、モジュールの宣言と型の宣言を加えたものになる（決定 7）。ADR 0002 の規則 3 に改訂の注記を付け、examples/README の説明も揃える。
- **ADR 0003 の規則 7**: 仕様での引数の訳は、型を括弧で付記し、`x: T` の注記を M0 では省く（決定 7）。規則 7 の訳そのものは変えず、M1 で注記を戻すかを決める。
- **ADR 0004 の規則 3**: `effects` 節は決定 8 の並べ方で書く。完全一致の検査は集合として行うので、検査の意味は変わらない。規則 3 に並べ方の注記を付ける。
- **ADR 0007**: 決定 1 の例にある「表記は確定ではない」の注記は残す。例は本 ADR の規則（`move` 付きクロージャ、`return`、効果の並べ方）に合っているが、`task.scope`・`s.spawn`・`join` の API の形は型システムの範囲と P1 の実装で変わりうるためである。
- **DESIGN.md**: 未決の論点の表を更新する。あわせて、契約の検査方法の行を「決定」に直す（ADR 0006 の承認による）。
- **examples**: 上の「サンプルの修正」のとおり。README の「採用した構文の約束」に本 ADR の規則を加え、仕様の範囲の説明を決定 7 に揃える。
- **型システムの範囲の ADR（M1 の前）** に次を引き継ぐ: 暗黙に複製される型の範囲（`old` の引数）、篩型と基の型の間の変換と定数の扱い、メソッドの受け手の書き方、式の中で型引数を明示する書き方の要否。
- **モジュールの単位の ADR（M1 の前）** に、ファイルとモジュール名の対応と、他のモジュールの参照の書き方を引き継ぐ。
- **信頼基盤の宣言方法の ADR（M4 の前）** に、`trust base` を宣言できる範囲と、検査を外した箇所の契約の書き方を引き継ぐ。

## 根拠の限界と再検証

- 各決定の観点 1 の評価は、一般に知られている傾向（学習データに多い言語の書き方、Rust でよくある誤り）に基づく定性的な判断であり、この言語で生成エラー率を計測した結果ではない。
- 候補の案出しと採点を同じ者（Claude）が行っており、偏りがありうる。
- サンプルが構文解析を通ることは、処理系がない段階で目で確かめたものである。M0 の構文解析器で通らない箇所が見つかった場合は、ADR 0006 の影響の記述どおりサンプルを直し、表記の決定を変える必要がある場合はこの ADR を改める。
- M0 の完了後、ADR 0002 の計測（構文エラー率）と合わせて、次を計測する。結果が本決定と大きく食い違う場合は、この ADR を見直す。
  - `old`・`where`/`self`・`check`・`module` の宣言の各表記での、AI の構文エラーと正規形の違反の数
  - `return` の書き忘れ、`if` を式として書く誤り、効果の並べ方の違反の数（整形器が直せるものを含む）
