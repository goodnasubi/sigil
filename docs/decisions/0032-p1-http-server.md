# 0032: HTTP/1.1 サーバー（PR 6-3g、段階 6）

- **状態**: 提案（Issue #407）。判断点 A〜I は**未決定**（末尾の「人間の判断が要る点」）。決定の記録は後日、別の作業で本 ADR に書き足す。
- **日付**: 2026-11-12
- **対象**: ADR 0018 の PR 6-3 の本体（ADR 0031 の分割計画の 6-3g）。6-3e で入った `std.os.net`（`TcpListener`・`TcpStream`・`NetError`）と `task.roots` の上に置く HTTP/1.1 のサーバーの範囲・API・並行の形・上限・解釈の規則・ファジング・検証・PR の分割。
- **要承認**: セキュリティ関連（ADR 0020 決定 3 の G1・G2、ADR 0031 決定 6）。本 ADR の PR と、本 ADR に従う実装の PR は、CI が緑で別系統のエージェントが承認しても、**人間（所有者）の承認なしにマージしない**。
- **前提**: TLS は実装しない（ADR 0018 判断 5）。サービスの前に TLS を終端する中継がある。ただし上限と解釈の規則は、前段が要求を正しく区切るとは仮定しない（ADR 0020 決定 4）。

## 背景

- ADR 0031 は、ソケットの最小の API（決定 3）、複数ルートの入口 `task.roots`／`RootGroup.reserve`／`RootSlot.start` と `on_abort`（決定 4）、上限の入口の割り当て（決定 6）を決め、HTTP/1.1 の解釈そのもの（ADR 0020 決定 4 の上限表と密輸の規則）を本 ADR に送った。6-3e（PR #402）・6-3f（PR #404）は main（`8c30fa1`）に入っている。
- ADR 0020 は、HTTP サーバーの上限の既定値（決定 4 の表）、入力の解釈の規則、`fuzz_http_request`（決定 2）、G1・G2（決定 3）、段階 6-3 の項目（決定 5）を決めている。最悪のメモリの式の `S`（1 つのタスクの大きさ）に値を入れるのは本 ADR とされている（ADR 0031 決定 6）。
- ADR 0018 決定 7 は、1 件の要求の異常停止を要求のタスクの範囲で止め、500 を返して続けると決めた。ADR 0031 決定 4-2 は、そのための境界を `on_abort` とし、「応答の送信の状態」は 6-3g で決めるとした。ADR 0018 決定 8 は、停止の印の費用を PR 6-3 で HTTP サーバーの処理量として測ると決めている。
- 起草の時点で確かめた現状（main `8c30fa1`、手元の `sigil check`）:
  - `trust none` の埋め込みモジュール（`std.crypto`）が、表（`src/stdlib.rs`）の宣言の実体として使われている。信頼基盤を増やさずに、標準ライブラリを Sigil で書く前例がある。
  - 関数の型の値は `Sendable` でない（ADR 0013 決定 3）。`fn serve(l: &TcpListener, h: fn(&TcpStream) -> Int)` の中で、`h` を `RootSlot.start` のクロージャがとらえると「`h` の型は `Sendable` でないため、タスクへ移せない」で拒まれる。一方、`start` のクロージャの中で**名前で宣言した関数**を呼ぶ形は通る。`task.timeout` に借用をとらえる移動しないクロージャ（`|| head(&c.s)`）を渡す形も通る。
  - 上限の既定値の置き場所として `CODEOWNERS` にある `/src/limits.rs` は、まだ無い（ADR 0020 W3 は「ADR 6-3 で置き場所が決まったら合わせる」とした）。
  - `.github/workflows/fuzz.yml` の長い実行は対象を名前で並べている（`fuzz_json`・`fuzz_parse`）。新しい対象は自動では入らない。

## 評価の観点

重要な順に並べる。

1. **外からの入力に対する守り**: 1 件の悪い入力・遅い接続・大きな入力で、サービスが止まらず、資源を使い切らない（ADR 0020 観点 2）。要求の区切りの解釈が前段と食い違わない。
2. **信頼基盤を増やさない**: `unchecked`・`raw.*`・原始操作の追加を 0 にする（ADR 0005・0016）。
3. **確かめ方が仕組みになっている**: 規則ごとのテスト、上限ごとの `limit_` テスト、ファジング、評価器との突き合わせで毎回確かめる（ADR 0020 観点 3）。
4. **既存の規則で書ける**: 新しい構文・効果・原始操作・型の規則を足さない。ADR 0031 の部品をそのまま使う。
5. **AI が誤りなく書けるか**: 上限・時間切れ・500 を利用者のコードに書かせない。利用者が書く部分を少なくする。

## 決定 1: HTTP の範囲 — 判断点 A

推奨（案 A1）の範囲:

| 項目 | 扱い |
|---|---|
| 版 | `HTTP/1.1` と `HTTP/1.0` の要求を受ける。それ以外の `HTTP/x.y` は 505、形の崩れた版は 400 |
| 要求の行 | `method SP request-target SP HTTP-version CRLF`。空白は 1 つずつ。メソッドは token。`CONNECT`・`TRACE` は 501 |
| 要求の対象 | origin-form（`/path?query`）だけ。`OPTIONS *` の asterisk-form は受ける。absolute-form・authority-form は 400（前段が origin-form で転送する前提。RFC 9112 の「absolute-form を受けなければならない」から外れることを明記する） |
| 見出し | `name ":" OWS value OWS CRLF`。名前は token。値は生のバイト列として渡す |
| 要求の本文 | `Content-Length` か `Transfer-Encoding: chunked` で区切る。どちらも無ければ本文は空 |
| 応答の本文 | 常に `Content-Length` を付ける（分割した転送の応答は作らない）。`HEAD` は本文を落とし、`Content-Length` は付ける |
| 持続接続 | `HTTP/1.1` は既定で保つ。`Connection: close`、`HTTP/1.0`（`keep-alive` の指定も読まない）、要求の数の上限、解釈の失敗で閉じる |
| パイプライン | 1 件ずつ逐次に処理する（ADR 0020 決定 4）。読み越したバイト列は次の要求の先頭として持ち越す。並べて処理しない |
| `Expect` | ADR 0020 決定 4 のとおり（`100-continue` だけ、上限の検査の後に `100 Continue`。他は 417） |
| `Upgrade` | 無視する（101 を返さない。HTTP/2・WebSocket は範囲外） |
| `Date`・`Server` | 付けない（壁時計の API が無い。版の情報を出さない） |

代案は「人間の判断が要る点」の判断点 A。

## 決定 2: API の形

### 2-1. モジュールと名前 — 判断点 B

推奨（案 B1）: 埋め込みモジュール **`std.http`**（`trust none`、`targets server`）。利用者から見える名前空間は `http`、層は `Os`（`TcpStream` に依るため）。`std.crypto` と同じく、表（`src/stdlib.rs`）の宣言の実体をこのモジュールが持つ。`std.http` は `net.*`・`Bytes`・`task.*` だけを使い、`unchecked`・`raw.*`・新しい `Builtin` を持たない。**信頼基盤の増分は 0** で、評価器とネイティブは同じ Sigil のコードを動かす（ADR 0031 判断点 D の案 B と同じ「単一の実装」の考え方）。

### 2-2. 型

| 型 | 中身（見込み） | 備考 |
|---|---|---|
| `Request` | `method: String`、`path: Bytes`、`query: Bytes`、`version: Int`（10 か 11）、`headers: List<Header>`、`body: Bytes` | 対象は百分率の符号を解かず、正規化もしない（6-4 の経路の照合の範囲） |
| `Header` | `name: String`（小文字に揃える）、`value: Bytes` | 値は前後の OWS を除いた生のバイト列 |
| `Response` | `status: Int`、`headers: List<Header>`、`body: Bytes` | `status` は 200〜599。`Content-Length`・`Transfer-Encoding`・`Connection` はライブラリの側が付ける（利用者は付けられない。決定 6） |
| `HttpLimits` | ADR 0020 決定 4 の HTTP の行のうち本 ADR が受け持つもの（決定 4-1） | 判断点 E |
| `HttpError` | 腕で解釈の失敗の種類を表す列挙（`BadRequest`・`UriTooLong`・`HeadersTooLarge`・`BodyTooLarge`・`NotImplemented`・`VersionNotSupported`・`ExpectationFailed`・`Timeout` など） | 状態コードへの写しは表で固定する。利用者のハンドラには渡らない |

- 型の細目（フィールドを公開するか、取り出す関数にするか）は 6-3g-b で検査器の枠に合わせて決め、本 ADR の補足に記録する。

### 2-3. ハンドラと受け付けのループ — 判断点 C

推奨（案 C1）: ライブラリは**接続 1 つ分の処理**と**解釈の純粋な関数**を出し、受け付けのループは利用者（6-4 ではフレームワーク）が `task.roots` で書く。

| 部品 | シグネチャ（見込み） | 効果 |
|---|---|---|
| `http.parse_request` | `parse_request(buf: &Bytes, limits: &HttpLimits) -> Result<Parsed, HttpError>` | なし（I/O をしない。`Parsed` は要求と消費したバイト数、または「足りない」） |
| `http.conn` | `conn(s: TcpStream) -> HttpConn` | なし |
| `http.serve_conn` | `serve_conn(c: &HttpConn, limits: &HttpLimits, h: fn(&Request) -> Response) -> Unit` | `net.server, clock, task.spawn, task.suspend, of(h)` |
| `http.abort_conn` | `abort_conn(c: HttpConn, limits: &HttpLimits) -> Unit` | `net.server, clock, task.spawn, task.suspend` |

利用者が書く形:

```
task.roots(256, |g| {
  while true {
    let slot = g.reserve();            // 上限にある間は accept を呼ばない
    match l.accept() {
      Ok(s) => {
        slot.start(http.conn(s),
          move |c| { http.serve_conn(c, &http.default_limits(), handle); },
          move |c| { http.abort_conn(c, &http.default_limits()); });
      }
      Err(e) => {}
    }
  }
});
```

- `handle` は名前で宣言した関数（`fn handle(r: &Request) -> Response`）。関数の型の値は `Sendable` でないので、`start` のクロージャがとらえられるのは名前の関数の呼び出しだけである（背景の確かめ）。起動したルートのクロージャは借用をとらえられないので、`HttpLimits` はルートの中で作るか、`Sendable` な値として移す。どちらにするかは 6-3g-b で確かめる。
- `parse_request` を I/O から切り離すのは、ファジングと評価器・ネイティブの突き合わせを、ソケット無しのバイト列の入力で行うため（決定 7・8）。
- `listen` の backlog の既定値 128 は `HttpLimits` が持ち、利用者は `net.listen(&host, port, limits.backlog())` と書く。

## 決定 3: 並行の形と 500 への写し

### 3-1. `task.roots` との関係

- 1 つの接続 = 1 つの起動したルート（ADR 0031 決定 4）。隔離の単位はルートで、1 つの接続の異常停止は他の接続と受け付けのルートを止めない。
- 同時の接続の数の上限（256）は `task.roots` の `limit` と `reserve` で守る（ADR 0031 決定 6）。`on_abort` のルートも同じスロットで数える（ADR 0031 決定 4-2）。
- 1 つの接続の中は逐次で、ライブラリはルートの中に子のタスクを作らない（`task.timeout` の内部を除く）。ハンドラが子のタスクを作るのは自由。
- 本 ADR は ADR 0031 決定 4 の形（同 ADR の判断点 C）をそのまま前提にする。その判断の扱いは本 ADR では変えない。

### 3-2. `on_abort` の状態 — 判断点 D

推奨（案 D1）: `HttpConn` は `TcpStream` と**送信の段階**（`Atomic<Int>`。待ち・読み取り中・ハンドラ中・送信中）を持つ。`serve_conn` は段階を移るたびに書き換え、`abort_conn` は段階で分ける。

| 異常停止の時点の段階 | `abort_conn` の動き |
|---|---|
| 読み取り中・ハンドラ中（応答をまだ 1 バイトも書いていない） | 固定の 500（`Connection: close`、本文の長さ 0）を書いてから `shutdown`・破棄で閉じる。書き込みは応答の送信の時間の上限で包む |
| 送信中（応答の一部を書いた後） | 何も書かずに閉じる（半端な応答の後ろに 500 を足すと、相手と前段が応答の区切りを誤る） |
| 待ち（前の応答を送り終え、次の要求のバイトが来ていない） | 何も書かずに閉じる |

- 500 の本文そのものは 6-4 の範囲（ADR 0020 決定 3 の項目 6）。6-3g は本文を空にする。
- `abort_conn` 自身の異常停止は ADR 0031 決定 4-2(c) のとおり閉じて報告するだけ。
- 段階の記録に `Atomic<Int>` を使えるか（`&HttpConn` の借用から書き換えられるか）は 6-3g-c の最初に確かめる。使えない場合は `Lock<Int>` に落とす。

## 決定 4: 資源の上限と時間

### 4-1. ADR 0020 決定 4 の表の各行の入口

| 上限（既定値） | 入口 | PR |
|---|---|---|
| 要求の行 8 KiB | `parse_request` が行の終わりまでのバイト数を数える。超えたら対象が長ければ 414、ほかは 400 | 6-3g-b |
| 見出しの部分 16 KiB（要求の行を除く。トレーラーを含む） | `parse_request` | 6-3g-b |
| 見出しの数 100（トレーラーを含む） | `parse_request` | 6-3g-b |
| 本文 1 MiB | `Content-Length` は値を読んだ時点で比べ、超えたら本文を読まずに 413。分割した転送は合計で数える | 6-3g-b |
| 分割した転送の大きさの行 1 KiB | `parse_request` | 6-3g-b |
| 同時の接続 256・backlog 128 | `task.roots` の `limit`・`reserve`、`net.listen` の引数（ADR 0031 決定 6） | 6-3g-c |
| 見出しの時間 10 秒・本文の時間 30 秒 | `serve_conn` が段階ごとに 1 つの `task.timeout` で包む（判断点 F） | 6-3g-c |
| ハンドラの時間 30 秒 | `task.timeout` で包み、時間切れで 503 | 6-3g-c |
| 応答の送信の時間 30 秒 | `write_all` を `task.timeout` で包み、時間切れで閉じる | 6-3g-c |
| 接続を保って待つ時間 60 秒 | 次の要求の最初のバイトまでを `task.timeout` で包む（判断点 F） | 6-3g-c |
| 1 つの接続の要求 1000 | `serve_conn` が数え、1000 件目の応答に `Connection: close` を付けて閉じる | 6-3g-c |
| 応答の本文 1 MiB | `serve_conn` がハンドラの戻り値を確かめ、超えたら 500 と標準エラーへの記録 | 6-3g-c |
| 問い合わせの欄の数 100 | 6-3g は問い合わせを生のバイト列で渡すだけ。欄に分けるのは 6-4 | 6-4 |
| JSON の深さ 64・ベアラートークン 4 KiB | 対象外 | 6-4・6-6 |

- 1 回の `read` の大きさは `requires max <= 65536`（ADR 0031 決定 3-2）。`serve_conn` は残りの上限より大きく読まない。
- 時間の上限は中断点でだけ効く（ADR 0020 決定 4、ADR 0007）。ライブラリの解釈は入力の長さに比例するだけで、上限で長さが抑えられているので、中断点の無い長い計算を持たない。ハンドラの中の長い計算は利用者の責任で、G3 の報告の対象。

### 4-2. 時間の上限の測り方 — 判断点 F

推奨（案 F1）:

- 各段階を、読みの 1 回ごとではなく**段階の全体**で 1 つの `task.timeout` に包む。1 バイトずつ送る遅い接続でも期限が延びない。
- 新しい接続: 受け付けから 10 秒で見出しを読み終える。
- 持続接続の 2 件目以降: 前の応答を送り終えてから、次の要求の**最初のバイト**まで 60 秒（接続を保って待つ時間）。最初のバイトから 10 秒で見出しを読み終える。
- 本文: 見出しを読み終えてから 30 秒。
- ADR 0020 の表の文言「見出しを読み終えるまでの時間（接続の受け付け、または前の応答の送信の終わりから）10 秒」をそのまま読むと、60 秒の行が働かない。案 F1 は持続接続の開始点を「最初のバイト」と読む。この読み方を採る場合、ADR 0020 決定 4 の文言の改訂が要る（既定値の変更ではないが、本 ADR の PR では ADR 0020 を変えない）。

### 4-3. 上限の値の置き場所と変更 — 判断点 E

推奨（案 E1）:

- 既定値は小さい専用の埋め込みモジュール（例: `src/stdlib/http_limits.sigil`）にだけ置き、`http.default_limits()` が返す。
- `HttpLimits` を作る関数は、各値を `1 <= v && v <= 上限の上限` の `requires` で受ける。「無制限」を表す値（0・負の値）を持たない（ADR 0020 決定 4）。上限の上限（例: 本文 64 MiB）は 6-3g-b で決めて本 ADR の補足に記録する。
- 設定の名前（環境変数など）は 6-4。6-3g は値を引数で受けるだけで、テストは小さい値（時間 100 ミリ秒など）で上限ちょうどと 1 つ超えを確かめる。
- `CODEOWNERS` の対象（ADR 0020 W3 の O2）を、既定値の置き場所に合わせる変更は `.github/**` なので**人間が行う**。6-3g-b の PR 本文で依頼する。

### 4-4. 最悪のメモリの見積もり

- ADR 0020 決定 4 の式は、見出し・本文・応答の本文の上限と `S` を数え、要求の行（8 KiB）と読みのバッファ（最大 64 KiB）を数えていない。本 ADR は次の式を提案する。
  - 1 つの接続: `8 KiB + 16 KiB + 1 MiB + 1 MiB + 64 KiB + S_http` ≈ 2.09 MiB + `S_http`。
  - `S_http` は、`serve_conn` から `std.os.net` の待ちまでの状態オブジェクトの合計（ADR 0030 決定 1）と、`Request`・`Response` の固定部分。ハンドラの作業の領域は含めない（ADR 0020 と同じ）。
  - 256 接続で ≈ 535 MiB + 256 × `S_http`。
- `S_http` の値は 6-3g-c で、上限ちょうどの負荷で生きている塊を測り（`sigil_blocks` などの既存の計数）、本 ADR の補足に記録する。起動の時に標準エラーへ出す行（ADR 0020 決定 4）は 6-3g-c で入れる。ADR 0020 の式の改訂は判断点 E の影響に含める。

## 決定 5: 解釈の規則（要求の密輸の防止） — 判断点 G

ADR 0020 決定 4 の「入力の解釈の規則」に、推奨（案 G1）として次を足す。どれも RFC 9112 の厳しい側に倒す。**解釈に失敗した後は、応答を書いて接続を閉じる**（続くバイト列を信じない）。

| 番号 | 規則 | 応答 | 由来 |
|---|---|---|---|
| R1 | `Content-Length` と `Transfer-Encoding` の両方 | 400 | ADR 0020 |
| R2 | 値の違う `Content-Length` の重複。加えて、値の同じ重複と `5, 5` の並びも拒む | 400 | ADR 0020＋本 ADR |
| R3 | `Content-Length` の値は `1*DIGIT` だけ（符号・空白・16 進を拒む）。桁あふれする長さは 413 | 400／413 | 本 ADR |
| R4 | `Transfer-Encoding` は小文字の `chunked` ちょうど 1 つだけ。大文字・前後の空白・並び・重複は拒む | 501（値が `chunked` 以外）／400（形の崩れ・重複） | ADR 0020＋本 ADR（ADR 0020 決定 2 の TE.TE の種が拒まれる形） |
| R5 | `HTTP/1.0` の要求の `Transfer-Encoding` | 400 | 本 ADR（RFC 9112 6.1） |
| R6 | 分割した転送の大きさは 16 進の数字だけ。拡張（`;`）は拒む。塊の後は `CRLF` ちょうど | 400 | 本 ADR |
| R7 | 見出しの折り返し | 400 | ADR 0020 |
| R8 | 行の終わりは `CRLF` だけ。`LF` だけ、`CR` だけ、要求の行の前の空行も拒む | 400 | ADR 0020＋本 ADR |
| R9 | 見出しの名前の前後の空白、名前の token 外の文字 | 400 | ADR 0020＋本 ADR |
| R10 | 見出しの値の制御文字（`HTAB` を除く。`NUL` を含む）。`0x80` 以上は不透明なバイトとして受ける | 400 | 本 ADR |
| R11 | `Host` が無い、または複数（`HTTP/1.1`） | 400 | 本 ADR（RFC 9112 3.2） |
| R12 | 要求の行の空白が 1 つでない、対象の制御文字・空白・`0x80` 以上 | 400 | 本 ADR |

- 規則ごとに、拒まれる入力と、境目で通る入力を 1 組ずつテストにする（`tests/http_parse_rules.rs`。名前は `rule_R1_cl_and_te` の形）。
- 同じ表を `fuzz_http_request` の種（決定 7）に入れる。

## 決定 6: セキュリティ（G1: 脅威と対策）

ADR 0020 決定 3 の G1 の 4 つの観点。

| 観点 | 何から何を守るか | 対策 |
|---|---|---|
| 入力 | 壊れた要求・密輸・注入から、要求の区切りと応答の区切り | 決定 5 の規則。解釈の失敗の後は閉じる。**応答の見出しの注入**: ハンドラが返す見出しの名前は token、値は `CR`・`LF`・`NUL` を含まないことを `serve_conn` が確かめ、破ればハンドラの誤りとして 500。`Content-Length`・`Transfer-Encoding`・`Connection` はハンドラが付けられない（ライブラリが付ける）。状態コードは 200〜599（1xx・101 を返させない） |
| 認証 | 範囲外 | 6-6。6-3g は `Authorization` の値を生のバイト列で渡すだけ |
| 秘密 | 見出しの値（`Authorization` など）の漏れ | `std.http` は要求の見出し・本文を標準エラーにもエラーの応答にも出さない。エラーの応答は固定の文（本文は 6-4） |
| 資源 | 接続・メモリ・時間の使い切り | 決定 4 の表と時間の上限。同時の接続は `reserve` で受け付けを止める |

- **ディレクトリの横断を持ち込まない**: `std.http` は対象をファイルの経路に写さず、`fs.*` の効果を持たない。`std.http` の関数の効果の宣言に `fs.read`・`fs.write` が無いことを、表の単体テストで固定する。静的なファイルの配信は 6-3g の範囲外。
- **信頼基盤の増分は 0**（判断点 B の案 B1）。`std.http` が `trust none` であることを表の単体テストで固定し、`unchecked` が要る場面が見つかったら、実装を止めて本 ADR を改訂する（ADR 0018 判断 2 のレビューの対象）。
- **セキュリティ関連の扱い**: 本 ADR と 6-3g-b〜6-3g-d は、AGENTS.md の「セキュリティ関連」として人間の承認を必須にする。

## 決定 7: ファジングと回帰テスト — 判断点 H

- 対象は `http.parse_request`（純粋な関数）。`tests/fuzz_http_request.rs` が評価器で呼ぶ（ADR 0020 決定 2 の「Sigil の対象」）。
- 確かめる性質: どの入力にも `Ok`／`Err` を返す（契約違反・桁あふれ・範囲の外の読み書き・スタックの枯渇は誤り）。消費したバイト数が入力の長さを超えない。`Ok` の要求を書き出して読み直すと同じ要求になる（往復）。入力を任意の位置で 2 つに分けて与えても同じ結果になる（読みの粒度に依らない）。
- 入力: ランダム、種の変異、文法からの組み立て。種（`tests/fuzz/corpus/http_request/`）には決定 5 の R1〜R12 の各形と、ADR 0020 決定 2 の密輸の既知の形（CL.TE・TE.CL・TE.TE・`Content-Length` の重複・大きさの行の崩れ）を必ず入れる。
- 見つけた誤りは小さくして `tests/fuzz/regress/http_request/` に置き、毎回走らせる。
- 短い実行は通常の `cargo test` の中で、CI の増分が全体で 60 秒以内に収まる回数（ADR 0020 決定 2）。
- ネイティブとの突き合わせは、入力をまとめたファイルを 1 回のビルドと 1 回の実行で処理し、評価器の結果と比べる（ADR 0020 決定 2）。
- 長い実行（推奨: 案 H1）: `.github/workflows/fuzz.yml` に `fuzz_http_request` の段を足す。`.github/**` は人間だけが変えるので、6-3g-b の PR で依頼する。足されるまでは、ADR 0020 決定 2 のとおり手で 30 分以上走らせ、回数・種・結果を PR に記録する。

## 決定 8: 評価器との差と検証の方法

ADR 0030 補足 D の方針（差は表に固定する）に従う。`std.http` は評価器とネイティブで同じ Sigil のコードなので、新しい差は原則として生じない。

- **解釈**: `parse_request` を、同じ入力の集まりについて評価器とネイティブで動かし、結果（`Ok` の中身か `Err` の腕と消費したバイト数）を比べる（決定 7 と共用）。
- **接続**: `tests/` の Rust の `std::net` のクライアントが、評価器・ネイティブ（ワーカー 1・4）に同じバイト列を送り、応答のバイト列の連結・閉じられた接続の数を比べる（ADR 0031 決定 5-2 と同じ。待ち受けは `port` 0 と `local_port`）。持続接続とパイプラインは、送る位置を変えて（1 バイトずつ、まとめて）同じ応答になることを確かめる。
- **時間**: 実時間モード（ADR 0031 決定 1-3）で、小さい上限（数百ミリ秒）を使い、遅い接続（1 バイトずつ送る）が見出しの時間で 408 になること、待つ時間で閉じられることを確かめる。
- **ネイティブだけの試験**: fd の漏れ（多数の接続の後に `/proc/<pid>/fd` が増えない）、同時の接続の上限ちょうどの負荷でのメモリ（決定 4-4 の `S_http`）、停止の印の費用（ADR 0018 決定 8。処理量を測って記録）。
- **表への追記**: 差が見つかった場合だけ、ADR 0030 補足 D-3 の表に行を足す（6-3g-d）。評価器の処理の速さ（1 MiB の本文など）はテストの大きさで調整し、差ではないので表に入れない。

## 人間の判断が要る点

どれも**未決定**。推奨は起草者（Claude）の案で、決定の記録は後日行う。

### 判断点 A: HTTP の範囲（決定 1）

- **選択肢**: A1 = 決定 1 の表（1.0・1.1、origin-form、`Content-Length` と分割した転送の要求本文、持続接続、逐次のパイプライン）。A2 = 1.1 だけ・持続接続なし（毎回閉じる）・分割した転送の要求は 411／501。A3 = A1 からパイプラインを外す（応答の前に次の要求のバイトが来たら閉じる）。
- **推奨**: A1。
- **理由**: ADR 0020 の表に持続接続（60 秒・1000 件）と分割した転送の行があり、A2 ではそれが使われない。前段の中継は持続接続と分割した転送を使う。A3 は、読み越しが TCP の分割の都合でも起きるので、正しい相手を閉じうる。逐次の処理と読み越しの持ち越しは、区切りが決定 5 で一意なら密輸の種にならない。
- **影響範囲**: `std.http` の解釈と `serve_conn`、規則とファジングの種の数、6-4 の前提。absolute-form を拒むことは RFC 9112 からの意図した逸脱として残る。

### 判断点 B: モジュールの置き場所と実装（決定 2-1）

- **選択肢**: B1 = `std.http`（埋め込み、`trust none`、名前空間 `http`、層 `Os`）。B2 = `std.os.http`（`trust base`。OS 層の命名にそろえる）。B3 = 評価器とネイティブの Rust の組み込み。B4 = 標準ライブラリの外の利用者のモジュール（`examples/` などの Sigil のソース）。
- **推奨**: B1。
- **理由**: 解釈は OS の機能を直接呼ばないので `trust base` にする理由が無く、`trust none` なら信頼基盤の増分が 0 になる（観点 2）。`std.crypto` の前例がある。B3 は二重の実装で、ADR 0031 判断点 D の記録（二重の実装の層を無くす理由づけ）とも逆向き。B4 は表の単体テストと効果の固定、ファジングの枠に載せにくい。
- **影響範囲**: `src/stdlib.rs` の `Os` の行（一覧の単体テスト）、`src/stdlib/http.sigil` の新設、`sigil spec` の出力（名前空間 `http` が増える。仕様の差分として人間のレビューの対象）。

### 判断点 C: ハンドラと受け付けのループの形（決定 2-3）

- **選択肢**: C1 = 接続 1 つ分の `serve_conn` と純粋な `parse_request` を出し、受け付けのループは利用者が `task.roots` で書く。ハンドラは `fn(&Request) -> Response`。C2 = 高水準の `http.serve(listener, limits, handler)` を出す。C3 = 書き出し口を渡す形（`fn(&Request, &mut ResponseWriter)`）で、応答を流して書く。
- **推奨**: C1。
- **理由**: C2 はハンドラの関数の値を起動したルートへ移す必要があり、関数の型の値が `Sendable` でない今の規則（ADR 0013 決定 3。ADR 0022 は提案のまま）では書けない（背景の確かめ）。C1 は今の規則で書け、上限の検査は `reserve` と `serve_conn` の内側に閉じる。C3 は送信の途中の異常停止が増え（決定 3-2 の「送信中」）、応答の大きさの上限も数えにくい。
- **影響範囲**: 利用者（6-4 のフレームワーク）が書く受け付けのループ。ADR 0022 の扱いが決まった後に C2 を 6-4 で足す余地を残す。ADR 0031 決定 4-1 の「フレームワークが部品で書ける形」の確かめ（ADR 0031 の改訂は要らない見込み）。

### 判断点 D: 500 への写しと送信の段階（決定 3-2）

- **選択肢**: D1 = 接続の値に送信の段階を持たせ、応答を書き始める前の異常停止だけ 500 を書く。D2 = 常に 500 を書いてから閉じる。D3 = 500 を書かずに閉じるだけ。
- **推奨**: D1。
- **理由**: D2 は半端な応答の後ろに 500 を足し、相手と前段の応答の区切りを崩す。D3 は ADR 0018 決定 7 の「500 を返して続ける」を満たさない。C1 の形では応答はライブラリが書くので、送信中の異常停止はライブラリの誤りに限られ、閉じるだけで足りる。
- **影響範囲**: `HttpConn` の中身（`Atomic<Int>` か `Lock<Int>`）、`abort_conn`、決定 3-2 の 3 つのテスト。

### 判断点 E: 上限の値の置き場所と変更の可否（決定 4-3・4-4）

- **選択肢**: E1 = 専用の小さい埋め込みモジュールに既定値を置き、`HttpLimits` を範囲の `requires` 付きで作れるようにする（6-3g から値を変えられる。設定の名前は 6-4）。E2 = 既定値を `std.http` に埋め込み、6-3g では変えられない（6-4 で足す）。E3 = 既定値を Rust の `src/limits.rs` に置き、Sigil へ渡す。
- **推奨**: E1。
- **理由**: 時間の上限のテストを実時間で既定値（10〜60 秒）のまま回せないので、6-3g の時点で小さい値を渡せる必要がある。専用のファイルにすると、`CODEOWNERS` で既定値だけを所有者のレビューの対象にできる（ADR 0020 W3 の O2 の趣旨）。E3 は Rust から Sigil へ値を渡す新しい経路（原始操作か契約変更）が要る。
- **影響範囲**: `CODEOWNERS` の行の変更（人間の作業）。ADR 0020 決定 4 の最悪のメモリの式に、要求の行と読みのバッファを足す改訂（決定 4-4）。上限の上限の値（6-3g-b で記録）。

### 判断点 F: 時間の上限の測り方（決定 4-2）

- **選択肢**: F1 = 段階の全体を 1 つの期限で包み、持続接続では「最初のバイトまで 60 秒、そこから見出しまで 10 秒」と読む。F2 = ADR 0020 の文言どおり、前の応答の終わりから 10 秒（60 秒の行は働かない）。F3 = 読みの 1 回ごとの期限（バイトが来るたびに延びる）。
- **推奨**: F1。
- **理由**: F3 は 1 バイトずつ送る遅い接続（いわゆる Slowloris）で期限が延び、接続を使い切られる。F2 は ADR 0020 の 60 秒の行と矛盾する。F1 は両方の行を生かし、遅い接続も各段階の期限で切れる。
- **影響範囲**: `serve_conn` の時間の扱い、実時間のテスト。F1 を採る場合は ADR 0020 決定 4 の文言の改訂が要る（別の PR）。

### 判断点 G: ADR 0020 より厳しい解釈の規則（決定 5）

- **選択肢**: G1 = 決定 5 の R1〜R12（ADR 0020 の規則に、`Content-Length` の形・`chunked` の小文字ちょうど・拡張の拒否・`Host` の一意・制御文字・空行の拒否などを足す）。G2 = ADR 0020 の規則だけを入れ、他は RFC 9112 の寛容な側（`chunked` の大文字小文字を区別しない、同じ値の `Content-Length` の並びを受ける、拡張を読み飛ばす、要求の前の空行を読み飛ばす）。
- **推奨**: G1。
- **理由**: 密輸は「前段と解釈が食い違う余地」から生まれ、寛容な受け方はその余地を広げる。ADR 0020 決定 2 は TE.TE の種（大文字・空白・重複）が拒まれることを求めており、G2 の大文字小文字の区別なしと合わない。P1 の相手は既知の前段と JSON の API で、厳しい側の互換の損は小さい。
- **影響範囲**: `parse_request`、規則ごとのテストと種。正しいが珍しい要求（拡張付きの分割した転送など）を 400 で拒むこと。

### 判断点 H: ファジングの長い実行（決定 7）

- **選択肢**: H1 = `.github/workflows/fuzz.yml` に `fuzz_http_request` を足す（人間の作業）。足すまでは手で 30 分以上走らせて記録する。H2 = CI に足さず、手での実行と記録だけにする。
- **推奨**: H1。
- **理由**: ADR 0020 W1（C1）の定期の実行の趣旨と同じ。HTTP の解釈は外の入力を最初に読むコードで、長い実行の効き目が最も大きい対象の 1 つ。
- **影響範囲**: `.github/workflows/fuzz.yml`（人間のみ）。定期の実行の時間（60 分の打ち切りの中に収める回数）。

### 判断点 I: PR の分割（上の分割計画）

- **選択肢**: I1 = 6-3g-a〜d の 4 つ（ADR・解釈・接続・完了の記録）。I2 = ADR の後の実装を 1 つの PR にする。I3 = 評価器とネイティブで分ける。
- **推奨**: I1。
- **理由**: 解釈（純粋な関数）はソケット無しで確かめられ、レビューの単位として独立する。I2 は人間の承認が要るのに大きすぎる。I3 は単一の実装（判断点 B の B1）なので分ける意味が無い。
- **影響範囲**: 後続の Issue の起票（`docs/BACKLOG.json` の `spawn_rules`。本 ADR の PR では変えない）。

- 分割した転送の応答・応答の流し書き（大きな応答）。
- `Date` の見出し（壁時計の API が要る）。
- 前段が付ける見出し（`X-Forwarded-For` など）の扱い（ADR 6-4。既定では信じない）。
- 相手のアドレスの取得、`TCP_NODELAY`（ADR 0031 の未決のまま）。
- HTTP/2・WebSocket・TLS・`net.client`（ADR 0018 の「行わないこと」）。

## 決めないこと

- ADR 0030 の判断点 3〜6、ADR 0031 の判断点 B〜F、ADR 0007 の条件 8、Issue #366 の扱いは、本 ADR では決めず、承認の状態にも触れない。本 ADR はそれらの ADR の現在の本文（決定の形）を前提に書いている。前提の形が改まれば、本 ADR を改訂する。
  - 中断をまたいで `&HttpConn` を持つ場面は、ADR 0031 のソケットの操作と同じく、現行の実装の振る舞いの範囲で使うだけである（ADR 0007 の条件 8 の結論に依存しない）。
  - 入口の引数に `&Lock<T>` を持つ形は使わない（Issue #366 に触れない）。
- 500 の本文、設定の名前、経路の照合（6-4）。

## 根拠の限界

- 本 ADR は設計の提案で、**実装も計測もしていない**。背景の「確かめた現状」は、手元の `sigil check`（`target/debug/sigil`、2026-11-11 のビルド）で小さなプログラムを検査した結果だけで、`Atomic<Int>` を `&HttpConn` から書き換えられるか、`HttpLimits` をルートへ渡せるかは確かめていない。
- 決定 4-4 の式の `S_http` は未知。評価器で 1 MiB の本文を扱う時間も測っていない（テストの大きさの調整が要りうる）。
- 決定 5 の規則は RFC 9112 の知識に基づき、既存の前段（中継）の振る舞いとの突き合わせはしていない。厳しい側の規則で、正しい前段の要求を拒む例が見つかったら、本 ADR を改訂する。
- 候補の案出しと推奨を同じ者（Claude）が行っており、偏りがありうる（ADR 0020 の根拠の限界と同じ）。
