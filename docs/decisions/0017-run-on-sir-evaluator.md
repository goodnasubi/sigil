# 0017: `sigil run` の実行器と、インタプリタの破棄の順序の食い違いの扱い

- **状態**: 承認（2026-10-26。所有者の委任を受けて Claude が決定。）実装済み。

## 背景

[ADR 0015](0015-m5-native-output.md) の「M5 の完了の記録」は、次の追跡項目を M6 の早期に決めるとした。

- インタプリタ（`src/interp.rs`）の破棄の順序が、仕様（[ADR 0006](0006-p0-scope-and-bootstrap.md) の条件 9）と食い違う。食い違うのは次の 5 つの場合である。
  - `match` の束縛による移動
  - 値を消費するメソッドの受け手
  - `move` クロージャの取り込み
  - クロージャを `Copyable` として扱うこと
  - 構造体の一部の欄だけの移動
- SIR の評価器（`src/ir_eval.rs`）と実行ファイルは、仕様の想定どおりに破棄する。
- 決めることは、次のどちらにするかである。
  - (a) インタプリタの移動の追跡を直して、仕様に合わせる。
  - (b) `sigil run` を SIR の評価器へ置き換える。

この論点は、信頼基盤の宣言方法（[ADR 0016](0016-trust-base-declaration.md)）とは別の ADR にした。理由は次の 3 つである。

- 互いに依存しない。ADR 0016 は原始操作の実行を範囲に含めない。本 ADR は信頼基盤に触れない。
- 決める時期が違う。本 ADR は M6 の早期、ADR 0016 は P1 の範囲を決める ADR の前である。
- 承認と実装を別々に進められる。本 ADR は 1 つの PR で済み、ADR 0016 の判断を待たせない。

### 現状（main `be945bd`）

- **食い違いが見える範囲**:
  - 破棄の順序が観測できるのは、`Options::trace_drops` を立てたときだけである。立てられるのは、ライブラリの関数と `sigil build --trace-drops` である。
  - `sigil run` には破棄を記録する引数がない。P0 には利用者が書く破棄の処理もない。
  - したがって今の食い違いは、テストの中でだけ見える。
  - 一方で P1 では、ファイルの扱い・`Lock` など、解放の時期が外から観測できる資源が入る（ADR 0007）。そうなると、同じプログラムが `sigil run` と実行ファイルで違う動きをする。
- **SIR の評価器の準備**:
  - インタプリタと同じ `Options`・`Outcome`・`Failure` を使い、`fs_files`・`capture_console`・`trace_drops`・`stack_bytes` をすべて扱う。
  - lowering は、インタプリタが実行できる構文をすべて扱う（`no_build_unsupported_left`）。
  - 停止の報告は、どちらも `src/report.rs` で作る。
- **比較のテスト**:
  - `tests/common/mod.rs` の `run*` は、すべての実行の事例でインタプリタと SIR の評価器を比べる。比べるのは値・出力・破棄の記録・停止の報告である。
  - ネイティブの実行ファイルとの比較は 411 件ある（ADR 0015 の決定 8）。
  - `tests/m3_drop_limits.rs` は、上の 5 つの場合について、インタプリタの現状の順序と、SIR の評価器と実行ファイルの仕様どおりの順序の両方を固定している。
- **規模**: `src/interp.rs` は 2204 行、`src/lower.rs` と `src/ir_eval.rs` は合わせて 3627 行ある。
- **インタプリタを前提にした計画**:
  - [ADR 0007](0007-concurrency-model.md) の P1-a は、「M3・M4 のインタプリタに単一スレッドの実行割り当てを加える」としている。
  - ADR 0006 の決定 4 は、P3 の「すぐ実行できる形態」について、「M3・M4 のインタプリタを土台にできるか」をその時点で検討するとしている。

## 評価の観点

重要な順に並べる。

1. **`sigil run` と実行ファイルの意味の一致**: 同じプログラムが、2 つの実行の仕方で同じ動き（値・出力・停止・破棄の順序）をすること。テストで常に確かめられること。
2. **実装の重複を増やさないか**: P1-a の実行の割り当て・取り消しのときの破棄、[ADR 0016](0016-trust-base-declaration.md) の原始操作など、これから入る機能を何か所に書くことになるか。
3. **誤りを見つける力**: 独立に書いた 2 つの実装を比べることで、lowering の誤りを見つけられること。
4. **費用**: 変更の量と、既存のテストへの影響。

## 選択肢

- **A: インタプリタを直す**（追跡項目の (a)）。
  - インタプリタの移動の追跡を、5 つの場合について仕様どおりにする。
  - `sigil run` は今のままインタプリタで動かす。
- **B: `sigil run` を SIR の評価器にし、インタプリタはテストの比較役として凍結する**（追跡項目の (b)）。
  - `sigil run` は lowering と SIR の評価器で実行する。
  - インタプリタはテストの中だけで使い、値・出力・停止の報告の比較を続ける。
  - 破棄の順序は、インタプリタとは比べない。
  - インタプリタには新しい機能を加えない。
- **C: B に加えて、インタプリタを今削除する**。

## 比較

| 観点 | A: インタプリタを直す | B: SIR にして凍結 | C: SIR にして削除 |
|---|---|---|---|
| 1. 意味の一致 | ○ 直した 5 つの場合は揃う。破棄の規則は 2 か所に書かれたままで、次の食い違いの余地が残る | ◎ `sigil run` と実行ファイルは同じ lowering を通るので、破棄の順序は作りから揃う | ◎ B と同じ |
| 2. 実装の重複 | × これからの機能を、インタプリタ・SIR の評価器・コード生成の 3 か所に書く | ◎ 新しい機能は lowering・評価器・コード生成だけに書く | ◎ |
| 3. 誤りを見つける力 | ◎ 独立した 2 つの実装の比較が、破棄の順序まで続く | ○ 値・出力・停止は独立した実装との比較が続く。破棄の順序は lowering を共有する 2 つ（評価器と実行ファイル）の比較になる | × lowering の誤りは、評価器と実行ファイルの両方に同じ形で出るので、比較では見つからない |
| 4. 費用 | × 検査器が求めた移動の情報（`Typed.moves`）を、AST をたどるインタプリタの中で作り直す必要がある。lowering の破棄の組み立てを、もう 1 つ書くことになる | ◎ `src/main.rs` の呼び出しを替え、`m3_drop_limits.rs` のインタプリタ側の固定を外すだけ | ○ B に加え、比較の補助関数とインタプリタ固有のテストを書き直す |

## 決定

**B** を採用する。

- **`sigil run`**:
  - `ir_eval::run_with` で実行する。`--fs-double` の扱い・報告の形・終了コード（成功は 0、異常停止は 70、それ以外の失敗は 1）は変えない。
  - あわせて `sigil run --trace-drops` を加える。破棄を記録したとき、`sigil build --trace-drops` の実行ファイルと同じ形（`drop: <表示>` を標準エラーへ 1 行ずつ。ADR 0015 の決定 7）で出す。これで、`sigil run` と実行ファイルの破棄の順序が同じことを、コマンドラインから確かめられる。
- **インタプリタの位置づけ**:
  - インタプリタは「意味論の基準」ではなくなり、テストで使う比較役になる。意味論の基準は、仕様（ADR）と、それを実装した lowering とする。ADR 0015 の観点 1 は、M5 までの基準を述べたものとして残す。
  - インタプリタには、新しい構文・標準ライブラリ・実行の機能を加えない。直すのは、比較で見つかった食い違いが、インタプリタ側の誤りだった場合だけとする。
  - 本 ADR の後に入る機能のテストは、`tests/common` の比較のうち、SIR の評価器と実行ファイルの比較だけを使う。そのための補助関数を加える。
- **破棄の順序のテスト**:
  - `tests/m3_drop_limits.rs` から、インタプリタの現状の順序を固定した `assert_eq!` を外す。SIR の評価器と実行ファイルの、仕様どおりの順序の固定は残す。
  - ファイルの先頭の説明を「インタプリタは破棄の順序の基準ではない（ADR 0017）」に改める。
  - インタプリタの既知の制限そのものは、ADR 0006 の条件 9 の記録に残す。
- **インタプリタを削除する時期**:
  - **[ADR 0018](0018-p1-scope.md) の決定 4 が削除を決めた**。SIR の検証器を入れ（PR 1-4）、その後に削除する（PR 1-5）。以下の「決め直す」条件は、決定 4 の前の記述として残す。
  - 次のどちらかが先に来たら、削除するかを決め直す。
    - P1-a で、実行の割り当てなどの新しい機能のために、インタプリタとの比較を外す事例が全体の 1 割を超えたとき。
      - 「全体」は、`scripts/native-report.sh` が数える突き合わせの件数とする。
      - 現在の基準値（main `be945bd`）は、411 件のうちインタプリタとの比較を外しているもの 0 件である。411 件はすべて `tests/common` の `run*` を通り、インタプリタ・SIR の評価器・実行ファイルの 3 つを比べている。
      - 411 件の外に、`tests/m3_drop_limits.rs` の 6 件がある。SIR の評価器と実行ファイルだけで破棄の順序を比べる事例で、`spec_ids_of`・`sir_ids` の呼び出しである。これは 411 件にも、外した件数にも数えない。
      - 1 割は、今の件数なら 41 件である。件数が増減したら、その時点の突き合わせの件数の 1 割とする。
    - P1 の範囲を決める ADR。
  - 削除する前に、lowering の誤りを見つける別の手段を決める。案は、検査器の型の情報と SIR の型の一致の検査や、lowering の単体テストである。

### 停止のときの動き（スタックの枯渇を含む）

`sigil run` を SIR の評価器にしても、スタックの枯渇の扱いは、次のとおり今と同じであることを確かめた（main `be945bd` のコード）。

- **スレッドとスタックの大きさ**:
  - `interp::run_sources_with` と `ir_eval::run_sources_with` は、どちらも `Options::stack_bytes` の大きさのスタックを持つスレッドを作り、その中で実行する。既定は 256 MiB である。
  - `sigil run` は `Options::default()` を使うので、大きさは変わらない。
- **枯渇の判定**: どちらも、スレッドの入口のスタックの番地から `stack_bytes / 4 * 3`（既定で 192 MiB）より深くなったときに、`StackExhausted` で停止する。
- **失敗の形**:
  - どちらも `RunError::Stop` の `StopKind::StackExhausted` を返す。報告の文字列は、`src/report.rs` の同じ関数が作る。
  - `sigil run` は、それを `<パス>: 異常停止: スタックの枯渇（関数 名前、N 行目）` として標準エラーに出し、終了コード 70 で終わる。
  - スレッドを作れないとき、評価器の内部の誤りのときは `RunError::Entry` で、終了コード 1 になる。この形も同じである。
- **違うところ**:
  - 1 つの枠の大きさが実装で違うので、止まる深さは違う。
  - 報告の「関数・行」は、枯渇を検出した地点なので、一般には違いうる。`tests/common` の比較が、スタックの枯渇では種類だけを比べるのはこのためである。
  - 本 ADR を書くときに、深い再帰（`d(n) = d(n - 1) + 1`、n = 1 億）を release ビルドで両方に実行した。報告はどちらも `異常停止: スタックの枯渇（関数 d、14 行目）` で一致した。
  - SIR の評価器には、値の入れ子が深すぎて表示・破棄できないときの停止（`値の入れ子が深すぎる`）がある。インタプリタにも同じ種類の停止があり、どちらも `StackExhausted` である。
- 以上から、`sigil run` の利用者に見える変化は、止まる深さと、報告の関数・行が変わりうることだけである。完了条件の `cli_run_stack_exhausted` で、終了コード 70 と報告の見出し（`異常停止: スタックの枯渇`）を固定する。

## 理由

- 観点 1: B では、`sigil run` と実行ファイルが同じ lowering を通る。破棄の順序は作りから揃い、評価器とコード生成の違いだけが残る。その違いは、既存の比較のテスト（411 件）がすでに見ている。A では破棄の規則が 2 か所に書かれたままなので、P1 で解放の時期が観測できる資源が入ったときに、同じ種類の食い違いが新しく出うる。
- 観点 2: P1-a の実行の割り当て、取り消しのときの破棄（ADR 0007 の条件 9）、ADR 0016 の原始操作の実行は、どれも SIR の評価器とコード生成には要る。A ではこれをインタプリタにも書くことになり、3 か所になる。
- 観点 3: B の欠点は、破棄の順序について独立した実装との比較を失うことである。しかし今のインタプリタは、その 5 つの場合でまさに誤っていて、比較役になっていない。値・出力・停止の比較は続くので、lowering の誤りの多くは引き続き見つかる。C はその比較まで失うので、今はとらない。
- 観点 4: B の変更は小さく、M6（言語サーバー）の作業を遅らせない。

## 選ばなかった案と理由

- **A（インタプリタを直す）**: 観点 2・4 で劣る。インタプリタの中で移動の情報を作り直すのは、検査器と lowering がすでに持つ情報の 3 つめの実装になる。
- **C（今削除する）**: 観点 3 で劣る。lowering の誤りを見つける別の手段を決める前に、比較役をなくすことになる。

## 実装の手順

1 つの PR で行う。

1. `src/main.rs` の `run` を `sigil::ir_eval::run_with` に替え、`--trace-drops` を加える。使い方の文言を直す。
2. `tests/common/mod.rs` の比較を、次のとおり直す。
   - `compare`（インタプリタと SIR の評価器の比較）から、破棄の記録の比較（成功のときと、停止のときの 2 か所の `drops`）を外す。値・出力・停止の報告・停止までの出力の比較は残す。
   - `native::check` に渡す期待値を、インタプリタの結果（`a`）から SIR の評価器の結果（`b`）に替える。実行ファイルの破棄の記録（`--trace-drops`）は、SIR の評価器の記録と比べることになる。`native::check` の中の破棄の順序の `assert_eq!` は、そのまま残す。
   - `run*` が返す値を、SIR の評価器の結果（`b`）に替える。各テストの `assert` は、`sigil run` と同じ実行器の結果を見ることになる。インタプリタとの比較は `compare` の中だけで行う。
   - インタプリタを呼ばずに、SIR の評価器と実行ファイルだけを比べる補助関数 `sir_native*`（`run*` と同じ 4 つの形）を加える。本 ADR の後に入る機能のテストに使う。
   - この変更で `native-report.sh` の件数は変わらない（実行ファイルを比べる事例の集合は同じ）。
3. `tests/m3_drop_limits.rs` から、インタプリタの現状の順序を固定した `assert_eq!` を外す（決定）。
4. 完了条件のテストを加える。

## 影響

この ADR が承認されたら、実装の PR で次を反映する。

- **ADR 0006**:
  - 条件 9 の「既知の制限」に、`sigil run` は SIR の評価器で動き仕様どおりに破棄すること、制限はテスト用のインタプリタだけに残ることを追記する。
  - 決定 4 の「すぐ実行できる形態」の理由の「M3・M4 のインタプリタを土台にできるか」を、「SIR の評価器（またはインタプリタ）を土台にできるか」に改める。
- **ADR 0007**: P1-a の「M3・M4 のインタプリタに単一スレッドの実行割り当て…を加える」を、「SIR の評価器に」に改める（本 ADR の決定でインタプリタに新しい機能を加えないため）。
- **ADR 0015**: 「M5 の完了の記録」の追跡項目に、本 ADR で (b) に決めたことを追記する。
- **README.md**: ステータスの ADR の行に本 ADR を加え、`sigil run` の説明を直す。
- **docs/DESIGN.md**: 変えない（実行方式の章は、インタプリタに触れていない）。

## 人間の判断が要る点

依存の追加・CI の変更・秘密情報は要らない。CI（`.github/workflows/ci.yml`）は `cargo fmt --check`・`cargo clippy`・`cargo test`・`scripts/native-report.sh` を実行する。本 ADR はこの設定を変えない。`native-report.sh` が数える突き合わせと飛ばしの件数も変わらない見込みである。`tests/common` の比較は実装の手順の 2 のとおり直すが、実行ファイルを比べる事例の集合は変えないためである。変わった場合は、ADR 0015 の決定 8 の運用どおり、理由を確かめてから上限と下限を直す。

## 根拠の限界と再検証

- 候補の案出しと採点を、同じ者（Claude）が行っており、偏りがありうる。
- 観点 3 の「値・出力・停止の比較で、lowering の誤りの多くは見つかる」は見込みである。M5 の間に見つかった食い違いのうち、破棄の順序でだけ見つかったものの数は記録していない。
- `sigil run` の速さ（lowering の分の費用）は、性能が非目標（DESIGN.md の 4 章）なので観点に入れていない。参考として、本 ADR を書くときに 1 つの事例で測った値を記す。B の判断は、この値には依らない。
  - 事例: `while` で n 回まわし、毎回、構造体を作って欄を足し、`List` に `push` する関数。
  - 条件: main `be945bd`、release ビルドで、ライブラリの `interp::run` と `ir_eval::run` を呼んだ。1 回ずつの測定である。
  - 結果:

    | n | インタプリタ | SIR の評価器（lowering を含む） |
    |---|---|---|
    | 1000 | 8.0 ms | 1.7 ms |
    | 4000 | 134 ms | 2.8 ms |
    | 16000 | 1.76 s | 13.8 ms |
