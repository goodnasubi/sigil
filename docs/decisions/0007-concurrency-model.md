# 0007: 並行処理のモデル

- **状態**: 承認（2026-10-25。所有者の委任を受けて Claude が決定。計測による再検証の条件は末尾を参照）

## 背景

[ADR 0006](0006-p0-scope-and-bootstrap.md) は、並行処理のモデルを P1（サーバー）の前に本 ADR で決めるとし、P0 が満たすべき 11 の条件（決定 3）と、本 ADR に引き継ぐ未決点を挙げた。
[ADR 0003](0003-ownership-and-borrowing.md) は `Send` / `Sync` に相当する区別を、[ADR 0004](0004-effects.md) は `async` を効果とするかを、それぞれ並行処理の ADR に回している。
本 ADR では次の 6 点を決める。

1. 並行処理のモデル
2. スレッドをまたぐ型の区別と、型の性質の導出の仕組み（ADR 0006 の条件 1）との接続
3. 効果システムとの関係（`async`・待機・起動・チャネル、`state`・`clock` の扱い）
4. 中断点をまたぐ借用と、取り消し時の破棄
5. 出力先ごとの違いと、Python 連携の境界
6. ADR 0006 の 11 条件への答え（と、本 ADR で追加する条件 12）と、実装・テストの時期

前提:

- 書き手は AI。人間は仕様（シグネチャと 4 節）だけをレビューする（[ADR 0001](0001-vision-and-scope.md)）
- データ競合をコンパイル時に排除する（ADR 0001 の必須条件）。参照は二級で、借用は引数としてだけ渡せる。借用をとらえるクロージャは脱出できない（ADR 0003）
- 効果は固定カテゴリの宣言と推論結果の完全一致検査。高階関数は `of(f)` で引数の効果を引き継ぐ（ADR 0004）
- 出力先はネイティブ・WebAssembly・JavaScript。ブラウザの JavaScript は単一スレッドで、イベント処理の中で長く止まると画面が固まる

## 評価の観点

重要な順に並べる。

1. **データ競合の排除（必須）**: 型と所有権の検査だけで、スレッド間のデータ競合が起こらないこと。
2. **AI が誤りなく書けるか**: 規則と概念が少なく、検査エラーの直し方が明確か。Rust の非同期処理（`Future` の `Send` 境界、`Pin`、`'static` の要求）が扱いにくいことは広く知られている。
3. **仕様の読みやすさ**: 並行性に関する情報が仕様に現れ、その表記が少ないこと。「この関数は待つことがあるか」「並行に処理を起動するか」が仕様から分かること。
4. **出力先で同じ意味になるか**: ネイティブ・WebAssembly・JavaScript で、同じプログラムが同じ範囲の振る舞いをすること。
5. **UI とサーバーの両方で書けるか**: ブラウザの単一スレッドで画面を固めずに通信を待てること。サーバーで多数の接続を少ない OS スレッドで扱い、複数の CPU を使えること。

## 選択肢

- **A: OS スレッド + 共有所有**: Rust の `std::thread` に相当。スレッドを起動し、スレッド間の共有は参照カウント型と排他制御で行う。
- **B: `async` / `await`**: Rust・JavaScript・C# と同じく、非同期の関数を `async` で宣言し、呼び出し側で `await` する。非同期の関数は将来の値（`Future`）を返す。
- **C: アクター / メッセージ渡し**: Erlang のように、処理の単位（アクター）が状態を持ち、メッセージだけでやりとりする。共有は持たない。
- **D: 中断を効果として扱う構造化並行処理**: `async` / `await` の構文と `Future` の値を持たない。中断しうること（待つこと）を効果カテゴリで表し、中断する関数も普通の関数と同じ書き方で呼ぶ。並行な処理（タスク）は、範囲（スコープ）の中でだけ起動でき、範囲を抜ける前に必ず終わる（Trio・Kotlin のコルーチン・Swift の構造化並行処理と同系統）。タスク間のやりとりはチャネルと、スレッド間用の共有所有の型で行う。
- **E: A + B の組み合わせ**: OS スレッドと `async` / `await` の両方を持つ（Rust の現状）。

## 比較

| 観点 | A: OS スレッド | B: async/await | C: アクター | D: 中断を効果とする構造化並行処理 | E: A + B |
|---|---|---|---|---|---|
| 1. データ競合の排除 | ◎ 型の区別（決定 2）で可能 | ◎ 同左 | ◎ 共有しないので自明 | ◎ 同左（決定 2） | ◎ |
| 2. AI が書けるか | ○ 概念は少ないが、多数の接続を扱うには向かない | △ `Future` の値・`Send` 境界・取り消し忘れ・`await` 忘れ（JavaScript）の誤りが多い | ○ 概念は少ないが、要求と応答を組み立てる定型が増える | ○ 普通の関数と同じ書き方。新しい概念は範囲・起動・チャネルの 3 つ | × 2 つの仕組みの使い分けと相互変換が要る |
| 3. 仕様の読みやすさ | △ スレッドを起動するかは仕様に現れない（効果を足せば別） | △ `async` は仕様に現れるが、中で何を待つかは現れない | ○ | ◎ 「待つことがある」「処理を起動する」「他の処理と共有する値に触れる」が `effects` 節に現れる | △ |
| 4. 出力先で同じ意味 | × ブラウザの JavaScript にスレッドがない | ○ JavaScript の非同期関数に対応づけられる | ○ | ○ 中断する関数だけを変換すればよい（決定 5）。並列に動くかは出力先で異なるが、観測できる違いは順序だけ | △ |
| 5. UI とサーバー | △ UI で通信を待つと画面が固まる。サーバーで接続ごとに OS スレッドは重い | ◎ | △ UI の状態をアクターに分けるのは不自然 | ◎ | ◎ |

B の欠点の多くは、非同期の関数と同期の関数で書き分けが要ること（関数の色の問題）と、`Future` という値の扱いから来る。D では、中断しうるかを効果として推論し、高階関数は `of(f)` で引き継ぐので、同じ高階関数を両方に使える。色の違いは残るが、それは `effects` 節の違いとして現れ、ADR 0004 と同じく「呼び出し先の効果を宣言に足す」ことで直せる。

C の利点（共有しない）は、D のチャネルと所有の移動で同じ書き方ができる。アクターは D の上の標準ライブラリの部品として作れる。

## 決定 1: 並行処理のモデル

**D: 中断を効果として扱う構造化並行処理** を採用する。観点 1 は全案が満たし、観点 2・3 で D が最も良く、観点 5 で B と並ぶ。観点 4 の制約（ブラウザでは並列に動かない）は決定 5 で扱う。

### 規則

1. **タスク**: 並行に動く処理の単位をタスクと呼ぶ。プログラムの入口（`main`、サーバーのリクエスト処理、UI のイベント処理）はタスクとして実行環境が起動する。
2. **起動は範囲の中だけ**: タスクは標準ライブラリの `task.scope(f)` が開く範囲の中でだけ起動できる。`task.scope` は本体のクロージャ `f` に範囲 `s: &Scope` を **借用の引数として** 渡す（ADR 0003 の規則 3: 借用は引数としてだけ渡せる）。`f` は呼び出しの間だけ使われる非脱出のクロージャなので、外側の変数の借用をとらえてよい。`s` は構造体に入れることも、返すことも、起動するクロージャにとらえさせることもできない。範囲は、中で起動したすべてのタスクが終わるまで戻らない。範囲から外れて動き続けるタスク（切り離されたタスク）は通常のコードでは作れない。長く動き続ける処理（サーバーの待ち受けなど）は、入口に近い範囲で起動する。
3. **起動するクロージャ**: `s.spawn(g)` に渡すクロージャ `g` は脱出するクロージャとして扱う（ADR 0003 の規則 5）。とらえる値は移動するか、スレッド間用の共有所有の型で持つ。とらえる値と戻り値はすべて `Sendable`（決定 2）でなければならない。帰結として、子のタスクは `s`（借用）をとらえられず、親の範囲に兄弟のタスクを起動できない。子がさらにタスクを起動するときは、子の中で新しい `task.scope` を開く。タスクの親子関係は、範囲の入れ子（呼び出しの入れ子）と一致する。
4. **結果**: `s.spawn` は取っ手を返し、`join` は子のクロージャの戻り値をそのまま返す（子が `Result<T, E>` を返すなら `join` も `Result<T, E>` を返す）。取っ手は `Sendable` でなく、`join` できるのは範囲の本体だけである。子が取り消されるのは、範囲全体が取り消されるとき（決定 4）に限り、そのとき本体も取り消されるので、取り消された子の `join` が値を返すことはない。`task.scope(f)` は `f` の戻り値を返す。
5. **中断の書き方**: `async` / `await` の構文と、将来の値を表す型は持たない。中断しうる関数（決定 3 の `task.suspend` を持つ関数）も、普通の関数と同じく呼び、戻り値を受け取る。
6. **やりとり**: タスク間のやりとりは、チャネル（`Channel<T>`。`T` は `Sendable`）と、スレッド間用の共有所有の型（決定 2）で行う。
7. **スレッドは隠す**: OS スレッドを直接起動する API は通常のコードに公開しない。タスクを OS スレッドに割り当てる部品（実行の割り当て）は、標準ライブラリの OS 依存部分に置く（ADR 0006 の条件 10）。OS（P6）で必要になる低い層の API は、その段階の ADR で決める。
8. **大域の可変な値**: 大域の可変な値は持たない。`Shareable` な型に限って許すなどの緩和は、必要になったときに別の ADR で決める。タスクの外から共有されない値だけでタスクが閉じていることを、決定 2 の規則の前提とする。標準ライブラリの内部の大域の状態（乱数の状態、実行の割り当て）は信頼基盤の例外とし、検査を外した箇所の契約に、タスクをまたいで安全である前提を書く（ADR 0005）。

例（表記は確定ではない。構文の表記は ADR 0006 の決定 4 の論点で決める）:

```
fn fetch_both(a: Url, b: Url) -> Result<(Page, Page), NetError>
  intent "2 つのページを並行に取得する"
  requires none
  ensures none
  effects net.client, task.spawn, task.suspend
{
  return task.scope(|s| {
    let ha = s.spawn(move || http.get(a));   // http.get は Result<Page, NetError> を返す
    let hb = s.spawn(move || http.get(b));
    let pa = ha.join()?;                      // join は Result<Page, NetError> を返す
    let pb = hb.join()?;
    return Ok((pa, pb));
  });
}
```

`ha.join()?` で本体が早期に戻っても、範囲は `hb` の終了を待ってから戻る。一方の失敗で他方を取り消すには、決定 4 の `task.all_ok` を使う。

## 決定 2: スレッドをまたぐ型の区別

### 選択肢

- **A: 区別を持たない**: すべてのタスクを 1 つのスレッドで動かす（JavaScript と同じ）。サーバーで複数の CPU を使えない。
- **B: `Send` / `Sync` に相当する 2 つの性質を、構成要素から導く**。
- **C: 1 つの性質だけにする**（「別の処理に渡せる」だけ）。

C では、「別の処理に移せるが、複数の処理から同時に読むことはできない」型（`Cell<T>`。下の表）を区別できず、スレッド間用の共有所有の型の中身を正しく制限できない。A は観点 5 を満たさない。**B** を採用する。

### 規則

- **`Sendable`**（別の処理に渡せる）: 値の所有を、別のスレッドで動きうる別のタスクへ移してよい。
- **`Shareable`**（複数の処理から同時に読める）: 共有借用を通して、複数のタスクから同時に読んでよい。
- **導出**: 構造体・列挙型・タプル・クロージャ（とらえた値の一覧。ADR 0006 の条件 3）は、構成要素がすべてその性質を持つとき、その性質を持つ。導出は ADR 0006 の条件 1 の仕組み（P0 で「暗黙に複製されるか」を実装したもの）に、新しい性質として 2 つを登録して行う。
- **基本の型**: 性質の基本の宣言（導出の出発点）は標準ライブラリだけが行う。利用者は性質を手で付けられない。検査を外して付ける場合は信頼基盤のモジュールに限り、安全の前提を契約として書く（ADR 0005）。

| 型 | `Sendable` | `Shareable` | 備考 |
|---|---|---|---|
| `Int`・`Float`・`Bool`・`String`・`List<T>` など | 構成要素による | 構成要素による | |
| `Shared<T>`（単一スレッド用の参照カウント） | × | × | 参照カウントの増減が原子的でない。複製した `Shared` が元のタスクに残りうるので、移すこともできない |
| `Cell<T>`（単一スレッド用の実行時の排他検査） | `T` が `Sendable` なら ○ | × | 所有ごと移すのは安全だが、排他の検査が原子的でないので、複数のタスクから同時に触れられない |
| `SyncShared<T>`（スレッド間用の参照カウント） | `T` が `Sendable` かつ `Shareable` なら ○ | 同左 | |
| `Lock<T>`（スレッド間用の排他制御） | `T` が `Sendable` なら ○ | `T` が `Sendable` なら ○ | 書き換えはこの型を介してだけ行う |
| `Channel<T>` の送り口・受け口 | `T` が `Sendable` なら ○ | ○ | |

- **タスク全体は移せる**: タスクの中の値は、`Sendable` でなくても、そのタスクごと別の OS スレッドに移って実行を続けてよい。`Sendable` でない値はタスクの外に出られず（規則 3）、大域の可変な値もない（決定 1 の規則 8）ので、タスクが中断している間に他のスレッドからその値に触れる経路がないためである。Rust の「`Future` が `Send` でない」エラーに当たるものは生じない。
- **仕様での表示**: 総称型の制約として仕様に現れる（例: `T: Sendable`）。人間向けには「別の処理に渡せる」「複数の処理から同時に読める」と訳す。
- **名前**: ADR 0006 の条件 2 で後から加えるとしたスレッド間用の共有所有の型の名前を、`SyncShared` と `Lock` とする。`Shared` / `Cell` との間の暗黙の変換は持たない。

## 決定 3: 効果システムとの関係

### 選択肢

- **A: 中断を効果にしない**: すべての関数が中断しうるとみなす（Go・Java の仮想スレッドと同じ）。仕様に現れず、JavaScript への出力ではすべての関数を非同期にするか、実行時のスタックの切り替えが要る。
- **B: 新しいカテゴリ `task` を加え、`state` は変えない**。
- **C: `state` の下位にスレッド間の書き換えを加え、中断は `clock` に含める**。

C では、`clock` が「時刻」と「他の処理を待つ」の 2 つの意味を持ち、仕様の読み手に区別できない。また ADR 0004 の階層の規則により `effects state` がスレッド間の書き換えも含むことになり、既存の `effects state`（[examples/04-effects](../../examples/04-effects/effects.sigil) の `count_up`）の意味が広がる。A は観点 3・4 で劣る。**B** を採用する。

### 追加するカテゴリ

ADR 0005 の手続き（ADR に記録してから標準ライブラリが追加する）に従い、本 ADR で ADR 0004 の表に次の 1 カテゴリ（下位 3 つ）を加える。利用者が追加できない点は変わらない。

| カテゴリ | 意味 | 使える出力先 |
|---|---|---|
| `task.spawn` | 並行に動くタスクを起動する | すべて |
| `task.suspend` | 中断しうる（他のタスク・チャネル・時間・外部の応答を待つ） | すべて |
| `task.share` | 他のタスクと共有する値を読み書きする（`SyncShared` を通した `Lock` の操作、チャネルの送受信、原子的な値） | すべて |

- **他のタスクを観測する操作は必ず中断点**: `task.share` の操作のうち、他のタスクの書き込みを観測できるもの（チャネルの受信、`Lock` の取得、原子的な値の読み出し）は、すべて `task.suspend` も起こす。中断しない「試すだけ」の操作（受信の試行・取得の試行）は持たない。これにより、中断点を通らずに他のタスクを待つこと（原子的な値でのスピン待ちなど）は書けない（決定 5 の進行性）。

- **どの操作が中断するか**: 他のタスクの終了の待機（`join`、範囲の終わり）、チャネルの送受信、`Lock` の取得、原子的な値の読み出し、時間の待機、`task.yield`（他のタスクに実行を譲る）、ネットワーク（`net.client`・`net.server`）と `db` の応答の待機は `task.suspend` を起こす。`console`・`fs.read` / `fs.write`・`process` の起動は中断せず、その間 OS スレッドを止める（ネイティブの実行の割り当ては、止まった OS スレッドの代わりに別の OS スレッドで他のタスクを続ける）。この線引きにより、P0 のサンプル（`fs.read` を使う）の効果の宣言は変わらない。
- **推論**: `task.*` も他のカテゴリと同じく「呼び出した関数の効果の和」で推論し、宣言と完全一致を検査する（ADR 0004 の規則 3）。`task.scope(f)` の効果は `task.suspend, of(f)`、`s.spawn(g)` の効果は `task.spawn, of(g)` とする（子のタスクで起こる効果も、起動した関数の効果に数える）。
- **関数の色**: 中断しうるかは `task.suspend` の有無として仕様に現れる。`apply_all` のような高階関数は `of(f)` により、中断する関数にも中断しない関数にもそのまま使える（ADR 0006 の条件 5 の検討の答え）。中断しない関数の中から中断する関数を呼ぶ方法（同期的に待つ API）は通常のコードに持たない。入口が最初からタスクなので不要である。
- **`state`**: 意味を変えない。`state` は単一スレッド用の共有所有の型（`Shared`・`Cell`）を通した書き換えで、そのタスクの中だけで観測できる。他のタスクと共有する値の読み書きは `task.share` とする（ADR 0006 の条件 6 への答え: 分ける。ただし `state` の下位ではなく別のカテゴリにする）。
- **`clock`**: 意味を「現在時刻を読む・時刻を基準に待つ」のまま保つ。時間を待つ操作（`sleep`・時間切れ）は `clock, task.suspend` を起こす。同期的に待つ（OS スレッドを止める）操作は持たない（ADR 0006 の条件 7 への答え。P0 の「同期的に待つ実装だけを持つ」を改める）。
- **破棄の処理**: 型が定める後始末（破棄の処理）は `task.suspend` を起こせない。破棄の処理も `effects` 節を持つ関数として定義し（定義の表記は型システムの範囲の論点で決める）、その宣言に `task.suspend` を含めるとコンパイルエラーにする。完全一致の検査（ADR 0004 の規則 3）により、本体が `task.suspend` を起こせば宣言にも現れなければならないので、宣言を検査すれば足りる。ネットワークの接続などの丁寧な終了（相手に終了を伝えて待つ）は、破棄の前に明示的な関数で行う。

## 決定 4: 中断点をまたぐ借用と、取り消し時の破棄

### 選択肢

- **A: 中断点をまたぐ借用を禁止する**: 借用の引数を持つ関数は中断できない。
- **B: 同じタスクの中では許す**: 借用は中断点で終わらない。タスクをまたぐ借用は、起動するクロージャが借用をとらえられないこと（決定 1 の規則 3）で禁止される。

A では、`fn handle(req: &Request) ... effects task.suspend` のような関数が書けず、値を移動するか複製する定型が増える（観点 2）。B は安全である。借用の元の値は同じタスクの呼び出し元の枠にあり、呼び出し元は呼び出し先が戻るまで止まっている。他のタスクはその値に触れられない（`Sendable` でない値はタスクの外に出られず、`Sendable` な値も移動した後は元のタスクから使えない）。**B** を採用する。

- ADR 0006 の条件 8 で用意する借用の区間の計算は、中断点で借用を終わらせない。中断点は、中断をまたいで生きる値（借用を含む）を求めて、中断する関数を状態機械に変換する（決定 5）ためにだけ使う。
- `Lock` の中で中断してもよい（`Lock` はタスク用の排他制御で、待つ側はタスクとして中断する）。デッドロックは型では防げないので、標準ライブラリの説明と、テスト用の実行環境（下記）で扱う。

### 取り消し

- **取り消しの単位は範囲**: 取り消しは範囲全体（本体と、そこで起動したすべての子のタスク、さらにその内側の範囲）に対して要求する。個々の取っ手を取り消す操作は持たない。取り消しを要求するのは次の 2 つだけである。
  - 外側からの伝播: タスクが取り消されると、その中で開いている範囲もすべて取り消される。
  - 標準ライブラリの部品: `task.all_ok(gs)`（すべての子が `Ok` を返せば一覧を返し、最初に `Err` を返した子があれば、その範囲の残りを取り消してその `Err` を返す）、`task.race(gs)`（最初に終わった子の値を返し、残りを取り消す）、`task.timeout(d, g)`（時間切れなら取り消して時間切れを返す）。これらは中で範囲を開き、自分が開いた範囲だけを取り消す。子のタスクが兄弟を取り消すことはできない（`s` をとらえられないため）。1 件の失敗で兄弟を取り消したいときは、これらの部品を使う。
  - 部品の戻り方と効果: これらの部品は、取り消した子がすべて止まり（次の中断点に達し、決定 4 の順序で破棄を終え）てから戻る。範囲の規則（決定 1 の規則 2）どおり、戻った後に動き続ける子はない。効果は、`task.all_ok(gs)`・`task.race(gs)` が `task.spawn, task.suspend` と `gs` の要素の関数の効果の和、`task.timeout(d, g)` が `clock, task.spawn, task.suspend, of(g)` である。関数の一覧の効果の和を引き継ぐ表記（ADR 0004 の規則 4 の `of(f)` を一覧に広げるもの）は、型システムの範囲の論点で決める。
- **取り消しは中断点でだけ起こる**: 取り消しを要求されたタスクは、次に中断点に達した時点で止まる。中断しない区間の途中では起こらない。
- **破棄の順序**: 取り消されたタスクは、中断点からその関数が早期に戻ったときと同じ順序で値を破棄する（ADR 0006 の条件 9 の規則の延長）。内側の呼び出しの枠から外側へ、各枠では宣言の逆順に破棄する。取り消された関数の `ensures` は検査しない（戻り値を返していないため）。
- **取り消しは値ではない**: 中断しうる関数の戻り値に取り消しを表す型は加えない。取り消された範囲の本体と子は値を返さずに止まり、取り消しの結果は、取り消しを要求した部品の戻り値（`task.all_ok` の `Err`、`task.timeout` の時間切れ）としてだけ現れる。
- **契約違反**: タスクの中の契約違反は、P0 と同じくプログラム全体を停止する（ADR 0006 の決定 5）。サーバーで 1 件の要求の失敗をどう隔離するかは、P1 の範囲を決める ADR で検討する。

### テスト用の実行環境

ADR 0004 の規則 7 の延長として、テスト用の実行環境では実行の割り当てを差し替え、タスクの実行順を固定する・乱数の種で変えることができる。時間の待機は仮想の時計で進める。

## 決定 5: 出力先ごとの違いと Python 連携

### 意味の定義

- **順序**: 並行に動くタスクの間の順序は、`task.share` の操作と `task.suspend` の待ち合わせの順序としてだけ観測でき、その順序は決まっていない。
- **進行性**: タスクの切り替えは中断点でだけ起こるとみなす。保証するのは「タスクが中断点に達したとき、実行できる他のタスクがあればいずれ進む」ことだけである。中断点に達しないタスクは、他のタスクを止めてよい（JavaScript とブラウザの WebAssembly では実際に止まる。ネイティブで他のタスクが並列に進むことを、プログラムは前提にしてはならない）。
- **中断点を通らない待機は書けない**: 他のタスクを観測する操作はすべて中断点である（決定 3）ので、他のタスクの進行を待つ処理は必ず中断点を通る。単一スレッドの協調的な実行でも、待っている側が中断して待たれている側が進むので、ネイティブで終わるプログラムがブラウザで止まることはない。
- データ競合がない（決定 2）ので、上の 2 点のもとで、出力先による違いは「どの順序が実際に起こるか」と「中断点のない長い計算の間に他のタスクが進むか」だけであり、許される振る舞いの範囲は同じである。長い計算は、`task.yield` を挟んで他のタスクに譲る。

### 出力先

| 出力先 | 実行の割り当て | 中断する関数の変換 | 並列性 |
|---|---|---|---|
| ネイティブ | OS スレッドの集まりの上で多数のタスクを割り当てる（P1） | `task.suspend` を持つ関数だけを状態機械に変換する。他の関数は変換しない | 複数の CPU で並列に動く |
| WebAssembly（ブラウザ） | 単一スレッドで、ブラウザのイベントループに合わせて割り当てる（P2） | ネイティブと同じ変換 | 並列に動かない。WebAssembly のスレッド（Web Worker と共有メモリ）は P2 の ADR で検討する。`Sendable` の検査を出力先によらず行うので、後で並列にしてもプログラムは変わらない |
| JavaScript | 同上（P2） | `task.suspend` を持つ関数を JavaScript の非同期関数に、中断点を `await` に変換する | 並列に動かない |

- 中断しうるかは効果から静的に分かるので、変換する関数は必要なものに限られる。再帰する中断する関数は、呼び出しの枠をヒープに確保する。
- 出力先による効果の制限（ADR 0004 の規則 5）は、`task.*` に対しては置かない（すべての出力先で使える）。ブラウザで中断点のない長い計算は画面と他のタスクを止める。これは型では防げないので、UI の記述モデルの ADR（P2 の前）で扱う。
- 同期的に待つ API を持たないことで、ブラウザのイベント処理の中で止まる誤りは書けない。

### Python 連携の境界

詳細は Python 連携の ADR（P3 の前）で決める。本 ADR では次の前提を置く。

- Python に公開する関数の引数・戻り値と、Python 側の取っ手が持つ型は `Sendable` に限る。Python 側の複数のスレッド（GIL のない Python を含む）から呼ばれうるためである。
- `task.suspend` を持つ公開関数は、束縛が Sigil の実行環境のタスクとして実行し、呼び出した Python のスレッドはその終了を待つ（待つ間は GIL を手放す）。Python の `asyncio` から待てる形で公開するかは、Python 連携の ADR で決める。
- Python から受け取った関数の呼び出し（`foreign`）は中断しない（`task.suspend` を起こさない）呼び出しとして扱い、呼び出しの間 OS スレッドを止める。

## 決定 6: ADR 0006 の 11 条件（＋追加の条件 12）への答えと実装の時期

並行処理そのものの実装は P1 で行う。P1 の段階分けは P1 の範囲を決める ADR で決めるが、本 ADR では次の順を前提にする: (P1-a) M3・M4 のインタプリタに単一スレッドの実行割り当てとテスト用の実行環境の差し替えを加える、(P1-b) ネイティブ出力に状態機械の変換と複数の OS スレッドの実行割り当てを加える。WebAssembly・JavaScript の実行割り当ては P2 で作る。

| 条件 | 本 ADR の答え | P0 での確かめ（ADR 0006 の表のまま） | 並行処理の実装とテスト |
|---|---|---|---|
| 1. 型の性質の導出 | 必要。`Sendable`・`Shareable` を登録する（決定 2） | M1・M2 | P1-a: 2 つの性質を登録し、決定 2 の表の各型について導出結果を固定する |
| 2. 共有所有の型を分ける | 必要。スレッド間用は `SyncShared`・`Lock`（決定 2） | M4 | P1-a: `Shared` から `SyncShared` への暗黙の変換がエラー、`Shared` をとらえたクロージャの起動がエラー |
| 3. クロージャのとらえた値 | 必要。起動するクロージャの `Sendable` の検査に使う（決定 1 の規則 3） | M2 | P1-a: 借用をとらえたクロージャ、`Sendable` でない値をとらえたクロージャの起動がエラー |
| 4. カテゴリを追加できる実装 | 必要。`task.*` を追加する（決定 3） | M1 | P1-a: 標準ライブラリの表に `task.*` を加え、コンパイラを変えずに検査が働く |
| 5. 非同期を効果として扱う余地 | 効果として扱う（`task.suspend`）。関数の色は `of(f)` で緩和する（決定 3） | M1 | P1-a: `apply_all` に中断する関数を渡すと `of(f)` が `task.suspend` に置き換わる |
| 6. `state` の粒度 | 分ける。`state` は変えず、スレッド間は `task.share`（決定 3）。`state` の下位カテゴリは使わない | M1 | P1-a: `Lock` の操作が `task.share` と推論され、`state` では一致しない |
| 7. `clock` の待つ | 時間を待つ操作は `clock, task.suspend`。同期的に待つ操作は持たない（決定 3） | —（P0 は `clock` を入れない） | P1-a: `sleep` の効果の推論、仮想の時計での時間切れと取り消し |
| 8. 借用の区間の計算 | 必要。ただし中断点で借用は終わらない。中断点は中断をまたいで生きる値を求めるのに使う（決定 4） | M2 | P1-a: 借用の引数を持つ中断する関数が検査を通る。P1-b: 中断をまたぐ値の計算が区間の部品を使う |
| 9. 破棄の地点の規則 | 必要。取り消しは早期の戻りと同じ順序（決定 4） | M3・M5 | P1-a: 取り消し時の破棄の順序を、破棄を記録するテスト用の型で固定する。P1-b: 実行ファイルでも同じ順序 |
| 10. ランタイムの分割 | 必要。実行の割り当ては OS 依存部分に置く（決定 1 の規則 7） | M4・M5 | P1-b: 核の部分だけを使うプログラムが実行の割り当てに依存しない |
| 11. 出力先による制限 | `task.*` は全出力先で使える。規則 5 の仕組みはそのまま使える（決定 5） | M1 | P1-a: 単一スレッドの実行割り当てで、原子的な値を待つタスクと書くタスクの組が止まらずに終わる。P2: 同じプログラムをネイティブと JavaScript で動かし、テスト用の実行環境で順序を固定したときの結果が一致する。あわせて、他のタスクの進行を待つプログラム（チャネル・`Lock`・原子的な値）が JavaScript でも止まらずに終わる（決定 5 の進行性） |

- **条件 12: 大域の可変な値を持たない**（決定 1 の規則 8）。P0 では無条件に禁止し、M1 で、大域の可変な値の宣言がエラーになることをテストで固定する。

## 未決として残す点

- 大域の可変な値を `Shareable` な型に限って許すか（決定 1 の規則 8）。
- 破棄の処理の定義の表記（型システムの範囲の論点）。
- WebAssembly のスレッドの導入の時期と方法（P2 の ADR）。
- サーバーで 1 件の要求の契約違反を隔離するか（P1 の範囲の ADR）。

## 根拠の限界と再検証

- 「`async` / `await` が AI にとって誤りやすい」「中断を効果にすれば関数の色の問題が緩和される」は、一般に知られている傾向に基づく定性的な判断で、計測していない。
- 「タスク全体は `Sendable` でなくても別の OS スレッドに移れる」は、大域の可変な値がないこと（決定 1 の規則 8）と、信頼基盤がスレッドごとの領域に値を隠さないことを前提にしている。信頼基盤の実装でこの前提が崩れると、データ競合の排除が成り立たない。P1-b で、信頼基盤の検査を外した箇所の契約にこの前提を書く。
- `fs` の操作を中断点にしない線引きは、ネイティブの実行の割り当てが止まった OS スレッドを補うことを前提にしている。多数のファイル操作を同時に行うサーバーで性能の問題になる場合は見直す。
- 構造化並行処理だけで、切り離されたタスクなしにサーバー・UI の実用の課題を書けるかは未検証である。
- 中断点のない長い計算は取り消せず、それを含む範囲は計算が終わるまで戻らない（時間切れも効かない）。`task.yield` を挟むことは AI の書き方に任せており、検査では強制しない。
- 子のタスクには借用を渡せない（決定 1 の規則 3）ので、親の大きな値を子が読むには、移動するか `SyncShared` に入れる必要がある。範囲が子より長く生きることを使えば借用を渡しても安全になりうるが、ADR 0003 の規則 5 の例外になるため採らなかった。実用の課題で複製や `SyncShared` が多発する場合は見直す。
- 原子的な値の読み出しを中断点にしたため、ネイティブでは読み出しごとに実行の割り当てを経由する費用がかかりうる。
- 候補の案出しと採点を同じ者（Claude）が行っており、偏りがありうる。
- 次の場合は、この ADR を見直す。
  - P1 で、AI が書いたコードの `task.*` の効果の一致検査のエラー率が、他のカテゴリより大きく高い場合
  - 中断点をまたぐ借用の許可（決定 4）が、状態機械への変換で実装できない場合
  - ブラウザで並列に動かないことが、P2 の UI の課題で問題になった場合（WebAssembly のスレッドの導入の前倒し）
