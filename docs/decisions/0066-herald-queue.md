- **状態**: 提案

## 背景

`sigil-herald-queue` は、Sigil 製のメッセージキュー部品である。非同期ジョブの置き場として、メール送信、重い処理の後回し、部品間の疎結合な連携に用いる。

### 既に決まっていること・前提

1. **未着手部品の共通前提**:
   - メール送信の再試行と遅延配送（`sigil-raven-mail`）
   - 脅威インテリジェンスの配布（`sigil-beacon-intel`）
   - 動画変換ジョブの投入（`sigil-lantern-stream`）
   - SNS の通知配送（`sigil-agora-post`）
   - サーバーレスのイベント口（`sigil-summon-functions`）
   これら後続部品が本部品を利用する想定となっており、後続部品の設計が本 ADR の決定に依存する。
2. **着手順の決定（2026-11-25）**:
   部品群の実装順序を typesafe-ai 正式判定（`jev-1.13.0`）で再考し、`sigil-herald-queue` が第2件目に決定した。第1件目の `sigil-shield-tls` は 2026-11-27（JST）に全段完了（ADR 0063 の Sigil 実装完了、G3 の最終判断で公開と PR のマージが承認）したため、本部品の開始手続きを行う（計画下書き `backend-suite-plan-draft.md` §22、Issue #768 担当決めの記録）。
3. **仕様と実装のリポジトリ分離**:
   仕様は sigil リポジトリの ADR として起草・管理し、実装は独立したリポジトリ `goodnasubi/sigil-herald-queue` に置く（ADR 0044 決定 4 のパターン、sigix・KV・認証・shield-tls と共通）。
4. **先行部品の利用可能性**:
   `sigil-db`（ADR 0045、データベース核）および `sigil-stash-kv`（ADR 0059、単一キー KV）の実装が完了している。

## 決定 1 — 持ち方の選択（独立したキューサーバー）

計画下書き §4 の 3 つの選択肢を比較検討した。

| 案 | 概要 | 利点 | 欠点 |
|---|---|---|---|
| **A: 独立キューサーバー（採用）** | 投入・取得・確認応答（ack）を持つ専用デーモンプロセスとして動作 | ブロッキング待機（長いポーリング）を提供でき、無駄なポーリング負荷を排除できる。部品間の結合度が最も低く、キュー固有のライフサイクル（不可視時間、再試行、DLQ）を厳密に管理できる | 独立プロセスの管理・通信オーバーヘッドが加わる |
| **B: KV ストア（sigil-stash-kv）の上** | stash-kv のキー・バリュー操作の上にライブラリとしてキューを構築 | 新しいデーモンが不要 | stash-kv は単一キーの GET/PUT/DELETE に特化しており（ADR 0059）、リスト構造・複数キー原子的操作・通知機構を持たない。ワーカー間の競合制御や待機の実装が困難で信頼性が著しく低下する |
| **C: sigil-db のジョブ表とポーリング** | 各部品が共通の sigil-db テーブルを直接ポーリング（`SELECT FOR UPDATE` 等） | 専用サーバーが不要で、業務データと同一トランザクションでジョブを投入しやすい | 多数のワーカーによる高頻度ポーリングが DB 本体の接続数・トランザクション競合のボトルネックになる。各部品が sigil-db のスキーマに直接結合し疎結合性が失われる |

### 決定理由

**案 A（独立キューサーバー）を採用する。**
`sigil-stash-kv` は単一キー操作を前提とした設計であり、キューとしての待ち行列・不可視時間・原子的リースを支えるには不適である。また、`sigil-db` への直接ポーリングは DB への負荷集中と強結合を招く。
投入（enqueue）・取得（dequeue）・確認応答（ack/nack）の責務を一元管理する独立サーバーとすることで、ワーカーの待機を効率的に処理し、後続部品群（メール・動画変換・通知等）に対して統一的で疎結合な非同期実行基盤を提供する。

## 決定 2 — 配送保証の水準とライフサイクル

### 2.1 配送セマンティクス（at-least-once）

配送保証は **at-least-once（少なくとも1回配送）** を基本とする。
ネットワーク分断、ワーカープロセスの突然死、処理遅延・タイムアウトが存在する環境において、中央キュー単体で完全な exactly-once を保証することは困難であり、過度な分散トランザクション負荷を生む。各利用者部品（メール送信、通知配信等）は、重複配送が発生しうる前提で冪等性（同一ジョブの再実行耐性）を持つ設計とする。

### 2.2 リース方式と不可視時間（Visibility Timeout）

ジョブの取得と確認応答にはリース方式を採用する。

1. **取得と不可視化**:
   - ワーカーがジョブを取得（`DEQUEUE`）すると、ジョブは指定されたリース期間（`lease_seconds`、既定例: 30秒）の間、他のワーカーから不可視（invisible）になる。
   - 取得時、キューサーバーはジョブごとに一意な一時トークン `lease_token`（16バイト）を払い出す。
2. **確認応答（ACK）**:
   - ワーカーが処理を完了した際、`job_id` と `lease_token` を添えて `ACK` を送る。
   - トークンが一致し、かつリース期間内であれば、ジョブはキューから完全に削除される。
   - リース期限切れ後に別ワーカーへ再リースされていた場合、旧ワーカーの `ACK` は `TokenExpired` エラーとなり、不整合な二重削除や他ワーカーの成果物破壊を防ぐ。
3. **明示的な拒否・一時失敗（NACK）**:
   - ワーカーが一時的なエラー（外部 API の一時障害等）を検出した場合、`NACK` を送信できる。
   - `NACK` を受け取ると、キューは不可視時間を即座に解除するか、指定された遅延時間（バックオフ秒数）を付与してジョブを待機状態（Ready）に戻す。
4. **リース期限切れ（Timeout）**:
   - ワーカーがクラッシュまたは無応答となり、リース期間内に `ACK` も `NACK` も届かなかった場合、キューサーバーは自動的に不可視状態を解除し、再配送可能とする。

### 2.3 順序保証の範囲

- 単一キュー内において、投入時刻順（FIFO）での配送を基本方針とする。
- ただし、再試行が発生したジョブ、遅延指定されたジョブ、および複数ワーカーが並行取得する環境下では、厳密な全体順序は維持されない（ベストエフォート FIFO）。
- 初版ではメッセージグループ単位の厳密な順序付け（FIFO グループ）は導入せず、後続の検討とする。

### 2.4 再試行とデッドレターキュー（DLQ）

- 各ジョブは最大再試行回数（`max_retries`、既定値: 3回、ジョブ投入時に個別指定可能）を持つ。
- ワーカーのリース期限切れまたは `NACK` により再配送されるたびに、試行回数（`attempt`）が 1 増加する。
- `attempt > max_retries` に達したジョブは、処理不能な異常メッセージ（Poison Message）とみなし、自動的に当該キューに紐づくデッドレターキュー（DLQ: 例 `queue_name.DLQ`）へ移動する。これにより、異常ジョブがキュー先頭で無限再試行されてシステム全体が滞留することを防ぐ。
- DLQ 内のジョブは破棄されず保持され、管理者が `INSPECT` や再投入（Redrive）、明示削除（`DELETE`）できる。

### 2.5 遅延配送（Delayed Messages）

- ジョブ投入時に遅延秒数（`delay_seconds`、0〜86400秒）を指定できる。
- 指定された秒数が経過するまでジョブは不可視となり、`DEQUEUE` の対象にならない。
- これは `sigil-raven-mail` における送信遅延や再送バックオフ要件を直接支援する。

## 決定 3 — 永続化の持ち方と復旧の振る舞い

### 3.1 永続化基盤（sigil-db 核の利用）

永続化には [ADR 0045](0045-p4-1-database-core.md) の `sigil-db` 核（型付き関係 API・WAL・直列トランザクション・復旧機構）をライブラリとして内部利用する（[ADR 0059](0059-kv-store.md) `sigil-stash-kv` と同一の方式）。

| 方式 | 評価 |
|---|---|
| **専用の追記ログ（WAL）を独自開発** | キュー専用に特化した最適化が可能だが、クラッシュ耐性・fsync 同期・チェックポイント・破損復旧の検証コストが過大であり、新たな脆弱性やデータ消失のリスクを抱える |
| **sigil-db 核の組み込み利用（採用）** | 既に検証済みの堅牢な WAL と直列トランザクションを再利用できる。信頼基盤を増やさず、最小限の工数で高い永続性保証を得られる |

- ジョブの投入・状態遷移・ACK による消去は、sigil-db 核の直列トランザクションを通じて WAL に同期記録する。
- 投入完了の応答（`Enqueued`）は、WAL への同期書き込み完了後にのみクライアントへ返す。
- メモリ専用モード（永続化を行わない高速モード）もオプションとして備え、単体テストや揮発を許容する一時ジョブで利用可能とする。

### 3.2 再起動時の復旧の振る舞い

キューサーバーがクラッシュまたは再起動した場合、起動時に sigil-db 核の WAL から最新状態を復元する。

1. **Ready 状態のジョブ**: そのまま待機キューに復元される。
2. **Leased（処理中）だったジョブ**:
   - クラッシュ時にワーカーに貸出中だったジョブは、クラッシュによってワーカーとの接続が途絶したとみなし、試行回数（`attempt`）を 1 加算した上で、即座に Ready 状態に戻す（または `max_retries` を超えていれば DLQ へ移送）。
   - これにより、サーバー再起動によって処理中ジョブが永久に行方不明（ロスト）になることを防止する。
3. **Delayed（遅延中）のジョブ**: 保存された目標時刻（投入時刻 ＋ 遅延秒数）と現在時刻を比較し、既に経過していれば Ready、未来であれば残り時間待機する。
4. **ACK 済みジョブ**: トランザクションコミット済みの削除は復旧後も完全に消去されている。

## 決定 4 — API とプロトコル

### 4.1 基本操作

クライアントとキューサーバー間の論理操作は以下の通り。

| 操作 | 引数 | 戻り値 | 振る舞い |
|---|---|---|---|
| `ENQUEUE` | `queue: String`, `payload: Bytes`, `delay_seconds: u32`, `max_retries: u32` | `Result<JobId, QueueError>` | ジョブを投入し、一意な `JobId`（UUID / 64bit ID）を返す。 |
| `DEQUEUE` | `queue: String`, `lease_seconds: u32`, `wait_seconds: u32` | `Result<Option<Job>, QueueError>` | ジョブを取得する。ジョブが無い場合、`wait_seconds`（最大 30秒）までロングポーリング待機する。ジョブには `id`, `payload`, `attempt`, `lease_token` が含まれる。 |
| `ACK` | `queue: String`, `job_id: JobId`, `lease_token: Bytes` | `Result<(), QueueError>` | ジョブの完了を通知し、キューから削除する。トークン不一致または期限切れはエラー。 |
| `NACK` | `queue: String`, `job_id: JobId`, `lease_token: Bytes`, `delay_seconds: u32` | `Result<(), QueueError>` | 一時失敗を通知し、ジョブを Ready 状態（遅延付き可）に戻す。 |
| `INSPECT` | `queue: String` | `Result<QueueStats, QueueError>` | 待機数、処理中数、DLQ 数などの統計情報を取得する。 |
| `PING` | なし | `Result<(), QueueError>` | 接続確認および死活監視。 |

### 4.2 プロトコルとデータ形式

[ADR 0059](0059-kv-store.md)（sigil-stash-kv）の設計規則を踏襲し、**版付きの長さ付きバイナリプロトコル（TCP）** を採用する。

- **フレーム構成**:
  - `Frame Length` (32 bit, ビッグエンディアン): 版からフレーム末尾までのバイト長（上限: 64 KB または 1 MB）。
  - `Protocol Version` (8 bit): 初版は `1`。
  - `Command / Response Type` (8 bit): 操作または結果の種別コード。
  - `Payload Body`: コマンド固有の引数・応答データ。
- **ペイロードの透過性**:
  ジョブ本文（`payload`）は任意のバイナリ列（`Bytes`）として扱い、キューサーバー自体は中身のフォーマット（JSON、Protobuf 等）を解釈しない。
- **待ち受けとセキュリティ**:
  - 既定の待ち受けはループバック（`127.0.0.1`）。
  - 外部接続を許可する場合は、明示的に設定された内部隔離ネットワークに限定する。
  - DoS 対策として、同時接続数上限、フレーム長上限（既定 1MB）、読み書きタイムアウト（既定 10秒、ロングポーリングを除く）を設ける。

### 4.3 Sigil クライアントライブラリ

`sigil-herald-queue` リポジトリ内で、上記プロトコルを抽象化した型付きクライアント `sigil_herald_queue::Client` を提供する。各後続部品（`raven-mail` 等）はこのクライアントをインポートして利用する。

## 決定 5 — 実装段の分割と完了条件

実装は 4 つの独立した段階に分割して進める。各段階は単独でビルド・テスト可能とする。

| 段 | 段階名 | 成果物と完了条件 |
|---|---|---|
| **1** | キューの核と契約（メモリ内モデル） | メモリ内で動作する純粋なキュー状態機械（Ready / Leased / Delayed / DeadLettered）の実装。モック時計を用いて、投入、リース取得、不可視時間、ACK/NACK、最大再試行回数、DLQ 移送、遅延投入の振る舞いを網羅した単体テストを整える。 |
| **2** | sigil-db 核を用いた永続化アダプター | 固定版の `sigil-db` 核を組み込み、ジョブの保存と状態変更を WAL・トランザクションへ記録する。プロセス中断・再起動を模擬した試験を行い、クラッシュ時に処理中だったジョブが安全に再配送され、ACK 済みジョブが確実に消去されていることを検証する。 |
| **3** | TCP プロトコルと Sigil クライアント | 版付きバイナリプロトコルのサーバー実装、ロングポーリング（`wait_seconds`）機構、および型付き Sigil クライアントライブラリ。ループバック経由の統合試験、不正フレームや上限超過に対する防御試験、パーサーのファジングを実施する。 |
| **4** | 負荷・境界試験と公開前記録（G2） | 大量ジョブ投入時の資源上限（メモリ・ディスク枯渇時の振る舞い）、ワーカー突然死時の Poison Message 耐性試験。ADR 0020 G2 基準に基づくセキュリティ検証記録（`docs/pre-publish-record.md`）を作成する。 |

## 影響と適合の限界

### 影響
- 後続の未着手部品（`sigil-raven-mail`、`sigil-beacon-intel`、`sigil-lantern-stream`、`sigil-agora-post`、`sigil-summon-functions`）は、本 ADR の API 仕様およびクライアントライブラリに準拠して非同期処理を設計・実装できる。
- バックエンド全体において、非同期タスクのためのポーリング実装が sigil-db に乱立することを防止し、疎結合なアーキテクチャが確立される。

### 適合の限界
- **単一ノード限定**: 初版は単一インスタンス（単一ノード）での運用を前提とする。複数ノード間でのデータ複製（レプリケーション）や分散コンセンサスは持たない。
- **全体順序の保証外**: 並行ワーカー環境や再試行時における厳密なグローバル FIFO 順序は保証しない（決定 2.3）。
- **ペイロード上限**: 1 ジョブあたりのペイロードは最大 1MB（既定）とし、動画や大容量ファイルの直接格納は行わない（オブジェクトストレージやファイルパスの参照を渡す運用とする）。

## 正式判定（typesafe-ai）の記録

### 判定の準備と経緯

AGENTS.md の「判断の手順」（理念 → typesafe-ai 正式判定）に従い、起草にあたって判定項目を整理した。
起草セッション環境には判定 API の認証キー `TYPESAFE_API_KEY` が設定されておらず、起草時点での API 呼び出しは実施できなかった（先例 ADR 0044、ADR 0060、ADR 0065 と同一の状況）。そのため、評価軸および 5 つの判断点の問い・選択肢・起草者採用案を以下に記録し、見張り・所有者による確認・追認が可能な状態とする。

### 固定する評価軸（state）

```text
ADR 0001・0005・0027 の理念に基づき、人間が仕様をレビューできる明示的な型付き契約、メモリ安全性、既存の検証済み部品（sigil-db 核）の再利用、小さく単独で検証できる実装段階を最優先とする。ADR 0020 の最小権限と資源上限、ADR 0044 決定 4 の仕様と実装のリポジトリ分離を守る。
前提: Sigil 製の後続バックエンド部品群（メール、インテリジェンス、動画変換、SNS通知、イベント処理）が共通で利用するメッセージキュー基盤であること。初版は単一ノードでの確実なジョブ永続化と安全な再配送（at-least-once、不可視時間、デッドレター）を担保し、不要な複雑性と結合を避けること。
```

### 問いと採用案の一覧

| 問い | 選択（起草者の採用案） | 理由・根拠 |
|---|---|---|
| **Q1: 持ち方の選択 (Architecture)** | `standalone_server`: 独立したキューサーバープロセス | stash-kv（単一キー特化）の上では不可視制御が困難。sigil-db 直接ポーリングは DB 負荷と強結合を招くため、独立サーバーが最適。 |
| **Q2: 配送保証 (Delivery)** | `at_least_once_lease`: at-least-once ＋ リース（不可視時間） ＋ DLQ | 分散環境での現実的かつ堅牢な保証。ワーカークラッシュ時の再配送と Poison Message 隔離を両立する。 |
| **Q3: 永続化基盤 (Storage)** | `db_core`: `sigil-db` 核（WAL・トランザクション）を内部利用 | 自前の追記ログ開発による車輪の再発明とクラッシュ耐性の欠陥リスクを避け、検証済み核を再利用する（stash-kv と同方針）。 |
| **Q4: プロトコル (Protocol)** | `versioned_binary_tcp`: 版付き長さ付きバイナリ TCP ＋ Sigil クライアント | ADR 0059 踏襲。軽量で厳格な境界検査が可能。ペイロードは透過的なバイト列とする。 |
| **Q5: 実装段分け (Stages)** | `four_stages`: メモリ内核 → 永続化アダプター → TCP/クライアント → 負荷・G2 | 永続化と通信を段階的に分離して単体・統合試験を確実に積み上げる構成。 |
