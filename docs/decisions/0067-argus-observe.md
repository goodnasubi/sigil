# 0067: 監視・ログ収集（sigil-argus-observe）

- **状態**: 提案
- **日付**: 2026-11-27（JST）
- **対象**: [Issue #771](https://github.com/goodnasubi/sigil/issues/771)、レーン E
- **仕様基準**: sigil の `main`、`8498243`
- **範囲**: ADR の起草のみ。実装リポジトリは `goodnasubi/sigil-argus-observe`（[ADR 0044](0044-p4-scope.md) 決定 4 のパターン）。本リポジトリのコンパイラ・標準ライブラリのコード変更は含めない。

---

## 背景

`sigil-argus-observe` は、Sigil 製の監視・ログ収集部品である（利用者向け製品名は Scan、2026-11-23 決定）。各部品のメトリクスとログを集めて見る場所であり、異常の検知と後からの原因追跡の土台となる。各部品が生きているかの確認と通知（死活監視）も本部品の核に含める。

### 既に決まっていること・前提

1. **後続・関連部品との連携**:
   - `sigil-aegis-waf`: 検知・遮断の記録の送り先として本部品を使う。
   - `sigil-vigil-ops`: 自律障害解決の層。本部品の検知・メトリクス・ログを入力にして原因特定と復旧手順の選択を行う。
   - `sigil-beacon-intel`: 脅威インテリジェンス部品。「argus-observe が観測し、beacon-intel が指標の集約と配布を担う」分担とする。
   - `sigil-hourglass-time`: 時刻同期部品。クロックのずれ（ドリフト）を本部品へ知らせる連携を将来像に含む。
2. **着手順の決定（2026-11-25）**:
   部品群の実装順序を typesafe-ai 正式判定（`jev-1.13.0`）で再考し、`sigil-argus-observe` が第3件目に決定した。第1件目の `sigil-shield-tls` は 2026-11-27（JST）に全段完了し、第2件目の `sigil-herald-queue` も同日に実装第4段および G3（外部公開の承認）まで全項目決定済みで完了したため、本部品の開始手続きを行う（計画下書き `backend-suite-plan-draft.md` §22、Issue #771）。
3. **形式の先行**:
   集める側より先に「各部品が出すログ・メトリクスの形式の約束」が必要である。形式が部品ごとにばらけると収集側が差異を吸収し続けることになるため、部品が増える前に共通の約束を決める（計画下書き §6、§22）。
4. **現状の制約**:
   `sigil` 本体の `src/stdlib` にログ・メトリクス専用のモジュールは存在せず、各部品は現状、標準出力へ書き出すしかない。構造化の材料として `src/stdlib/json.sigil`（ADR 0013 / ADR 0038）が利用可能である。
5. **仕様と実装のリポジトリ分離**:
   仕様は sigil リポジトリの ADR として起草・管理し、実装は独立したリポジトリ `goodnasubi/sigil-argus-observe` に置く（ADR 0044 決定 4 のパターン、sigix・KV・認証・shield-tls・herald-queue と共通）。リポジトリは作成済み（README のみ）。

## 本 ADR で決めないこと

- 実装そのもの（本 ADR の PR がマージされた後の各段で進める）。
- 利用者側の部品（`aegis-waf`、`vigil-ops`、`beacon-intel`、`hourglass-time` 等）の内部仕様。関係として連携インターフェースの要請のみを扱う。
- 総合監視ポータルの新設（2026-11-22 の typesafe-ai 正式判定で「新設せず、ポータルの役割は `sigil-orchestra` のダッシュボードが担い、監視データは `sigil-argus-observe` が供給する」と決定済み）。
- 複数ノード間の分散合意・クラスタリング（初版は単一ノードで堅牢に動作する監視デーモンとする）。
- 外部公開の承認（[ADR 0020](0020-p1-security-addendum.md) 決定 3 の G3 で所有者が判断する）。

## 決定 1 — 持ち方の選択（形式先行の約束と段階的収集サーバー）

計画下書き §6 の 2 つの選択肢を比較検討した。

| 案 | 概要 | 利点 | 欠点 |
|---|---|---|---|
| **A: 形式の約束先行** | ログ・メトリクスの形式（JSON 1 行等）だけを先に ADR で決め、各部品は標準出力／ファイルへ出力。収集・可視化サーバーは後段とする | 初期の実装負担が軽く、各部品が即座に統一された形式でログを出力できる | ログの集約・検索・死活監視・異常通知が各部品任せとなり、障害時の原因究明が遅れる |
| **B: 収集サーバーの一気開発** | 受け取り・保存・簡易な表示・死活監視を行う収集サーバーデーモンを一気に部品として構築する | 集中監視・死活監視・異常通知が一括で整い、後続部品の運用基盤が完成する | 設計・実装規模が大きく、監視対象部品がまだ少ない初期段階での検証が重くなる |

### 決定理由

**形式の約束を先行して厳格に規定し、段階的（4 段階）に収集サーバーを構築する折衷アプローチを採用する。**
各部品が独自形式でログを出力し始めると後の統一コストが跳ね上がるため、本 ADR でログおよびメトリクスの厳格な形式（スキーマ・フィールド名・型・制約）を最優先で確定する。
その上で、実装第 1 段として各部品が組み込める軽量なエミッターライブラリ（標準出力・バッファ出力）を提供し、第 2 段以降で収集・保存・死活監視サーバーを段階的に立ち上げる。これにより、各部品の開発をブロックせずに安全に集約監視基盤を整える。

## 決定 2 — ログ形式の約束（JSON Lines / NDJSON）

各部品が出力し、本部品が収集するログの共通フォーマットを規定する。

### 2.1 フォーマット

- **エンコーディング**: UTF-8。
- **構造**: 1 行 1 JSON オブジェクト（改行区切り JSON / NDJSON: `\n` 区切り）。
- **サイズ上限**: 1 行あたり最大 64 KB（65,536 バイト）。過大なログ出力によるバッファ溢れや DoS を防止する。上限を超過したメッセージは末尾を切り詰め、切り詰めを示すフィールドを付与する。

### 2.2 必須フィールド

すべてのログ行に以下の 4 フィールドを含める。

| フィールド | 型 | 説明 | 例 |
|---|---|---|---|
| `ts` | `String` | ISO 8601 / RFC 3339 形式（UTC、末尾 `Z`、ミリ秒またはマイクロ秒精度） | `"2026-11-27T11:22:40.123456Z"` |
| `component` | `String` | 出力元部品名（英小文字ハイフン区切り） | `"sigil-shield-tls"`、`"sigil-herald-queue"` |
| `level` | `String` | ログ水準（大文字）。`DEBUG`, `INFO`, `WARN`, `ERROR`, `FATAL` の 5 段階 | `"INFO"` |
| `msg` | `String` | 人間および AI エージェントが読むログ本文（改行コードを含めない） | `"connection accepted"` |

### 2.3 任意フィールド

必要に応じて以下のフィールドを追加できる。

| フィールド | 型 | 説明 |
|---|---|---|
| `trace_id` | `String` | リクエストや非同期ジョブを横断追跡する一意の識別子（UUID または 16進文字列） |
| `span_id` | `String` | 個別処理単位のスパン識別子 |
| `target` | `String` | 発生箇所のモジュール名・関数名 |
| `err` | `Object` | エラー詳細（`code`, `kind`, `message` 等の構造体） |
| `fields` | `Object` | 任意の構造化コンテキスト（キー・バリューの辞書） |

## 決定 3 — メトリクスの基本形

システムの稼働状況・性能・リソース消費を把握するためのメトリクスの構造を規定する。

### 3.1 メトリクスの種類

メトリクスは以下の 3 種類に限定し、解釈の曖昧さを排除する。

1. **Counter（カウンター）**:
   - 単調増加する累積値（リセット時を除く）。
   - 例: リクエスト総数（`http_requests_total`）、エラー総数（`job_errors_total`）、受信バイト数（`bytes_received_total`）。
2. **Gauge（ゲージ）**:
   - 任意に増減する現在の瞬時値。
   - 例: 現在の接続数（`active_connections`）、キュー滞留数（`queue_depth`）、メモリ使用量（`memory_used_bytes`）。
3. **Histogram（ヒストグラム）**:
   - 観測値の分布（処理時間・レイテンシ・サイズ等）。
   - 累積観測数（`_count`）、累積合計値（`_sum`）、および定義済みバケット上限ごとの観測数（`_bucket{le="..."}`）を記録する。

### 3.2 データ構造

メトリクスの表現形式（JSON オブジェクト）:

```json
{
  "ts": "2026-11-27T11:22:40.123456Z",
  "component": "sigil-herald-queue",
  "name": "queue_depth",
  "type": "gauge",
  "value": 42.0,
  "labels": {
    "queue": "default"
  }
}
```

フィールド定義:
- `ts`: ISO 8601 / RFC 3339 形式（UTC、末尾 `Z`、ミリ秒またはマイクロ秒精度）。サンプリング時刻。
- `component`: 出力元部品名（英小文字ハイフン区切り）。必須項目。
- `name`: メトリクス名（スネークケース）。
- `type`: メトリクス種別（`counter`, `gauge`, `histogram`）。
- `value`: 観測値（数値）。
- `labels`: キー・バリューの辞書（文字列ペア）。

### 3.3 命名規則と制約

- **名前**: スネークケース（`[a-z][a-z0-9_]*`）。単位をサフィックスに明示する（`_total`, `_bytes`, `_seconds`, `_ratio` 等）。
- **ラベルの制約**:
  - ラベル数は 1 メトリクスあたり最大 10 個まで。
  - **カーディナリティの制御**: ユーザー ID、セッション ID、生 URL、タイムスタンプなどの値が無制限に増える文字列をラベル値にしてはならない。
- **出力元部品の正規化規則と主キー衝突防止契約**:
  - 複数部品が同一のメトリクス名（例: `http_requests_total`）やラベル（例: ラベルなし、または同一エンドポイント名）を同一時刻に出力した場合、保存キーや時系列系列（Series）において別部品のサンプルが衝突する危険がある。
  - この衝突により ADR 0045 の一意主キー制約による挿入拒否、または既存サンプルの置換による観測データの欠落が発生することを防ぐため、以下の契約を義務付ける。
    1. **出力元部品のラベル正規化規則**: メトリクス受信時（またはエミッター側での出力時）に、`component` フィールドの値を必ず `labels["component"]` としてラベル集合へ組み込む正規化を行う（すでに `labels` 内に同名キーがある場合は `component` フィールドの値で統一・上書きする。出力元と異なる対象部品を指定する場合（死活監視の監視対象など）は、`target_component` などの別名ラベルを用いて出力元情報と監視対象情報の双方を保持する）。
    2. **ラベル数上限の適用**: 正規化後のラベル集合に対して最大 10 個の上限を適用する（ユーザー定義ラベルは実質最大 9 個まで）。

## 決定 4 — 保存先と保持の考え方

### 4.1 保存基盤

- **永続化エンジン**: `sigil-db` 核（ADR 0045、WAL と単一テーブル/追記構造）を内部エンジンとして利用する（`sigil-stash-kv` や `sigil-herald-queue` と同方針）。自前でファイル追記と破損復旧を再実装しない。
- **データ分離**:
  - ログ表: 時刻・部品名・水準をインデックスとした追記型テーブル。
  - メトリクス表: 出力元部品名（`component`）・メトリクス名・時刻・ラベルハッシュ（`component` を含む正規化済みラベル集合のハッシュ）を一意主キーとした時系列テーブル。出力元部品を保存キーに含めることで、異なる部品間で同一メトリクス名・同一時刻・同一ラベルのサンプルが衝突することによる挿入拒否やデータ欠落を完全に排除する。

### 4.2 保持期間（Retention）と容量制限

- **ログの保持**:
  - 既定で過去 7 日間を保持。
  - ディスク使用量上限（既定 10 GB）を設ける。
  - 容量上限に達した場合は、古い日付のログから安全に FIFO で削除（ローテーション）する。
- **メトリクスの保持と集計（ダウンサンプリング）**:
  - 生データ（秒単位）: 24 時間保持。
  - 1 分間集計値（平均・最大・最小・合計）: 7 日間保持。
  - 1 時間集計値: 30 日間保持。
  - 古い生データは定期的な集約処理後に消去し、保存容量を抑制する。

## 決定 5 — 死活監視の範囲と通知

### 5.1 核に含める死活監視の範囲

`sigil-argus-observe` は単なるログ・メトリクスの受け皿に留まらず、各部品の健全性を評価する死活監視エンジンを核に内蔵する。

1. **プル型（ヘルスチェックポーリング）**:
   - 監視対象部品のヘルスチェック口（HTTP `/healthz` または軽量 TCP ポート）に対して定期的に健全性確認要求を送信する（既定 10 秒間隔）。
   - 連続 N 回（既定 3 回）のタイムアウト（既定 3 秒）またはエラー応答をもって `UNHEALTHY`（異常）と判定する。
2. **プッシュ型（ハートビート受信）**:
   - バックグラウンドワーカーなど待受ポートを持たない部品から、定期的にハートビートメトリクス（`heartbeat_ping`）を受信する。
   - 規定時間（例: 30 秒）受信が途絶えた場合に `DEAD`（停止）と判定する。

### 5.2 異常の通知と外部連携

1. **内部ログ・メトリクスへの反映**:
   - 状態変化時に `FATAL` / `WARN` レベルのシステムログを出力し、状態メトリクス `component_up{target_component="..."}`（1: 正常, 0: 異常）を即座に更新する（正規化規則により出力元 `component="sigil-argus-observe"` と監視対象 `target_component="..."` の双方が保持され、複数部品の状態識別と保存キー衝突防止を両立する）。
2. **非同期通知のディスパッチ**:
   - `sigil-herald-queue`（ADR 0066）へ通知ジョブを投入する。
   - 後続の `sigil-raven-mail`（メール通知）や `sigil-agora-post`（SNS・Webhook 通知）がキューからジョブを取り出して外部へ配信する。
3. **自律復旧層へのイベント通知**:
   - `sigil-vigil-ops` に対して異常検知イベントを通知し、自律的な再起動やランブック実行のトリガーを提供する。

## 決定 6 — 範囲の切り分け（インフラ系ツールの責任境界）

監視・ログ収集の核以外のインフラ系ツール・運用手順について、責任境界を明確に切り分ける。

| 領域 | 責任の所在 | 本部品（sigil-argus-observe）の関与 |
|---|---|---|
| **バックアップと復元** | **各既存部品側の機能**（[ADR 0044](0044-p4-scope.md) 決定 5）<br>対象は `sigil-db` のデータ状態と `sigil-container` の宣言・状態 | 本部品自身はバックアップ機構を持たない。本部品の永続化データ（`sigil-db` 核上）は `sigil-db` 側の標準的なバックアップ・リストア手順に従う。 |
| **デプロイ支援** | **当面は各部品の運用手順の範囲**（初期スコープ外） | 本部品はデプロイツールや CI/CD 実行機構を提供しない。監視対象部品の起動・停止・再起動は `sigil-orchestra` または手動運用手順に委ねる。 |
| **証明書更新支援** | **TLS 終端部品 `sigil-shield-tls` 側の範囲**（[ADR 0063](0063-shield-tls.md)） | 本部品は証明書の有効期限や更新成否のメトリクス・ログを受け取って死活監視・警告を行うのみとし、証明書発行・更新処理自体は行わない。 |

## 決定 7 — 実装段の分割と完了条件

実装は 4 つの独立した段階に分割して進める。各段階は単独でビルド・テスト可能とする。

| 段 | 段階名 | 成果物と完了条件 |
|---|---|---|
| **1** | ログ・メトリクス契約とエミッターライブラリ | JSON Lines ログシリアライザ、Counter/Gauge/Histogram のメモリ内データ構造、標準出力およびインメモリバッファへ書き出すエミッターライブラリ。フォーマット準拠性、64 KB 上限切り詰め、ラベル制約および component 正規化規則を検証する網羅的単体テスト。 |
| **2** | 収集・保存コアと死活監視エンジン | `sigil-db` 核を用いたログ・メトリクスのバッファリングとトランザクション永続化アダプター。プル型（HTTP/TCP）およびプッシュ型（ハートビート）の死活監視状態機械（`Healthy`, `Degraded`, `Dead`）。モック時計を用いたタイムアウト・復旧判定の単体テスト。 |
| **3** | 受信プロトコルとクエリ API | ログ・メトリクスを受信するネットワーク口（TCP/HTTP）と、総合ポータル（`sigil-orchestra` のダッシュボード）にデータを提供するクエリ API（直近ログ検索、メトリクス集計、部品状態一覧）。ループバック経由の統合通信試験と DoS 防御境界試験。 |
| **4** | データ保持ローテーション・負荷境界試験・公開前記録（G2） | ディスク容量上限（10 GB）および保持期間（7 日）超過時の FIFO ローテーション・削除試験。高頻度ログ流入時の流量制御（レートリミット）。ADR 0020 G2 基準に基づくセキュリティ検証記録（`docs/pre-publish-record.md`）の作成。 |

## 影響と適合の限界

### 影響
- 各バックエンド部品（`shield-tls`, `herald-queue`, `sigix` 等）は、本 ADR のログ・メトリクス契約に沿った統一フォーマットでログを出力できるようになる。
- 総合監視ポータル（`sigil-orchestra`）は、新設の独自ポータルを作ることなく、本部品のクエリ API を通じて全体の可視化を実現できる。
- 障害検知から自律解決（`sigil-vigil-ops`）への接続基盤が確立される。

### 適合の限界
- **単一ノード限定**: 初版は単一ノードでの収集・保存を前提とし、複数ノード間でのログ分散集約やレプリケーションは含まない。
- **全件全文検索の非提供**: 初版は時刻範囲、部品名、ログ水準、プレフィックス一致などの基本的なインデックス検索のみを提供し、高機能な分散全文検索エンジンは目指さない。
- **データ破棄の許容**: ディスク容量枯渇時や過大な負荷時には、システムの稼働継続を最優先とし、古いデータから破棄（Drop）される。

### 判定の準備と経緯

AGENTS.md の「判断の手順」（理念 → typesafe-ai 正式判定）に従い、起草にあたって判定項目を整理した。
起草セッション環境には判定 API の認証キー `TYPESAFE_API_KEY` が設定されておらず、起草時点での API 呼び出しは実施できなかった（先例 ADR 0044、ADR 0060、ADR 0065、ADR 0066 と同一の状況）。そのため、評価軸および 7 つの判断点の問い・選択肢・起草者採用案を以下に記録し、見張り・所有者による確認・追認が可能な状態とする。

### 固定する評価軸（state）

```text
ADR 0001・0005・0027 の理念に基づき、人間が仕様をレビューできる明示的な型付き契約、メモリ安全性、既存の検証済み部品（sigil-db 核）の再利用、小さく単独で検証できる実装段階を最優先とする。ADR 0020 の最小権限と資源上限、ADR 0044 決定 4 の仕様と実装のリポジトリ分離を守る。
前提: 監視・ログ収集部品（製品名 Scan）の設計において、各部品に共通するログ・メトリクス形式の約束を先行して確定し、独立したポータル新設を避けつつ orchestra や vigil-ops と疎結合に連携する堅牢な単一ノード基盤を定義すること。
```

### 問いと採用案の一覧

| 問い | 選択（起草者の採用案） | 理由・根拠 |
|---|---|---|
| **Q1: 持ち方の選択 (Architecture)** | `spec_first_staged`: 形式先行の約束 ＋ 段階的サーバー構築 | 部品ごとの形式散逸を防ぐため形式の約束を先行定義し、エミッターから収集サーバーへ 4 段階で着実に立ち上げる。 |
| **Q2: ログ形式 (Log Format)** | `ndjson_structured`: 1行1JSON（NDJSON）＋ 必須4項目 | 軽量かつ機械可読性が高く、`src/stdlib/json.sigil` を活かせる。64 KB 上限で安全性を確保。 |
| **Q3: メトリクス種別 (Metrics Types)** | `three_types`: Counter, Gauge, Histogram | Prometheus 等で実績のある最小限の基本形に絞り、解釈の曖昧さを排除。 |
| **Q4: 保存基盤 (Storage)** | `db_core_retention`: `sigil-db` 核の再利用 ＋ 7日/10GB 制限 | 既存の検証済み核を再利用し、厳格な容量上限と FIFO ローテーションでディスク枯渇を防ぐ。 |
| **Q5: 死活監視 (Liveness)** | `hybrid_liveness`: プル型ヘルスチェック ＋ プッシュ型ハートビート | 待受ポートを持つ部品とワーカー部品の双方に対応し、herald-queue 経由で異常通知を疎結合に配送する。 |
| **Q6: 範囲切り分け (Scope Boundary)** | `clear_separation`: バックアップは各部品、デプロイは運用手順、証明書更新は shield-tls | 核（監視・ログ収集）の責務に集中し、不要な肥大化を防止する（ADR 0044 決定 5、ADR 0063 整合）。 |
| **Q7: 実装段分け (Stages)** | `four_stages`: エミッター → 収集コア/死活 → 受信/API → ローテーション/G2 | 各段階を単独で検証可能な構成とし、依存関係に沿って確実に積み上げる。 |
