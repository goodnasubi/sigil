# 0065: std.crypto の P-256 ECDH

- **状態**: 提案
- **日付**: 2026-11-26（JST）
- **対象**: [Issue #759](https://github.com/goodnasubi/sigil/issues/759)、レーン E
- **範囲**: ADR の起草のみ。`std.crypto` への実装は、本 ADR の承認後にレーン D2 の別 PR で行う。

## 背景

[ADR 0063](0063-shield-tls.md) 決定 6 の段 6 は、`secp256r1`（P-256）の鍵交換を `sigil-shield-tls` に加える。前提となる標準部品として、決定 1.4 は「P-256 の ECDH（受け取る点の曲線上の検査を含む）」を挙げ、[ADR 0064](0064-ecdsa-p256.md) は ECDH を範囲外として別の ADR・PR に残した。`std.crypto` に P-256 の ECDH はまだない。段 6 はこれが無いと始められない。

TLS 1.3 の鍵交換で使うのは、一時鍵どうしの ECDH である。サーバーは、クライアントの `key_share` の点を検査し、一時鍵を作って自分の点を返し、共有値をハンドシェイクの鍵導出へ渡す。[RFC 8446 §4.2.8.2](https://www.rfc-editor.org/rfc/rfc8446#section-4.2.8.2) は、P-256 の点を非圧縮形式（65 バイト）で送ることと、受け取った点が曲線上にあることの検査を求める。共有値は、共有点の X 座標を素数の長さ（32 バイト）に左をゼロで埋めた値である（[§7.4.2](https://www.rfc-editor.org/rfc/rfc8446#section-7.4.2)）。

既に `std.crypto` にあるものは、X25519（[ADR 0058](0058-tls13-crypto-primitives.md)）と、P-256 の体・点・スカラー倍算を含む ECDSA（ADR 0064、実装済み）である。

## 選択肢

| 案 | 利点 | 欠点 |
|---|---|---|
| 用途別の専用型（`EcdhP256PrivateKey`・`EcdhP256PublicKey`）を設け、共有値を `Secret` で返す | 署名鍵と鍵交換鍵の取り違えを型で防げる。検証済みの点だけが入口になり、共有値の計算は失敗しない。X25519・ECDSA と形が揃う | 型と変換が増える |
| ECDSA の鍵型をそのまま ECDH にも使う | 型が増えない | 署名用の鍵を鍵交換にも使える。用途を混ぜる誤用を型で止められない |
| `Bytes` と `Secret` を直接受け取る | 型が要らない | 点の検査が呼び出し側の責任になり、検査を忘れた経路が作れる（曲線外の点の攻撃） |

## 決定 1 — 公開 API

最初の案を採用する。ADR 0058・ADR 0064 に合わせ、鍵は内部表現を公開しない用途別の型とする。各関数は `effects none` とする。

| 入口 | 契約 |
|---|---|
| `EcdhP256PrivateKey.from_secret(key: Secret) -> Result<EcdhP256PrivateKey, EcdhP256Error>` | 符号なしビッグエンディアンの 32 バイトを消費する。P-256 の基点の位数を `n` として、`1 <= d < n` の値だけを受理する。失敗時も入力を破棄してゼロ化する |
| `EcdhP256PublicKey.from_bytes(encoded: &Bytes) -> Result<EcdhP256PublicKey, EcdhP256Error>` | 決定 2 の検査を全て行う。受理した点だけが `EcdhP256PublicKey` になる |
| `EcdhP256PublicKey.to_bytes(self: &EcdhP256PublicKey) -> Bytes` | SEC 1 の非圧縮点の 65 バイト。TLS の `key_share` にそのまま入る |
| `ecdh_p256_public_key(private: &EcdhP256PrivateKey) -> EcdhP256PublicKey` | 基点との乗算で公開鍵を導出する |
| `ecdh_p256_shared_secret(private: &EcdhP256PrivateKey, peer: &EcdhP256PublicKey) -> Secret` | 共有点の X 座標を 32 バイトの `Secret` で返す。KDF・ハッシュは適用しない（TLS 側が HKDF に渡す） |

`EcdhP256Error` は `InvalidPrivateKey` と `InvalidPublicKey` を持つ。秘密由来の値はエラーに載せない。秘密鍵は `Secret` を所有し、表示・公開バイト列への変換は提供しない。

`ecdh_p256_shared_secret` は `Result` を返さない。曲線上の検証済みの点と、`1 <= d < n` の鍵だけが入口の型になるため、結果の点が無限遠点になる入力は存在しない（余因子が 1 で、点の位数は素数 `n`）。X25519 は低位の点で共有値が全ゼロになりうるため `Result` を返す（ADR 0058）が、P-256 にはその経路がない。

鍵の生成は提供しない（ADR 0064 と同じ）。呼び出し側は `std.os_random.bytes` で 32 バイトを取り、`from_secret` に渡す。範囲外（確率はおよそ 2^-32）なら `InvalidPrivateKey` になるので、TLS 側が新しい乱数で作り直す。棄却される値は破棄されるので、再試行の回数は秘密を漏らさない。

TLS 側は、`key_share` の 65 バイトを `from_bytes` に渡し、失敗したら `illegal_parameter` で終える。一時鍵を作り、`ecdh_p256_public_key(..).to_bytes()` を自分の `key_share` に載せ、共有値を鍵スケジュールの (EC)DHE の入力にする。鍵の再利用はしない。どのグループを選ぶか（まず `x25519`）は ADR 0063 決定 1.2 のままとする。

## 決定 2 — 受け取る点の検査

`from_bytes` は、次を全て確かめ、どれかに当たれば `InvalidPublicKey` を返す。

- 長さがちょうど 65 バイトで、先頭が `0x04`（非圧縮形式）である。圧縮点（`0x02`・`0x03`）、無限遠点の符号化（`0x00`）、ハイブリッド形式（`0x06`・`0x07`）は拒否する。
- X・Y の各 32 バイトが、体の素数 `p` に対して `0 <= 座標 < p` にある。
- 点が曲線の式 `y^2 = x^3 - 3x + b (mod p)` を満たす（[SP 800-56A Rev. 3 §5.6.2.3.3](https://csrc.nist.gov/pubs/sp/800/56/a/r3/final) の完全な検証）。

P-256 の余因子は 1 なので、曲線上の点は基点の部分群に属する。小さい部分群への攻撃の検査は別に要らない。この検査は、決定 1 の `ecdh_p256_shared_secret` が失敗しないことの根拠である。検査の入力（受け取った点）は公開とみなし、検査の結果で分岐してよい。ADR 0064 の `EcdsaP256PublicKey.from_bytes` と同じ検査なので、実装は検査の関数を共有してよい（型は分ける）。

## 決定 3 — 定数時間

[ADR 0020](0020-p1-security-addendum.md) 決定 1 の R1〜R6 と ADR 0058 決定 3 を適用する。秘密のスカラー、共有点の全ての中間値（射影座標を含む）、共有値は秘密として追跡する。秘密に依存する分岐、早期終了、ループ回数、添字・アドレス、除算・剰余、非定数時間関数への引き渡し、ログへの出力を禁じる。

スカラー倍算は ECDSA と同じ固定 256 回の演算列を使う。点の加算・倍算は例外のない完全な式を使い、無限遠点・同じ点・逆の点を分岐で扱わない。アフィン座標への変換の逆元は、公開の固定指数（`p - 2`）のべき乗で行い、秘密に依存する反復を持たない。公開できるのは、入力の長さ、`from_bytes`・`from_secret` の受理結果、確定した公開鍵と、共有値の長さだけである。作業用の値は破棄時にゼロ化する。

ECDSA の内部関数（体・点・スカラー倍算）を共有するときは、基点でない公開の点を底にする経路も、同じ規則で `ct_rules` に登録する。

## 実装の完了条件

| 項目 | 確認方法 |
|---|---|
| 公開ベクタ | [RFC 5903 §8.1](https://www.rfc-editor.org/rfc/rfc5903#section-8.1) の 256 ビットのランダム楕円曲線群（P-256）の ECDH の試験値で、両側の公開鍵と共有値を照合する。[RFC 8448 §5](https://www.rfc-editor.org/rfc/rfc8448#section-5) の `secp256r1` の `key_share` の値も使う。RFC に共有値がなければ、独立実装で計算した値を出典とともに置く。SIR 評価器とネイティブ出力で実行する |
| 境界と相互運用 | 決定 2 の各拒否（長さ違い、先頭の符号、座標 `>= p`、曲線外の点、`(0, 0)`、X と Y の入れ替え）と、`d = 0`・`d = n`・`d > n`・長さ違いの拒否、`d = n - 1` の受理を確かめる。`ecdh(a, B) = ecdh(b, A)` を複数の鍵で確かめる。独立実装（OpenSSL など）が出した固定ベクタを出典とともに置く。曲線外の点と、ねじれた曲線の点を含む公開の不正な点の集合（Wycheproof の `ecdh_secp256r1` など）を、出典とともに使う |
| 定数時間の静的検査 | `ct_rules_static` と `ct_rules_clif` に、秘密鍵の取り込み・公開鍵の導出・共有値の計算と、秘密を扱う全補助関数を登録する。秘密に依存した違反の検出、呼び出し先までの検査、生成コードでの秘密領域のゼロ化を確認する |
| タイミング計測 | ネイティブの共有値の計算を `ct_measure` で測る。公開の点を固定し、固定鍵群と変動鍵群を同一実行ファイルで比較する。Welch の t 値の絶対値が 4.5 未満、陽性対照が 4.5 以上であることを確認し、CPU・最適化条件・試行数・t 値・検出感度を記録する |

## 影響と適合の限界

本 ADR が扱うのは、P-256（`secp256r1`）の一時鍵どうしの ECDH と、TLS 1.3 の鍵交換グループ `secp256r1` を支える暗号部品である。X25519（ADR 0058）とは別の型・別の関数で、共通の抽象は設けない。どちらも共有値は 32 バイトの `Secret` で、`Result` の有無（決定 1）だけが違う。

範囲外とするもの: P-384・P-521・他の曲線、ハイブリッド方式（鍵交換の併用）、圧縮点、鍵の生成、共有値への KDF の適用、静的な鍵を使う運用（鍵の再利用の API）、TLS 1.2 以前の鍵交換、証明書の検証。TLS 全体の適合範囲は ADR 0063 決定 1.1 に従う。本 ADR の実装により、ADR 0063 が記録した「P-256 の鍵交換を持たない」という適合の限界のうち、鍵交換の部分が解消される。署名の RSA は残る。

実装はレーン D2 の別 PR で行う。TLS 側の `key_share` の検査と HelloRetryRequest を含む接続・相互運用は、ADR 0063 の段 6 で検証する。

## 判断の記録

判断の手順（理念 → typesafe-ai 正式判定）に従い、2026-11-26（JST）に見張りが typesafe-ai (`jev-1.13.0`) で正式判定を実施した。判定したのは次の 2 問で、どちらも本 ADR の採用案が選ばれた。

| 問い | 採用案 | 確率 | confidence |
|---|---|---:|---:|
| ECDH の鍵の型 | 専用型（`EcdhP256*`）。ECDSA の型は使い回さない | 0.97 | 0.96 |
| 共有値の API | `Secret` を返し、`Result` にしない | 0.99 | 0.98 |

判定の入力と応答の JSON は見張りが保管している（本 ADR には載せていない）。

次の 3 問は正式判定を実施していない。採用案と根拠だけを記録する。レビューで別案が適当と判断された場合は、判定を実施して本節を更新する。

| 問い | 採用案 | 根拠 |
|---|---|---|
| 点の検査の置き場所 | `from_bytes` に集約し、受理した点だけが型になる | 検査を忘れた経路を作れない。TLS の `illegal_parameter` への対応が 1 か所になる |
| 鍵の生成 | 提供しない。`std.os_random.bytes` と `from_secret` | ADR 0064 と同じ。乱数の入口を標準の 1 か所に保つ |
| 共有値への KDF | 適用しない | TLS 側の HKDF が (EC)DHE の入力として使う。部品を用途に縛らない |

採用案の根拠（判定した 2 問）は次のとおり。鍵の型は、署名鍵と鍵交換鍵の用途を型で分ける（ADR 0058・0064 の方針）ためで、TLS の一時鍵と証明書の鍵は別物である。共有値の API は、検証済みの点と範囲内の鍵だけが入口なので失敗する経路がなく、失敗の分岐を呼び出し側に作らないためである。
