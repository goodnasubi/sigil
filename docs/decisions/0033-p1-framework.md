## 背景

[ADR 0005](0005-long-term-goals.md) および [ADR 0018](0018-p1-scope.md) は、P1 の目標を「サーバーと Docker コンテナでのリリース（G5）、Spring の置き換え（G10）」とし、段階 6-4「フレームワーク」で次を担うとした。

- ルーティング
- 設定（環境変数・起動引数）
- 入力検証（篩型と `check`）
- テスト用の実行環境での差し替え
- 終了の合図での停止

依存する段階 6-3（HTTP/1.1 サーバー、[ADR 0032](0032-p1-http-server.md)）は 6-3g-a〜d の実装が完了し、`std.http`・`std.http.limits`・`task.roots` が `main` に入っている。一方で、[ADR 0020](0020-p1-security-addendum.md)・[ADR 0022](0022-type-identity-traits-and-function-types.md)・[ADR 0030](0030-p1b-native-concurrency.md)・[ADR 0031](0031-p1-first-wait-ops-and-socket-api.md)・[ADR 0032](0032-p1-http-server.md) は、フレームワークおよびその周辺に関わる複数の論点を段階 6-4 へ送っている。

### 現状の確認（`main` `373a2a5`）

本初稿の起草にあたり、リポジトリの実物で確認した事実は次のとおりである。

1. **HTTP サーバー基盤（`std.http` / `std.http.limits`）**:
   - `HttpLimits`（`with_*` 15 項目、`memory_bound()`）、`HttpParser`（増分解釈）、`HttpConn`、`HttpRequest`（`method()`・`path()`・`query()` は生の `Bytes` で百分率符号化を解かない・`headers()`・`header(name)`・`body()`・`body_len()`）、`HttpResponse`、`HttpError`、`http.serve_conn`、`http.abort_conn` が `trust none` で実装済みである（`src/stdlib/http.sigil`・`src/stdlib/http_limits.sigil`・`src/stdlib.rs`）。
   - `http.serve_conn` のハンドラ引数は `h: fn(&HttpRequest) -> HttpResponse`（引数の位置の関数型）で、`serve_conn` の効果は `net.server, clock, task.spawn, task.suspend, task.share, of(h)` である。
   - `abort_conn` や解釈失敗・時間切れの応答は現在本文が空（`content-length: 0`）であり、500 の本文は 6-4 へ送られている（ADR 0032 決定 3-2・補足 B-1）。
   - `std.os.net`（`src/stdlib/os_net.sigil`・`src/ir_eval/call.rs`）の `accept4` は接続元のアドレスを受け取らない（`addr = 0, addrlen = 0` のみ許可）。また `TcpListener` に公開の `close` 操作はなく、値の破棄で閉じる。
2. **トレイトと関数型（ADR 0022、2-4a〜d 実装済み）**:
   - 置ける位置（構造体のフィールド・列挙型の値の中身・戻り値の型・`let` の型注釈）には、効果節を明示した関数型 `fn(...) -> ... effects ...` を書ける（`src/check/resolve.rs`）。
   - `src/check/unify.rs` において、置ける位置の関数型（効果節あり）は `Sendable` かつ `Shareable` を持つ。一方、引数の位置の関数型（効果節なし）は `Sendable`・`Shareable` を持たない。
   - 型引数（`List<fn(...)>` など）、置ける位置の関数型の引数としての関数型、および置ける位置の関数型の中での `of(...)` は `ErrorKind::FnTypePosition` で拒否される（`src/check/resolve.rs`）。
3. **`SyncShared<T>` の制約（`src/check/register.rs`・`tests/atomic_share_190.rs`）**:
   - `SyncShared<T>` は `T: Sendable` かつ `T: Shareable` のとき `Sendable`・`Shareable` になり、`clone()` によって同じ実体を指すハンドルを増やせる。
   - しかし `src/check/register.rs` に登録されているメソッドは `new(value: T) -> SyncShared<T>` と `get(self: &SyncShared<T>) -> T`（`impl<T: Copyable> SyncShared<T>`）のみである。そのため、**非 `Copyable` な型（`List<Route>` を持つ `Router` や文字列を含む設定構造体など）を `SyncShared<T>` に入れることはできても、読み出す手段が現在存在しない**。
4. **環境変数と起動引数（`src/stdlib/os_env.sigil`・`src/shared/args.rs`・`src/effects.rs`）**:
   - 起動引数は `src/shared/args.rs`（`parse_arg`）により入口関数の引数として型つきで渡される（`sigil run` とネイティブの双方で実装済み）。
   - 効果カテゴリ `env`（`Targets::SERVER`）は `src/effects.rs` に定義済みで、ネイティブの `std.os.env.get`（`src/stdlib/os_env.sigil`）も `_start` が渡す `ENVP` を読む形で内部実装されている（`std.os.sched` が利用）。しかし **`src/stdlib.rs` の利用者の表（`NAMESPACED_FNS`）および評価器（`src/ir_eval/`・`src/exec.rs` の `Options`）に `env.get` が公開・接続されていない**。
5. **JSON・入力検証（`src/json.rs`・`src/check/call.rs`）**:
   - `src/json.rs`（`MAX_DEPTH = 128`）は Rust 製の処理系・LSP 用であり、Sigil の利用者コードから使える JSON モジュールはまだない。
   - 篩型 `T.check(...)` は型検査器・実行器に実装済みである（`src/check/call.rs`）。
6. **シグナルと複数ルートの停止（`src/ir_eval/call.rs`・`src/stdlib/os_io.sigil`・`src/check/register.rs`）**:
   - `RootGroup` には `reserve(self: &RootGroup) -> RootSlot` のみがあり、終了合図での受け付け停止やドレインの入口がない。
   - `raw.syscall` の許可表および `std.os.io` には `signalfd4` / `rt_sigaction` などのシグナル受信機構がない。
7. **標準名前空間の予約一覧（`src/check/mod.rs`・`src/stdlib.rs`）**:
   - `std_heads()` は `["console", "fs", "http", "net", "raw", "std"]` に固定されている（追加時は ADR 0021 の改訂を伴う）。

## 評価の観点

Sigil の理念とこれまでの ADR に照らし、次の順で判断する。

1. **宣言効果と推論効果の完全一致・最小能力（[ADR 0004](0004-effects.md)・[ADR 0027](0027-ai-era-security-design-principles.md) 決定 2）**: 暗黙の大域権限（ambient authority）を持ち込まず、ハンドラやフレームワーク部品が到達できる能力（効果）を型と宣言から機械的に監査できること。
2. **信頼基盤は小さく・明示的・列挙可能に（[ADR 0005](0005-long-term-goals.md)・[ADR 0016](0016-trust-base-declaration.md)）**: `unchecked`・`raw.*`・新規の `Builtin`・許可システムコールの追加を極小に抑え、原則 `trust none` の Sigil コードで実装すること。やむを得ず `std.os.*` や `raw.syscall` を触る部分は独立した段に切り出して人間承認を得ること。
3. **AI が誤りにくい「既定で安全」と「守れない層の排除」（[ADR 0020](0020-p1-security-addendum.md)・[ADR 0027](0027-ai-era-security-design-principles.md) 決定 3）**: 上限外しの禁止、認証の既定拒否（fail-closed）、安全な 500 本文、`X-Forwarded-For` 等の不信用を、利用者の書き忘れに頼らず型・API 境界で強制すること。
4. **後戻りしない順序と 6-5・6-6 への接続性（[ADR 0018](0018-p1-scope.md) 観点 2）**: 6-5（PostgreSQL）と 6-6（認証）でフレームワークのコア設計を作り直さずに差し込めること。
5. **評価器とネイティブの単一実装・テスト容易性**: ソケットなし単体テスト・評価器での差し替え・ファジング（`fuzz_app_json`）により回帰を機械的に固定できること。

## フレームワークの目的と範囲

### 目的

`std.http`（接続・HTTP/1.1 解釈・単一接続内の時間と大きさの上限・異常停止時の 500 隔離）の上に、実用のサーバーアプリケーション（P1 完了条件のサンプルサービス、Spring の置き換えの第一歩）を AI が安全かつ簡潔に書けるアプリケーション層を提供する。

### 提供するもの（6-4 の範囲）

| 区分 | 内容 | 由来 |
|---|---|---|
| 受け付け・起動の枠 | `HttpLimits` と `task.roots` と `http.serve_conn` / `abort_conn` を結ぶ起動ループ、起動時の `memory_bound()` 表示（`console.log`） | ADR 0018・0032 |
| ルーティングと経路照合 | HTTP メソッド＋パスによる照合（静的パス・パス変数）、404 / 405 の定型応答、クエリ文字列の分割と上限（100 個、超過時 400） | ADR 0018・0020・0032 |
| ミドルウェア／フック | 前処理・後処理・認証の共通パイプライン（ADR 0022 の型規則内で書ける形） | ADR 0022 |
| 認証の差し込み口（既定拒否） | 経路ごとの認証要否の明示、未設定・未認証での既定拒否（401）、公開経路の監査用列挙（検証の実体は 6-6） | ADR 0020 |
| 設定と上限の検証 | 環境変数（`env.get`）および起動引数からの設定・上限読み込み、無制限値（0・負値・上限の上限超）の起動時拒否 | ADR 0018・0020 |
| JSON の読み書きと深さ上限 | Sigil 実装（`trust none`）による JSON 解析・直列化、入れ子深さ上限（既定 64、超過時 400）、`fuzz_app_json` | ADR 0020 |
| 入力検証の型境界 | 篩型 `T.check` や検証関数と組み合わせたリクエスト検証と 400 系エラー応答への写像 | ADR 0018 |
| 安全なエラー応答 | 500 の固定本文（契約違反の位置・詳細を出さず、標準エラーへ出す）および 4xx/503 の定型応答 | ADR 0018・0020・0032 |
| テスト用の差し替え | ソケットを開かずにルーターを呼ぶ直接ディスパッチ入口、および評価器での `env` 差し替え（`exec::Options::env_vars`） | ADR 0004・0018 |
| 終了の合図での停止 | `SIGTERM` / `SIGINT` 受信時の新規受け付け停止と処理中接続の完了待ち（ドレイン） | ADR 0018 |

### 提供しないもの（6-4 の範囲外）

- **TLS 終端・HTTP/2・WebSocket・HTTP クライアント**: 前段中継で終端する前提（ADR 0018 判断 5・決定 2、ADR 0032 決定 1）。
- **静的ファイル配信**: `std.http` と同じく `fs.*` 効果を持たない（ディレクトリ横断の危険を構造的に防ぐ。ADR 0032 決定 6）。
- **HTML テンプレート**: P2 の UI と一緒に決める（ADR 0018 決定 2）。
- **PostgreSQL 接続・プール・認証トークンの暗号検証実体**: それぞれ段階 6-5、6-6 の対象。
- **ORM・実行時リフレクション・DI コンテナの暗黙注入**: 静的型・効果宣言とテスト実行環境の差し替えで代替する（ADR 0004・0005・0018）。
- **メトリクス収集・分散トレース・高度ログ基盤**: P1 の出力は `console` に限る（ADR 0018 決定 2）。
- **正規表現ベースのルーティング・`X-Forwarded-For` 等による暗黙の IP 判定**: ReDoS および IP スプーフィングの入口を作らない。

## 既存 ADR からの持ち越し事項の洗い出しと扱い

Issue #445 および既存 ADR から 6-4 へ送られた全項目を洗い出し、本 ADR での扱いを整理する。

| # | 持ち越し事項 | 出典 | 現状と 6-4 での扱い | 対応する判断点 |
|---|---|---|---|---|
| 1 | **上限の設定の名前** | ADR 0020 決定 4・5、ADR 0032 決定 4-3 | `HttpLimits` 15 項目＋フレームワーク上限（クエリ数・JSON 深さ・停止猶予）の環境変数名を固定し、無制限値を拒否する | 判断点 E・F |
| 2 | **JSON の深さ** | ADR 0020 決定 2・4・5 | 既定 64（上限外し不可、超過時 400）。Sigil 製反復パーサーと `fuzz_app_json`（往復一致・深さ境界）を入れる | 判断点 G |
| 3 | **`X-Forwarded-For` 等のヘッダーを信じるか** | ADR 0020 決定 4、ADR 0031・0032 未決 | 既定では信じない。`std.os.net` が接続元アドレスを取らないため信頼プロキシ検証も不可。P1 では暗黙の信頼経路を持たない | 判断点 I |
| 4 | **ハンドラの表と `SyncShared`** | ADR 0022 決定 3・根拠の限界 398 行目 | 置ける位置の関数型は `Sendable + Shareable` だが、`SyncShared.get` が `T: Copyable` 必須のため `Router` 等を読めない。読み出し手段を足して確かめる | 判断点 B |
| 5 | **ミドルウェアの形** | ADR 0022 根拠の限界 402 行目 | 引数位置・置ける位置の制約（`FnTypePosition`）内で、言語変更なしに構造体・フックで書ける形を確定する | 判断点 C |
| 6 | **トレイト機能の十分性検証**（`dyn`・関連型・既定実装なし） | ADR 0022 根拠の限界 396 行目 | ルーティング・JSON・入力検証の実装を通じ、ADR 0022 の範囲で足りるかを確かめ、不足があれば記録する | 判断点 B・C・G |
| 7 | **URL 問い合わせの欄の数（上限 100）とパス正規化** | ADR 0020 決定 4、ADR 0032 決定 2-2・4-1・補足 A-3 | `std.http` が生の `Bytes` で渡す `query` と `path` をフレームワーク層で分割・検証し、100 超・不正文字・`..` を 400 で拒む | 判断点 H |
| 8 | **500 の本文と内部情報の遮断** | ADR 0018 決定 7、ADR 0020 決定 3 項目 6、ADR 0032 決定 3-2・補足 B-1 | `std.http` は空本文で返した。6-4 の定型エラー応答で固定の安全な本文を返し、契約違反の詳細は標準エラーのみに出す | 判断点 J |
| 9 | **既定で拒否する認証の差し込み口** | ADR 0020 決定 3 項目 5・決定 5 | 6-6 を待たず、6-4 のルーター設計に認証必須（既定拒否）と公開経路の列挙を組み込む | 判断点 D |
| 10 | **設定（環境変数・起動引数）とテスト差し替え** | ADR 0018 決定 2、ADR 0004 決定 7 | 起動引数は既存の入口引数、環境変数は `env.get` の公開と評価器 `exec::Options::env_vars` 差し替え、テスト用直接ディスパッチで担う | 判断点 F・J |
| 11 | **終了の合図での停止** | ADR 0018 決定 2、ADR 0030・0031 未決 | `SIGTERM` / `SIGINT` での受け付け停止と処理中接続のドレイン方法を定める | 判断点 K |
| 12 | **高水準 `http.serve` の再検討** | ADR 0032 未決（388 行目） | `std.http` に高水準ループを戻すのではなく、6-4 のフレームワーク（`std.web` 等）として `task.roots` と `HttpLimits` を束ねる | 判断点 A・B |
| 13 | **モジュールの配置と `std_heads` の扱い** | ADR 0021（2-2b） | `std.*` に新しい標準名前空間（例: `web`・`json`・`env`）を増やす場合、ADR 0021 の `std_heads()` の改訂が必要 | 判断点 A |

## 脅威と対策（ADR 0020 決定 3 の G1）

[ADR 0020](0020-p1-security-addendum.md) 決定 3（関門 G1）および決定 5（6-4 の行）に従い、入力・認証・秘密・資源の 4 分類について脅威と対策を定める。

| 分類 | 想定する脅威 | 何から何を守るか | 本 ADR での対策（判断点） |
|---|---|---|---|
| **入力** | (1) 深い入れ子の JSON によるスタック枯渇（プロセス全体の停止）。<br>(2) 多数のクエリパラメータや巨大なパス・不正なパーセント記号・`..` による計算量増大やパス解釈の不整合。<br>(3) 悪意ある `X-Forwarded-For` / `Forwarded` によるクライアント偽装。 | 外からの HTTP 要求から、プロセス生存性・ハンドラの入力整合・アクセス制御の前提を守る。 | ・JSON は再帰に依らない反復パーサーとし、深さ上限 64（変更上限あり、無制限不可）を超えたら 400（判断点 G）。`fuzz_app_json` を短い実行・長い実行に入れる。<br>・クエリ欄数は上限 100（超過 400）、パスは `..` や制御・NUL 文字を拒否（判断点 H）。<br>・`X-Forwarded-*` は既定で信用しない（判断点 I）。 |
| **認証** | (1) 新規エンドポイント追加時に AI が認証チェックを書き忘れ、無認証で公開される。<br>(2) 認証機能の実装（6-6）前の設定不備で fail-open になる。 | 保護すべき業務 API とデータへの不正アクセスを防ぐ。 | ・すべての経路は既定で認証必須（`AuthPolicy.Required`）とし、公開経路は明示宣言のみ許可（判断点 D）。<br>・認証検証器が未設定のまま `Required` 経路へ到達した場合は常に 401 で拒否（fail-closed）。<br>・公開経路一覧を取得でき、G3 の報告へ載せる。 |
| **秘密** | (1) 署名鍵・DB パスワード等がコマンドライン引数経由で `ps` 等から漏洩する、またはリポジトリへ埋め込まれる。<br>(2) 契約違反の 500 応答や JSON パース失敗応答に、内部の変数・位置・契約文が含まれて外部へ漏れる。 | 秘密鍵・パスワード・内部構造の外部漏洩を防ぐ。 | ・秘密設定は起動引数ではなく `env.get` 経由で読み、環境変数はログやエラー応答に出さない（判断点 E・F）。<br>・500 等のエラー本文は固定文のみとし、内部の停止報告は標準エラーのみに出す（判断点 J）。<br>・`std.web` / `std.json` に `Secret` や秘密値の `Displayable` 表示経路を作らない。 |
| **資源** | (1) 環境変数に `0` や極端に大きい値を設定し、実質無制限となってメモリ枯渇（プロセス停止）を招く。<br>(2) `SIGTERM` 時に接続を即断し処理中リクエスト・DB 処理を破壊する、または逆にハングしてコンテナが停止しない。 | メモリ上限・接続数・プロセスの正常終了性を守る。 | ・環境変数による上限変更は `HttpLimits` と同じく上限の上限で検証し、`<= 0` や超過は起動失敗にする（判断点 E）。<br>・起動時に `HttpLimits.memory_bound()` を標準出力へ出す。<br>・`SyncShared` 共有で接続ごとのルーティング表複製を防ぐ（判断点 B）。<br>・`SIGTERM`/`SIGINT` で受け付けを止め、猶予上限つきで処理中ルートを終了させる（判断点 K）。 |

### 判断点 A: フレームワークの配置とモジュール構成

- **課題**: サーバーアプリケーションのフレームワークを、処理系に埋め込んだ標準モジュール（`std.*`）として提供するか、ユーザー空間の `--root` 配下の通常モジュール群として提供するか。
- **選択肢**:
  - **A1（埋め込み `trust none` 標準モジュール）**: `std.http`（ADR 0032）・`std.crypto`（ADR 0024）と同じ作法で、`std.web`・`std.json`（および `env` 名前空間）を `trust none`・`Layer::Os` / `Layer::Core` の埋め込みモジュールとして提供する。`std_heads()` に `web`・`json`・`env` 等を追加する（ADR 0021 改訂）。
  - **A2（ユーザー空間ライブラリ）**: 言語に足りない部品（`env.get`、`SyncShared` 読み出し、停止機構）だけを標準に足し、ルーターや JSON はリポジトリ内の通常 Sigil ファイル（例: `lib/web/...`）に置き、各アプリが `--root` を揃えて `use` で取り込む。
- **理念に照らした評価**:
  - ADR 0021 の決定により Sigil は P1 でパッケージ設定ファイルを持たないため、A2 ではアプリごとにソースツリーへコピーするか `--root` の配置を合わせる必要があり、第 3 者プログラムやサンプル・テストから共通利用しにくい。また、`web` 層が `fs.*` や `unchecked` を持たないことをコンパイラの単体テスト（`std.http` の `http_is_trust_none_and_has_no_fs_effects` 相当）で機械的に固定しにくい。
  - A1 は信頼基盤増分 0 のまま、単一実装・`trust none` 固定テスト・6-5/6-6 との一貫した接続を実現できる。なお、`std.web` 自体は `db` や具体的な暗号トークン仕様に依存せず、関数型フックと `HttpRequest` / `HttpResponse` だけで閉じる設計にすれば循環や後戻りも起きない。
- **推奨: A1**（`trust none` の埋め込み標準モジュール。**未決定**）。

### 判断点 B: ハンドラ表と `SyncShared<T>` の拡張（ADR 0022 持ち越し）

- **課題**: ルーティング表 `Router`（`List<Route>` を包む構造体）を `task.roots` で起動する全接続タスクへ共有したい。`Route` のフィールド `handler: fn(&AppRequest) -> HttpResponse effects ...` 自体は ADR 0022 決定 3 により `Sendable + Shareable` である。しかし `SyncShared<T>` の現行メソッドは `get(self: &SyncShared<T>) -> T`（`T: Copyable`）のみであり、非 `Copyable` な `Router` を読み出せない。
- **選択肢**:
  - **B1（`SyncShared<T>` への非 `Copyable` 読み出し追加）**: `SyncShared<T>`（`<T>`、ただし `new` 時点で `T: Sendable + Shareable` が要るかは性質導出と整合させる）に、内容をコピーせずに共有参照で読む操作を 1 つ足す。具体的な形として次の 2 つの小選択肢がある。
    - B1-a: `with<U>(self: &SyncShared<T>, f: fn(&T) -> U) -> U`（効果 `task.share, of(f)`）— 評価器の `Rc<Val::Cell>` の借用寿命がクロージャ呼び出し内に閉じ、参照返しの制限に当たらない。
    - B1-b: `borrow(self: &SyncShared<T>) -> &T`（効果 `task.share`）— `LockGuard.get(self: &LockGuard<T>) -> &T` と対称で簡潔。評価器の `Val::Ref` 表現が `SyncShared` でも同様に扱えるかが実装確認点。
  - **B2（`Lock<Router>` で代用）**: 既に `LockGuard.get` が `&T` を返せる `Lock<T>` を使う。
  - **B3（接続ごとに `Router` を生成・または単一 `match` 関数）**: 共有せず、接続ルートの中で毎回 `Router` を作るか、巨大な 1 関数に書かせる。
- **理念に照らした評価**:
  - B2 は読み取り専用のルーティング表へのアクセスを接続間で直列化してしまい、全ハンドラに `Result<..., LockBroken>` の分岐が漏れ出す。
  - B3 は `Router` の値やクロージャを接続ごとに再構築する無駄が大きく、ADR 0022 が「ハンドラの表を共有して読む」ために置ける位置の関数型を `Sendable + Shareable` にした設計意図を活かせない。
  - B1 は ADR 0007 決定 2 の `SyncShared` 本来の役割そのものであり、新しい信頼基盤概念を増やさず既存の共有機構を完結させる（小選択肢では、評価器・ネイティブ双方の安全性が明快な **B1-a（`with`）または対称性の高い B1-b（`borrow`）** を実装時検証のうえ採用する。特に参照寿命の問題が起きない `with` が保守的だが、`LockGuard.get` と揃う `borrow` が可能なら利用側はさらに簡潔になる）。
- **推奨: B1**（`SyncShared<T>` に非 `Copyable` 読み出しを追加し、`SyncShared<Router>` でルーティング表を共有。小選択肢は `borrow` の評価器整合が保てるなら `borrow`、難しければ `with`。**未決定**）。

### 判断点 C: ハンドラの効果上限とミドルウェアの形（ADR 0022 持ち越し）

- **課題**: ADR 0022 決定 3 は「置ける位置の関数型には効果節が必須」「効果に `of(...)` を書けない」「関数型の引数に関数型を書けない」と定めた。このため `fn(Req, fn(Req) -> Resp) -> Resp` 型の高階ミドルウェア関数を一覧に並べる形は、`FnTypePosition` によりそのままでは書けない。また、`Route` のフィールドに関数型を置く以上、その型に書く効果の上限 `D` を決める必要がある（実際のハンドラは `E ⊑ D` を満たせば入れられる）。
- **選択肢**:
  - **C1（固定フック構造体パイプライン＋最小権限のサーバー効果上限 `D`）**: 言語規則は一切変えず、ミドルウェアを「リクエスト前処理（`BeforeHook`: 検査・中断応答 `Option<HttpResponse>`）」「認証検証器（`AuthVerifier`）」「レスポンス後処理（`AfterHook`: 共通ヘッダ付与・アクセスログ等）」の型付きフックとして `App` / `Router` のフィールド（またはそれぞれの構造体一覧）に保持する。ハンドラおよびフックの効果上限 `D` は P1 サーバー用途に必要な能力に限定する（例: `db, console, clock, random, env, task.spawn, task.suspend, task.share` — **`fs.read`・`fs.write`・`net.client`・`net.server`・`foreign`・`process` は含めない**）。なお、`db` 等を使わないアプリ向けに、より狭い効果上限のビルダーまたは `effects none` 専用の軽量入口も併記できるかを実装時に確認する。
  - **C2（ADR 0022 改訂: `dyn Trait` または `of(...)` つき高階関数型の導入）**: コンパイラを拡張し、一般的な `next` チェイン型ミドルウェアを書けるようにする。
  - **C3（ミドルウェアを持たず各ハンドラ内で手動呼び出し）**: フレームワーク側はルーティングのみ提供し、前後処理・認証を各ハンドラに書かせる。
- **理念に照らした評価**:
  - C3 は AI が書き忘れる温床となり、ADR 0027 決定 3（「安全な書き方が最短」）に反する。
  - C2 は段階 6-4 に言語仕様・型検査器・単相化の大きな変更を持ち込み、ADR 0018 観点 2・ADR 0022 決定 2（「P1 では `dyn` を持たない」）を覆す。
  - C1 は既存の `E ⊑ D` 部分効果規則だけで完結し、さらに `D` から `fs.*`・`process`・`foreign`・`net.*` を外すことで「宣言効果と能力の境界」を型レベルで強制できる（ADR 0027 決定 2）。ただし `Route` のハンドラ型に `D` を書くと、`main`／受け付けループの宣言効果にも `D` が伝播する点は留意が必要である（実アプリが必要とする効果と一致するため通常は問題にならないが、純粋関数テスト用には別入口または静的チェックを用意できる）。
- **推奨: C1**（言語仕様を変更せず、フック構造体パイプライン＋最小権限のサーバー効果上限 `D`。**未決定**）。

### 判断点 D: 既定で拒否する認証の差し込み口（ADR 0020 決定 3 項目 5）

- **課題**: 具体的な Bearer HMAC トークン検証は段階 6-6 だが、ADR 0020 決定 3 項目 5 は「フレームワークの経路は、明示して外さない限り認証を求める（既定で拒否）。認証を外した経路の一覧を報告に載せる」ことを求めている。
- **選択肢**:
  - **D1（`AuthPolicy` 既定必須＋明示的公開指定＋監査用一覧＋fail-closed 401）**: 経路登録の基本 API（例: `router.route(method, path, handler)`）は既定で `AuthPolicy.Required` とし、認証不要の経路（ヘルスチェック等）だけを別関数（例: `router.public_route(...)`）で登録させる。`App` は認証検証器（`fn(&HttpRequest) -> Result<AuthIdentity, HttpResponse> effects ...` 相当）を差し込む口を持ち、検証器が未設定のまま `Required` 経路にリクエストが来た場合も失敗時と同じく **401 を返して拒否（fail-closed）** する。`router.public_routes()` で認証を外した経路の一覧を文字列として取得でき、G3 関門の報告に直接使える。
  - **D2（6-4 では認証概念を持たず、6-6 でルーターを書き換える）**: 6-4 は無認証ルーターとして作る。
  - **D3（既定で公開し、必要な経路にだけ認証フックを付けさせる）**: オプトイン認証。
- **理念に照らした評価**:
  - D3 は AI 開発で最も起きやすい「認証の付け忘れ」を許すため不採用（ADR 0020・0027）。
  - D2 は 6-6 でルーター API と既存テストを作り直す後戻りが発生する。
  - D1 は「安全が最短・デフォルト拒否」「6-6 への綺麗な接続」「G3 監査の機械化」をすべて満たす。
- **推奨: D1**（既定必須の `AuthPolicy` と明示的 `public_route`、未設定時 fail-closed 401、公開経路一覧 API。**未決定**）。

### 判断点 E: 上限の設定の名前と読み込み・検証（ADR 0020 決定 4・5）

- **課題**: `HttpLimits` の 15 項目およびフレームワーク固有上限の設定名（環境変数名等）と読み込み方、無制限値の拒否規則を決める（ADR 0020 決定 4・5、ADR 0032 補足 A-2）。
- **選択肢**:
  - **E1（`SIGIL_HTTP_*` / `SIGIL_APP_*` 環境変数＋起動時範囲検証）**:
    - 次の環境変数名に対応させ、未設定時は既定値を使い、設定時は整数変換（`parse_int`）と各項目の一貫した範囲検査（`1 <= v && v <= 上限の上限`）を行い、範囲外や数値でない場合は起動を失敗させる（`Result<AppConfig, ConfigError>`）。無制限（`0`・`-1` 等）は一切受け付けない。
    - `HttpLimits` 15 項目:
      - `SIGIL_HTTP_REQUEST_LINE_BYTES`（既定 8192、上限 65536）
      - `SIGIL_HTTP_HEAD_BYTES`（既定 16384、上限 262144）
      - `SIGIL_HTTP_HEADERS_MAX`（既定 100、上限 1000）
      - `SIGIL_HTTP_BODY_BYTES`（既定 1048576、上限 67108864）
      - `SIGIL_HTTP_CHUNK_LINE_BYTES`（既定 1024、上限 1024）
      - `SIGIL_HTTP_ENCODED_BODY_BYTES`（既定 2097152、上限 134217728）
      - `SIGIL_HTTP_CONNS_MAX`（既定 256、上限 4096）
      - `SIGIL_HTTP_BACKLOG`（既定 128、上限 1024）
      - `SIGIL_HTTP_HEAD_MS`（既定 10000、上限 600000）
      - `SIGIL_HTTP_BODY_MS`（既定 30000、上限 600000）
      - `SIGIL_HTTP_HANDLER_MS`（既定 30000、上限 600000）
      - `SIGIL_HTTP_SEND_MS`（既定 30000、上限 600000）
      - `SIGIL_HTTP_IDLE_MS`（既定 60000、上限 600000）
      - `SIGIL_HTTP_REQUESTS_PER_CONN`（既定 1000、上限 100000）
      - `SIGIL_HTTP_RESPONSE_BODY_BYTES`（既定 1048576、上限 67108864）
    - フレームワーク上限（`AppLimits`）:
      - `SIGIL_APP_QUERY_PARAMS_MAX`（既定 100、上限 1000）
      - `SIGIL_APP_JSON_MAX_DEPTH`（既定 64、上限 128）
      - `SIGIL_APP_SHUTDOWN_GRACE_MS`（既定 10000、上限 300000）
    - あわせて `SIGIL_APP_HOST`（既定 `"127.0.0.1"` 等、安全側でローカル既定）・`SIGIL_APP_PORT`（既定 `8080` 等、1..=65535 あるいはテスト用 0 指定は入口引数で受ける）や、起動時 `HttpLimits.memory_bound()` の `console.log` 出力を定型化する。なお、`SIGIL_APP_HOST` の既定値を `127.0.0.1` にする（コンテナ公開時は明示設定させる）ことで ADR 0027 決定 3 の「認証なしでの不用意な外部リッスン回避」にも寄与する。
  - **E2（設定ファイルから読み込む）**: TOML/JSON 等の設定ファイルを `fs.read` で読む。
  - **E3（環境変数読み込みを持たずコード上の `with_*` のみに留める）**: 上限変更はソースコード変更のみ。
- **理念に照らした評価**:
  - E2 は不要な `fs.read` 効果とファイル構文解析を持ち込む。E3 は ADR 0020 決定 4・5 の要件を満たさない。E1 はコンテナ運用（環境変数注入）および ADR 0020 決定 3 項目 3（「上限を外す設定が拒まれるテスト」）に直結する。
- **推奨: E1**（`SIGIL_HTTP_*` / `SIGIL_APP_*` の明示的な環境変数名と起動時範囲検証。**未決定**）。

### 判断点 F: `env.get` の公開とテスト用の実行環境での差し替え

- **課題**: 環境変数を読む `std.os.env.get` は内部実装済み（`src/stdlib/os_env.sigil`）だが利用者の標準ライブラリ表（`src/stdlib.rs`）に未登録で、評価器（`src/ir_eval/`）にもテスト用の差し替えがない。
- **選択肢**:
  - **F1（`env.get` の公開＋評価器 `exec::Options::env_vars` 差し替え）**:
    - `src/stdlib.rs` の `NAMESPACED_FNS` に `env.get(name: &String) -> Option<String>`（`Layer::Os`, `effects: "env"`）を登録する（`fs.read` と同じ型・層設計）。
    - ネイティブは既存の `std.os.env.get`（空番地を `None`、文字列を `Some(s)` へ包む薄いラッパ）を結ぶ。
    - 評価器（`src/ir_eval/`）は `exec::Options` に `env_vars: Option<std::collections::BTreeMap<String, String>>` を追加する（`fs_files` と対称）。`Some(map)` のときはその表を引き、`None` のときはホスト環境（または決定的テストのため空表にするかも選択・明記する。テスト再現性と安全性を優先するなら評価器既定は実環境を読むか空にするか明確化が必要だが、ネイティブとの突き合わせでは同じ入力環境を与えるため `None` 時は `std::env::var` 相当とし、テストでは `Some(...)` で差し替えるのが `fs_files` と完全に一貫する）。
  - **F2（`env.get` を公開せず、すべて起動引数で受け取らせる）**: 入口関数の引数のみ。
- **理念に照らした評価**:
  - F2 では環境変数による設定や、6-6 で必須とされる「署名の鍵を環境変数で受け取る（ADR 0018 判断 6c）」を実現できない（CLI 引数への鍵渡しはプロセス一覧から漏れる危険がある）。
  - F1 は既に存在する `std.os.env` と `env` 効果を表に繋ぐだけで信頼基盤を増やさず、`fs_files` と同じ作法で評価器テストの差し替えができる。
- **推奨: F1**（`env.get` の公開＋`exec::Options::env_vars` 差し替え。**未決定**）。

### 判断点 G: JSON の実装と深さ上限 64（ADR 0020 決定 2・4・5）

- **課題**: ADR 0020 決定 4 はフレームワークの JSON 本文の入れ子深さ上限を 64（超過時 400）と定め、決定 2・5 は Sigil で書く場合の `fuzz_app_json`（往復一致・深さ境界・異常停止なし）を完了条件にしている。
- **選択肢**:
  - **G1（`trust none` の Sigil 製反復 JSON モジュール `std.json`＋`fuzz_app_json`）**:
    - 構造体・列挙型（例: `JsonValue` = `Null` / `Bool(Bool)` / `Int(Int)` / `Float(Float)` / `Str(String)` / `Array(List<JsonValue>)` / `Object(List<JsonField>)`）と反復パーサー（再帰を使わず明示的な状態スタックと `depth <= max_depth` 検査）・シリアライザーを `trust none` の Sigil で書く。
    - 数値表現（整数 `Int` と小数 `Float` の扱い）・キー重複時の扱い（後ろ優先／拒否／一覧保持。セキュリティ上の曖昧さ回避には **重複キー拒否または明確な 1 規則固定** が望ましい）・UTF-8 とサロゲートペア／エスケープの検証を明確に定める。
    - `tests/fuzz_app_json.rs` を追加し、評価器とネイティブの突き合わせ・往復一致・深さ 64 通過／65 拒否を固定する。
  - **G2（Rust の `src/json.rs` を組み込みとして呼ぶ）**: 処理系既存のパーサーを `Builtin` 経由で公開する。
  - **G3（JSON パーサーを持たず生バイト列のみ）**: 利用者が毎回文字列処理する。
- **理念に照らした評価**:
  - G2 は P1 完了条件「出力に Rust のコードを含めない（ADR 0018）」に反し、組み込み（信頼基盤）を増やす。
  - G3 は ADR 0020 決定 4（深さ 64 → 400）および実用 JSON API の要件を満たさない。
  - G1 は `std.http` と同じく `trust none` で単一実装・評価器突き合わせ・自前ファジングができ、再帰禁止によりスタック枯渇も構造的に防げる。なお、`JsonValue` のような再帰的列挙型が現行の単相化・破棄・評価器・ネイティブで安全に扱えることは 6-4d の冒頭で確認する（構造的制約があればインデックス参照型の平坦表現へ逃がせる）。
- **推奨: G1**（`trust none` の Sigil 製反復 JSON モジュール＋深さ上限 64＋`fuzz_app_json`。**未決定**）。

### 判断点 H: 入力検証（クエリ上限 100・パス検査・篩型 `T.check`）

- **課題**: ADR 0018 決定 2 の「入力検証（篩型と `check`）」、ADR 0020 決定 4 の「問い合わせの欄の数 100（超過時 400）」、ADR 0032 決定 2-2 の「`path`・`query` は生の `Bytes` で百分率符号化を解かない」をフレームワーク側でどう繋ぐか。
- **選択肢**:
  - **H1（境界パーサー＋篩型 `T.check` 統合）**:
    - フレームワークがリクエスト到着時に `query`（`Bytes`）を `&` で分割し、**欄数 > 上限（既定 100）または不正な UTF-8／不正なパーセント符号化があればハンドラを呼ばずに 400 を返す**。
    - `path`（`Bytes`）はパーセントデコード（`%00` や不正シーケンスを 400 で拒否）およびセグメント検査（`.`・`..`・空セグメントの扱い固定）を行ってからルーティング照合へ渡す。
    - ハンドラ側では、パス変数・クエリ値・JSON 値を文字列・整数として取り出す補助関数（`param(name) -> Result<String, HttpResponse>` 等）と、利用者の篩型 `T.check(v)` を組み合わせ、検証失敗を 400 応答へ簡潔に写像できるヘルパーを用意する。
  - **H2（クエリやパスの解釈を各ハンドラに任せる）**: `HttpRequest.query()` をそのまま渡す。
- **理念に照らした評価**:
  - H2 は上限 100 の検査や `%00`・`..` の拒否をハンドラ書き手が漏らす危険がある（ADR 0027 観点 1）。
  - H1 は危険な境界解析をフレームワーク 1 か所に集約し、篩型 `check` という Sigil の強みを Web 入力検証に活かせる。
- **推奨: H1**（フレームワーク側でのクエリ上限・パス検査＋篩型 `T.check` 連携。**未決定**）。

### 判断点 I: `X-Forwarded-For` 等の前段ヘッダーを信じるか（ADR 0020・0031・0032 持ち越し）

- **課題**: サービス前段に TLS 終端プロキシがある前提（ADR 0018 判断 5）で、`X-Forwarded-For`・`Forwarded`・`X-Forwarded-Proto`・`X-Forwarded-Host`・`X-Real-IP` をフレームワークが信用して扱うか。
- **選択肢**:
  - **I1（既定で信じない・P1 では専用クライアント IP API を持たない）**: ADR 0020 決定 4 の「既定では信じない」を厳格に採る。現状 `std.os.net` は接続元 IP を取得しない（`SYS_ACCEPT4` で `addr = 0` のみ許可）ため、接続元が信頼できる前段（trusted proxy）かどうかをネットワーク層で検証できない。検証不能なままヘッダーを信じる専用メソッド（`client_ip()` 等）を設けると AI が認証やレート制限に誤用するため、**P1 ではフレームワークに `X-Forwarded-*` を解釈する API を置かない**（監査ログ等の目的で生ヘッダーを見たい場合のみ `HttpRequest.header(&"x-forwarded-for")` として未検証の生値に触れる）。
  - **I2（設定フラグでオプトインして `client_ip()` を提供する）**: 環境変数 `SIGIL_APP_TRUST_PROXY=true` 等を置いたときに `X-Forwarded-For` の末尾または先頭を返す。
  - **I3（`accept4` を拡張して接続元 IP 取得と CIDR 判定まで P1 で作る）**: ソケット syscall 許可表を変更し、信頼プロキシ CIDR 検証を実装する。
- **理念に照らした評価**:
  - I2 は信頼プロキシの検証なしにフラグ 1 つで偽装可能な IP を返してしまい、ADR 0027 決定 3（「危険なデフォルト・誤用しやすい API の排除」）に反する。
  - I3 は `raw.syscall` 変更と CIDR 解析を伴うが、P1 の目標（Spring 置き換え最小・Bearer トークン認証）にクライアント IP 判定は不要である。
  - I1 は安全かつ最小で、信頼基盤増分 0 である。将来 trusted proxy 判定が必要になった時点で接続元 IP 取得とセットで安全に設計すれば後戻りもない。
- **推奨: I1**（既定で信じない。P1 では専用クライアント IP API を持たず、誤用経路をなくす。**未決定**）。

### 判断点 J: 500 等のエラー応答の本文とテスト用差し替え（ADR 0020・0032 持ち越し）

- **課題**:
  1. `std.http`（ADR 0032）は `abort_conn` や 4xx/500 の応答本文を空にした。フレームワーク層でどのような本文を返すか。
  2. ソケットを開かずに高速・決定的にフレームワークアプリをテストする手段をどう提供するか。
- **選択肢**:
  - **J1（固定の安全なエラー本文＋ソケット無しディスパッチ入口）**:
    - 500 応答の本文は常に固定の文（例: `"internal server error"`、または固定の JSON `{"error":"internal server error"}` で `content-type` を明示）とし、**契約違反の文・ファイル名・行番号・スタック・変数値を一切含めない**（ADR 0020 決定 3 項目 6）。`std.http` の `abort_conn` 経路は従来どおり空本文（`http.abort_conn` は触らず、フレームワークのハンドラ呼び出し側で通常のエラー応答を返す場合や `abort_conn` と整合させる場合を区別して整理する。なお、契約違反がハンドラ内で起き `serve_conn` を抜けて `abort_conn` へ落ちる場合は `std.http` 側が空 500 を返すので、そこでは内部情報が漏れない既定を満たしており、フレームワークが明示的に 500 や 4xx を生成する場面で固定文を返す。あるいは `abort_conn` にも固定文オプションが必要かを 6-4c で確認する）。
    - テスト用入口として `app.dispatch(&req) -> HttpResponse`（ソケット・`net.server` 効果なし）を提供し、評価器で `exec::Options::env_vars`（判断点 F）・`fs_files`・`capture_console`・`schedule_seed` と組み合わせて単体テストできるようにする。
  - **J2（開発用フラグで 500 本文に詳細エラーを出す）**: 設定で詳細本文を切り替えられるようにする。
- **理念に照らした評価**:
  - J2 は設定ミスによる本番情報漏洩のリスクがあり、ADR 0020 決定 3 項目 6 に反する。
  - J1 は安全側で一貫しており、評価器・ソケット無しテストも書きやすい。
- **推奨: J1**（固定のエラー本文＋ソケット無し `dispatch` テスト入口。**未決定**）。

### 判断点 K: 終了の合図（`SIGTERM` / `SIGINT`）での優雅な停止（ADR 0018 決定 2、ADR 0030・0031 持ち越し）

- **課題**: ADR 0018 決定 2 は「終了の合図での停止」をフレームワークの必須項目としている。しかし現在、`TcpListener.accept` は接続が来るまで永久にブロックし、`SIGKILL` 以外の `SIGTERM` / `SIGINT` を受けて新規受付を止め、処理中のルート完了を待って終了する手段がない。
- **選択肢**:
  - **K1（`signalfd4` 限定導入＋`RootGroup` 停止連携）**:
    - Linux の `signalfd4`（x86-64 syscall 289）＋ `rt_sigprocmask`（syscall 14）を `SIGTERM`（15）・`SIGINT`（2）のみに限定して `raw.syscall` 許可表へ追加する。任意のユーザシグナルハンドラ（`rt_sigaction`）は導入しない。
    - `std.os.io` の `epoll` で `signalfd` を待ち受けられるようにし、フレームワークの受け付けループが「新しい接続（`accept`）」と「停止の合図」を競合待機できるようにする（または `RootGroup` に「停止合図の待機・受付中断の通知」を持たせる）。
    - 合図を受けたら即座に `accept` ループを抜け、`task.roots` の枠内で起動済みルートの完了（または `SHUTDOWN_GRACE_MS` タイムアウト）を待ってプロセスを終了コード 0 で終える。
    - 評価器（`ir_eval`）では、シグナル配送そのものの代わりにテスト用の停止合図（指定回数・指定時間・チャネル/条件による停止トリガ）で受け付けループ終了とドレインを検証できるようにする。
  - **K2（P1 では優雅な停止を持たず、コンテナの停止シグナルでそのまま終了させる）**: ADR 0018 決定 2 の当該項目を見送り／後回しにする。
  - **K3（汎用シグナルハンドラ API を導入する）**: 任意のシグナル処理機構を作る。
- **理念に照らした評価**:
  - K2 はコンテナローリングアップデート時等に処理中リクエストを切断する問題があり、ADR 0018 決定 2 に反する。
  - K3 はシグナル安全性の複雑さと信頼基盤を大きく増やす。
  - K1 は非同期シグナルハンドラの危険を避け（`signalfd` は通常の fd 読み取りとして安全に扱える）、用途を `SIGTERM`/`SIGINT` に限定して信頼基盤の増加を最小に抑える。ただし `raw.syscall` 許可表および `std.os.io` / `std.os.sched` への変更を伴うため、**他の純粋フレームワーク PR とは明確に分離し、人間の明示的な承認を経て合流する**（ADR 0018 判断 2）。
- **推奨: K1**（`signalfd4` 限定導入による受け付け停止＋猶予期限つきドレイン。信頼基盤周辺変更は独立 PR で人間承認。**未決定**）。

## 完了条件（ADR 0018・0020 の要求との対応）

本 ADR の実装群（6-4b〜6-4g）が満たすべき完了条件は次のとおりとする。

1. **上限の設定と無制限値の拒否**（ADR 0020 決定 3 項目 3・決定 4・決定 5）: すべての `SIGIL_HTTP_*`・`SIGIL_APP_*` 設定が範囲外（`<= 0` や上限の上限超）を拒否し、`limit_app_*`・設定テストが通ること。
2. **JSON の深さ上限とファジング**（ADR 0020 決定 2・4・5）: 深さ 64 は通り 65 で 400（`Err`）になること。`fuzz_app_json`（往復一致・契約違反ゼロ・スタック枯渇なし・評価器とネイティブ一致）が `cargo test` の短い実行に入り、長い実行（`.github/workflows/fuzz.yml`）の段が用意されること。
3. **既定で拒否する認証の差し込み口**（ADR 0020 決定 3 項目 5）: 公開指定のない経路は未認証で 401（fail-closed）になり、公開指定された経路一覧を列挙できること。
4. **安全な 500 の本文と秘密・権限の隔離**（ADR 0020 決定 3 項目 4・6）: 500 応答の本文に契約違反の文・位置・環境変数の値を含めず固定文にすること。`std.web`・`std.json` が `trust none` で `fs.*`・`unchecked`・`raw.*` を持たないこと。
5. **`X-Forwarded-For` 等の不信用**（ADR 0020 決定 4）: 既定で信用しない方針がテストおよび API 形状で保たれていること。
6. **テスト差し替えと優雅な停止**（ADR 0018 決定 2）: ソケット無しディスパッチテストと `env_vars` 差し替えが動き、ネイティブで `SIGTERM` / `SIGINT` による受け付け停止・処理中接続完了後の終了が確かめられること。
7. **G1・G2 の記録**（ADR 0020 決定 3）: 本 ADR の「脅威と対策」（G1）および最終 PR（6-4g）での G2 確認記録が残ること。

## 本 ADR で決めないこと

- PostgreSQL 通信方式・SCRAM-SHA-256・接続プール・トランザクション中断の後始末（段階 6-5）。
- Bearer トークンの HMAC-SHA256 検証実装・鍵長 32 バイト未満の起動失敗・トークンファジング `fuzz_bearer_token`（段階 6-6）。
- TLS 終端・HTTP/2・WebSocket・HTML テンプレート・静的ファイル配信・メトリクス（P1 の範囲外）。

## 根拠の限界と再検証

- 本初稿は設計案の起草段階であり、**実装および計測を行っていない**。
- 特に次の 3 点は、対応する実装段の着手時に必ず実コードで検証し、想定と異なる場合は本 ADR を改訂する。
  1. **判断点 B（`SyncShared<T>`）**: `borrow`（`&T` 返し）と `with`（クロージャ渡し）のどちらが評価器（`Val::Shared(Rc<Val::Cell(...)>)`）とネイティブの両方で破棄・借用規則と綺麗に整合するか（6-4b で検証）。
  2. **判断点 G（`JsonValue` の再帰的構造）**: 再帰的な列挙型を持つ `JsonValue` を `trust none` の Sigil コードとして書いたとき、現行の単相化・所有権・破棄・評価器／ネイティブ突き合わせで問題が出ないか（6-4d の冒頭で検証し、制約があれば平坦な配列＋添字表現へ切り替える）。
  3. **判断点 K（`signalfd4` と `TcpListener` 中断）**: `accept` が `io_wait_fd` で待っているタスクを `signalfd` 発火時に取り消す／起こす方法が、現行 `std.os.sched` の取り消しと競合なく書けるか（6-4f で検証）。
- 起草（agy / Gemini 系統）と正式判定・レビュー（`typesafe-ai`・Codex Cloud 等）を分離することで、単一エージェントによる案出しと採点の偏りを抑える。
