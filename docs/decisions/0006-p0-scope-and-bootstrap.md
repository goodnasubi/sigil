# 0006: P0 の範囲と実装の始め方

- **状態**: 承認（2026-10-25。所有者の委任を受けて Claude が決定。計測による再検証の条件は末尾を参照）

## 背景

[ADR 0005](0005-long-term-goals.md) で、最初の段階 P0（言語の核）の成果物を、コンパイラ（ネイティブ出力）・型・所有権・効果・契約の検査・仕様の抽出と表示・標準ライブラリの最小部分・言語サーバーと定めた。
処理系はまだない。実装を始めるにあたり、次の 5 点を決める。

1. コンパイラを書く言語と、セルフホスト（Sigil で Sigil のコンパイラを書くこと）の時期
2. P0 を、それだけで使える成果物が出る小さな段階（マイルストーン）に分けること
3. 並行処理のモデル（ADR 0007 で決める予定）を後から加えられるよう、P0 の型システムと効果システムが満たすべき条件
4. [DESIGN.md](../DESIGN.md) の未決の論点のうち、P0 の前に決めるものと後でよいもの
5. P0 での契約（`requires` / `ensures`）の検査方法

前提:

- 書き手は AI。人間は仕様だけをレビューする（[ADR 0001](0001-vision-and-scope.md)）
- 構文は波括弧 + 契約節、正規形以外はコンパイルエラー（[ADR 0002](0002-syntax-family.md)）
- 所有権は参照を二級に限る規則（[ADR 0003](0003-ownership-and-borrowing.md)）、効果は固定カテゴリの宣言と推論結果の完全一致検査（[ADR 0004](0004-effects.md)）
- 出力先はネイティブ（最初は Linux x86-64）・WebAssembly・JavaScript・実行環境なしのネイティブ。ブラウザで動く IDE を P2 で作る（ADR 0005）

## 決定 1: コンパイラを書く言語

### 評価の観点

重要な順に並べる。

1. **AI が誤りなく書けるか**: コンパイラ自体も AI が書き、保守する。学習データの量と、誤りをコンパイラ（実装言語の）が検出してくれる度合いを見る。
2. **ADR 0002〜0004 の機能の実装しやすさ**: 構文木の変換、所有権・借用の検査、効果の推論、仕様の抽出は、いずれも木構造に対する場合分けの多い処理である。代数的データ型とパターン照合、その網羅性の検査があると誤りが減る。
3. **ネイティブ / WebAssembly 出力の作りやすさ**: コード生成の部品（バックエンド）が実装言語から使えるか。
4. **ビルドと配布の容易さ**: 単一の実行ファイルで配れるか。コンパイラ自体を WebAssembly にしてブラウザの IDE（P2）で動かせるか。

### 選択肢

- **A: Rust**
- **B: OCaml**: コンパイラを書く言語として実績が多い（Rust の最初のコンパイラ、Flow、Hack など）。
- **C: Go**
- **D: 最初から Sigil で書く**: 処理系がまだないため、実際には「別の言語で最小の処理系を書き、すぐ Sigil に移る」ことになる。下の「セルフホストの時期」で扱う。

### 比較

| 観点 | A: Rust | B: OCaml | C: Go |
|---|---|---|---|
| 1. AI が書けるか | ○ 学習データが多い。型と借用の検査が AI の誤りを早く検出する。借用の検査エラーで手戻りはある | △ 学習データが少ない。ライブラリの選択（標準ライブラリの代替が複数ある）で揺れやすい | ○ 学習データが多く、規則が少ない |
| 2. 機能の実装しやすさ | ○ 列挙型と網羅的な `match` がある。木の書き換えは所有権のため OCaml より冗長 | ◎ 代数的データ型とパターン照合が言語の中心で、木の変換を最も簡潔に書ける | △ 直和型がなく、構文木の場合分けを型スイッチで書くため、場合の漏れをコンパイル時に検出できない |
| 3. ネイティブ / WebAssembly 出力 | ◎ Cranelift（Rust で書かれたコード生成器）、LLVM の束縛、WebAssembly を組み立てる部品が揃っている | ○ LLVM の束縛はあるが、保守が少ない | △ 使えるコード生成器の部品が少ない |
| 4. ビルドと配布 | ○ cargo で単一の実行ファイルにでき、WebAssembly にもしやすい。ビルドは遅い | △ opam による環境構築が必要。Windows 対応が弱い | ◎ ビルドが速く、単一の実行ファイルになる。WebAssembly 出力は大きくなりやすい |

補足: Sigil の所有権と借用の規則は Rust に倣っている（ADR 0003）。Rust でコンパイラを書くと、検査器を作る AI が、検査の対象と同じ考え方の言語を日常的に書くことになり、規則の境界の事例（どこで移動し、どこで借用が終わるか）を実装言語で確かめられる。

### 決定

**A: Rust** を採用する。

最も重い観点 1 で B に勝り、観点 2 で C に勝る。観点 3・4（コード生成の部品と、IDE のためにコンパイラを WebAssembly にできること）は ADR 0005 の段階計画に直接効く。

あわせて次を決める。

- **最初のネイティブ出力には Cranelift を使う**。LLVM より組み込みと配布が容易で、ビルドも速い。最適化は非目標（DESIGN.md 4 章）なので性能差は問わない。WebAssembly・JavaScript 出力は P2 で別に作る（コンパイラの中間表現は出力先に依存しない形にする）。
- **外部の部品は、コンパイラ自体の実装の補助に限る**（コード生成器・リンカ・テスト用の道具など）。Sigil の標準ライブラリやランタイムに既存言語のライブラリを持ち込まない方針（ADR 0005）は変えない。唯一の例外は、M5 の実行ファイルに含める暫定の Rust 製ランタイムで、範囲と置き換えの時期を決定 2 の「M5 のランタイムとリンカ」に記す。

### セルフホストの時期

- **P0 の間はセルフホストしない**。言語の仕様がまだ動く段階で 2 つの処理系を保守すると、変更の費用が倍になる。
- **P1 の完了後に、次の条件をすべて満たしたら着手を判断する**（判断は ADR に記録する）。
  - P1 のフレームワーク（ADR 0005 の決定 2 に挙げたルーティング・設定・入力検証・データベース接続・認証を持つもの）を Sigil で書き、ADR 0003 の規則（参照を二級に限る）で困らないことを確かめた
  - 標準ライブラリに、コンパイラを書くのに要る部品（文字列処理・ハッシュ表・ファイル入出力）が揃った
  - 上記のフレームワークを書く間に、書いたプログラムの書き直しを要する言語仕様の変更が起きていない（期間ではなく、実際のプログラムが変更なしで検査を通り続けることを基準にする）
- セルフホストした後も、Rust 版は当面、自己コンパイルの起点（ブートストラップ）として残す。

## 決定 2: P0 のマイルストーン

### 評価の観点

重要な順に並べる。

1. **各段階が単独で使える成果物を出すか**: ADR 0005 の段階計画と同じ条件。
2. **仕様と検査を早く使えるか**: 仕様の抽出と検査は ADR 0001 の中心であり、AI が書いたコードを人間が仕様でレビューする流れを最も早く試せる順がよい。
3. **ADR 0002〜0004 の計測を早く始められるか**: 3 つの ADR は、処理系ができた段階で検査のエラー率を計測すると定めている。
4. **後の段階で手戻りが見つかる危険**: 遅い段階で前提の誤りが見つかると、前の段階を作り直すことになる。

### 選択肢

- **A: 工程順**: 構文 → 型・効果 → 所有権 → 実行 → ネイティブ出力 → 言語サーバーの順に、コンパイラの工程を前から作る。
- **B: 縦切り**: 小さな部分言語で、構文解析から実行ファイルの出力までを最初に通し、言語機能を少しずつ広げる。
- **C: 実行を先**: インタプリタを最初に作ってサンプルを動かし、検査を後から加える。

### 比較

| 観点 | A: 工程順 | B: 縦切り | C: 実行を先 |
|---|---|---|---|
| 1. 単独で使える成果物 | ○ 各段階が道具（`fmt`・`spec`・`check`・`run`・`build`）を出す | ○ 最初から実行ファイルを出せるが、検査が揃うのは最後 | ○ |
| 2. 仕様と検査を早く使える | ◎ 最初の段階で仕様を表示でき、続く 2 段階で検査が揃う | △ 各段階で検査は部分言語の分だけ | × 検査が最後になる |
| 3. 計測を早く始められる | ◎ M0〜M2 で 3 つの計測が可能になる | △ 全規則の検査が揃うまで計測の対象が狭い | △ |
| 4. 後での手戻り | △ ネイティブ出力の問題が M5 まで見つからない | ◎ 出力の問題が最初に見つかる | ○ 意味論は早く固まるが、検査を後で足すと、動いていたコードが検査を通らない手戻りが出る |

### 決定

**A: 工程順** を採用し、P0 を次の 7 段階に分ける。

観点 1 は 3 案とも満たし、観点 2・3 で A が勝る。観点 4 の欠点は、M3・M4 のインタプリタを意味論の基準として M5 の出力と比べること、M5 の前に中間表現を決めること（決定 4）、Cranelift についての再検証の条件（末尾）で補う。

各段階は前の段階に依存し、終わった時点で単独で使える道具を出す。対象のサンプルは [examples/](../../examples/) の採用構文（候補 C）のファイルとする（`01-average/c-brace.sigil`、`02-read-port/c-brace.sigil`、`03-ownership/ownership.sigil`、`04-effects/effects.sigil`）。候補 A・B のファイルは対象にしない。

コメントアウトされた「コンパイルエラーになる例」は、各段階で独立したテスト用のファイル（期待するエラーを記したもの）に切り出して使う。

| 段階 | 内容 | 単独で使える成果物 |
|---|---|---|
| M0 | 字句解析・構文解析・整形器（正規形の検査）・仕様の抽出 | `sigil fmt`（正規形への整形と検査）、`sigil spec`（仕様の表示）。AI が書いたコードの仕様を、検査なしでも人間に示せる |
| M1 | 名前解決・型検査・効果の推論と一致検査 | `sigil check` の最初の版。効果の宣言の誤りを検出できる |
| M2 | 所有権・借用の検査 | `sigil check` で ADR 0003 の規則をすべて検査できる |
| M3 | 参照用の実行（インタプリタ）・契約の実行時検査・標準ライブラリのうち効果を持たない部分 | `sigil run` の最初の版。効果を持たない関数を実行し、契約違反を検出できる。意味論の基準として後の段階の比較に使う |
| M4 | 標準ライブラリの効果を持つ部分（`console`・`fs.read`・`Shared`・`Cell`）・核と OS 依存部分の分割・テスト用の実行環境（効果の差し替え） | `sigil run` でサンプルを `main` から実行できる |
| M5 | ネイティブ出力（Linux x86-64、Cranelift） | `sigil build`。単一の実行ファイルを出力できる |
| M6 | 言語サーバー | エディタや AI が検査結果・仕様を機械が読める形で受け取れる |

### 完了条件

各段階の完了条件は、リポジトリの自動テストとして書き、継続的インテグレーションで常に通ることを条件とする。決定 3 の「条件の確かめ方」の表で各段階に割り当てたテストも、その段階の完了条件に含める。

**M0**

- 4 つのサンプルの未確定の表記（`old(...)`、篩型の `where` と `self`、`Port.check`、モジュールの宣言）を、M0 の前に ADR で決めた表記（決定 4。[ADR 0008](0008-m0-notation.md)）に直してから、ADR 0008 で加えた `05-control` とともに、すべて構文解析を通る。
- `sigil fmt` を 4 つのサンプルと `05-control` にかけると、内容が変わらない（サンプルが正規形であることの確認。変わる場合はサンプル側を直し、その理由を記録する）。
- 字下げや空白を崩したサンプルを `sigil fmt --check` にかけると、正規形でないとしてエラーになる。
- 契約節を欠いた関数、順序を入れ替えた関数、`intent` が空の関数がエラーになる（ADR 0002 の規則 2）。
- `module` の宣言を欠いたファイル、宣言が 2 つあるファイル、`targets`・`trust` の節を欠いた・順序を入れ替えた・`targets` に重複がある・並びが文字の順でない宣言、`ensures` 以外で `old` を使った関数がエラーになる（ADR 0008 の決定 3・6）。効果の並べ方の違反（ADR 0008 の決定 8）が `sigil fmt --check` でエラーになる。
- [ADR 0009](0009-lexical-and-grammar.md) の字句エラー（タブ・CR・ブロックコメント・予約語の誤用・未定義のエスケープ・改行を含む文字列・先頭の 0・16 進や指数のリテラル）と構文エラー（各位置の大小文字の規約に反する名前、予約名の定義、比較の連鎖、括弧なしの `&&` と `||` の混在、呼び出し以外の式文、腕に `,` を付けた文の `match`、腕にブロックを書いた値の `match`）がエラーになり、正規形の違反（不要な括弧・末尾のカンマ・空行と行末コメントの空白・小数の末尾の 0・戻り値のない関数の末尾の `return;`・`|x| { return e; }` の形のクロージャ・すべての腕が `return 式;` だけの文の `match` など。ADR 0009 の決定 7・11）が `sigil fmt --check` でエラーになる。
- `sigil spec` の出力（モジュールの宣言・型の宣言・シグネチャと 4 節。本体は含まない）が、サンプルごとに用意した期待出力と一致する。引数の受け渡し方は ADR 0003 の規則 7 の訳を、ADR 0008 の決定 7 の差分（型の付記、`x: T` の注記を省く）付きで使う。

**M1**

- 4 つのサンプルが型検査と効果の検査を通る。
- `04-effects` のエラー例 3 件（宣言の不足・宣言の余分・ブラウザ向けモジュールでの `fs.read`）が、それぞれ期待どおりのエラーになる。
- `apply_all` に効果なしの関数を渡したとき `of(f)` が消え、`with_tax` が `effects none` のまま通る。`console` を起こす関数を渡すと、呼び出し側の宣言不足としてエラーになる。
- `02-read-port` の篩型（`Port`）が型として解釈される（範囲の検査は M3 の実行時検査で行う）。
- 決定 3 の条件 1・4・5・6・11・12 のテストが通る。
- [ADR 0011](0011-type-system-scope.md) の「M1 の完了条件に加えるもの」のテストが通る（型システムの範囲の各決定の型エラーと通る例、`-> Unit` の除去と制約の並べ方、性質の導出）。

**M2**

- `03-ownership` が検査を通る。（`tests/m2_completion.rs` の `examples_pass_all_checks`）
- `03-ownership` のエラー例 3 件（移動した後の使用・構造体の中の参照・借用の引数が 2 つある関数からの参照の返却）が、それぞれ期待どおりのエラーになる。（同 `example_03_error_use_after_move`・`example_03_error_reference_in_struct`・`example_03_error_two_borrow_args_return`）
- 次のエラー例を追加し、期待どおりのエラーになる: 排他借用の間の共有借用、借用をとらえたクロージャの変数への保存（ADR 0003 の規則 5）。（同 `err_mut_and_shared_in_one_call`・`err_get_then_push`、`err_closure_without_move_escaping`・`err_move_closure_captures_reference`）
- 決定 3 の条件 1・3・8 のテストが通る。（条件 1: `rule_override_changes_move_or_copy`。条件 3: `tests/closures.rs` の `closure_captures_api`・`move_closure_with_noncopyable_capture_is_not_copyable`。条件 8: `src/borrow.rs` の単体テスト。表の該当行も参照）
- [ADR 0012](0012-ownership-check-and-stdlib.md) の「M2 の完了条件に加えるもの」のテストが通る（移動・借用・クロージャ・篩型・契約の式の各規則のエラーと通る例、同 ADR の決定 2 で直したサンプル、標準の自由関数の名前の宣言のエラー）。

**M3**

- 効果を持たない関数（`01-average` の `average`、`03-ownership` の `main` 以外の関数、`04-effects` の `add_tax`・`apply_all`・`with_tax`）を、同じディレクトリに加えたテスト用の入口から呼び、戻り値が期待どおりになる。
- `requires` を破る呼び出し（例: `average` に空の一覧を渡す）と、`ensures` を破る実装（テスト用に用意した誤った実装。`old(...)` を使う `deposit` を含む）が、実行時に契約違反として停止する（決定 5）。
- 篩型への変換で範囲外の値を渡すと、範囲外として扱われる（`Port` の範囲の検査）。
- 標準ライブラリは、効果を持たない部分のうちサンプルが使うもの（`List`・`Option`・`Result`・`String` とその関数）に限る。**改訂（[ADR 0013](0013-termination-stdlib-and-function-values.md)）**: 範囲を、同 ADR の決定 2 の正式な一覧（`clone`・`get_mut`・`find`・`min_by`・`to_int`・`Int.min_value()` を含む）に改めた。
- [ADR 0013](0013-termination-stdlib-and-function-values.md) の「M3 の完了条件に加えるもの」のテストが通る（停止の扱い、標準ライブラリの各関数の意味、関数の値を引数に渡すこと、借用区間の部品の対のテスト）。
- 決定 3 の条件 9 のテストが通る。

**M3 の記録（最初の PR）**

- **範囲**: `sigil run <ファイル> <関数> [引数...]`、AST を直接たどるインタープリタ（`src/interp.rs`）、4 種類の異常停止（契約違反・`Int` の桁あふれ・0 での除算・スタック枯渇）。実行の前に `check` を通す。
- **異常停止の終了コード: 70**。契約違反・桁あふれ・0 での除算・スタック枯渇のどれでも同じ値とし、種類と位置は標準エラーに出す。検査のエラーや入口の指定の誤りなど、異常停止でない失敗は 1、使い方の誤りは 2。値は BSD の `EX_SOFTWARE`（内部のソフトウェアの誤り）に合わせた。M5 の実行ファイルも同じ値を使う。
- **スタック枯渇**: 実行専用のスレッド（既定 256 MiB）で、スタックのアドレスの使用量が 3/4 を超えたら停止する。ホストのスタックあふれ（プロセスの異常終了）にはしない。呼び出しを伴わない深い値は、破棄を反復で行い、表示・比較は同じ予算を超えたら `StackExhausted` で停止する。入口の引数は宣言の型に合わせる（`Float` の位置の整数は `Float` にし、合わない型や `Int` の範囲外の整数は入口の誤りとして終了コード 1）。ステップ数の上限は設けない（ADR 0013）。既知の制限: `Slot`・`MutRef`・クロージャの環境を通した深い入れ子の破棄は、反復化の対象外。
- **破棄の順序（条件 9）**: 各スコープでは宣言の逆順に破棄し、内側のスコープ・内側の呼び出しの枠から外側へ進む。1 つの値は、自分を先に破棄し、続いて欄・要素を宣言の順（リストは添字の順）に破棄する。`?` による早期の戻りと、契約違反・桁あふれ・0 での除算などすべての異常停止は、同じ解放の経路を通るので順序は同じである。`ensures` の違反では、局所変数、戻り値、引数（逆順）、呼び出し元の値の順になる。文の途中の一時値はその文の終わりで破棄する。順序は `Options::trace_drops` を立てたときだけ記録し、`Outcome.drops`・`Failure.drops` に出す（記録しないときの動作は変わらない）。記録のときだけ、移動した値の元の場所を空にし、`clone` は実際に複製して、移動済みの場所や共有された値が遅れて記録されないようにする。破棄の反復化（深い値の走査）は、行きがけ順で子を逆順に積むので、条件 9 の順序と食い違わない。既知の制限: 構造体の一部の欄だけの移動、`match` の束縛による移動、値を消費する標準ライブラリのメソッドの受け手、クロージャの環境に取り込まれた値は、移動の追跡が粗く、破棄の位置が仕様の想定とずれることがある（M5 の出力で詰める）。クロージャの値は記録中も `Copyable` として扱うので、`let d = c;` で `c` は空にならない。これらの現状の順序は `tests/m3_drop_limits.rs` で固定してあり、仕様の想定に近づけたらそのテストを直す。スタックの枯渇による停止のときの破棄は、条件 9 のとおり内側の枠から外側へ、各枠で宣言の逆順になる（同じファイルのテスト）。
- **`fs.read` の差し替えと `Cell`・`Shared`**: `Options::fs_files`（パス -> 内容の表）を渡すと、`fs.read(&p)` は表を引き、ない `p` は `Err(IoError.NotFound(p))` を返す。表がない（既定）ときは実際のファイルを読まず未対応として止まる（実ファイルは M4）。`sigil run --fs-double 仮のパス=実ファイル ...` で同じ差し替えができる。`Cell.new(v)` は書き換えられる箱、`Shared.new(x)` は `x` をそのまま共有の持ち主にする（値は `Rc` で共有される）。`Shared<Cell<T>>` の `get`・`set` は箱の中身を読み書きする。`Path` は `String` と同じ表現で、`is_empty` を持つ。`IoError` は `IoError.NotFound(パス)` だけを作る。

  1. （実施済み）ADR 0013 の完了条件のテスト（`tests/m3_stdlib.rs`）
  2. （実施済み）決定 3 の条件 9（破棄の順序）のテスト（`tests/m3_drop_order.rs`）と、借用区間の部品の対のテスト（`tests/borrow_pairs.rs`。`src/borrow.rs` の単体テストと名前が一致することも確かめる）

  4. （M4 の効果操作で実施）実際のファイルの `fs.read`・`fs.write`、`Path` の操作（下の「M4 の記録（効果操作）」）

**M4 の記録（効果操作）**

- **実ファイルの `fs.read`・`fs.write`**: `Options::fs_files` が `None`（既定）のとき、`fs.read(&p)` は実ファイルを UTF-8 の文字列として読み、`fs.write(&p, &s)` は `p` を作成または上書きする（`std::fs`）。`Options::fs_files` が `Some` のときは従来どおり表だけを使い、`fs.write` は表を書き換える（実ファイルには触れない）。差し替えの表と実ファイルは混ぜない。
- **`IoError` の腕**: 失敗は `Err(IoError.NotFound(パス))`・`Err(IoError.PermissionDenied(パス))`・`Err(IoError.Other(パス))` のいずれかで、`std::io::ErrorKind` の `NotFound`・`PermissionDenied`・それ以外に対応する。`IoError` は不透明型のままで、プログラムから腕を取り出す手段はまだない（`ConfigError.Io` に包んで運ぶだけ）。OS のエラーメッセージは含めない（環境で変わり、テストが不安定になるため）。UTF-8 でないファイルの読み込みは `Other`。
- **`Path`**: 実行時の表現は `String` のまま。`Path.new(s: &String) -> Path`、`join(self: &Path, name: &String) -> Path`、`file_name(self: &Path) -> Option<String>`、`parent(self: &Path) -> Option<Path>` を加えた（効果は `none`）。意味は Rust の `std::path::Path` に従う（`join` に絶対パスを渡すとそれに置き換わる。`/` の `parent`・`file_name` は `None`。`a` の `parent` は空のパス）。区切りは実行環境の OS のものを使う。パスの存在確認や正規化など、ファイルシステムを引く操作は加えていない。
- **`Cell` の複製（決定）**: `Cell` 単体の `clone` は独立した複製を作る（中身も複製する）。`Shared<Cell<T>>` の `clone` は、同じ `Cell` を指す（共有の所有を増やす）。`Shared.new(cell)` は `Cell` を `Value::Shared` で包んで両者を区別する。構造体・一覧・列挙・組が `Shared` の外に `Cell` を持つとき、その値の `clone` は `Cell` も複製する。`Shared` の中の `Cell` は複製せず共有を保つ。`trace_drops` の記録中の `clone`（`deep_clone`）も同じ規則で、`Cell` 単体の `clone` は破棄される値を 2 つにし、`Shared` の `clone` は 1 つのままにする。
- **`--fs-double` の重複**: 同じ仮のパスを 2 回指定すると使い方の誤りとして終了コード 2 で止まる（後勝ちにも先勝ちにもしない）。
- **残した制限**: `deep_clone` は再帰で、何万段も入れ子になった `Cell` 入りの値の `clone` はホストのスタックを使う（破棄は反復化済み）。`fs` は同期で、ファイルの読み書きの途中で中断した部分の書き込みは戻さない。`console.log` の出力は文字列に溜めたまま（本物の標準出力は未実装）。

**M5 のランタイムとリンカ**

- **ランタイムの供給元**: 出力した実行ファイルが使う実行時の機能（`console` の出力、`fs.read`、メモリの確保と解放、契約違反による停止と終了コード）は、P0 では **暫定の Rust 製ランタイム** が供給する。Rust で書いた静的ライブラリとし（Rust の標準ライブラリに依存してよい）、コンパイラが生成したオブジェクトと静的にリンクする。最小のコンテナで動かすため、実行時の動的リンクに頼らない。
- **境界**: 暫定ランタイムの境界は、M4 で決める標準ライブラリの OS 依存部分の宣言（関数のシグネチャと効果）とする。Sigil のプログラムから Rust の関数を直接は呼べない。このため、置き換えても Sigil のプログラムは変わらない。
- **リンカ**: P0 の間は、ビルドする環境にある外部のリンカに依存する。どのリンカを使うか（Rust のツールチェーンに含まれる `rust-lld` か、環境の `cc` 経由のリンカか）は、M5 の前の論点「出力先とコンパイラ構成」（決定 4）で決める。リンカは実行ファイルの組み立てに使う道具で、出力に既存言語のコードを含めないので、決定 1 の「コンパイラ自体の実装の補助」として扱う。
- **置き換えの時期**: 暫定ランタイムは、標準ライブラリの OS 依存部分を Sigil（信頼基盤のモジュール。ADR 0005 の決定 3）で書いたものに置き換える。その実装には M5 のネイティブ出力と、M4 の前に決める信頼基盤の宣言方法が先に要る。置き換えは P1 の範囲を決める ADR で P1 の完了条件に含め、P1 の完了までに行う。
- **ADR 0005 との関係**: ADR 0005 は、置き換えの方針を「既存の部品を使うことではなく Sigil で作り直すこと」とし、標準ライブラリとランタイムに既存言語のライブラリを持ち込まない。暫定ランタイムは出力した実行ファイルに Rust のコードを含めるので、この方針の **期限付きの例外** とする。例外の範囲は上に挙げた機能に限り、Sigil の利用者が既存言語のライブラリを使う手段（ADR 0001 の非目標）にはしない。

- 関数にカーソルを置くと、`sigil spec` と同じ仕様を返す。

M6 の完了をもって P0 の完了とする。契約の静的検査（証明）は P0 に含めず、実行時検査に留める（決定 5）。

## 決定 3: 並行処理を後から加えるための条件

並行処理のモデル（スレッド・非同期・アクターなど）は ADR 0007 で決める。

### 選択肢

- **A: P0 の前にモデルを決める**: ADR 0007 を先に書き、P0 から並行処理を実装する。
- **B: 何も条件を置かない**: P0 を並行処理を考えずに作り、ADR 0007 で必要になった箇所を改める。
- **C: モデルは決めず、後の決定を妨げない条件だけを決め、テストで固定する**。

### 比較

| 観点 | A: 先に決める | B: 条件なし | C: 条件だけ決める |
|---|---|---|---|
| 1. P0 の着手を遅らせない | × モデルの比較が先に要る | ◎ | ○ 条件の分だけ設計の手間が増える |
| 2. 後での改修の費用 | ◎ | × 型・効果・借用の検査器の中心を作り直す可能性がある | ○ 条件の漏れの分だけ改修がありうる |
| 3. 早すぎる決定の危険 | × 処理系の経験がない段階でモデルを固定する | ◎ | ○ 決めるのは拡張の余地だけ |

### 決定

**C** を採用する。P0 の実装が後の決定を妨げないよう、次の条件を満たすことだけを決める。

#### 型システム

1. **型の性質を構造から導く仕組み**: 「スレッドをまたいで渡せるか」「スレッド間で共有できるか」（Rust の `Send` / `Sync` に相当）を後から加えられるよう、型の性質を、型の構成要素から自動で導く仕組みを型検査器に用意する。P0 では「暗黙に複製されるか」（ADR 0003 の規則 1）をこの仕組みで実装し、新しい性質を追加しやすいことを確かめる。
2. **共有所有の型を最初から分けておく**: ADR 0003 の規則 4 は、単一スレッド用とスレッド間用の共有所有の型を区別している。P0 では単一スレッド用（`Shared`・`Cell`）だけを作るが、スレッド間用を別の型として後から加えることを前提に名前を付け、両者を暗黙に変換しない。
3. **脱出するクロージャがとらえる値を検査できること**: スレッドや非同期の処理に渡すクロージャは脱出するクロージャである（ADR 0003 の規則 5）。とらえた値の型を後から上記の性質で検査できるよう、クロージャの型にとらえた値の一覧を保持する。

#### 効果システム

4. **カテゴリを追加できる実装**: ADR 0004 の効果カテゴリは、コンパイラに埋め込んだ固定の列挙ではなく、標準ライブラリが宣言する表として実装する。並行処理の効果（例: スレッドの起動、非同期の待機）を、ADR 0005 の手続き（ADR に記録して標準ライブラリが追加する）で加えられるようにする。
5. **非同期を効果として扱う余地**: ADR 0004 は `async` を効果とするかを未決とした。どちらに決めても、効果の推論が「呼び出した関数の効果の和」で求まり、`of(f)` の引き継ぎが同じ規則で働くことを条件とする。非同期を効果とした場合に、同期の関数と非同期の関数で書き分けが必要になる問題（関数の色の問題）が `of(f)` で緩和できるかを ADR 0007 で検討する。
6. **`state` 効果の粒度**: 単一スレッドの共有所有を通した書き換えと、スレッド間の排他制御を通した書き換えを、同じ `state` にするか分けるかは ADR 0007 で決める。P0 の推論器は、`state` の下に下位カテゴリを後から加えられる形にする（ADR 0004 の階層の規則をそのまま使う）。
7. **`clock` の「待つ」**: ADR 0004 の `clock` は「待つ」を含む。非同期の待機との関係は ADR 0007 で決める。P0 では同期的に待つ実装だけを持つ。
   - **改訂（[ADR 0007](0007-concurrency-model.md)）**: 時間を待つ操作は `clock, task.suspend` を起こし、同期的に待つ操作は持たない。P0 には `clock` を入れない。

#### 所有権・実行時の意味論

8. **借用の範囲の定義を一か所にまとめる**: ADR 0003 の規則 2 により、借用は使われる最後の地点で終わる。また規則 3 により借用は引数としてだけ渡せるので、返される参照を除き、呼び出し先に渡った借用は、その呼び出しから戻るまでに終わる。規則 3 により返された参照（借用の引数がちょうど 1 つの場合）が持つ借用の区間も、区間計算の部品の対象に含める。非同期の関数が中断点をまたいで借用の引数を持ち続けることを許すかは ADR 0007 で決める。P0 の借用検査器は、借用が有効な区間の計算を一か所にまとめ、中断点という区切りを後から加えられるようにする。
9. **破棄の地点の規則**: 破棄の地点はコンパイル時に決まる（ADR 0003）。並行処理では、処理の取り消し（キャンセル）時にどこで何が破棄されるかを決める必要がある。P0 では、早期の戻り（`?`）と契約違反による停止の際の破棄の順序を明確に定め、テストで固定する。取り消しはこの規則の延長として定義する。
10. **ランタイムの分割**: 実行の割り当て（スケジューラ）など並行処理の実行時の部品は、標準ライブラリのうち OS の機能を使う部分に置けるよう、核の部分にスレッドや非同期の前提を持ち込まない。
11. **出力先による制限**: ブラウザ（WebAssembly・JavaScript）ではスレッドの扱いが限られる。ADR 0004 の規則 5（出力先による効果の制限）を、並行処理の効果にもそのまま使えることを確かめる。
12. **大域の可変な値を持たない**（[ADR 0007](0007-concurrency-model.md) で追加）: タスクの値がタスクの外から共有されないことを、スレッドをまたぐ型の区別の前提とする。P0 では大域の可変な値を無条件に禁止する。緩和（`Shareable` な型に限って許すなど）は後の ADR で決める。標準ライブラリの内部の大域の状態（乱数の状態、実行の割り当て）は信頼基盤の例外とし、検査を外した箇所の契約に安全の前提を書く。

## 決定 5: P0 での契約の検査方法

### 評価の観点

重要な順に並べる。

1. **仕様として信頼できるか**: `requires` / `ensures` が守られることを、どこまで保証できるか。
2. **P0 の実装量**: P0 の完了を大きく遅らせないか。
3. **AI が誤りなく書けるか**: 検査を通らないときの直し方が明確か。
4. **後から変えられるか**: 後で別の方法を加えるとき、それまでに書いた契約を書き直さずに済むか。

### 選択肢

- **A: 実行時検査のみ**: `requires` は関数の入口で、`ensures` は戻る直前に評価し、偽なら契約違反として停止する。
- **B: 静的検査（証明）を P0 に含める**: Dafny・SPARK などのように、契約が常に成り立つことをコンパイル時に証明する。
- **C: 実行時検査を基本に、静的に真偽が決まる簡単な場合だけコンパイル時に判定する**

### 比較

| 観点 | A: 実行時のみ | B: 静的検査 | C: 実行時 + 簡単な静的判定 |
|---|---|---|---|
| 1. 仕様の信頼性 | △ 実行した経路でしか違反を見つけられない | ◎ すべての経路で成り立つことを示せる | △ A とほぼ同じ（静的に判定できる場合は少ない） |
| 2. P0 の実装量 | ◎ インタプリタとコード生成に契約の評価を足すだけ | × 証明器との接続と、ループ不変条件など契約の言語の拡張が要る | ○ |
| 3. AI が書けるか | ◎ 契約は通常の式として書けばよい | △ 証明が通らないときの手がかりが少なく、補助の注釈が要る | ○ |
| 4. 後から変えられるか | ○ 契約の式の意味（評価したときの真偽）を先に固めるので、静的検査を後で加えても契約の書き方は変わらない。静的に示せた契約は実行時の検査を省くだけになる | △ 証明器の都合で契約の言語を先に狭めると、後で広げにくい | ○ ただし、どの契約が静的に判定されたかの境界が仕様の読み手に見えにくい |

### 決定

**A: 実行時検査のみ** を採用する。観点 1 では B に劣るが、観点 2〜4 で勝り、P0 の目的（言語の核を動かし、ADR 0002〜0004 の決定を計測で確かめること）を遅らせない。観点 1 の不足は、静的検査を P0 の後に加えることで補う（決定 4 の「P0 の後でよいもの」）。

- `old(...)` は関数の入口で値を記録して評価する（表記は [ADR 0008](0008-m0-notation.md) で決定）。
- 篩型（`Port` など）の範囲は、篩型への変換の時点で実行時に検査する。
- 契約違反は `Result` ではなく停止として扱う（呼び出し側の誤りまたは実装の誤りであり、回復の対象ではないため）。停止を効果に数えるかは、決定 4 の「異常停止・無限ループを効果に数えるか」で M3 の前に決める（[ADR 0012](0012-ownership-check-and-stdlib.md) の決定 7 で「M1 の前」から改めた）。**追記（[ADR 0013](0013-termination-stdlib-and-function-values.md)）**: 異常停止も無限ループも効果に数えないと決めた。`ensures` は「戻るならば成り立つ」ことを表し、契約の式の評価中の異常停止は契約違反と区別して報告する。

## 影響

- **リポジトリ**: Rust のコンパイラを、このリポジトリに置く（ディレクトリ構成は M0 の着手時に決める）。リポジトリが言語と標準ライブラリを扱うという ADR 0005 の方針に沿う。
- **examples**: 完了条件のため、サンプルにテスト用の入口と、エラー例を切り出したファイルを加える。サンプルの未確定の表記は M0 の前に決めた表記に直す。サンプルの書き方が正規形と食い違う場合も、サンプルを直す。
- **ランタイム**: P0 の間は、ネイティブ出力に暫定の Rust 製ランタイムを含める（ADR 0005 の方針の期限付きの例外。決定 2 の「M5 のランタイムとリンカ」）。
- **ADR 0002〜0004 の計測**: 3 つの ADR は「処理系ができた段階で計測する」と定めている。M0 の完了で構文エラー率（ADR 0002）を、M1 で効果の検査のエラー率（ADR 0004）を、M2 で所有権の検査のエラー率（ADR 0003）を計測できるようになる。各段階の完了後に計測を行い、結果を記録する。
- **DESIGN.md**: 未決の論点の表に、決める時期と、本 ADR で加えた論点（サンプルの未確定の表記、モジュールの単位と出力先の指定）を加え、本 ADR で決めたもの（実装言語と段階分け、P0 の契約の検査方法）を反映する。あわせて、長期目標と段階計画の行の「P0〜P6」を、ADR 0005 の段階表に合わせて「P0〜P7」に訂正する（DESIGN.md の記載の誤りの訂正で、ADR 0005 の決定は変えない）。
- **README**: ステータスに P0 の進め方を加える。

## 根拠の限界と再検証

- 実装言語の比較（特に観点 1「AI が誤りなく書けるか」）は、一般に知られている傾向（学習データの量、型検査の強さ）に基づく定性的な判断であり、各言語でこの処理系の一部を書かせて比べた結果ではない。
- マイルストーンの分け方と規模の見積もりは、処理系を書く前の見込みである。M0 の完了時に、残りの段階の分け方を見直す。
- 並行処理の条件（決定 3）は、ADR 0007 の候補を具体的に比べる前に列挙したもので、漏れがありうる。ADR 0007 で、どの条件が実際に必要だったかを確認する。
- 候補の案出しと採点を同じ者（Claude）が行っており、偏りがありうる。
- 次の場合は、この ADR を見直す。
  - M0〜M2 の実装で、Rust の借用の検査エラーへの対処がコンパイラ開発の主な手戻りになった場合（実装言語の再検討）
  - Cranelift で、M5 の完了条件（実行結果の一致）を満たせない機能が見つかった場合（バックエンドの再検討）
  - M3〜M6 で、実行時検査では見つからなかった契約違反が問題になった場合（静的検査を P0 の後まで待つかの再検討）
