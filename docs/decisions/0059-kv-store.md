# 0059: KV ストア（sigil-stash-kv）

- **状態**: 提案（typesafe-ai 正式判定済み）
- **日付**: 2026-11-23（JST）
- **対象**: [Issue #723](https://github.com/goodnasubi/sigil/issues/723)、レーン E

## 背景

小規模なサービスで、再起動後も使えるセッションと単一キーの共有状態、再生成できる sigix のキャッシュを扱う。仕様は本リポジトリで管理し、実装は [`goodnasubi/sigil-stash-kv`](https://github.com/goodnasubi/sigil-stash-kv) に置く。[ADR 0044](0044-p4-scope.md) 決定 4 と [ADR 0056](0056-sigix-web-server.md) のリポジトリ分離に従う。Issue が挙げる計画下書き `backend-suite-plan-draft.md` §3 は本リポジトリで確認できなかったため、起草の材料は Issue 本文と関連 ADR とした。

## 決定 1 — sigil-db 核を利用する

単一ノードの KV とし、永続モードは [ADR 0045](0045-p4-1-database-core.md) の sigil-db 核の型付き関係 API に、バイナリキーを主キーとする専用の表を載せる。値と絶対期限（期限なしも表現）を同じ行に置く。キーごとの読み取り・期限判定・更新は核の直列トランザクションで行う。WAL・同期・checkpoint・復旧・排他ロックは核が担い、永続モードの更新成功は commit の同期成功後にだけ返す。応答喪失や `CommitUnknown` ではクライアントが成否不明として扱う。核が再 open を要求した場合は処理を停止して復旧する。

キャッシュには明示的に選んだ別のメモリ専用インスタンスを使う。永続モードの障害でメモリ専用モードに切り替わることはない。独立した永続化案は、書き込みの中断・復旧・互換性の検証を再度必要とする。メモリ専用に絞る案では、再起動時に未失効のセッションと共有状態を保持できない。[ADR 0001](0001-vision-and-scope.md) が求めるレビュー可能な仕様に沿い、KV 固有の意味と核の保証をそれぞれ既存の試験と契約で検証できる形を選ぶ。

## 決定 2 — 版付きの最小 TCP プロトコル

初版は独自の長さ付きバイナリプロトコルと Sigil の型付きクライアントを提供する。Redis 互換案には既存クライアントを使える利点があるが、Issue に互換要件はなく、RESP とコマンドの互換範囲を維持するコストが加わる。

- 各フレームは 32 bit 符号なしビッグエンディアンのフレーム長、1 byte のプロトコル版（初版は 1）、1 byte の操作または結果の種別、種別ごとの本文で構成する。フレーム長は版からフレーム末尾までのバイト数で、2〜4096 byte とする。可変長のフィールドは長さとバイト列、TTL は秒の整数で表す。判定入力ではミリ秒を例示したが、初版は既存の公開時計に合わせて秒単位とする。操作・結果の符号、各フィールドの符号化、正例・負例は TCP の実装段の仕様表と fixture で固定する。
- 接続ごとに一度に 1 要求を処理し、要求と応答は 1 対 1 とする。応答は成功、値、キーなし、型付きエラーを区別する。未知の操作や引数の誤りはエラーにする。未対応版、上限外のフレーム長、途中で切れたフレームなど、継続できない入力は接続を閉じる。
- 待ち受けは既定でループバック。別ホストからの接続は、明示設定した隔離内部ネットワークに限定する。キー・値・セッション ID をログに出さない。フレーム長は確保前に検査し、同時接続、読み書き期限、ストア容量には有限の上限を置く。上限値・タイムアウト・エラーの対応表は各実装段で固定し、境界値も試験する。

## 決定 3 — 初版は単一キーの操作に絞る

キーと値は任意のバイト列。キーは 1〜512 byte、値は 0〜3072 byte とし、キー・行の符号化後にも核の 1024／4096 byte 上限を適用する。同じ公開上限をメモリ専用モードにも適用する。容量上限では、新規書き込みをエラーにする前に期限切れデータの回収を試みてよい。他の有効なキーを暗黙に削除しない。

| 操作 | 初版の契約 |
|---|---|
| `GET(key)` | 未期限の値を返す。未登録・削除済み・期限切れはキーなし。障害はエラー。 |
| `PUT(key, value, ttl)` | 作成または置換。値と期限を原子的に設定し、置換時は前の期限も置き換える。TTL は正の整数秒または明示的な期限なし。メモリ専用のキャッシュとセッションで TTL は必須。期限の計算があふれる値は拒否する。 |
| `DELETE(key)` | キーを失効させる。無いキーにも成功を返す。永続モードで成功した削除は復旧後も有効。 |
| `PING` | 接続確認。保存データにはアクセスしない。 |

- **期限** — `now >= deadline` で期限切れとし、GC を待たず読み取りから除く。期限の判定と削除を同一トランザクション（メモリ専用では同じ直列操作）で行い、古い期限に基づいて新しい値を消さない。回収は上限付きの遅延削除または小分けの掃除とする。永続モードの期限は UTC の Unix 時刻で保持し、再起動しても残り TTL を作り直さない。信頼でき、受理時から逆行しない時刻を再起動をまたいで確保することを運用の前提とする。時刻の取得エラーや検出した逆行時は期限付きの値の読み取りと設定をエラーにする。メモリ専用モードでは単調時計で経過時間を測る。
- **セッション** — 永続モードに有限 TTL で置き、明示的な失効は `DELETE` の成功で確定する。セッション利用者はキーを再利用せず、更新によって失効済みの識別子を再登録しない。`GET` のキーなしや KV のエラーを認証成功に使わない。削除の成否が不明なら失効が確定したとは扱わない。論理削除・期限切れ後も WAL やバックアップに旧値が残りうる。
- **sigix** — キャッシュは経路ごとに明示的に有効化し、共有を許可した公開 `GET` の応答だけを有限 TTL で保存する。キーは経路と対象の識別子（ホスト、パス、クエリなど）を含め、同じキーで応答を共有してよい条件を連携段で明文化する。認証付き要求や Cookie に依存する要求、共有禁止の指示や `Set-Cookie` を含む応答、`Vary` に従って表現を区別できない応答、キー・応答が上限を超えるものは通過させる。ミス、期限切れ、容量超過、KV 障害時はオリジンを利用する。既存の sigix 段階 1・2 はこの連携に依存しない。
- **共有状態** — 単一キーの値の参照・置換に限る。比較交換、独立した期限更新、複数キー操作、一覧、通知、自動追い出し、複製・分散は後続の検討とする。

認証部品 `sigil-rune-auth` と TLS 終端部品 `sigil-shield-tls` の仕様および利用者向け製品名は別の判断に委ねる。公開関門は [ADR 0020](0020-p1-security-addendum.md) に従う。

## 決定 4 — 核を固定版で取り込み、段階ごとに検証する

永続アダプターを薄く保ち、`rel_get`／`rel_insert`／`rel_replace`／`rel_delete` とトランザクション API の公開契約に依存する。SQL・PostgreSQL 通信・DB サーバーの起動、内部ページ形式への直接アクセスは依存に含めない。メモリ専用の段は核なしで検証できる。DB モジュールの取得・組み込みは実装リポジトリのビルドで再現できるようにし、コンパイラと標準ライブラリ、核をそれぞれ完全なコミット SHA で固定する。浮動する `main` を取得してビルドする仕組みは使わない。

仕様の参照版は `sigil` の `0c1c441e60933fadbe05e1c5c63b11bcf4ad4409` と `sigil-db` の `9483e36f08c35bfc62b3beeb008a531887506037`。実装の固定版は各段で必要な API と試験に照らして確定し、更新時は互換性・上限・復旧試験を再実行する。言語や標準ライブラリに不足があれば本リポジトリで契約変更を先に検討する。アプリ側の信頼基盤追加で迂回しない。参照版には公開 `clock.unix_seconds` がある。メモリ専用モードが使う単調時計の公開 API は参照版では確認できておらず、必要な契約を段 1 で確認する。時刻を差し替えた KV 契約の試験は先に進められる。

| 段 | 成果物と完了条件 |
|---|---|
| 1. KV 契約とメモリ専用実装 | 型付き操作 API と時刻を差し替えられる単体試験。原子的な PUT、失効・期限境界、上限、競合時の順序を確認する。 |
| 2. 永続アダプター | 固定した sigil-db 核を接続し、同じ操作契約を検証する。中断・復旧試験で成功済み更新と削除、原子的な期限の保存、期限切れの再起動後の扱い、commit 成否不明時の停止を確認する。 |
| 3. TCP と Sigil クライアント | 版付きフレームの仕様表と fixture、ループバック統合試験を揃える。分割読み取り、不正長、上限、タイムアウト、切断を試験し、パーサーのファジングを行う。 |
| 4. sigix の任意のキャッシュ連携 | sigix 側でキャッシュ可能な経路を設定し、ヒット・ミス・期限切れ・共有不可・上限超過・障害時の通過を試験する。KV 本体の初版は段 3 で使える状態とする。 |

段 1 → 2 → 3 → 4 の順に進める。メモリだけの試作を最初に切り出すことで、永続化とネットワーク境界の検証を別の PR で行える。DB サーバー経由の案は別プロセスと通信に依存し、核の型付き API を使う場合より障害境界が増える。
