# 0031: 最初の待ちの操作とソケット API の形（PR 6-3a、段階 6）

- **状態**: 提案（PR 6-3a、Issue #369）。所有者の判断が要る点は、末尾の「人間の判断が要る点」に判断点 A〜F として挙げた。**判断点 A（時計）は、2026-11-10 08:24 JST に所有者が案 A（外の待ちがあるときだけ実時間に結ぶ）で決定した**（下の決定 1-3 の決定の記録。Issue #375 のコメント）。判断点 B〜F は未承認で、本 ADR 全体の承認も記録されていない。[ADR 0030](0030-p1b-native-concurrency.md) の判断点 3〜6 も未承認のままで、本 ADR は「承認済み」とは書かない（前提として参照するだけ）。
- **日付**: 2026-11-10
- **対象**: ADR 0018 決定 3 の段階 6 の最初の作業。ネイティブ・評価器の両方で、fd の準備完了と期限で中断する言語の操作、TCP ソケットの最小の API、複数ルートの入口とルート単位の隔離、段階 6 の PR の細分。HTTP/1.1 の解釈そのもの（ADR 0020 決定 4 の上限表と密輸の規則）は、本 ADR の後の HTTP の ADR（下の 6-3g）で決める。

## 背景

- [ADR 0030](0030-p1b-native-concurrency.md) の段階 5 は、`epoll` と時間の待機の**機構**（`std.os.io`。専用の I/O スレッド、`EPOLLONESHOT`、期限の最小ヒープ、完了の列、取り消し）と、複数ワーカーの実行の割り当て（`std.os.sched`）を入れた。補足 C は、完了の列から実行可能待ち行列への**結線**と、本番のスレッドの本体（`body`）を `worker_run` と `io_loop` に振り分ける作業を、最初の待ちの操作と一緒に入れるとした。補足 D は、複数ルートの入口とルート単位の隔離、ルートをまたぐ `LockBroken` の配送を段階 6 へ回した。両方とも「PR 6-3 の ADR で決める」とされている。
- [ADR 0026](0026-p1a-concurrency.md) 決定 4 は、`sigil run` の入口は 1 つのルートタスクで、「サーバーが要求ごとにルートタスクを起動する形」は段階 6 で決める、とした。評価器の `run_roots_with`（`src/ir_eval/mod.rs`）は複数のルートを扱えるが、ルートは**実行の開始時に引数の組の数だけ**決まり、実行中に起動する入口は無い。ネイティブのルートは 1 つ（番号 0）だけである。
- 現状の `task.sleep` は、評価器でもネイティブ（`std.os.sched` の `S_CLOCK`）でも**仮想の時計**で動く。実行可能なタスクが無くなったとき、時計を最も早い目覚めまで**飛ばす**（実時間で待たない）。ネイティブの `task.timeout`・`task.race`・`task.all_ok` は未対応で、生成コードがビルドで止める（`src/codegen/func/task.rs`、ADR 0030 補足 D の表）。一方、ADR 0020 決定 4 は、要求の処理の時間の上限を `task.timeout` で実装すると決めている。
- 効果の体系（[ADR 0004](0004-effects.md)）には `net.server`（接続を待ち受ける。応答を待つ操作は `task.suspend` も起こす）、`net.client`、`clock`（待つ操作は `task.suspend` も起こす）が定義済みで、`src/effects.rs` の対象は `net.server` が server のみ、`clock` が browser・server、`task.suspend` が bare を含むすべて。[ADR 0007](0007-concurrency-model.md) 決定 3 は、`fs.read`／`fs.write`／`console` は中断せず OS スレッドを止めるが、ネットワークと `db` の応答の待機は `task.suspend` を起こす、と線を引いた。
- 標準ライブラリの OS 層には、OS の機能を呼ぶ名前空間の関数（`fs.read(&p)`・`console.log(&x)`。`src/stdlib.rs` の `NAMESPACED_FNS`、層は `Os`）と、中身を見せない型（`OPAQUE_TYPES`。`Path`・`IoError` など）がある。`Os` の行の集合は単体テストで ADR の一覧に固定されている（行を足す PR は、ADR の一覧と一緒に変える）。標準ライブラリのネイティブの実体は、`std.os.*` の埋め込みモジュール（`trust base`、`raw.syscall` を使う `unchecked` の関数）で、評価器は Rust の組み込みで同じ API を持つ（`std.os.console`・`std.os.fs` など。評価器が呼ばない `std.os.thread`・`std.os.sched`・`std.os.io` は例外）。
- 評価器の `raw.syscall` の許可表は 9 個（`read`・`write`・`close`・`mmap`・`munmap`・`exit_group`・`openat`・`newfstatat`・`unlinkat`。`src/ir_eval/call.rs`、`tests/raw_syscall_table.rs`）。ソケット系のシステムコールは含まない。行の追加は ADR 0018 判断 2 のレビューの対象。
- ADR 0026 決定 4 は、止めたタスクが持つ資源（ソケットを含む）を取り消しと同じ順序で破棄すること、破棄の処理は `task.suspend` を起こせないが、ソケットを閉じるなどの**中断しない I/O は破棄でしてよい**ことを決めている。本 ADR はこれを前提にする。
- [ADR 0020](0020-p1-security-addendum.md) 決定 4 は、HTTP サーバーの上限（同時の接続の数 256、`listen` の backlog 128、各種の時間の上限、サイズの上限）を既定値として持ち、決定 5 は「`epoll` と接続の受け付けの止め（同時の接続の数の上限）」を段階 5・6 に割り当てている。段階 6 の各 ADR は決定 5 の項目を完了条件に含める。

本 ADR は**設計の提案**であり、実装は含まない。決める点には推奨を付け、所有者の確認が要る点は判断点としてまとめる。

## 評価の観点

重要な順に並べる。

1. **安全**: データ競合を型と所有権で排除する保証（ADR 0007）と、fd のリソースの安全（二重の close・漏れ・番号の再利用の取り違えが起きないこと）を保つ。信頼基盤（`unchecked`・`raw.*`）を最小にする（ADR 0005・0016）。
2. **外部からの入力に対する守り**: ADR 0020 の上限（接続数・サイズ・時間）を、API の形で破りにくくする。
3. **評価器との意味の一致**: 評価器が意味の基準で、ネイティブはそれと突き合わせる（ADR 0015）。突き合わせられない部分は、差を表に固定する（ADR 0030 の方針）。
4. **既存の言語の規則の再利用**: 新しい効果カテゴリ・構文を足さない。ADR 0007 の構造化並行処理、ADR 0026 の `task` の API と同じ作法にそろえる。
5. **AI が誤りなく書けるか**: 公開する操作を少なくし、fd の番号や `epoll` を利用者に見せない。

## 決定 1: 最初の待ちの操作の形

### 1-1. 公開する操作と、公開しない操作

- 言語に公開する「待つ操作」は、次の 2 種類だけとする。
  - **時間**: 既存の `task.sleep`・`task.timeout`（ADR 0026 決定 3。シグネチャと効果は変えない。`clock, task.suspend` ／ `clock, task.spawn, task.suspend, of(g)`）。
  - **ソケットの操作**: `accept`・`read`・`write_all`（決定 3）。それぞれが、必要なときに内部で fd の準備完了を待つ。効果は `net.server, task.suspend`。
- **fd の準備完了を直接待つ操作（`io.wait_fd` など）は、利用者に公開しない**。fd の番号は `Int` で、所有の規則（二重の close など）を型で守れない。待つ対象はソケットの型の操作の中に閉じ込める。
- ただし実装には**内部の原始操作 `io.wait_fd(fd: Int, events: Int) -> Int`** が要る（待つ操作は、スケジューラの操作なので Sigil では書けない。`task.*` の部品と同じ）。これは `Builtin` の列挙子として足し、**`trust base` のモジュール（`std.*`）からだけ**呼べるようにする（利用者のモジュールから呼ぶとエラー）。シグネチャは `io.wait_fd(fd: Int, events: Int) -> Int`、効果は `task.suspend`、戻り値は準備のできたイベントの印（負の値はエラー）。`Builtin` の追加は `src/ir.rs` の契約変更なので、単独の PR（6-3b）にする（AGENTS.md）。

### 1-2. 待ちの共通の規則

- **中断点**: 待つ操作は中断点である（ADR 0007 決定 3）。待っている間、その OS スレッドは他のタスクの実行に使われる。
- **取り消し**: 待っているタスクが取り消されると、次の手順で終わる。(1) fd の登録を外す（`io_cancel`。トークンの登録・期限・取り出していない完了を外す）。(2) 外し終えてから、状態オブジェクトの値を取り消しの順序（ADR 0030 決定 1）で破棄する。fd を持つ値の破棄は `close` を呼ぶので、**登録を外すのが `close` より先**でなければならない（fd の番号が再利用されて、古い登録が別のソケットの通知を受けるのを防ぐ。`std.os.io` は通知を (トークン, 世代) で引くので、取り消し後に届いた古い通知は捨てられる）。
- **トークン**: 1 つのタスクが同時に持つ待ちは 1 つだけなので、`std.os.io` のトークンにはタスク番号を使う（`std.os.io` の範囲は 1 以上 2147483646 以下。範囲を超えないことは 6-3c で確かめ、超える場合は停止する）。
- **失敗の型**: ソケットの操作は `Result<_, NetError>` を返す（決定 3）。`io.wait_fd` の負の値（`epoll` の登録の失敗など）は、ソケットの操作の中で `NetError` に写す。待ちそのものが「取り消し」で終わる場合は、`Result` ではなく取り消しの伝播（ADR 0007 決定 4）で終わる。
- **時間切れ**: `task.timeout` の時間切れは `None`（ADR 0026 決定 3 のとおり）。ソケットの操作に時間切れの引数は足さない。時間の上限は `task.timeout` で包んで実現する（ADR 0020 決定 4 の「要求の処理の時間の上限は `task.timeout` で実装する」と同じ）。内側のソケットの待ちは、取り消しの規則で外れる。

### 1-3. 時計（`task.sleep`／`task.timeout` の時間）— 判断点 A

fd を待つ操作が入ると、「実行可能なタスクが無いとき、時計を最も早い目覚めまで飛ばす」という現在の仮想の時計の規則は、そのままでは成り立たない。クライアントからの入力を待っているだけのサーバーで時計を飛ばすと、30 秒の `task.timeout` が一瞬で時間切れになる。次の案を示す。

- **案 A（推奨）: 外の待ちがあるときだけ実時間に結ぶ**。時計は仮想のまま、プロセスが**最初に fd の待ちを登録した時点**から「実時間モード」に入る（以後、もとの仮想の時計に戻らない。戻ると時刻が逆行しうる）。実時間モードでは、時計は単調な実時間（`clock_gettime`）の経過に従って進み、実行可能なタスクが無いときは `epoll_wait` のタイムアウトに最も近い期限を使って**実際に待つ**。実時間モードに入るまで（fd の待ちを一度も使わないプログラム）は、今の仮想の時計の規則（時計を飛ばす）のまま。
  - 利点: 並行処理のサンプル（`examples/06-concurrency`）や既存のテストの `task.sleep` の観測が変わらない。fd を使わない評価器との突き合わせ（ADR 0030 5-2h）が壊れない。サーバーは自然に実時間になる。
  - 欠点: 同じ `task.sleep` の意味がプログラムの履歴（fd を使ったか）で変わる。説明が要る。
- **案 B: 実行時の指定**。環境変数（例: `SIGIL_CLOCK=real|virtual`）か起動の引数で時計の種類を選ぶ。既定は仮想。利点: 規則が単純。欠点: サーバーを実時間で動かし忘れると、時間の上限がすべて即時に切れて、検出しにくい。
- **案 C: 常に実時間**。`task.sleep` は実際に待つ。欠点: 既存の突き合わせとテストが、時間がかかり不安定になる。決定的モード（ADR 0030 決定 2）の意味が失われる。

評価器にも案 A を同じ規則で写す（評価器の `sleepers`・`clock` に、外の待ちの有無と実時間モードの旗を足す）。

> **判断点 A（決定済み）**: 所有者が 2026-11-10 08:24 JST に、**推奨案 A「外の待ちがあるときだけ実時間に結ぶ」**で決定した（Issue #375 のコメント。所有者の決定を、メインのチャットに基づいて記録したもの）。決定した規則は上の案 A のとおり: fd の待ちを一度も登録していない間は、今の仮想の時計（実行可能なタスクが無ければ時計を飛ばす）のままとし、最初に fd の待ちを登録した時点から実時間モードに入って戻らない。実時間モードでは、実行可能なタスクが無いとき、`epoll_wait` のタイムアウトに最も近い期限を使って実際に待つ。案 B（実行時の指定）と案 C（常に実時間）は採らない。決定の記録は案の文言以外を足していない（`epoll_wait` の丸めと期限の精度は、「根拠の限界」のとおり 6-3c で測る）。
>
> **判断点 D に依存して止まる範囲**: 時計の規則そのもの（実時間モードへの入り、ネイティブの `epoll_wait` での実際の待ち）は、判断点 D に依存しない。止まるのは、評価器の「外の待ち」の実体（決定 5-1。評価器の `io.wait_fd` と、評価器の実時間モードを動かす入力）で、これは判断点 D（評価器でのソケットの実装）の承認を待つ。それまで評価器の `io.wait_fd` は `unreachable` のままとし、評価器の時計は今の仮想の時計のままにする。

## 決定 2: 5-2f から延期した結線を入れる PR

ADR 0030 補足 C-2 の 2 つの作業を、**PR 6-3c（下の分割計画）**で入れる。

- 完了の列（`io_take`／`io_take_wait`）から実行可能待ち行列へ、`wake` と `notify` でタスクを積む結線。
- 本番のスレッドの本体（`body`）を、引数で `worker_run` と `io_loop` に振り分ける作業。I/O スレッドは、実時間モードに入った時点（最初の `io.wait_fd` の登録）で**遅延して作る**案を推奨する（fd を使わないプログラムは、これまでどおり I/O スレッドを持たない）。作るのは `std.os.thread.spawn` で、終了は `io_stop` → `join` → `io_free`（5-2f の手順）。

結線は、`io.wait_fd`（決定 1-1）と**同じ PR**で入れる。結線を検証する言語の操作が無い、という補足 C の理由は、`io.wait_fd` が `trust base` のテスト用モジュール（パイプで待つ）から呼べるようになることで解消する。ソケットの API（6-3e）を待たずに、結線を実際に動かして確かめられる。

## 決定 3: ソケット API の形（最小）

TCP の待ち受けとバイト列の読み書きだけを決める。HTTP の解釈、`net.client`（接続する側）、UDP、IPv6、名前解決（DNS）は含めない（ADR 0018 の「行わないこと」に従う。テストの相手側は、`tests/` の Rust の `std::net` が務める）。

### 3-1. モジュールと型

- ネイティブの実体: 埋め込みモジュール **`std.os.net`**（`trust base`、`targets server`）。`std.os.fs`・`std.os.console` と同じく暗黙に結ぶ OS 層で、利用者のモジュールから `use std.*` できない（ADR 0016 決定 3）。評価器は Rust の組み込みで同じ API を持つ（決定 5）。
- 利用者から見える名前: 名前空間 **`net`**（`fs.read` と同じ作法）。型は `TcpListener`・`TcpStream`・`NetError`（`OPAQUE_TYPES`、層は `Os`）。`bare` の出力先では使えない（`OsItemInCore`。ADR 0014）。
- `TcpListener`・`TcpStream`: 中身を見せない型。**複製できない**（`clone` は型検査でエラー）、`Copyable` でない。`Sendable`（ハンドラのタスクへ移すため）、`Shareable` でない（複数のタスクが同じ接続を同時に読み書きできない）。**fd の番号は利用者に見せない**（取り出す関数も、番号から作る関数も持たない）。
- **所有権と破棄**: 1 つの値が 1 つの fd を所有する。値の破棄で `close(2)` を 1 回呼ぶ（ADR 0026 決定 4 が許す中断しない I/O）。破棄は中断せず、失敗は捨てる。取り消し・異常停止での値の破棄でも同じ。**ただし `task.roots` の `start` に渡した接続は、所有者がルートの外（`RootGroup`）なので、そのルートの異常停止では破棄されず、`on_abort` に渡る**（決定 4-2。正常終了・集まりの取り消し・`on_abort` の異常停止では、通常どおり破棄で `close` される）。丁寧な終了（相手に書き込み側の終了を伝える）は、破棄の前に `shutdown` を明示的に呼ぶ（ADR 0007 決定 3）。

### 3-2. 操作

| 操作 | シグネチャ | 効果 | 備考 |
|---|---|---|---|
| `net.listen` | `listen(host: &String, port: Int, backlog: Int) -> Result<TcpListener, NetError>` | `net.server` | 中断しない。`host` は IPv4 のドット表記だけ（名前解決をしない）。`requires 0 <= port && port <= 65535 && 1 <= backlog && backlog <= 1024`。`port` が 0 なら空いている番号を選ぶ。`SO_REUSEADDR` を付ける。ソケットは非ブロッキングかつ close-on-exec で作る |
| `TcpListener.local_port` | `local_port(self: &TcpListener) -> Int` | `net.server` | 中断しない。実際の待ち受けの番号（`getsockname`）。テストで `port` に 0 を使うときに要る |
| `TcpListener.accept` | `accept(self: &TcpListener) -> Result<TcpStream, NetError>` | `net.server, task.suspend` | 接続が来るまで中断する。得た `TcpStream` も非ブロッキング |
| `TcpStream.read` | `read(self: &TcpStream, max: Int) -> Result<Bytes, NetError>` | `net.server, task.suspend` | 1 バイト以上読めるか、相手が書き込みを終えるまで中断する。**空の `Bytes` は相手の終了（EOF）**。`requires 1 <= max && max <= 65536`（1 回の読みの大きさの上限。ADR 0020 決定 4 の上限を、API の側で破れなくする） |
| `TcpStream.write_all` | `write_all(self: &TcpStream, data: &Bytes) -> Result<Unit, NetError>` | `net.server, task.suspend` | 全部書き終えるまで繰り返し、書けないときは中断する。書き込みが戻るのは、全部をカーネルに渡したとき |
| `TcpStream.shutdown` | `shutdown(self: &TcpStream) -> Result<Unit, NetError>` | `net.server` | 中断しない。書き込み側を閉じる（`SHUT_WR`）。読み込み側は開いたまま |

- `read` の戻り値が `Bytes` なのは ADR 0023（`Bytes` 型）による。HTTP の解釈は `Bytes` の上で行う。
- `write` は部分書き込みを返さず `write_all` にそろえる（部分書き込みの続きを間違える誤りを、利用者に書かせない）。
- `TcpStream` の相手のアドレスの取得、`TCP_NODELAY` などの調整、`TcpListener` のクローズの明示は持たない（必要になった段階の ADR で足す。閉じるのは破棄）。
- 読み書きを時間で打ち切る引数は持たない（決定 1-2）。

### 3-3. エラー — 判断点 B

`IoError` は腕を取り出せない型（ADR 0014）で、HTTP のサーバーは「相手が切った」と「それ以外」を分けて扱う必要がある。次を推奨する。

- **新しい型 `NetError`**。腕: `AddrInUse`、`PermissionDenied`、`Closed`（相手のリセット・切断・壊れた接続）、`Other`。`Other` は、想定外の `errno` を含む。プログラムは腕で `match` できる。
- 標準の列挙を `OPAQUE_TYPES` の枠で表せるかは検査器の実装を調べて確かめる必要がある（6-3e の最初の作業）。表せない場合の代案は、`NetError` を中身を見せない型にして `is_closed(self: &NetError) -> Bool` を足す。
- `IoError` を再利用する案は採らない（腕を取り出せないので、`Closed` の分岐が書けない）。

### 3-4. ネイティブの実装の骨格（信頼基盤の範囲）

`std.os.net` は、次の `raw.syscall` だけを使う（x86-64 の番号。見込みで、6-3e で実機と `tests/raw_syscall_table.rs` に照らして確かめる）。

| 目的 | システムコール |
|---|---|
| 作る | `socket`（41。`SOCK_NONBLOCK`・`SOCK_CLOEXEC` 付き） |
| 設定 | `setsockopt`（54。`SO_REUSEADDR`） |
| 待ち受け | `bind`（49）・`listen`（50）・`getsockname`（51） |
| 受け付け | `accept4`（288。`SOCK_NONBLOCK`・`SOCK_CLOEXEC` 付き） |
| 読み | `recvfrom`（45） |
| 書き | `sendto`（44。**`MSG_NOSIGNAL`** 付き） |
| 終了 | `shutdown`（48）・`close`（3） |

- 書きに `write` でなく `sendto`＋`MSG_NOSIGNAL` を使うのは、シグナルの処理を持たない（ADR 0030 の未決）ので、閉じた接続への書き込みで `SIGPIPE` がプロセスを落とすのを避けるためである。
- `EAGAIN` なら `io.wait_fd(fd, EPOLLIN/EPOLLOUT)` で待って、同じ操作をやり直す。`EINTR` はやり直す。ほかの負の値は `NetError` に写す。
- `unchecked` の前提の文は、「`sockaddr` の領域は確保した大きさの範囲で書く」「`fd` は `TcpListener`／`TcpStream` の所有する値だけ」「`close` は破棄でだけ、1 回」を軸に書く。`sockaddr` の組み立て（`AF_INET` の 16 バイト）は、1 つの関数に閉じ込める。
- **評価器の `raw.syscall` 許可表には足さない**（ADR 0030 決定 3 の推奨と同じ。ネイティブだけが使う標準モジュールで、評価器は呼ばない）。`tests/raw_syscall_table.rs` は変えない。

## 決定 4: 複数ルートの入口とルート単位の隔離

ADR 0026 決定 4 に従う。**隔離の単位はルートタスク**で、範囲の内側の子だけを切り離すことはしない。ADR 0030 補足 D の D-2 の 3 項目（ルート単位の隔離、複数ルートの入口、ルートをまたぐ `LockBroken` の配送）を、本決定で形を決め、6-3d で入れる。

### 4-1. 入口の形 — 判断点 C

サーバーは、接続ごと（HTTP の要求ごと）にルートタスクを起動する。起動の API を次の形にすることを推奨する。構造化並行処理（ADR 0007 決定 1。子は範囲より長く生きない）を保つため、`task.scope` と同じ「範囲の形」にする。

| 部品 | シグネチャ | 効果 |
|---|---|---|
| `task.roots` | `fn roots<T>(limit: Int, f: fn(&RootGroup) -> T) -> T` | `task.suspend, of(f)` |
| `RootGroup.reserve` | `fn reserve(self: &RootGroup) -> RootSlot` | `task.suspend` |
| `RootSlot.start` | `fn start<C: Sendable>(self: RootSlot, conn: C, g: fn(&C) -> Unit, on_abort: fn(C) -> Unit) -> Unit` | `task.spawn, of(g), of(on_abort)` |

- `task.roots(limit, f)` は、同時に生きる起動したルートの数の上限 `limit` を持つ**ルートの集まり**（`RootGroup`）を作り、本体 `f` を実行する。`limit` は `1 <= limit && limit <= 4096`。`RootGroup` と `RootSlot` は利用者が宣言できない前置きの型で、`Scope` と同じく借用の引数としてだけ現れ、複製できない（`RootSlot` は移動する）。
- `reserve` は、起動中のルートが `limit` に達しているとき、1 つが終わるまで**中断する**。返る `RootSlot` は「1 つ起動できる権利」で、破棄すると返る（起動せずに捨てた場合も上限から外れる）。**受け付けのループは、`accept` の前に `reserve` を呼ぶ**。これで、上限にある間は `accept` を呼ばず、新しい接続を受け付けない（ADR 0020 決定 4 の「同時の接続の数」の動き）。上限の検査を API の形に埋め込み、書き忘れを起こさない。
- `start` は、スロットを消費して新しいルートタスクを起動する。**接続（`conn`。典型は `TcpStream`）は `g` にとらえさせず、`start` の引数で渡す**。`g` は `&C` を引数に受け取って使う（借用は引数なのでとらえの禁止に触れない）。`g` と `on_abort` は脱出するクロージャとして扱い（ADR 0026 決定 3 の起動の検査と同じ）、借用をとらえてはならず、とらえる値は `Sendable` で、移動する。戻り値は `Unit` に限る（`join` は無い）。`conn` の所有者は起動したルートの**外**（ルートの集まり `RootGroup` の記録）にあり、ルートの中のタスクは借用だけを持つ。この所有の置き方が 4-2 の「500 を返せる境界」を作る。
- 起動したルートは、親の `task.roots` の範囲より長く生きない。`f` が戻ると、`task.roots` は起動済みのルートがすべて終わるまで**待ってから**戻る（`task.scope` が子の完了を待つのと同じ。穏やかな停止）。`f` が取り消された、または異常停止した場合は、起動済みのルートを**起動の逆順**に取り消し、すべて終わるのを待つ（ADR 0030 決定 1 の順序）。
- ルート 1 つの中の構造（そのルートの `task.scope`、子のタスク）は、これまでのルートと同じ。親から見て `task.roots` の起動は `Scope.spawn` と別物で、**停止の単位は起動したルート自身**になる（決定 4-2）。
- 代案: 受け付けと起動を 1 つにまとめた高水準の部品（`net.serve(listener, limit, handler)`）を言語の組み込みにする案。DoS の上限を 1 か所に集められるが、HTTP の都合を標準の組み込みに入れすぎる。フレームワーク（6-4）が上の部品で書ける形を推奨する。

### 4-2. ルート単位の隔離

- 起動したルートの中で異常停止（契約違反・桁あふれ・0 での除算など。ADR 0018 決定 7 の範囲）が起きたら、**そのルートに属するすべてのタスク**を取り消しと同じ順序で破棄して終わらせる。停止の報告は標準エラーに出す。**ほかのルートと親（受け付けのルート）は動き続ける**。`RootGroup` の起動済みの数から外れ、スロットが空く。
- 隔離できない停止（確保器の整合の破れ、スタックの溢れ、状態オブジェクトの破損）は、従来どおりプロセス全体を `exit_group(70)` で止める（ADR 0030 決定 7）。
- **異常停止したルートの接続は誰が持つのか**（Codex の指摘 P2。ADR 0018 決定 7 の「要求を 500 で終えて続ける」を実現できる境界が要る）。異常停止はそのルートの全タスクを破棄する（`src/ir_eval/sched.rs` の `stop_root` が、そのルートのタスクの値・通信路・`Lock` の値を捨てる）ので、接続をルートの中のタスクが所有していると、停止と同時に `close` され、500 を書けない。`start` が結果を返さないので、親も失敗を観測できない。次の案を比べた。
  - **案 1: 親（accept する側）が接続を所有し、ルートには借用だけを渡す**。借用は脱出するクロージャにとらえさせられず（ADR 0026 決定 3）、`TcpStream` は `Shareable` でないため、別のルートが親の持つ接続を借用できない。型の規則を変えずには成り立たない。採らない。
  - **案 2（推奨）: ルートの外に所有を置き、異常停止のときだけ `on_abort` に接続を渡す**。上の `start` の形。`conn` は `RootGroup` の記録が所有する。(a) `g` が正常に終わったら、`conn` を破棄して閉じ、スロットを空ける。(b) `g` のルートが異常停止したら、そのルートの全タスクを破棄した後で、**`conn` を破棄せず**、新しい短いルート（同じスロットで数える）で `on_abort(conn)` を実行する。`on_abort` は接続を持つ生存側で、フレームワークが 500 を書いて閉じる（書き込みが半端だった可能性は、フレームワークが応答の送信の状態を持って判断する。6-3g）。(c) `on_abort` 自身が異常停止したら、`conn` を破棄して閉じ、標準エラーに報告するだけで、それ以上は続けない。(d) 起動した集まりが取り消されたとき（`f` の取り消し・異常停止）は、`on_abort` を呼ばず `conn` を破棄して閉じる。親は失敗を観測する手段を持たず、ランタイムが監督する。スロットは `on_abort` が終わるまで返らないので、失敗した接続も同時の接続の数に数えられる（ADR 0020 の上限を超えない）。
  - **案 3: `start` が終了結果を返す／`RootGroup.finished()` で問い合わせる**。`conn` を `Finished { conn, ok }` で親へ返す。親は 500 を書いて閉じる。親で「受け付け」と「結果の回収」を同時に待つので、回収用の子のタスクが 1 つ要り（`RootGroup` を `Shareable` にする）、回収し忘れでスロットが埋まる。案 2 より部品が多い。
  - 案 2 は、親のタスクを待ちに使わず、ランタイムが監督する分だけ単純である。どちらを採るかは判断点 C。HTTP の 500 の本体は、`on_abort` を使うフレームワーク（6-3g、ADR 0020 の 500 の本体の規則）の役目。

### 4-3. `LockBroken` の配送

- 異常停止したルートのタスクが `Lock` を持っていた場合、その `Lock` は「壊れた」状態になる。**別のルートのタスクがその `Lock` を取得しようと待っていたら、起こして `Err(LockBroken)` で返す**（ADR 0026 決定 4）。壊れた `Lock` を戻す手段は持たない。
- 評価器は既にこの規則を持つ（`src/ir_eval/sched.rs`）。ネイティブは、タスクのレコードに属するルートの番号を持ち、停止したルートの `Lock` の保持者を探して壊す作業を足す。
- ルートの入口を足しても、`task.roots` の外のコード（`sigil run` の入口）の異常停止は、従来どおりプログラム全体の異常停止として報告される（ADR 0026 決定 4）。

## 決定 5: 評価器との関係と、突き合わせの仕方

### 5-1. 評価器での扱い — 判断点 D

評価器は意味の基準で、`net.*` と `task.roots` も評価器が持つ。ソケットの実体について次の案を示す。

- **案 A（推奨）: 評価器は Rust の標準ライブラリ（`std::net`）の組み込みで実装する**。ソケットは非ブロッキング。操作が `WouldBlock` のとき、タスクを「外の待ち」で中断する。実行可能なタスクが無いとき、評価器は準備完了を短い間隔の繰り返しで確かめる（`std` に `poll` が無いため。性能は要らない）。時計は決定 1-3 の案 A の規則で、外の待ちがあれば実時間に結ぶ。`raw.syscall` の許可表は変えない。これは `fs`・`console` と同じ作法（評価器は Rust の組み込み、ネイティブは `std.os.*` の Sigil 実装）。
- 案 B: 評価器の許可表にソケット系を足し、評価器でも `std.os.net` の Sigil のコードをそのまま動かす。実装が 1 つで済むが、`sockaddr` などの領域の検査・`accept4` の出力の検査を許可表に実装する必要があり、行の追加は ADR 0018 判断 2 のレビューの対象になる。信頼基盤の外の Rust の実装が 1 つ減る代わりに、許可表が広がる。
- 案 C: 評価器は `net.*` を持たず、ネイティブだけが持つ。評価器との突き合わせができないので、ADR 0015 の基準を外れる。採らない。

### 5-2. 突き合わせ（ADR 0015 の拡張）

ソケットのプログラムは外の相手を要するので、これまでの「同じ入力で、評価器とネイティブの出力を比べる」は使えない。次の方針にする。

- **相手を共通にする**: `tests/` の Rust のテストが、`std::net` のクライアントとして、評価器で動かしたプログラムと、ネイティブにビルドして動かしたプログラムの**両方に同じ入力のバイト列を送り**、受け取った応答のバイト列とタスクの順序に依らない性質（応答の集合、閉じられる接続の数）を比べる。待ち受けは `port` を 0 にして `local_port` で実際の番号を知らせる（標準出力に出す）。
- **決定的モード**（ネイティブのワーカー数 1）で、接続を 1 つずつ逐次に送れば、応答の順序も一致する。複数の接続の並行は、順序に依らない性質だけを比べる（ADR 0030 決定 2 の方針）。
- **評価器とネイティブの差を表に固定する**（ADR 0030 補足 D-3 の表に追加する）: 外の待ちの確かめ方（評価器は繰り返し、ネイティブは `epoll`）、読みの粒度（カーネルの分割に依る。テストは受け取ったバイト列の連結を比べる）、`task.roots` のルートの終了の順序。
- ネイティブだけの試験: `SIGPIPE` が起きないこと（閉じた接続への `write_all` が `Err(Closed)` になること）、fd の漏れ（接続を大量に作って閉じても、`/proc/self/fd` の数が増えないこと）、取り消された待ちの後の fd の再利用、同時の接続数の上限（`reserve`）。

## 決定 6: ADR 0020 との整合

- 上限の既定値の表（ADR 0020 決定 4）は HTTP の ADR（6-3g）で実装するが、本 ADR の API が受け持つ入口を次のとおり決める。
  - 同時の接続の数の上限（256）: `task.roots` の `limit` と `reserve` で守る（決定 4-1）。
  - `listen` の backlog: `net.listen` の引数（既定値 128 は HTTP の層が渡す）。
  - 1 回の読みの大きさ: `read` の `requires`（65536 以下）。HTTP の層は、見出しの大きさなどの合計の上限を自分で数える。
  - 時間の上限（見出しを読み終えるまで 10 秒など）: `task.timeout` で包む（決定 1-2）。時間の上限が正しく働くことは、決定 1-3 の実時間モードに依る。
- 起動の時に出す最悪のメモリ見積もりの式の `S`（タスクの大きさ）は、ADR 0030 の状態オブジェクトの大きさで決まる。値を入れるのは HTTP の ADR（ADR 0020 決定 4 の指示）。
- **待ち受けのアドレスは明示**: `net.listen` は `host` を必須の引数にし、既定の `0.0.0.0` を持たない。コンテナでは `"0.0.0.0"` と書くことになり、`sigil spec` の効果（`net.server`）と合わせて、レビューで見える。
- **セキュリティ関連の変更**: ネットワークに面するコード（`std.os.net`、`task.roots`、HTTP の解釈）は、ADR 0020 の G1・G2 の関門の対象で、AGENTS.md の「セキュリティ関連」に当たる（CODEOWNERS の承認が要る）。6-3e と HTTP の ADR は、人間のレビューを必須にする。
- 信頼基盤の追加: `std.os.net`・`io.wait_fd`・`task.roots` の `unchecked` の関数と原始操作の差分は、ADR 0018 判断 2 のレビューの対象（`scripts/trust-base-diff.sh` の検出）。

## 人間の判断が要る点

判断点 A は決定済み。判断点 B〜F は未承認で、状態は「提案」。

- **判断点 A: 時計（決定 1-3）**。**2026-11-10 08:24 JST に所有者が案 A（外の待ちがあるときだけ実時間に結ぶ）で決定済み**（Issue #375 のコメント）。
- **判断点 B: ソケットのエラーの型（決定 3-3）**。新しい `NetError`（腕 `AddrInUse`／`PermissionDenied`／`Closed`／`Other`）を推奨。代案は中身を見せない型＋`is_closed`。
- **判断点 C: 複数ルートの入口の形と、500 を返せる境界（決定 4-1・4-2）**。`task.roots`＋`reserve`＋`start` の範囲の形を推奨。代案は `net.serve` の高水準の組み込み。**異常停止したルートの接続の扱い**は、案 2（接続の所有をルートの外に置き、異常停止のときだけ `on_abort` に渡す）を推奨。代案は案 3（`finished` で親に返す）。案 1（親が所有し借用を渡す）は型の規則に合わず採らない。
- **判断点 D: 評価器でのソケットの実装（決定 5-1）**。案 A（Rust の `std::net` の組み込み。許可表は変えない）を推奨。案 B（許可表を広げて同じ Sigil のコードを動かす）は ADR 0018 判断 2 のレビューを要する。
- **判断点 E: ソケット API の最小の範囲（決定 3-2）**。`listen`・`local_port`・`accept`・`read`・`write_all`・`shutdown` を最小とすること。`net.client`、UDP、IPv6、DNS を含めないこと。
- **判断点 F: PR 分割と、要承認の PR（上の分割計画）**。6-3b（契約変更）と 6-3e・6-3g（セキュリティ関連）を要承認とする分け方。

## 影響

- **ADR 0004**: `net.server`・`clock`・`task.suspend` の意味は変えない。`net.server` の説明の「応答を待つ操作」を、本 ADR のソケットの操作が満たす、と読む（追記は 6-3e）。
- **ADR 0018**: 段階 6 の表の 6-3 を本 ADR の 6-3a〜6-3g で細分する（承認の後に反映）。
- **ADR 0026**: 決定 4 の「段階 6 で決める」を本 ADR の決定 4 が満たす。`task` の API の表に `task.roots`・`RootGroup`・`RootSlot` を足す（6-3d）。
- **ADR 0030**: 補足 C-2（結線）を決定 2 が、補足 D-2（複数ルートの入口・隔離・`LockBroken`）を決定 4 が満たす。補足 D-3 の表に、決定 5-2 の差を足す。判断点 3〜6 は変えない。
- **README**: ステータスに本 ADR を加える。

## 未決として残す点

- `net.client`（接続する側）、UDP、IPv6、名前解決。
- `TcpStream` の調整（`TCP_NODELAY`、keep-alive）と、相手のアドレスの取得（前段が付ける見出しを信じるかは ADR 0020 決定 4／ADR 6-4）。
- 実行可能待ち行列の公平性、I/O スレッドを複数にすること、ワーカー自身が `epoll_wait` を回す方式（ADR 0030 決定 3）。
- 有界チャネルの再検討（ADR 0026／0030 の未決）。
- `RootGroup` を範囲の形でなく、長寿命のオブジェクトにすること（破棄が中断できない制約との関係で、範囲の形を選んだ）。
- シグナルの扱い（`SIGPIPE` は `MSG_NOSIGNAL` で避けるだけで、一般の方針は ADR 0030 の未決のまま）。

## 決めないこと

- **ADR 0007 の条件 8**（中断をまたぐ借用の文言と実装の食い違い）の判断は、**別途所有者の判断待ち**。本 ADR は決めず、結論に依存もしない。ソケットの操作の `&TcpStream` を中断をまたいで持つ場面は、現行の実装の振る舞い（5-2d の状態機械の変換が借用を保つ）の範囲で使うだけである。
- **Issue #366**（`&Lock<Int>` を引数に持つ入口で SIGSEGV）は範囲外。`task.roots` の `g` の引数は持たない（`fn() -> Unit`）ので、この形には触れない。
- **ADR 0030 の判断点 3〜6** は未承認のまま。本 ADR は変えず、「承認済み」とも書かない。

## 根拠の限界

- 本 ADR は設計の提案であり、**実装も計測もしていない**。`x86-64` のシステムコールの番号、`SOCK_NONBLOCK` などのフラグ、`sockaddr_in` の配置は、Linux のマニュアルの知識に基づく。6-3e で実機の試験で確かめる（本 ADR の段階では照合していない）。`tests/raw_syscall_table.rs` は評価器の許可表のテストで、ネイティブの番号の根拠にはならない。
- 決定 1-3 の実時間モードは、`task.sleep` の観測を「fd を使うか」で分ける規則で、見落としがありうる。`epoll_wait` のタイムアウトの丸め（ミリ秒）と期限の精度は、6-3c で測る。
- 決定 4-2 の `on_abort` の形（接続の所有をルートの外に置く）は、評価器の `stop_root` が値を捨てる範囲から接続を除く変更を要し、ネイティブでも同じ除外が要る。除外した接続が漏れないことは、6-3d の試験で固定する。
- 決定 4-1 の `task.roots` の形（範囲の形、`reserve`／`start` の分離）は、HTTP のサーバーを実際に書く前の見込みである。6-3g で書いてみて合わなければ、本 ADR を改訂する。
- `std.os.net` の標準の列挙（`NetError`）が検査器の枠で表せるか、`RootSlot` の破棄で上限が返る仕組みが評価器・ネイティブの破棄の機構に載るかは、実装を調べるまで確定できない。
- 並列モードでの競合（複数のワーカーが同じ `TcpListener` を使わないこと、`Sendable` の検査が保証する範囲）は、型の保証が主な防御で、負荷試験は補助である（ADR 0030 の根拠の限界と同じ）。
