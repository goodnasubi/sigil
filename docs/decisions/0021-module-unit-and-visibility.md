# 0021: モジュールの単位と公開の範囲（ADR 0018 の PR 2-1）

- **状態**: 提案（承認待ち）。本 ADR は決定の案と推奨を示す。実装（PR 2-2）は承認の後に始める。依存の追加・CI の変更・権限の設定・データベースのスキーマには当たらない。所有者に確かめたい点は末尾の「人間の判断が要る点」に分けた。

## 背景

[ADR 0018](0018-p1-scope.md) の段階 2 の最初の PR として、DESIGN.md の 5 章が「M1 の前」としたまま未決だった **モジュールの単位と公開の範囲** を決める（パッケージの設定ファイルを持つかを含む）。P1 では HTTP サーバー・PostgreSQL の接続・暗号の基本部品を Sigil で書く。1 つのファイルや 1 つの名前空間では収まらず、標準ライブラリの Sigil への置き換え（段階 3）も、モジュールどうしの参照を前提にする。

### 現状（main `1914f1e`）

- 各ファイルの先頭に `module 名前` + `targets` + `trust` の宣言がちょうど 1 つある（[ADR 0008](0008-m0-notation.md) の決定 6）。ファイルの位置とモジュール名の対応は決めていない。
- モジュールどうしの参照（`import` に当たるもの）はない。`sigil check` と `run`・`build` は複数のファイルを受け取るが、宣言（名前・`targets`・`trust`）がすべて同じファイルだけを 1 つに合わせる（`exec::merge_sources`、食い違えば `ModuleMismatch`。[ADR 0014](0014-core-and-os-split.md) の決定 4）。
- 公開の範囲の区別はない。合わせたファイルの宣言は、すべて互いに見える。
- 標準ライブラリは `src/stdlib.rs` の表で、1 つの仮のモジュール `std.std` として常に見える。`std`・`std.*` は予約で、`--trust-base` に挙げても許されない（[ADR 0016](0016-trust-base-declaration.md) の決定 3）。
- 言語サーバー（[ADR 0019](0019-m6-machine-spec-and-language-server.md) の PR2）は、同じディレクトリで宣言が同じファイルを「組」として検査する。これは本 ADR までの仮の決め方で、変更のたびに組の全ファイルを検査し直す（規模の方針は ADR 2-1 で決めるとした）。
- `--trust-base` の許可の一覧は専用のファイルに置く（[ADR 0018](0018-p1-scope.md) の判断 1 の注記。設定ファイルを持つことになれば移すかを本 ADR で見直す）。

### 前提

- 書き手は AI、人間は仕様だけを読む（[ADR 0001](0001-vision-and-scope.md)）。仕様に、何を公開し何に依るかが現れること。
- 同じ意味の書き方を 1 つにする（[ADR 0002](0002-syntax-family.md) の規則 1）。
- 依存の追加は所有者の承認事項で、レジストリへの送信は P1 では行わない（ADR 0018 の判断 8）。

## 評価の観点

重要な順に並べる。

1. **仕様として読めるか**: 公開の範囲とモジュール間の依存が、`sigil spec` に現れること。
2. **AI が誤りなく書けるか**: ファイルとモジュールの対応、参照の書き方が 1 通りで、エラーの直し方が 1 つに決まること。
3. **検査の保証を弱めないか**: 出力先の検査（ADR 0004 の規則 5）、核が OS 層を参照しない検査（ADR 0014）、`trust base` の許可（ADR 0016）が、モジュールをまたいでも働くこと。
4. **実装量と、段階 3 以降で作り直さずに済むか**。

## 決定 1: モジュールの単位

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| A: 1 ファイル = 1 モジュール | ファイルの位置からモジュール名が決まる | 対応が 1 つに決まる。検査と言語サーバーの単位がファイルになり、組の仕組みが要らない | 大きなモジュールが 1 つのファイルになる |
| B: 1 ディレクトリ = 1 モジュール | ディレクトリ内のファイルを合わせる | 大きなモジュールを分けて書ける | 今の `merge_sources` と同じく、ファイルの位置から宣言がずれうる。変更のたびに全ファイルを検査し直す |
| C: 宣言が同じファイルを合わせる（今のまま） | | 変更なし | 位置と名前の対応がなく、`ModuleMismatch` の特例が残る。参照を足すと、どのファイルが組かの規則が増える |

**推奨: A**。

- ファイルの位置とモジュール名: ソースの根（決定 2）からの相対パスで、`/` を `.` に、拡張子 `.sigil` を除いたものがモジュール名である（例: `<根>/app/http/server.sigil` は `app.http.server`）。`module` の宣言の名前と食い違えばエラー（新しい `ModulePathMismatch`）。
- 大きなモジュールは、公開の範囲（決定 4）を使って複数のモジュールに分ける。ファイルを分けて 1 つのモジュールにする手段は持たない。
- `merge_sources` と `ModuleMismatch` は廃止する。核（`bare`）の検査を迂回させないために ADR 0014 の決定 4 が置いた「宣言がすべて同じ」という条件は、モジュールが 1 ファイルになるので不要になる（宣言は常にそのファイルの宣言だけで決まる）。

## 決定 2: ソースの根とパッケージの設定ファイル

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| P1: 設定ファイルを持たない | ソースの根は `--root <ディレクトリ>`（省略時は現在のディレクトリ）で与える | 依存の追加も新しい形式の解析も要らない。レジストリを使わない P1 の方針と合う | 根の指定を毎回書く（スクリプトに書く） |
| P2: 設定ファイルを持つ | `sigil.toml` など | 根・出力先・許可の一覧を 1 か所に置ける | TOML を解析するか自前の形式を作る必要がある（依存の追加は所有者の承認事項）。出力先と信頼基盤は ADR 0008 の決定 6 で宣言に置くと決めており、重複する |

**推奨: P1**（設定ファイルを持たない）。

- 出力先（`targets`）と信頼基盤（`trust`）は、ADR 0008 の決定 6 のとおりモジュールの宣言に残す。
- `--trust-base` の許可の一覧は専用のファイルのままにする（ADR 0018 の判断 1 と PR 3-0）。設定ファイルがないので、移す先もない。
- 外のパッケージへの依存は P1 では持たない（レジストリへの送信と同じく、P1 の範囲の外）。必要になったら、設定ファイルと合わせて新しい ADR で決める。

## 決定 3: モジュールどうしの参照

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| U1: 名前を 1 つずつ取り込む | `use app.http.server.handle;`（1 行に 1 つの名前。並びは辞書順。別名・ワイルドカード・再公開はなし） | 使う名前が先頭で分かる。書き方が 1 つ。仕様に依存が 1 行ずつ出る | 名前が増えると行が増える |
| U2: モジュールを取り込み、修飾して使う | `use app.http.server;` の後 `server.handle(x)` | 行が少ない | `Type.method(...)`・列挙型の変種（`Pair.Two(...)`）の書き方と衝突する。名前空間が増える |
| U3: 常に完全な修飾 | `app.http.server.handle(x)` | 取り込みの行がない | 式が長くなり、既存の `Type.method` との区別が難しい |

**推奨: U1**。

- `use` は `module` の宣言の直後に、辞書順に並べる。順序の違反・重複・未使用の `use` は構文エラーまたは検査のエラーにする（宣言の節と同じく、正規形の違反）。
- 取り込める名前は、相手のモジュールの `pub` の宣言だけ（決定 4）。型を取り込めば、その型のメソッド（`impl`）は同時に使える。
- 取り込んだ名前と自分のモジュールの宣言が同じ名前ならエラー。取り込みどうしの衝突もエラー（別名で逃がす手段は持たない。名前を変えるのは書き手の側）。
- 標準ライブラリの前置きは、段階 3 で標準ライブラリを Sigil のモジュールに替えるまで今のまま（`use` なしで見える）。替えた後に `use std.…` を要するかは、段階 3 の ADR で決める。
- モジュールの参照の輪（循環）はエラー（新しい `ModuleCycle`）。検査は依存の順に行い、輪がないので、各モジュールを 1 度だけ検査すればよい。

## 決定 4: 公開の範囲

- 宣言（`fn`・`struct`・`enum`・`type`・将来の `trait`）は既定で非公開（そのモジュールの中だけで見える）。`pub` を前に付けたものだけが他のモジュールから見える。
- `struct` の欄と `enum` の変種は、その型が `pub` なら公開される（欄ごとの公開の区別は P1 では持たない）。値の不変条件を守りたい型は、篩型（`type T = … where …`）と `T.check` で表す（その型の値の作り方は検査で守られる）。
- `impl` のメソッドは、`pub` を付けたものだけ公開される。
- 公開した関数のシグネチャが、非公開の型を名指しするとエラー（新しい `PrivateInPublic`）。仕様に出るシグネチャが、取り込めない型を指さないようにするため。
- `trust base` のモジュールの `unchecked` の関数（ADR 0016）は、`pub` かどうかによらず ADR 0016 の規則どおり前提の文を持つ。可視性は検査の規則を変えない。

## 決定 5: 検査の保証との関係

- **出力先**: モジュール M が N を取り込むには、M の `targets` が N の `targets` に含まれること（N が M の出力先のすべてで使えること）。含まれなければエラー（新しい `TargetMismatch`）。効果の検査（ADR 0004 の規則 5）は、取り込んだ関数の効果の宣言をそのまま使う。
- **核と OS 層**: ADR 0014 の `OsItemInCore` は、核のモジュールが OS 層の名前を指すときに働くので、取り込み経由でも同じく働く。利用者のモジュールを「核」と宣言する手段は ADR 0014 のままで、本 ADR は変えない。
- **信頼基盤**: `trust base` を宣言できるモジュールは、`--trust-base` の許可と `std.*` に限る（ADR 0016 の決定 3）。通常のモジュールが `trust base` のモジュールを取り込むことは許す（取り込む側の検査は弱まらない）。許可の確認は、取り込んだ各モジュールの宣言ごとに行う。
- **契約・所有権・借用**: 他のモジュールの関数は、シグネチャと 4 節だけを見て検査する（本体を見ない）。これは今の同じモジュール内の呼び出しの検査と同じ規則である。

## 決定 6: 仕様・言語サーバー・コマンドへの影響

- `sigil spec` は、モジュールの宣言の後に `use` の一覧を出し、各宣言に「公開」「非公開」を付ける。人間は依存と公開の範囲を、同じ出力で読める。非公開の宣言も出すのは、`unchecked` の前提の文のように、レビューが非公開の関数も対象にするため（ADR 0018 の判断 2）。
- 言語サーバーの「組」（ADR 0019 の PR2 の仮の決め方）は廃止する。1 ファイルを検査し、その `use` の先を依存の順に読む。変更のたびに全体を検査し直さず、変更したファイルと、それを取り込むファイルだけを検査し直す。
- `sigil check`・`run`・`build` は `--root` を受け取る。引数のファイルは根からの相対位置でモジュール名が決まる。`run` と `build` は入口のモジュールから `use` で辿れるモジュールだけを対象にする。
- 診断の位置は、ファイルごとの位置のままにする（ADR 0019 の「各ファイルの先頭に改行を足す」仕組みは、ファイルを合わせないので不要になる）。

## 決定 7: 実装の分け方（PR 2-2 以降）

| PR | 内容 |
|---|---|
| 2-2a | 構文: `use`・`pub`。`--root` とファイルとモジュール名の対応（`ModulePathMismatch`）。`sigil spec` の出力 |
| 2-2b | 名前の解決と検査: 取り込み・可視性・輪・`TargetMismatch`・`PrivateInPublic`。他のモジュールの関数をシグネチャで検査する |
| 2-2c | lowering・SIR の評価器・ネイティブ出力で、複数のモジュールを 1 つのプログラムにする。`merge_sources` と `ModuleMismatch` を廃止し、テストの補助を複数モジュールの形にする。言語サーバーの組を廃止する |

- 各 PR の完了条件に、誤りの注入の確かめ（ADR 0018 の決定 4 の運用）を含める: 可視性と輪の検査は、誤りを埋め込んだ版を作って落ちることを確かめ、期待値を決め打ちした事例を持つ。
- 既存のテストが使う `run_sources`（同じ宣言の複数ファイル）は、2-2c で複数モジュールの形に書き換える。書き換えで失う機能は PR に明記する。

## 却下した案

- **ディレクトリ = モジュール（B）**: 変更のたびに全ファイルを検査し直す規模の問題と、位置と宣言のずれが残る。
- **設定ファイル（P2）**: 依存の追加（所有者の承認事項）を伴いうる。ADR 0008 の決定 6 の宣言と重複する。P1 に必要な機能がない。
- **モジュールの取り込みと修飾（U2）・常に完全な修飾（U3）**: `Type.method` や変種の `Pair.Two` と見分けがつきにくく、AI の誤りが増える。

## 影響

- **ADR 0008**: 決定 6 の「モジュールの単位の ADR に引き継ぐ」を本 ADR で解決済みとする。
- **ADR 0014**: 決定 4 の `merge_sources` の条件は、PR 2-2c で不要になる。
- **ADR 0016**: 設定ファイルを持たないので、許可の一覧は専用のファイルのままにする。
- **ADR 0018**: PR 表の 2-1 を完了とし、2-2 を 2-2a・2-2b・2-2c に分ける。
- **ADR 0019**: PR2 の「組」の仮の決め方を、PR 2-2c で廃止する。
- **docs/DESIGN.md**: 5 章の「モジュールの単位と出力先の指定」の行を、本 ADR で改める。

## 人間の判断が要る点

本 ADR の範囲に、依存の追加・CI の変更・権限の設定・データベースのスキーマに当たる点はない。所有者に確かめたい点は次の 2 つで、承認の前に答えがほしい。

1. **パッケージの設定ファイルを持たない（P1）でよいか**。持つ場合は TOML などの解析に依存を足すか自前で書くかを決める必要があり、依存の追加は所有者の承認事項である。
2. **`use` を 1 つの名前ごと（U1）にしてよいか**。AI の書き間違いを減らすために書き方を 1 つにする案だが、行は増える。

## 未決の点

- 欄ごとの公開の区別と、中身を隠す型（不透明な型）は、P1 では持たない。必要になった段階（PostgreSQL の接続の型など）で、本 ADR を改める。
- 標準ライブラリを Sigil のモジュールに替えた後の `use std.…` の要否は、段階 3 の ADR で決める。
- 外のパッケージへの依存とバージョンの扱いは、P1 の範囲の外。
