# 0063: TLS 終端（sigil-shield-tls）

- **状態**: 提案
- **日付**: 2026-11-25（JST）
- **対象**: [Issue #749](https://github.com/goodnasubi/sigil/issues/749)、レーン E
- **仕様基準**: sigil の `main`、`a50e6ef2883fd0029f5c457c4961561dcc186202`
- **範囲**: ADR の起草のみ。実装リポジトリは `goodnasubi/sigil-shield-tls`（[ADR 0044](0044-p4-scope.md) 決定 4 のパターン）。本リポジトリのコンパイラ・標準ライブラリのコード変更は含めない。前提となる標準部品（決定 1）と sigix への追補（決定 5）は別の ADR・Issue で扱う。

## 背景

`sigil-shield-tls` は、平文 HTTP で待ち受ける Sigil 製サービスの前段に置く TLS 終端部品である。「小さいサービスを公開できる組み合わせ」（sigix ＋ sigil-db ＋ KV ＋ 認証 ＋ TLS 終端）の最後の欠けにあたる。

### 既に決まっていること

- sigix には TLS 終端を持たせず、専用の終端部品を前段に置く（所有者決定 2026-11-21、typesafe-ai 正式判定 B 案 0.95、confidence 0.92。[ADR 0056](0056-sigix-web-server.md) 前提 3、[ADR 0018](0018-p1-scope.md) 判断 5）。
- 前提の暗号部品は完了済み。[ADR 0058](0058-tls13-crypto-primitives.md) の全段が 2026-11-23 に完了し、X25519・AES-128/256-GCM・ChaCha20-Poly1305・HKDF-SHA-256/384・SHA-384 が標準ライブラリにある。
- ソケットは `TcpStream.shutdown`（半閉じ）・`peer_addr`・`local_addr` を持ち（[ADR 0031](0031-p1-first-wait-ops-and-socket-api.md)）、ファイルは `File::mode` で権限ビットを読める（[ADR 0049](0049-common-fs-boundary.md)）。名前解決（DNS）と Unix ドメインソケットはない。
- sigix は、信頼する接続元（既定はループバック）から渡された `X-Forwarded-For`・`X-Forwarded-Proto` だけを信頼し、それ以外は接続元で上書きする（ADR 0056 決定 6）。認証（[ADR 0060](0060-rune-auth.md)）は、接続元ごとのログイン抑制に `X-Forwarded-For` を使う。**前段が接続元を後段へ渡さないと、全利用者が終端部品の 1 つのアドレスに集約され、抑制が共有・無効化される。**
- 実装リポジトリの [`docs/nginx2root-lessons.md`](https://github.com/goodnasubi/sigil-shield-tls/blob/b0f7875/docs/nginx2root-lessons.md) が、nginx の TLS 周辺の欠陥から次の 4 要件を挙げている。本 ADR はこの 4 要件を必ず取り込む（CVE の内容そのものは本 ADR では独自に検証していない。要件だけを採る）。

| 要件 | 本 ADR での置き場所 |
|---|---|
| R1: 読み取りは必ず前進するか、タイムアウトで終わる | 決定 4.4 |
| R2: SNI の振り分け先と、証明書を検証する名前を一致させる | 決定 2.4・決定 3 |
| R3: ClientHello の長さと境界を厳密に検証する | 決定 4.2・4.3 |
| R4: PROXY protocol のパースも攻撃面として扱う | 決定 4.6・決定 5 |

### ADR 0058 が本 ADR に委ねたもの

| 委ねられたもの | 決め方 |

## 本 ADR で決めないこと

- 実装そのもの（ADR のマージ後に段ごとに進める）。
- sigix・認証・sigil-aegis-waf（WAF）の仕様。名前と、本 ADR が要る要求（決定 5）だけを出す。
- ACME の内蔵、TLS クライアント、HTTP/2・HTTP/3、Encrypted Client Hello、クライアント証明書、DTLS。
- 製品名（UI を持たない部品のため当面は不要）。
- **外部公開の承認。** 外部公開は [ADR 0020](0020-p1-security-addendum.md) 決定 3 の G3 で所有者が決める。本 ADR も各段の G2 も承認しない。

## 評価の観点

重要な順に並べる。

1. 秘密（秘密鍵・通信の鍵・平文）が漏れないこと。
2. 1 つの悪い入力や悪い接続でプロセスが止まらないこと。外から来る入力を解釈する玄関を小さく、厳密にすること。
3. 確かめ方が仕組みになっていること（テスト・ファジング・検査）。
4. 信頼基盤と依存を増やさないこと（ADR 0005、ADR 0020）。
5. 適合の限界を隠さず、明示して記録すること。

## 決定 1 — 終端の範囲と対応方式

`sigil-shield-tls` は、TCP の接続を受け、TLS 1.3 のサーバーとしてハンドシェイクと保護レコードの処理を行い、復号した平文を後段へ中継する。HTTP は解釈しない（決定 5）。

| 項目 | 採るもの | 採らないもの（理由） |
|---|---|---|
| 版 | TLS 1.3 のみ | TLS 1.2 以前（旧暗号と降格の攻撃面） |
| ハンドシェイク | 完全な 1-RTT。HelloRetryRequest を含む | 0-RTT・PSK・セッション再開・チケット（再送、セッション状態、名前を越えた再開の経路を作らない。再接続のたびに完全ハンドシェイクになる費用は、決定 4.5 の上限で受ける） |
| 暗号スイート | `TLS_CHACHA20_POLY1305_SHA256`・`TLS_AES_128_GCM_SHA256`・`TLS_AES_256_GCM_SHA384`（ADR 0058 の 3 種） | それ以外 |
| 鍵交換 | `x25519`（段 3）。`secp256r1`（P-256）は段 6 | P-384、ハイブリッド方式（標準部品がない。クライアントが提示しても、使える `x25519` があれば無視して進める） |
| サーバーの署名 | `ecdsa_secp256r1_sha256` のみ | RSA-PSS・RSA-PKCS1（大整数演算と鍵処理で信頼基盤が増える）、Ed25519（公開 Web PKI の証明書に使えない。起草時点の認識であり、公開前に再確認する）、P-384 |
| クライアント証明書 | 要求しない | 相互認証は範囲外 |
| ALPN | 提示があれば `http/1.1` だけを選ぶ。`http/1.1` を含まない提示は致命的アラート `no_application_protocol`。提示がなければ `http/1.1` として扱う | `h2`（sigix は HTTP/1.1 のみ）。ALPN を無視した別プロトコルの混入を防ぐ |
| OCSP ステープル・SCT の配布 | しない（証明書に埋め込まれた SCT をそのまま送るだけ） | OCSP 応答の取得に TLS クライアントが要る |

優先順位は、スイートは ChaCha20-Poly1305、AES-128-GCM、AES-256-GCM の順とする。標準ライブラリの AES は秘密を添字にする表引きを使わない定数時間の実装（ADR 0058 決定 3）のため、ソフトウェアでは ChaCha20 のほうが速い見込みである。段 2 の実測で AES が上回る場合に限り入れ替え、実測を記録する。

### 1.1 適合の限界（人間の判断が要る点）

[RFC 8446 §9.1](https://www.rfc-editor.org/rfc/rfc8446#section-9.1) は、準拠する実装に `rsa_pss_rsae_sha256`・`rsa_pkcs1_sha256`・`ecdsa_secp256r1_sha256` の署名と、`secp256r1` の鍵交換への対応を MUST としている。初期の `sigil-shield-tls` は、RSA 署名に対応せず、P-256 の鍵交換は段 6 まで持たない。したがって **RFC 8446 に完全に適合するとは主張しない**。README と検証記録に、TLS 1.3 の部分集合を実装していることと、この限界を明記する。

互換への影響は次のとおり。準拠するクライアントは `ecdsa_secp256r1_sha256` と `secp256r1` の両方に対応する MUST を負うため、サーバーが ECDSA P-256 の証明書と P-256 鍵交換を持てば、準拠クライアントとは必ず相互運用できる。段 6 まではクライアントが `x25519` を提示する場合だけ接続でき、FIPS 要件で `x25519` を除いたクライアントは接続できない。RSA の証明書しか持てない運用は取れない。

### 1.2 ハンドシェイクの規則

- ClientHello の `supported_versions` に `0x0304` がなければ、ServerHello を返さず致命的アラート `protocol_version` で終える。
- スイートは、サーバーの優先順の中でクライアントが提示した最初のものを選ぶ。共通がなければ `handshake_failure`。
- 鍵交換のグループは、クライアントの `supported_groups` に対応するもの（まず `x25519`）を選ぶ。その `key_share` がなければ、1 接続に 1 回だけ HelloRetryRequest を返す。2 つ目の ClientHello が、1 つ目と `key_share` 以外で食い違えば `illegal_parameter`。共通のグループがなければ `handshake_failure`。
- 署名は、`signature_algorithms` に `ecdsa_secp256r1_sha256` がなければ `handshake_failure`。
- `pre_shared_key`・`psk_key_exchange_modes`・`early_data` は、構造だけ検査して**受理しない**（完全ハンドシェイクを行う）。0-RTT の再送を許さないため、復号できない早期のレコードを読み飛ばす予算は 0 とし、受け取れば致命的アラートで終える。
- 互換モード（[RFC 8446 付録 D.4](https://www.rfc-editor.org/rfc/rfc8446#appendix-D.4)）のため、ClientHello の `legacy_session_id` をそのまま ServerHello に返し、ServerHello の直後に ChangeCipherSpec を 1 つ送る。クライアントからの ChangeCipherSpec は、ClientHello の後からクライアントの Finished の前までに 1 つだけ受理して捨てる。それ以外の位置・個数は `unexpected_message`。
- 未知のグループ・スイート・拡張・署名方式は無視する（Encrypted Client Hello の GREASE を含む。拒否しない）。拡張の重複と、既知の拡張の構造の誤りは拒否する（決定 4.3）。

### 1.3 鍵更新と nonce

- 方向別の 64 ビットのシーケンス番号を使い、nonce は [RFC 8446 §5.3](https://www.rfc-editor.org/rfc/rfc8446#section-5.3) の構成とする。シーケンス番号は 1 つの鍵ごとに 0 から数え、鍵更新で 0 に戻す。ADR 0058 の契約（同じ鍵で同じ nonce を生成しない）は、この方向別の番号が 1 つの鍵で単調に進むことで守る。
- 送信したレコード数が **2^23** に達する前に、`KeyUpdate(update_not_requested)` を送って送信鍵を更新する（[RFC 8446 §5.5](https://www.rfc-editor.org/rfc/rfc8446#section-5.5) は AES-GCM で約 2^24.5 レコードを目安としている。余裕を持たせる）。更新できないまま 2^23 を超える場合は、接続を終える。
- 受信した `KeyUpdate` は受理し、`update_requested` なら自分の送信鍵も更新して返す。受信する `KeyUpdate` は接続あたり **16 回**まで。超えれば `unexpected_message` で終える（応答の増幅と CPU 消費を抑える）。
- 平文の断片は 2^14 バイト以下、暗号文は 2^14 + 256 バイト以下。受信した内部平文が全ゼロ（種別を持たない）なら `unexpected_message`。認証に失敗したレコードは `bad_record_mac` で即座に接続を終え、読み続けない。
- ハンドシェイクの外のメッセージ（`NewSessionTicket`・`CertificateRequest`・クライアント側の再ハンドシェイク）は `unexpected_message`。

### 1.4 前提となる標準部品

次は `std.crypto` として、別の ADR（D2）と実装 PR で先に整える。定数時間の規則と検査は ADR 0020・ADR 0058 決定 3 に従う。

| 部品 | 用途 | 前提とする段 |
|---|---|---|
| ECDSA P-256 署名（SHA-256、[RFC 6979](https://www.rfc-editor.org/rfc/rfc6979) の決定的な nonce） | `CertificateVerify` | 段 3 |
| P-256 の ECDH（受け取る点の曲線上の検査を含む） | `secp256r1` の鍵交換 | 段 6 |

PEM・Base64・DER の読み取りと X.509 の読み取りは、`sigil-shield-tls` のモジュール（trust none）に置く。他の用途が現れた時点で、標準ライブラリへの移動を別の ADR で検討する。

## 決定 2 — 証明書の扱い

### 2.1 取得と更新

**ACME クライアントは内蔵しない。** ACME の内蔵には、TLS クライアント、証明書チェーンの検証、ルート証明書の管理、HTTP-01/DNS-01 の応答が先に要り、信頼基盤と攻撃面が大きく増える。証明書は、外部のクライアント（運用者が選ぶ ACME クライアントなど）が PEM ファイルとして更新する。ACME を Sigil で内蔵する場合は、別の ADR で決める。

### 2.2 保管

- 秘密鍵は PEM のファイルで、PKCS#8（`BEGIN PRIVATE KEY`）と SEC1（`BEGIN EC PRIVATE KEY`）の P-256 の鍵だけを受け付ける。暗号化された鍵（パスフレーズ付き）・RSA・Ed25519・他の曲線は、起動時または読み込み時に理由を示して拒否する。パスフレーズを同じホストに置いても鍵の保護にならず、扱いが増えるだけのため。
- 鍵のファイルは、`File::mode` が返す権限ビットのうち `0o077`（グループ・その他の権限）が 1 つでも立っていれば拒否する。読み取りは `follow_symlinks(false)` で開いた `Dir` 起点とし、シンボリックリンクを追わない（ADR 0049）。
- 鍵は読み込み後すぐ `Secret` に入れ、ログ・エラー・診断の出力に載せない。証明書のチェーンは公開の値として扱う。
- 鍵は環境変数や KV には置かない。

### 2.3 読み込み時の検査（フェイルクローズ）

証明書のチェーン（リーフ → 中間）と鍵を 1 組として読み、次の全てを満たす場合だけ受理する。**サーバーは、リーフの署名やチェーンの署名を検証しない**（検証するのはクライアントである）。読み取りだけを行い、署名値は読み飛ばす。

| 検査 | 内容 |
|---|---|
| 構造 | DER の長さ・入れ子が厳密。バージョン v3。チェーンは 8 枚以下、各証明書は 16 KiB 以下、PEM のファイルは 64 KiB 以下。リーフ以外は、直前の証明書の発行者名と、自分の主体者名が DER の完全一致でつながる |
| 公開鍵 | リーフの SPKI が P-256 の `id-ecPublicKey`（非圧縮の点）。秘密鍵から導いた公開鍵と一致する |
| 有効期間 | 現在時刻が `notBefore` 以上 `notAfter` 以下。時計を取得できない場合は受理しない |
| 名前 | `subjectAltName` の `dNSName` の一覧を読み、設定した各名前を全て覆う（2.4）。`commonName` は見ない。IP アドレスの SAN は扱わない |

起動時に 1 組も受理できなければ、起動を拒否する（待ち受けを始めない）。期限が 14 日以内に迫った証明書は、ポーリングのたびに警告を記録する。

### 2.4 SNI による振り分けと名前の一致（R2）

- 証明書は、**設定した名前の集合**に結び付ける。名前は ASCII のラベルだけ（国際化ドメイン名は A-label の `xn--` で書く）。完全一致と、先頭の 1 ラベルだけが `*` の名前（`*.example.com`。ちょうど 1 ラベルに一致し、`example.com` 自身には一致しない。部分的な `*` は不可）を許す。名前は 1 つの証明書にだけ結び付ける。重複した名前の設定は起動時に拒否する。
- ClientHello の `server_name` は、ホスト名を 1 つだけ含む。重複する種別や複数の名前は `illegal_parameter`。名前は ASCII の小文字に正規化して照合する。末尾の `.`、IP アドレスのリテラル、使えない文字、253 バイトを超える長さ、63 バイトを超えるラベルは、**一致しない名前と同じ**扱いにする。
- **一致しない名前・名前の無い接続は、致命的アラート `unrecognized_name` で拒否する。** 暗黙の既定の証明書は置かない。SNI の無い接続を受けたい場合だけ、設定で名前（`default_server_name`）を明示する。名前の不一致の理由（構文の誤りと未登録）は、外へ区別して返さない。
- 証明書の選択に使った**正規化済みの名前**を、そのまま接続情報（決定 5）の `AUTHORITY` に載せる。選択と報告で別の解釈をしない（R2）。
- 振り分けはこの証明書の選択だけで行う。後段の振り分けは、終端部品では行わない（決定 3）。

### 2.5 再読み込み

- 証明書とその鍵のファイルを、起動時と、一定間隔（`reload_interval`、既定 300 秒、範囲 30〜86400 秒）で読み直す。シグナルによる再読み込みの仕組みがないため、時間による確認とする。
- 読み直しでは、**1 回の読み取りで得たバイト列**を検査し（読み取りと検査の間にファイルが変わる競合を避ける）、2.3 を全て満たす 1 組だけを新しい設定として差し替える。差し替えは、証明書と鍵を 1 組にまとめて一度に行う。新しい接続だけが新しい設定を使い、確立済みの接続は影響を受けない。
- 検査に失敗した更新（鍵と証明書の更新の途中で食い違う場合を含む）は、旧設定を維持し、理由を記録して次の確認で再試行する。起動後の失敗でプロセスを止めない。
- 現在の証明書が期限切れになっても接続は受ける（クライアントが拒否し、原因が記録から見える）。期限切れは error として記録する。

## 決定 3 — 平文区間の制約

終端部品と後段の間は平文のため、次のように縛る。

- 後段（上流）は、設定で**数値の IP アドレスとポート**を 1 つ指定する（DNS は使わない。ADR 0031）。1 つの待ち受けに上流は 1 つ。**名前による後段の振り分けは終端部品では行わない**。仮想ホストの振り分けは後段（sigix）が Host で行う（R2: 証明書の選択と後段の振り分けで、名前の解釈を分けない）。
- 上流は、既定でループバック（`127.0.0.1`・`::1`）だけを許す。非ループバックは `allow_non_loopback_upstream = true` の明示がある場合だけ許し、起動時に検査して、許可のない違反は起動を拒否する。非ループバックの許可は、公開前の G3 で所有者へ提示する（人間の判断が要る点）。
- 待ち受けのアドレスは設定で必須とし、既定値を置かない。443 番への割り当ては、コンテナのポート公開などの運用で行う。
- 終端部品は、1 つの TLS 接続に対して新しい上流接続を 1 つ開き、接続を共有・再利用しない。他の接続の要求と混ざる経路を作らない。
- **ローカルの他のプロセス**は、上流の待ち受けに直接接続し、接続情報のヘッダーを偽装できる。ホストを共有する他者を信頼できない環境では使わない。これは本構成の限界として G3 で所有者へ提示する。

## 決定 4 — 入力パースの安全性

玄関は、TCP から最初に読むバイト列（TLS レコード）と、その中の ClientHello である。ここは認証前で、どんなバイト列も来る。

### 4.1 原則

- 認証前に解釈するのは、TLS レコード層、ClientHello、アラート、`KeyUpdate`、Finished だけとする。HTTP と PROXY protocol は解釈しない。
- 全ての長さの前置きは、残りの長さと上限に照らして読む前に検査し、読み終えた位置が長さ通りであることを検査する。範囲外・余り・不足は、確保や演算の前に拒否する。
- 解釈の誤りは致命的アラートと接続の終了にする。続行（fail-open）や、後段への転送はしない。

### 4.2 レコード層

- レコードの先頭 5 バイト（種別・旧版・長さ）を読み、種別が既知（`change_cipher_spec`・`alert`・`handshake`・`application_data`）で、旧版が `0x0301` または `0x0303` で、長さが 2^14 以下（暗号化後は 2^14 + 256 以下）でなければ、それ以上読まずに終える。
- ハンドシェイクメッセージは複数のレコードに分けて届いてよい。再構成は ClientHello 1 つにつき**最大 16 KiB**（16,384 バイト）、**最大 8 レコード**までとし、超えれば `decode_error`（長さの誤り）または `illegal_parameter`（その他）で終える。再構成の途中に他の種別のレコードが割り込んだら、`unexpected_message`。
- **長さ 0 のハンドシェイクのレコードは拒否する**（[RFC 8446 §5.1](https://www.rfc-editor.org/rfc/rfc8446#section-5.1)）。暗号化後の長さ 0 の `application_data` は許すが、連続して **16 個**を超えれば `unexpected_message` で終える（読み取りが前進しない状態を作らない）。
- ハンドシェイクが終わる前に読むバイト総量は **32 KiB** までとし、超えれば終える。

### 4.3 ClientHello の規則

| 項目 | 規則（違反時のアラート） |
|---|---|
| メッセージ | 種別 `client_hello`。3 バイトの長さが実長と一致し、全てを消費して余りがない（`decode_error`） |
| `legacy_version` | `0x0303`（`illegal_parameter`） |
| `random` | 32 バイト |
| `legacy_session_id` | 0〜32 バイト（`illegal_parameter`） |
| `cipher_suites` | 長さは偶数で 2〜128 バイト（64 個以下）。未知のものは読み飛ばす（`decode_error`） |
| `legacy_compression_methods` | ちょうど 1 バイトで値は 0（`illegal_parameter`） |
| 拡張の一覧 | 全体の長さが残りと一致する。拡張は **64 個以下**。**同じ種別の重複は拒否**（`illegal_parameter`）。`pre_shared_key` があれば最後（`illegal_parameter`）。未知の拡張は長さだけ検査して読み飛ばす |
| `supported_versions` | 必須。リストは奇数でなく、偶数バイトで 254 バイト以下。`0x0304` がなければ `protocol_version` |
| `supported_groups` | 偶数バイト。64 個以下。未知のグループは読み飛ばす |
| `key_share` | 全体の長さと各項目の長さが一致する。**8 項目以下**。グループの重複は拒否（`illegal_parameter`）。`x25519` は 32 バイトちょうど。`secp256r1` は 65 バイトで先頭が `0x04` かつ曲線上の点（`illegal_parameter`） |
| `signature_algorithms` | 偶数バイト。64 個以下 |
| `server_name` | 決定 2.4 の規則。リストの長さと名前の長さが一致する |
| `application_layer_protocol_negotiation` | 各名前は 1〜255 バイト。合計 1 KiB 以下 |

### 4.4 読み取りの前進と期限（R1）

- 接続の読み取りは、全て「**残り期限つきの読み取り**」だけで行う。期限は、ハンドシェイク全体で**10 秒**（範囲 1〜60）とし、各読み取りの期限は残りの時間で打ち切る。1 バイトも前進しない（読み取りが 0 バイトで返る・期限が来る）なら終える。
- 各ループは、**入力を 1 バイト以上消費するか、上限に達して終える**ことを不変条件とする。消費せずに繰り返す経路を、コードに置かない。
- ハンドシェイクの後は、アイドル期限（**60 秒**、範囲 5〜3600）と書き込みの期限（**30 秒**、範囲 1〜300）で終える。相手が読まない場合に、書き込みのバッファが無限にたまることはない（各方向のバッファは 2 レコード分、32 KiB 以下で、満ちたら読み取りを止め、期限まで待つ）。
- 上流の接続の確立は、期限（**3 秒**、範囲 1〜30）で終える。

### 4.5 資源の上限

上限は設定で変えられるが、**範囲の外・無制限の値は受け付けず、起動を拒否する**（ADR 0020 決定 4）。テストは各行について、直下・一致・超過の境界を確かめる。

| 項目 | 既定 | 範囲 | 超過時 |
|---|---|---|---|
| 同時接続数 | 1024 | 1〜65536 | 新しい接続を即座に閉じる |
| ハンドシェイク中の同時接続数 | 64 | 1〜1024 | 新しい接続を即座に閉じる |
| 接続元（IPv4 は /32、IPv6 は /64）ごとの同時接続数 | 32 | 1〜1024 | 新しい接続を即座に閉じる |
| 接続元ごとのハンドシェイク中の接続数 | 4 | 1〜64 | 新しい接続を即座に閉じる |
| 鍵交換と署名を同時に計算する数 | 2 | 1〜64 | 順番を待つ（待ちはハンドシェイクの期限で打ち切る） |
| ClientHello の大きさ | 16 KiB | 固定 | 終える |
| 拡張の数・スイートの数・`key_share` の項目数 | 64・64・8 | 固定 | 終える |
| 受信する `KeyUpdate` | 16 回 | 固定 | 終える |
| 証明書のチェーン・ファイル・名前の数 | 8 枚・64 KiB・名前 256 個、SAN 100 個 | 固定 | 読み込みを拒否 |

起動時に、同時接続数 × 1 接続あたりの最大使用量（バッファ 64 KiB 程度）から最悪のメモリ使用量を見積もり、上限（既定 256 MiB）を超える組み合わせの設定は拒否する（ADR 0020 決定 4 と同じ考え方）。

ハンドシェイクは CPU の費用が支配的である。ADR 0058 の実測では、X25519 のスカラー倍算はネイティブで 1 回 20〜30 ms で、1 回のハンドシェイクで 2 回要る。これに ECDSA P-256 の署名が加わるため、**ハンドシェイクは 1 回あたり百ミリ秒の桁の CPU を使う見込み**で、1 コアあたり毎秒 10 回前後が目安になる（P-256 は未実装のため、段 3・段 7 で実測し記録する）。上の「同時に計算する数」と、接続元ごとの上限は、この費用による枯渇への対策であり、公開前の G3 で実測を所有者へ提示する。

### 4.6 PROXY protocol の範囲（R4）

- 終端部品は、**PROXY protocol を受け付けない**。クライアント側の最初のバイトは、常に TLS レコードとして解釈する（ClientHello の前に別の形式を判別しない）。前段にレイヤー 4 の中継を置く構成は、本 ADR の対象外とする。
- 後段へは、PROXY protocol **v2 の送信だけ**を行う（決定 5）。受け取る側のパースは、受け取る側の攻撃面として、同じ要件（R4）を課す（決定 5 の追補の要求）。

### 4.7 確かめ方

- ファジングの対象を追加する（ADR 0020 決定 2）: ClientHello の解析、レコード層の読み取りと再構成、PEM・DER・X.509 の読み取り、設定の読み込み。各段の G2 で短い実行を、G3 で 1 時間以上の長い実行を行う。
- 各行の規則と上限を、負の例（長さの過不足、重複、範囲外、全ゼロ、0 長レコードの連続、分割された ClientHello の境界）で試験する。
- 秘密を扱う関数は、ADR 0020 決定 1 と ADR 0058 決定 3 の検査（`sigil test --ct` の登録を含む）の対象に登録する。

## 決定 5 — 後段との接続形式

### 5.1 形式（typesafe-ai 正式判定済み）

後段へ渡す平文は **HTTP のまま**とし、接続の先頭に **PROXY protocol v2 のヘッダーを 1 回だけ**付ける。終端部品は HTTP を解釈せず、TLS と中継だけを担う。HTTP を解釈して `X-Forwarded-*` を各要求に挿入する方式は採らない。要求の境界を厳密に解析する必要が生じ、要求スマグリングの攻撃面と信頼基盤が終端部品に加わるため（ADR 0056 の「脅威と対策」3）。

ヘッダーは、[PROXY protocol v2 の仕様](https://www.haproxy.org/download/3.0/doc/proxy-protocol.txt)に従い、次の内容とする。

| 項目 | 内容 |
|---|---|
| コマンド | `PROXY` |
| アドレス | クライアントの接続元（`peer_addr`）と、受け付けた先（`local_addr`）。TCP over IPv4 または IPv6 |
| TLV `AUTHORITY` | 決定 2.4 の正規化済みの SNI の名前。SNI がなければ付けない |
| TLV `SSL` | TLS を使った接続であること。サブ TLV で TLS の版（`TLSv1.3`）。クライアント証明書はない |

TLV を含むヘッダー全体は、1 KiB 以下とする。

### 5.2 後段（受け取る側）への要求

sigix の ADR 0056 は、本 ADR の時点で PROXY protocol v2 の受信を決めていない。**sigix への追補（別 Issue・別 ADR）が先に要る**。追補が満たす要求は次のとおり。

1. PROXY v2 を受信するのは、専用の待ち受け設定に限り、信頼する接続元（既定はループバックの許可リスト）からの接続だけとする。ヘッダーが無い・不正・許可リスト外からの接続は、HTTP として解釈せずに閉じる。信頼しない接続元から PROXY を受けても、受理しない（偽装の防止）。
2. パースは、決定 4.1 の原則（長さの検査・上限・余りの拒否）に従い、不正な入力でプロセスが落ちないことをファジングで確かめる（R4）。
3. HTTP/1.1 の `Host` が、`AUTHORITY`（SNI）と一致しない要求は、`421 Misdirected Request` で拒否する（証明書を検証した名前と、要求の宛先の名前を一致させる。R2）。
4. `X-Forwarded-For` は、PROXY のクライアントの接続元から作る。`X-Forwarded-Proto` は、`SSL` TLV から `https` とする。これにより、sigix の背後の認証が接続元ごとのログイン抑制に使うアドレスが、終端部品のアドレスに潰れない。

### 5.3 障害時の振る舞い

- 上流の接続は、ハンドシェイクが完了してから開く（ハンドシェイクだけの接続が上流の資源を使わない）。完了前に届いた平文は、上限（32 KiB）までバッファする。
- 上流に接続できない・期限を超えた場合は、**固定の `502 Bad Gateway` の応答**（`Connection: close`、固定の本文）を暗号化して送り、`close_notify` で終える。応答に外部の入力を含めない。
- 上流が、応答の途中で異常に終了（リセット・期限）した場合は、`close_notify` を送らず、致命的アラート `internal_error` で終える。クライアントが応答の切り詰めを完了と取り違えないため。上流が正常に終わった場合は、残りを送り切ってから `close_notify` で終える。
- クライアントが `close_notify` を送った場合は、上流への書き込みを `shutdown` で閉じ、上流の応答の終わりまでアイドル期限の範囲で待つ。`close_notify` なしの TCP の切断は、切り詰めとして扱い、上流を閉じる。
- ログには、接続元・正規化済みの SNI の名前（文字を `[a-z0-9._*-]` に制限し、長さを切る。ログへの注入を防ぐ）・結果の分類だけを出す。鍵・平文・ClientHello の中身・通信の鍵は出さない。

実装は `goodnasubi/sigil-shield-tls` に置く。各段は PR 単位で進め、各段が ADR 0020 の G2（決定 1 の検査、決定 2 の対象の追加と短い実行、決定 4 の上限のテスト）を満たしてから次へ進む。段 1 を暗号より先に作るのは、外から最初に入力を受ける玄関を先に固めるためである。

| 段 | 内容 | 完了条件 | レーン |

| 0（前提） | `std.crypto` に ECDSA P-256 署名（決定 1.4）を加える。P-256 の ECDH は段 6 の前に加える | 別 ADR・別 PR。RFC 6979 の公開ベクタ、定数時間の検査 | D2 |
| 1 | 入口の解析（レコード層、ClientHello、アラート、上限、4.2〜4.5）。暗号は呼ばない | 4.3 の全ての行と 4.2 の負の例の試験、ファジング対象の追加と短い実行、決定 4.5 の上限の試験、「消費せずに繰り返さない」の試験 | E |
| 2 | 鍵スケジュールと保護レコード（`HKDF-Expand-Label`、レコード、nonce、鍵更新、3 スイート） | [RFC 8448](https://www.rfc-editor.org/rfc/rfc8448) のサーバー側の値との一致、鍵更新の境界（2^23・16 回）、AEAD の失敗、スイートの優先順の実測の記録 | E |

| 5 | 中継（待ち受け、接続ごとのタスク、4.5 の上限、タイムアウト、上流への接続、PROXY v2 の付与、終了の扱い、ログ） | 決定 3・5.1・5.3 の試験（ループバック検査、502、`internal_error` と `close_notify`、半閉じ）、各上限と期限の境界、ログに秘密が出ないこと | E |
| 6 | P-256 の鍵交換を加える（標準部品の ECDH が前提） | `key_share` の曲線上の検査、HelloRetryRequest を含む試験、RFC 8448 の対応する値 | E |
| 7 | 相互運用・負荷・公開前の記録 | `curl`・`openssl s_client` などの既存の TLS クライアントを外部のプロセスとして使う相互運用の試験（実装には取り込まない）、ハンドシェイクの毎秒の実測、`docs/pre-publish-record.md`（G2 の記録と、G3 で所有者へ提示する項目）。**G2 は外部公開を承認しない** | E |

## 脅威と対策（ADR 0020 G1）

終端部品は外部のネットワークに直接面する唯一の部品であり、認証の前に外からのバイト列を最初に受ける。

| 区分 | 何から何を守るか | 守る決定 |
|---|---|---|
| 入力 | 壊れた・巨大・遅い ClientHello とレコードで、プロセスが落ちる・止まる・資源を使い切る。長さの食い違いによる読み過ぎ・読み不足（R3） | 決定 4.1〜4.5、ファジング（4.7） |
| 認証 | サーバーの身元。SNI の振り分けと、検証される名前のずれ（R2）。名前の無い接続への暗黙の証明書。後段の振り分けと証明書の選択のずれ。PROXY ヘッダーの偽装（R4） | 決定 2.4・3・5.2 |
| 秘密 | 秘密鍵・通信の鍵・平文が、ログ・エラー・メモリ・ファイルの権限で漏れる | 決定 2.2・5.3、`Secret`、定数時間の検査（4.7） |
| 資源 | 同時接続・ハンドシェイクの CPU・低速接続による枯渇。読み取りが前進しない状態（R1） | 決定 4.4・4.5 |

そのほかの脅威:

- **降格**: TLS 1.2 以下を提示しない・受理しない（決定 1）。
- **再送（0-RTT）**: 早期データを受理しない。セッション再開もない（決定 1.2）。
- **別プロトコルの混入**: ALPN を `http/1.1` に限る（決定 1）。
- **要求の宛先のずれ（ドメインフロンティング）**: 後段が `Host` と SNI を照合する（決定 5.2）。
- **要求スマグリング**: 終端部品は HTTP を解釈せず、接続ごとに上流の接続を分ける（決定 3・5.1）。
- **切り詰め**: 上流の異常終了は、`close_notify` ではなく致命的アラートで終える（決定 5.3）。
- **ローカルの他のプロセス**: 上流の待ち受けと PROXY ヘッダーを偽装できる。信頼できない環境では使わない（決定 3）。
- **時計**: 証明書の有効期間の検査に使う。時計を取得できなければ、新しい証明書を受理しない（決定 2.3）。巻き戻りの監視は運用と G3 で扱う。
- **タイミング**: 秘密を扱う関数は定数時間の規則を適用する（決定 1.4・4.7）。RSA を使わないため、PKCS#1 の padding oracle の系統はない。

## ADR 0020 の公開関門との関係

- **G1**: 本 ADR の「脅威と対策」が、入力・認証・秘密・資源の 4 つを置く。
- **G2**: 各段（決定 6）が、決定 1 の検査・決定 2 の対象の追加と短い実行・決定 4 の上限のテストを含めて完了する。**G2 は外部公開を承認しない。**
- **G3**: 終端部品は外部公開の入口そのものであり、段 7 の後、最初に外部公開する前に、実装者と別のセッションがレビューする。所有者が報告を読んで決める。ADR 0020 の確認項目に加え、次を確認する: 相互運用の試験の結果、ファジング（全対象で 1 時間以上）、上限の試験、0-RTT・再開が無効であること、ハンドシェイクの CPU 費用の実測、鍵の権限の検査。
- G3 で所有者へ提示する項目: 適合の限界（1.1）、ハンドシェイクの CPU 費用と枯渇への耐性（4.5）、証明書の更新運用と時計、平文区間の非ループバックの許可とローカルのプロセスによる偽装（決定 3）、再開がないことによる接続の費用、外部公開そのものの可否。

## 前提となる別の作業（本 ADR の範囲外）

| 作業 | 内容 | 期限 |
|---|---|---|
| `std.crypto` の追加 ADR | ECDSA P-256 署名（段 0）、P-256 の ECDH | 段 3、段 6 の前 |
| sigix への追補 | PROXY v2 の受信、`Host` と SNI の照合、`X-Forwarded-Proto`（決定 5.2） | 段 5 の相互運用の前 |
| 認証（sigil-rune-auth） | 変更なし。sigix が `X-Forwarded-For` を渡す経路が保たれることを、結合の試験で確かめる | 段 7 |

## 影響

小さいサービスを公開する組み合わせに、TLS 終端が加わる。終端部品は、HTTP を解釈せず、証明書を持たず ACME も持たない小さな信頼基盤になる。その代わりに、証明書の更新を外部に頼り、RSA と P-256 の鍵交換を初期に持たず、再開と 0-RTT を持たない。これらは、適合の限界と費用として記録し、G3 で所有者へ提示する。

## 人間の判断が要る点

次を、所有者が確認する。判断の手順（理念 → typesafe-ai 正式判定）で決めた採用案が覆る場合は、段 3 より前に伝える。

1. **適合の限界（決定 1.1）**: RSA 署名を持たず、RFC 8446 に完全には適合しない。正式判定の確率は採用案 0.55、RSA 署名まで含む案 0.40 で、**confidence は 0.33 と低い**。採用案は後から RSA を足す余地を残している（段を分けているため）が、足すには定数時間の大整数演算を標準部品に加える大きな作業が要る。
2. 本 ADR は、外部公開を承認しない（G3 は所有者の判断）。
3. 平文区間の非ループバックの許可、ホストを共有する環境でのローカルのプロセスによる偽装（決定 3）。
4. 証明書の更新を、外部の ACME クライアントの運用に頼ること。ACME の内蔵は別の ADR で決める。
5. この ADR は、外部公開の関門（ADR 0020）に関わる判断を含む。レビューは別系統のエージェントが行い、所有者の確認を求める。
