# 0005: 長期目標と段階計画

- **状態**: 承認（2026-10-22。長期目標はリポジトリ所有者の決定。段階の順序と既存 ADR の改訂は、所有者の委任を受けて Claude が決定）

## 背景

[ADR 0001](0001-vision-and-scope.md) では、Java・React・Node.js を置き換える言語を目標とした。
所有者から、さらに先の最終目標が示された。本 ADR はそれを記録し、既存の決定との食い違いを解消し、実現の順序を定める。

## 決定 1: 長期目標（所有者の決定）

Sigil で、次のものを置き換えられるようにする。

| # | 置き換える対象 | 種類 |
|---|---|---|
| G1 | Next.js（フロントエンドとサーバーを一体で書く Web フレームワーク） | フレームワーク |
| G2 | Python（スクリプト・データ処理などの用途） | 言語の使われ方 |
| G3 | データベース | アプリケーション |
| G4 | Git（ソースを管理するリポジトリ管理） | アプリケーション |
| G5 | サービスを Docker コンテナで動く形にしてリリースする仕組み | 開発・配布の道具 |
| G6 | コンテナを管理する仕組み（コンテナの実行・配置の管理） | 基盤ソフトウェア |
| G7 | OS（VMware ESXi 上の仮想マシンで動く OS を含む） | 基盤ソフトウェア |
| G8 | IDE（統合開発環境） | 開発の道具 |
| G9 | Web ブラウザ | アプリケーション |
| G10 | Spring（Java のサーバーアプリケーション用フレームワーク） | フレームワーク |

ADR 0001 の目標（Java・React・Node.js の置き換え）はそのまま有効であり、G1〜G10 はその先に位置づける。

G8 の IDE は、人間がコードを読まない前提（ADR 0001）に合わせ、既存の IDE とは役割を変える。人間に対しては **仕様をレビューする場**（仕様の表示・仕様の差分・検証結果の確認）、AI に対しては **コードを書くための道具**（検査結果・補完・定義の参照などを機械が使える形で返す言語サーバー）を提供する。

## 決定 2: 段階計画（Claude の決定）

依存関係の順に、次の段階で進める。各段階は、それだけで使える成果物を出すことを条件とする（全体が完成するまで何も使えない状態を避けるため）。

| 段階 | 内容 | 主な成果物 | 前提 |
|---|---|---|---|
| P0 | 言語の核 | コンパイラ（ネイティブ出力）、型・所有権・効果・契約の検査、仕様の抽出と表示、標準ライブラリの最小部分、言語サーバー（AI と IDE が使う検査・補完の窓口） | なし |
| P1 | サーバーと Docker コンテナでのリリース（G5）、Spring の置き換え（G10） | HTTP サーバーのライブラリ、サーバーアプリケーションのフレームワーク（ルーティング・設定・入力検証・データベース接続・認証）、Docker で動くコンテナイメージを作る道具 | P0 |
| P2 | Web フルスタック（Java・React・Node.js・G1）と IDE（G8） | WebAssembly / JavaScript 出力、UI の記述モデル、フロントとサーバーをまとめて書くフレームワーク、IDE（Sigil で書く Web アプリとして実装） | P1 |
| P3 | Python の置き換え（G2）と Python 連携 | すぐ実行できる実行形態（スクリプト実行・対話実行）、Python からの呼び出し | P0 |
| P4 | データベース（G3）・リポジトリ管理（G4） | Sigil で書いたアプリケーションとして実装 | P1 |
| P5 | コンテナ管理（G6） | コンテナの実行・配置を管理する仕組み | P1、P4 |
| P6 | OS（G7） | OS 本体（ハードウェアの上で直接動く）、ESXi 上の仮想マシンで動く形 | P0、ADR 0003 の改訂（下記） |
| P7 | ブラウザ（G9） | HTML・CSS の表示、JavaScript の実行、Sigil の WebAssembly 出力の実行 | P1、P2（P3〜P6 と並行して進められる） |

順序の理由:

- P0 はすべての前提である。
- P1 を早くに置くのは、「サービスを Docker コンテナで動かしてリリースする」が、他のすべての段階の成果物を実際に動かす手段になるためである。
- IDE は P2 の Web フルスタックで作る最初の大きなアプリケーションとする。ブラウザで動く IDE にすれば、Docker コンテナで配布でき（P1）、どの環境からも使える。その中心機能の仕様の表示と言語サーバーは P0 で作るので、P2 では画面を付けることが主な作業になる。
- Spring の置き換え（G10）は、サーバーを書く仕組みそのものなので P1 に置く。Spring の中心機能の一つである依存性の注入（部品の差し替え）は、Sigil では効果の宣言とテスト用の実行環境での差し替え（ADR 0004）が一部を担うため、同じ仕組みをそのまま作るのではなく、Sigil の決定に合う形で設計する。データベース接続は、既存のデータベース（PostgreSQL など）の通信方式を Sigil で実装して行う（既存のライブラリは使わない）。
- P7 のブラウザは、既存の Web を表示するために HTML・CSS の解釈と配置、JavaScript の実行環境まで作る必要があり、規模が大きい。P2 で UI の記述モデルと WebAssembly / JavaScript 出力を作った後に始める。OS には依存しないので、P3〜P6 と並行して進められる。P6 の OS ができれば、その上で動く画面（GUI）の中心になる。
- P4 のデータベースとリポジトリ管理は、言語の機能ではなく **Sigil で書くアプリケーション** である。大規模な実用プログラムを Sigil で書くことで、ADR 0002〜0004 の決定（構文・所有権・効果）を検証する場にもなる。
- P6 の OS は、言語として最も厳しい要件（ハードウェアの直接操作）を持つため最後に置く。ただし、P0 の段階から「実行環境なしでも動くコードを出力できる」設計にしておく（下記の影響を参照）。

## 決定 3: 既存の決定の改訂（Claude の決定）

### ADR 0003 の改訂: 検査を外す仕組み（unsafe）を許す範囲

OS（G7）は、メモリの特定番地を直接読み書きする、割り込みを扱う、ページ表を書き換えるなど、所有権の検査では安全性を示せない操作を必要とする。ADR 0003 は検査を外す仕組みを「標準ライブラリ・ランタイム・処理系が生成するコード」だけに許しており、このままでは OS を書けない。

そこで、許す範囲を次のように改める。

- 検査を外す仕組みを使ってよいのは **信頼基盤**（trusted base）に属するモジュールだけとする。信頼基盤は、標準ライブラリ・ランタイム・処理系が生成するコード・**プラットフォーム層**（OS のハードウェア抽象層やデバイスドライバのうち、ハードウェアを直接操作する最小部分）からなる。
- 信頼基盤のモジュールは、モジュールの宣言で信頼基盤であることを明示する。通常のモジュールからは検査を外す仕組みを使えない点は変わらない。
  - 注記（[ADR 0016](0016-trust-base-declaration.md)）: 宣言だけでは足りず、処理系の外の許可（`--trust-base <モジュール名>`。ADR 0016 の決定 3）も要る。検査を外す仕組みの中身は原始操作 `raw.*` であり、安全の前提は `unchecked "前提"` の節と原始操作の表に書く（決定 1・2）。
- 検査を外した各箇所には、安全である前提を契約（`requires` / `ensures`）として書くことを必須とする。人間はコードを読まないので、この前提が仕様として人間に示される唯一の情報になる。
- 信頼基盤は最小に保つ。将来は形式検証（seL4 のように、実装が仕様を満たすことを数学的に証明する方法）の対象にすることを目指す。

### ADR 0004 の改訂: 効果のカテゴリ

ADR 0004 では、利用者が効果のカテゴリを追加できないとした。OS とコンテナ管理には、ハードウェアの操作・割り込み・メモリ配置の操作・コンテナの操作など、既存のカテゴリ（本 ADR の時点で 13 個。ADR 0007 で `task.*` の 3 個を加えて 16 個）にない効果がある。

- 利用者による追加はできないままとする。
- 標準ライブラリとプラットフォーム層は、段階 P5・P6 で必要になったカテゴリを追加できる。追加は ADR に記録してから行う（読み手が知るべき語彙を管理するため）。

## 影響

- **Docker コンテナ**: P1 では、Sigil で書いたサービスを Docker で実行できるコンテナイメージとして出力する。Docker のイメージ形式は業界標準の OCI 形式と互換なので、OCI 形式で出力すれば Docker 以外のコンテナ実行環境でも動く。Docker が動くのは主に Linux なので、P1 のネイティブ出力は Linux（x86-64）を最初の対象にする。

- **出力先の追加**: ADR 0001 の出力先（ネイティブ・WebAssembly・JavaScript）に、**実行環境なしのネイティブ出力**（OS の上ではなくハードウェアの上で直接動くコード）を加える。対象は x86-64 を先にし、ESXi 上の仮想マシン（多くは x86-64）で動かすことを最初の目標とする。ESXi の仮想ハードウェア（準仮想化のネットワーク・ストレージ装置など）用のドライバが必要になる。
- **標準ライブラリの分割**: 標準ライブラリを、実行環境なしでも使える核の部分（OS に依存しない部分。メモリの確保は使う）と、OS の機能を使う部分に分ける（Rust の `core` / `std` に相当）。この分割は P0 から設計に入れる。
  - **改訂（[ADR 0014](0014-core-and-os-split.md) 決定 2）**: 当初の「核はメモリ確保に依存しない部分」を、「OS に依存しない部分（確保は使う）」に改めた。確保に依存しない最小部分（Rust の `core` と `alloc` の区別）は、必要になる P6 の ADR で分ける。
- **Python の置き換えと連携**: ADR 0001 の「Python から呼び出せる」は、置き換えまでの移行手段として位置づける。Python の置き換えには、コンパイルを意識せずにすぐ実行できる形態（スクリプト実行・対話実行）が必要になる。
- **リポジトリの分け方**: このリポジトリ（`sigil`）は言語と標準ライブラリを扱う。P4 以降のアプリケーション（データベース・リポジトリ管理・コンテナ管理・OS）は、それぞれ別のリポジトリで開発することを想定する。
- **ADR 0001 の非目標**: 「Sigil から既存言語のライブラリを使うこと」は引き続き当面は後回しとする。置き換えの方針は、既存の部品を使うことではなく Sigil で作り直すことである。

## 規模についての注記

G1〜G10 の置き換え対象は、それぞれが長年にわたり大規模に開発されてきたソフトウェアである（例: Linux、Git、PostgreSQL、Kubernetes、Visual Studio Code、Chromium、Spring）。段階ごとに使える成果物を出す方針は、この規模でも途中の成果が無駄にならないようにするためである。各段階の範囲（最初はどの機能まで置き換えるか）は、その段階に入るときに ADR で決める。
