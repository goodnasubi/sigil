# 0062: OS カーネル向け効果カテゴリ（アドレス空間操作・割り込み制御・機器 I/O）

- **状態**: 提案（Issue #744 起草、レーン E。正式判定は未実施・問いを末尾に記録）。実装・マージの承認を意味しない。
- **日付**: 2026-11-24（JST）
- **対象**: [Issue #744](https://github.com/goodnasubi/sigil/issues/744)、[ADR 0054](0054-p6-os.md) 決定 5、[ADR 0004](0004-effects.md)、[ADR 0016](0016-trust-base-declaration.md)

---

## 背景

[ADR 0005](0005-long-term-goals.md) の P6（OS 本体）および [ADR 0054](0054-p6-os.md)（P6 の OS 本体）では、ESXi VM 上の最小カーネル（P6-2）から実機（P6-4）に至る OS カーネルを Sigil で記述する方針を定めている。

ADR 0054 決定 5 では次のように定められている:
> 追加候補は、機器 I/O、割り込み制御、アドレス空間操作とする。型付き契約が必要になった段で、カテゴリ名、対象、権限を表す型、宣言と推論の規則、否定例と検証方法を個別の ADR に記録し、承認後に標準ライブラリまたはプラットフォーム層へ追加する。ADR 0004・0005 に従い、利用者によるカテゴリ追加は禁止する。
> 機器操作を許す場合は P6 用の明示した出力プロファイルと能力の境界に閉じる。ADR 0028 の一般の `bare` で使える効果の条件を維持する。機器操作を既存の `state` や `effects none` に割り当てることは許さない。各段の実装は必要な効果の ADR を前提とする。

現行の `src/effects.rs` において、`bare`（実行環境なし）で許されている効果は `state`（共有所有の型を通したメモリ書き換え）と `task.suspend`（協調点としての yield。ADR 0028）のみであり、CPU アーキテクチャやハードウェアに直接作用する効果カテゴリは存在しない。

P6-2（ESXi の最小カーネル）の着手には、ページ管理（アドレス空間操作）および割り込みハンドラの初期化・制御が不可欠である。これらを司る低レベル原始操作を `RAW_OPS`（ADR 0016）に登録するにあたり、前提となる効果カテゴリを本 ADR で確定させる必要がある。

---

## 選択肢

### 1. 効果カテゴリの語彙体系と階層性

- **案 A: フラットな個別カテゴリ名（`mmu`, `interrupt`, `io`）**
  - 利点: 名前が短く、既存の `console`, `clock`, `state` などと同様にシンプル。
  - 欠点: ハードウェア・アーキテクチャ特権操作であることが名前空間から分かりにくく、将来のユーザー空間抽象や論理的 I/O との語彙の衝突が起きやすい。上位カテゴリによる一括指定（畳み込み）ができない。
- **案 B: ハードウェア階層カテゴリ名（`hw.mmu`, `hw.interrupt`, `hw.io`）**
  - 利点: ADR 0004 の階層規則（`fs.read`, `fs.write`, `net.client` 等と同様）に整合し、ハードウェア操作であることが一目で判別できる。上位カテゴリ `hw` を指定することで、低レベルドライバ等のシグネチャで下位効果を包括して表現できる。
  - 欠点: 階層の深さが 1 段増える。
- **案 C: 単一の `hardware`（または `hw`）カテゴリへの集約**
  - 利点: 効果の語彙が増えない。
  - 欠点: メモリ保護の変更、割り込みマスク、ポートアクセスといった根本的に危険性と性質の異なる操作が同一カテゴリに混淆し、人間が `sigil spec` をレビューする際に「関数がハードウェアに対して具体的に何をするか」を判別できなくなる（ADR 0054 正式判定において 90% の確率で否定された選択肢）。

### 2. 機器 I/O（`hw.io`）を本 ADR に含めるか否か

- **案 A: 今回はアドレス空間操作と割り込み制御のみに絞り、機器 I/O は P6-3（最小機器）で別途起草する**
  - 利点: P6-2 直近の最小差分に絞れる。
  - 欠点: P6-2（最小カーネル）の段階でも、割り込みコントローラ（APIC 等）の初期化・EOI 送出や、早期ブートデバッグのためのシリアル出力（UART ポート I/O や MMIO）が必要となり、カテゴリ未定義で実装が立ち往生する。またハードウェア効果体系の全体整合性が分断される。
- **案 B: アドレス空間操作・割り込み制御と同時に機器 I/O も含めて定義する**
  - 利点: OS カーネルの基幹を成す 3 大低レイヤハードウェア操作を一貫した体系の下で定義でき、P6-2 のカーネル初期化・ブート出力から P6-3 の仮想デバイス入出力まで後戻りなくスムーズに進められる。
  - 欠点: 起草時の検討範囲が広がる。

### 3. 出力対象（`Targets`）と文脈の制約方式

- **案 A: 既存の `bare` 全般で無条件に許可する**
  - 利点: 効果対象の定義が単純。
  - 欠点: ADR 0028 の一般則（「bare を含んでよいのは、実行環境なしでも意味が定義でき、値も権限も環境とやり取りしない効果に限る」）に抵触し、OS 以外の一般的な `targets bare` モジュール（組み込みアルゴリズムや暗号ライブラリ等）に特権操作が露出する恐れがある。
- **案 B: 出力対象を `bare` かつ P6 出力プロファイル選択時のみに限定し、信頼基盤（`trust base`）かつ明示的な能力型を介した文脈に厳格に束縛する**
  - 利点: 一般の `server` や `browser` への漏洩を防ぐだけでなく、P6 以外の通常 `bare` モジュールへの露出も防ぎ、ADR 0054 決定 5（「機器操作を許す場合は P6 用の明示した出力プロファイルと能力の境界に閉じる」）の方針を厳密に遵守できる。
  - 欠点: `Targets` や検査系に `BARE_ONLY` および P6 プロファイルの検査条件を導入する必要がある。

---

## 決定

### 決定 1 — 効果カテゴリの命名と意味

ハードウェア・CPU 特権操作を表すカテゴリとして、**案 B（階層カテゴリ）** を採用し、以下の 3 つのカテゴリを新設する:

| カテゴリ | 意味 | 含まれる主な操作 |
|---|---|---|
| `hw.mmu` | アドレス空間・仮想記憶の操作 | ページテーブルの作成・更新・切り替え（CR3 レジスタ変更など）、TLB フラッシュ（`invlpg` など）、メモリ保護属性の設定 |
| `hw.interrupt` | 割り込み状態・割り込みコントローラの制御 | 割り込みの有効化／無効化（`cli`/`sti`）、割り込みベクタ・IDT の設定、割り込みマスク、EOI（End of Interrupt）の送信 |
| `hw.io` | 機器との低レベル直接入出力 | ポート I/O（x86 の `in`/`out` 命令）、メモリマップド I/O（MMIO）レジスタの読み書き |

- **階層の包含規則（ADR 0004 規則 1 に準拠）**:
  - `hw` は上位カテゴリであり、`hw.mmu`、`hw.interrupt`、`hw.io` のすべてを包含する。
  - 完全一致規則（ADR 0004 規則 3）に基づき、`src/check/effects.rs` では宣言した `hw` が `EffectTable::atoms()` により 3 つの葉（`hw.mmu`、`hw.interrupt`、`hw.io`）に展開される。そのため、関数の本体から 3 種すべてが推論される場合にのみ `hw` に畳んで `effects hw` と宣言できる（一部しか推論されない場合は、推論されなかった葉が過剰宣言 `EffectExtra` として拒否される。ただし ADR 0016 決定 4 の `raw_delegated` により宣言に委ねる原始操作を呼ぶ関数では、宣言が推論より多くてよい例外が適用される）。
  - 特定の操作のみを行う関数（例: 割り込みを禁止する関数）は、不要な権限の露出を避け完全一致規則を満たすためにも、`effects hw.interrupt` のように最下位のカテゴリを明記することを原則とする。

### 決定 2 — 機器 I/O（`hw.io`）を本 ADR に含める判断

**機器 I/O（`hw.io`）は、本 ADR においてアドレス空間操作・割り込み制御と同時に定義に含める（案 B を採用）。**

- **判断の理由**:
  1. **P6-2（最小カーネル）における不可欠性**: P6-2 では ESXi VM 上で最小カーネルを起動し割り込みとページ管理を初期化するが、割り込みコントローラ（Local APIC / IOAPIC）のレジスタ操作は MMIO またはポート I/O で行われる。また、起動初期の診断・エラー報告に用いられるシリアルポート（COM1）や VGA バッファへの書き込みもポート I/O / MMIO である。したがって、機器 I/O を除外すると P6-2 自体の実装が成立しない。
  2. **ハードウェア操作の境界の整合性**: アドレス空間（MMU）、割り込み（Interrupt）、機器入出力（I/O）は、ノイマン型コンピュータにおける特権ハードウェア操作の不可分な 3 要素である。これらを同一の体系（`hw.*`）の下で統一的に設計することで、語彙のばらつきや将来の二度手間を防止する。

### 決定 3 — 許可される文脈と信頼基盤（`trust base`）との関係

ハードウェア効果は、実行時にシステムの整合性・安全性を破壊しうる最も特権的な作用であるため、以下の多層防御により文脈を制限する:

1. **直接の発生源は信頼基盤の原始操作（`raw.*`）のみとする**:
   - `hw.mmu`, `hw.interrupt`, `hw.io` を引き起こす最小の命令群は、すべて `src/stdlib.rs` の `RAW_OPS` 表（ADR 0016）に原始操作として登録される。
   - ADR 0016 に従い、原始操作を直接呼び出せるのは **`trust base` を宣言し、かつ関数の契約節に `unchecked "前提の文"` を明記した関数** のみに限定される。
   - 一般のモジュール（`trust none`）が勝手に `raw.*` を呼び出してこれらの効果を発生させることは、コンパイラによって拒絶される（`UncheckedOutsideTrustBase` / `RawOutsideUnchecked`）。
2. **通常モジュールへの公開は型付きの安全な抽象（Safe Abstraction）を介する**:
   - プラットフォーム層（OS カーネルの信頼基盤モジュール）は、原始操作を安全にカプセル化した API（例: ページ確保器、割り込みガード型、デバイスドライバ用チャネルなど）を外部に提供する。
   - 通常のモジュールがそれらの API を呼び出す場合、効果の一致検査（ADR 0004）により、そのモジュールの関数シグネチャにも `effects hw.*`（または特定のサブカテゴリ）の宣言が強制される。これにより、どの通常モジュールがハードウェア作用に依存しているかが `sigil spec` 上で完全に可視化される。
3. **既存効果への偽装・隠蔽の禁止（ADR 0054 決定 5 の遵守）**:
   - MMIO やページテーブル操作がメモリ書き換えを伴うからといって、既存の `effects state` に割り当てたり、副作用を過小評価して `effects none` とすることは厳格に禁止する。
   - すべてのハードウェア直接作用は、必ず `hw.*` 体系の下で追跡されなければならない。

### 決定 4 — 検査系での扱いと出力対象制約

1. **出力対象（`Targets`）と P6 プロファイルの制約**:
   - `hw.*` カテゴリの有効な出力対象は **`bare` かつ P6 出力プロファイルが選択されたビルドのみ** とする。
   - `src/effects.rs` の `Targets` に `BARE_ONLY`（`bare: true, server: false, browser: false`）を新設し、`hw.*` の各行に設定する。モジュールの宣言が `targets server` や `targets browser` を含む場合、`hw.*` 効果を宣言または推論した関数が含まれていると、対象不一致エラー（`TargetMismatch`）としてコンパイルを拒絶する。
   - 加えて、ADR 0054 決定 5（「機器操作を許す場合は P6 用の明示した出力プロファイルと能力の境界に閉じる」）に基づき、**`hw.*` を許可するのは P6 出力プロファイルが選択されたビルドに限り、P6 プロファイル以外ではたとえ `targets bare` であっても `hw.*` の宣言および推論を拒絶する**。
   - **検査の実現方法**: 本 ADR は設計のみであり実装コードの変更は含まないため、検査の実現方法（`Targets` への項目追加か、型検査・効果検査時の別途のプロファイル検査か等）は後続の実装段で決定する。
   - **否定例**:
     - 非 P6 プロファイルの `targets bare` モジュール（組み込みアルゴリズム、暗号ライブラリなど）で `fn foo() -> () effects hw.mmu` を宣言、または内部で `hw.*` 原始操作を呼び出した場合、P6 プロファイルが選択されていないためコンパイルエラーとして拒絶される。
     - `targets server` または `targets browser` のモジュールで `effects hw.io` 等を使用した場合、`TargetMismatch` エラーとして拒絶される。
2. **効果表の登録と完全一致検査（ADR 0004 規則 3）**:
   - `EffectTable::standard()` への登録は、葉カテゴリである **`hw.mmu`、`hw.interrupt`、`hw.io` の 3 つのみ** に限定する（親の `hw` は登録しない）。
   - 親の `hw` は、既存の `EffectTable::valid()` の階層解決ロジック（表に名前自体が無くても下位カテゴリが 2 つ以上存在すれば有効とする仕様）により自動的に許可されるため、登録が葉のみであっても `effects hw` と書くことができる。
   - 逆に親の `hw` を表に登録してしまうと、`EffectTable::atoms("hw")` に `hw` 自身が含まれてしまい、3 種すべてのハードウェア操作を呼び出す `effects hw` 関数の完全一致検査において過剰宣言（`EffectExtra`）として誤って拒絶される。
   - 葉のみを登録することで、`atoms("hw")` は `{hw.mmu, hw.interrupt, hw.io}` の 3 つの葉集合となり、`effects hw` と書いた関数の完全一致検査はこれら葉の集合として正しく照合される。
   - 他の効果カテゴリと同様、関数の本体から推論された効果の集合とシグネチャの宣言は完全に一致しなければならない（余分も不足もエラー）。
3. **効果の順序（ADR 0022 決定 2）**:
   - 下位カテゴリ（例: `hw.mmu`）は上位カテゴリ（`hw`）に覆われる（`hw.mmu ⊑ hw`）。トレイト実装等においてはこの順序関係に基づいて適合性を検査する。

### 決定 5 — 人間向け仕様表示（`sigil spec`）

人間はコードを読まず仕様だけをレビューする原則（ADR 0001）に基づき、`sigil spec` では各カテゴリを次の日本語名で表示する:

| カテゴリ | `sigil spec` での表示名 |
|---|---|
| `hw` | ハードウェア直接操作 |
| `hw.mmu` | アドレス空間操作（仮想記憶・ページ表） |
| `hw.interrupt` | 割り込み制御（割り込み禁止・許可・ハンドラ管理） |
| `hw.io` | 機器入出力（ポート I/O・MMIO） |

仕様の差分を見るだけで、AI がハードウェア操作の種類や権限を増やしたことが即座に人間に伝わるようにする。

## 影響

- **標準ライブラリ・コンパイラ（`src/effects.rs`）**:
  - `Targets::BARE_ONLY` の追加。
  - `EffectTable::standard()` に葉カテゴリ `hw.mmu`, `hw.interrupt`, `hw.io` の登録（親の `hw` は登録せず、`valid()` の下位カテゴリ検査と `atoms()` の葉展開に委ねる）。
- **後続の実装（P6-2 先行段・次段）**:
  - 本 ADR の承認後、P6-2 に必要な具体的な原始操作（CR3 操作、ページ無効化、割り込みフラグ操作、ポート I/O 等）を `src/stdlib.rs` の `RAW_OPS` に登録する Issue・PR を起票できる。
- **OS リポジトリ（`sigil-os`）**:
  - ESXi 向け最小カーネルの起動コードおよびプラットフォーム層において、型安全かつ効果が明示された形で特権コードを記述可能になる。

## 人間の判断が要る点

- 本 ADR は効果カテゴリの設計のみであり、実装コード（`src/effects.rs` や `src/stdlib.rs`）の変更は含んでいない。
- 正式判定は未実施であり、末尾の問いの結果や所有者レビューで異論があれば改訂する。
