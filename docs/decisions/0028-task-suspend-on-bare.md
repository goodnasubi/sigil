# 0028: bare における `task.suspend` の許可（`task.yield` の協調点）

- **状態**: 承認（2026-11-06。所有者が判定をクマ（muse）へ委任し、判定を採用して正式化と実装を承認した）
- **日付**: 2026-11-06
- **対象**: 効果の対象（targets）検査、`std.crypto`、ADR 0024 決定 2 の扱い

---

## 背景

ADR 0024 決定 2 は、PBKDF2 の反復ブロック処理において **1024 反復ごとに `task.yield` を呼び出す**と定めた。理由は、PBKDF2 の計算（10,000〜100,000 回の反復）が単一スレッド上で数十ミリ秒〜数百ミリ秒を消費しうるため、イベントループや同一スレッドの他タスクをブロックしないよう協調的に譲る、というものだった。`task.yield` は引数を取らないため秘密情報漏洩規則 R4 に抵触せず、呼び出し周期と反復回数は公開の値であるためタイミング漏洩の原因にもならない、という確認も同 ADR にある。

暗号シリーズの実装（6-1d、PR #290）で、この決定がそのままでは実装できないことが判明した。

- `std.crypto` のモジュール対象は **bare・server・browser の 3 つ**を含む（組み込みを含む全対象で暗号を使えることが前提）。
- 一方、効果 `task.suspend` の対象は **HOSTED（server・browser のみ、bare 不可）** である。効果の対象表（`src/effects.rs`）では、bare で使える効果は `state` だけだった。
- 関数が宣言・推論した効果はモジュールの対象すべてで使えなければならないため、対象照合で検査が落ち、`std.crypto` の中では `task.yield` を書けなかった。

このため PR #290 は ADR 0024 決定 2 から **逸脱し、`task.yield` なしで出荷**された。逸脱は PR とマージ後の報告に記録済みで、bare での扱いは言語設計の判断事項として残された。本 ADR はその判断である。

衝突は 2 つの層からなる。

1. **機械的な層**: 効果ごとの対象表（言語全体に効く）とモジュールごとの対象（標準ライブラリの宣言）の組み合わせでは、対象の広いモジュールは対象の狭い効果を一切使えない。今回の暗号に限らず、bare を含むモジュールが長時間処理を持つたびに再発しうる構造である。
2. **意味の層**: bare は「実行環境なし」であり、スケジューラが存在しない。譲る相手のいない環境で「中断して譲る」ことに何の意味を持たせるかは、機械的な可否とは別に決める必要がある。

---

## 決定

**効果 `task.suspend` の対象に bare を含める。**

- 広げるのは `task.suspend` のみとする。`task.spawn` と `task.share` は HOSTED のまま変えない（生成や共有は bare では劣化のしようがなく、意味を持たないため）。
- bare での `task.yield` の意味は「協調点」とする。スケジューラが存在しない実行では no-op であり、将来スケジューラを持つ bare 向け実行基盤（OS 対象を含む）が現れた場合は、実際に譲る協調点として解釈してよい。
- 関数は従来どおり効果 `task.suspend` を宣言する。仕様（`sigil spec`）には中断しうることが従来どおり露出するので、「黙って劣化する」のは実行の意味だけであり、仕様の正直さは損なわれない。

### 前例への歯止め（一般則）

効果カテゴリが bare を含んでよいのは、**実行環境なしでも意味が定義でき、値も権限も環境とやり取りしない効果に限る**。本決定時点でこれに該当するのは `state`（既存）と `task.suspend`（本決定）のみである。新しい効果を bare へ広げる場合は、この条件を満たすことを ADR で示すこと。

---

## 理由

1. **影響範囲が構造的に閉じている。** `task.suspend` を広げても、bare で新たに使えるようになる標準関数は実質 `task.yield` だけである。他の中断系の部品は、本当に実行環境が要る効果と組になっている（例: `sleep` は `clock` を伴うため、`clock` が HOSTED である限り bare では今までどおり検査で落ちる）。表の 1 行を広げても、環境依存の部品が bare へ漏れることはない。
2. **劣化できる効果とできない効果の間に、原則的な線が引ける。** `task.yield` は値を返さず、権限（ケイパビリティ）も与えない「譲る合図」でしかないため、環境なしでは no-op への劣化が定義できる。対して `clock`・`random`・`fs`・`net` は環境と値や権限をやり取りする効果であり、bare では偽装も劣化もできない。この区別があるため、本決定は場当たりの例外ではなく上記の一般則として書ける。権限を与えない以上、ADR 0027 のケイパビリティ原則とも衝突しない。
3. **関数単位の targets 制限（選択肢 2）は、現時点で 1 関数のために言語仕様を大きくしすぎる。** 一般性こそあるが、対象を絞りたい関数の実例は `pbkdf2_sha256` だけであり、「モジュールが対象を持つ」単純な模型を二層化する対価に見合わない。加えて選択肢 2 では bare で PBKDF2 自体が使えなくなるが、組み込みでのパスワードハッシュは現実の用途であり、機能の喪失は重い。却下ではなく保留とし、対象を絞りたい関数の 2 つ目の実例が現れた時点で改めて ADR で検討する。
4. **yield なしの正式容認（選択肢 3）は、承認済みの設計判断を実装都合で覆すことになる。** ADR 0024 決定 2 の狙い（長時間処理の協調をライブラリ側で保証し、呼び出し側に委ねない）は ADR 0027 決定 3（危険なデフォルトの排除）とも一致する判断であり、効果の対象表という実装寄りの都合で捨てるべきではない。hosted のサーバーランタイム（P1）が来てから直すと、`std.crypto` の仕様と振る舞いの変更が後負けになる。
5. **将来の方向と前方互換である。** 組み込み OS を対象にする方針（2026-11-03）の先では、bare 上に Sigil 自身のスケジューラが載りうる。そのとき協調点は実意味を持ち、本決定の no-op 解釈はそのまま「協調点の予約」として活きる。

---

## 帰結

- ADR 0024 決定 2 がそのまま実装可能になり、PR #290 の逸脱は後続の実装で解消される。
- `sha256` など他の長時間処理への波及: `Sha256` は `update` の単位で呼び出し側が処理を刻めるため、内部の協調点は不要という線引きを採る。単一の呼び出しで長時間を占有する関数だけが、内部に協調点を持つ対象になる。
