## 背景

- [ADR 0007](0007-concurrency-model.md) が並行処理のモデル（中断を効果として扱う構造化並行処理）を決め、[ADR 0018](0018-p1-scope.md) の決定 3 が P1 を段階に分けた。段階 4（P1-a）で、評価器に単一スレッドの実行割り当て（決定的な FIFO、仮想の時計、要求の隔離）を入れ、意味の基準を固定した（[ADR 0026](0026-p1a-concurrency.md)、ADR 0007 決定 6 の「P1-a の列の完了の記録」）。
- 段階 3（[ADR 0025](0025-runtime-replacement.md)）で、ネイティブ出力から Rust の暫定ランタイムと glibc がなくなった。出力は `cc -nostdlib -static -no-pie` でリンクされ、`_start`・システムコール・確保器・文字列・一覧・`console`・`fs`・`env` を Sigil と生成コードが持つ（3-7c・3-7d）。
- 段階 5（P1-b）は、この上に並行処理をネイティブで実現する。ADR 0018 の PR 5-1 の行は、本 ADR で決める範囲を次の 5 つとしている: 状態機械の変換、実行の割り当て、`epoll`、スレッドの作成、原子的な操作の原始操作。実装は PR 5-2 で、ADR 0007 決定 6 の表の P1-b の列（条件 8・9・10）を満たす。
- ネイティブ出力の現状（`main` `81ad269`）:
  - `task.yield` は何もしない（[ADR 0028](0028-task-suspend-on-bare.md)）。`task.scope`・`spawn`・`join`・チャネル・`Lock`・`Atomic` などの並行の操作は、すべて「ネイティブ出力未対応」で止まる（`src/codegen/func/call.rs`）。
  - 生成コードと標準ライブラリは、単一スレッドを前提にしている（ADR 0025 補足 A-5。確保器は排他を持たない）。複数の OS スレッドにする PR は、この前提の見直しを必須とする、と A-5 が定めている。
  - `raw.syscall` の評価器の許可表は 9 個で、`futex`・`clone`・`epoll_*` などは含まない（補足 A-3。行の追加は ADR 0018 判断 2 のレビューを要する）。
  - 原始操作の表（`RAW_OPS`）は 15 行で、原子的な操作を持たない（ADR 0018 の表が「原子的な操作（P1-b）は、ADR 5-1 で行を足す」としている）。

本 ADR は **設計の提案**であり、実装は含まない。決める点には推奨を付け、所有者の確認が要る点は「判断点」としてまとめる。

## 評価の観点

重要な順に並べる。

1. **データ競合の排除（必須）**: 型と所有権の検査だけでデータ競合が起こらないという ADR 0007 の保証を、実際の複数スレッドの上で保つこと。信頼基盤（検査を外した箇所）が、その保証を壊さないこと。
2. **評価器との意味の一致**: ネイティブの結果が評価器の結果と一致すること（ADR 0015 の突き合わせ）。非決定な並列実行でも、順序に依らない性質は一致すること。
3. **信頼基盤を最小に保つこと**（ADR 0005・0016）: 原始操作の追加、機械語のバイト列、`unchecked` の関数を、必要な分だけにとどめる。
4. **出力に既存言語のコードを含めないこと**（ADR 0005・0018 判断 7）: glibc も Rust のランタイムも持ち込まない。
5. **AI が誤りなく書けるか**: 規則が少なく、メモリ順序のような誤りやすい概念を表に出さないこと。
6. **多数の接続を少ないスレッドで扱えること**（ADR 0007 観点 5）: 段階 6 の HTTP サーバーが成り立つこと。

## 決定 1: タスクの実行の方式（状態機械の変換）

### 選択肢

- **A: 状態機械の変換（スタックを持たないタスク）**。中断しうる関数を、中断点ごとに再開できる状態機械に変換する。タスクの状態は確保した固定番地の塊（状態オブジェクト）に持つ。ADR 0018・ADR 0007（決定 6 の条件 8・9）が前提にした方式。
- **B: スタックを持つタスク（コルーチン）**。タスクごとに専用のスタックを `mmap` で取り、中断点でレジスタとスタックポインタを切り替える。関数の変換は要らない。切り替えの機械語は、既存の `sigil_switch_stack`（ADR 0025 補足 C-6）と同じ作りで足りる。
- **C: A と B の併用**。

### 決定（推奨）

**A** を採る。

- 中断点が、生成コードにとって静的に分かる（ADR 0004 の完全一致の検査により、関数の効果は宣言と推論が一致している。`task.suspend` を含む関数が中断しうる関数である）。変換の対象を、効果から決められる。
- 状態オブジェクトを固定番地に置き、移動させない。中断点をまたぐ借用（ADR 0007 決定 4: 借用は中断点で終わらない）は、この固定番地の中の値か、親の範囲の値を指す。Rust の `Pin` のような仕組みは要らない（構造化並行処理では、親の範囲が子より長く生きる）。
- タスク 1 つあたりのメモリが小さい（状態オブジェクト 1 つ）。B は、タスクごとにスタックの領域とガードページを持つので、多数の接続（観点 6）で重い。B は、深い再帰を持つタスクで有利だが、そのためにタスクごとに大きなスタックを予約するのは、`mmap` の仮想領域を多数消費する。
- ADR 0007 決定 6 の条件 8 の P1-b の確かめ（「中断をまたぐ値の計算が区間の部品を使う」）は、A を前提にしている。
- 代償: 変換が lowering と codegen に入り、実装が大きい（PR 5-2 の中心）。再開時に、変換された関数の呼び出しの連鎖（中断しうる関数が中断しうる関数を呼ぶ）を再入するので、連鎖が深いと再開の費用が連鎖の深さに比例する。最初の版では最適化しない（「根拠の限界」）。

### 変換の仕様（細目は PR 5-2 で確定する）

- **対象**: 推論された効果に `task.suspend` を含む関数と、その本体のクロージャ。関数の値の呼び出しは、関数の型が持つ効果（ADR 0022 の `of(f)` の引き継ぎ）で、中断しうるかを決める。
- **中断点**: `task.suspend` を直接起こす操作（`join`・`sleep`・`yield`・チャネルの受信と送信・`Lock.acquire`・`Atomic.load` など。ADR 0026 決定 3 の表）と、中断しうる関数の呼び出し。
- **状態オブジェクト**: 中断をまたいで生きる局所の値と、呼び出している子の状態、現在の状態番号を持つ。確保は確保器から行う（解放はタスクの完了時）。
- **再開の入口**: 変換後の関数は「状態オブジェクトを受け取り、完了（値）か中断を返す」関数になる。中断のとき、実行の割り当てが後で同じ入口を呼ぶ。
- **取り消し**: 取り消しは中断点で観測する（ADR 0007 決定 4）。再開時に取り消しの旗を見て、早期の戻りと同じ破棄の順序（条件 9）で、状態オブジェクトの中の値を破棄して終える。
- **検証**: 評価器の結果と突き合わせる（決定的な単一ワーカーのモード。決定 2）。破棄の順序は、評価器と同じ記録用の型で固定する（ADR 0026 のテストを実行ファイルでも流す）。

> **判断点 2（承認済み）**: 所有者が 2026-11-09 18:12 JST に、メインのチャットで**案 A（状態機械の変換）**を承認した。決定 1 の案 A のとおり、中断しうる関数を状態機械に変換する。案 B（スタックを持つタスク）と案 C（併用）は採らない。

## 決定 2: 実行の割り当て（スケジューラ）

### 決定（推奨）

- **ワーカー**: 複数の OS スレッド（ワーカー）がタスクを実行する。数は既定で利用できる CPU の数（`sched_getaffinity`）、環境変数などでの上書きは後で決める。**ワーカー数が 1 のモード**を必ず用意する。
- **決定的モード（ワーカー数 1）**: 実行可能待ち行列は FIFO で、切り替えは中断点でだけ起こる。評価器の既定（ADR 0026 決定 6）と同じ順序の意味になるので、評価器との突き合わせ（ADR 0015）の基準にする。仮想の時計は、このモードのテスト用の差し替えとして用意する（評価器と同じ）。
- **並列モード（ワーカー数 2 以上）**: 実行可能待ち行列は、最初の版では 1 本の共有の待ち行列を排他（`futex` を使う簡素な排他）で守る。ワーカー別の待ち行列と仕事の盗み合いは、計測してから別の PR で入れる（最適化であって、意味は変わらない）。
- **待機**: 実行可能なタスクが無いワーカーは `futex` で眠り、タスクが実行可能になったとき起こされる。
- **タスクの移動**: 状態オブジェクトは固定番地なので、タスクは任意のワーカーに移れる（ADR 0007 の「タスク全体は `Sendable` でなくても別の OS スレッドに移れる」）。この前提は、**スレッドごとの領域に値を隠さない**ことに依る（ADR 0007 の根拠の限界）。決定 6 の棚卸しはそのための決定である。
- **突き合わせの方針**: 並列モードの結果は順序に依存しうるので、突き合わせは (a) 決定的モードで全件、(b) 並列モードでは「順序に依らない性質」（合計・集合・最終の状態）だけ、とする。並列モードの競合の確かめは、繰り返しの負荷試験で行う（「根拠の限界」）。

## 決定 3: `epoll`（待ち受けと時間の待機）

### 決定（推奨）

- 入出力の待ちを持つタスク（段階 6 の HTTP で使う `net.server` の操作）は、`epoll` に登録して中断する。**専用の I/O スレッド 1 本**が `epoll_wait` で待ち、準備ができたタスクを実行可能待ち行列に積んでワーカーを起こす。ワーカー自身が `epoll_wait` を回す案（先頭のワーカーが待つ方式）は、実装が複雑になるので採らない。**ただし、PR 5-2f は機構（完了の列に積むところまで）だけを入れ、実行可能待ち行列への結線は最初の待ちの操作と一緒に入れる**（補足 C）。
- 登録は 1 回きり（`EPOLLONESHOT`）にして、同じ記述子の準備完了が複数のタスクを同時に起こさないようにする。
- **時間の待機**（`task.sleep`・`task.timeout`）は、I/O スレッドが期限の一覧（最小ヒープ）を持ち、最も近い期限を `epoll_wait` のタイムアウトに使う。時刻は `clock_gettime` のシステムコールで読む（`-nostdlib` なので vDSO は使わない）。決定的モードの仮想の時計は、これと別に、評価器と同じ規則で動く。
- 本 ADR が決めるのは **機構**だけである。ソケットの API の形（シグネチャと効果）は段階 6 の HTTP の ADR（PR 6-3）で決める（ADR 0018 決定 3 の依存の理由）。PR 5-2 は、機構を検証できる最小の入出力（パイプや `eventfd`）で試験する。結線を含む範囲の分け方は補足 C のとおり（結線を検証する言語の操作が、段階 6 のソケット API と一緒に決まるまで無い）。
- 必要なシステムコール（x86-64）の見込み: `epoll_create1`・`epoll_ctl`・`epoll_wait`、`eventfd2`（ワーカーから I/O スレッドを起こす）、`futex`、`clock_gettime`。番号は PR 5-2 で `tests/raw_syscall_table.rs` と評価器の許可表に合わせて確かめる。**評価器の許可表にこれらを足すかは、PR 5-2 で決める**（評価器は並列実行をしないので、許可表に足さず、ネイティブだけが使う標準モジュール（Sigil 製、評価器は呼ばない）にする案を推奨する。`std.os.console` などと同じ作法）。

## 決定 4: スレッドの作成 — **判断点 1（所有者の確認待ち）**

ワーカーと I/O スレッドを作る手段。ADR 0018 判断 7 が、P1-b でうまくいかなかった場合に限って glibc を残す余地を持つとし、**ADR 5-1（本 ADR）で決めて所有者の確認を求める**とした点である。なお、**出力から glibc を外すこと自体は 3-7c で実装済み**で、以下の案 B は「いったん外した glibc を、スレッドの作成のために戻す」ことを意味する。

### 選択肢

- **案 A: `clone` のシステムコールで書く（glibc なし）**。
  - 必要なもの:
    - 新しいスレッドのスタックの確保（`mmap`、ガードページ）。
    - `clone` の呼び出し。`clone` は子が新しいスタックで同じ命令列の続きから走るので、**小さな機械語の部品**（`_start` と同じ作りで、`clone` を発行し、子では関数と引数を取り出して呼び、戻ったら `exit` する）が要る。信頼基盤に入る機械語のバイト列で、3-7b と同じく所有者の承認と逆アセンブルの確認が要る。
    - 終了の待ち合わせ（`CLONE_CHILD_CLEARTID` と `futex`）。
  - スレッドごとの値（スタックの下限など）は、TLS を使わず、**スタックの位置から求める**案を推奨する（スタックを 2 の冪の大きさで整列させ、スタックポインタの上位ビットから、そのスレッドの制御ブロックを引く）。生成コードに TLS が要らない。
  - 利点: 出力が glibc を含まない（観点 4）。ビルド環境に `libc6-dev` が要らないまま（CI の PR (2) が通る）。信頼基盤は、機械語の部品 1 つと Sigil の関数だけ。
  - 欠点: シグナル・スタックの扱い・`exit` の順序など、glibc が肩代わりしてきた細部を自分で正しくする必要がある。実績のある `pthread` より危険が大きい。
- **案 B: スレッドの作成だけ glibc の `pthread_create` を使う**。
  - 必要なもの: glibc の静的ライブラリ（`libc.a`）を再びリンクし、**C の関数を呼ぶ手段**を足す。ADR 0018 決定 6 の「C の関数を呼ぶ原始操作を持たない」（観点 3）を見直すことになる。glibc の起動の処理（`__libc_start_main`）と、3-7b・3-7c で作った自前の `_start` との整合も要る。
  - 利点: 実績があり、P1-b の危険が小さい。
  - 欠点: 3-7c で達成した「出力が glibc を含まない」を戻す。`tests/link_37c.rs` の確認（glibc のシンボルが無い、`INTERP` が無い）を、スレッドを使うプログラムについて緩める必要がある。ADR 0006 の期限付きの例外に、スレッドの作成の分を加える。`libc6-dev` が CI に残る。C の関数を呼ぶ手段は、glibc の任意の関数が信頼基盤に入る入口になる（ADR 0018 観点 3 が避けた点）。
- **案 C: 案 A を先に試し、基準を満たさなければ案 B にする**（ADR 0018 判断 7 の推奨の形）。

### 推奨（結論は確認待ち）

**案 C**、すなわち案 A（`clone`）から始める。案 B に切り替える基準を、**あらかじめ測れる形で**決めておく。次のどれかを満たせなかったら、所有者に案 B への切り替えを諮る。

1. **作成と終了の負荷試験**: スレッドの作成・終了・待ち合わせを 100 万回繰り返して、スタックの領域の漏れ（`/proc` で確認）も、ハングも、異常終了もない。
2. **競合の試験**: 複数のスレッドが、原子的な操作・`Lock`・チャネルを使うプログラムを繰り返し動かして、結果が期待と一致する。
3. **停止の経路**: ワーカーの 1 つが契約違反で止まったとき（決定 7）、プロセスが正しいコードで終わり、他のスレッドがハングしない。

案 A の機械語の部品と、スレッド作成の標準モジュールは、案 C の最初の PR（PR 5-2c、下の分割計画）で入れる。その時点で 3 つの基準を試験にして、結果を所有者に示す。**基準は本 ADR の承認で確定する**ので、数値（100 万回など）に異論があれば、承認の際に直す。

> **判断点 1（確認済み）**: 所有者が 2026-11-09 に**案 C**で確認した。スレッドの作成は `clone`（案 A）から始め、上の 3 つの基準（作成と終了の負荷試験、競合の試験、停止の経路）のどれかを満たせなかった場合に、案 B（glibc を戻す）への切り替えを所有者に諮る。基準の数値（100 万回など）は、確認の時点では変えていない。ビルド環境の前提（`libc6-dev`）は、この段階では変えない。案 A の機械語の部品は、PR 5-2c で入れ、その PR でも所有者の承認を求める（機械語のバイト列のため）。

## 決定 5: 原子的な操作の原始操作

`RAW_OPS` に行を足すときは先に ADR に記録する（ADR 0016 決定 1）。本決定がその記録である。

### 決定（推奨）

次の 6 行を、核の層（`Layer::Core`）に足す。**メモリ順序は逐次一貫（seq_cst）だけ**とし、順序の引数を表に出さない（観点 5。誤りやすい概念を表に出さない。弱い順序は計測してから別の ADR で足す）。

| 行 | 意味 |
|---|---|
| `atomic_load_i64(a: Addr) -> Int` | 8 バイトを原子的に読む |
| `atomic_store_i64(a: Addr, v: Int)` | 8 バイトを原子的に書く |
| `atomic_add_i64(a: Addr, v: Int) -> Int` | 加えて、**加える前**の値を返す |
| `atomic_swap_i64(a: Addr, v: Int) -> Int` | 書き換えて、前の値を返す |
| `atomic_cas_i64(a: Addr, expected: Int, new: Int) -> Int` | 値が `expected` なら `new` に書き換える。**前の値**を返す（成功は前の値が `expected` と等しいことで分かる） |
| `atomic_fence()` | 逐次一貫の壁 |

- **効果**: `none`（ほかの原始操作と同じ。システムコールのような外部の作用ではなく、メモリの操作）。ただし結果が他のスレッドの動きに依るので、前提の文に「他のスレッドが同じ番地を並行に操作しうる」ことを書く。
- **前提**: `a` は 8 バイト整列の、生きた領域を指す。整列していなければ評価器は停止する（`requires` ではなく前提の文と、評価器の実行時検査）。
- **ネイティブ**: Cranelift の `atomic_load`・`atomic_store`・`atomic_rmw`・`atomic_cas`・`fence` で直接生成する（機械語の部品は要らない）。
- **評価器**: 評価器はタスクを 1 つのスレッドで動かすので（ADR 0026 決定 6）、通常の読み書きと同じ意味で足りる。検査（整列・範囲）だけ入れる。
- **futex**: `raw.syscall`（効果を宣言に委ねる唯一の原始操作）で `futex` を呼ぶ。新しい原始操作は足さない。
- **使う場所**: `Atomic`・`SyncShared`・`Lock`・チャネル・実行可能待ち行列・確保器の排他。これらの組み込みを、ネイティブでは Sigil の標準モジュール（`unchecked`）として書く（`Lock` などの構造は ADR 0026 決定 3 のとおり）。
- **見直しの記録との関係**: ADR 0016 の見直し記録（PR #339）は、`unchecked` の関数が `requires none` で呼び出し側に義務を課す形になっていることを示した。原子的な操作を使う関数は、**番地の有効性と整列**という同じ種類の義務を呼び出し側に課す。この義務の扱いは、ADR 0016 決定 2 の見直し（所有者の判断）と一緒に決める。本 ADR は、新しい関数を信頼基盤の `std.*` の内側に限る（利用者のコードから呼べない）ことで、その見直しの結論を先取りしない。

## 決定 6: 単一スレッド前提の棚卸しと対処

複数の OS スレッドにする前に、ADR 0025 補足 A-5 が必須とした見直しを行う。**一覧は `grep` で作った暫定のもので、PR 5-2b の最初の作業として、コードを読んで確定する**。

| 項目 | 現状 | 並列でどうなるか | 推奨する対処 |
|---|---|---|---|
| 確保器の大域の状態（`STATE`・`LIVE`。`std.os.alloc`） | 排他なし | 競合で壊れる | 最初の版は **確保器の入口で 1 本の排他**（`futex` を使う簡素な排他）。正しさを先に。スレッドごとの小さな確保の貯めは、計測してから最適化として入れる |
| 生成コードの破棄の積み・表示のバッファ（ADR 0025 補足 G-2・H など。静的データ） | 静的、単一スレッド | 競合 | **スレッドごと**に持つ（スタックの位置から引く制御ブロックの中、または状態オブジェクトの中） |
| スタックの下限（`sigil_stack_limit` の静的データ。補足 C-6） | 静的、1 つ | スレッドごとに違う | スレッドごと（制御ブロック）。入口が比べる下限を、スタックの位置から求める |
| `ENVP` | 起動時に 1 回書く | 起動後は読むだけ | そのままでよい（起動の後は書き換えない、という前提の文のとおり） |
| 生存数の数え（`SIGIL_RT_LIVE`、補足 C-5） | 静的 | 競合 | 原子的な加算、または確保器の排他の中で数える |
| 型の記述子・文字列定数など | 読むだけ | 安全 | そのまま |
| 利用者の大域の可変な値 | ADR 0007 規則 8 により禁止 | — | 変更なし |

- **帰結**: ADR 0007 の根拠の限界が前提にした「信頼基盤がスレッドごとの領域に値を隠さない」は、上の「スレッドごとに持つ」項目が **状態オブジェクトや制御ブロックを通じて他のスレッドから見えない**ことを意味しない。タスクがワーカーを移るとき、スレッドごとの領域に残る値が、そのタスクの意味に影響しないことが要る。破棄の積みのように、**タスクの途中で別のワーカーに移りうる値は、スレッドごとではなくタスクごと（状態オブジェクトの中）に持つ**。PR 5-2b で、各項目について「スレッドごと」か「タスクごと」かを決めて、前提の文に書く。
- [ADR 0029](0029-scope-arena-allocation.md)（スコープアリーナ。承認済みで、具体化は未着手）が実装されると、タスクごとのデータスタックが状態オブジェクトの自然な置き場になる。本 ADR はそれに依らずに成り立つ（確保器の排他で足りる）。0029 の具体化の時期との前後は、PR 5-2 の着手時に確かめる。

## 決定 7: 停止・要求の隔離・取り消し（ネイティブでの意味）

評価器は、要求の隔離（1 件の要求の契約違反でプロセス全体を止めない。ADR 0018 決定 7、ADR 0026 決定 4）を持つ。ネイティブでも同じ意味にする。

### 決定（推奨）

- **隔離できる停止**（契約違反・桁あふれ・0 での除算・`unwrap` の失敗など、タスクの中で起こる停止。ADR 0018 決定 7 の範囲）: 隔離の単位は**ルートタスク**である（ADR 0026 決定 4）。停止が起きたタスクの**子や兄弟だけを切り離すことはせず**、そのルートタスクに属するすべてのタスク（範囲の内側の子を含む）を、取り消しと同じ順序（決定 1）で、状態オブジェクトの中の値を破棄して終わらせる。停止したタスクが保持していた `Lock` は「壊れた」状態にし、その `Lock` を待っているタスクは起こして取得を失敗で返す（ADR 0026 決定 4）。**別のルートタスクは動き続ける**。評価器の `src/ir_eval/sched.rs`（失敗の分岐が `stop_root` を呼ぶ）と同じ意味である。**ただし、ネイティブ出力のルートタスクは 1 つだけで複数ルートの入口が無いため、「別のルートタスクは動き続ける」とルートをまたぐ `LockBroken` の配送は、5-2g では実装も観測もしない。段階 6 で入口と一緒に入れる**（補足 D）。異常停止の報告は、従来どおり標準エラーに出す。
- **隔離できない停止**（確保器の整合性の破れ、スタックの溢れ、状態オブジェクトの破損）: 従来どおりプロセス全体を `exit_group(70)` で止める。スタックの溢れは、スレッドごとのガードページに当たると `SIGSEGV` になり、シグナルの処理を持たないので、プロセスが落ちる。これは、ワーカーのスタックの下限の検査（入口が比べる）をすり抜けた場合の最後の止めである（補足 C-6 と同じ位置づけ）。
- **取り消し**: 決定 1 のとおり。範囲を抜けるときに子が完了するのを待つ（ADR 0007 決定 1）。
- 隔離の細目（壊れた `Lock` を待っているタスクの起こし方、止めたタスクの資源の後始末、確保器の整合）は、評価器の決定 4（ADR 0026）と同じ規則を、ネイティブに写す。差が出る点は PR 5-2g で表にして固定する（範囲の分け方は補足 D）。

### A-2. 確保器の排他の細目（本 PR で実装）

- ロックの語は、状態のページの**最後の語**（4088）に置く。状態のページの使用済みの位置は 0〜103 までなので重ならない。`atomic_cas_i64(語, 0, 1)` が 0 を返したら取れた。放すのは `atomic_store_i64(語, 0)`。
- 公開の入口は、状態のページを作ってから（`state()`）ロックを取り、本体（`alloc_locked`・`free_locked`）を呼び、放してから戻る。`live_blocks` は、状態のページがまだ無ければ（一度も確保していなければ）`LIVE` は 0 なので、ロックを取らずに `LIVE` を返す。
- **決定 6 の「`futex` を使う簡素な排他」を、5-2b では「回転して待つ排他」に狭める**。競合は複数の OS スレッドが動いてから（5-2c 以降）起こり、それまで競合した経路は試験できない。試験できない待機の経路を信頼基盤に入れることを避け、`futex` で眠る待機は、競合を試験できる 5-2e で足す。確保器の中の区間は短い（表の探索と更新）ので、回転して待つ費用は小さい。
- `halt()`（`exit_group(70)`）は、プロセス全体を終えるので、ロックを放さなくてよい。
- 同じスレッドが、ロックを持ったまま入口を呼び直す（再入）と、回転して戻らない。入口は公開の 3 つだけで、内側（`*_locked`）から入口を呼ばない。
- 追加した `unchecked` の関数は 5 個（`alloc_locked`・`free_locked`・`lock_addr`・`lock`・`unlock`）。ADR 0016 の見直し記録の計測の 85 個から 90 個になる。原始操作の呼び出しは 554 回から 558 回になる（`atomic_cas_i64` +1、`atomic_store_i64` +1、`offset` +1、`addr_to_int` +1。`src/stdlib/*.sigil` のコメント行を除く出現の数）。前提の文の「単一スレッド」は、「確保器の排他の下で呼ばれる」に直した。

### A-3. 決定 6 の表の訂正（破棄の積みは「スレッドごと」）

決定 6 の「帰結」は、**破棄の積み**を「タスクの途中で別のワーカーに移りうる値は、タスクごと」の例に挙げたが、誤りである。値の破棄は中断しない（ADR 0007 決定 3。破棄の処理は `task.suspend` を起こせない）ので、破棄の積みを使っている間にタスクが別のワーカーに移ることはない。破棄の積み（作業の列）と表示バッファは、**スレッドごと**で足りる。表示バッファも、表示の間は中断しない。

「タスクごと」が要るのは、中断をまたいで生きる値だけで、それは状態オブジェクトの中にある（決定 1）。

### A-4. 5-2c の完了条件に加えること

- スレッドごとの 3 つ（作業の列・表示バッファ・スタックの下限）を、**最初のスレッドを作るより前に**スレッドごとにする。スレッドごとの制御ブロックを、スタックの位置から引く（スタックを 2 の冪の大きさで整列させ、スタックポインタの上位ビットから制御ブロックの番地を求める。決定 4 の案 A）。生成コードに TLS は要らない。
- 最初のスレッドを作る前に、確保器を一度呼ぶ（`STATE` の前提）。
- 上の 2 つが済むまで、5-2c の `clone` の部品を使うプログラムを出力しない（出力にスレッドを作る関数を結ばない）。

### A-5. 5-2b で、スレッドごとの 3 つを変えない理由

スレッドごとにするには、スレッドごとの制御ブロックを引く仕組みが要り、それはスレッドのスタックの確保と整列（5-2c の `clone` の部品）と切り離せない。5-2b でその一部だけを入れると、複数のスレッドが存在せず試験できない仕組みを信頼基盤に入れることになる。単一スレッドの間は、3 つの静的データは今のままで正しい。

## 補足 B（PR 5-2c）: スレッドの作り方 — 新しい機械語を足さない設計

- **日付**: 2026-11-09
- **状態**: 提案（本 ADR に従う。判断点 2〜6 と本 ADR 全体の承認は、まだ記録されていない。判断点 1 は 2026-11-09 に案 C で確認済み）
- 決定 4 の案 A は「`clone` に小さな機械語の部品が要る」としていた。PR 5-2c（Issue #349）の設計で、**新しい機械語のバイト列を足さずに済む**ことが分かったので、その設計を記録する。決定 4 の案 A の「機械語の部品」の記述を、本補足が置き換える。決定 4 の判断（案 C）は変えない。

### B-1. `clone` の呼び方（機械語を足さない）

- 既存の `sigil_syscall6`（ADR 0025 C-4。3-7b で承認済み）は、`syscall` を発行した直後に `ret` する。`clone` の子は、新しいスタックで `syscall` から戻り、親のレジスタの写しを持つ。したがって子の `ret` は、**新しいスタックの先頭の語を戻り番地として取る**。
- そこで、`std.os.thread.spawn` は、子のスタックの先頭 `s`（16 バイト整列）に、`[s] = sigil_thread_entry の番地`、`[s + 8] = ハンドル` を書いてから `raw.syscall(56, フラグ, s, 0, ctid, 0, 0)` を呼ぶ。子は `ret` で `sigil_thread_entry(フラグ, s)` に入る（rdi = フラグ、rsi = s は、`sigil_syscall6` が `syscall` の前に詰めた値のまま）。`ret` の後の rsp は `s + 8`（8 の奇数倍）で、関数の入口が求める「呼び出された直後」の整列と一致する。
- `sigil_thread_entry`（生成コード。Cranelift）は、`[s + 8]` のハンドルを読み、`std.os.thread.thread_main(ハンドル)` を呼び、`exit`（番号 60。スレッドだけ終わる）で終わる。戻らない。番地は、起動の処理が大域 `std.os.thread.ENTRY` に書く（`ENVP` と同じ作法。ADR 0025 C-4）。
- **帰結**: 信頼基盤に入る機械語のバイト列は、`_start`・`sigil_syscall6`・スタックの切り替え（3-7b）のままで増えない。代わりに、信頼基盤の前提が増える: 「`sigil_syscall6` は `syscall` の直後に `ret` する」「子の戻り番地は、`spawn` が置いた先頭の語になる」。前者は `tests/start_37b.rs` の逆アセンブルの試験が固定している。後者は `spawn` の前提の文に書き、スレッドの試験が固定する。
- 終了の待ち合わせは `CLONE_CHILD_CLEARTID` と `futex`: フラグは `CLONE_VM|CLONE_FS|CLONE_FILES|CLONE_SIGHAND|CLONE_THREAD|CLONE_SYSVSEM|CLONE_CHILD_CLEARTID`（0x250F00）。ハンドルの先頭の語（ctid）を 1 にしてから作ると、子が終わったときカーネルが 0 にして `futex` で起こす。待つ側は、**`FUTEX_PRIVATE_FLAG` を付けない** `FUTEX_WAIT`（番号 202、操作 0）で待つ（カーネルの起こしは共有の鍵を使う）。

### B-2. スレッドごとの領域（TCB なしの整列スタック）

補足 A-4 の「スタックの位置から制御ブロックを引く」を、次の形で実装する。TLS は使わない。

- 各スレッドのスタックは、`STACK_REGION`（256MiB。2 の冪）に整列した領域の中にある。`mmap` で 2 倍（512MiB、`MAP_NORESERVE`）を取り、整列した 256MiB を切り出す（余りは触らない仮想の領域。解放するときは、取った全体を `munmap` する）。主スレッドも同じ（起動の処理が同じ形で取る）。
- スタックポインタの下位 28 ビットを落とすと、領域の先頭（`region_base`）になる。領域の並び: `[0, 4096)` ガードページ（読み書き不可）、`[4096, ..)` 作業の列（破棄の積み。64KiB + 24）、その次に表示バッファ（4KiB + 24）、`[64MiB, 256MiB)` スタック。
- **スタックの下限は `region_base + 64MiB`**（領域の 1/4。今の「上端から 192MiB 下」と同じ）。`sigil_stack_limit` は、静的データを読まず、スタックポインタから計算する。作業の列と表示バッファは、静的データでなく、領域の先頭からの固定の位置になる。領域は `mmap` のゼロの領域なので、状態の語は 0 で始まる。
- 作業の列も表示バッファも、使っている間は中断しない（値の破棄・表示は `task.suspend` を起こせない。補足 A-3）ので、スレッドごとで足りる。

### B-3. 判断点 1 の 3 基準の確かめ方（ADR の基準の具体化）

| 基準 | 試験 | 通常の試験の回数 |
|---|---|---|
| 1. 作成と終了の負荷 | 作る・終える・待ち合わせるを繰り返し、仮想メモリの上限（約 3GiB）の下で `spawn` が失敗しない（領域が漏れれば `mmap` が失敗する）。生きている塊の数も元に戻る | 2000 回（通常）。**100 万回**は `#[ignore]` の試験で、手で実行して結果を PR に書く |
| 2. 競合 | 8 スレッドの原子的な加算の総数、6 スレッドの確保・解放の読み戻しと塊の数、4 スレッドの破棄と表示 | — |
| 3. 停止の経路 | ワーカーが確保器の異常停止で止まると、プロセスは終了コード 70 で終わり、`join` で待つ親もハングしない。ワーカーのスタックの溢れは、スレッドの下限で報告して終了コード 70 になる（ガードページの `SIGSEGV` にならない） | — |

### B-4. 範囲外・残ること

- `body`（スレッドが実行する本体）は、5-2c では何もしない。5-2e が実行の割り当て（ワーカー）に置き換える。試験は、`std.os.thread` のソースの `body` を差し替える。
- `SIGSEGV` を捕まえない（シグナルの扱いは「未決として残す点」のまま）。ガードページに当たると、プロセスは `SIGSEGV` で落ちる。スタックの下限の検査をすり抜けた場合の最後の止めである。
- スレッドの数の上限、スタックの大きさを変えられるか（今は 256MiB の固定。仮想領域のみ）は、5-2e で扱う。

## 補足 C（PR 5-2f）: 5-2f の範囲は機構のみ、結線は最初の待ちの操作と一緒に

- **日付**: 2026-11-10
- **状態**: 提案（本 ADR に従う。判断点 3〜6 と本 ADR 全体の承認は、まだ記録されていない）
- PR #358（5-2f、Issue #357）の実装で、決定 3 のうち結線を後に回した。決定 3 の「準備ができたタスクを実行可能待ち行列に積んでワーカーを起こす」までを 5-2f に含める読み方を、本補足が置き換える。実装の前に ADR で確定するため（AGENTS.md「実装中に ADR との食い違いを見つけたら、実装を止めて ADR の修正 PR を出す」。PR #358 の Codex の P1 指摘）。決定 3 の機構の設計（専用の I/O スレッド、`EPOLLONESHOT`、期限の最小ヒープ、`clock_gettime`）は変えない。

### C-1. 5-2f に含めるもの（機構のみ）

`std.os.io`（`src/stdlib/os_io.sigil`）に、次を入れる。

- 専用の I/O スレッドの本体（`epoll_wait` を回す `io_loop`）。スレッドの作成は呼び出し側が `std.os.thread.spawn` で行う（`std.os.io` は `std.os.thread` に依らない）。
- `EPOLLONESHOT` の登録と再登録（`EPOLL_CTL_MOD`）、`eventfd2` による起床。
- 期限の最小ヒープ（最も近い期限を `epoll_wait` のタイムアウトに使う）と、`clock_gettime`。期限より前に I/O スレッドが起きても、時刻が届くまでは起こさない。
- 準備完了と期限を積む「完了の列」（`io_take`・`io_take_wait`）。
- 取り消し（`io_cancel`）と、停止の後始末（`io_stop` → `join` → `io_free`）。

評価器の許可表には足さず、暗黙には結ばない（決定 3 の推奨どおり）。決定的モードの仮想の時計（`std.os.sched` の S_CLOCK）は変えない。試験はパイプと実時間で行う。

### C-2. 5-2f に含めず、最初の待ちの操作と一緒に入れるもの

- 完了の列から実行可能待ち行列への結線（`std.os.sched` の `wake` と `notify`）。
- 本番のスレッドの本体（`body`）を、引数で `worker_run` と `io_loop` に振り分ける作業。5-2f の試験は、`std.os.thread` の `body` を差し替える（5-2c の試験と同じ作り）。
- 入れる時期は、最初の待ちの操作（fd／期限で中断する言語の操作）を入れるときで、段階 6 のソケット API と一緒に決める（決定 3。PR 6-3 の ADR）。

**理由**: 結線を検証する言語の操作がまだ無い。fd や期限でタスクを中断する操作が無いので、タスクから `io_wait_fd` などを呼ぶ経路が無く、結線は動かして確かめられない。検証できない結線を信頼基盤（`trust base`）に入れることを避ける（補足 A-2 が、試験できない待機の経路を 5-2b に入れなかったのと同じ考え方）。

### C-3. 5-2f で残る既知の事項

- I/O スレッドの `epoll_wait` が EINTR 以外の失敗を返し続けた場合は、停止の旗が立つまで回り続ける。エラーの伝え方は、結線と一緒に決める。

## 補足 D（PR 5-2g）: 5-2g の範囲は単一ルート内の機構のみ、ルート単位の隔離は段階 6 へ

- **日付**: 2026-11-10
- **状態**: 提案（本 ADR に従う。判断点 3〜6 と本 ADR 全体の承認は、まだ記録されていない）
- Issue #360（5-2g）の着手前に、決定 7 の範囲の曖昧さが見つかった。決定 7 は「隔離の単位はルートタスク」「別のルートタスクは動き続ける」「壊れた `Lock` の待機者に取得の失敗を返す」と定めるが、ネイティブ出力のルートタスクは 1 つ（番号 0）だけで、複数ルートの入口が無い（`src/stdlib/os_sched.sigil` の冒頭コメント、`start_locked`）。ADR 0026 決定 4 は「`sigil run` の入口は 1 つのルートタスク。サーバーが要求ごとにルートタスクを起動する形は段階 6（PR 6-3・6-4）で決める」とする。評価器は複数ルートを扱える（`src/ir_eval/mod.rs` の `run_roots_with`、`src/ir_eval/sched.rs` の `run_roots`・`stop_root`）。この曖昧さは、所有者が委任した仕様判断の手順で、「複数ルートの入口は段階 6 に回す（ADR 0026 決定 4 どおり）」に決まった。実装の前に ADR で確定する（補足 C と同じ形）。

### D-1. 5-2g に含めるもの（単一ルート内で観測できる機構）

- 停止の伝播順序: 作成順の逆の一列で取り消す（評価器の `stop_root_inner`／`cancel_all_inner` と同じ）。
- 取り消し時の値の破棄（状態オブジェクトの中の値、ごみの列、チャネルの項、`Lock` の値、タスクの結果）。
- 壊れた `Lock` の扱いのうち、単一ルート内で観測できる範囲。
- 評価器との差の表の固定（D-3）。

### D-2. 5-2g に含めず、段階 6 へ回すもの

- ルートタスク単位の隔離（別のルートタスクが動き続けること）。
- 複数ルートの入口（サーバーが要求ごとにルートタスクを起動する形）。
- それに伴う `LockBroken` の待機者への配送のうち、ルートをまたぐ部分。

入れる時期は、最初の待ちの操作とソケット API と一緒に決める（補足 C-2。PR 6-3・6-4 の ADR）。

**理由**: 複数ルートの入口がネイティブにまだ無く、観測も検証もできない。検証できない信頼基盤（`trust base`）のコードを入れることを避ける（補足 C と同じ考え方）。

### D-3. 評価器との差の表に固定する項目

| 項目 | 評価器 | ネイティブ |
|---|---|---|
| ルートタスクの数 | 複数（`run_roots_with`） | 1 つ（番号 0）。別のルートが動き続けることは観測できない |
| `task.timeout` | 対応 | 対応（PR #380） |
| `race`／`all_ok` | 対応 | 未対応（生成コードがビルドで止める） |
| 眠りのない本物のライブロックの停止 | 検出して停止する | 無い |
| 兄弟の部分木の取り消し | 兄弟ごとの再帰 | 作成順の逆の一列 |

これらのうち、5-2g で埋めるものと、表で固定するだけのものの区別は、実装時の判断に委ねる。本補足は範囲の分け方だけを確定し、実装の詳細は決め打ちしない。

## 未決として残す点

- ワーカー別の待ち行列と、仕事の盗み合い（性能の計測の後）。
- チャネルを有界にするか（ADR 0026 の未決。P1-b で再検討するとされた点。本 ADR では変えない）。
- 弱いメモリ順序（逐次一貫より弱い順序）の導入。
- シグナルの扱い（`SIGPIPE`、スタックの溢れの `SIGSEGV` を捕まえるか）。
- aarch64（ADR 0025 は x86-64 の Linux に限る）。
- WebAssembly・JavaScript の実行の割り当て（P2）。
- 関数の値を通した呼び出しが多い連鎖での、再開の費用の最適化。

## 根拠の限界

- 本 ADR は設計の提案であり、**実装も計測もしていない**。状態機械の変換の費用（再開の費用が連鎖の深さに比例する点）、共有の待ち行列と 1 本の確保器の排他の性能は、PR 5-2 の実装後に計測するまで分からない。
- 決定 6 の棚卸しは `grep` による暫定の一覧で、漏れがありうる。PR 5-2b の最初の作業で確定する。
- システムコールの番号・`clone` のフラグ・`futex` の細部は、Linux x86-64 の知識に基づく。PR 5-2 で実機の試験により確かめる（本 ADR の段階では、Linux のマニュアルと照合していない）。
- 並列モードの競合は、非決定なので、試験で見つからない誤りが残りうる。決定的モードと、データ競合を型で排除する ADR 0007 の保証が主な防御で、負荷試験は補助である。TSan のような検出器は、現在の環境に無い。
- 判断点 1 の 3 つの基準（100 万回など）は、経験に基づく目安で、根拠は強くない。承認の際に調整してよい。
