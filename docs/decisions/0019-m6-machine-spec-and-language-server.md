# 0019: M6 の仕様の機械向けの形式と、言語サーバー

- **状態**: 提案（2026-10-26）。依存の追加（判断 1・2）は所有者の判断を求める。

## 背景

- [ADR 0006](0006-p0-scope-and-bootstrap.md) は、M6 を次のとおり定め、M6 の完了をもって P0 の完了とした。
  - 言語サーバーの標準の通信方式（Language Server Protocol。以下 LSP）で、M1・M2 の検査結果を診断として返す。
  - 関数にカーソルを置くと、`sigil spec` と同じ仕様を返す。
  - 上の 2 点を、言語サーバーを起動してサンプルを開く自動テストで確かめる。
- [ADR 0008](0008-m0-notation.md) の決定 7 は、`sigil spec` を日本語の定型文とし、「機械向けの形式は、言語サーバー（M6）の前に決める」とした。DESIGN.md の 5 章も同じ時期を書いている。
- [ADR 0018](0018-p1-scope.md) は、本 ADR を ADR 0-1 とし、JSON・LSP のクレートが要るかを本 ADR で所有者に問うとした。P1 の実装は M6 の後に始める（ADR 0018 の決定 1）。

### 現状（main `9e05390`）

- **依存**: `Cargo.toml` の依存は、所有者が承認した Cranelift の 4 クレートだけである。JSON を読み書きする部品はない。
- **診断**:
  - `src/error.rs` の `Error` は、種類（`ErrorKind`）・位置（`Span`）・日本語の文からなる。
  - `ErrorKind` の注記は「テストと将来の機械可読な出力のために安定した名前を持つ」としている。
  - `Span` は始まりの行と列（1 始まり、列は文字数）だけで、終わりを持たない。
  - 検査は最初の 1 件のエラーで打ち切る（字句・構文・型・効果・移動・借用のどの段も）。
- **仕様の抽出**（`src/spec.rs`）:
  - 構文だけから日本語の定型文を作る。`unchecked` の関数があるときだけ検査器を呼んで、「使う原始操作」「推論できない効果」の行を作る（ADR 0016）。
  - 項目（モジュール・型・構造体・列挙型・関数・メソッド）ごとの塊を空行で区切って並べる。
  - 関数の宣言（`FnDecl`）は始まりの位置（`span`）と各節の行（`clause_lines`）を持つ。
- **複数のファイル**: `sigil check` は、同じモジュールの宣言を持つ複数のファイルを合わせて検査する（`ModuleMismatch`）。モジュールどうしの参照はない（「モジュールの単位」は ADR 0018 の ADR 2-1 で決める）。`examples/04-effects` は 2 つのファイル（`effects.sigil`・`entry.sigil`）からなる。
- **文字**: 識別子と演算子は ASCII に限られ、ASCII でない文字は文字列のリテラルとコメントの中にだけ現れる（ADR 0009）。

## 本 ADR で決めないこと

- 補完・定義への移動・名前の変更・整形の要求など、M6 の 3 点以外の言語サーバーの機能。P2 の IDE の ADR で決める。
- エディタの拡張機能（VS Code の拡張など）の配布。M6 は言語サーバーを `sigil lsp` として出すところまでとする。
- 2 件目以降のエラーを報告すること（決定 4）。
- 式の訳し方（ADR 0008 の決定 7 が P2 に送った）。

## 評価の観点

重要な順に並べる。

1. **AI が誤りなく読めるか**: 機械向けの形式が、日本語の文を解析せずに、仕様と検査結果の各要素を取り出せること。
2. **人間に示すものと一致するか**: 機械向けの形式と言語サーバーが示す仕様が、`sigil spec` の日本語の定型文と食い違わないこと（ADR 0006 の「`sigil spec` と同じ仕様」）。
3. **依存を増やさないか**: 処理系の依存は所有者の承認が要り、少ないほど供給元の危険が小さい（ADR 0006）。
4. **実装量と、テストで確かめられること**。
5. **後で作り直さずに済むか**: P2 の IDE（ブラウザで動く。ADR 0005）が同じ形式と言語サーバーを使えること。

## 決定 1: 仕様の機械向けの形式

### 選択肢

- **A: 構造を持つ JSON**。項目ごとに、名前・引数の受け渡し方・型・節の式などを欄に分けて出す。
- **B: 日本語の定型文を JSON で包む**。項目ごとに、名前・位置・定型文の塊だけを出す。
- **C: A と B の両方**。項目ごとに構造の欄を持ち、同じ項目の日本語の定型文の塊（`text`）も持つ。

### 決定

**C** を採用する。`sigil spec --json <ファイル>` で出す。

- 一番外は `{"format": 1, "module": {...}, "items": [...]}` とする。`format` は形式の版で、欄を消す・意味を変えるときだけ上げる。欄を足すときは上げない。
- 各項目は、少なくとも次の欄を持つ。
  - `kind`: `"module"`・`"type"`・`"struct"`・`"enum"`・`"fn"`・`"method"` のどれか。
  - `name`: 名前。メソッドは `型.名前`（`sigil spec` と同じ）。
  - `span`: 宣言の始まりの位置（`{"line": 行, "col": 列}`。1 始まり、列は文字数）。
  - `text`: `sigil spec` がその項目について出す塊と、1 文字も違わない文字列。
- 関数とメソッドは、さらに次の欄を持つ。
  - `intent`: 意図の文字列。
  - `params`: `[{"name": ..., "mode": ..., "type": ...}]`。`mode` は `"own"`（受け取る）・`"ref"`（読む）・`"mut"`（書き換える）・`"call"`（関数の値を呼ぶ）。`type` は `sigil spec` と同じ型の表記の文字列。
  - `returns`: 型の表記、または `null`（戻り値なし）。
  - `requires`・`ensures`: 式の正規形の表記の文字列、または `null`（`none`）。
  - `effects`: 効果のカテゴリと `of(...)` の文字列の配列（正規形の並び）。
  - `generics`: 型引数と制約。
  - `unchecked`: 前提の文、または `null`。
  - `raw_ops`・`uninferred_effects`: `sigil spec` の「使う原始操作」「推論できない効果」の行の中身（`unchecked` でなければ空の配列）。
- 型・構造体・列挙型は、`sigil spec` の行に対応する欄（篩型の基の型と条件、欄の名前と型、変種と中身の型）を持つ。
- 例（`examples/03-ownership` の `deposit`。`text` は省略して示す）:

```json
{"kind": "fn", "name": "deposit", "span": {"line": 26, "col": 1},
 "intent": "口座に入金する",
 "params": [{"name": "account", "mode": "mut", "type": "Account"},
            {"name": "amount", "mode": "own", "type": "Int"}],
 "returns": null, "requires": "amount > 0",
 "ensures": "account.balance == old(account.balance) + amount",
 "effects": [], "generics": [], "unchecked": null,
 "raw_ops": [], "uninferred_effects": [], "text": "関数 deposit\n  意図: ..."}
```

- 構造の欄と `text` は、同じ関数（`src/spec.rs` の項目ごとの関数）から作る。`text` を構造の欄から組み立て直す形にし、2 つが食い違わないようにする。

### 理由

- 観点 1: A の欄があれば、AI は「この関数は `fs.read` を起こすか」「`account` を書き換えるか」を、日本語の文を解析せずに知れる。B では日本語の定型文を解析することになり、文の言い回しを変えるたびに読む側が壊れる。
- 観点 2: `text` があれば、言語サーバーは `text` をそのまま示すだけで、`sigil spec` と同じ仕様を返せる。人間が読む文と機械が読む欄が、同じ出力に並ぶ。
- 観点 5: P2 の IDE は、`text` を表示に、欄を検索や絞り込みに使える。

### 選ばなかった案と理由

- **A だけ**: 言語サーバーが日本語の定型文を別に作ることになり、`sigil spec` と食い違いうる（観点 2）。
- **B だけ**: 上のとおり（観点 1）。

## 決定 2: 診断の機械向けの形式

### 決定

`sigil check --json <ファイル>...` で、次の形を出す。言語サーバーの診断も同じ内容から作る。

```json
{"format": 1, "ok": false,
 "diagnostics": [{"file": "a.sigil", "kind": "UseAfterMove", "phase": "check",
                  "line": 12, "col": 5, "message": "..."}]}
```

- `kind` は `ErrorKind` の変種の名前とする。`ErrorKind` の注記どおり、安定した名前として扱い、名前を変えるときは `format` を上げる。
- `phase` は `"lex"`・`"syntax"`・`"fmt"`・`"check"` のどれか（`Phase`）。
- `message` は今の日本語の文のままとする。
- 最初の 1 件で打ち切る今の動きは変えない（決定 4）。`diagnostics` は配列にしておき、後で複数にしても形を変えずに済むようにする。
- 終了コードは `--json` のないときと同じとする。

### 理由

- 観点 1: AI は今、標準エラーの文を解析してエラーの種類を知っている。`kind` を欄に出せば、種類ごとの直し方を文の言い回しに依らずに選べる。
- 言語サーバーと CLI の診断を同じ内容から作るので、片方だけ直す誤りが起きない。

## 決定 3: JSON と LSP の実装の方法

### 選択肢

| 案 | JSON | LSP | 依存の追加 |
|---|---|---|---|
| A: すべて自前 | 処理系の中に JSON の書き出しと読み取りを書く（`src/json.rs`） | 標準入出力の上の JSON-RPC と、M6 に要る要求だけを自前で扱う | なし |
| B: JSON だけクレート | `serde`・`serde_json` | 自前 | 2 クレート（`serde_derive` などの推移的な依存を含む） |
| C: 同期の LSP の部品 | `serde`・`serde_json` | `lsp-server`・`lsp-types`（rust-analyzer が使う同期の部品） | 4 クレートと、その推移的な依存（`crossbeam-channel` など） |
| D: 非同期の LSP の枠組み | `serde`・`serde_json` | `tower-lsp` | `tokio` を含む多数 |

### 比較

| 観点 | A | B | C | D |
|---|---|---|---|---|
| 3. 依存 | ◎ なし | ○ 少ない | △ | × 非同期の実行環境ごと入る |
| 4. 実装量 | △ JSON の読み書き（数百行）と LSP の枠（数百行）を書く | ○ | ◎ | ◎ |
| 4. 正しさの確かめ | ○ 扱う形が狭いので、テストで覆える | ◎ 広く使われている | ◎ | ◎ |
| 5. 後の段階 | ○ P1 では Sigil で JSON を書く。自前の Rust の実装の試験の事例を、Sigil の実装の試験に流用できる | ○ | ○ | ○ |

### 決定（推奨。判断 1・2 で所有者が決める）

**A** を推奨する。

- M6 で扱う LSP の要求は、`initialize`・`initialized`・`shutdown`・`exit`・`textDocument/didOpen`・`didChange`（全文の同期）・`didClose`・`textDocument/hover` と、送る通知の `textDocument/publishDiagnostics` だけである。
- 読み取る JSON は、LSP のクライアントが送るものに限られる。JSON の規格（RFC 8259）のすべての形（数・文字列のエスケープ・入れ子）は読むが、性能は求めない。
- 自前の JSON の読み取りは、次のテストで確かめる。
  - RFC 8259 の例と、壊れた入力（閉じない括弧、不正なエスケープ、先頭の 0 の数、制御文字）を拒むこと。
  - 書き出したものを読み戻すと同じ値になること。
  - 深い入れ子で、スタックを使い切らずにエラーにすること（深さの上限）。

### 理由

- 観点 3: 処理系の依存は今 Cranelift の 4 クレートだけで、所有者の承認を通している。M6 の範囲は狭く、依存を増やす利点が小さい。
- C・D は、M6 の要求の数に比べて大きい。D は非同期の実行環境（`tokio`）ごと入り、言語サーバーの 1 本の標準入出力には要らない。
- B は JSON の正しさの点で A より安心だが、`serde` は手続きマクロ（`serde_derive`）とその推移的な依存（`syn`・`quote`・`proc-macro2`）を連れてくる。

### 選ばなかった案と理由

- **B・C・D**: 上のとおり。ただし所有者が依存の追加を許す場合は、B が次の候補である（判断 1）。

## 決定 4: 言語サーバーの診断の範囲

- **起動**: `sigil lsp [--trust-base <モジュール>]...` で起動し、標準入出力で LSP を話す。`--trust-base` の意味は `sigil check` と同じとする（ADR 0018 の PR 3-0 で一覧のファイルを読むようになったら、言語サーバーも同じファイルを読む）。
- **検査の範囲**: 字句・構文（正規形の違反を含む）・型・効果・移動・借用の検査（`sigil check` と同じ）。実行（契約の実行時検査）はしない。
- **件数**: 文書ごとに最初の 1 件だけを返す。検査を最初の 1 件で打ち切る今の作りを変えない。
- **複数のファイル**: 開いた文書と同じディレクトリにあり、同じモジュールの宣言を持つ `.sigil` のファイルを合わせて検査する（`sigil check` に同じファイルを並べたのと同じ）。
  - 開いている文書はエディタの中身を、開いていない文書はディスクの中身を使う。
  - 構文解析を通らないほかのファイル（`examples/01-average` の `a-sexpr.sigil` のような、比較のために置いた別の表記の案）は、モジュールの宣言が読めないので合わせない。開いた文書そのものが構文解析を通らなければ、その構文エラーを返す。
  - 合わせた検査のエラーが別のファイルにあるときは、そのファイルの診断として返す（開いていなくても `publishDiagnostics` を送る）。
  - これは「モジュールの単位」（ADR 0018 の ADR 2-1）までの仮の決め方で、ADR 2-1 で改める。
- **送る時期**: `didOpen`・`didChange` のたびに検査し直し、診断を送る（エラーがなくなったら空の配列を送る）。
- **診断の欄**: `range`（決定 6）、`severity` は誤り（1）、`code` は `ErrorKind` の名前、`source` は `"sigil"`、`message` は日本語の文。
- **処理系の不具合**: 検査が Rust の panic を起こしたときは、言語サーバーを落とさず、`code` を `"InternalError"` とした診断を文書の先頭に返す（`std::panic::catch_unwind`）。

### 理由

- 2 件目以降のエラーを報告するには、各段のエラーからの立ち直り（構文の再同期、型の誤りの伝播の抑止）が要る。M6 の完了条件は「検査結果を診断として返す」で、件数を求めていない。立ち直りは P2 の IDE で、補完などと一緒に決める。
- 複数のファイル: `examples/04-effects` の `entry.sigil` は、1 つだけで検査すると名前が解決できない。サンプルを開いて誤りのない診断が返ることを M6 の完了条件で確かめるには、合わせた検査が要る。

## 決定 5: 仕様の表示（hover）

- 次の位置で `textDocument/hover` を受けたら、その関数の `text`（決定 1）を返す。返す形は `MarkupContent` の `plaintext` とする。
  - 関数・メソッドの宣言の、`fn` から本体の `{` の前まで（名前・引数・4 節の行）。
  - 同じモジュールの自由関数を、名前で呼んでいる箇所（`f(...)`）。
  - `型.名前(...)` の形で、同じモジュールのメソッドを呼んでいる箇所。
- 型・構造体・列挙型の宣言の名前の上では、その項目の `text` を返す。
- 値の上のメソッドの呼び出し（`x.m(...)`）と、標準ライブラリの関数は、M6 では返さない（`null`）。
  - 前者は、受け手の型を知るために検査を通す必要があり、検査が途中で止まった文書では返せないことがある。後者は、標準ライブラリが Rust の表で、`sigil spec` の出力を持たない。
  - どちらも、P1 の段階 3（標準ライブラリの Sigil 版）の後に加える。
- 呼び出しの箇所の名前の解決は構文だけで行い、構文が通れば型の誤りがあっても返す。

### 理由

- ADR 0006 の M6 は「関数にカーソルを置くと仕様を返す」で、宣言の上で返すのが最小である。呼び出しの箇所で返せると、AI と人間が呼ぶ先の契約をその場で知れるので、構文だけで解決できる範囲は入れる。
- `text` をそのまま返すので、`sigil spec` と同じであることが作りから成り立つ（観点 2）。

## 決定 6: 位置の扱い

- **終わりの位置**: `Span` に終わりを足さない。診断の `range` は、始まりの位置から、そこで始まる字句の終わりまでとする。言語サーバーが、その行を字句解析して長さを求める。字句が取れない位置（ファイルの終わりなど）は、1 文字の範囲にする。
- **列の数え方**: LSP の既定は UTF-16 の符号単位で数える。処理系の列は文字数で数える。
  - 言語サーバーは、文書の中身を使って、文字数と UTF-16 の符号単位を相互に変換する。
  - `initialize` でクライアントが `positionEncoding` に `utf-32` を挙げた場合は、それを選び、変換をしない（LSP 3.17）。
  - ASCII でない文字は文字列のリテラルとコメントの中にだけあるので、変換が値を変えるのはその行だけである。テストでは、文字列に日本語と絵文字（UTF-16 で 2 単位）を含む行の後ろのエラーで確かめる。

### 理由

- `Span` に終わりを足すと、字句解析器から検査器までのすべての `Span` を作る箇所を直すことになる。M6 の診断には、字句 1 つの範囲で足りる。範囲を式全体に広げることは、P2 の IDE で決める。

| `lsp_utf16_positions` | 同 | 日本語と絵文字の文字列のリテラルの後ろにある誤りの範囲が、UTF-16 の符号単位で正しい。`utf-32` を挙げたクライアントには文字数で返す |

| `lsp_internal_error_isolated` | 同 | テスト用の差し込み口で検査に panic を起こさせると、`InternalError` の診断が返り、言語サーバーは続けて次の要求に応える |

- テストは `cargo test` の中で動き、エディタを要しない。CI の設定は変えない。

## 実装の手順

1. **PR1: JSON と機械向けの形式**。`src/json.rs`（判断 1 の結論による）、`sigil spec --json`、`sigil check --json`。`spec_json_*`・`check_json_kinds`。
2. **PR2: 言語サーバーの枠と診断**。`sigil lsp`、`Content-Length` の枠の読み書き、`initialize`〜`exit`、全文の同期、決定 4 の診断、決定 6 の位置の変換。`lsp_samples_no_diagnostics`・`lsp_error_diagnostic`・`lsp_utf16_positions`・`lsp_shutdown`・`lsp_internal_error_isolated`。
3. **PR3: hover と M6 の完了**。決定 5、`lsp_hover_matches_spec`。ADR 0006 に M6 の完了（P0 の完了）を記録する。

## 人間の判断が要る点

### 判断 1: JSON を読み書きするクレートを加えるか

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| J1: 加えない（推奨） | 自前の `src/json.rs` | 依存が増えない。供給元の危険がない | 数百行を書いて保守する。読み取りの誤りはテストで覆うしかない |
| J2: `serde` と `serde_json` | 型からの導出で読み書きする | 広く使われ、正しさの実績がある。実装量が小さい | 手続きマクロとその推移的な依存（`syn`・`quote`・`proc-macro2` など）が入る |
| J3: `serde_json` だけ（`serde_json::Value` で扱い、導出を使わない） | 値の木を手で組み立てる | 読み取りの正しさは J2 と同じ | `serde_json` が `serde` に依存するので、J2 と依存はほぼ変わらない |

### 判断 2: LSP のクレートを加えるか

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| L1: 加えない（推奨） | 自前の枠と、M6 の 8 つの要求・1 つの通知だけ | 依存が増えない。扱う要求が少ない | LSP の型を自分で書く。要求が増える P2 で書く量が増える |
| L2: `lsp-server`・`lsp-types` | 同期の枠と、LSP の型の定義 | LSP の型の誤りがない。P2 で機能を足しやすい | J2 が前提になる。`crossbeam-channel` などが入る |
| L3: `tower-lsp` | 非同期の枠組み | 機能が多い | `tokio` を含む多数の依存。M6 には大きすぎる |

- 推奨は J1・L1 の組である。L2 を選ぶ場合は、J2 も選ぶことになる。
- 判断が出るまで、PR1 を始めない。どれを選んでも、決定 1・2・4・5・6 と完了条件は変わらない（変わるのは `src/json.rs` の有無と、その単体テストだけである）。

### 判断の要らない点

- CI の変更: 要らない。テストは `cargo test` の中で `sigil lsp` を子のプロセスとして起動する。
- 秘密情報・認証・権限・データベース: 関わらない。

## 根拠の限界と再検証

- 候補の案出しと採点を、同じ者（Claude）が行っており、偏りがありうる。
- 決定 3 の自前の実装の行数（JSON・LSP でそれぞれ数百行）は見積もりで、書いていない。PR1・PR2 で、どちらかが 800 行を超えたら、判断 1・2 を所有者に問い直す。
- 決定 4 の「最初の 1 件だけ」で、AI が直す作業が遅くならないかは確かめていない。P1 の段階 2 で、1 回の検査で 1 件しか直せないために検査をくり返した回数が目立つ場合は、エラーからの立ち直りを P2 より前に検討する。
- 決定 1 の欄は、今の `sigil spec` の行に合わせて決めた。P1 でトレイト・モジュールの公開の範囲が入ると欄が増える。欄を足すときは `format` を上げない（決定 1）が、意味を変える必要が出たら上げる。
- 次を計測する。
  - PR1・PR2 の自前の実装の行数。
  - `sigil check --json` の `kind` ごとの出現の数（P1 の間、AI が書いたコードで多い誤りの種類を知るため）。
