# 0043: P2-5 仕様レビュー IDE

- **状態**: 提案（typesafe-ai の正式判定は実施済み。末尾の「正式判定の記録」を参照。Codex Cloud レビュー受領済み）
- **日付**: 2026-11-17（JST）
- **対象**: [Issue #567](https://github.com/goodnasubi/sigil/issues/567)、レーン E

## 背景

[ADR 0038](0038-p2-scope.md) の最終段 P2-5（仕様レビュー IDE）を、先行する [ADR 0039](0039-p2-1-javascript-output.md)（JS 出力）、[ADR 0040](0040-p2-2-ui-model.md)（UI 記述モデル）、[ADR 0041](0041-p2-3-fullstack.md)（フルスタック）、および [ADR 0042](0042-p2-4-wasm-output.md)（WebAssembly 出力）の上に具体化する。P2-5 は、Sigil で書かれた最初の大きな Web アプリケーションであり、「AI がコードを書き、人間は仕様だけをレビューする」（[ADR 0001](0001-vision-and-scope.md)）という言語の根本理念を具現化する作業環境である。

人間は汎用のソースコード編集や手動プログラミングを行うのではなく、AI が生成・更新した仕様（構文・型・契約・効果）をレビューし、検査と検証の結果を確認する。AI のための作業窓口としては既存の言語サーバー（[ADR 0019](0019-m6-machine-spec-and-language-server.md) の LSP）を維持し、IDE は人間が直感的に仕様とその変化を把握できる画面を提供する。

起草の基準は `main` の `7374cdc`。ADR 番号 0043 は main のファイル・索引・オープン PR・リモートブランチで未使用であることを確認した。本 PR は本 ADR の新規作成と索引追加のみを行う。以下に定める画面構造、API、CLI、データ形式は実装に向けた決定であり、現行の処理系や `sigil spec` に追加された機能を記述するものではない。

## 選択肢と決定

| 判断 | 採用する案 | 他案を採用しない理由 |
|---|---|---|
| アプリケーション構成 | P2-3 フルスタック構成の Web アプリ。クライアントは P2-2 UI（JS／Wasm）、サーバーは P1 のネイティブ出力（`std.web`） | コンパイラ処理系全体をブラウザ（Wasm）へ移植すると、ファイルシステムアクセスや信頼基盤の制約が大きく、起動・実行負荷も過大になる。クライアント／サーバー分離により単一コンテナで完結させる |
| 画面の構成と順序 | 1. 既存の `sigil spec --json` を用いた仕様表示 → 2. 二つの版の仕様差分 → 3. 検証結果の確認 | 汎用エディタ（コード編集・端末・Git 操作）を最初から目指すと「人間は仕様だけをレビューする」理念と乖離し、範囲が発散する |
| 仕様差分のモデル | 利用者が指定した 2 つのワークスペース（スナップショット）の構造化比較。モジュール・項目・型・契約・効果の追加／削除／変更を示す | Git そのものの履歴管理やブランチ操作の実装は P4 に属する。初版で Git 内部構造に依存すると責務が過大になる。名前変更も初版は削除と追加で十分である |
| 検査・検証結果の提示 | 入力の版・対象・実行された検査と厳密に結び付ける。型検査成功と契約証明済みを混同せず、未検証・失敗・反例・証明済みを明確に区別する | 型検査成功を「安全・証明済み」と過剰表示すると、契約の未検証や反例の見落としを招き、人間による仕様レビューの信頼性を損なう |
| バックエンドの安全境界 | サーバー起動時に明示的に許可されたワークスペースのみを読み込み、ブラウザから任意のパス指定・コマンド実行・`--trust-base` の追加を拒否する | Web インターフェイスからサーバー上の任意ファイル読み込みや任意コマンド実行を許すと、重大なセキュリティ侵害となる（ADR 0020, ADR 0027 準拠） |
| AI 窓口と持ち越し機能 | 既存 LSP（ADR 0019）の診断・仕様参照を維持。補完・定義参照・名前変更等の拡張や、推測による契約式の自然言語訳は初版の必須から外す | ADR 0008／0019 からの持ち越し事項を初版に詰め込むと P2 の完了が遅延する。自然言語訳の推測で仕様の意味が変わる危険を排除する |

正式判定の確率は意味の正しさの証明ではない。採用理由は、既存 ADR の役割分担と安全原則を維持し、単一コンテナ配布物として人間と AI の協調を実証できることにある。**本 ADR の正式判定は実施済み**で、後の節に結果と扱いを記録する。

## 決定 1: 画面構成とレビュー導線

仕様レビュー IDE は、以下の 3 つの主要画面（ビュー）を順に提供し、人間がコードではなく仕様の変化と検証状態を把握できるようにする。汎用のテキストエディタ、端末画面、拡張機能機構は初版に含めない。

### 1. 仕様表示（Screen 1: Spec Viewer）
- 既存の `sigil spec --json` が出力する `text` と構造化 JSON データをそのまま利用して画面を構成する。IDE 内部で独自の仕様解析器や別形式の仕様抽出器を作り直さない。
- モジュール階層（モジュールツリー）、公開項目（型、定数、関数）、関数の入出力型、効果宣言、および事前・事後条件（`requires`, `ensures`）を一覧・詳細表示する。
- 契約式は既存の正規形の式（例: `result >= 0`）と日本語の定型文を表示し、推測による自然言語訳で意味を変えない。

### 2. 仕様差分（Screen 2: Spec Diff）
- 利用者が指定した二つのワークスペースの版（スナップショット A と B、例えば変更前と変更後）の仕様を構造的に比較する。
- 差分表示の単位:
  - モジュールの追加・削除
  - 項目の追加・削除
  - 型定義の変更（フィールドの増減、型の変更、篩型の不変条件の変更）
  - 関数のシグネチャ変更（引数・戻り値の変更）
  - 効果宣言の変更（許可効果の追加・削除）
  - 契約式の変更（事前条件・事後条件の追加・削除・変更）
- テキストの行単位の diff ではなく、意味的な仕様項目の「追加」「削除」「変更」としてハイライト表示する。
- 名前の変更（リネーム）は、初版では「旧項目の削除」と「新項目の追加」として扱い、ヒューリスティクスによる同一性推測は行わない。

### 3. 検証結果の確認（Screen 3: Verification Status）
- 指定された版の各モジュール・項目に対して実行された検査・検証の結果を提示する。
- 各項目について、実行された検査の種類（型検査、効果検査、契約の静的証明、反例探索）と結び付けて状態を表示する。
- 画面上の表示状態を以下のように厳密に区別する:
  - **証明済み（Verified）**: ソルバーまたは検証系により契約式が静的に証明された。
  - **型検査成功（Type Checked）**: 型および効果の完全一致検査に合格した（契約式の証明ではないことを明示）。
  - **失敗（Failed）**: 型検査エラー、または契約の反証・不整合が検出された。
  - **反例あり（Counter-Example Found）**: 契約に違反する具体的な反例入力が提示された。
  - **未検証（Unverified）**: 対象の検証器が未対応、未実行、あるいはスキップされた。
  - **陳腐化（Stale）**: ソースが変更され、前回の検査結果から無効化された状態。
- **型検査の合格をもって「証明済み」と表示してはならない**。対応していない検証は「未検証」として正直に示す。

## 決定 2: ワークスペースの扱いと仕様差分

IDE は複数の版の仕様を比較するために「ワークスペースのスナップショット」を扱う。

### スナップショットの入力モデル
- サーバー起動時に許可された基準ディレクトリ配下において、相対パスで指定される 2 つのディレクトリ（例: `workspace/v1` と `workspace/v2`）を比較対象とする。
- Git そのもののリポジトリ操作（コミット追跡、ブランチ切替、マージ等）の実装は P4 に属するため、初版ではファイルツリーのスナップショット（ディレクトリ）を比較単位とする。Git コマンドを内部で自動呼び出しする機能は初版の必須としない。

### 仕様差分の抽出
- サーバーは両スナップショットに対して `sigil spec --json` 相当の解析を実行し、得られた構造化ツリーの完全一致比較を行う。
- 差分の出力構造（`SpecDiff`）:
  - `added_modules`: 新規モジュール一覧
  - `removed_modules`: 削除されたモジュール一覧
  - `modified_modules`: 変更のあったモジュール（内部のアイテム差分 `added_items`, `removed_items`, `modified_items` を含む）
  - 各アイテムの差分には、変更前後の型、効果、契約の比較情報を含む。

## 決定 3: 検査・検証結果の結び付けと状態モデル

検査・検証の結果は、以下の 4 つ組で一意に結び付けられる。

```text
(SnapshotId, ModulePath, ItemName, CheckKind) -> CheckResult
```

- `CheckKind`: `TypeCheck`, `EffectCheck`, `ContractVerification`
- `CheckResult`:
  - `status`: `Passed`, `Failed`, `CounterExample`, `Unverified`, `Stale`
  - `diagnostics`: エラーメッセージ、ソース位置、違反した契約式
  - `counter_example`: 反例入力が存在する場合の具象値表現（例: `{ x: -1 }`）
  - `timestamp`: 検査が実行された時刻

古い結果（Stale）と最新の結果、未実施と成功、型検査成功と契約証明済みを混同してはならない。画面上でもアイコンやバッジの色・ラベルを明確に分ける。

## 決定 4: バックエンドサーバー、安全境界、実行上限

IDE バックエンドは P2-3 フルスタック構成のサーバー（P1 ネイティブ出力、`std.web`）として単一バイナリで提供される。

### ワークスペースの安全境界
- サーバー起動時の引数 `--allow-dir <path>` で許可ディレクトリを明示する（複数指定可）。
- サーバーは許可ディレクトリ配下のファイルのみを読み込む。
- クライアント（ブラウザ）から送信されるパス文字列に対して厳格な検証を行う:
  - 親ディレクトリ参照（`..`）の禁止。
  - 絶対パス指定の禁止（許可ディレクトリからの相対パスのみ）。
  - シンボリックリンクによる許可範囲外への脱出を拒否。
  - 無効なパスや範囲外アクセスは即座に `403 Forbidden` または固定のエラー応答を返す。

### コマンドと信頼基盤の隔離
- ブラウザからの任意のシステムコマンド実行（シェル実行）を一切許可しない。
- ブラウザから `--trust-base` の追加や変更を要求することを許さない。コンパイラの実行時オプションはサーバーの起動構成で固定される。
- 初版の IDE はレビュー専用とし、ブラウザからの任意のファイル書き込み・保存 API は提供しない（読み取り専用の安全なレビュー環境）。

### 橋渡し方式・並行実行と入出力の上限
サーバーの枯渇攻撃や過負荷を防ぐため、以下の静的上限を設ける。
- **橋渡し方式**: サーバーは同一バイナリ内のライブラリ呼び出し、または同一コンテナ内のローカルプロセス呼び出しによりコンパイラおよび言語サーバー核を利用する。
- **並行解析数上限**: 同時に実行できるコンパイラ／仕様解析処理は最大 4（CPU コア数に応じて起動時に設定可能）。上限超過時はキューイングせず即時エラー（`429 Too Many Requests` または `503 Service Unavailable`）を返す。
- **解析タイムアウト**: 1 回の仕様解析・検証要求は 30 秒で打ち切り（超過時は `Timeout` 診断）。
- **レスポンス上限**: JSON API の応答サイズは最大 16 MiB（ADR 0041 の上限に準拠）。
- **ワークスペース走査上限**: 1 ワークスペースあたりのファイル数上限 1,000 件、総バイト数上限 50 MiB。

## 決定 5: AI 向け窓口（LSP）と持ち越し事項の境界

人間が IDE 画面で仕様をレビューする一方で、AI エージェントがコードを編集・検証するための窓口として、既存の言語サーバー（[ADR 0019](0019-m6-machine-spec-and-language-server.md)）を独立して維持する。

### 既存 LSP の維持
- 標準入出力を用いた LSP サーバー（`sigil lsp`）は引き続き動作し、診断（エラー・警告）、仕様参照（`sigil/spec`）、契約・効果情報の提供を行う。
- IDE バックエンドと LSP は、コンパイラ核（`check`, `spec`）を共通のライブラリとして共有する。

### 持ち越し機能の整理と初版の範囲外
以下の機能は初版の必須範囲から明確に外す。
1. **LSP 拡張機能（ADR 0019 からの持ち越し）**:
   - 入力補完（completion）、定義ジャンプ（definition）、シンボル名変更（rename）、複数診断の集約、ファイル変更監視（file watching）の拡張は初版には含めない。
2. **契約式の自然言語訳（ADR 0008／0019 からの持ち越し）**:
   - 契約式（`requires`, `ensures`）の自由な自然言語訳（推測による日本語化）は行わない。
   - 既存の正規形の式（例: `result > 0`）と定型的な日本語テンプレート（例: `戻り値 > 0`）のみを表示し、AI やヒューリスティクスが推測で意味を変質させるリスクを排除する。正確性を担保できる翻訳規則は将来の別 ADR で定める。

## 決定 6: 初版の対応集合と技術的一覧（P2-1 / ADR 0039 準拠）

P2-5 の IDE アプリケーション（クライアントおよびサーバー）を構築するために使用する構文・型・標準操作、およびシステム境界の仕様を、[ADR 0039 決定 1〜5](0039-p2-1-javascript-output.md) と同一の形式で列挙する。

### 構文と型の許可一覧

| 区分 | 初版に含むもの |
|---|---|
| 宣言 | `module`・`targets`（`browser`／`server`／`bare`）・`use`・公開範囲、関数と仕様 4 節、構造体・列挙型・組、総称型／総称関数、篩型 |
| 文 | `let`／`let mut`、束縛・組分解、局所／フィールド／借用先への代入、呼び出し文、`return`、`if`／`else`、`while`、文の `match` |
| 式 | 整数・小数・文字列・真偽値・組・一覧のリテラル、構造体／列挙型の構築、フィールドアクセス、関数／メソッド呼び出し、式の `match`、`?`、`&`／`&mut`、クロージャと `move` |
| 演算 | 数値の `+ - * / %` と単項 `-`、比較、短絡する `&&`／`||` と `!`、String の連結、Int のビット演算（`&`／`|`／`^`／`~`／`<<`／`>>`） |
| 型 | `Int`・`Float`・`Bool`・`Unit`・`String`・`Bytes`・`List<T>`・`Option<T>`・`Result<T,E>`、利用者の構造体／列挙型・組・篩型・借用・関数型、IDE 固有の DTO 型（`SpecTree`, `SpecDiff`, `CheckResult` 等） |
| 契約 | `requires`・`ensures`・`result`・`old(e)`、篩型の前提。静的に証明されない条件は実行時にも検査する |

### 標準操作の許可一覧

IDE アプリケーション（ブラウザ側およびサーバー側）が依存する標準ライブラリの操作一覧。

- **組み込み**: 明示的な `.clone()`（`Copyable` 規則を遵守）。
- **数値操作**: `to_float`、`to_int`、`Int.min_value`、回転・シフト演算。
- **文字列操作**: `String.len`／`is_empty`／`trim`／`lines`／`parse_int`／`as_bytes`。
- **コレクション操作**: `List.new`／`push`／`get`／`get_mut`／`len`／`is_empty`／`map`／`find`／`filter`。
- **Option / Result**: `is_some`／`is_none`／`unwrap_or`／`map`／`ok_or`、`is_ok`／`is_err`／`map_err`。
- **Bytes 操作**: `Bytes.new`／`len`／`is_empty`／`get`／`set`／`push`／`slice`／`concat`／`to_string_utf8`。
- **JSON 操作**: `std.json` による DTO の直列化・逆直列化（RFC 8259 準拠、深さ・サイズ上限あり）。
- **クライアント通信（ブラウザ）**: `client.fetch`（効果 `net.client`、ADR 0041 準拠）。
- **サーバー操作（ネイティブ）**: `std.http`（効果 `net.server`）、ファイル読込（効果 `fs.read`）、プロセス呼出（効果 `env` または限定された内部プロセス呼出）。

### 数値表現

- `Int`: 符号付き 64 ビット整数（`-2^63`〜`2^63-1`）。ブラウザ側（JS: BigInt、Wasm: i64）およびサーバー側（x86_64: 64 ビットレジスタ）で完全一致。桁あふれ・ゼロ除算・最小値除算は SIR 検査算術を経て安全に停止する。
- `Float`: IEEE 754 binary64。NaN・無限大・負のゼロを維持し、境界での丸めを統一する。

### 文字列 ABI とデータ境界

- `String`: 内部表現は妥当な UTF-8（サーバー／Wasm）またはスカラー列 JS string（JS）。
- ブラウザ／サーバー通信境界（HTTP JSON）:
  - すべての文字列は UTF-8 として検証され、不正サロゲートや不正バイト列は境界で拒否される。
  - HTML 表示において、仕様の識別子やテキストは安全な DOM 生成（`UiNode::text`）によりエスケープされ、XSS を防止する（ADR 0040 準拠）。

### 所有値の破棄と異常停止

- SIR の `Drop`／`Move`／`cleanup` 規則に完全準拠する。
- 画面遷移や状態更新に伴い、前回の UI 状態およびキャッシュされた仕様ツリーは規則に従って即座に破棄される。
- サーバー側での解析エラーやタイムアウトは、未処理の例外とせず、型安全な `Result` または固定エラーレスポンスとしてクライアントへ返却される。

### ホスト呼び出しと境界

- **クライアント側**:
  - DOM アダプター操作（`createElement`, `setTextContent` 等）、イベントリスナー登録。
  - 同一オリジン HTTP 要求の発行（`fetch`）。
  - ログ出力（`console.log`、効果 `console`）。
  - 任意の外部 JS や未許可 Web API の呼び出しは行わない。
- **サーバー側**:
  - 許可ディレクトリ配下に限定されたファイル読み込み。
  - コンパイラ・仕様抽出器の内部呼び出し。
  - HTTP 接続の待受と静的資産配信。

### CLI

IDE を起動・ビルドするための CLI コマンド体系を定める。

```text
# IDE サーバーの起動
sigil ide [--allow-dir <dir>]... [--port <port>] [--host <host>] [--client <js|wasm>]

# IDE 配布物（フルスタック）のビルド
sigil build --target fullstack --client <js|wasm> src/ide/main.sigil -o dist/ide
```

- `--allow-dir <dir>`: レビュー対象としてアクセスを許可するワークスペースのディレクトリ。未指定時はカレントディレクトリのみを許可。
- `--port <port>`: 待受ポート番号（既定: 8080）。
- `--host <host>`: 待受ホスト（既定: 127.0.0.1、ローカルホスト限定）。
- `--client <js|wasm>`: クライアント成果物の出力形式を選択（既定: `js`）。Wasm を指定した場合は `.wasm` と `.mjs` が配信される。

## 決定 7: 適合の確かめ方と完了条件

P2-5 の完了は、以下の検証がすべて満たされることによって確認される。

| 比較・検証項目 | 確認内容 |
|---|---|
| 単一 Docker 配布物 | P1 の OCI/Docker コンテナイメージとしてビルド・起動でき、追加の外部サービス（Node.js や外部 DB 等）なしで単独起動すること |
| 画面 1: 仕様表示 | ブラウザからアクセスし、ワークスペースの `sigil spec --json` の内容（モジュール階層、型、関数、契約、効果）が正確に表示されること |
| 画面 2: 仕様差分 | 変更前後の 2 つのスナップショットを指定し、モジュール・型・関数・契約・効果の追加／削除／変更が構造的にハイライト表示されること |
| 画面 3: 検証結果 | 型検査合格、契約証明済み、反例あり、未検証、陳腐化の各状態が正しく識別され、型検査合格が証明済みと偽装されないこと |
| クライアント両出力 | クライアントとして JS 出力（`--client js`）と Wasm 出力（`--client wasm`）の両方を選択でき、同一の表示・操作が行えること |
| AI 向け LSP の維持 | IDE 稼働中も既存の `sigil lsp` による診断および仕様参照が通常通り動作すること |
| 安全境界の防御 | 許可範囲外のパス指定、パストラバーサル（`..`）、不正なコマンド注入がすべて `403` またはエラーとして即座に拒否されること |
| 並行・上限の遮断 | 並行要求上限、タイムアウト、レスポンス上限を超過した要求が正しく遮断され、サーバーがクラッシュしないこと |
