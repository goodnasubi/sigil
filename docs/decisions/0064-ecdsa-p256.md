# 0064: std.crypto の ECDSA P-256 署名

- **状態**: 提案
- **日付**: 2026-11-25（JST）
- **対象**: [Issue #752](https://github.com/goodnasubi/sigil/issues/752)、レーン E

## 背景

TLS 1.3 のサーバーは `CertificateVerify` で証明書に対応する秘密鍵の保有と、ハンドシェイクの内容を署名で示す。[ADR 0063](0063-shield-tls.md) は段 3 の前提として、SHA-256 と RFC 6979 の決定的な nonce を使う ECDSA P-256 署名を段 0 に置いた。証明書の読み込み時には、秘密鍵から公開鍵を導いてリーフの公開鍵と照合する。

## 選択肢

| 案 | 利点 | 欠点 |
|---|---|---|
| `std.crypto` に用途別の鍵型・署名型を設け、P-256/SHA-256 に固定する | 鍵や方式の取り違えを型で防げる。公開ベクタと定数時間検査を標準部品に集約できる | 型と厳密な入出力変換が増える |
| `Bytes` と `Secret` を直接受け取り、曲線やハッシュを引数で選ぶ | 別の方式を追加するときに入口を再利用しやすい | 検査と組み合わせの保証が実行時になり、初期の実装範囲が広がる |
| TLS 終端に専用の署名を組み込む | TLS の呼び出し方だけを扱えばよい | 暗号の検査を標準部品から分散させ、ADR 0063 が定めた段 0 の境界がなくなる |

## 決定 1 — 公開 API

最初の案を採用する。[ADR 0024](0024-crypto-primitives.md) と [ADR 0058](0058-tls13-crypto-primitives.md) に合わせ、鍵・署名は内部表現を公開しない用途別の型とする。署名の外部形式は TLS にそのまま渡せる DER とする。固定幅の連結形式を選ぶ案では TLS 側にも符号化が必要になる。ダイジェストを受け取る案では呼び出し側がハッシュの選択と適用回数を管理する必要がある。次はシグネチャの設計であり、各関数は `effects none` とする。

| 入口 | 契約 |
|---|---|
| `EcdsaP256PrivateKey.from_secret(key: Secret) -> Result<EcdsaP256PrivateKey, EcdsaP256Error>` | 符号なしビッグエンディアンの 32 バイトを消費する。P-256 の基点の位数を `n` として、`1 <= d < n` の値だけを受理する。失敗時も入力を破棄してゼロ化する |
| `EcdsaP256PublicKey.from_bytes(encoded: &Bytes) -> Result<EcdsaP256PublicKey, EcdsaP256Error>` | SEC 1 の非圧縮点（先頭 `0x04` に X と Y の各 32 バイトが続く 65 バイト）を受け取る。座標が P-256 の体の素数 `p` に対して `0 <= 座標 < p` にあり、無限遠点でなく、P-256 の曲線式を満たすことを確かめる。余因子は 1 なので、受理した点は基点の部分群に属する |
| `ecdsa_p256_public_key(private: &EcdsaP256PrivateKey) -> EcdsaP256PublicKey` と `EcdsaP256PublicKey.to_bytes(self: &EcdsaP256PublicKey) -> Bytes` | 検証済みの秘密鍵から公開鍵を導出する。出力は同じ 65 バイトの非圧縮形式とし、TLS 側の SPKI の点と照合できる |
| `EcdsaP256Signature.from_der(encoded: &Bytes) -> Result<EcdsaP256Signature, EcdsaP256Error>` と `EcdsaP256Signature.to_der(self: &EcdsaP256Signature) -> Bytes` | `r` と `s` を ASN.1 DER の `SEQUENCE` 内の 2 個の正の `INTEGER` で表す。最短の長さ・整数表現を要求し、余分なデータや `1 <= r, s < n` を満たさない値を拒否する。出力は最大 72 バイトとする。[RFC 8446 §4.2.3](https://www.rfc-editor.org/rfc/rfc8446#section-4.2.3) |
| `ecdsa_p256_sign(private: &EcdsaP256PrivateKey, message: &Bytes) -> Result<EcdsaP256Signature, EcdsaP256Error>` | メッセージを SHA-256 でハッシュし、決定 2 の方式で署名する |
| `ecdsa_p256_verify(public: &EcdsaP256PublicKey, message: &Bytes, signature: &EcdsaP256Signature) -> Bool` | 同じ SHA-256 でハッシュして ECDSA の検証を行う。正しく符号化されていても照合に失敗すれば `false` を返す |

`EcdsaP256Error` は `InvalidPrivateKey`、`InvalidPublicKey`、`InvalidSignature`、`SigningFailed` を持つ。秘密由来の値や失敗した候補はエラーに載せない。秘密鍵は `Secret` を所有し、操作時に借用する。表示・公開バイト列への変換は提供しない。

TLS 側は PEM・PKCS#8・SEC1 の秘密鍵コンテナと証明書を処理し、得られたスカラーを `Secret` として渡す。`CertificateVerify` では TLS 側が 64 個の `0x20`、文脈文字列 `TLS 1.3, server CertificateVerify`、1 個の `0x00`、合意した暗号スイートのトランスクリプトハッシュを連結し、そのメッセージ全体を渡す。署名用の SHA-256 はスイートのハッシュ方式にかかわらず `std.crypto` がメッセージに 1 回適用する。[RFC 8446 §4.4.3](https://www.rfc-editor.org/rfc/rfc8446#section-4.4.3)

## 決定 2 — nonce と定数時間

nonce はメッセージの SHA-256 ダイジェストと秘密鍵から HMAC-SHA-256 を用いて生成する。変換、候補の範囲検査、棄却後の更新は [RFC 6979 §3.2–3.4](https://www.rfc-editor.org/rfc/rfc6979#section-3.2) に従う。剰余で範囲内へ丸める方式や呼び出し側が nonce を渡す入口は設けない。署名の `s` は low-S に正規化せず、検証でも low-S を要求しない。

RFC の再試行をそのまま実装すると、秘密由来の棄却回数が実行時間に出る。1 候補に限ると、RFC 6979 が次の候補で成功する入力をより多く拒否する。毎回 4 候補分を固定の演算列で処理し、候補の範囲違反や `r = 0`・`s = 0` をマスクで扱い、最初の有効な組を選ぶ。有効な組を得た後も、棄却時と同じ状態更新と残りの候補の演算を行う。範囲外の候補の演算にはマスクで固定の有効なスカラーを与え、署名の選択からは除く。4 候補を使い切ったときは署名を返さず、署名生成失敗を返す。成功時は RFC 6979 の候補順と同じ署名になる。上限を持たない RFC 6979 の処理がさらに候補を試す入力でも、本 API は失敗を返す。TLS 側は署名生成失敗を受けた場合にハンドシェイクを終了する。

[ADR 0020](0020-p1-security-addendum.md) 決定 1 の R1〜R6 と ADR 0058 決定 3 を適用する。秘密鍵、nonce、HMAC 状態、秘密スカラーの点演算・逆元計算と署名確定前の中間値は秘密として追跡する。署名対象メッセージの長さは公開とし、検証は公開鍵・メッセージ・署名を扱う。秘密に依存する分岐、早期終了、ループ回数、添字・アドレス、除算・剰余、非定数時間関数への引き渡し、ログへの出力を禁じる。スカラー倍算・逆元計算の演算列を固定し、例外的な点を含む経路も同じ規則に従う。インポートで公開できるのは長さと最終的な受理結果だけとする。署名生成・鍵導出で公開できるのは確定した署名・公開鍵と、署名生成の最終結果だけとする。DER 符号化は署名の公開後に行う。秘密を保持する鍵と作業領域は成功・失敗の両経路で破棄時にゼロ化し、コンパイラの一時値やレジスタに関する消去の限界を実装 PR に記録する。

## 実装の完了条件

| 項目 | 確認方法 |
|---|---|
| 公開ベクタ | [RFC 6979 付録 A.2.5](https://www.rfc-editor.org/rfc/rfc6979#appendix-A.2.5) の P-256/SHA-256 の `sample`・`test` について、公開鍵座標、内部テストの `k`、署名の `r`・`s` を期待値と照合する。SIR 評価器とネイティブ出力で実行する |
| 境界と相互運用 | 独立実装で得た公開鍵・DER 署名の固定ベクタを出典とともに置き、符号化と検証を照合する。鍵の長さ違い・`d = 0`・`d >= n`、範囲外座標・曲線外点、負の整数・余剰ゼロ・切り詰め・末尾データ、`r/s = 0`・`r/s >= n` を拒否する。メッセージ・鍵・署名の変更で検証が失敗する。内部テストで nonce の範囲違反、`r/s = 0`、全候補棄却を通し、最初の有効な候補の選択と失敗時の出力を確かめる |
| 定数時間の静的検査 | `ct_rules_static` と `ct_rules_clif` に秘密鍵取り込み・公開鍵導出・署名生成と、秘密を扱う全補助関数を登録する。秘密に依存した違反の検出、呼び出し先までの検査、生成コードでの秘密領域のゼロ化を確認する。既存検査で追えない経路があれば先に検査を拡張する |
| タイミング計測 | ネイティブの秘密鍵取り込み・鍵導出・署名を `ct_measure` で測る。同一実行ファイル・同一の公開入力で固定鍵群と変動鍵群を比較する。署名生成の計測は固定長の内部表現を境界とし、公開後の DER 符号化を含めない。対象の Welch の t 値の絶対値が 4.5 未満、陽性対照が 4.5 以上であることを確認し、CPU・最適化条件・試行数・t 値・検出感度を記録する。測定結果は静的検査と合わせて評価する |

## 影響と適合の限界

本 ADR が扱うのは P-256（`secp256r1`）の ECDSA と SHA-256、TLS 署名方式 `ecdsa_secp256r1_sha256` を支える暗号部品である。鍵交換の P-256 ECDH は段 6 の前に別の ADR と PR で扱う。他の曲線・ハッシュ、RSA・EdDSA、圧縮点、署名の固定幅連結形式、鍵の生成、証明書チェーン検証は範囲外とする。TLS 1.3 全体の適合範囲は ADR 0063 決定 1.1 に従う。

起草はレーン E。実装は本 ADR の承認後にレーン D2 の別 PR で行う。TLS 側の `CertificateVerify` の接続と相互運用は ADR 0063 の段 3 で検証する。
