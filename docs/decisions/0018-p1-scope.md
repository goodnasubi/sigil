# 0018: P1 の範囲・順序・PR の分け方と、P0 から持ち越した項目の扱い

- **状態**: 提案（2026-10-26）。所有者の判断を求める点は「人間の判断が要る点」の判断 1〜8（判断 6 は 6a・6b・6c の 3 つに分けた）にまとめた。判断が出るまで、その判断に依る PR は始めない。

## 背景

[ADR 0005](0005-long-term-goals.md) は P1 を「サーバーと Docker コンテナでのリリース（G5）、Spring の置き換え（G10）」とし、成果物を次のとおりとした。

- HTTP サーバーのライブラリ。
- サーバーアプリケーションのフレームワーク（ルーティング・設定・入力検証・データベース接続・認証）。
  - データベース接続は、PostgreSQL などの通信方式を Sigil で実装して行う（既存のライブラリは使わない）。
  - Spring の依存性の注入は、効果の宣言とテスト用の実行環境での差し替え（[ADR 0004](0004-effects.md)）で一部を担う。
- Docker で動くコンテナイメージを作る道具（OCI 形式）。
- ネイティブ出力は Linux（x86-64）を最初の対象にする。

これまでの ADR は、次のことを「P1 の範囲を決める ADR」（本 ADR）に送った。

- [ADR 0006](0006-p0-scope-and-bootstrap.md) の「置き換えの時期」:
  - 暫定の Rust 製ランタイムを、Sigil で書いた信頼基盤のモジュールに置き換える。
  - 置き換えを P1 の完了条件に含め、P1 の完了までに行う。
  - 暫定ランタイムは、ADR 0005 の方針（標準ライブラリとランタイムに既存言語のライブラリを持ち込まない）の期限付きの例外である。
- [ADR 0007](0007-concurrency-model.md):
  - P1 の段階分けを本 ADR で決める。ADR 0007 は (P1-a) SIR の評価器に単一スレッドの実行割り当てとテスト用の実行環境の差し替え、(P1-b) ネイティブ出力に状態機械の変換と複数の OS スレッドの実行割り当て、の順を前提にした。
  - サーバーで 1 件の要求の契約違反をどう隔離するかを、本 ADR で検討する。
- [ADR 0011](0011-type-system-scope.md): 利用者のトレイト、関数の型をフィールド・戻り値に置くこと、`Bytes` を P1 の前に決め、本 ADR で表に加える。
- [ADR 0015](0015-m5-native-output.md) の「M5 の完了の記録」と「根拠の限界と再検証」:
  - ネイティブ出力は文字列とパスを解放しない（PR5 の注記）。
  - `runs_in_scratch_container` は手で実行するだけで、CI に入っていない。
  - M5 の完了後に計測する 3 つの数（食い違いの数、`m3_drop_limits.rs` の順序の違い、Cranelift の段で初めて見つかった誤り）。
- [ADR 0016](0016-trust-base-declaration.md):
  - 原始操作の実際の一覧と、その実行（評価器・ネイティブ）。
  - `--trust-base` の許可の運用（所有者が「P1 の範囲を決める ADR で決める」とした）と、一覧の置き場所。
  - 前提の文のレビューを必須にする変更の範囲。
  - 大域の状態の構文（決定 5）と、性質を手で付ける構文（決定 7）は、それを要する P1 の ADR で決める。
  - P1 で決定 1・2 を見直す条件と、P1 の完了時に数える数。
- [ADR 0017](0017-run-on-sir-evaluator.md): インタプリタを削除するかを、「比較を外した事例が突き合わせの 1 割を超える」か「P1 の範囲を決める ADR」の早い方で決め直す。

あわせて、本 ADR の起草を求めた指示は、CI の外部のアクションをタグで参照している件（版の固定）を扱うよう求めた。

### 現状（main `6189325`）

- **P0 の進み**:
  - M0〜M5 が完了し、ADR 0016・0017 は実装済みである。
  - M6（言語サーバー）は始まっていない。ADR 0006 は「M6 の完了をもって P0 の完了とする」とした。
  - DESIGN.md の 5 章は、仕様の機械向けの形式を「M6 の前」に決めるとしている。まだ決まっていない。
- **未決のまま期限を過ぎた論点**:
  - 「モジュールの単位と出力先の指定」は DESIGN.md の 5 章で「M1 の前」とされたが、未決である。
  - モジュールどうしの参照はなく、宣言がすべて同じファイルだけを合わせられる（ADR 0016 の現状）。
  - ライブラリ（HTTP・フレームワーク・データベース）を利用者のプログラムから使うには、この論点が先に要る。
- **実行器と比較のテスト**:
  - `sigil run` は SIR の評価器で走る。インタプリタ（`src/interp.rs`、2216 行）はテストの比較だけに使う。
  - インタプリタとの比較を外した事例（`sir_native*` を使う事例）は 0 件である。突き合わせは 411 件なので、1 割は 41 件である。
- **ランタイム**:
  - `runtime/core`（核）と `runtime/os`（OS 依存）は Rust の静的ライブラリで、`cc -static -no-pie` で glibc の `libc.a` とリンクする（ADR 0015 の決定 6）。
  - 文字列は `Box` に入れた Rust の `String`（`RtStr`）で、`sigil_rt_str_free` はあるが、生成コードは文字列とパスの破棄でこれを呼ばない（`src/codegen.rs` の冒頭の注記）。
  - `stdlib::RAW_OPS` は空である。利用者のプログラムは検査を外す手段を持たない。
- **効果のカテゴリ**: `net.client`・`net.server`・`db`・`env`・`task.*` は ADR 0004 と ADR 0007 で定義済みで、P1 の機能を表すのに新しいカテゴリは要らない見込みである。
- **CI**（`.github/workflows/ci.yml`）:
  - `actions/checkout@v4` と `actions/cache@v4` を、版のタグで参照している（コミットの番号で固定していない）。
  - Docker と PostgreSQL は使っていない。

## 本 ADR で決めないこと

- 各段階の中の設計（HTTP の API の形、ルーティングの表記、PostgreSQL の通信の細目、確保器の作り方など）。
  - 段階ごとに ADR を書き、その ADR で PR の細かい分け方まで決める（決定 3）。
- 所有者の判断を求める点（判断 1〜8。6 は 6a〜6c）の結論。
  - 本 ADR は選択肢と推奨を示すだけである。

## 評価の観点

重要な順に並べる。

1. **P1 の目標に届くか**: 「Sigil で書いたサービスを Docker コンテナでリリースする」が、既存言語のコードを出力に含めずに、P1 の終わりに実際に動くこと。
2. **後戻りしない順序か**: ある段階の成果物が、後の段階の前提を作り直させないこと（例: 言語の機能を後から足して、ライブラリを書き直すこと）。
3. **検査を外せる範囲が最小で、人間に見えるか**: P1 で初めて検査を外したコードが入る。前提の文が人間のレビューを通ること（ADR 0005・0016）。
4. **食い違いを見つける手段を失わないか**: インタプリタを外しても、lowering と生成コードの誤りが見つかること。
5. **1 つの PR が小さく、独立して確かめられるか**。

## 決定 1: M6 と P1 の関係

### 選択肢

- **A: M6 を終えてから P1 の実装を始める**。P1 の ADR（設計）は M6 の実装と並行して書いてよい。
- **B: M6 と P1 の実装を並行して進める**。
- **C: M6 を P1 の後に回す**。

### 決定

**A** を採用する。

- P1 の実装の PR は、M6 の完了（P0 の完了）の後に始める。
- ただし、次は M6 と並行して進めてよい。
  - 段階 1 の「準備」の PR（決定 3）。どれも言語の機能を足さず、M6 と触る場所が重ならない。
  - 段階 2 以降の ADR の起草。
- M6 の前に、仕様の機械向けの形式を決める ADR（M6 の ADR）を書く（DESIGN.md の 5 章）。

### 理由

- 観点 2: 言語サーバーの診断は、P1 で AI が大量のライブラリのコードを書くときの検査の道具になる。先に作れば P1 の全体で使える。
- ADR 0006 は M6 で P0 を閉じるとした。C はこの決定を変えることになり、変える理由がない。
- B は、M6 の診断の形式と、P1 で足す構文（モジュール・トレイト）が同時に動き、言語サーバーのテストが何度も壊れる。

## 決定 2: P1 で行うこと・行わないこと

### 行うこと

| 区分 | 内容 | 由来 |
|---|---|---|
| 言語の前提 | モジュールの単位と公開の範囲、利用者のトレイトと関数の型の拡張、`Bytes` | DESIGN.md の 5 章、ADR 0011 |
| ランタイムの置き換え | 原始操作の一覧と実行、大域の状態の構文、確保器、核と OS 依存部分の標準ライブラリを Sigil で書き直す、暫定ランタイム（`runtime/`）の削除 | ADR 0006・0016 |
| 並行処理 | P1-a（SIR の評価器）と P1-b（ネイティブ）。ADR 0007 の 11 の条件の P1 の列をすべてテストで固定する | ADR 0007 |
| HTTP | HTTP/1.1 のサーバーのライブラリ（平文。TLS は判断 5） | ADR 0005 |
| フレームワーク | ルーティング・設定（環境変数・起動引数）・入力検証（篩型と `check`）・テスト用の実行環境での差し替え・終了の合図での停止 | ADR 0005 |
| データベース接続 | PostgreSQL の通信方式（版 3）を Sigil で実装する。接続の集まり（プール）を含む | ADR 0005 |
| 認証 | フレームワークの認証の差し込み口と、具体的な方式 1 つ（判断 6c） | ADR 0005 |
| 暗号の基本部品 | SHA-256・HMAC・PBKDF2・定数時間の比較。PostgreSQL の SCRAM-SHA-256、認証、イメージの digest が共通して使う | 上の 3 つが要る |
| コンテナイメージ | 静的な実行ファイルを 1 つ入れた OCI イメージ（圧縮しない層）を出力する道具。`docker load` で読める | ADR 0005 |
| 持ち越し | 文字列・パスの解放（決定 5）、インタプリタの削除（決定 4）、追跡項目（決定 8） | ADR 0015・0016・0017 |

### 行わないこと

- TLS（HTTPS）の実装。前段の仕組みで終端する前提にする（判断 5）。
- HTTP/2・WebSocket・HTTP の送信側（クライアント）。
  - クライアントは `net.client` の効果としては定義済みだが、P1 の目標に要らない。
- イメージのレジストリへの送信（判断 8）。
- データベースのスキーマの移行の道具・ORM・PostgreSQL 以外のデータベース。
- Linux x86-64 以外の出力先（ARM・macOS・Windows・WebAssembly）。
- コンテナの実行・配置の管理（P5）。
- 契約の静的検査（P0 の後の論点で、P1 に入れない）。
- HTML の雛形の表示（P2 の UI と一緒に決める）。
- 監視の指標・分散トレース。ログは `console` の出力に限る。

### 理由

- 観点 1: 「行うこと」は、ADR 0005 の成果物と、それを Sigil だけで作るために要るものに限った。
- 行わないことのうち TLS・暗号の範囲・レジストリは、安全と秘密情報に関わるので所有者の判断にした（「人間の判断が要る点」）。

## 決定 3: 段階・順序・PR の分け方

### 段階と順序

```
段階 0  M6（P0 の完了）
段階 1  準備（M6 と並行可）
段階 2  言語の前提（モジュール → トレイトと関数の型 → Bytes）
段階 3  ランタイムの置き換え（P1-R）
段階 4  並行処理 P1-a（SIR の評価器）
段階 5  並行処理 P1-b（ネイティブ）
段階 6  サーバーの部品（暗号 → イメージの道具 / HTTP → フレームワーク → PostgreSQL → 認証）
段階 7  P1 の完了（サンプルのサービスをコンテナで動かす）
```

- 段階 6 の暗号の基本部品は、段階 2 の後ならいつでも始めてよい（並行処理に依らない）。
- 段階 6 のイメージの道具は、段階 3 と暗号の後ならいつでも始めてよい。
- HTTP（PR 6-3）は段階 5（PR 5-2）の後に始める。この依存は意図したもので、理由は次のとおりである。
  - 待ち受けと読み書きは `net.server` の効果を持ち、ADR 0004 の改訂で `task.suspend` も起こす。HTTP の API の形（シグネチャと効果）は、P1-a で `task.*` が入るまで決められない。
  - P1-a の後なら、評価器の上で HTTP を書くことはできる。しかし実行ファイルとの突き合わせ（決定 4 の後の唯一の基準）ができず、多数の接続を同時に扱う確かめは P1-b の実行の割り当てと `epoll` が要る。
  - 段階 3 が延びた場合は、下の「段階 3 の見直しの契機」で、P1-a の後に評価器の上で HTTP を先に書く順序に切り替える。

### 段階 3 の見直しの契機

段階 3 は最も大きく、見積もりが外れやすい。次のどれかに当たったら、その時点で順序を見直す ADR（本 ADR の改訂）を書く。

- ADR 3-1 で見積もった PR の数を、実際の PR の数が 1.5 倍を超えた。
- PR 3-2〜3-6 の途中で、ADR 0016 の決定 1・2 の見直しの条件（前提を関数の単位で書けない、呼び出し側の義務が要る、効果の委任がシステムコール以外に要る）に当たった。
- 移行の間の突き合わせ（決定 6）で、Sigil 版と Rust の組み込みの食い違いが、同じ標準ライブラリの関数について 3 回以上直しても残った。

見直しで取りうる案は次の 2 つで、どちらにするかはその ADR で決める。

- 暫定ランタイムを残したまま段階 4（P1-a）に進み、置き換えの残りを段階 6 と並行して進める。P1 の完了条件（Rust のコードを含めない）は変えない。
- P1-a の後に、評価器の上で HTTP（PR 6-3）を先に書く。

### 理由

- **モジュールを最初にする**: ライブラリを別のファイルに置けないと、HTTP・フレームワーク・標準ライブラリの Sigil 版のどれも書けない（観点 2）。
- **トレイトと関数の型を、ランタイムの置き換えの前にする**: 標準ライブラリの Sigil 版の形（`Displayable` の実装など）がトレイトで決まる。後から足すと、書き直すことになる。
- **ランタイムの置き換えを並行処理の前にする**:
  - P1-b の実行の割り当ては、ADR 0007 の規則 7 で OS 依存部分に置く。先に OS 依存部分を Sigil にしておけば、実行の割り当てを最初から Sigil で書ける。逆だと、Rust の暫定ランタイムに実行の割り当てを書き、置き換えのときに書き直すことになる。
  - 暫定ランタイムに機能を足すことは、ADR 0006 の期限付きの例外を広げることになる。
- **インタプリタの削除を段階 1 に置く**: 決定 4 のとおり、段階 3 で標準ライブラリを Sigil に替えると、凍結したインタプリタはそれを実行できない。削除しないと、段階 3 で比較を外す事例が一度に増える。

- 0-1・0-2（M6）と 3-0（許可の運用）の前後は、0-1 → 0-2 → 2-1 → 2-2 → 3-0 である。3-0 は、原始操作の表に最初の行が入る 3-2 より前に必ず合流させる。

## 決定 4: インタプリタの削除（ADR 0017 の再検討）

ADR 0017 は、削除の前に「lowering の誤りを見つける別の手段」を決めるとした。

### 選択肢

- **A: 今は削除せず、P1-a の終わりに数えて決める**（ADR 0017 のもともとの計画）。
- **B: 段階 1 で、別の手段を入れてから削除する**。
- **C: 別の手段なしに、すぐ削除する**。

### 決定

**B** を採用する。

- 別の手段として、**SIR の検証器** を入れる（PR 1-4）。
  - lowering の出力ごとに、検査器が付けた式の型と、SIR の値の型が一致することを確かめる。
  - 移動した値を後で使っていないこと、破棄が各経路でちょうど 1 回であることを、SIR の上で確かめる。
  - テストの実行（`tests/common` の `run*`）では常に検証器を通す。
- 検証器を入れた後、インタプリタを削除する（PR 1-5）。
  - `src/interp.rs` と、`tests/common` のインタプリタとの比較を外す。`run*` は SIR の評価器と実行ファイルを比べる。
  - `tests/m3_drop_limits.rs` のうちインタプリタだけを扱う部分を外す。
- 削除の PR に、ADR 0017 の計測の 2 つの数を記録する。
  - インタプリタとの比較を外した事例の数（今は 0 件）。
  - インタプリタとの比較だけで見つかった lowering の誤りの数（ADR 0017 の実装の後の PR の記録から数える）。
- 2 つ目の数が 0 でなければ、その誤りの種類を検証器が見つけられることを、削除の前にテストで確かめる。
- 2 つ目の数を過去の記録から数えられない場合（PR の記録に、どの比較で見つかったかが書かれていない場合）は、次の **誤りの埋め込み** で代える。
  - `src/lower.rs` に、lowering の誤りを 1 つずつ意図して埋め込んだ版を 10 個以上作る。誤りの種類は少なくとも次を含める。
    - 破棄の順序を入れ替える。
    - 移動した値の破棄を残す（2 回の破棄）。
    - 経路の 1 つで破棄を落とす。
    - 構造体の欄の番号をずらす。
    - `match` の腕の束縛の値を取り違える。
    - 早期の戻りで、後に宣言した値の破棄を飛ばす。
  - 各版で、(1) インタプリタとの比較を含む今のテスト、(2) インタプリタとの比較を外し、検証器と評価器・実行ファイルの比較だけにしたテスト、の 2 つを走らせ、それぞれが見つけた版の数を数える。
  - (1) だけが見つけた版があれば、その種類を検証器が見つけるようにしてから削除する。
  - 埋め込みの版は PR に残さず、使った誤りの一覧と結果の表だけを削除の PR に記録する。

### 理由

- 観点 4: 段階 3 で標準ライブラリを Sigil に替えると、凍結したインタプリタは原始操作を実行できない（ADR 0017 はインタプリタに機能を足さないとした）。ほぼすべての事例が `console` を使うので、比較を外す事例が一度に 1 割を超える。A は、段階 3 の途中で削除を決めることになり、それまでの PR では比較が抜けたまま進む。
- 検証器は、インタプリタと違って破棄の規則を 2 か所に書かない。ADR 0017 が問題にした「同じ規則の 2 つの実装の食い違い」が起きない。
- C は、ADR 0017 の「削除の前に別の手段を決める」に反する。

### 選ばなかった案と理由

- **A・C**: 上のとおり。

## 決定 5: ネイティブ出力の文字列・パスの解放

### 選択肢

- **A: 段階 1 で、今の Rust のランタイムのまま解放する**。
- **B: 段階 3 の置き換えで、Sigil 版の文字列と一緒に直す**。

### 決定

**A** を採用する（PR 1-2）。

- 生成コードが、文字列とパスの破棄で解放を呼ぶようにする。
- 解放の前に、生成コードとランタイムが文字列の指す先を複製せずに共有している箇所を調べ、共有をなくす。調べる経路は次のとおりである。
  - 記述子による複製（`Clone` の値・構造体・組・一覧の要素に文字列があるとき、指す先まで複製しているか）。
  - `String.clone`・`Path.clone` の呼び出し。
  - 構造体・組の欄の読み出し（借用として読むときに、指す先を持ち主と共有したまま、別の値として破棄していないか）。
  - `match` の束縛と、組・構造体の分解。
  - 一覧の要素の取り出し（`get`・くり返し）と、表の鍵・値。
  - 文字列のリテラル（読み取り専用のデータを指すなら、解放してはいけない。使うたびに確保するか、解放しない印を持たせる）。
  - パスを返すランタイムの関数（`path_join`・`path_parent`・`path_file_name`）と、文字列を返すもの（`trim`・`concat`・`lines` など）の戻り値の持ち主。
  - クロージャのとらえた値。
  - 停止の経路（異常停止の前の破棄）。
- ランタイムに、テストのためだけに生きている塊の数を返す入口を加える。数えるのは文字列・パス・頭付きの塊である。
- 完了条件:
  - 文字列を作って捨てる処理を 10 万回くり返すプログラムで、終わる前の生きている塊の数が、くり返しの回数に比例しない。
  - 既存の突き合わせ（411 件）がすべて通る。
  - 同じ塊を 2 回解放すると、テスト用のビルドのランタイムが異常停止で知らせる。

### 理由

- 観点 1・2: P1 のサーバーは止まらずに動き続ける。解放しないと、要求ごとに使用量が増える。
- B では、段階 3 までのすべての PR が漏れる出力のまま進む。また、段階 3 の Sigil 版の文字列は、A で直した破棄の規則（生成コードの側）をそのまま使える。直すのは生成コードの側で、ランタイムの側の変更は小さい。
- A で加えるテストは、段階 3 で Sigil 版に替えた後も、同じ条件の回帰の検査として使える。

### 選ばなかった案と理由

- **B**: 上のとおり。

## 決定 6: 暫定ランタイムの置き換え（原始操作の一覧と実行）

ADR 0016 は、原始操作の一覧と実行を本 ADR で決めるとした。本 ADR は方針と最初の一覧を決め、細目（型の細部・確保器・大域の状態の構文）は ADR 3-1 で決める。

### 最初の一覧

| 原始操作 | 層 | 効果 | 内容 |
|---|---|---|---|
| `raw.load_i64(a: Addr) -> Int` | 核 | なし | 番地から 8 バイトを読む |
| `raw.store_i64(a: Addr, v: Int)` | 核 | なし | 番地へ 8 バイトを書く |
| `raw.load_u8(a: Addr) -> Int` | 核 | なし | 番地から 1 バイトを読む（0〜255） |
| `raw.store_u8(a: Addr, v: Int)` | 核 | なし | 番地へ 1 バイトを書く（`requires` で 0〜255） |
| `raw.load_addr`・`raw.store_addr` | 核 | なし | 番地を読み書きする |
| `raw.offset(a: Addr, n: Int) -> Addr` | 核 | なし | 番地を n バイトずらす |
| `raw.copy(dst: Addr, src: Addr, n: Int)` | 核 | なし | n バイトを写す（重なってよい） |
| `raw.alloc(size: Int, align: Int) -> Addr` | 核 | なし | 塊を得る |
| `raw.free(a: Addr, size: Int, align: Int)` | 核 | なし | 塊を返す |
| `raw.syscall(n: Int, a0..a5: Int) -> Int` | OS | 宣言に委ねる | Linux のシステムコール |

- 核の `raw.alloc`・`raw.free` の実体は、出力先のプラットフォーム層が与える。P1 のネイティブでは、OS 依存部分の Sigil の確保器（`mmap` の上）が与える。これが、核が OS 依存部分に頼る唯一の箇所で、ADR 3-1 で前提の文と一緒に定める。
- 浮動小数点数とビット列の相互の変換のように、検査を外さずに書ける操作は、原始操作にせず通常の標準ライブラリの関数にする。
- 原子的な操作（P1-b）は、ADR 5-1 で行を足す。
- 行を足すことは、判断 2 のレビューの対象にする。

### 番地の読み書き・確保・解放を「効果なし」とする根拠

- ADR 0004・0013 の効果は、プログラムの外から観測できる作用を表す。メモリの確保と解放は外から観測できず、使用量は非目標（DESIGN.md の 4 章）なので、`raw.alloc`・`raw.free` は効果なしとする。
- `raw.store_*` は、その関数が所有する値か、`&mut` で借りた値の中身を書き換えるときに限って使う。これは通常の Sigil の所有した値・`&mut` の引数への代入と同じで、効果なしである。この限定は、使う関数の前提の文に書く。
- `Shared`・`SyncShared`・`Lock` の中身を `raw.store_*` で書き換える関数（標準ライブラリの実装）は、宣言する効果（`state`・`task.share`）と推論（なし）が一致しない。これを効果の委任で解くかどうかは ADR 3-1 で決める。委任で解く場合は、ADR 0016 の決定 1・2 の見直しの条件（効果の委任がシステムコール以外に要る）に当たるので、ADR 0016 に記録して見直す。

### 解放の誤り

- `raw.free` の `size`・`align` が、その塊を得た `raw.alloc` の値と違うとき:
  - SIR の評価器は、塊の表に確保の時の `size`・`align` を持っており、違えば異常停止にする。番地が表にない（確保していない、解放済み）ときも同じである。
  - 実行ファイルは確かめない。誤りは前提の文の違反で、動きは定めない（確保器の状態が壊れうる）。
  - これを補うのは評価器との突き合わせで、`raw.free` を呼ぶ経路は評価器で必ずテストする。ADR 3-1 で、確保器が塊の頭に大きさを持って実行ファイルでも確かめるかを決める。
- `raw.alloc` の失敗（メモリが得られない）は、プロセス全体の異常停止にする（決定 7）。
- `raw.alloc` の `size` が 0 以下、`align` が 2 の累乗でないときは、`requires` の違反（契約違反）にする。

### `raw.syscall` に渡す番地

`raw.syscall` の引数は `Int` で、番地を渡してもカーネルがそのまま読み書きする。評価器の範囲の確かめは、ここで迂回されうる。

- **評価器**: システムコールの表を持ち、表にある番号だけを実行する。表にない番号は異常停止にする。
  - 表の各行は、どの引数が番地で、どの引数がその長さかを持つ（例: `read(fd, buf, count)` は `buf` から `count` バイトに書く）。
  - 評価器は、実行の前に、番地の範囲が生きている塊の中にあることを確かめ、外なら異常停止にする。
  - `mmap`・`munmap` の行は、得た領域を塊の表に足し、返した領域を表から除く。
  - 表に載せるシステムコールは、ADR 3-1 で `console`・`fs`・`path`・`env`・確保器が使うものから始め、行を足すことは判断 2 のレビューの対象にする。
- **実行ファイル**: 確かめない。`raw.syscall` を呼ぶ関数の前提の文に、「渡す番地の範囲は生きた塊の中にある」ことを書くことを必須にする。
- 番地の範囲の誤りは、評価器との突き合わせで見つける。評価器の表にないシステムコールを呼ぶ関数は、評価器で動かせないので、テストで評価器を通らないことになる。この場合はシステムコールの表に行を足すまで、その関数を合流させない。

### 実行の方針

- **SIR の評価器**: 原始操作を実際に実行する。番地は本物の番地とし、評価器は確保した塊の表を持って、読み書きのたびに範囲と生存を確かめる。範囲の外・解放済みの塊への読み書きは、異常停止にする。`raw.syscall` は、Rust のインラインアセンブリ（`core::arch::asm!`。依存の追加は要らない）で実行する。
- **ネイティブ**: 読み書きは Cranelift の読み書きの命令にする。`raw.syscall` と起動の入口（`_start`）は、処理系が機械語を生成する（ADR 0005 の「処理系が生成するコード」で、信頼基盤に入る）。
- **移行の間**: 標準ライブラリの関数を 1 つずつ Sigil 版に替える。替えるまでは、評価器は Rust の組み込みを使い、実行ファイルは Sigil 版を使う。両者の突き合わせで、Sigil 版の誤りを見つける。替えた後は、評価器も Sigil 版を実行し、組み込みを消す。
- **glibc**: 置き換えの終わり（PR 3-7）で、出力を glibc とリンクしない（`-nostdlib`）。判断 7 で所有者の確認を求める。

### 理由

- 観点 3: 原始操作をシステムコールと番地の読み書きに限ると、C の関数を呼ぶ原始操作が要らない。C の関数を呼べると、glibc の任意の関数が信頼基盤に入り、ADR 0001 の非目標（既存言語のライブラリを使う手段）に近づく。
- 観点 4: 評価器が番地の範囲を確かめるので、信頼基盤のコードの誤り（範囲の外の読み書き）が、テストで異常停止として見える。実行ファイルでは見えない誤りを、評価器との突き合わせが見つける。
- 移行の間の二重の実装は、インタプリタを外した後（決定 4）の、標準ライブラリの側の基準の役を果たす。

### 選ばなかった案と理由

- **C の関数を呼ぶ原始操作（`raw.ccall`）**: 上のとおり。
- **評価器では原始操作を実行せず、Rust の組み込みを残し続ける**: 標準ライブラリの実装が 2 つ残り、評価器と実行ファイルで違う標準ライブラリが動く。移行の間だけに限る。
- **評価器の番地を、評価器の中の配列の添字にする**: システムコールに番地を渡すたびに変換が要り、`read`・`write` の受け渡しが複雑になる。

## 決定 7: 1 件の要求の失敗の隔離（ADR 0007）

### 選択肢

- **A: P0 と同じく、契約違反でプロセス全体を止める**。コンテナの再起動に任せる。
- **B: 要求ごとのタスクの範囲で止める**。契約違反を起こしたタスクとその子を、取り消しと同じ順序で破棄して終わらせる。サーバーは 500 を返して続ける。
- **C: 要求ごとにプロセスを分ける**。

### 決定

**B** を採用する。細目は ADR 4-1（P1-a）で決める。

- 隔離の境目は、フレームワークが要求ごとに起動するタスクの範囲とする。利用者は境目を書かない。
- 桁あふれ・0 での除算も、契約違反と同じ扱いにする（ADR 0013 で同じ種類の異常停止としたため）。
- スタックの枯渇と、確保の失敗は、プロセス全体を止める。どちらもプロセスで共有する資源（OS スレッドのスタック、メモリ）が尽きたことを表し、そのタスクの破棄を行うこと自体にスタックやメモリが要るので、他のタスクを続けられると保証できないためである。
- 異常停止したタスクが `Lock` を持っていた場合、その `Lock` を「壊れた」状態にし、以後の取得を失敗にする。
- 隔離した異常停止は、停止の報告と同じ内容を標準エラーへ出す。
- ADR 0013 の「異常停止は破棄をしてからプログラムを止める」は、要求のタスクの範囲では「破棄をしてからそのタスクの範囲を止める」と読み替える。この読み替えは ADR 4-1 で ADR 0013 に追記する。

### ADR 4-1 で必ず決めること

- **壊れた `Lock` を待っているタスク**:
  - 待っている間に `Lock` が壊れたとき、待っているタスクを起こして取得を失敗で返すか（推奨）、待たせ続けるか。
  - 取得の失敗の型（`Result` の失敗の側）と、壊れた状態を戻す手段を持つか。
- **止めたタスクの資源の後始末**:
  - 中断中のタスクを止めたとき、それが持つ資源（データベースの接続・ソケット・ファイル）を、取り消しと同じ順序で破棄すること。
  - 破棄の処理が I/O（ソケットを閉じる、データベースへの終了の通知）をしてよいか、中断してよいか。
  - トランザクションの途中のデータベースの接続を、接続の集まりに戻さず捨てる（または巻き戻してから戻す）こと。どちらにするかは ADR 6-5 で決めるが、破棄の側の仕組みは ADR 4-1 で用意する。
- **確保器の整合**:
  - タスクを止めるのは中断点と異常停止の地点に限られ、確保器（ADR 3-1）の関数の中に中断点を置かないこと。
  - 確保器の関数の中で契約違反が起きない（状態を書き換える前にすべての検査を終える）ことを、確保器の前提の文に書くこと。
  - 上の 2 つが守れない箇所があれば、そこで止まったときはプロセス全体を止めること。
- **停止の経路での漏れ**: ADR 0006・0015 が「インタプリタと厳密に揃えない」とした停止の経路の漏れは、要求のタスクの範囲で止めるとプロセスが続くので、漏れのままにできない。止めたタスクの値がすべて破棄されることをテストで固定する。

### 理由

- 観点 1: A では、1 件の不正な入力でサービス全体が止まり、同時に処理中の他の要求も失われる。Spring の置き換え（G10）として受け入れにくい。
- B が成り立つのは、大域の可変な値がなく（条件 12）、タスクの値は所有権で分かれているからである。止めたタスクが壊しうる共有の状態は `SyncShared`・`Lock` に限られ、`Lock` を壊れた状態にすれば他のタスクに見える。
- C は、プロセスの起動の費用が大きく、接続の集まり（データベース）を共有できない。

### 選ばなかった案と理由

- **A・C**: 上のとおり。

## 人間の判断が要る点

### 判断 1: `--trust-base` の許可の運用

ADR 0016 の決定 3 で、許可は `--trust-base <モジュール名>` のオプションで与え、`std.` で始まる標準ライブラリは常に許すとした。所有者はその運用を本 ADR で決めるとした。段階 3（PR 3-0）の前に決める必要がある。PR 3-2 で原始操作の表に最初の行が入り、検査を外したコードが実際に書けるようになるからである。

なお、P1 で書く信頼基盤のコードは、ほとんどが標準ライブラリ（`std.` で始まるモジュール）で、`--trust-base` を付けなくても常に許される。したがって、許可の一覧よりも、判断 2（どの変更をレビューするか）の方が、実際の守りになる。

| 案 | 内容 | 設定の変更 | 利点 | 欠点 |
|---|---|---|---|---|
| T1: 今のまま | オプションだけ。許可を変える PR（ビルドの手順や CI の設定の変更）は、所有者が承認するまで合流しないという手順の約束にする | なし | すぐ始められる | 約束が守られたことを仕組みで確かめられない。許可が散らばったスクリプトの中にあり、見落としやすい |
| T2: 一覧のファイル + コードの所有者 | 許可の一覧をリポジトリの 1 つのファイル（例: `trust-base.list`）に置き、処理系が読む。オプションはテスト用に残す。そのファイル・原始操作の表（`src/stdlib.rs`）・信頼基盤の標準ライブラリの置き場所を `CODEOWNERS` で所有者に割り当て、ブランチの保護で所有者のレビューを必須にする | GitHub のリポジトリの設定（権限） | 許可が 1 か所に集まり、変更が仕組みで止まる | リポジトリの設定の変更が要る。`CODEOWNERS` はファイルの単位でしか効かず、`std` の中の `unchecked` の関数だけを選べない |
| T3: T2 + CI での検出 | T2 に加えて、CI で基準の版と比べ、`unchecked` の関数（本体と前提の文）・原始操作の表・許可の一覧が変わった PR を検出し、変わった前提の文を PR に表示する（変わったら失敗にするか、印を付けるかは所有者が選ぶ） | T2 の設定 + CI の変更 | 判断 2 の範囲を、関数の単位で仕組みとして守れる。人間は表示された前提の文だけを読めばよい | CI の変更が要る。検出のスクリプトを保守する |
| T4: 署名した一覧 | 所有者が鍵で署名した一覧だけを処理系が受け付ける | 鍵の管理 | 改ざんに最も強い | 秘密情報の管理が要り、1 人の所有者には費用が見合わない |

**推奨: T3**。段階 3 の前に T2 を入れ（PR 3-0）、検出の CI は PR 3-2 と同時に入れる。

- 理由: ADR 0005 は「人間はコードを読まず、前提の文が人間に示される唯一の情報」とした。検査を外したコードが入る変更を、人間が見落とさない仕組みが要る。T1 は約束だけで、AI が書いた PR を AI が合流させる流れでは、仕組みとしての止めがない。
- 所有者が設定の変更を避けたい場合の最小案は、T1 と「`unchecked`・`raw.` を含む差分のある PR は所有者が合流させる」という手順の約束の組である。
- 一覧の置き場所: パッケージの設定ファイルを持つかは ADR 2-1 で決める。持つことになったら、一覧をそこへ移すかを ADR 2-1 で見直す。それまでは専用のファイルにする。

### 判断 2: 前提の文のレビューを必須にする変更の範囲

| 案 | 対象 |
|---|---|
| S1 | 原始操作の表と、許可の一覧の変更だけ |
| S2 | S1 + `unchecked` の関数の追加・削除・本体の変更・前提の文の変更 |
| S3 | S2 + 信頼基盤のモジュールのすべての変更 |

**推奨: S2**。

- `unchecked` の関数の本体を変えると、前提の文を変えなくても前提が崩れうる。S1 ではこれを見落とす。
- 信頼基盤のモジュールでも、`unchecked` でない関数は通常の検査がすべて働く（ADR 0016 の決定 4）。S3 は、検査で守れる変更まで人間に読ませる。
- 判断 1 で T3 を選んだ場合、S2 の検出は CI が行う。

### 判断 3: CI のアクションの版の固定

| 案 | 内容 |
|---|---|
| V1 | 今のまま、版のタグ（`@v4`）で参照する |
| V2 | コミットの番号（40 桁）で固定し、行の末尾に版をコメントで書く（例: `actions/checkout@<番号> # v4.x.y`） |
| V3 | V2 + 版の更新の PR を自動で作る仕組み（Dependabot の設定ファイルを加える） |

**推奨: V2**。

- タグは付け替えられるので、参照先のアクションの中身が知らないうちに変わりうる。番号で固定すれば、変わるのは PR で番号を変えたときだけになる。
- 対象は `actions/checkout` と `actions/cache` の 2 つで、更新の頻度は低い。V3 の自動の PR は、2 つのために設定を 1 つ増やすほどの利点がない。必要になったら加える。
- 実装（PR 1-3）は `ci.yml` だけを変える。番号は、PR を作るときに各アクションのリポジトリのタグから引き、PR の本文に引いた方法を書く（本 ADR には番号を書かない）。

### 判断 4: P1 で CI に加えるもの

P1 の完了条件は、Docker と PostgreSQL を使うテストを含む。

- 案 A: Docker と PostgreSQL のテストを CI に入れる（GitHub Actions の `services` で PostgreSQL の公式イメージを使う。イメージの版を固定する）。
- 案 B: 手で実行するテスト（`#[ignore]`）に留め、実行した記録を ADR に残す（`runs_in_scratch_container` と同じ運用）。

**推奨: A**。P1 の目標そのものが「コンテナで動かす」なので、それを毎回確かめないと、後の段階の変更で壊れても気付かない。どちらにするかは PR 6-2 の前に決めればよい。外部のイメージ（PostgreSQL）を CI で使うことは依存の追加に当たるので、所有者の判断とする。

- B の利点: CI の設定を変えず、外部のイメージという依存を増やさない。CI の時間が延びない。Docker の版や PostgreSQL のイメージの更新で、Sigil と関係なく CI が落ちることがない。

### 判断 5: TLS を P1 で実装しない

- 案 A: P1 では TLS を実装しない。サービスは平文の HTTP で待ち受け、HTTPS はコンテナの前段（逆向きの中継やロードバランサ）で終端する。
- 案 B: P1 で TLS 1.3 を Sigil で実装する。

**推奨: A**。TLS は鍵の交換と暗号の実装が大きく、誤りが秘密の漏洩に直結する。P1 の目標（サービスをコンテナでリリースする）は、前段での終端で満たせる。B は P1 の後の段階の ADR で扱う。安全に関わるので所有者の判断とする。

- B の利点: 前段の仕組みなしに、サービスだけで HTTPS を公開できる。サービスと前段の間も暗号化され、内部の網を信じなくてよい。TLS に要る暗号（楕円曲線・AES-GCM など）は P2 以降のブラウザ（P7）でも要るので、先に作ることになる。

### 判断 6a: 暗号の基本部品を Sigil で実装すること

- 案 A: SHA-256・HMAC・PBKDF2・定数時間の比較を Sigil で実装する（ADR 0005 は既存のライブラリを使わないとした）。正しさは、規格の文書が示す検査用の値（テストベクタ）で確かめる。
- 案 B: P1 では暗号を実装せず、暗号が要る機能（PostgreSQL の SCRAM、認証の署名、イメージの digest）を後に回すか、暗号の要らない方式にする。

**推奨: A**。PostgreSQL の既定の認証（SCRAM-SHA-256）とイメージの digest（SHA-256）は、P1 の目標に欠かせない。

- B の利点: 暗号の実装の誤り（タイミングによる漏洩など）の危険を P1 に持ち込まない。ただし、PostgreSQL を平文のパスワード（`password` 方式）か `trust` 方式で使うことになり、安全はむしろ下がる。
- 定数時間の比較が、Cranelift の最適化の後も定数時間であることは、生成コードを見なければ確かめられない。ADR 6-1 で確かめ方を決める。
- 安全に関わるので所有者の判断とする。

### 判断 6b: PostgreSQL の認証と通信

- 案 A: SCRAM-SHA-256 だけを実装する（平文のパスワードを送らない方式）。通信は平文で、データベースはサービスと同じ内部の網に置く前提にする。
- 案 B: A に加えて、データベースとの通信を TLS で暗号化する。
- 案 C: `password`（平文）・`md5` の方式も実装する。

**推奨: A**。PostgreSQL 14 以降の既定の方式が SCRAM-SHA-256 で、これだけで接続できる。

- B の利点: データベースを別の網（管理されたデータベースのサービスなど）に置ける。判断 5 の B と同じ TLS の実装が要るので、判断 5 で A を選ぶなら B は取れない。
- C の利点: 古い設定のデータベースにもつながる。ただし平文と `md5` は弱い方式で、新しく作る理由がない。
- 接続の情報（パスワード）は環境変数（`env` の効果）で受け取り、リポジトリと CI の設定に置かない。テスト用の PostgreSQL のパスワードは、CI の中だけで使う使い捨ての値にする（判断 4）。
- 秘密・DB に関わるので所有者の判断とする。

### 判断 6c: フレームワークの API の認証の方式

- 案 A: HMAC で署名した持参の印（ベアラートークン）を検証する。印を発行する側は P1 では作らない。
- 案 B: パスワードの照合（PBKDF2 で保存）と、セッションの cookie。
- 案 C: 外部の認証の仕組み（OpenID Connect など）に任せ、前段が付けた見出しを信じる。

**推奨: A**。A は暗号の部品だけで書け、状態（セッションの保存先）が要らない。署名の鍵は環境変数（`env` の効果）で受け取り、リポジトリには置かない。

- B の利点: ブラウザから使う画面つきのサービス（P2）にそのまま使える。利用者の登録とログインまでサービスの中で完結する。欠点は、パスワードの保存とセッションの保存先（データベースのスキーマ）が要ること。
- C の利点: 認証の実装をほぼ持たずに済み、既存の認証の仕組み（社内の SSO など）とつながる。欠点は、前段の設定に安全が依存し、Sigil の側で確かめられないこと。
- 秘密・認証に関わるので所有者の判断とする。

### 判断 7: 出力から glibc を外すこと（ビルド環境の前提の変更）

ADR 0015 で所有者は、ビルド環境の前提を「`cc` + glibc の静的リンク」として承認した。決定 6 は、置き換えの終わりで glibc とリンクしない（`cc -nostdlib -static` で、起動の入口とシステムコールの入口を処理系が生成する）ことを提案する。

- 利点: 出力に既存言語のコードを含めないこと（ADR 0005）を、ランタイムだけでなく C の標準ライブラリについても満たす。ビルド環境に `libc.a` が要らなくなる。
- 欠点: スレッドの作成（P1-b）を、glibc の `pthread` なしに `clone` のシステムコールで書く必要がある。

**推奨: 外す**。ただし、P1-b で `clone` によるスレッドの作成がうまくいかなかった場合に限り、スレッドの作成だけ glibc を残し、ADR 0006 の期限付きの例外に加える（ADR 5-1 で決める）。ビルド環境の前提を変えるので、所有者の確認を求める。

- 残す案の利点: glibc の起動の処理（スレッドごとの領域の準備・`atexit` など）と `pthread` は実績があり、P1-b の危険が小さい。ADR 0015 で承認したビルド環境のまま進められる。P6（OS）まで残しても、出力が Linux の上で動く限り困らない。
- 残す場合は、C の関数を呼ぶ手段が要るので、決定 6 の「C の関数を呼ぶ原始操作を持たない」を見直すことになる。

### 判断 8: イメージのレジストリへの送信

- 案 A: P1 では送信しない。イメージの道具は `docker load` で読めるファイルを出力するまでとする。
- 案 B: P1 でレジストリへの送信（認証情報を使う）まで作る。

**推奨: A**。送信にはレジストリの認証情報（秘密情報）の扱いが要る。リリースの手順のうち送信は既存の `docker push` で足り、出力に既存言語のコードを含めないという方針には関わらない。

- B の利点: Docker の道具がない環境（CI の中、P5 のコンテナ管理）からもリリースでき、「Docker を置き換える」（G5・G6）に一歩近づく。送信には HTTP のクライアントと、多くのレジストリで TLS が要るので、判断 5 と `net.client` の実装に依る。

### 判断の要らない点

- 依存の追加: 本 ADR の決定 1〜8 は、新しいクレートを要しない（決定 6 の `asm!` は Rust の言語の機能である）。M6 で要るものは ADR 0-1 で問う。
- データベースのスキーマ: P1 で作るのはサンプルのサービスのスキーマだけで、このリポジトリが運用するデータベースはない。

## 根拠の限界と再検証

- 候補の案出しと採点を、同じ者（Claude）が行っており、偏りがありうる。
- 段階の順序は、各段階の大きさを見積もらずに、依存の関係だけから決めた。段階 3（ランタイムの置き換え）が見込みより大きい場合の見直しの契機と案は、決定 3 の「段階 3 の見直しの契機」に置いた。
- 決定 4 の SIR の検証器が、インタプリタとの比較で見つかってきた誤りを見つけられるかは、削除の PR で数えるまで分からない。削除の後に、評価器と実行ファイルの両方で同じように間違う lowering の誤りが見つかった場合は、その種類を検証器に加え、ADR に記録する。
- 決定 6 の最初の一覧は、暫定ランタイムの機能（`console`・`fs`・`path`・確保）を想像して決めたもので、実際に書いていない。ADR 3-1 で書いてみて足りなければ、行を足す（判断 2 のレビューの対象）。
- 決定 7 の「`Lock` を壊れた状態にすれば隔離が成り立つ」は、信頼基盤が隠れた共有の状態を持たないことを前提にしている。確保器の大域の状態（ADR 3-1）は、要求のタスクが止まっても壊れないこと（確保・解放の途中で止まらないこと）を前提の文に書く必要がある。
- 次を計測する。
  - 段階ごとの PR の数と、各段階の ADR で見積もった数との差（段階の大きさの見積もりの精度）。
  - P1 の完了時に、`unchecked` の関数の数・原始操作の呼び出しの数（ADR 0016）。
  - 判断 1 の仕組みが、検査を外した変更を止めた回数。
