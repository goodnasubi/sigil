# 0023: Bytes 型とビット演算（ADR 0018 の PR 2-5、ADR 0020）

- **状態**: 提案

## 背景

- [ADR 0018](0018-p1-scope.md) の段階 2 は、モジュール（2-1・2-2）→ 利用者のトレイトと関数の型（2-3・2-4）→ `Bytes` とビット演算（2-5）の順である。
- [ADR 0020](0020-p1-security-addendum.md) は、P1 のセキュリティ追補として定数時間処理（決定 1）を定めた。その中で、SHA-256・HMAC・PBKDF2（段階 6-1）、PostgreSQL 通信の SCRAM 認証（段階 6-5）、OCI コンテナイメージ出力（段階 6-2）の前提として、`Int` のビット演算および `Bytes` の 1 バイト読み書きが必須であると規定している。
- [ADR 0009](0009-lexical-and-grammar.md)（決定 8）は、P0 においてビット演算を保留とし（`&`・`|` は借用やクロージャの区切りに予約）、16 進・2 進リテラルも保留とした。
- [ADR 0011](0011-type-system-scope.md)（決定 1）は、`Int` を 64 ビット符号付き整数（2 の補数、桁あふれは異常停止）と定め、固定幅整数は持たないとした。
- 本 ADR は、P1 の暗号・通信・バイナリ生成の基盤となる `Bytes` 型と `Int` のビット演算の仕様を定める。

### 現状（main）

- **数値型**: `Int`（64 ビット符号付き整数）と `Float`（IEEE 754 倍精度）のみ。
- **ビット演算**: 演算子・標準関数ともに存在しない。
- **バイナリ列**: 存在しない。文字列 `String` は UTF-8 前提であり、任意のバイナリデータを安全かつ効率的に扱う手段がない。
- **整数リテラル**: 10 進数のみ（`0` または先頭が 0 以外の数字列）。16 進・2 進リテラルはない。

## 本 ADR で決めないこと

- 暗号アルゴリズム（SHA-256・HMAC・PBKDF2 など）そのものの実装。段階 6-1（[ADR 0020](0020-p1-security-addendum.md) 参照）で定める。
- OCI イメージの tar 出力や PostgreSQL の wire protocol の個別パケット定義。段階 6-2・6-5 で定める。
- 固定幅整数型（`U8`, `U32`, `U64`, `I32` など）の導入。`Int`（64 ビット符号付き）と `Bytes` で P1 の要件は十分満たせるため、型システムの複雑化を避けて P1 では導入しない。

## 評価の観点

重要な順に並べる。

1. **定数時間保証とセキュリティ（ADR 0020）**: 暗号処理（SHA-256・HMAC・PBKDF2・SCRAM・定数時間比較）において、秘密データに基づく分岐やタイミング漏洩を生じさせない命令・API 設計であること。
2. **P1 の具現性（暗号・DB・コンテナ）**: SHA-256、SCRAM-SHA-256、PostgreSQL パケット組み立て、OCI tar 生成に必要な操作が過不足なく揃っていること。
3. **言語仕様との調和と一貫性**: 所有権・借用規則（ADR 0003）、契約（ADR 0002）、性質（Prop / Trait、ADR 0011・0022）、既存の構文規則（ADR 0009）と矛盾しないこと。
4. **実装の単純性と段階的検証性**: 段階的に分割して PR を作成・検証できること。

## 決定 1: `Bytes` 型の表現と所有権・性質

### 選択肢

- **B1: 独立した組み込み値型（ヒープ確保、所有権を持つ）**
- **B2: `List<Int>`（要素が 0〜255）で代用する**
- **B3: 不変（イミュータブル）なバイト列のみとする**

### 決定

**B1** を採用する。

`Bytes` は、動的な長さを持つ連続したバイト列（8 ビット符号なしバイトの並び）を表す独立した組み込み型とする。

- **メモリ表現**: ポインタ・長さ・容量（8 バイトのアライメントを持つ連続バッファ）からなる。ネイティブおよび評価器ではヒープ確保（段階 3 のアロケータまたは現在のランタイムヒープ）により管理される。
- **所有権・借用**: `String` や `List<T>` と同様、単一の所有者を持ち、ムーブセマンティクスに従う。借用は `&Bytes`（共有借用）および `&mut Bytes`（排他借用）として扱われる。
- **性質（Properties）**:
  - `Equatable`: `==`, `!=` による内容一致比較が可能（辞書順ではなく同一性判定）。※暗号論的比較には定数時間の `ct_eq` を用いる（決定 4）。
  - `Comparable`: 辞書順の大小比較が可能（`byte_cmp` または `<` 演算子）。
  - `Sendable`, `Shareable`: 内部にスレッド非安全な参照や内部可変性を持たないため、スレッド間送信・共有が可能（ADR 0007）。
  - `Clone`: `bytes.clone()` によりディープコピー（バッファの複製）が可能。`Copyable` ではない。
- **要素の型**: 要素は `Int`（0 <= x <= 255）として表現される。個別の `Byte` 型や `U8` 型は作らず、既存の `Int` を用いてシンプルに保つ。

## 決定 2: `Bytes` の標準ライブラリ API

`std.core` に以下の API を提供する（シグネチャと契約）。

### 1. 生成・構築

- `Bytes.new() -> Bytes`
  - 空の `Bytes`（長さ 0）を生成する。
- `Bytes.with_capacity(capacity: Int) -> Bytes`
  - `requires capacity >= 0`
  - 指定容量を事前確保した空の `Bytes` を生成する。
- `Bytes.from_list(bytes: &List<Int>) -> Result<Bytes, String>`
  - 各要素が `0 <= x <= 255` であることを検証し、`Bytes` を構築する。範囲外の要素がある場合は `Err` を返す。

### 2. 状態・要素アクセス

- `len(self: &Bytes) -> Int`
  - バイト長を返す。
- `is_empty(self: &Bytes) -> Bool`
  - `self.len() == 0` を返す。
- `get(self: &Bytes, index: Int) -> Option<Int>`
  - 指定位置のバイト値を `Option<Int>`（0〜255）で返す。範囲外は `None`。
- `set(self: &mut Bytes, index: Int, byte: Int) -> Result<Unit, String>`
  - 指定位置のバイト値を更新する。`0 <= byte <= 255` かつインデックスが範囲内なら `Ok(())`、それ以外は `Err`。
- `push(self: &mut Bytes, byte: Int)`
  - `requires 0 <= byte && byte <= 255`
  - 末尾に 1 バイトを追加する。

### 3. スライス・結合・部分抽出

- `slice(self: &Bytes, start: Int, end: Int) -> Result<Bytes, String>`
  - 指定範囲 `[start, end)` の複製を新たな `Bytes` として返す（`0 <= start && start <= end && end <= self.len()`）。
- `concat(self: &Bytes, other: &Bytes) -> Bytes`
  - 2 つの `Bytes` を連結した新しい `Bytes` を返す。
- `extend(self: &mut Bytes, other: &Bytes)`
  - 末尾に `other` の全バイトを追記する。

### 4. 文字列（UTF-8）との相互変換

- `to_string_utf8(self: &Bytes) -> Result<String, String>`
  - バイト列が正しい UTF-8 であるかを検証し、`String` を生成する。不正なバイト列の場合は `Err`。
- `String.as_bytes(self: &String) -> Bytes`
  - 文字列の UTF-8 バイト列の複製を `Bytes` として返す。

### 5. バイナリ・エンコーディング（整数との相互変換）

ビッグエンディアン（BE）およびリトルエンディアン（LE）での整数（16/32/64 ビット）読み書きを提供する（PostgreSQL・OCI・暗号で使用）。

- `push_u16_be(self: &mut Bytes, value: Int)`: 下位 16 ビットを BE で追加。
- `push_u32_be(self: &mut Bytes, value: Int)`: 下位 32 ビットを BE で追加（PostgreSQL のメッセージ長、SHA-256 のブロックパディング）。
- `push_u64_be(self: &mut Bytes, value: Int)`: 64 ビット整数を BE で追加（SHA-256 のメッセージ長ビットカウンタ）。
- `push_u32_le(self: &mut Bytes, value: Int)`: 下位 32 ビットを LE で追加。
- `read_u32_be(self: &Bytes, offset: Int) -> Option<Int>`: BE で 32 ビット符号なし整数を読み取る（0〜0xFFFFFFFF）。

## 決定 3: `Int` のビット演算（構文と演算子）

### 選択肢

- **O1: 専用の演算子記号を導入する**
  - AND: `&`, OR: `|`, XOR: `^`, NOT: `~`, SHL: `<<`, SHR: `>>`
- **O2: 演算子ではなく標準ライブラリの関数／メソッドにする**
  - 例: `a.bit_and(b)`, `a.bit_or(b)`, `a.shl(n)`
- **O3: 折衷案（主要な演算子は記号、回転等はメソッド）**

### 決定

**O3** を採用する。

#### 1. 演算子記号の採用

暗号処理（SHA-256 の $\Sigma, \sigma, Ch, Maj$ 式）やバイナリプロトコル解析では、ビット論理演算とシフトが極めて高頻度で出現する。関数形式 `a.bit_xor(b.bit_and(c))` では可読性が著しく低下し、AI のコード生成および人間の仕様レビューにおいて誤りを見落としやすくなる。

そのため、以下の演算子記号を導入する：
- ビット論理積（AND）: `&`（中置二項）
- ビット論理和（OR）: `|`（中置二項）
- 排他的論理和（XOR）: `^`（中置二項）
- ビット否定（NOT）: `~`（前置単項）
- 左論理シフト: `<<`（中置二項）
- 右論理シフト: `>>`（中置二項、0 埋め / unsigned shift）
- 右算術シフト: `>>>` またはメソッド `ashr`（後述）

#### 2. 構文の衝突回避と字句解析の明確化

ADR 0009 で `&` は借用（前置 `&` / `&mut`）、`|` はクロージャ引数（`|x|` / `||`）に予約されていた。
- 前置 `&`（借用）と中置 `&`（ビット積）:
  - 式の先頭や二項演算子の直後は前置 `&`（借用）。
  - 式のオペランドとオペランドの間にある場合は中置 `&`（ビット積）。これは Rust 等と同様に字句・構文解析で明確に区別可能である。
- クロージャ `|...|` と中置 `|`（ビット和）:
  - クロージャの始まりは式の開始位置（先行して二項演算子や文頭がある場合）。
  - 中置 `|` は左辺の式が完了した直後に現れる。
- 曖昧さを防ぐため、論理演算子 `&&`・`||` とビット演算子 `&`・`|`・`^` を同じ式の中で括弧なしで混在させることは **構文エラー** とする（ADR 0009 決定 8 の「`&&` と `||` を混ぜるときは括弧を必須にする」規則を拡張）。

#### 3. 演算子の優先順位表の更新（ADR 0009 決定 8 の改訂）

| 順位 | 演算子 | 結合性 | 備考 |
|---|---|---|---|
| 1 | `a.b`, `f(...)`, `式?` | 左 | フィールド、呼び出し、早期リターン |
| 2 | 前置 `!`, `-`, `~`, `&`, `&mut` | 右（前置） | `~` はビット否定（2 の補数のビット反転） |
| 3 | `*`, `/`, `%` | 左 | 算術乗除余 |
| 4 | `+`, `-` | 左 | 算術加減 |
| 5 | `<<`, `>>` | 左 | ビットシフト |
| 6 | `&` | 左 | ビット論理積 |
| 7 | `^` | 左 | ビット排他的論理和 |
| 8 | `|` | 左 | ビット論理和 |
| 9 | `==`, `!=`, `<`, `<=`, `>`, `>=` | 結合しない | 比較 |
| 10 | `&&` | 左 | 論理積（`&`, `|`, `^` との直接混在は要括弧） |
| 11 | `||` | 左 | 論理和（`&&` との混在は要括弧） |
| 12 | クロージャ `|引数| 式` | — | 式の末尾まで拡張 |

#### 4. シフト演算の規則とシフト量

- シフト演算 `a << n` および `a >> n` において、シフト量 `n` は `requires 0 <= n && n < 64` とする。
- 負のシフト量または 64 以上のシフト量は **異常停止（Panic）** とする（ADR 0020 決定 1）。
- 右シフト `>>` は **論理右シフト（ゼロ埋め、Cranelift の `ushr`）** とする。
  - 暗号・ハッシュ・バイナリパケット処理の 99% 以上は符号なしビット列としてのシフトを必要とするため、`>>` を論理右シフトに割り当てる。
  - 符号付き算術右シフトが必要な稀なケースのために、メソッド `ashr(self: Int, n: Int) -> Int`（Cranelift の `sshr`）を提供する。

#### 5. ビット回転（Rotate）の API

x86-64 には CPU 命令（`ror`, `rol`）が存在し、SHA-256 では 32 ビット回転が中核演算となる。
専用の演算子記号は設けず、明快なメソッドを提供する：

- `rotl(self: Int, n: Int, width: Int) -> Int`
  - `requires 0 <= n && n < width && (width == 32 || width == 64)`
  - `width` ビット幅での左循環シフト（Cranelift の `rotl` 命令にマップ、32 ビット幅の場合は下位 32 ビットで回転）。
- `rotr(self: Int, n: Int, width: Int) -> Int`
  - `requires 0 <= n && n < width && (width == 32 || width == 64)`
  - `width` ビット幅での右循環シフト（Cranelift の `rotr` 命令にマップ）。
- 暗号で頻出する 32 ビット専用の簡易メソッド：
  - `rotr32(self: Int, n: Int) -> Int`: 32 ビット右回転（下位 32 ビットを対象とし、上位 32 ビットは 0 クリア）。

## 決定 4: 定数時間操作と暗号要件（ADR 0020 との整合性）

ADR 0020 の決定 1 で定めた静的規則（R1〜R6）および定数時間保証との関係を以下のように確定する。

1. **Cranelift 命令への直接マッピング**:
   - `&` -> `band`
   - `|` -> `bor`
   - `^` -> `bxor`
   - `~` -> 64 ビット `-1` との `bxor` または `bnot`
   - `<<` -> `ishl`
   - `>>` -> `ushr`
   - `rotr32` -> 下位 32 ビットの `rotr` + 32 ビットマスク
   これらはすべてデータ依存の条件分岐を含まない単一命令（または固定命令列）として生成される。
2. **定数時間比較 `ct_eq`**:
   - `Bytes` の通常の一致比較 `a == b` は、先頭から走査して異なるバイトで早期リターンするため定数時間ではない。
   - 暗号鍵・ハッシュ値・MAC タグ・署名・パスワード比較のために、以下の関数を `std.core` に提供する：
     ```sigil
     ct_eq(a: &Bytes, b: &Bytes) -> Bool
       effects none
     ```
   - 実装は、長さが一致しない場合は即座に偽とし（長さは公開情報、ADR 0020）、長さが一致する場合は全バイトを走査して累積排他的論理和を計算する定数時間ループとする（R1 分岐を排除）。
3. **16 進数・2 進数リテラル**:
   - 暗号定数（SHA-256 の初期ハッシュ値 $H^{(0)}$ や定数 $K$）を簡潔に定義するため、`0x` プレフィックスの 16 進リテラル（例: `0x6a09e667`）および `0b` プレフィックスの 2 進リテラル（例: `0b101010`）を導入する。
   - 大文字小文字（`0x1a` / `0x1A`）は許容するが、整形器（`fmt`）によって小文字 `0x...` に統一される。

## 決定 5: ユースケース（暗号・PostgreSQL・OCI）の充足性検証

本 ADR で定める仕様が、後続の P1 タスクの要件を満たすかを検証・マッピングする。

| ユースケース | 必要な操作 | 本 ADR での対応 |
|---|---|---|
| **SHA-256**（段階 6-1） | 32 ビット論理演算（Ch, Maj）<br>32 ビット回転（$\Sigma_0, \Sigma_1, \sigma_0, \sigma_1$）<br>BE パディングと 64 ビット長追記 | `&`, `|`, `^`, `~`<br>`rotr32`<br>`push_u32_be`, `push_u64_be`, `read_u32_be` |
| **HMAC-SHA256**（段階 6-1） | 鍵のパディング（64 バイト）<br>`ipad`（`0x36`）, `opad`（`0x5c`）との XOR | `Bytes.with_capacity`, `push`<br>`^` 演算子と `Bytes` 走査 |
| **PBKDF2**（段階 6-1） | イテレーション毎のブロック XOR<br>ビッグエンディアンカウンタ | `^` 演算子、スライス操作<br>`push_u32_be` |
| **SCRAM-SHA-256**（段階 6-5） | `ClientKey`, `StoredKey` 等のバイト列 XOR<br>`ct_eq` による検証 | `Bytes` のイテレーションと `^`<br>`ct_eq(a, b)` |
| **PostgreSQL Protocol**（段階 6-5） | メッセージ種別（1 バイト Char/Int）<br>パケット長（32 ビット BE 整数）の読み書き<br>可変長バイト列の連結 | `push`, `get`<br>`push_u32_be`, `read_u32_be`<br>`concat`, `extend` |
| **OCI イメージ出力**（段階 6-2） | tar ヘッダ（512 バイトブロック生成、8 進数/固定長バイナリ）<br>チェックサム計算<br>レイヤ digest（SHA-256 ハッシュの 16 進文字列化） | `Bytes.new`, `set`, `slice`<br>`get`, `+` 算術<br>`as_bytes`, `to_string_utf8`, 16 進変換 |

すべてのユースケースについて、必要十分な操作が揃っていることを確認した。

## 影響

- **ADR 0009（字句と文法）**:
  - 整数リテラルに 16 進数（`0x[0-9a-fA-F]+`）および 2 進数（`0b[01]+`）を追加。
  - 式の優先順位表にビット否定 `~`、シフト `<<`, `>>`、ビット演算子 `&`, `^`, `|` を追加。
- **ADR 0011（型システム）**:
  - 基本組み込み型に `Bytes` を追加。
  - ビット演算子の型制約（`Int` 同士の演算で結果は `Int`）を規定。
- **ADR 0018（P1 の範囲）**:
  - PR 2-5 を 2-5a と 2-5b に分割して進める。
- **ADR 0020（セキュリティ追補）**:
  - 決定 1 の前提であるビット演算と `Bytes` 操作が本 ADR により具体化される。
