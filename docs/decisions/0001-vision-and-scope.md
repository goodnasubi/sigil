# 0001: 言語の目標と範囲

- **状態**: 承認（2026-10-22、リポジトリ所有者の決定）

## 背景

初期の README・設計草案では Sigil を「実験的な言語」と位置づけ、性能や既存言語との関係を非目標にしていた。
所有者の意図は、AI が人間に代わってコーディングする実用言語であり、Java・React・Node.js を置き換えることにある。
この差を解消するため、目標と範囲を明文化する。

## 決定

1. **書き手は AI**: コードは AI が書き、AI が読み、AI が保守する。人間がコードを書くことは前提にしない。
2. **人間の役割は仕様のレビューのみ**: 人間はコードを読まない。言語は、仕様（意図・事前条件・事後条件・効果）をコードから機械的に取り出し、人間がレビューできる形で示せなければならない。また、コードがその仕様を満たすことを処理系が検証する。
3. **対象はフロントエンドからバックエンドまで全て**: 1 つの言語で、ブラウザの UI（React の置き換え）、サーバー（Java・Node.js の置き換え）、その間の通信を記述する。
4. **実行方式は独自**: コンパイラと実行環境（ランタイム・標準ライブラリ）を独自に作る。JVM や Node.js の上には載せない。
5. **Rust と同等のメモリ安全性**: 解放後の使用、二重解放、ヌル参照、データ競合などのメモリ不具合を、コンパイル時の検査で起こらないようにする。

## 影響

- **ブラウザでの実行**: ブラウザが直接実行できるのは JavaScript と WebAssembly だけである。独自の実行方式のままフロントエンドを扱うには、WebAssembly を出力先の 1 つにする必要がある（サーバー側はネイティブコードを出力する）。出力先の詳細は別の ADR で決める。
- **メモリ管理**: Rust と同等の安全性をガベージコレクションなしで得るには、所有権と借用のような静的検査が必要になる。Rust ではこの検査が人間にとって難しいことが知られているが、書き手が AI であれば、厳密な規則を課すことの負担は小さいと見込む（未検証の仮説）。
- **非目標の見直し**: 性能と既存資産との連携は、置き換えを目指す以上いずれ必須になる。「当面は後回し」に改める。
- **構文の比較観点**: 構文候補の評価に「仕様を人間に示しやすいか」と「所有権・借用を明示しやすいか」を加える。

## 追加の決定（2026-10-22、リポジトリ所有者の決定）

6. **Python から呼び出せる**: Sigil で書いた関数・型を、Python から呼び出せるようにする。
7. **ブラウザ向けには JavaScript も出力する**: ブラウザ向けの出力先は WebAssembly だけでなく JavaScript も検討の対象にする。

### 追加の決定の影響

- **Python 連携の方式**: 独自の実行方式は変えず、Sigil をネイティブの共有ライブラリとしてコンパイルし、Python 用の束縛（バインディング）を自動生成する方式が有力である（Rust における PyO3 に相当）。方式は別の ADR で決める。
- **境界での安全性**: Python は型や所有権を静的に検査しない。そのため、Python から渡された値に対しては、型・事前条件の検査を呼び出しの境界で実行時に行う必要がある。Python に渡す値は複製するか、Sigil 側が所有したまま参照用の取っ手（ハンドル）だけを渡す。
- **JavaScript 出力でのメモリ安全性**: 所有権と借用の検査はコンパイル時に行うので、JavaScript に出力しても安全性の保証は変わらない。ただし JavaScript ではメモリ解放をガベージコレクションが行うため、資源（ファイル・接続など）の解放時期がネイティブ・WebAssembly と食い違わないよう、言語の意味論として解放時期を決めておく必要がある。
- **出力先の一覧**: サーバーはネイティブコード、ブラウザは WebAssembly と JavaScript、Python 連携はネイティブの共有ライブラリとなる。
- **非目標の見直し**: 「既存言語のライブラリとの連携」のうち、Python から Sigil を呼ぶ方向は後回しにせず目標に含める。Sigil から npm・Maven などの既存ライブラリを使う方向は、引き続き当面は後回しとする。
