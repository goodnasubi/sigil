# 0027: AI が書く前提の安全設計原則（攻撃側 AI の実証知見に基づく）

- **状態**: 承認（2026-11-04。所有者が承認した）
- **日付**: 2026-11-03
- **対象**: 言語設計全体（型システム、標準ライブラリ、ランタイム、ツールチェーン）、および将来の組み込み OS 対象

---

## 背景

2025 年後半以降、サイバー攻撃における AI の役割が「助言者」（文面やコード断片の生成）から「実行者」（偵察→侵入→横展開→持ち出しの連鎖実行）へ移行したことが、複数の独立した公表資料で確認されている。

- Anthropic は、中国の国家支援グループと評価する活動（GTG-1002）が Claude Code と MCP を用いて約 30 の標的へ侵入したと公表した（2025-11-13）。ただし「AI が作業の 80〜90% を実行した」という同社の主張は単独ソースであり、IoC が公開されておらず外部検証はできない。本 ADR はこの数字を根拠にしない。
- Sysdig は、LLM エージェントがエンドツーエンドで実行した初のランサムウェア恐喝と評価する事例（JADEPUFFER、2026-07-01）を公表した。侵入口は修正済み CVE と MinIO / Nacos のデフォルト認証情報であり、手口そのものは従来型だった。
- Google GTIG は、AI で開発されたと評価する初のゼロデイが、メモリ破壊ではなく「ハードコードされた信頼前提」という意味論的ロジック欠陥だったと報告した（2026-05-11）。
- 一方で Mandiant は M-Trends 2026 において「2025 年は侵害が AI の直接の結果だった年とは考えない」と明記している。確認済み事例のほぼ全てで、AI が変えたのは新規の攻撃能力ではなく、速度・並列性・コストである。

Sigil の設計にとって、より直接的な知見は次の 3 点である。

1. **書き手の能力に安全を依存できない。** Veracode の測定（2025-07-30）では、AI 生成コードの約 45% が既知の脆弱性パターンを含むセキュリティテストに不合格であり、2026 年春の追試でも合格率は約 55% にとどまり、モデルが新しく・大きくなっても改善しなかった。Sigil の前提は「AI がコードを書き、人間は仕様だけをレビューする」（[ADR 0001](0001-vision-and-scope.md)）であり、確率的に書かれるコードの欠陥を、言語と検証の側で受け止める設計が要る。
2. **危険なのは低レベルのバグだけではなく、権限と信頼の前提が慣習に埋もれることである。** 上記の AI 製ゼロデイや JADEPUFFER のデフォルト認証情報はその実例である。英 NCSC は、プロンプトインジェクションが原理的に残る理由を「データと命令の分離が言語処理系のレベルで存在しない」ことと分析した（2025-12-08）。裏返すと、データと命令・権限を処理系のレベルで分離できる言語は、実在の攻撃クラスを構造的に消せる。SQL インジェクションがパラメータ化クエリでほぼ解けた歴史がその先例である。
3. **言語レベルの安全策は実測で効く。** CISA / NSA の共同ガイダンス（2025-06）は、メモリ安全言語への移行により Android のメモリ安全性脆弱性の比率が 76%（2019 年）から 24%（2024 年）へ下がったことを引いている。また DARPA AIxCC 決勝（2025-08）で自律システムが成果を上げた鍵は、「再現可能な検証（証拠）と自動パッチ検証」のループだった。

さらに所有者は 2026-11-03、フィジカル AI の到来を前に、Sigil は組み込み OS も対象にする方針を示した。物理世界で動作するソフトウェアでは、侵害時の被害が物理的になりうるため、能力（後述のケイパビリティ）の制御と、安全側に倒れる既定値の重要性がサーバー用途以上に高い。

本 ADR は、これらの実証知見から導かれる安全設計の原則を定める。個別の言語仕様の変更は、各原則ごとに別の ADR と Issue で具体化する。

---

## 決定 1: 情報フロー（汚染）の型レベル追跡

信頼できない入力に由来する値には型の上で出所を付け（taint）、命令位置・権限位置への流入を検査器が拒否する方向を採る。

- 文字列の連結で SQL 文、シェルコマンド、HTML、プロンプト等の「命令」を組み立てる書き方を標準に用意せず、パラメータ化された構築だけを標準とする。
- 汚染の伝播と解除（サニタイズ）の規則は型システムの一部として定義し、解除は明示的な検証関数の通過としてのみ認める。
- 具体的な型設計（注釈の構文、伝播規則、既存の所有権・借用との相互作用）は別 ADR で定める。

## 決定 2: ケイパビリティ指向を既定とし、環境既定の権限（ambient authority）を排除する

ファイル、ネットワーク、時刻、乱数、プロセス起動などの副作用は、暗黙に使える大域権限ではなく、明示的に渡される能力オブジェクト経由でのみ使えるようにする。

- [ADR 0004](0004-effects.md) の効果（effects）の宣言を、能力の宣言として監査可能にする方向で発展させる。「このコードが到達できる範囲」が宣言として読み取れ、人間にも別の AI レビュアーにも機械的に監査できる状態を目標とする。
- 標準ライブラリの既定の入口は、必要最小の能力だけを要求する形に設計する。

## 決定 3: 危険なデフォルトを言語と標準ライブラリから排除する

次に挙げる類の挙動は、標準の書き方では到達不能にする。

- デフォルト認証情報での起動、認証なしでの外部リッスン
- 証明書検証なしの TLS、検証失敗時に処理を続ける fail-open な挙動
- 秘密情報の表示・記録（[ADR 0024](0024-crypto-primitives.md) の `Secret` の表示不可はこの原則の先行例）

根拠は、AI は学習分布で最も多い＝最も簡単な書き方に寄るため、「安全な書き方が最短の書き方」であることが、確率的にコードを書く書き手に対して特に効くことである。

## 決定 4: 機械可読で高速なフィードバックを言語仕様の一部とする

AI の開発ループは「生成→検証→修正」の反復速度で決まる。以下を利便性ではなく安全機構として扱う。

- 診断は人間向け文章だけでなく、機械が消費できる構造化形式（エラーコードと位置情報）で出す。
- 決定的なフォーマッタ、再現可能なビルドとロックファイルを標準とする。
- 依存は出所（provenance）と署名を持ち、実在が確認できない依存名を解決時に弾く（存在しない API やパッケージの幻覚、および slopsquatting 型の混入への対策を兼ねる）。

## 決定 5: 仕様と意図を機械検証可能な形で書けるようにする

事前条件・事後条件、プロパティテスト、ファジングの組み込み支援を標準装備の方向とし、「AI が書いた実装」と「人間（または別の AI）が書いた検証可能な仕様」を分離できるようにする。人間の注意が最も希少な資源になる前提では、レビュー対象を「全コード」から「仕様と境界」へ寄せることが合理的である。

## 決定 6: 曖昧さを減らす

暗黙の型変換、文脈依存のオーバーロード、環境依存の挙動は、AI の幻覚（存在しない API の使用）と相性が悪い。小さく規則的な意味論を保ち、新しい言語機能の追加時には「AI が誤用しやすい形になっていないか」を審査項目に加える。

## 決定 7: 観測可能性を既定にする

構造化ログ、トレース、権限使用の記録が、ランタイムの標準的な出力として得られるようにする。AI が書いたコードの事後監査可能性は、実行時の機能と同じ設計上の価値を持つ。Five Eyes の共同ガイダンス（2026-05-01）が AI エージェントのリスク区分の一つに「説明責任」を置いたこととも整合する。

## 決定 8: 組み込み・フィジカル AI 対象への適用

上記の原則は、組み込み OS 対象では特に厳格に適用する。

- 物理的な動作（アクチュエーション）に至る能力は、明示の能力に加えて人間の承認境界を必須とする形を標準とする。
- リソース制約の下でも、秘密のゼロ化や定数時間性（[ADR 0024](0024-crypto-primitives.md)）のような保護を落とさない。具体的な制約（メモリ上限、リアルタイム性、no_std 相当のランタイム形態）との両立は、組み込み対象の段階 ADR で定める。

## 却下した代替案

- **モデルの改善に任せる**: Veracode の追試が示すとおり、モデルが新しくなっても生成コードの合格率は改善しなかった。書き手の能力向上は歓迎するが、安全の根拠にはしない。
- **実行時の監視だけで守る**: 振る舞いの検知は必要だが（決定 7 はその前提を支える）、言語で表現不能にできる攻撃クラスは設計で消す方が確実である。監視は代替ではなく補完として位置づける。
- **人間が全コードをレビューする前提に戻す**: [ADR 0001](0001-vision-and-scope.md) の前提と矛盾し、AI の生成量に対して持続しない。レビュー対象を仕様と境界へ寄せる（決定 5）のが本 ADR の立場である。

## 影響と未決事項

- 本 ADR は原則の宣言であり、言語仕様の具体的な変更を含まない。各決定の具体化は、別 ADR・別 Issue として、仕様に影響する変更の承認手続きに従って進める。
- 既存の ADR（[0003](0003-ownership-and-borrowing.md) 所有権と借用、[0004](0004-effects.md) 効果、[0020](0020-p1-security-addendum.md) P1 セキュリティ補遺、[0024](0024-crypto-primitives.md) 暗号）とは整合させる前提で書かれている。具体化の過程で矛盾が見つかれば、その ADR の側で扱う。
- 未決事項: 汚染型の具体設計、能力の受け渡しの構文、既存の P0 / P1 実装への遡及適用の範囲、組み込みランタイムの形態。
