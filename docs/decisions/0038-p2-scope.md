# 0038: P2 の範囲（Web フルスタックと仕様レビュー IDE）

- **状態**: 提案（範囲は typesafe-ai で正式判定済み。別系統のレビュー前）
- **日付**: 2026-11-16（JST）
- **対象**: [Issue #553](https://github.com/goodnasubi/sigil/issues/553)

## 背景

[ADR 0005](0005-long-term-goals.md) は、P2 で Web フルスタック（G1）と IDE（G8）を作り、各段階の最初の範囲を開始時の ADR で決めるとしている。Issue #553 により P1 は 7-1 まで完了している。本 ADR は P2 の段組み・各段の範囲・完了条件を定める。Next.js や既存 IDE の全機能互換は P2 の完了条件にしない。

人間は仕様だけをレビューし、AI がコードを書く（[ADR 0001](0001-vision-and-scope.md)）。IDE はこの役割分担を画面にする最初の大きな Sigil 製 Web アプリケーションとする。

既存の決定を再利用する。

- [ADR 0004](0004-effects.md): 効果の完全一致検査・出力先制限・UI イベント入口の効果宣言。
- [ADR 0008](0008-m0-notation.md)・[ADR 0019](0019-m6-machine-spec-and-language-server.md): 日本語の仕様と構造化 JSON、検査診断、標準入出力の LSP。表示用の仕様を IDE 内で別に生成しない。
- [ADR 0033](0033-p1-framework.md): `std.web`、設定・入力検証・既定拒否の認証・上限・停止処理。P2 用の別サーバーを作り直さない。
- [ADR 0027](0027-ai-era-security-design-principles.md): 明示的な権限、最小の信頼基盤、独立した検証。

起草時の基準は `main` の `994f045`。本 PR は ADR だけとし、処理系・`sigil spec` の出力・実装・バックログを変更しない。

## 選択肢

| 判断 | 採用案 | 他の案と見送る理由 |
|---|---|---|
| 出力と順序 | JS を先に単独で使える出力とし、UI とフルスタックを経て Wasm を加える | Wasm 先行／両出力同時完成は、ホスト境界と出力器の二つを揃えるまで UI を使えない |
| UI とサーバー | 宣言 UI、明示的な効果、P1 の拡張、型付き通信 | React／Next.js 互換・SSR・hydration を最初から必須にすると範囲が広い。別サーバーは P1 の検証済み境界を重複させる |
| IDE | 仕様表示→仕様差分→検証結果の確認 | 汎用エディタの全機能は人間の役割と一致しない。表示だけでは仕様変更と検証の確認が完結しない |

正式判定は末尾に入力・応答を記録した。同じ評価軸で上記三案が選ばれた。確率は設計の正しさの証明ではなく、採用理由は既存 ADR との整合と各段の検証可能性に置く。

## 決定 1: 段組みと各段の成果物

原則の依存順は P2-1→P2-2→P2-3→P2-4→P2-5 とする。IDE の仕様表示は P2-3 の後に先行してよいが、P2 全体の完了には P2-4 を含む全段が必要である。各段は小さい実装 PR に分け、後続がなくても利用・検証できる成果物を残す。

| 段 | 最初に含める範囲 | その段の完了を確かめる方法 |
|---|---|---|
| P2-1: JavaScript 出力 | 検査済みのブラウザ向け純粋な核（数値・文字列・コレクション・関数・所有権・契約）と最小ホスト境界。生成物は Node.js なしで既存ブラウザで動く | 共通プログラムで SIR 評価器と値・契約失敗・資源の破棄順序を比較。未対応機能・サーバー専用効果は生成前に診断する |
| P2-2: UI の記述モデル | 宣言的な要素・テキスト・属性・一覧・イベント・入力フォーム。明示的な状態と更新による再描画。標準 HTML/CSS で配置・装飾する | カウンター・入力検証・一覧更新をブラウザで操作でき、イベントと描画の効果検査・文字列の安全な表示を確認する |
| P2-3: フルスタック | 一つのプロジェクトの browser/server/common 分離、型付き要求応答、同一オリジン HTTP、静的資産配信と成果物生成。サーバーは P1 のネイティブ出力 | Sigil UI→検証済みサーバー処理→UI 更新の小さいアプリを P1 のコンテナで実行。入力不正・認証失敗・上限超過が拒否され、秘密がブラウザ配信物に入らないことを確認する |
| P2-4: WebAssembly 出力 | P2-1 の同じ核を Wasm でもブラウザ実行し、P2-2 の UI と P2-3 の通信に接続する。JS ホスト層を共有する | JS・Wasm・SIR 評価器で共通の適合例と失敗例を比較し、同じ小アプリを両出力で操作する |
| P2-5: 仕様レビュー IDE | Sigil 製 Web アプリとして、仕様表示・二つの版の仕様差分・版に対応する検証結果。既存 LSP を AI の窓口として維持する | 変更前後の仕様と検査成功／失敗／未検証を Docker 配布物の画面で確認し、AI 向け LSP の既存機能も利用できる |

各出力器の初版に含む具体的な構文・型・標準操作、数値表現、文字列 ABI、所有値の破棄、ホスト呼び出し、CLI は P2-1／P2-4 の個別 ADR で実装前に列挙する。「核」は全言語機能の実装済みを意味しない。IDE が使う機能は両出力で対応させ、暗黙の縮退で完了扱いにしない。

## 決定 2: JS と Wasm の役割

JavaScript 単独出力を使える製品として維持する。Wasm では Sigil の核の処理をコンパイルし、DOM・ブラウザのイベント・通信・読み込みは生成した JS ホスト層を介する。Wasm を選んだときに未対応処理を黙って JS 実装へ切り替えない。小さい明示的なホスト境界への呼び出しと、出力器の代替実行を区別する。

JS の GC に所有値の資源解放時期を任せない。整数・浮動小数・Unicode・契約・異常終了・破棄順序は共通の言語の意味を満たす。ブラウザで許さないファイル・DB・環境変数・待受操作をホスト経由で開放しない。Wasm の導入で効果・所有権検査を弱めない。

## 決定 3: 宣言 UI と効果・契約

表示の構造は状態から値を作る純粋な関数で表し、イベントから明示的に状態を更新する。DOM を操作する描画器とイベントの入口には `dom` 等の実際の効果を書く。共有状態・通信・待機を行う場合も既存の `state`・`net.client`・`task.suspend` 等の規則に従い、描画の裏で隠れた I/O を起こさない。

契約と篩型による入力検証を UI に接続しても、サーバーでの再検証は省略しない。テキストは安全な DOM 操作で表示し、任意 HTML・任意 JavaScript の文字列注入を初版 API にしない。イベントの寿命と所有権、コールバックの効果上限、URL・属性の許可範囲は UI の個別 ADR で定める。新しい JSX 構文や効果カテゴリを本 ADR では追加しない。

## 決定 4: P1 の上に置くフルスタック

ブラウザ・サーバー・共有のコードを同じプロジェクトで検査・ビルドし、配信物は分離する。サーバーへの呼び出しは型付き要求応答の通信境界とし、通常の関数呼び出しに偽装して効果や失敗を隠さない。共有する型があっても受信データは信頼せず、構造・篩型・サイズ上限を境界で検査する。

P1 の `std.web` と既定拒否の認証、設定・JSON・HTTP 上限を再利用する。ブラウザへは公開する型・通信定義と必要なコードだけを配り、サーバー用モジュール・秘密値・設定を含めない。同一オリジンを初版の範囲とする。HTTP/2・WebSocket・任意クロスオリジン・SSR・hydration・汎用 RPC・既存 npm ライブラリ互換は必須にしない。

ブラウザからの認証接続方式・CSRF/XSS 対策・資産経路・通信形式・期限や件数の上限は個別 ADR で確定する。P1 の Bearer 検証を、ブラウザに署名鍵を渡す設計に読み替えない。本 ADR は新たな認証方式や外部公開の承認ではない。

## 決定 5: IDE の初版と持ち越し

最初の画面は既存の `sigil spec --json` の `text` と構造を利用する仕様表示とする。次に仕様差分、最後に検証結果の確認を加える。

- 差分は利用者が指定した二つのワークスペースの版（スナップショット）を比較し、モジュール・項目・型・契約・効果の追加／削除／変更を示す。名前変更は当面削除と追加でよい。Git そのものの実装は P4 に属する。
- 検査・検証結果は、入力の版・対象・実行した検査と結び付ける。古い結果・未実施・失敗・反例・証明済みを混同せず、対応していない検証は未検証として示す。型検査成功を契約の証明済みと表示しない。
- サーバーが起動時に許可されたワークスペースだけを読み、既存コンパイラと言語サーバーを利用する。ブラウザから任意のパス・コマンド・`--trust-base` の追加を許さない。橋渡し方式・並行実行・入力／出力／時間の上限は IDE の個別 ADR で定める。コンパイラをブラウザへ移植することは必須にしない。
- AI 向けは既存 LSP の診断・仕様参照を維持する。補完・定義参照・名前変更・複数診断・ファイル監視の拡張は初版の必須範囲にしない（ADR 0019 からの持ち越しをここで区切る）。
- 契約式の自然言語訳（ADR 0008／0019 の持ち越し）は P2 の必須範囲から外す。既存の正規形の式と日本語の定型文を表示し、推測による訳で意味を変えない。追加する際は別 ADR で正確さを決める。

汎用のソース編集画面、端末・任意シェル、拡張機能市場、共同編集、AI エージェントの自動実行は初版に含めない。AI が作った変更を仕様としてレビューできることを初版の単位にする。

## P2 全体の完了条件

1. P2-1〜P2-5 の成果物が揃い、JS と Wasm の両方で同じ UI・フルスタック適合例が動く。未対応機能が明示され、共通の検査と意味論を維持する。
2. Sigil 製 IDE を P1 の Docker／OCI 配布物として起動でき、仕様表示・二版の仕様差分・版に対応する検証結果を一続きで確認できる。ブラウザ出力を明示的に選んで両方で確認できる。
3. 既存 LSP の AI 向け診断・仕様参照を維持し、CLI と IDE の仕様・検査結果が一致することを自動確認する。
4. 各段の適合・境界拒否・ブラウザ操作・コンテナ統合の検証記録を残す。各段の個別 ADR が定める安全上の確認・必要な承認を完了する。P1 からの外部公開前の残課題を P2 開始によって解決済みとは扱わない。

## 影響と実装前に確定すること

本 ADR は範囲の決定であり、言語の細部・ホスト ABI・新しい信頼基盤への包括的な承認ではない。出力器、UI、フルスタック、IDE の各段で上記の未確定事項を個別 ADR にし、契約変更→ADR→実装→サンプル・テストの順で進める。依存追加やセキュリティ対象は既存の承認手続きを維持する。

P1 の外部公開前の残課題は Issue #547〜#552 で別管理されている。本 ADR で修正や再起票はしない。P2 の開始条件と、成果物を外部公開できる条件を分けて記録する。
