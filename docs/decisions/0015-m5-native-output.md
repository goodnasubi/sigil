# 0015: M5 の範囲と、ネイティブ出力のコンパイラ構成（中間表現・ランタイム・リンカ）

- **状態**: 提案（2026-10-25。Claude の案。依存の追加（Cranelift）・ビルド環境の前提・CI は人間の判断が要る（いずれも未承認）。末尾の「人間の判断が要る点」を参照）

## 背景

M4 は完了した（[ADR 0014](0014-core-and-os-split.md) の PR1・PR2a・PR2b まで。main `6d4ae05`）。次の段階 M5 は、[ADR 0006](0006-p0-scope-and-bootstrap.md) の決定 2 で「ネイティブ出力（Linux x86-64、Cranelift）。`sigil build` で単一の実行ファイルを出力できる」と定めた。M5 の前に決める論点として、同 ADR の決定 4 は「出力先とコンパイラ構成（中間表現の形とリンカ）」を挙げ、ADR 0014 は「M5 に引き継ぐこと」として暫定ランタイムの核と OS 層への分割を挙げた。

M5 の完了条件（ADR 0006）:

- 4 つのサンプルを `sigil build` で実行ファイルにでき、その実行結果（標準出力・終了コード・契約違反による停止）が M4 のインタプリタと一致する（差し替えた `fs.read` の入力は実際のファイルとして置く）。
- 出力した実行ファイルが、Sigil の処理系を入れていない Linux x86-64 の環境（最小のコンテナ）で動く。
- 決定 3 の条件 9（破棄の順序）・10（核だけのプログラムが OS の機能に依存しない）のテストを、実行ファイルでも通す。

本 ADR は、M5 の範囲を確定し、実装担当がそのまま作れる粒度でコンパイラ構成を決める。あわせて、ADR 0014 が積み残した「信頼基盤（`trust base`）の宣言方法」の ADR との順序を決める。

### 現状（main `6d4ae05`）

- 処理系は `parse` → `check`（型・効果・所有権・借用）→ `interp`（AST を直接たどる）の 3 段。検査器 `src/check.rs` は結果（式の型・メソッドの解決・型引数の具体化）を外に出さない（`check_file` は `R<()>`）。
- AST の式（`ast::Expr`）は位置（`Span`）を持たない。
- 外部依存のクレートはない（`Cargo.toml` の注記「依存クレートの追加は人間の承認が要る」）。
- リポジトリに CI の設定（`.github/` など）はない。
- ビルド環境（この開発用の container）には `cc`（gcc）、`/usr/lib/x86_64-linux-gnu/libc.a`（glibc の静的ライブラリ）、Rust 1.97 の `x86_64-unknown-linux-gnu`（`rust-lld` 同梱）、`docker` がある。`x86_64-unknown-linux-musl` の標準ライブラリは入っていない。

## 評価の観点

重要な順に並べる。

1. **意味の一致**: 実行ファイルの結果が、意味論の基準である M3・M4 のインタプリタと一致すること（ADR 0006 の決定 2 の A の欠点を補う手段）。一致を自動テストで確かめられること。
2. **後の段階で作り直さずに済むか**: 中間表現が出力先に依存しない（P2 の WebAssembly・JavaScript）。暫定ランタイムを Sigil の信頼基盤に置き換えるとき（P1）、Sigil のプログラムが変わらない。
3. **AI が誤りなく実装できるか**: 部品の境界が明確で、各部品を単独でテストできること。
4. **依存と環境の前提を最小にすること**: 追加するクレートと、ビルド環境に求める道具が少ないこと。

## 決定 1: M5 の範囲

### 選択肢

- **A: インタプリタが実行できるものすべて**。`sigil run` が実行できるプログラムは `sigil build` でも実行ファイルにでき、結果が一致する。一致は、既存のインタプリタのテストの事例を実行ファイルでも動かして確かめる
- **B: 4 つのサンプルだけ**。サンプルが使わない構文は `sigil build` がエラーにする
- **C: A を M5a（サンプル）と M5b（残り）に分ける**

### 決定

**A** を採用する。

- **対象の出力**: Linux x86-64 の、静的にリンクした ELF の実行ファイル（決定 6）。`targets` に `bare` を含むモジュールも同じ形で出力する（ADR 0014 の決定 1。実行環境なしの出力は P6）。`browser` だけのモジュールも、P0 では同じ形で出力する（`targets` は書けるコードの制約で、出力の指定ではない）。
- **言語の範囲**: `sigil check` を通り、インタプリタが実行できるすべての構文と標準ライブラリ（ADR 0013 の決定 2 と ADR 0014 の決定 2 の一覧）。
- **作りかけの間**: 未実装の構文は `sigil build` が `ErrorKind::BuildUnsupported`（新設。検査のエラーと同じ終了コード 1）で止める。M5 の完了は「`BuildUnsupported` を出す箇所が処理系に残っていない」ことを条件とする（下の完了条件のテスト `no_build_unsupported_left`）。
- **一致の確かめ方**: 次のテストの、インタプリタを呼ぶ補助関数（`ok`・`stopped`・`run_sources_with` を包む関数など）の事例を、すべて実行ファイルでも動かして比べる（決定 8 の「差分の比較」）。
  - `tests/interp.rs`・`tests/m3_stdlib.rs`・`tests/m3_drop_order.rs`・`tests/m3_fs_cell.rs`・`tests/m4_effects.rs`・`tests/m4_core_split.rs` の実行の事例
  - 5 つのサンプル（`01`〜`05`）とテスト用の入口
- **対象外**: `tests/m3_drop_limits.rs` の事例（インタプリタの移動の追跡が粗く、破棄の位置が仕様の想定とずれることを固定したもの。ADR 0006 の M3 の記録で「M5 の出力で詰める」とした）。M5 の実行ファイルは仕様の想定（決定 5 の破棄の規則）どおりに破棄し、その結果を新しいテストで固定する。インタプリタとの食い違いは、`m3_drop_limits.rs` の各事例に「実行ファイルの順序」を並べて記録し、インタプリタを直すかは M5 の後に決める。

### 理由

- 観点 1: B ではサンプル以外の構文の意味の一致が確かめられず、M6・P1 で初めて食い違いが見つかる。既存のテストの事例は ADR 0013・0014 の意味（停止・破棄・標準ライブラリ）をすでに固定しているので、それを流用すれば一致の基準を新しく書かずに済む。
- 観点 3: 事例は既にあり、補助関数を 1 か所包むだけで両方を動かせる。
- C は段階を増やすだけで、M5b の範囲は結局 A と同じになる。作りかけの間の扱いは `BuildUnsupported` で足りる。

### 選ばなかった案と理由

- **B（サンプルだけ）**: 上のとおり。P1 のフレームワークを書くときにネイティブ出力が使えない構文が残る。
- **C（M5a / M5b）**: 段階の名前が増えるだけで、作業の順は A の実装の手順と同じになる。

## 決定 2: 中間表現

### 選択肢

- **A: 型を検査した AST から、単相化（型引数を具体化）した中間表現（基本ブロックの並び）を作り、そこから Cranelift の IR を作る**
- **B: 型を検査した AST から直接 Cranelift の IR を作る**
- **C: 中間表現を Cranelift の IR とする**（P2 でも Cranelift を経由する）

### 決定

**A** を採用する。中間表現を **SIR**（Sigil IR）と呼び、`src/ir.rs` に定義する。

#### 形

```rust
pub struct Program {
    pub funcs: Vec<Func>,            // 単相化した関数（同じ総称の関数の具体化ごとに 1 つ）
    pub types: Vec<TypeDef>,         // 構造体・列挙型の具体化ごとの定義
    pub strings: Vec<String>,        // 文字列のリテラル
    pub stop_sites: Vec<StopSite>,   // 異常停止の報告（種類・関数・行・during）。決定 5
    pub entry: FuncId,
    pub core_only: bool,             // モジュールの targets に bare がある（決定 6 のリンク）
}
pub struct Func { pub name: String, pub params: Vec<LocalId>, pub ret: Ty, pub locals: Vec<Local>, pub blocks: Vec<Block> }
pub struct Block { pub stmts: Vec<Stmt>, pub term: Term }
pub enum Ty { Int, Float, Bool, Unit, Str, Path, IoError, List(Box<Ty>), Tuple(Vec<Ty>),
              Adt(TypeId), Ref(Box<Ty>), MutRef(Box<Ty>), Shared(Box<Ty>), Cell(Box<Ty>), FnRef(Vec<Ty>, Box<Ty>) }
pub enum Stmt {
    Assign(Place, Rvalue),
    Drop(Place),                     // 破棄（決定 5 の順で lowering が並べる）
    Move(Place),                     // 移動した元を「空」にする（破棄の対象から外す）
}
pub enum Term {
    Goto(BlockId),
    Branch(Operand, BlockId, BlockId),
    Switch(Operand, Vec<(i64, BlockId)>, BlockId),   // 列挙型の腕
    Call { func: Callee, args: Vec<Operand>, dest: Place, next: BlockId, cleanup: BlockId },
    CheckedOp { op: ArithOp, a: Operand, b: Operand, dest: Place, next: BlockId, stop: StopId, cleanup: BlockId },
    Assert { cond: Operand, stop: StopId, next: BlockId, cleanup: BlockId },  // requires・ensures・篩型・標準の requires
    Return,
    Resume,                           // cleanup の終わり: 停止を呼び出し元へ伝える
}
```

- **単相化**: 総称の関数・型は、使われた具体化ごとに複製する（`List<Int>` と `List<String>` は別の型）。`clone` と `Copyable` の判定は具体化した型で決める。境界（`Displayable`・`Comparable`・`Numeric`）に依存する呼び出し・演算（表示・比較・算術）も、具体化した型で選ぶ（SIR には境界による間接の呼び出しを残さない）。
- **契約**: `requires` は入口の `Assert`、`ensures` は各 `Return` の直前の `Assert`、`old(e)` は入口で一時の局所変数に評価しておく。契約の式の中の異常停止は `StopSite.during` を持つ別の停止の地点にする（ADR 0013 の決定 1）。
- **関数の値**: `FnRef` は（コードの番地, 環境の番地）の組。引数に渡すのは呼び出しの間の借用（ADR 0013 の決定 3）なので、環境を複製も移動もしない。クロージャの環境は、とらえた値を並べた構造体として `types` に置く。
- **再帰する列挙型**: 循環を通る腕の中身は、処理系がヒープに置く（ADR 0013 の決定 2 の「間接化の型は置かず、処理系が間接化して持つ」）。lowering が `Adt` の欄に間接の印を付ける。
- 出力先に依存しない: SIR は Cranelift の型も呼び出し規約も持たない。P2 の WebAssembly・JavaScript 出力は SIR から作る。

#### SIR の評価器

`src/ir_eval.rs` に、SIR を直接実行する評価器を置く。用途はテストだけで、lowering の誤りを Cranelift と切り離して見つけるため（下の実装の手順の PR2）。結果の表示・停止の報告・破棄の記録は、インタプリタと同じ形（`interp::Outcome`・`Failure`）で返す。

### 理由

- 観点 2: ADR 0006 の決定 1 は「中間表現は出力先に依存しない形にする」と決めている。B・C では P2 で lowering をもう一度作ることになる。
- 観点 1・3: 破棄の順序（条件 9）・移動した値を破棄しないこと・異常停止の経路は、型と制御の流れの両方を見て決める。これを SIR の 1 か所（lowering）で決め、Cranelift の段は SIR を機械的に訳すだけにすると、意味の誤りと出力の誤りを分けて探せる。SIR の評価器で、依存を加える前に lowering を確かめられる。

### 選ばなかった案と理由

- **B（AST から直接）**: 単相化・破棄・停止の経路を Cranelift の IR を作りながら決めることになり、意味の誤りと出力の誤りが混ざる。P2 で作り直しになる。
- **C（Cranelift の IR を中間表現に）**: WebAssembly は Cranelift の入力ではなく出力の側で、JavaScript は扱えない。

## 決定 3: 検査器から lowering への型の情報の渡し方

### 選択肢

- **A: 検査器が、式ごとの型・呼び出しの解決（どの関数・メソッドか、型引数の具体化）・移動の地点を表に記録し、`check::typed(&File) -> R<Typed<'_>>` で返す。表の鍵は式の番地（`*const Expr as usize`）とする**
- **B: AST の式に通し番号（`ExprId`）を持たせる**
- **C: lowering が自分で型を推論し直す**

### 決定

**A** を採用する。

```rust
pub struct Typed<'a> {
    pub file: &'a File,                              // 番地が有効な間だけ使えるよう借用で結ぶ
    pub expr_ty: HashMap<usize, Ty>,                 // 式の番地 -> 具体化前の型（型引数を含みうる）
    pub calls: HashMap<usize, Resolved>,             // 呼び出しの式 -> 解決した関数・メソッドと型引数
    pub moves: HashSet<usize>,                       // 値を移動する名前の式（それ以外の読みは複製か借用）
    pub let_ty: HashMap<usize, Ty>,                  // `let` の文の番地 -> 束縛した型
}
```

- 検査器は、冗長な型注釈の判定のために注釈を外して検査し直す（`Ck` の `skip`・`annot_n`）。表に記録するのは、外さずに検査した 1 回目だけにする（`skip.is_none()` のときだけ記録する）。
- 検査器の中で式を複製して検査する箇所があれば、複製の番地を記録しない（元の番地だけを鍵にする）。
- `Ty`（`check.rs` の内部の型）は `pub(crate)` にして lowering から使う。外に出す API は `Typed` だけで、`sigil check` の動作は変えない。
- 漏れの検出: 「`file` の中のすべての式に `expr_ty` がある」ことを、サンプルとテストの全ソースで確かめる単体テストを置く（`typed_covers_every_expr`）。

### 理由

- 観点 3: AST の形も、パーサ・整形器・仕様の抽出も変えずに済む。C は型推論を 2 つ持つことになり、食い違いが意味の不一致として M5 の後に見つかる。
- B は `ast::Expr` の全ての腕と、AST を作る全ての箇所（パーサ・テスト）を変える大きな変更で、M5 の成果を前に進めない。

### 選ばなかった案と理由

- **B（`ExprId`）**: 上のとおり変更が大きい。言語サーバー（M6）で位置の情報が要るときに、`Span` と合わせて改めて検討する。
- **C（推論し直す）**: 上のとおり。

## 決定 4: 値の表現

SIR の型を、Cranelift の段で次の表現にする。表現は実行ファイルの中だけのもので、言語の意味には現れない。

| 型 | 表現 |
|---|---|
| `Int` | `i64`。桁あふれ・0 での除算・最小値を `-1` で割ることは `CheckedOp` で検出する |
| `Float` | `f64` |
| `Bool` | `i8`（0・1） |
| `Unit` | 値を持たない（引数・戻り値から除く） |
| `String`・`Path` | ランタイムが持つヒープの領域への番地 1 つ（中身は UTF-8 のバイト列・長さ・容量）。`len` は Unicode のスカラー値の数をランタイムが数える |
| `List<T>` | ランタイムが持つ領域への番地 1 つ（要素の大きさは具体化した `T` で決まり、生成したコードが渡す） |
| 構造体・組 | 欄を宣言の順に並べた、生成したコードが持つ領域（スタック上か、入れ物の中ではヒープ上） |
| 列挙型 | 腕の番号（`i64`）と、最も大きい腕の中身の領域。循環を通る腕の中身はヒープへの番地 |
| `&T`・`&mut T` | 番地 |
| `Shared<T>` | ヒープの領域（参照の数 `i64` と `T`）への番地。参照の数は原子的でない（単一スレッド用。ADR 0006 の条件 2） |
| `Cell<T>` | `T` と同じ領域（中身をその場で書き換える） |
| 関数の値 | （コードの番地, 環境の番地）の組 |
| `IoError` | 腕の番号と、パスの `String` |

- 呼び出し規約は Cranelift の既定（System V）。Sigil の関数どうしの呼び出しには、隠れた戻り値として「停止中」の印を足す（決定 5）。
- メモリの確保と解放は、ランタイムの `sigil_rt_alloc`・`sigil_rt_free` を呼ぶ（ADR 0014 の決定 2: 確保器は環境が供給する）。

## 決定 5: 異常停止と破棄

### 選択肢

- **A: 停止の印を戻り値で伝える**。異常停止は、その地点の停止の番号を印に入れて `cleanup` の block へ進み、生きている値を破棄して呼び出し元へ戻る。呼び出し元は呼び出しの後で印を調べ、立っていれば自分の `cleanup` へ進む。入口まで戻ったら、ランタイムが報告を出して終了コード 70 で終わる
- **B: 巻き戻し（unwinding）**。停止の地点から、例外の巻き戻しの表（`.eh_frame`）を使って枠を戻りながら破棄する
- **C: 破棄せずにその場で終わる**

### 決定

**A** を採用する。

- `?` による早期の戻りと異常停止は、同じ `cleanup` の並びを通る（ADR 0006 の M3 の記録「すべての異常停止は同じ解放の経路を通る」）。lowering は、各地点で生きている値を宣言の逆順に破棄する `cleanup` の block を作る（内側のスコープから外側へ。1 つの値は自分を先に、続いて欄・要素を宣言の順に。ADR 0006 の条件 9）。
- 移動した値（`Stmt::Move`）は破棄しない。構造体の一部の欄だけの移動・`match` の束縛による移動・値を消費する標準のメソッドの受け手・クロージャの環境に取り込まれた値も、仕様の想定どおり、移動した値を破棄しない（インタプリタの既知の制限。決定 1 の対象外）。
- **スタックの枯渇**: 生成した各関数の入口で、スタックの番地（Cranelift の `get_stack_pointer`）をランタイムが決めた下限と比べ、下回れば `StackExhausted` の停止として同じ `cleanup` の経路を通る。ランタイムは、インタプリタと同じく 256 MiB のスタックを持つスレッドで入口を呼び、下限をスタックの上端（スレッドの入口で読んだスタックの番地）から 192 MiB 下に置く。残りの 64 MiB は、ランタイムの関数と停止の報告・破棄の経路が使う余裕である。止まる深さは枠の大きさが違うのでインタプリタと一致しない（比べるのは停止の種類と、破棄の記録の形だけ。決定 8）。
- **報告**: 停止の地点ごとに、インタプリタの `interp::Stop` の表示（`異常停止: 種類（関数 名前、N 行目）` と `during`）と同じ文字列を、lowering が `stop_sites` に作っておく。ランタイムはそれを標準エラーに 1 行で出す。インタプリタの表示とずれないよう、`Stop` の表示の文字列を作る関数を `interp.rs` から `src/report.rs` に移し、lowering とインタプリタが共に使う。
- 異常停止の中の異常停止（破棄の途中の停止）はない（破棄は利用者のコードを呼ばない。P0 には利用者の破棄の処理がない）。

### 理由

- 観点 1: A は、M3 のインタプリタの「破棄してから停止する」を同じ形で作るので、条件 9 の順序がインタプリタと揃う。
- 観点 4: B は巻き戻しの表と、ランタイム側の巻き戻しの処理（`libunwind` など）が要る。Cranelift の巻き戻しの情報の出力は限られ、静的リンクでの扱いも難しい。性能は非目標（DESIGN.md の 4 章）なので、呼び出しごとに印を調べる費用は問わない。

### 選ばなかった案と理由

- **B（巻き戻し）**: 上のとおり。
- **C（破棄しない）**: 条件 9（停止のときの破棄の順序）を満たせない。

## 決定 6: 暫定ランタイムとリンク

### ランタイムの構成

- **2 つのクレート** に分ける（ADR 0014 の「M5 に引き継ぐこと」）。どちらも外部のクレートに依存しない（Rust の標準ライブラリだけ）。`crate-type = ["staticlib"]`。
  - `runtime/core`（クレート名 `sigil_rt_core`）: 確保と解放、`String`・`List`・`Shared` の操作、値の表示（戻り値の表示・`Displayable`）、異常停止の報告と終了コード 70、スタックの下限、入口の引数の読み取り（`sigil run` と同じ書き方）、破棄の記録（決定 8）。
  - `runtime/os`（クレート名 `sigil_rt_os`）: `console.log`、`fs.read`・`fs.write`、`Path` の操作、`IoError`。ADR 0014 の決定 2 の OS 層の一覧と 1 対 1 に対応する関数だけを持つ。
- 関数の名前は `sigil_rt_` で始め、`extern "C"` とする。境界は ADR 0014 の決定 2 の宣言で、Sigil のプログラムから名前で呼ぶ手段は作らない（ADR 0006 の「境界」）。
- **意味の共有**: インタプリタとランタイムで同じ意味の処理（`Float` の表示・`String.lines`・`parse_int`・`trim`・`Path` の `join`・`file_name`・`parent`・入口の引数の読み取り）は、1 つの Rust のファイルに書き、両方から `#[path = "..."] mod` で取り込む（`src/shared/` に置く）。インタプリタの現在の実装をそこへ移す。2 つの実装を持たない。

### ランタイムの組み込み

- ルートの `build.rs` が、2 つのランタイムのクレートを `cargo build --release --manifest-path runtime/<名前>/Cargo.toml --target-dir $OUT_DIR/rt` でビルドし、できた `.a` を `include_bytes!` で `sigil` の実行ファイルに埋め込む。`sigil build` は、それを一時ディレクトリに書き出してリンクに使う。処理系は単一の実行ファイルのまま配れる（ADR 0006 の決定 1 の観点 4）。
- ランタイムのクレートはワークスペースの外に置き（ルートの `Cargo.toml` に `[workspace]` を作らない）、`build.rs` から別の `--target-dir` でビルドする。同じ target ディレクトリを使う入れ子の `cargo` は、ロックの待ち合いで止まるためである。

### リンカと出力の形

### 選択肢

- **A: 環境の `cc`（gcc の駆動）で、glibc の静的ライブラリ（`libc.a`）と静的にリンクする**（`cc -static -no-pie -o 出力 生成.o libsigil_rt_core.a [libsigil_rt_os.a] -lpthread -ldl`）
- **B: Rust に同梱の `rust-lld` を直接呼ぶ**。起動のオブジェクト（`crt1.o` など）と `libc.a` の場所を処理系が探して渡す
- **C: musl の標準ライブラリ（`x86_64-unknown-linux-musl`）でランタイムをビルドし、musl と静的にリンクする**

### 決定

**A** を採用する。

- 生成したコードは `cranelift-object` で ELF のオブジェクト（`.o`）にする。
- `Program.core_only`（モジュールの `targets` に `bare` がある）なら、`libsigil_rt_os.a` をリンクに渡さない。生成したコードが OS 層の関数を 1 つでも呼んでいればリンクが失敗するので、ADR 0006 の条件 10 の M5 側（核だけのプログラムが OS の機能に依存しない）は「リンクが成功する」ことで確かめられる。
- 出力は動的リンクを持たない ELF（`PT_INTERP`・`PT_DYNAMIC` がない）にする。
- `cc` が見つからない・`libc.a` がないときは、`sigil build` は理由と必要な道具を示して終了コード 1 で止める。

### 理由

- 観点 4: A は、ビルド環境の標準の道具だけで動き、起動のオブジェクトの場所を処理系が知る必要がない。この開発環境には `cc` と `libc.a` がある。
- B は起動のオブジェクトと `libc.a` の場所の探索を処理系が持つことになり、配布先によって場所が違う。
- C は musl の標準ライブラリを Rust のツールチェーンに足す必要があり（`rustup target add`）、ビルド環境の変更になる。出力の静的リンクは A でも得られる。

### 選ばなかった案と理由

- **B（`rust-lld` を直接）**: 上のとおり。リンカの起動の手間を処理系が持つ。
- **C（musl）**: 上のとおり。A で `libc.a` が使えない環境が問題になった場合の代わりとして残す（下の再検証）。

## 決定 7: `sigil build` と実行ファイルの動き

- **使い方**: `sigil build [--trace-drops] <ファイル>... <関数> -o <出力>`。複数のファイルは `run_sources` と同じく合わせ、宣言の一致（`ModuleMismatch`。ADR 0014 の決定 4）を求める。入口の関数は組み立ての時点で決める。
- **実行ファイルの引数**: 入口の関数の引数を、`sigil run` と同じ書き方（`true`/`false`・整数・小数・`[a,b,...]`・それ以外は文字列）で受け取り、宣言の型に合わせる（インタプリタの `coerce` と同じ規則。決定 6 の「意味の共有」）。合わなければ `入口の指定が誤り: …` を標準エラーに出して終了コード 1。
- **成功**: 戻り値を `sigil run` と同じ表示で標準出力に 1 行出し、終了コード 0。`console.log` の出力は、書いた時点で標準出力に出す（ADR 0006 の M4 の記録と同じ）。
- **異常停止**: 決定 5 の報告を標準エラーに 1 行出し、終了コード 70。`sigil run` は先頭に `<パス>: ` を付けるが、実行ファイルは付けない（比べるときは、インタプリタの側の `Failure.error` の表示と比べる）。
- **`--trace-drops`**: 実行ファイルが、構造体の値を破棄するたびに、インタプリタの `Options::trace_drops` の記録と同じ表示を `drop: <表示>` の形で標準エラーに 1 行ずつ出す。付けないときは何も出さず、記録の処理も生成しない。
- **`fs.read` の差し替え**: 実行ファイルには差し替えの仕組みを持たない（ADR 0004 の規則 7 は実行環境の機能で、M5 の完了条件も実際のファイルとして置くとしている）。

## 決定 8: 差分の比較（一致のテスト）

- `tests/common/native.rs` に、補助関数 `both(srcs, entry, args, opts)` を置く。インタプリタで実行し、同じソースを `sigil build`（ライブラリの関数 `native::build`）で一時ディレクトリに組み立てて実行し、次を比べる。
  - 成功: 戻り値の表示と `console.log` の出力（標準出力の全体）、終了コード 0
  - 異常停止: `Failure.error` の表示と標準エラーの 1 行、終了コード 70、停止の前の標準出力
  - `trace_drops` の事例: 破棄の記録の並び（`StackExhausted` の事例は、記録の数を比べず、各記録の表示がインタプリタの記録に含まれることだけを比べる）
- **差し替えた `fs` の事例**: `Options::fs_files` の仮のパス `p` を、一時ディレクトリの下の `<tmp>/<p の先頭の / を除いたもの>` の実際のファイルにする。引数と、期待する出力の中の `p` も同じく置き換えて比べる。表にないパスは作らない（`NotFound` になる）。
- 決定 1 の各テストファイルの、インタプリタを呼ぶ補助関数を `both` に替える。M5 の作りかけの間は、`SIGIL_NATIVE=1` のときだけ実行ファイルの側も動かす（`BuildUnsupported` の構文が残っている間に既存のテストを落とさないため）。M5 の完了で、この切替えをなくし常に両方を動かす。
- `cc` か `libc.a` がない環境では、`both` は実行ファイルの側を動かさずに失敗する（黙って飛ばさない）。
- 異常停止の報告を標準エラーに出す前に、それまでの標準出力（`console.log` の出力）を書き出し切るのはランタイムの責務とする（`sigil_rt_core` の停止の処理が標準出力を flush してから報告を出し、終了コード 70 で終わる）。上の「停止の前の標準出力」の比較はこれに依存する。

## 決定 9: 「信頼基盤の宣言方法」の ADR との順序

### 決定

**本 ADR（M5）を先に、信頼基盤の宣言方法の ADR を後に書く**。後者の決める時期を、ADR 0006 の決定 4 の「M4 の前」から「P1 の範囲を決める ADR の前（暫定ランタイムを Sigil に置き換える前）」に改める。

### 理由

- M5 の実行ファイルの中で検査を外したコードを持つのは、Rust で書いた暫定ランタイムだけである。Sigil のプログラムは Rust の関数を直接呼べず（ADR 0006 の「境界」）、標準ライブラリの OS 層の宣言を通して呼ぶので、M5 には Sigil のソースで検査を外す仕組みが要らない。標準ライブラリの本体も、P0 ではインタプリタの組み込みと暫定ランタイムが持ち、Sigil で書いた `trust base` のモジュールはまだない。
- 信頼基盤の宣言方法が初めて必要になるのは、(1) 暫定ランタイムを Sigil の信頼基盤のモジュールに置き換えるとき（ADR 0006 の「置き換えの時期」。P1 の完了まで）と、(2) 条件 12 の大域の状態の例外（実行の割り当て・乱数。ADR 0007 の P1-b）である。どちらも M5 のネイティブ出力を前提にする（置き換えた Sigil のランタイムをネイティブにコンパイルする必要がある）ので、M5 の後に、M5 で決めた値の表現（決定 4）と呼び出し規約を材料にして決める方が、検査を外す操作（番地の読み書き・確保器の呼び出し）の範囲を具体的に決められる。
- M5 の間に `trust base` を書いた利用者のモジュールは、今と同じく宣言として読むだけで意味を持たない（検査を外す構文がまだないので、安全性は損なわない）。

## 人間の判断が要る点

次の 3 点は、依存の追加・ビルド環境・CI に当たるので、本 ADR では案を示すだけにし、判断を求める。PR3 までは、これらの判断を待たずに進められる。

1. **依存クレートの追加（未承認。PR4 の前に要る）**: Cranelift のクレート `cranelift-codegen`・`cranelift-frontend`・`cranelift-module`・`cranelift-object` を `Cargo.toml` に足す。ADR 0006 の決定 1 で Cranelift の使用は決まっているが、`Cargo.toml` の注記どおり、追加には人間の承認が要る。推移的に `object`・`gimli`・`regalloc2`・`target-lexicon`・`hashbrown` などが入る。版は承認の時点の最新の安定版にし、`Cargo.lock` で固定する。ランタイムのクレートは外部に依存しない。
2. **ビルド環境の前提（未承認。PR4 の前に要る）**: `sigil build` が、ビルドする環境の `cc` と glibc の静的ライブラリ（`libc.a`。Debian 系では `libc6-dev`、Fedora 系では `glibc-static`）を前提にすること（決定 6 の A）。これを前提にしてよいか、musl（決定 6 の C。`rustup target add x86_64-unknown-linux-musl` が要る）にするかの判断を求める。
3. **CI と最小のコンテナでの確かめ（未承認。PR6 の前に要る）**: ADR 0006 は完了条件を CI で常に通すとしているが、リポジトリに CI の設定がない。本 ADR は CI の設定を変えず、「最小のコンテナで動く」を、静的リンクの確かめ（`executable_is_static`）・空の環境での実行（`runs_without_toolchain`）と、`docker` を使う `#[ignore]` のテストを手で実行した記録で満たす案にした。これで足りるか、CI を加えて `docker` のテストを常に動かすかの判断を求める。

## 根拠の限界と再検証

- 候補の案出しと採点を同じ者（Claude）が行っており、偏りがありうる。
- 決定 3 の番地を鍵にする方法は、検査器が式を複製せずに検査することに依存する。`typed_covers_every_expr` が通らない箇所が 3 つ以上見つかった場合は、`ExprId`（決定 3 の B）を検討し直す。
- 決定 5 の停止の印は、呼び出しごとに分岐を足す。性能は非目標だが、P1 のサーバーで計測して問題になった場合は、巻き戻し（決定 5 の B）を検討し直す。
- 決定 6 の 2 つの Rust の staticlib は、それぞれが Rust の標準ライブラリ（`std`）を中に持つ。同時にリンクすると、`std` のシンボル（`rust_begin_unwind`・`__rust_alloc` など）が重複してリンクが失敗するおそれがある。また、`cc` に渡す追加のライブラリ（`--print native-static-libs` が示すもの。`-lgcc_s`・`-lutil`・`-lrt`・`-lm` など）が決定 6 の `-lpthread -ldl` だけでは足りないおそれがある。PR3 で 2 つの `.a` を作ってリンクを試し、PR4 で実際の出力をリンクして、実測で次のどれにするかを決め、PR に記録する。
  - **代替 1**: OS 層を、核の `.a` に依存する別のクレート（`sigil_rt_os` が `sigil_rt_core` を `rlib` として使う）にし、staticlib として「核のみ」（`sigil_rt_core`）と「核+OS」（`sigil_rt_full`。両方を 1 つの `.a` に含める）の 2 種を作る。`core_only` なら前者、それ以外は後者だけを渡す。`std` は各 `.a` に 1 つだけになる。条件 10 の確かめ（OS 層を呼ぶとリンクが失敗する）は前者で変わらず成り立つ。
  - **代替 2**: 2 つの `.a` のままにし、重複を避けるリンカの指定（`-Wl,--allow-multiple-definition` など）を使う。同じ版の `std` の同じ定義なので動く見込みはあるが、重複の扱いをリンカに任せるので、代替 1 が使えない場合に限る。
  - 追加のライブラリは、`build.rs` がランタイムをビルドするときに `--print native-static-libs` の出力を読み、`sigil build` の `cc` の引数に加える（決め打ちしない）。
- 決定 6 の A は glibc の静的リンクに依存する。glibc の静的リンクで、ランタイムが使う機能（ファイル・標準出力・スレッド）に警告や不具合が出た場合は、musl（C）に切り替える。
- 決定 9 は、M5 の間に Sigil のソースで検査を外す必要が生じないことを前提にしている。M5 の実装で、標準ライブラリの本体を Sigil で書く必要が生じた場合は、信頼基盤の宣言方法の ADR を M5 の途中に前倒しする。
- M5 の完了後、次を計測する。結果が本決定と大きく食い違う場合は、この ADR を見直す。
  - 差分の比較で見つかった食い違いの数と、そのうちインタプリタの側を直したもの・実行ファイルの側を直したものの数
  - `m3_drop_limits.rs` の事例で、実行ファイルとインタプリタの順序が違ったものの数
  - SIR の評価器では見つからず、Cranelift の段で初めて見つかった誤りの数（多ければ評価器の役割を見直す）
