# 0060: 認証・セッション管理（sigil-rune-auth）

- **状態**: 提案（正式判定は未実施。理由と問いを末尾に記録）。実装・マージ・外部公開の承認を意味しない。
- **日付**: 2026-11-24（JST）
- **対象**: [Issue #725](https://github.com/goodnasubi/sigil/issues/725)、レーン E。起草のみで、実装は含まない。

## 背景

「小さいサービスを公開できる組み合わせ」（sigix ＋ sigil-db ＋ KV ＋ 認証 ＋ TLS 終端）の中核となる、ログイン・トークンとセッションの発行と失効の部品を定める。仕様は本リポジトリで管理し、実装は独立したリポジトリ `goodnasubi/sigil-rune-auth` に置く（[ADR 0044](0044-p4-scope.md) 決定 4、sigix・[ADR 0059](0059-kv-store.md) と同じ）。

[ADR 0037](0037-p1-authentication.md) は HMAC 署名ベアラートークンの**検証だけ**を定め、発行・ログイン・パスワード照合・cookie・セッション・失効・OAuth/OIDC を範囲外とした。本 ADR は、その検証器（`web.verify_bearer`、`Router.with_auth`）を使う側として、範囲外だった発行側とセッション管理を定める。ADR 0037 の形式・検査・失敗の一様性は変えない。

利用できる既存部品（本 ADR 起草時点の main `947815b` で確認）:

- ADR 0024: `Secret`、`hmac_sha256`、定数時間比較 `ct_eq`、`pbkdf2_sha256`（反復回数 4096〜100000 に固定）。`std.os.random.bytes`（OS 暗号乱数、`effects random`、失敗は `None`）。`clock.unix_seconds()`（UTC Unix 秒、失敗は `None`）。
- ADR 0059: KV。永続モードは有限 TTL を持ち、`DELETE` の成功が失効の確定になる。単一キーの操作だけで、比較交換・一覧・複数キー操作はない。実装段 1・2 は完了し、TCP とクライアント（段 3）は未完了。
- sigil-db 核（ADR 0045）: 型付き関係 API、一意索引、直列トランザクション。ディレクトリは 1 プロセスが排他ロックで所有する。
- sigix（ADR 0056）: 静的配信とリバースプロキシ。

## 決定 1 — 形: 独立した認証サービス

(A) 独立した認証サービスにする。ログイン・セッション・失効・トークン発行は 1 つのサービスだけが担い、各アプリは ADR 0037 の検証器でアクセストークンを受ける。

- ユーザー DB（パスワードの派生値）、セッションの KV 資格、発行用の署名鍵を、認証サービス 1 つに閉じ込める。(B) のライブラリ配布は、これらをアプリごとに持ち込み、cookie・CSRF・パスワード照合の実装と検証を各アプリで繰り返す。侵害されたアプリ 1 つから全利用者のパスワード派生値に届く。
- 署名鍵は audience ごとに分ける（ADR 0037 の「鍵と audience はサービス・環境ごとに分離」の延長）。各アプリが持つのは自分の audience の鍵だけで、HMAC は対称なため、その鍵で偽造できるのは自分向けのトークンだけになる。他アプリ向けのトークンは作れない。
- アプリは通常の要求ごとに認証サービスを呼ばない。署名と期限をローカルで検証するので、認証サービスが一時的に落ちても発行済みのアクセストークンは期限まで使える（可用性の利点であり、失効が最大でトークンの寿命だけ遅れる原因でもある。決定 2）。
- 認証サービスの前段に sigix（ADR 0056 段階 2）を置き、同じオリジンの `/auth/` に載せる。TLS は前段で終端する（`sigil-shield-tls` は名前だけ。仕様は別の判断）。
- `sigil-rune-auth` はサービスに加え、同じリポジトリの型付きクライアント（要求の組み立てと応答の解釈）と、純粋な核のモジュール（決定 4 の段 1）を提供する。ライブラリとしての配布は、この小さな面に限る。

不採用の案: (B) ライブラリのみ（上述）。(A) で毎要求を認証サービスへ問い合わせる方式（可用性・負荷が悪く、ADR 0037 の検証器の再利用にならない）。

## 決定 2 — 初版の範囲と資格情報

初版に入れる: パスワードログイン、セッションの発行と失効、アクセストークンの発行、利用者の登録と無効化。

資格情報は 2 種類にする。

| 資格情報 | 形 | 寿命 | 失効 |
|---|---|---|---|
| セッション | 不透明な乱数 ID。cookie に載せ、サーバー側（KV）に保存 | 絶対寿命。既定 8 時間、範囲 5 分〜30 日。延長しない | 即時（`DELETE` の成功で確定） |
| アクセストークン | ADR 0037 の `sigil1.<payload>.<tag>`。ペイロードは変えない | 既定 300 秒、範囲 60〜3600 秒（ADR 0037 の上限） | 個別失効なし。セッションが失効すると、次の発行から止まる |

- **セッション ID**: `std.os.random.bytes(32)`。取得失敗はログイン失敗（サービスは続行できない値で代用しない）。ログインのたびに新しい ID を発行し、クライアントが送った ID は使わない（固定化攻撃の防止）。cookie は `__Host-sigil_session`、属性は `Secure; HttpOnly; SameSite=Lax; Path=/`（`Domain` は付けない）。
- **KV の保存**: キーは固定の接頭辞と ID の SHA-256 値。ID そのものは保存しない（KV やそのバックアップが漏れても、そのまま使える資格にならない）。値は固定バイナリ（版、利用者 ID、利用者の世代、発行・期限の Unix 秒）。TTL は絶対寿命。期限は KV の期限に加えて、読み出し側でも検査する。**一度書いたセッションの記録は更新しない**。ADR 0059 の「失効済みの識別子を再登録しない」を守るため、読み取り→書き込みの競合で削除済みのセッションを復活させる経路を作らない。
- **検証の失敗は閉じる**: KV の「キーなし」・エラー・期限切れ・世代の不一致・利用者の無効化は、すべて未認証として扱う。KV の障害でセッションを成功にしない。
- **ログアウト**: KV の `DELETE` の成功をもって失効とする。成否が不明（接続断・`CommitUnknown`）のときは、失効が確定したと応答せず 503 を返し、cookie の削除指示は付ける。そのセッション ID を、プロセス内の保留リストに入れて検証から除外し続け、`DELETE` が成功するまで再試行する。保留リストは再起動で失われる。これは受容する制約として記録する。
- **全セッションの失効**: KV に一覧・複数キー操作がないため、利用者ごとの「世代」の整数を sigil-db の利用者行に持ち、セッションの記録に発行時の世代を入れる。世代を上げると、その利用者の全セッションが次の検証で失効する。利用者の無効化も同じ検査で止まる。
- **アクセストークンの発行**: 有効なセッションで、登録済みの audience に対してだけ発行する。`sub` は不透明な利用者 ID（`u` ＋ 小文字 hex 32 桁、ADR 0037 の文字制約に収まる）で、利用者名ではない。`iat`・`exp` は ADR 0037 の範囲で、`exp − iat` は設定値。署名は audience ごとの 32 バイト鍵による HMAC-SHA256。発行器は、ADR 0037 の固定ベクタと `web.verify_bearer` との往復で、形式の一致を確かめる。
- **パスワード**: PBKDF2-HMAC-SHA256（ADR 0024）、塩 16 バイト（OS 乱数）、導出鍵 32 バイト、反復回数は記録に含める。照合は `ct_eq` だけで行い、`==` は使わない。長さは 12〜256 バイト。未知の利用者でも同じコストの照合（ダミーの記録）を行い、応答は「利用者名かパスワードが違う」の一様な 401 だけにする。反復回数が現行の設定より少ない記録は、ログイン成功時に再計算して置き換える。

初版に入れない: 自己登録、パスワードの再設定・変更の自己操作、メール、多要素認証、OAuth/OIDC・外部 IdP、ロール・権限（アプリは `sub` から自分で対応づける。トークンの項目は増やさない）、IP・User-Agent への束縛、sliding な延長、管理用の HTTP API、cookie 以外の持ち方（ヘッダーでのセッション ID 受け渡し）、鍵の無停止ローテーション（ADR 0037 の制約を継承）。

### エンドポイント

すべて JSON。認証サービスの応答は固定形式で、理由別の本文を作らない。

| 操作 | 内容 |
|---|---|
| `POST /auth/login` | `{username, password}`。成功で新しいセッションを作り cookie を返す。失敗は一様な 401。制限超過は 429 |
| `POST /auth/logout` | セッションを失効し、cookie の削除を指示する。成否不明は 503 |
| `GET /auth/session` | 有効なセッションなら `{sub}`。無ければ 401。転送された cookie を持つサーバー側アプリの確認にも使える |
| `POST /auth/token` | `{audience}`。セッションが有効で audience が登録済みなら、アクセストークンと期限を返す。それ以外は 401 または 403 |

- **CSRF**: 状態を変える要求（login・logout・token）は、`Content-Type: application/json`、かつ `Origin` が設定した公開オリジンと完全一致のときだけ受け付ける。`Origin` が無い要求は拒否する。`SameSite=Lax` との組み合わせで、ログイン CSRF も防ぐ。
- **ログイン抑制**: プロセス内で、利用者名ごとの失敗回数（15 分に 5 回で 15 分の拒否）と、同時に走る PBKDF2 の数の上限を持つ。直接の接続元は sigix の `X-Forwarded-For`（ADR 0056 で信頼した接続元の場合だけ）を使い、接続元ごとの上限も持つ。この状態は再起動で消える。KV には置かない（原子的な加算が無く、競合で過少に数えるため）。認証サービスは 1 インスタンス前提とする。
- キー・パスワード・セッション ID・トークン・`Authorization`・`Cookie` をログ・エラー・応答に出さない。ログに出せるのは、利用者 ID と固定の分類だけ。

## 決定 3 — 依存の持ち方

| 依存 | 用途 | 制約 |
|---|---|---|
| ADR 0059 KV（永続モード） | セッション | 有限 TTL、単一キー操作だけ。TCP クライアント（KV 段 3）が必要。段 3 の前は、同じ呼び出しを `stash.persistent`（同一プロセス）に差し替えて試験する。KV はキャッシュ用のメモリ専用インスタンスとは別にし、永続モードの障害でメモリ専用に切り替えない |
| sigil-db 核 | 利用者の表 `users(id 主キー, username 一意索引, 派生値, 状態, 世代, 作成)` | 型付き API だけ。核は 1 プロセスが排他ロックで所有するので、認証サービスだけが開く。初版の利用者操作（登録・無効化・世代を上げる・パスワード設定）はサービスを止めて行う CLI で行い、管理用の HTTP は作らない |
| ADR 0024 | PBKDF2・HMAC・`ct_eq`・`Secret` | 下記の反復回数の制約 |
| ADR 0037 | 検証（アプリ側） | 形式・検査・失敗を変えない。発行側がこの形式を正確に実装する必要がある（0037 の「根拠の限界」） |
| sigix（ADR 0056） | 前段・リバースプロキシ | `/auth/` を載せる。sigix は認証に依存しない |
| 壁時計・OS 乱数 | 期限と ID | どちらも取得失敗は値で扱い、推測値で代用しない。時計の取得失敗はログインとトークン発行の失敗 |

アプリ側（sigix の背後の Web アプリなど）は、ブラウザ・API クライアントが取得したアクセストークンを `Authorization: Bearer` で受け、ADR 0037 の検証器で検証する。サーバー側で cookie を受けるアプリは `GET /auth/session` で確認する。どちらも、認証サービスの停止中は新しいログインができず、既存のアクセストークンは期限まで使える。

### 範囲外の問題（本 ADR では扱わない。別途の判断が要る）

- **PBKDF2 の反復回数の上限**: ADR 0024 / 0020 は 4096〜100000 に固定している。現行の一般的な指針（OWASP の Password Storage Cheat Sheet は PBKDF2-HMAC-SHA256 で 600,000 回。起草時に原典は再確認していない）より低い。初版は許される最大の 100000 回で始め、反復回数を記録に含めて、上限が上がった後に再計算で移行できる形にする。上限の変更は ADR 0024 の改訂として別に決める。言語側の隙間を認証部品の独自実装で迂回しない。
- **定数時間性の検査の登録**: `tests/ct_rules.rs` は本リポジトリの標準ライブラリを対象にしており、別リポジトリの照合コードを登録できない。初版は `ct_eq` だけを使い、`==` を使わないことをコード審査と試験で確認する。登録の仕組みが必要かは段 1 の中で報告する。
- **KV の原子的な加算がない**: ログイン抑制を KV に置けない理由。複数インスタンス化は後続の判断とする。

## 決定 4 — 実装段の分割と完了条件

実装は前の段が通ってから進める。本 PR は文書だけで、段の Issue は ADR のマージ後に切る。

| 段 | 依存 | 内容と完了条件 |
|---|---|---|
| 1. 純粋な核 | 本 ADR | パスワード記録の符号化・照合、ID と KV キーの導出、セッション記録の符号化、ADR 0037 形式のアクセストークン発行器。独立に計算した固定ベクタと否定例、上限境界、`web.verify_bearer` との往復を、評価器とネイティブの両方で確認する。コンパイラ・標準ライブラリ・核の SHA を固定する |
| 2. 利用者の表とログイン | 段 1 | sigil-db の利用者表、CLI（登録・無効化・世代を上げる・パスワード設定）、ログイン照合、抑制。中断・復旧、未知の利用者と誤パスワードの一様性、抑制の境界、再計算による移行を試験する |
| 3. セッション | 段 2、KV 段 2（クライアントは KV 段 3） | 発行・検証・ログアウト・保留リスト・世代による失効。KV の障害・成否不明・期限境界・復活しないことを試験する。KV のクライアントが無い間は `stash.persistent` で通し、クライアントが揃った時点で同じ試験を TCP 経由でも通す |
| 4. HTTP サービス | 段 3 | 4 つのエンドポイント、cookie、Origin・Content-Type の検査、固定の失敗応答、秘密がログ・応答に出ないこと。要求のファジングと上限。sigix の背後での結合試験と、ADR 0037 の検証器を使うアプリへの往復 |
| 5. 公開前の記録 | 段 4 | ADR 0020 の G2 記録を本 ADR の補足 A に追加する。時計の監視、TLS 終端と内部網、鍵の交換運用、ログイン抑制の限界、保留リストの喪失、PBKDF2 の反復回数を、G3 で所有者へ提示する項目として記録する。G2 は外部公開を承認しない |

## 脅威と対策（G1）

| 分類 | 何から何を守るか | 対策 |
|---|---|---|
| 入力 | 任意の JSON・巨大なボディ・重複したヘッダーから処理系を守る | 本文・フィールドの長さ上限、厳格な JSON、`Err` で返す。ファジング（段 4） |
| 認証 | パスワードの総当たり・列挙・CSRF・固定化から利用者を守る | 一様な 401、ダミー照合、抑制、Origin と Content-Type、`__Host-` cookie、ログインごとの新 ID |
| 秘密 | KV・DB・ログ・バックアップの漏洩から資格を守る | セッション ID はハッシュだけを保存、パスワードは PBKDF2、署名鍵は環境の起動時設定、ログに出さない |
| セッション | 失効の取りこぼし・復活を防ぐ | `DELETE` の成功で確定、記録を更新しない、保留リスト、世代 |
| 資源 | PBKDF2 による CPU 枯渇を防ぐ | 同時ハッシュ数の上限、抑制、パスワード長の上限 |

HMAC は盗聴・持参者の再使用を防がない（ADR 0037 の受容を継承）。TLS 終端・内部網、時計の巻き戻り、鍵の交換運用は G3 で所有者へ提示する。

## 影響

- 認証のための鍵・パスワード・セッションの面が 1 サービスに集まり、レビューと試験の対象が絞れる。代わりに、そのサービスの停止中は新しいログインとトークン発行ができなくなる。
- 失効は、セッションでは即時、アクセストークンでは最大でその寿命（既定 300 秒）だけ遅れる。
- 認証サービスは 1 インスタンスの前提で、KV と sigil-db を別々の排他的な所有者として持つ。

## 正式判定の記録

**起草時点では未実施。** 起草セッション（claude.ai の Code セッション）には、判定 API の認証キー `TYPESAFE_API_KEY` が設定されておらず、AGENTS.md の「キーが無い環境」に当たる（ADR 0044 の起草時と同じ）。判断の手順に従い、理念（ADR 0001・0005・0027: 人間が仕様をレビューできること、最小の信頼基盤、曖昧さの削減）と既存 ADR・Issue の前提で、起草者の案を決定 1〜4 とした。**判定を経ていない起草者の案**であり、見張りが次の 4 つの問いで判定し、結果を本 ADR に追記する（採用案と食い違えば改訂する）。

評価軸（`state` の冒頭）: ADR 0001・0005・0027、ADR 0020 の公開関門、ADR 0037（検証だけが既決）、ADR 0059（KV は単一キーで、永続セッションに使う）、いまは外部公開しない、小さいサービス向け。

| 問い | 起草者の案 | 比較する案 |
|---|---|---|
| Form | `service`: 独立した認証サービス。検証は ADR 0037 の検証器 | `library`: 各アプリに組み込むライブラリ／`hybrid`: ライブラリ＋任意のサービス |
| Credentials | `session_plus_token`: KV の不透明セッション ＋ 短命の ADR 0037 アクセストークン | `stateless_only`: ADR 0037 のトークンだけ／`session_only`: 不透明セッションだけ（毎回サービスへ問い合わせ） |
| Scope | `login_session_token`: パスワードログイン・セッション・トークン発行・CLI での利用者管理 | `token_only`: 発行だけ（ログインなし）／`full`: 再設定・多要素・OAuth を含む |
| Stages | `five_stages`: 純粋な核 → 利用者とログイン → セッション → HTTP → 公開前の記録 | `service_first`: HTTP サービスを先に作り機能を足す |

判定の入力と応答の JSON は、見張りが保管し、結果を本節に追記する（ADR 0044 と同じ運用）。
