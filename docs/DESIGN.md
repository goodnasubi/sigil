# 設計の全体像（草案）

このドキュメントは Sigil の設計方針を整理する草案です。決定事項は [decisions/](decisions/) に記録し、ここでは全体像のみを扱います。

## 1. 目的

人間に代わって AI がコーディングし、Java・React・Node.js を置き換えられる言語を作る（[ADR 0001](decisions/0001-vision-and-scope.md)）。そのために以下を保証する。

- **仕様の分離**: 人間がレビューする仕様（意図・事前条件・事後条件・効果）が、コード本体から機械的に取り出せる。
- **仕様の検証**: コード本体が仕様を満たすことを、型・所有権・契約・効果の検査で確かめる。
- **メモリ安全性**: 解放後の使用・二重解放・ヌル参照・データ競合を、コンパイル時に排除する（Rust と同等）。
- **全層の記述**: ブラウザの UI、サーバー、その間の通信を 1 つの言語で書ける。
- **Python からの呼び出し**: Sigil で書いた関数・型を Python から呼び出せる。

## 2. 役割分担

| 担い手 | 役割 |
|---|---|
| AI | コードの記述・修正・保守。仕様の草案作成 |
| 処理系 | 型・所有権・契約・効果の検査。仕様の抽出と人間向けの表示 |
| 人間 | 仕様のレビューのみ（コードは読まない） |

## 3. 実行方式

- コンパイラと実行環境（ランタイム・標準ライブラリ）を独自に作る。JVM や Node.js の上には載せない。
- 出力先（想定）:
  - サーバー: ネイティブコード
  - ブラウザ: WebAssembly と JavaScript（ブラウザが直接実行できるのはこの 2 つだけのため）
  - Python 連携: ネイティブの共有ライブラリと、自動生成する Python 用の束縛
- メモリ管理はガベージコレクションに頼らず、所有権と借用の静的検査で安全性を得る（[ADR 0003](decisions/0003-ownership-and-borrowing.md)）。破棄の地点はコンパイル時に決まり、JavaScript 出力でも資源はその地点で解放する。
- 並行処理は、中断しうることを効果として扱う構造化並行処理とする（[ADR 0007](decisions/0007-concurrency-model.md)）。ネイティブでは複数の OS スレッドで、ブラウザでは単一スレッドで同じプログラムが動く。
- Python から渡される値は静的に検査されないため、呼び出しの境界で型と事前条件を実行時に検査する。

## 4. 非目標（当面は後回し）

- Sigil から既存言語のライブラリ（npm・Maven など）を使うこと（Python から Sigil を呼ぶ方向は目標に含める）
- 実行性能の最適化
- 人間が手で書くための短い記法

いずれも置き換えを目指す以上いずれ必要になるが、まず意味論・安全性・検証を固める。

|---|---|---|

| 総称型の括弧・本体の値の返し方 | **決定**: 型の位置の `<>`、`return` 必須（[ADR 0008](decisions/0008-m0-notation.md)） | — |
| サンプルの未確定の表記（`old(...)`、篩型の `where` と `self`、`Port.check`、モジュールの宣言） | **決定**: `old(式)`、`where` + `self`、`T.check(v) -> Option<T>`、`module` の宣言（`targets`・`trust` の 2 節）、`if` は文で値は `match`、効果の並べ方（[ADR 0008](decisions/0008-m0-notation.md)） | — |

## 6. 長期目標と段階計画

最終的に Next.js・Spring・Python・データベース・Git・Docker コンテナでのリリースとコンテナ管理・OS（ESXi 上の仮想マシンを含む）を置き換え、IDE とブラウザを作ることを目指し、P0（言語の核）から P7（ブラウザ）までの段階で進める（[ADR 0005](decisions/0005-long-term-goals.md)）。

設計上の帰結:

- 出力先に「実行環境なしのネイティブ出力」（ハードウェアの上で直接動くコード）を加える。最初の対象は x86-64。
- 標準ライブラリを、実行環境なしでも使える核の部分と、OS の機能を使う部分に分ける。この分割は P0 から設計に入れる。
- 検査を外す仕組みは「信頼基盤」（標準ライブラリ・ランタイム・生成コード・OS のプラットフォーム層の最小部分）にだけ許し、各箇所に安全の前提を契約として書く。

## 7. 進め方

1. `examples/` に小さなサンプルを書き、構文の候補を比べる。
2. 候補ごとの利点・欠点を ADR に記録する。
3. 決定した項目を本ドキュメントに反映する。
