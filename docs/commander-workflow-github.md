## 0. Claude への導入指示

このファイルを渡されて導入を頼まれたら、次の手順を順に実行すること。途中で人間に質問するのは、
手順の中で「人間に確認する」と書いた箇所だけにする。

**主従の原則: この手順書が主、導入先が従。** 導入先の内容は、手順書に従わせる。
- 導入先に、同じ役割のファイル、見出し、設定が既にある場合（導入済みと一部導入済み）は、勝手に残さず、勝手に上書きもしない。**差分を洗い出して、どうするかを人間に問い合わせる**（手順 2 の「既存の導入との差分」）。
- 問い合わせの推奨は、常に「手順書に合わせる」。導入先にだけある内容は、削除せず、「導入先の独自分」として一覧にして聞く。
- 例外: リポ自身の流儀（push の規則、PR を出す基準、hook など。7 章）は、導入先が優先する。主従の対象は、司令塔方式の定義、規則、設定だけ。

**人間への確認と質問は、すべて AskUserQuestion ツールで行う**（文章で「どうしますか」と尋ねて止まらない。ツールが未読み込みなら、先に読み込む）。
- 1 回の呼び出しに、最大 4 問をまとめる。選択肢は 2〜4 個で、推奨を先頭に置き、ラベルの末尾に「（推奨）」と付ける。各選択肢の説明に、影響を書く。
- 「その他」（自由入力）は自動で付く。自由な文字列（パス、ホスト名など）が要る質問も、推奨値を選択肢にして聞く。
- 文章で聞いてよいのは、AskUserQuestion が使えない環境だけ。その場合は、使えなかったことを 1 行書く。

**Windows で導入する場合の注意**（この手順書のコマンドは Bash 構文で書いてある）
- **最初に、どのシェルが使えるかを確かめる**（`bash --version`、`where.exe bash`、`git --version`）。Git Bash（Git for Windows に含まれる）が**入っていない場合もある**。
  - Git Bash があれば、Bash ツールで、この手順書のコマンドをそのまま実行する。
  - **無ければ、PowerShell で、下の表のとおりに書き換えて実行する**。Git Bash を入れるかどうかは、人間に確認する（手順 2 の計画に書く。勝手に入れない）。
  - `git` と `gh` が PowerShell から呼べない場合は、導入できない。AskUserQuestion で聞いて止まる（選択肢: 「インストールした。再確認する（推奨）」「導入を中止する」。インストールは人間が行う）（種類 B で配下に GitHub リポジトリが無く、`gh` を使わない場合を除く）。

  | 手順書の書き方（Bash） | PowerShell での書き方 |
  |---|---|
  | `GH_HOST=<ホスト> gh ...`（GitHub Enterprise Server の場合） | `$env:GH_HOST='<ホスト>'; gh ...`（そのセッションの間、残る。終わったら `Remove-Item Env:GH_HOST`） |
  | `find . -maxdepth 3 -name .git -not -path ./.git` | `Get-ChildItem -Recurse -Depth 2 -Force -Filter .git \| Where-Object { $_.FullName -ne (Resolve-Path .git -ErrorAction SilentlyContinue).Path }`（`-Directory` は付けない。worktree と submodule の `.git`（ファイル）も拾うため） |
  | `grep -rn "文字列" .` | `Get-ChildItem -Recurse -File -Force \| Where-Object { $_.FullName -notmatch '\\\.git\\' } \| Select-String -Pattern "文字列"`（`Select-String` に `-Recurse` は無い。`.git` の中は除く。非再帰なら `Select-String -Path .\*.md -Pattern ...`） |
  | `ls ~/.claude/projects` | `Get-ChildItem $HOME\.claude\projects` |
  | `~/.claude/...` | `$HOME\.claude\...` |
  | `rm -rf <パス>` | `Remove-Item -Recurse -Force <パス>`（消す前に、対象を `Get-ChildItem` で見る） |
  | ヒアドキュメント `<<'E' ... E` | here-string `@' ... '@`（行頭に `'@` を置く）。日本語は UTF-8（BOM なし）で書く: `Set-Content -Encoding utf8` は Windows PowerShell 5.1 では BOM 付きになるので、`[System.IO.File]::WriteAllText($path, $text, (New-Object System.Text.UTF8Encoding $false))` を使う |
  | `cmd1 && cmd2` | PowerShell 7 なら同じ。5.1 では `cmd1; if ($?) { cmd2 }` |
  | `export VAR=値` | `$env:VAR='値'` |
- PowerShell の実行上の注意（5.1 と 7 で確認済み）:
  - `&&` は 7 だけで使える。5.1 では `cmd1; if ($?) { cmd2 }` を使う。`-Encoding utf8NoBOM` は 7 専用（5.1 ではエラー）。
  - 5.1 では、実行ポリシーで `.ps1` が実行できないことがある（`-ExecutionPolicy Bypass` を付けるか、`-Command` で渡す）。
  - 日本語を含む BOM なしの `.ps1` は、5.1 が文字化けして構文エラーにすることがある。`.ps1` にせず、コマンドで直接渡すか、BOM 付きで保存する。
  - 5.1 で BOM なしの UTF-8 ファイルを読むときは、`Get-Content -Encoding UTF8` を付ける。
  - Bash から `powershell -Command '...'` を呼ぶと、引用符とバッククォートが崩れる。スクリプトのファイルにするか、PowerShell ツールで直接実行する。
  - `git rev-parse --show-toplevel` は `/` 区切りのパスを返す（Windows でもそのまま使える）。
- Bash が無い環境では、`CLAUDE.md` に書く「PR の流れ」のコマンド例（`gh pr create ...` など）も、PowerShell で動く形（引用符の使い方、`$env:`）にして、導入先の `CLAUDE.md` に書く。
- PowerShell では、`VAR=値 コマンド` の前置きが動かず、`find`、`grep` も別物になる（上の表のとおりに書き換える）。
- Git Bash は、`/home/...` のようなパスを Windows のパスに変換する。WSL を呼ぶときは、`MSYS_NO_PATHCONV=1` を付ける。
- `~/.claude` は、`C:\Users\<ユーザー名>\.claude` を指す。メモリの置き場所の名前は、手順 6 のとおり、`ls` で突き合わせる。
- 使用中のフォルダやファイルは、削除や上書きに失敗する（プロセスが掴んでいる）。失敗したら、掴んでいるプロセスを確かめてから、やり直す。
- 日本語を含む文字列を、Python のコード内に直接書くと、バックスラッシュ（`\N` など）がエスケープとして解釈されて失敗することがある。ヒアドキュメント（`<<'E'`）か、ファイルへの書き出しで渡す。
- 改行コードは、導入先のリポジトリの設定（`.gitattributes`、`core.autocrlf`）に合わせる。置くファイルの改行を、勝手に変えない。

1. **導入先の種類を判定する**（導入先 = Claude Code を起動したディレクトリ。以下「ルート」）
   - **種類 A**: ルートが GitHub のリポジトリそのもの
     （`git rev-parse --show-toplevel` がルートを返し、`git remote get-url origin` が GitHub を指す）。
   - **種類 B**: それ以外。ルートが git 管理されていない、`origin` が無い、GitHub 以外のリモートを持つ、
     または配下に複数のリポジトリを置いた作業用ディレクトリである場合（**`origin` が無ければ B**）。
     配下の GitHub リポジトリを `find . -maxdepth 3 -name .git -not -path ./.git` で探し（ルート自身の `.git` は除く）、一覧にしておく。
   - どちらの場合も `gh auth status` を確かめる。失敗したら、GitHub への `gh auth login` を
     AskUserQuestion で頼んで止まる（選択肢: 「ログインした。再確認する（推奨）」「導入を中止する」。ログインは人間が行う）（種類 B で配下に GitHub リポジトリが一つもなければ、この確認は飛ばす）。
     GitHub Enterprise Server の場合は、`GH_HOST=<ホスト> gh auth status` で、そのホストの行を見る。
   - 種類 A なら既定ブランチ名を調べる（`git symbolic-ref refs/remotes/origin/HEAD`）。
     以下の `main` はその名前に読み替える。種類 B では、`origin/HEAD` が取れないので、
     ルート自身が git なら `git branch --show-current` を使い、作業のたびに対象リポジトリの既定ブランチを調べる。
   - **この手順書の操作のうち、reviewer などの子エージェントを起動する操作は、司令塔（メインのセッション）だけが行う。**
     子には頼めない（子は原則として孫を起動しない。例外は 2 章の運用の規則）。手順 5 と 7 の「reviewer に依頼」は、司令塔が起動する。
2. **導入計画を人間に示して、OK をもらう**（OK が出るまで、導入先のファイルは何も変更しない。手順 1 の判定と読み取りだけを行う）
   - **計画の冒頭で、次の 2 点を AskUserQuestion ツールで人間に聞く**（状態メモと UI の有無の確認も、同じ呼び出しにまとめる。最大 4 問。答えがないまま次へ進まない）。
     - 選択肢は 2〜4 個。推奨を先頭に置き、ラベルの末尾に「（推奨）」と付ける。各選択肢の説明に、影響（費用、衝突、共有範囲）を書く。
     - 「その他」は自動で付く（自由入力）。聞く前に、既存の `~/.claude/CLAUDE.md` の有無と行数を読み、質問文に書く。
     - (a) **司令塔モードの追記先**: 司令塔方式の核（3.2 の「司令塔方式」）は、既定で**ユーザー共通の `~/.claude/CLAUDE.md` に追記する**と明示する
       （Windows では `C:\Users\<ユーザー名>\.claude\CLAUDE.md`。なければ作る）。リポの `CLAUDE.md` に直書きするのは、人間が選んだ場合だけ。
       追記する行数の目安と、既存の内容と同じ見出しがあるかも示す。
     - (b) **同時に動かすサブエージェントの数**（以下 N）: 選択肢の例は「2（推奨）」「1」「3」。ファイルが重なる作業は同時にしない。
       並行は isolation: worktree で起動する。数を増やすほど、費用と衝突が増えることも添える。
   - 手順 1 の判定と、導入先の現状の読み取り（既存の `CLAUDE.md`、`.claude/`とメモリの有無と行数）をもとに、次を**一覧にして示す**。
     0. **既存の導入との差分**（導入先に、司令塔方式の定義、規則、設定が既にある場合。手順書が主、導入先が従）
        - 比べる対象: 8 定義（`.claude/agents/` と `~/.claude/agents/` の両方）、`CLAUDE.md`（`~/.claude/CLAUDE.md` とリポの `CLAUDE.md` の司令塔方式、PR の流れ、状態メモ、利用制限の各節）、ユーザー共通の PR の流れのスキル、`.claude/settings.json` の `allow` / `deny` / `effortLevel`、状態メモ。
        - 項目ごとに、次の 4 つに分類して一覧にする: **一致** / **手順書にあるが導入先に無い（不足）** / **内容が違う（相違）** / **導入先にだけある（独自分）**。
          追記と文言の違いだけの相違も、相違に入れる（モデル、effort、tools、数値、規則の有無は特に漏らさない）。
        - 一致は、一覧に件数だけ書く。それ以外は、項目ごとに差分（導入先の行 ↔ 手順書の行）を示す。
        - **相違と独自分は、項目ごとに AskUserQuestion で問い合わせる**（最大 4 問ずつ）。選択肢:
          「手順書に合わせる（推奨）」（導入先を手順書の内容に置き換える。置き換え前の内容は、報告に控える）／
          「導入先を残す」（手順書とは違うまま残す。**手順書へ逆反映する候補**として、報告に載せる）／
          「統合する」（両方の内容を、人間が示す形で合わせる）。
          不足は、問い合わせずに追加する（計画に載せて、OK をもらう）。独自分は、「残す（推奨）」「手順書に合わせて削除する」を選ばせる。
        - 問い合わせの答えは、状態メモの「決定済みの事項」（使う場合）か報告に残す。「導入先を残す」が選ばれた項目は、次回の導入でも同じ質問を繰り返さないよう、理由を 1 行添える。
        - 差分が無い（すべて一致）なら、「導入済みで差分なし」と報告して、手順 3 以降は行わない。
     1. **作る、変える、追記するファイル**（パス、新規か追記か、追記する行数の目安）:
        `.claude/agents/` の 8 定義、`CLAUDE.md`（追記。追記先は (a) の答え）、`.claude/settings.json`（`allow` / `deny` / `effortLevel` のマージ）、状態メモ（使う場合）。
        調整役は、人間が望んだ場合だけ、3.5 の雛形（スキルと CLAUDE.md の節）と状態ファイルを置く。望むかは、この計画を示したあと、承認の前に、追加の AskUserQuestion を 1 回出して聞く（選択肢: 「導入しない（推奨）」「導入する」）。
        既存のファイルと衝突する箇所は、上の 0（既存の導入との差分）で人間が選んだ方法に従う。
        **状態メモを使うか**（自動ループ運用を使うか。置き場所は既定でプロジェクトのルートの `commander-state.md`。別の場所にしたい場合は「その他」で答えてもらう）と、UI のあるリポジトリかどうかも、ここで AskUserQuestion で人間に確認する（(a)(b) と合わせて最大 4 問）。
        不要な項目（種類 B の Issue と GitHub 設定など）は、「該当なし」と並べずに省く。
     2. **作業の流れの変化**: メインのセッションが司令塔になり、設計と実装を子エージェントに任せること、
        同時に動かす子は最大 N 個（(b) の答え）、レビューとテストを経て司令塔がマージすること、マージ後に Issue へ追記すること、
        子の起動で費用が発生すること。UI のあるリポジトリでは、UI の変更に実機確認が加わること。
        あわせて、**サブエージェントの起動のしかた**を、短く説明する（3.2 の「司令塔方式」の要点）:
        - 起動するのは司令塔だけ。新規セッションではなく、Agent ツールで起動する（子は原則として孫を起動しない。例外は 2 章の運用の規則）。
        - 起動のたびに、`subagent_type`、`model`、`effort` の 3 つを明示して渡す。
          対応: 設計 designer = opus / medium、実装 implementer = sonnet / medium、機械的な作業 chore = haiku / low、レビュー reviewer = sonnet / medium、実機検証 verifier = sonnet / medium、Issue 管理 issue-keeper = sonnet / low、調査 researcher = sonnet / medium、テスト tester = sonnet / medium。
          省くと司令塔のモデルを引き継ぎ、意図しない費用になる。
        - 依頼文は、目的、対象ファイル、完了の条件、参照文書を、常体の短い文で書く。会話の経緯は渡さない。
        - 同時に動かすのは最大 N 個。並行は isolation: worktree で起動する。
        - 子は報告の冒頭に、自分が見たモデル ID を書く。実装した子とは別に、reviewer が確認する。
     3. **git と GitHub への影響**（種類 A）: 作業ブランチ `chore/commander-workflow` と、導入の PR を作ること。
        人間が GitHub の画面で行う設定（3.4）。
     4. **メモリへの影響**: 手順 6 で、メモリを読むこと。**人間の承認なしに、メモリを書き換えず、削除もしない**こと。
     5. **変更しないもの**: 既存のコード、リポ自身の流儀（push の規則など）、メモリ（承認がない限り）。司令塔方式の定義、規則、設定は、手順書が主なので、差分は 0 の問い合わせに従って変える（人間が「導入先を残す」と答えたものは残す）。
     6. **戻し方**: 導入の PR を取り消す（種類 A）、または、置いたファイルを削除する（種類 B）。
   - 計画を文章で示したあと、**AskUserQuestion で承認を聞く**（選択肢: 「OK、導入を始める（推奨）」「計画を修正する」。修正点は「その他」に書いてもらう）。
     「OK」が選ばれたら、手順 3 以降に進む。修正を求められたら、計画を直して、もう一度聞く。「OK」がなければ、何も変更せずに止まる。
3. **作業ブランチを作る**: 種類 A のときだけ、既定ブランチの最新から `chore/commander-workflow` を作る。
   種類 B ではルートに直接ファイルを置く。
4. **ファイルを置く**（手順書が主。すでにあるファイルは、手順 2 の「既存の導入との差分」で人間が選んだ方法で反映する。選ばれていない差分は、勝手に上書きも削除もしない）
   - 3.1 の 8 つの定義を `.claude/agents/` に作る。**同名の定義がすでにあれば**、`model`、`effort`、`tools`と本文の違いを
     手順 2 の問い合わせの答えに従って反映する（「手順書に合わせる」なら置き換え、「導入先を残す」なら触らない、「統合する」なら示された形に）。
     置き換える前に、元の内容を報告に控える。
   - 3.2 の内容を、手順 2 の (a) で決めた追記先の末尾に追記する（なければ作る）。同じ見出し（「## PR の流れ」など）がすでにあれば、
     重ねて書かず、**既存の見出しの行と手順書の行を比べ、手順 2 の問い合わせの答えに従って反映する**（手順書にだけある行は追加、違う行は答えのとおり、導入先にだけある行は答えのとおり残すか削除する）。
     追記先がユーザー共通の `~/.claude/CLAUDE.md` の場合、「PR の流れ」の詳細はユーザー共通のスキルに置く（3.2 冒頭の別の選択肢）。
   - 自動ループ運用の詳細は、3.2.1 のスキル（commander-auto-loop）を、3.2 の追記先と同じ系統（ユーザー共通は `~/.claude/skills/`、リポ専用は `.claude/skills/`）に作る。すでにあれば、手順 2 の問い合わせの答えに従って反映する。
   - 2 章の運用の規則（孫の規則を含む）、2 章、3.2、3.2.1、5.7 にある「同時に動かす子は最大 2」は、手順 2 の (b) で決めた N に置き換えて書く。
   - UI の無いリポジトリでは、3.2 の「PR の流れ」手順 4 の UI の項（`<…の置き場所>` の穴埋めを含む）を**書かない**。
   - 3.3 の `allow` / `deny` を `.claude/settings.json` にマージする（既存の項目は消さない）。
   - 自動ループ運用（5 章）を使う場合は、状態メモ（5.4 のコードブロックの雛形）の空のものを、既定ではプロジェクトのルートの `commander-state.md` に作り、`.git/info/exclude` に書いて git の対象から外す。
     置き場所を変えるのは、手順 2 で人間が別の場所を選んだ場合だけ。
   - 種類 A では、リポジトリにある lint、型検査、テストのコマンド（package.json、Makefile、pyproject.toml など）を調べ、
     `CLAUDE.md` の「PR の流れ」手順 5 に具体的なコマンドとして書き込む。見つからなければ人間に確認する。
     種類 B では書き込まず、作業のたびに対象リポジトリで調べる（手順 5 の記述のまま）。
   - 画面（UI）を持つリポジトリでは、実機の確認に必要な情報（検証環境の起動方法、本物の接続先、配備の手順）の
     置き場所を人間に確認し、`CLAUDE.md` の「PR の流れ」手順 4 の UI の項に書き込む。
5. **CLAUDE.md を精査する**（追記で長くなり、毎回の会話で全文が読み込まれるため）
   - 実装した子とは別に、reviewer（sonnet / medium）に依頼する。削る判断は機械的ではないので、chore（haiku）には任せない。
   - 見るもの: (1) 導入先の既存の規則と、追記した規則の重複と矛盾、(2) 常時は不要なもの（自動ループ運用の詳細など。
     要点の数行だけ残し、詳細は本ファイルの 5 章に任せる）、(3) 穴埋めの記号（`<…>`）の残り
     （コマンド例の `<ブランチ>`、`<番号>`、`<本文>`、`<owner/repo>` などの正当な書式は除く。残すのは、`<このリポジトリの…>` のような、導入先の値で埋めるべきもの）、
     (4) リポの push 規則と流儀（CLAUDE.md、docs、hook）との矛盾（7 章。矛盾はリポに寄せる）。
     規則そのものと、その理由の短い一言は削らない。
   - reviewer は、**削る案の一覧**を返す（自分では削らない）。司令塔が採否を決めて反映する。
   - 目安の上限（例: 150 行）を決めておき、超える場合は一覧に含める。
6. **導入先のメモリと周辺の指示を確かめる**（司令塔方式を阻害するものがないか）
   - 読む場所: 導入先のプロジェクトのメモリ（`~/.claude/projects/<導入先のパスを変換した名前>/memory/` の `MEMORY.md` と各ファイル。
     変換した名前は、パスの `:` と区切り文字を `-` に置き換えたもので、大文字小文字は環境で揺れる
     （例: `C--work-myproject`、`E--projects-app-web`）。**規則で決め打ちせず、`ls ~/.claude/projects` で導入先のパスと突き合わせる**）、
     ユーザーのメモリ（`~/.claude/CLAUDE.md`）、`CLAUDE.local.md`、導入先の親ディレクトリの `CLAUDE.md`、
     `.claude/settings.local.json`、既存の `.claude/agents/`。
   - 阻害の例: 「自分で実装する」「確認なしで進めない」「OK が出るまでコミットしない」のような、
     司令塔の役割、自律、PR の流れと食い違う記述。モデルやエフォートを固定する記述。同名のエージェント定義。
   - **メモリは人間のものなので、自分では書き換えず、削除もしない。** 阻害するものの一覧（ファイル名、該当の行、どう阻害するか、
     直す案）を作り、AskUserQuestion で人間に確認する（この手順は、人間に確認する箇所に当たる。1 件ごとに「直す」「削除」「残す」を選んでもらう）。人間が直すと削除すると決めたものだけ、
     その場で反映する。
   - **不要なメモリの削除**（阻害の確認と同時に行う）。削除の候補は、次のものから選ぶ。
     (1) 阻害するもの、(2) 古くて誤っているもの（参照先のファイルやブランチが無い、終わった作業の「次の宿題」など）、
     (3) 他のメモリや `CLAUDE.md` と重複するもの、(4) 終わった作業の一時的な状況メモ（コードや git の履歴から分かるもの）。
     - 削除の候補の一覧（ファイル名、理由、分類、「削除」か「書き直し」か）を作り、**人間が承認したものだけ**削除する。
       承認がないものは残す。迷うものは、削除ではなく書き直し（古い記述に日付を付ける、現状に直す）を提案する。
     - 削除するときは、ファイルを消し、`MEMORY.md` の索引の行も消し、他のメモリの `[[名前]]` のリンクが、消したものを指していないかを
       `grep` で確かめて直す。削除前に、消すファイルの一覧と中身の要点を報告に残す（戻せるように、バックアップを一時的に取ってもよい）。
     - 消さずに残すもの: ユーザー自身についての記述、人間が明示的に「覚えておいて」と言った指示、まだ有効な外部の参照先。
   - 阻害するものがなければ、「確認した場所の一覧と、阻害なし」を報告に書く。
7. **動作を確かめる**
   - reviewer を 1 回起動し、`/code-review` を呼ばせる（確認だけが目的。呼び出せた場合、結果は使わず破棄してよい）。
     ツールが使えない旨のエラーが返れば「呼び出せない」と判定し、`reviewer.md` から
     `/code-review` の行と `Skill` を外し、`CLAUDE.md` の「PR の流れ」手順 4 を
     「司令塔が `/code-review` を実行し、結果を reviewer に渡す」に改める。
8. **PR を作る**（種類 A のときだけ）: コミットして push し、`gh pr create --draft --fill --base <既定ブランチ>` で PR を作る（`--fill` が無いと、対話なしの実行で失敗する）。
   この PR は導入そのものなので、自分ではマージせず、人間のマージを待つ。
   種類 B では PR を作らず、置いたファイルの一覧を報告する。
9. **人間に、セッションの開き直しを指示する**（導入の最後の手順。報告より先に行う）
   - 理由: `CLAUDE.md`、メモリの索引（`MEMORY.md`）、`.claude/agents/` の定義、`.claude/settings.json` は、**セッションの開始時に読み込まれる**。
     導入と同じセッションでは、導入前の古い内容のまま動いていて、新しい規則（司令塔方式）が効かない恐れがある
     （メモリを直した場合も、このセッションには反映されない）。
   - 言い方: 「導入が終わりました。規則を効かせるため、このセッションを終了して、新しく開き直してください。
     続きの作業は、状態メモと報告から始められます」。人間が開き直すまで、新しい作業（設計と実装の依頼）は始めない。
   - 開き直したあと、最初に、司令塔方式が効いているかを確かめる（`CLAUDE.md` の「司令塔方式」の見出しが読めているか、
     `.claude/agents/` の 8 つの定義が見えているか）。
   定義が見えない場合は、3.1 冒頭の代用（`general-purpose`）で動く。
   - 調整役（3.5）を導入した場合は、開き直したセッションで、(a) 起動時に調整役の状態が画面に 1 行出るか、
     (b) 最初の応答で、調整役の確認と、いれば申告が行われるかを確かめる。出なければ、3.5 の導入後の確認に戻る。
10. **人間に報告する**（7 行以内）: 種類（A / B）、PR の URL またはファイルの一覧、手順 5 の精査の結果（削った行数と残った懸念）、
   手順 6 のメモリの確認結果（阻害するものと、人間の判断）、手順 7 の結果、調整役を導入した場合はその確認結果（1 行）、人間が GitHub の画面で行う設定（3.4）の一覧。
    報告のあと、**設定ごとに AskUserQuestion で状況を聞く**（選択肢: 「設定した」「あとで設定する」「設定しない、または使えない（無償版など）」。最大 4 問ずつ）。
    「あとで設定する」は、状態メモ（使う場合）か報告に残す。

## 1. 何をするか

- **司令塔**（メインのセッション）は、作業の依頼、自己レビューの依頼、マージだけを行う（自動ループ運用では、次の作業の選定と状態メモの更新も含む）。自分では設計も実装もしない。
- 設計や実装は **子エージェント**（サブエージェント）に任せる。子エージェントは作業ごとに新しく起動し、終わったら破棄する。
  修正も既定は新しい子を起動する（再開すると前の履歴を持ち越し、往復のたびに入力トークンが増える）。修正の依頼文は、ブランチ名と指摘（ファイル:行と直し方）だけ。
  再開してよいのは、直前の指摘への小さな追加修正で、子の履歴が小さいときだけ。reviewer は再レビューでも新規起動する（前回の判断に引きずられない）。
- 目的は **トークン（費用）を抑えること**。
  - 司令塔の会話は長くなるが、子は必要な文書だけを読んで始めるので軽い。
  - 重い読み書きを司令塔の外で行うことで、長い履歴を何度も読み直す費用を避けられる。
- **人間の判断が必須のこと以外は、司令塔が判断して、マージと片付けまで進める。** 「進めてよいですか」とは聞かない。
  人間の判断が必須なのは、「司令塔がマージしないもの」、レビューが指摘した重大な設計上の問題、修正の往復が 3 回を超えた場合、
  取り返しのつかない操作（データの削除と上書きなど）の場合に限る。
  ただし、Issue のクローズの可否と担当者の変更は、人に確認する（手順 10）。

クラウドのセッションや新規セッションは使わない（サブエージェントなら、起動のたびにモデルとエフォートを明示して指定できるため。別名で指定するので、実際に動いたモデルとエフォートは起動側から確認できない）。子エージェントは、同じ PC 上の Claude Code が起動するサブエージェントとして動かす。並行して作業させる場合は、子ごとに git worktree（作業用の別ディレクトリ）を割り当てる。

## 2. 役割とモデル

| 役割 | モデル | エフォート | 担当する作業 |
|---|---|---|---|
| 司令塔 | Sonnet | low | 依頼文の作成、自己レビューの依頼、マージ |
| 設計（designer） | Opus | medium | 設計判断（ADR）、方式の比較 |
| 実装（implementer） | Sonnet | medium | コードとテストの作成 |
| 機械的な作業（chore） | Haiku | low | 表記の統一、リンクの修正、単純な置換 |
| 調査（researcher） | Sonnet | medium | 設計の前に、既存の ADR、コード、Issue を読んで論点と根拠を整理する（書き換えない） |
| テスト（tester） | Sonnet | medium | 受け入れ条件と仕様からテストだけを書く（実装した子とは別に起動する） |
| 実機検証（verifier） | Sonnet | medium | 起動、配備、Playwright、本物の環境と AI での確認 |
| Issue 管理（issue-keeper） | Sonnet | low | マージ後の Issue の追記、チェック、クローズ |
| 自己レビュー（reviewer） | Sonnet | medium | PR の差分レビュー、UI 変更の実機確認（実装した子とは別に起動する） |

この表が model と effort の正本。3.1 の定義、3.2 の対応、手順 2 の対応は写し。
変更するときは、旧い値（例: `sonnet / medium`）を grep で全箇所探し、すべて直す。

運用の規則:

- 同時に動かす子は **最大 2 つ**。扱うファイルが重ならないように作業を分ける。
- **孫（子が起動する子）は、原則として使わない。** 例外は、調査が重く、子の文脈があふれそうなときだけ。次の条件をすべて満たす。
  - 司令塔が、依頼文に「孫の起動を許可する」と明記する（子が自分で決めない）。
  - 孫は researcher（読み取り専用）だけ。起動のたびに、`subagent_type`、`model`、`effort` を明示させる（sonnet / medium）。
  - 孫は最大 1 つ。孫も、同時に動かす数（最大 2）に数える。
  - 孫の結果は、子が要点を報告に含める。孫の起動数と用途も、報告に 1 行書かせる。
  - 孫は、さらに孫を起動しない。
- PR を出さない作業（文書と設定の編集など）では、子の報告の「確認済み」をそのまま信じない。司令塔が 1 か所以上を grep か Read で抜き取り確認する。広範囲と重要な変更は reviewer を新規起動する。
- 司令塔の会話が長くなったら `/compact` で圧縮する（人間が入力する。自動ループでは 5.6 の自動圧縮を使う）。モデルを切り替える前に圧縮すると、切り替え後の読み直しが安く済む。

## 3. セットアップ

### 3.1 子エージェントの定義

リポジトリに `.claude/agents/` を作り、次の 8 つのファイルを置く。チームで共有できるよう、このディレクトリもコミットする。

子を起動する前に、定義（`.claude/agents/` と `~/.claude/agents/`）の有無を確かめる。無いと、Agent ツールが「その種類は無い」と返す。
その場合は `general-purpose` で代用し、`model`、`effort` を明示して渡し、役割（implementer など）を依頼文の冒頭に「役割: 〜」と書く。
定義は、ユーザー共通の `~/.claude/agents/` に置くこともできる（リポに入れたくない場合）。

`.claude/agents/designer.md`

```markdown
---
name: designer
description: 設計判断（ADR）を書く。方式の比較と決定を docs/decisions/ に記録する。
model: opus
effort: medium
---
設計担当。依頼された論点について、選択肢、比較、決定、影響を ADR にまとめる。
- 既存の ADR と矛盾させない。矛盾する場合は、改訂する箇所を明記する。
- 作業ブランチを作り、コミットし、push して、PR を作成する（手順は CLAUDE.md の「PR の流れ」に従う）。
- 最後に、PR の URL と要点を 3 行以内で報告する。
```

`.claude/agents/implementer.md`

```markdown
---
name: implementer
description: 仕様や ADR に沿ってコードとテストを書く。
model: sonnet
effort: medium
---
実装担当。
- 変更は依頼された範囲に限る。
- push する前に、lint、型検査、テストをローカルで実行し、すべて通ることを確かめる。
- 作業ブランチを作り、コミットし、push して、PR を作成する（手順は CLAUDE.md の「PR の流れ」に従う）。
- 最後に、PR の URL、テスト結果、残った課題を 3 行以内で報告する。
```

`.claude/agents/chore.md`

```markdown
---
name: chore
description: 表記の統一やリンクの修正などの機械的な作業。判断を要しないもの。
model: haiku
effort: low
---
機械的な作業の担当。指示どおりに変更する。判断が必要になったら作業を止めて報告する。
PR の作成は CLAUDE.md の「PR の流れ」に従う。報告は 2 行以内。
```

`.claude/agents/reviewer.md`

```markdown
---
name: reviewer
description: PR の差分をレビューする。UI の変更では実機の確認も行う。実装した子とは別に起動する。
model: sonnet
effort: medium
tools: Bash, Read, Grep, Glob, Skill
---
レビュー担当。
まず PR のブランチを対象に、Claude Code 組み込みの `/code-review` を実行する（例: `/code-review medium <ブランチ名>`）。
続けて `gh pr diff <番号>` で差分を読み、`/code-review` の指摘も含めて次の観点で確かめる。
1. 正しさ（バグ、境界条件、エラー処理）
2. 依頼と仕様（ADR）に合っているか
3. テストが変更内容を確かめているか
4. セキュリティ（秘密情報の混入と入力検証）

画面（UI）に関わる変更では、依頼文の指示に従い、さらに次の 2 つを行う。差分を読むだけ、または模擬だけで「マージ可」にしない。
（実機検証担当 verifier の報告が依頼文にある場合は、それを根拠にしてよい。）
5. Playwright での見た目の確認（広い幅と狭い幅のスクリーンショットを撮って見る。崩れとはみ出しを判定する）。
6. 本物の環境と本物の AI を通した確認（模擬のテストページや模擬の API だけで済ませない）。

結果は「マージ可」「要修正」「未確認あり」のどれかで返す。
- 要修正なら、該当箇所（ファイル:行）と直し方を箇条書きにする。
- 5 と 6 のうち確認できなかったものがあれば「未確認あり」とし、何が未確認かを書く。模擬で確認した場合は、本物では未確認と書く。
コードは書き換えない。
```

`.claude/agents/verifier.md`

```markdown
---
name: verifier
description: 実機での確認（起動、配備、Playwright、本物の環境と AI）を行う。PRの差分は読まない。
model: sonnet
effort: medium
---
実機検証担当。依頼文の対象ブランチと受け入れ条件に沿って確かめる。コードは書き換えない。
1. 配備は、対象ブランチの変更から行う（既定ブランチから配備しない）。
2. Playwright で、広い幅と狭い幅のスクリーンショットを撮り、崩れとはみ出しを判定する。
3. 本物の環境と本物の AI を通して確かめる。模擬で確認した場合は、本物では未確認と書く。
4. 共用設定を変える場合は、元の値を控え、確認後に必ず戻し、戻したことを報告する。使うポートは依頼文に従う。
5. 起動したプロセスは、依頼文で許されるまで止めない。起動したポートと PID を報告する。
- 報告の冒頭にモデル ID。続けて「項目 → 方法 → 合格 / 不合格 / 未確認」を 5 行以内で。画面の URL と入り方を添える。
```

`.claude/agents/issue-keeper.md`

```markdown
---
name: issue-keeper
description: マージ後の Issue の追記、受け入れ条件のチェック、クローズを行う。
model: sonnet
effort: low
---
Issue 管理担当。依頼文の Issue 番号、リポジトリ、PRの結果に沿って、CLAUDE.md の「PRの流れ」手順 8〜10 を行う。
```

### 3.2 CLAUDE.md に追記する内容

リポジトリ直下の `CLAUDE.md` に、次の内容を追記する。

別の選択肢として、司令塔の核をユーザー共通の `~/.claude/CLAUDE.md` に、PR の流れの詳細をユーザー共通のスキルに置ける。
リポの CLAUDE.md は共有物で、リポごとの流儀（push の規則など）もあるため、個人の運用を直書きしたくない場合に向く。
その場合の置き場、整合確認、hook の確認は、7 章を読む。

```markdown
## 司令塔方式

- メインのセッションは司令塔。設計と実装は自分でせず、サブエージェント
  （設計 designer / 実装 implementer / 機械的な作業 chore / レビュー reviewer / 実機検証 verifier / Issue 管理 issue-keeper / 調査 researcher / テスト tester）に依頼する。
- 司令塔は sonnet / low 前提。自分のモデルが sonnet でないと分かったら（自分の説明文のモデル名で分かる）、
  **最初の応答で人間に警告**（意図しない費用の恐れ。`/model` で切り替えるか、このまま進めるかを確認）。エフォートは自分では確認できない。
- 同時のサブエージェントは最大 2。並行は isolation: worktree で起動。
- 孫（子が起動する子）は原則不使用。例外: 調査が重いとき、司令塔が依頼文で明記して許可した場合だけ（孫は researcher のみ、最大 1、同時数に数える、起動数と用途を報告させる）。
- 子の作業は **新規セッションではなく、必ずサブエージェント（Agent ツール）**。
  起動のたびに `subagent_type`、`model`、`effort` の 3 つを **明示**（定義ファイルの既定に頼らない。省くと司令塔のモデルを引き継ぎ、意図しない費用になる）。
  対応: 設計 designer = opus / medium、実装 implementer = sonnet / medium、機械的な作業 chore = haiku / low、レビュー reviewer = sonnet / medium、実機検証 verifier = sonnet / medium、Issue 管理 issue-keeper = sonnet / low、調査 researcher = sonnet / medium、テスト tester = sonnet / medium。
  重要な作業では、報告の冒頭に、子が自分の説明文で見たモデルIDを書かせる（エフォートは子から見えない）。
  定義が見つからなければ、`general-purpose` で代用し、`model`、`effort` を明示（役割は依頼文の冒頭に「役割: 〜」と書く）。
- PR を出さない作業（文書と設定の編集など）では、子の「確認済み」を信じ切らず、司令塔が 1 か所以上を grep か Read で抜き取り確認。広範囲と重要な変更は reviewer を新規起動。
- 依頼文の中身: 目的、対象ファイル、完了の条件、参照すべき文書。会話の経緯は渡さない。
- 依頼文の書き方: 丁寧語、挨拶、前置き、理由の説明なし。**常体の短い文、体言止め、箇条書き**（例:「対象: X。やること: Y。完了: Z」）。
  必要な制約だけ、1 文は短く、重複なし。
- 子の起動は新規が既定。修正の依頼文はブランチ名と指摘（ファイル:行と直し方）のみ。
  再開は、小さな追加修正で子の履歴が小さいときだけ。再開できるのは 1 回目の修正だけ。2 回目以降は新規起動。reviewer は再レビューでも新規起動。
- コミット、PR、報告は日本語。時刻は JST。
- 人間の判断が必須のこと以外は、司令塔が判断して、マージと片付けまで進める（「進めてよいですか」と聞かない）。
  必須: 「司令塔がマージしないもの」、レビューが指摘した重大な設計上の問題、修正の往復が 3 回超、取り返しのつかない操作（データの削除と上書きなど）。
  例外: Issue のクローズの可否と担当者の変更は、人に確認（手順 10）。
- 調整役（3.5）を導入した環境では、最初の応答で、用件より先に、調整役の確認と、いれば申告を行う。詳細は 3.5 の節。
- 自動ループ時は、子の報告の冒頭にモデルIDを常に書かせ、本文は 5 行以内。差分の全文は司令塔に貼らせない。
  定義の上限が小さい子（chore は 2 行など）は、その上限を優先。
- 自動ループ運用（人間の判断なしで、レビュー、マージ、次の作業の選定を繰り返す）: 完了報告 → reviewer → 修正（往復は最大 3 回）→ 再レビュー → 司令塔がマージ → 次の作業を選ぶ。
  停止: 「司令塔がマージしないもの」、重大な設計上の問題、未決の論点が空。状態メモ commander-state.md を節目ごとに更新し、圧縮と再開の後は最初に読む。
- 自動ループ運用と状態メモを扱うときは、スキル commander-auto-loop（3.2.1）を読んで従う。

## PR の流れ

0. ルートが git 管理されていない場合や、配下に複数のリポジトリがある場合は、git と gh の操作を
   すべて対象リポジトリのディレクトリで行う。worktree も対象リポジトリごとに作る。
   依頼文には対象リポジトリのパスを必ず書く。
1. 対象リポジトリの既定ブランチから作業ブランチを作る（例: feat/xxx, docs/adr-0006）。
2. コミットして `git push -u origin <ブランチ>` で push する。
3. `gh pr create --fill --base <既定ブランチ>` で PR を作成する。
4. 司令塔が reviewer に自己レビューを依頼する。
   - 「要修正」の場合は、作成した担当に修正を依頼し、もう一度レビューする（最大 3 回まで。
     超えたら人間に判断を求める）。修正の依頼は新規起動が既定（1 章）。
   - 画面（UI）に関わる変更では、**司令塔は、レビューを頼む依頼文に次の 2 つを必ず書く。頼まれなくても自動で行う。**
     1. **Playwright での見た目の確認**（広い幅と狭い幅のスクリーンショットと、崩れとはみ出しの判定）。
     2. **本物の環境と本物の AI を通した確認**（模擬のテストページや、模擬の API だけで済ませない。
        模擬で確認した場合は、本物では未確認と報告させる）。検証環境の構成（起動方法、接続先、配備の手順）は、
        <このリポジトリの検証環境の説明の置き場所>を読む。
     差分を読むだけ、または模擬だけで「マージ可」にしない。両方が済んでいない場合は「未確認あり」と返させ、
     司令塔は、確認を追加で頼む（頼めないものは人間に報告する）。
     配備は、レビュー対象のブランチの変更から行う（既定ブランチから配備すると変更が消える）。
   - **Issue に「受け入れ条件」がある場合**（頼まれなくても自動で行う）、司令塔は依頼文に Issue 番号とリポジトリ（owner/repo）を書き、
     reviewer に `gh issue view` で受け入れ条件を読ませ、**項目ごとにテストして結果を報告**させる
     （項目 → 方法 → 結果: 合格 / 不合格 / 未確認）。不合格は「要修正」、未確認は「未確認あり」。
5. CI（GitHub Actions など）は使わないので、マージの前に司令塔が担当の子に、PR のブランチで
   lint、型検査、テストをローカルで実行させ、すべて通ることを確かめる。
   失敗したら修正させ、手順 4 に戻る。テストを無効にして通すことはしない。
6. レビューが「マージ可」でテストも通ったら、司令塔が
   `gh pr merge <番号> --squash --delete-branch` を実行してマージする。
7. マージを確かめたら、worktree を削除する（`git worktree remove <パス>`）。
   `--delete-branch` がローカルブランチの削除に失敗した場合（そのブランチを worktree が checkout したまま）は、
   worktree の削除のあとに `git branch -D <ブランチ>` を実行する。
   squash マージでは `-d` が「未マージ」で失敗するため `-D` を使う。強制削除なので `allow` には入れず、確認のプロンプトで人間が承認する（マージ済みを `gh pr view` で確かめてから頼む）。
8. マージまで済んだら、関連する Issue に、修正内容を追記する（頼まれなくても自動で行う）。
   `gh issue comment <番号> -R <owner/repo> --body "<本文>"`。本文は、変更の中身、レビューで見つかった不具合とその対応、
   確認の結果（テスト、Playwright、本物の環境）、残りの項目を書く。Issue がクローズ済みでも追記する。
   関連する Issue がない場合は省く。
9. 追記したあと、受け入れ条件のチェックボックスを更新する（頼まれなくても自動で行う）。
   レビューで合格した項目だけ `- [ ]` を `- [x]` にする（不合格と未確認は外したまま）。
   Issue 本文を `gh issue view <番号> -R <owner/repo> --json body -q .body` で取得して該当行だけ書き換え、
   `gh issue edit <番号> -R <owner/repo> --body "<新しい本文>"` で反映する。他の記述は変えない。
   長い本文と日本語を含む本文は、`gh issue edit <番号> -R <owner/repo> --body-file <ファイル>` を使う（安全手順を参照）。
   チェックしなかった項目は、手順 8 の追記の「残りの項目」に理由とともに書く。受け入れ条件がない場合は省く。
10. 手順 9 のあと、Issue をクローズするか、AskUserQuestion で人間に確認する。選択肢は「クローズする」「クローズしない」。
   受け入れ条件がすべて `[x]`（または受け入れ条件がない）で、PRのマージが済んでいれば「クローズする」を、
   未チェックの項目が残ると Issue が複数の PR にまたがり続きがあるなら「クローズしない」を推奨にする。自動ループ運用でも省かない。
   「クローズする」: `gh issue close <番号> -R <owner/repo>`。
   「クローズしない」: 続けて AskUserQuestion で担当者を変えるか確認する（「変えない」「変える」。変える場合の担当者は「その他」の自由入力）。
   変える場合は `gh issue edit <番号> -R <owner/repo> --add-assignee <ユーザー名>`（外す場合は `--remove-assignee`） で反映し、結果を Issue への追記か報告に残す。
   関連する Issue がない場合は省く。

### PR の流れの補足（実運用で出た点）

- **マージ判定**: 「未確認あり」のまま司令塔がマージしない（自動判定にも拒否される）。人間に未確認の内容を示して許可を得るか、確認を追加で頼む。
  レビューの軽微な指摘（挙動に影響しないと差分が小さい）だけの修正は、司令塔がテストを再実行して通れば、再レビューを省いてよい。
  省いたことは、Issue の追記に書く。
- **マージ時の競合（マージできない）**: 作成担当に、既定ブランチを取り込ませ、競合を解消し、テストを再実行して push させる。そのあとマージし直す。
- **リポジトリ外の配備設定**: 識別子と環境変数の改名を含む PR は、起動スクリプトと環境ファイルなど、リポジトリ外の配備側の更新と、
  再配備とサーバーの再起動も、マージ後の作業に含める（実装担当に依頼文で頼む）。旧ディレクトリの削除も含む。
  他の作業（別 Issue）の配備先とポートには触れない。
- **共用設定の一時変更**（共用サービスの接続先の切替など、本物の環境での確認用）: 自動判定に拒否される。
  依頼の前に、人間の許可を得る。依頼文に「元の値を控え、確認後に必ず戻し、戻したことを報告」と書く。
  検証用のポートは、状態メモの「使用中のポートと環境」で重複を避ける。
- **子の最終報告が届かないとき**: 依頼文の末尾に「最終報告は通常の応答として返す（途中で SubagentHandback を使わない）」と書く。
  完了通知のあとも報告が届かない場合は、待たずに、出力ファイルの更新時刻と子の状態を見る。
  動きがなければ、同じ子の再開ではなく、新しい子を起動し直す（依頼文は経緯を含めて書き直す）。
  出力ファイルは、先頭を読まず、grep か末尾の 1 行だけを取り出す（全文を読むと文脈があふれる）。
- **長い検証の中間報告**: 依頼文に「詰まったら 30 分以内に原因付きで中間報告」を入れる。
  実行中の子に動きがあるかは、配備先のログとスクリーンショットの更新時刻で確かめる。
- **検証環境は人の画面確認が済むまで残す**: 受け入れ条件に「人が画面で確認」がある場合、依頼文に
  「確認後も自分が起動したプロセスを止めない（起動したポートと PID を報告）」と書く。止めるのは、人の確認が済んでから。
  環境の起動手順は、依頼文に毎回書かず、1 か所の文書にまとめて参照させる。
- **レビュー依頼の前にブランチを追従させる**: 配備して見せる前に、作成担当に既定ブランチを取り込ませ（競合は解消）、テストを通す。
  古いブランチを配備すると、別の作業で直った旧い表示が出て、原因の切り分けに時間を使う。
  取り込みで競合を解消した場合は、解消箇所を重点に再レビューさせる。
- **人の確認項目**: 受け入れ条件の「人が画面で見て良しとする」は、レビューで未確認になる。
  司令塔は、人に確認を頼むとき、画面の場所（URL とタブ名）と見てほしい点を添える。
  人が確認したと答えた項目は、Issue の追記に「人が確認」と書いてからチェックする。
- **状態メモの更新**: 子に依頼した直後と報告を受けた直後に、その場で更新する（最後にまとめない）。
- **共用設定の変更の承認**: 人間の「許可」の返事だけでは、自動判定に拒否されることがある。依頼の前に、
  人間へ「権限ダイアログの承認（またはマニュアルモード）が要る」ことを添えて頼む。拒否されても回避しない。
- **人に画面確認を頼む前**: 入口（共用の画面）が、今回のコードを通るか確かめる。共用サービスの接続先が他作業の配備先を向いていないか、
  配備したブランチは何かを見る。reviewer が別系統（別ポート）で確認した場合は、その旨と入口を人間に伝える。
  画面の URL、タブ名、入り方は、reviewer の報告に書かせる。他作業の配備先を向いている間は、マージ後も共用の画面に修正が出ないことを、人間に伝える。
- **reviewer の依頼文の定型**: 「最終報告は通常の応答として返す（SubagentHandback を使わない）」を毎回入れる。
  本文が届かないときは、出力ファイルを grep する。
- **日本語を含む `python3 -c`**: Git Bash では引数が化ける。検証はスクリプトファイルで行う。
- **二重管理**: 手順書の汎用部分が正本。ユーザー共通のスキルやリポの CLAUDE.md の補足は、導入時の写しに、そのリポと環境に固有の実績を足したもの。
  汎用の実績は手順書へ戻す。固有の値（ポート、ID、パス、メモリ名）は戻さない。
- **Issue 本文の更新（手順 9 と 10）の安全手順**: 取得 → 変換 → 内容の確認（長さとチェック数）→ 更新の順に分け、変換が失敗したら更新しない（`&&` でつなぐ）。更新の前に、元の本文を控える。控えと一時ファイルは作業用ディレクトリに置き、UTF-8 のバイトで読み書きする。更新は `gh issue edit <番号> -R <owner/repo> --body-file <ファイル>` を使い、更新後に本文の長さとチェック数を確かめる。空ファイルを渡さない。
- **本物の環境の入口情報**（ログイン、鍵の置き場所）: 文書かメモに、置き場所を書いておく（パスワードと鍵の実体は書かない）。
  無いと子が止まる。ID の総当たりと過去ログからの探索はしない。足りなければ、人間に聞く。
- **worktree の後始末**: `git worktree remove` は、そのディレクトリの外から実行する。
  シェルが握っていて空のディレクトリが残ったら、無理に止めず、状態メモに残して、セッション終了後に削除する。

## 司令塔がマージしないもの（人間の承認を待つ）

- 秘密情報、認証、権限に関わる変更
- データベースのスキーマ変更とデータ移行
- CI 設定（.github/workflows/）とデプロイ設定の変更
- 依存ライブラリの追加とメジャーバージョンの更新
```

### 3.2.1 自動ループ運用のスキル（3.2 から分けた詳細）

自動ループ運用の詳細は、CLAUDE.md を薄くするため、別のスキルに分ける。置き場は、ユーザー共通なら `~/.claude/skills/commander-auto-loop/SKILL.md`、リポ専用なら `.claude/skills/commander-auto-loop/SKILL.md`。
CLAUDE.md には、3.2 の要約と、このスキルを読む 1 行だけを置く。3.2 の追記先を決めたあと、同じ場所の系統（ユーザー共通かリポ専用か）にこのスキルを作る。

````markdown
---
name: commander-auto-loop
description: 自動ループ運用（人の判断なしで、レビュー、マージ、次の作業の選定を繰り返す）をするとき、状態メモ commander-state.md を更新するとき、会話の圧縮と再開の後に状態を読み戻すとき、利用制限で止まって再開するときに読む。
---

# 自動ループ運用（司令塔）

要点。詳細は導入手順の「5. 自動ループ運用」。

- 流れ: 子の完了報告 → reviewer が「マージ可 / 要修正 / 未確認あり」で返す → 要修正なら作成した担当に修正を依頼
  （同じブランチに追加コミット）→ 再レビュー → 「マージ可」ならローカルの lint、型検査、テストを通してから司令塔がマージ
  → 次の作業を司令塔が決めて繰り返す。「未確認あり」は、確認を追加で頼む（頼めないものは人間に報告して止まる）。
- 修正の往復は最大 3 回。超えたら人間に判断を求めて止まる。
- 停止条件: 「司令塔がマージしないもの」に当たる変更、レビューが重大な設計上の問題（安全性と既存の決定との矛盾）を
  指摘して直せない場合、未決の論点の一覧が空になった場合。人間に報告して止まる。
- 次の作業は、未決の論点の一覧から依存関係で先に必要なものを選び、理由を 1 行、状態メモに残す。
- 状態メモ commander-state.md（リポのルートに置く。`.git/info/exclude` で git から除外。リポをまたいで共有しない）を節目ごとに更新し、圧縮・再開後は最初に読む。節目（その場で、まとめて後回しにしない）:
  1. 子に依頼した直後: 進行中の作業に、PR と Issue 番号、担当、次の一手
  2. 子の報告を受けた直後: 判定（マージ可 / 要修正 / 未確認あり）、修正の往復の回数
  3. 共用設定とポートを使う作業の前後: 切り替えた設定の元の値、使うポート、戻したか
  4. マージと Issue のクローズの直後: 進行中から外し、決定済みの事項へ移す
  5. 人間の判断待ちで止まるとき（Issue のクローズと担当者の確認を含む）: 何を、なぜ待っているか
  6. 後始末が残ったとき: 残ったもの（削除できないディレクトリなど）
- 同時に動かす子は最大 2 本。ファイルが重なる作業は同時にしない。
- 利用制限や一時的な失敗で止まったら、解除まで待って再開する（予約メッセージで再開時刻を仕掛ける。
  約 1 時間後に見直しの予約を 1 本置く）。再開したら状態メモを読み、進行中の作業から続ける。
- 詳しくは導入手順の 5 章（見えない場合は上の規則だけで動く）。

## 子の長時間と停止の扱い

- 時間の上限は依頼文に書かない（Agent ツールにタイムアウト引数が無く、子は経過時間を測れない）。範囲（対象ファイルと完了の条件）で暴走を防ぐ。
- 長い処理（数分以上）は子に待たせない。コマンド側のタイムアウトを付け、バックグラウンドで走らせ、終了通知を待つ。
- 同じ失敗の再試行は 2 回まで。超えたら止めて報告させる。
- 応答が長く無いとき: 状態メモに「依頼中」を残し、約 1 時間後の見直しを予約する。止まったと判断したら TaskStop で止め、取り消せない操作でなければ新規の子で再依頼する。
````

### 3.3 権限の設定（確認のプロンプトを減らす）

`.claude/settings.json` に、よく使う安全なコマンドを許可しておく。

```json
{
  "permissions": {
    "allow": [
      "Bash(git status:*)", "Bash(git diff:*)", "Bash(git log:*)",
      "Bash(git add:*)", "Bash(git commit:*)", "Bash(git push -u origin:*)",
      "Bash(git worktree:*)",
      "Bash(gh pr create:*)", "Bash(gh pr view:*)", "Bash(gh pr diff:*)",
      "Bash(gh pr merge:*)", "Bash(gh issue view:*)", "Bash(gh issue comment:*)",
      "Bash(gh issue edit:*)", "Bash(gh issue close:*)", "Bash(gh api:*)"
    ],
    "deny": [
      "Bash(git push --force:*)", "Bash(git push -f:*)",
      "Bash(gh pr merge --admin:*)"
    ]
  },
  "effortLevel": "low"
}
```

- `effortLevel` はセッションの既定エフォート。子の effort は Agent ツールの呼び出しと定義で明示するので、セッションの `effortLevel` が効くのは司令塔だけ。司令塔は low 前提のため `"low"` にする。4 章の `/effort low` と合わせて二重の保険。
- モデルのバージョンを書くキー（claude-opus-5-5 など）は、モデルの世代交代で古くなるので使わない。サブエージェントの model / effort は、別名（opus、sonnet、haiku）で、定義ファイルの frontmatter と Agent ツールの呼び出しごとの指定に書く。
- サブエージェントのエフォートの優先順位（高い順）: 環境変数 CLAUDE_CODE_EFFORT_LEVEL、Agent ツールの呼び出しごとの effort、定義ファイル（.claude/agents/*.md）の effort、セッションのエフォート。`effortLevel` の位置が、この順位のどこに入るかは公式ドキュメントに明記されていない。
- マージの許可は prompt を省くだけ。「司令塔がマージしないもの」の保護は、規則と reviewer が担う（権限では守れない）。
- `gh api` は書き込みも通る広い許可。不要なら外してよい。

### 3.4 GitHub 側の設定

- 既定ブランチを保護し、直接 push を禁止する（「Settings > Branches > Branch protection rules」または Rulesets）。
  マージは PR 経由に限られるので、司令塔のマージも PR の記録として残る。
- 「Require status checks to pass before merging」は、GitHub Actions など CI を使わない場合は **無効** のままにする
  （有効にすると、チェックが報告されない PR をマージできない）。
- 「Require approvals」は、司令塔が自分でマージするため **無効** にするか、司令塔のアカウントを
  バイパスの対象にする。有効にすると、人間の承認がないとマージできなくなる。
- 前の節の「司令塔がマージしないもの」を確実に守るには、該当するパスに CODEOWNERS を設定し、
  「Require review from Code Owners」を有効にする。ただし有効にすると、そのパスを含む PR は
  すべて人間の承認が必要になる（司令塔のバイパスは効かない）。
  プライベートリポジトリでは、プランによって使えない機能がある。自社のプランで確認する。

### 3.5 調整役（任意の拡張）

複数セッションで共用の本物の環境を持つリポだけ。既定では導入しない。

8. 導入後の確認として、次の (a) から (c) を行う。
   - (a) 開き直したセッションで「調整役モード」と入力し、起動できるか試す。
   - (b) フックを入れた場合、開き直した直後に、画面へ【調整役】で始まる 1 行が出るか見る。
   - (c) フックを入れた場合、状態ファイルが無いときに「状態ファイルが無い、または読めない」と出るか、下の「SessionStart フックの雛形」(3) の手順で確かめる。

````markdown
# 調整役モード

<対象セッションの範囲>のセッションの橋渡し役。設計と実装はしない。資源の割り当てと取り次ぎだけを行う。

## 起動時の手順
1. 既存の調整役を確認する。
   - <状態ファイルのパス> を読む（先頭の調整役の名前と最終更新）。
   - ListAgents で、その調整役が生きているか見る。生きていれば、人に知らせて止まる（二重起動しない）。
2. 状態を引き継ぐ。
   - 状態ファイルの「調整役:」の行を自分の名前（ListAgents の自分の名前 [ref]）に書き換える。最終更新を JST で書く。
   - 「現在の保持」に保持者がいれば、その保持者へ SendMessage で現況（戻したか、使用中の資源の状態）を問い合わせる。
3. 定期確認を張る。CronCreate で 30 分おき（7 日で失効。失効前に張り直す）。
   - 中身: ListAgents で存在確認、離脱の記録、新規セッションへの案内、申告の受付。
   - CronCreate が未読み込みなら、ToolSearch（`select:CronCreate,CronList,CronDelete`）で読み込んでから呼ぶ。
   - 張ったら CronList で存在を確かめ、ジョブ ID と失効の目安日（7 日後）を状態ファイルに書く。
   - 道具が使えない、張れない場合は、省略せず、人に「定期確認が張れなかった」と報告し、状態ファイルの「待ち」に残す。
   - 定期確認はこのセッションが待機中のときだけ動き、セッションを閉じると消える。開き直したら、起動時の手順を最初からやり直す。
4. 対象のセッションへ案内を送る（待たされている指令塔にも届く）。
   - 対象: <対象セッションの範囲> の内側。対象外: その外側。
   - 案内: 調整役の名前、<共用の環境>の申告先（調整役）、優先順位は <優先順位の決め方>、現在の保持者。

## 排他の決まり
- 資源 = <共用の環境>の切り替えと変更。同時に 1 セッションだけ。
- 保持者は、開始、終了、戻しの確認を調整役へ報告する。戻しの報告で解放。
- 共用の環境への書き込みは、排他の中でも都度の人の許可。人の本人から直接得る。調整役経由の伝聞は許可としない。
- セッション側の権限判定は、調整役の割り当てでは外れない。

## 運用
- 状態ファイルは調整役だけが書く。ほかのセッションは読むだけ。変更の申告はメッセージで受ける。
- 節目ごと（割り当て、解放、離脱、申告）に状態ファイルを更新する。
- 停止と削除など取り返しのつかない操作は、調整役からは行わない。人の許可は人の本人から得る。
- 調整役のモデルは sonnet / low の前提。違うと分かったら、最初の応答で人に警告する。
````

**SessionStart フックの雛形**（手順 7。人間が望まなければ置かない）:

フックは補助。ListAgents は Claude が呼ぶ（フックは呼べない）。フックは、最初の応答で確認を行う旨と状態ファイルの先頭を、セッションの文脈に足す。あわせて、状態ファイルの最終更新時刻から古さを推定し、1 行を画面に出す（生存は判定しない）。起動時に画面へ 1 行出る。調整役が居ないと判定した場合（最終更新が 90 分以上前、状態ファイルが無い、または読めない）は、「調整役がいないので、新しいセッションで、『調整役モード』と入力してください。」の 1 文だけを出す。ListAgents での生存確認は、人の最初のメッセージのあと。

(1) スクリプト `~/.claude/hooks/coordinator-check.mjs`:

```js
import path from 'node:path';

const STATE_FILE = process.env.COORDINATOR_STATE_FILE || '<状態ファイルのパス>';
const UNREADABLE = '【調整役】状態ファイルが無い、または読めない。調整役は未起動の可能性';
// 調整役が居ないと判定したときに画面へ出す文（Claude 向けの additionalContext は別）
const ABSENT_SCREEN = '調整役がいないので、新しいセッションで、『調整役モード』と入力してください。';
// 古いと見なす分数。定期確認が 30 分おきで最終更新を書き換えるので、その 3 倍の 90 分。穴埋めの定期確認の間隔に合わせて調整してよい
const STALE_MIN = 90;

// 状態ファイルから 1 行の状態文を作る
function buildStatus(text) {
  const nameM = text.match(/^[-\s]*調整役[:：]\s*(.+)$/m);
  const timeM = text.match(/^[-\s]*最終更新[^:：\n]*[:：]\s*(\d{4})-(\d{2})-(\d{2})\s+(\d{1,2}):(\d{2})/m);
  if (!nameM || !timeM) return { status: UNREADABLE, screen: ABSENT_SCREEN };
  // 名前は括弧書きの注記（「（旧 ref …」）の手前まで
  const name = nameM[1].replace(/（.*$/, '').trim() || nameM[1].trim();
  const [, y, mo, d, h, mi] = timeM;
  const hh = h.padStart(2, '0');
  const stamp = `${y}-${mo}-${d} ${hh}:${mi} JST`;
  const t = Date.parse(`${y}-${mo}-${d}T${hh}:${mi}:00+09:00`);
  if (Number.isNaN(t)) return { status: UNREADABLE, screen: ABSENT_SCREEN };
  const mins = Math.max(0, Math.floor((Date.now() - t) / 60000));
  if (mins < STALE_MIN) {
    const s = `【調整役】${name}（最終更新 ${stamp}、${mins} 分前）`;
    return { status: s, screen: s };
  }
  return {
    status: `【調整役】${name}（最終更新 ${stamp}、${Math.floor(mins / 60)} 時間前）。古いので不在の可能性。調整役セッションを起動して「調整役モード」と入力する`,
    screen: ABSENT_SCREEN,
  };
}

    let body;
    let status = UNREADABLE;
    let screen = ABSENT_SCREEN;
    try {
      const text = fs.readFileSync(STATE_FILE, 'utf8');
      body = text.split(/\r?\n/).slice(0, 20).join('\n');
      ({ status, screen } = buildStatus(text));
    } catch {
      body = '状態ファイルが無い';
    }
    const msg =
      '【調整役の確認】最初の応答で、ユーザーの用件より先に、調整役の状態ファイル（' + path.basename(STATE_FILE) + '）の確認と、ListAgents での調整役の生存確認を行い、結果を 1 行で報告する。' +
      '調整役がいれば、調整役へ SendMessage で申告する（作業フォルダ、担当イシューまたは作業内容、<共用の環境>を使う予定の有無）。調整役から案内や申告の依頼が先に届いていれば、その返信で兼ねる。' +
      'フックの判定（ListAgents の結果と突き合わせる）: ' +
      status +
      '\n状態ファイルの先頭 20 行: ' +
      body;
    process.stdout.write(JSON.stringify({
      systemMessage: screen,
      hookSpecificOutput: { hookEventName: 'SessionStart', additionalContext: msg },
    }));
  }
} catch {
  // 補助なので、失敗しても何も出さない
}
process.exit(0);
```

(2) `~/.claude/settings.json` の hooks.SessionStart へ登録する。既存の設定を消さず、既存の hooks や SessionStart の配列があれば、その配列へ要素を足す（上書きしない）。

```json
{
  "hooks": {
    "SessionStart": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "node \"<ホームの絶対パス>/.claude/hooks/coordinator-check.mjs\""
          }
        ]
      }
    ]
  }
}
```

(3) 確認。3 パターンの stdin を渡して出力を見る。

- 配下の cwd: `echo '{"cwd":"<対象セッションの範囲のパス>"}' | node ~/.claude/hooks/coordinator-check.mjs`。`additionalContext` を含む JSON が出る。
- 配下でない cwd: `echo '{"cwd":"<配下でない任意のパス>"}' | node ~/.claude/hooks/coordinator-check.mjs`。何も出ない。
- 状態ファイルが無い場合: 環境変数 `COORDINATOR_STATE_FILE` に存在しないパスを入れて、配下の cwd で実行する（例: `echo '{"cwd":"<対象セッションの範囲のパス>"}' | COORDINATOR_STATE_FILE=/nonexistent node ~/.claude/hooks/coordinator-check.mjs`）。`systemMessage` が「調整役がいないので、新しいセッションで、『調整役モード』と入力してください。」の 1 文だけになる（`additionalContext` 側は「状態ファイルが無い、または読めない」）。状態ファイルは触らない。

フックが効くのは、セッションを開き直したあと。

## 4. 使い方

1. 司令塔として起動する: `claude --model sonnet` を実行し、`/effort low` でエフォートを下げる。
2. 依頼する例:
   > designer に ADR0006「P0 の範囲」を書かせて。参照は docs/decisions/0001〜0005。
   > 完了したら reviewer にレビューさせ、マージ可でテストも通ればマージして。
3. 2 つを並行させる例:
   > implementer を 2 つ worktree で起動して、A はパーサ（src/parser/）、B は検査器（src/check/）を担当させて。
4. 司令塔は子からの短い報告だけを受け取る。差分の全文は司令塔に貼らない（貼ると司令塔のトークンが増える）。

## 5. 自動ループ運用

人間の判断なしで、子の完了報告からマージ、次の作業の選定までを繰り返す運用。司令塔の役割（設計も実装もしない）は変わらない。

### 5.1 流れ

1. 子の完了報告を受ける。（PR を出さない作業は、2 章の抜き取り確認）
2. 別の子（reviewer、sonnet / medium）が PR をレビューし、結果を「マージ可」「要修正」「未確認あり」のどれかで返す。
   画面（UI）に関わる変更では、司令塔が依頼文に、Playwright での見た目の確認と、本物の環境と本物の AI を通した確認を必ず書く（頼まれなくても自動で行う）。
3. 「要修正」なら、PR を作成した担当に修正を依頼する（同じブランチに追加コミット。依頼は新規起動が既定で、reviewer の再レビューも新規起動。1 章）。その後、もう一度レビューする。
   「未確認あり」なら、未確認の項目の確認を追加で頼む（頼めないものは人間に報告して止まる）。
4. 「マージ可」なら、マージの前に、PR の流れの手順 5 を行う。司令塔が担当の子に、PR のブランチでローカルの lint、型検査、テストを実行させ、すべて通ることを確かめる。失敗したら修正に戻す（3 の往復に数える）。
5. すべて通ったら、司令塔がマージする（`gh pr merge <番号> --squash --delete-branch`）。
6. 次の作業を司令塔が決め（2）、同じ流れを繰り返す。

修正の往復は最大 3 回。超えたら人間に判断を求めて止まる。

### 5.2 次の作業の決め方

- 未決の論点の一覧（課題一覧。例: 未決の論点の表）から、依存関係で先に必要なものを選ぶ。
- 選んだ理由を 1 行、状態メモに残す。
- 一覧が空になったら、人間に報告して止まる。

### 5.3 人間の承認を待って止まるもの

- 3.2 の「司令塔がマージしないもの」の一覧のとおり。
- さらに、レビューが重大な設計上の問題（安全性、既存の決定との矛盾）を指摘し、修正で直せない場合。
- 取り返しのつかない操作（データの削除と上書きなど）。
- これら以外は、人間に確認を求めず、司令塔が判断して進める。

### 5.4 状態メモ

次の内容をファイルに書き、節目ごとに更新する（例: リポのルートの `commander-state.md`。`.git/info/exclude` に書いて git の対象から外す。リポをまたいで共有しない。リポごとに 1 つ）。

- 役割
- 運用の規則
- 決定済みの事項
- 進行中の作業（PR 番号、担当、次の一手）
- 使用中のポートと環境（検証用。他の作業の分も。重複を避けるため）
- 未処理の後始末（削除できなかったディレクトリなど）
- 次の作業の候補

雛形（見出し構成。手順 4 の「空の雛形」はこれ）:

```markdown
# commander-state

## 役割
## 運用の規則
## 決定済みの事項
## 進行中の作業

| PR と Issue 番号 | 担当 | 次の一手 |
|---|---|---|

## 使用中のポートと環境
## 未処理の後始末
## 次の作業の候補
```

更新の節目は、3.2.1 のスキルの「状態メモ」の項（子に依頼した直後、報告を受けた直後、共用設定とポートの前後、マージとクローズの直後、人間の判断待ち、後始末が残ったとき）。
会話が圧縮、再開されたら、最初にこのファイルを読む。

### 5.5 利用制限で止まったときの再開

- 利用制限や一時的な失敗で止まったら、解除まで待って再開する。
- 待つ手段として、予約メッセージ（`send_later` など、使えるもの）で再開時刻を仕掛けておく。
- 長時間、動きがなければ見直す安全網の予約を、約 1 時間後に 1 本置く。
- 再開したら状態メモを読み、進行中の作業から続ける。

### 5.6 圧縮

- 履歴が長いほど費用が増える。`/autocompact 200k`（または settings.json の `autoCompactWindow`）で、
  既定より早く圧縮させる。
- 公式ドキュメントで確認済みの事項:
  - `/autocompact [auto|トークン数]` は 100K〜1M の範囲で指定でき、v2.1.221 以降で使える。
    現在のモデル向けの設定として、ユーザー設定の `modelSettings` に保存される。
    （出典: https://code.claude.com/docs/en/commands.md）
  - 1M トークン級のモデルの既定のしきい値は約 967K。`autoCompactWindow` は 100000〜1000000。
    （出典: https://code.claude.com/docs/en/model-config.md、https://code.claude.com/docs/en/settings-reference.md）
  - 優先順位（高い順）: 環境変数 `CLAUDE_CODE_AUTO_COMPACT_WINDOW`、上位スコープの設定、`--autocompact`、
    保存済みの `modelSettings`、トップレベルの `autoCompactWindow`。（出典: 同上の model-config.md）
  - 圧縮後の復帰用に、`SessionStart` フック（matcher: `"compact"`）で状態メモを読ませる方法がある。
    `PreCompact`、`PostCompact` フックもある。（出典: https://code.claude.com/docs/en/hooks.md）
- 公式ドキュメントに記載が見つからなかったこと（断定しない）:
  - `/autocompact` で自動圧縮を切る（off）方法
  - プロジェクト単位での保存
  - `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` と `autoCompactWindow` の優先関係
  - `/compact` に渡す指示を設定ファイルで既定にする方法
- `/compact` は人間が入力するもの。司令塔はツールとして呼び出せないため、実行できない（実際に試して確認した）。

### 5.7 並行

同時に動かす子は最大 2 本。ファイルが重なる作業は同時にしない。

### 5.8 子の報告

自動ループ時は、報告の冒頭にモデルIDを常に書かせ、本文は 5 行以内にする。差分の全文は司令塔に貼らせない。
定義ファイルの上限がこれより小さい子（chore の 2 行など）は、その上限を優先する。

子の長時間と停止の扱いは、3.2.1 のスキルの「子の長時間と停止の扱い」節に従う。

## 6. トークンを抑えるための注意

- 依頼文には目的、対象、完了条件だけを書き、会話の経緯は渡さない。
- 子からの報告は短くさせる（各定義に行数の上限を書いてある）。
- 司令塔では、長いファイルの読み込みやテストの実行をしない。それらは子に任せる。
- 区切りのよいところで（人間が）`/compact` を実行し、残す内容（役割、対象リポジトリ、決定事項、
  未完了の作業）を指定する。自動ループ運用では、5.6 の自動圧縮を使う。
- 判断の質が成果物そのものになる設計作業だけに Opus を使い、それ以外は Sonnet か Haiku を使う。

## 7. リポごとの流儀との共存

リポごとに CLAUDE.md、docs、hook（push の規則など）がある場合の扱い。複数のリポに導入するときは、先にここを読む。

### 起点

- リポごとに CLAUDE.md と hook がある場合、セッションはリポのルートから開く。
- 親フォルダ起点だと、サブフォルダの CLAUDE.md は遅れて読まれ（そのフォルダのファイルに触れたとき）、hook は効かない。
- VS Code は、リポごとに別の窓で開く。

### AGENTS.md

- Claude Code は AGENTS.md を自動では読まない。
- 導入先に AGENTS.md がある場合は、CLAUDE.md に `@AGENTS.md` と書いて取り込む。

### 置き場

- 司令塔の核（役割、モデル、サブエージェントの使い方）は、ユーザー共通の `~/.claude/CLAUDE.md` に置ける。
- PR の流れの詳細は、ユーザー共通のスキル（例: PR の流れのスキル）に置ける。
- 自動ループ運用の詳細は、ユーザー共通のスキル（commander-auto-loop。3.2.1）に置ける。
- リポの流儀が優先。司令塔の運用と矛盾したら、リポに寄せる。
- リポの CLAUDE.md は共有物。個人の運用（司令塔方式など）を直書きしない。
- 個人の好み（言語、コマンド名、公開の可否など）は、手順書の対象外。導入先の独自分として扱い、手順 2 の問い合わせで「残す（推奨）」とする。

### 導入前の整合確認

導入先リポの CLAUDE.md、docs、hook と、司令塔の運用を突き合わせる。見る点の例:

- push の前後の順序（レビュー、テスト、push のどちらが先か）
- PR を出すかの基準（常に出すか、一定規模以上か）
- 人が後から確認する issue を自動でクローズしてよいか
- CI の有無（CI がある場合、手順 5 のローカル実行との関係）
- 依存追加の規則

矛盾はリポの流儀に寄せる。寄せた点は、状態メモの「決定済みの事項」に残す。

### hook の確認

- push するものが無いと、hook は通す（効いているように見えない）。
- 未 push の試験用コミットを作り、`git push --dry-run` で hook が効くことを確かめる。
- 確かめたら `git reset --hard HEAD~1` で試験用コミットを取り消す。
