## 1. 概要

本報告書は、Issue #550 の完了条件に基づき、G3 報告書（`docs/security/2026-11-16-g3-review-d9c1281e.md`）の項目 8「信頼基盤」で「未実施を含む」とされた課題の解消状況および調査結果を記録するものである。

2. **レビュー・承認記録の監査**: P1 期間に信頼基盤を変更した全 24 件の PR のうち、未確認だった残り 20 件のレビュー記録を確認し、#489 の所有者承認記録の有無を確定した。

### 2.1 実在するファイルの確認と対応

ADR 0018 判断 1 の T2/T3 が対象として定めた構成要素について、リポジトリ内の実在状況を確認した:

| 対象要素 | 想定パス | 実在状況 | 対応内容 |

| 許可の一覧 | `trust-base.list` | **実在しなかった** | 本 PR でリポジトリのルートに空のテンプレート（説明コメント付き）として新規作成・配置 |
| 信頼基盤の標準ライブラリ | `src/stdlib/*.sigil`, `src/stdlib/*.rs` | **実在する** | 22 個の `.sigil` ファイルおよび組み込み関連 Rust ファイルが存在。CODEOWNERS の対象として指定が必要 |

### 2.3 ブランチ保護（Branch Protection）の現状と推奨設定

- **現状**:
  - GitHub REST API（`repos/goodnasubi/sigil/branches/main/protection`）の確認結果、`HTTP 404: Branch not protected` となっており、`main` ブランチに保護設定が存在しない。
  - GitHub の仕様上、CODEOWNERS によるレビュー必須化を強制するためには、ブランチ保護ルールで「Require review from Code Owners」を有効にする必要がある。
- **所有者の判断を仰ぐ設定内容**:
  1. **Require a pull request before merging**: 有効
  2. **Require review from Code Owners**: 有効（所有者の承認なしでのマージをブロック）
  3. **Required approving reviews**: 1
  4. **Require status checks to pass before merging**: 有効（`test`, `fuzz`）
  5. **Do not allow bypassing the above settings**: 有効（管理者・Bot の迂回防止）

## 3. P1 信頼基盤変更 PR 24 件のレビュー記録監査（完了条件 2）

### 3.1 #489 の所有者承認記録の確定

- **結論**: **所有者による「先行承認」の記録が存在することを確定した。**
- **経緯と証拠**:
  - G3 報告書では「PR #489 に所有者承認の記録がない」と指摘されていた（PR コメントには agy のレビュー承認のみが転記されていた）。
  - しかし、PR #489 が対応した **Issue #483 のコメント（2026-11-14T16:07:50Z / 2026-11-15 01:07 JST、記録者: クマ）** において、所有者（池田さん）による先行承認が以下の通り明記されていた:
    > 「本 Issue（#483、6-4f）について、後続の PR も承認済みとして扱うこと。マージの条件は次の3点が揃うことです: (1) PR の差分が本 Issue の範囲内（`signalfd4` / `rt_sigprocmask` による SIGTERM / SIGINT の受け取り、受け付けの中断、`RootGroup` のドレイン、猶予タイムアウト、評価器テスト、`trust none` の維持）であること、(2) CI が緑であること、(3) 別系統のレビュー承認があること。条件が揃えば、所有者へ改めて確認せずにマージまで進めてよい。」
  - AGENTS.md の「レビューとマージ」規則には「人間の承認は、対象の Issue の段階で、範囲を明示して先行して与えることもできる（先行承認）。先行承認がある場合、その範囲内の差分にとどまる PR は、CI が緑で別系統のエージェントの承認が揃えば、改めて人間の承認を得ずにマージしてよい」と定められている。
  - PR #489 は上記 3 条件（差分範囲内、CI 緑、agy 承認）をすべて満たしてマージされていた。PR 側への参照転記が漏れていたために未承認と見えていたが、**ルールに基づいた正当な先行承認が存在していた**ことが確定した。

### 3.3 監査結果の分析

1. **初期 PR（#222〜#273 の 8 件）**:

## 4. 改善提案と運用上の留意点

1. **先行承認の参照の明記**:
   - Issue で先行承認が行われた場合、PR 作成時およびマージ時に、必ず PR 本文またはコメントに「Issue #XXX の先行承認（URL / 記録番号）」を明記する運用を徹底する。
2. **CODEOWNERS とブランチ保護の適用**:
   - 所有者による CODEOWNERS の設定反映および GitHub リポジトリ設定でのブランチ保護ルールの有効化を速やかに実施することを推奨する。
