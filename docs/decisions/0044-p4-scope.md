# 0044: P4 の範囲（データベースとリポジトリ管理）

- **状態**: 提案（typesafe-ai の正式判定は実施済み。末尾の「正式判定の記録」を参照。Codex Cloud レビュー受領済み）
- **日付**: 2026-11-17（JST）
- **対象**: [Issue #571](https://github.com/goodnasubi/sigil/issues/571)、レーン E

## 背景

[ADR 0005](0005-long-term-goals.md) の段階表は、P4 を「データベース（G3）・リポジトリ管理（G4）。Sigil で書いたアプリケーションとして実装。前提は P1」と定め、P5（コンテナ管理）の前提を「P1、P4」とする。P2（Web フルスタックと IDE）は全段が完了した（[ADR 0039](0039-p2-1-javascript-output.md)〜[ADR 0043](0043-p2-5-ide.md)）。所有者は 2026-11-17 に次段を P4 と決めた。理由は、P4 が P5 の前提であり、最長の依存鎖が動くためである。P3（Python の置き換え）は、他の段階が待っていないので後回しにする。

本 ADR は P4 の範囲・段組み・各段の完了条件の形を定める。各段の詳細設計は、段に入る前に個別 ADR で決める。ADR 0005 の「規模についての注記」のとおり、G3・G4 の置き換え対象（PostgreSQL、Git）は長年開発された大規模なソフトウェアであり、最初はどの機能までを置き換えるかを、この ADR で区切る。

### 用語: 「G3」の二つの意味

本リポジトリでは「G3」が二つの意味で使われる。本 ADR では次のように書き分ける。

- **G3（DB）**: ADR 0005 の長期目標 G3、データベースの置き換え。G4 はリポジトリ管理（Git）の置き換え。
- **公開関門 G3**: [ADR 0020](0020-p1-security-addendum.md) 決定 3 の、外部公開の前のセキュリティレビュー。G1（段階の ADR の脅威の節）・G2（段階の完了の確認）とともに「公開関門」と呼ぶ。

Issue #571 の「G3 は 2026-11-16 に所有者が『いまは外部公開しない』で一旦区切りと決定済み」は、後者（公開関門 G3、報告書 `docs/security/2026-11-16-g3-review-d9c1281e.md`）を指すと読んだ。報告書の未達の点は Issue #547〜#552 で追跡されている。

起草の基準は `main` の `a8c7d32`。0044 は main のファイル・索引・オープン PR で未使用であることを確認した。本 PR は本 ADR の新規作成と索引追加だけを変更し、処理系・`sigil spec` の出力・実装・バックログは変更しない。

## 現状の確認（2026-11-17 時点の main）

- P1 に、PostgreSQL の通信方式を Sigil で実装した**クライアント**がある（[ADR 0034](0034-p1-postgresql-client.md)。SCRAM-SHA-256 のみ、平文通信、接続プール）。**サーバー側の実装は無い**。
- 標準ライブラリのファイル操作（`os_fs`）は `read`／`write`／`read_bytes`／`write_bytes`（ファイル全体の読み書き）だけを確認できた。データベースと Git が必要とする **同期（fsync）・原子的な名前変更・追記・位置を指定した読み書き・ファイルのロック・ディレクトリの操作**は確認できなかった。圧縮（zlib／deflate）と SHA-1 も無い（SHA-256 は `std.crypto` にある）。
- 公開関門 G3 の報告書は、定数時間・ファジング・上限・信頼基盤のレビューに「未実施を含む」「満たさない」を残した。所有者は「いまは外部公開しない」と決め、残りの判断は外部公開の検討を再開した時点で行う（Issue #552）。
- [ADR 0038](0038-p2-scope.md) と [ADR 0043](0043-p2-5-ide.md) は、「Git そのものの実装は P4 に属する」と定め、P2-5 の仕様差分は Git に依存しない二つのスナップショットの比較とした。

## 選択肢と決定

| 判断 | 採用する案 | 他案を採用しない理由 |
|---|---|---|
| 段組みと順序 | データベース（P4-1・P4-2）を先に、リポジトリ管理（P4-3・P4-4）を後に置く。設計の共通部分（永続化の規則・障害の試験）を P4-1 の個別 ADR で先に決めれば、リポジトリ側の設計は並行して進めてよい | リポジトリ管理を先にすると、P5 が最初に必要とする状態の保存を後ろにずらす。両方を同時に完成させてから使うと、途中の成果物が使えない（ADR 0005 決定 2） |
| データベースの初版 | 単一ノード・永続・トランザクション付きの関係データベース。まず組み込み用の核、次に PostgreSQL の通信方式の部分集合を話すサーバー | 分散・複製・高可用性を初版に入れると範囲が過大になる。PostgreSQL の全機能互換は ADR 0038 の方針（既存製品の全機能互換を完了条件にしない）に合わない。独自の通信方式だけにすると、P1 のクライアントと既存の試験が使えない |
| リポジトリ管理の初版 | Git のオブジェクト形式と互換な、ローカルの操作（保存・履歴・差分・三方向併合・ブランチ）。ネットワーク転送は後の段 | 独自形式にすると、本物の Git で検査できず、移行もできない。転送まで含めると、P1 の HTTP とのつなぎや認証の判断が一度に増える |
| 実装するリポジトリ | 仕様（ADR）は `sigil` リポジトリに置き、実装は別のリポジトリで行う。ただし、リポジトリの作成は所有者の操作で、作成されるまでの扱いを決定 4 に定める | 実装を `sigil` に入れると、言語処理系の変更と大規模アプリケーションの変更が一つの履歴・CI・レビューに混ざる（ADR 0005 の想定に反する）。別リポジトリで ADR も持つと、番号の管理と仕様のレビューの場が二つに割れる |
| 外部公開 | 「いまは外部公開しない」を P4 でも維持し、P4 の各成果物にも公開関門 G1〜G3 を適用する | 外部公開の検討を P4 の開始条件にすると、P5 に至る依存鎖が止まる。公開関門を適用しないと、実在の利用者のデータを扱うデータベースが、検査なしに公開されうる |

正式判定は未実施である。上の採用案は、判定を経ていない起草者の案であり、判定の結果を装わない。採用理由は、ADR 0005 の段階表との整合、各段が単独で使える成果物を出すこと、検証できる完了条件を持つことに置く。

## 決定 1: 段組みと各段の成果物

### ADR 0005 の段階表との対応

| ADR 0005 の P4 | 本 ADR の段 | 置き換え対象 |
|---|---|---|
| データベース（G3） | P4-1 データベースの核、P4-2 データベースサーバー | データベース（PostgreSQL のような関係データベース） |
| リポジトリ管理（G4） | P4-3 リポジトリの核、P4-4 リポジトリの転送とホスティング | Git |
| 前提 P1 | 各段は P1 の成果物（HTTP・認証・PostgreSQL クライアント・コンテナ配布）を再利用する | — |
| P5 の前提 | 決定 5 に、P5 へ渡すものを列挙する | — |

### 各段の最初の範囲

| 段 | 最初に含める範囲 | その段の完了を確かめる方法 |
|---|---|---|
| P4-1: データベースの核 | 組み込み用の永続ストレージ（ページ、先行書き込みログ、トランザクション、クラッシュからの復旧）と、関係の表・索引・主キー。SQL の解析・実行は P4-2 | 一貫性（ACID）の性質試験と、プロセスを任意の時点で強制終了する復旧の試験（書き込み途中の電源断を模す）。保存形式の破損入力に対するファジング。同じ操作列を P1 の PostgreSQL（CI の公式イメージ）に与えた結果と比べる |
| P4-2: データベースサーバー | SQL の部分集合（宣言・挿入・更新・削除・選択・結合・集約・トランザクション）と、PostgreSQL の通信方式（v3）の部分集合を話すサーバー。認証は SCRAM-SHA-256 のみ | P1 のクライアント（ADR 0034）と接続プールで、既存の `pg_*` 試験の対象を本サーバーに替えて通る。同じ文の列を PostgreSQL と本サーバーに与え、結果と、エラーの種類を比べる（対象の文の範囲は個別 ADR が列挙する） |
| P4-3: リポジトリの核 | Git のオブジェクト形式（blob・tree・commit、緩い形式と pack の読み取り）と参照（ブランチ・タグ・HEAD）。ローカルの操作（初期化・追加・コミット・履歴・差分・checkout・三方向併合）。仕様差分（ADR 0043）が使える、スナップショットの取り出し | 本物の Git で作ったリポジトリを読み、本サーバーで作ったリポジトリを `git fsck`／`git log`／`git diff` が受理して同じ結果を返す。中断した書き込みの後で破損しない |
| P4-4: リポジトリの転送とホスティング | HTTP による取得・送信（P1 の `std.web` と認証の上）と、Sigil 製の小さな管理画面（P2 の UI）。ssh は対象外 | 本物の Git の `clone`／`fetch`／`push` が本サーバーに対して通る。権限のない操作と上限超過が既定で拒否される |

各段は単独で使える成果物を出す。後続の段が無くても、P4-1 は組み込み用の保存層として、P4-3 はローカルの履歴管理として利用・検証できる。P4-1 → P4-2 の順は固定する。P4-3 は P4-1 の個別 ADR で永続化の規則（原子的な更新、整合性の検査値、障害の注入）を決めた後に、並行して着手してよい。

## 決定 2: 各段の個別 ADR の方針と完了条件の形

- 各段は、実装の前に個別 ADR を `sigil` リポジトリの `docs/decisions/` に起草し、契約変更→ADR→実装→サンプル・テストの順で進める（ADR 0038 決定 1 と同じ）。個別 ADR は、対象とする機能・保存形式・通信の対応集合・上限・脅威と対策を列挙する。「全機能の実装済み」を意味しない。
- 完了条件は「参照実装との比較」を基本にする。データベースは PostgreSQL（CI にある公式イメージ）、リポジトリ管理は本物の Git を比較相手とし、比較できない性質（クラッシュ復旧、破損入力）は、固定した期待値と注入試験で確かめる。既存製品との差は、対応表に「未対応」として残す。暗黙の縮退で完了扱いにしない。
- データベースとリポジトリ管理は、**持続性の誤りが利用者のデータの喪失になる**。そのため、通常の機能試験に加え、(1) 強制終了と書き込み途中の中断の注入、(2) 保存形式のファジング、(3) 保存したデータを新しい版が読めること、を各段の完了条件に含める。既存の障害注入の枠（`docs/fault-injection/`）を、保存層の試験にも適用できるかを P4-1 の個別 ADR で検討する。
- 参照製品との比較のための試験は、`postgres.yml` と同様に隔離した環境で行い、秘密を使い捨てにする。外部のネットワークへ接続しない。

## 決定 3: 「いまは外部公開しない」との関係

- 公開関門 G3 の決定（2026-11-16、いまは外部公開しない）は **P4 でも維持する**。P4 の開発は、CI と手元のコンテナで動かす範囲（ADR 0020 が「外部公開に当たらない」とする範囲）で行う。
- P4 の各成果物の外部公開は、P1 の外部公開の条件（Issue #547〜#552 の判断を含む）とは別に、次を満たしたときに、所有者が判断する。(1) 個別 ADR に「脅威と対策」の節がある（公開関門 G1 に相当）、(2) 段の完了時に、定数時間・ファジング・上限・秘密の確認が入っている（G2 に相当）、(3) 実装者と別のセッションによる公開前レビューの報告が `docs/security/` に残り、所有者が公開の可否を決めている（G3 に相当）。ADR 0020 の改訂は本 ADR の範囲外とし、必要なら別 Issue とする。
- データベースとリポジトリ管理は、実在の利用者のデータ（認証情報を含む）を保存する。公開関門の確認の項目は、保存層に特有の観点（保存データの暗号化の有無と範囲、アクセス制御、バックアップに秘密が混ざること、削除したデータが残ること）を個別 ADR で加える。保存データの暗号化の要否は、本 ADR では決めない。

## 決定 4: 別リポジトリとの整合

ADR 0005 は、P4 以降のアプリケーションを別のリポジトリで開発することを「想定」した。本 ADR は次のように決める。

- **仕様（ADR）は `sigil` リポジトリに置く**。ADR の番号の管理と、人間による仕様のレビューの場を一つに保つためである。個別 ADR は、実装の置き場所と、依存する `sigil` のコミットまたは版を明記する。
- **実装は別のリポジトリで行う**。データベースとリポジトリ管理は、それぞれ別のリポジトリを想定する（名前は所有者が決める）。リポジトリの作成と、権限・CI・保護の設定は**所有者の操作**であり、エージェントは作成しない。
- 別リポジトリが作成されるまでは、**実装に着手しない**。個別 ADR の起草は `sigil` リポジトリで進めてよい。所有者が、作成を待たず `sigil` の中で始めると決める場合は、その旨と移す時期を個別 ADR に記録する。
- 別リポジトリは、`sigil` のコンパイラと標準ライブラリを、固定した版で利用する。必要な版の取得の方法（コンテナイメージ、または固定したコミットのビルド）は、P4-1 の個別 ADR より前に決める。
- 別リポジトリの実装中に見つかった言語や標準ライブラリの不足は、`sigil` リポジトリで Issue にし、ADR→実装の順で解決する。アプリケーションの側に、言語の欠陥の回避策を黙って入れない。信頼基盤（`unchecked`／`raw.*`）の追加は、ADR 0016 の許可の手続きに従う。
- 別リポジトリにも、`sigil` の作業の決まり（AGENTS.md の判断の手順、ブランチ・コミットの規則、レビューの分担）を引き継ぐ。その具体は、所有者がリポジトリを作成する際に定める。

## 決定 5: P5（コンテナ管理）への橋渡し

P5 の範囲は P5 に入るときの ADR で決める。ここでは、P4 が P5 のために**用意するもの**を、方向として定める。P5 の ADR が必要としない場合は、変えてよい。

1. **状態の保存**: コンテナの望ましい状態・観測した状態・割り当てを保存する、単一ノードで永続・トランザクション付きの保存層（P4-1）と、P1 のクライアントから使える形（P4-2）。
2. **変更の通知**: 状態の変化を購読する仕組み（PostgreSQL の `LISTEN`／`NOTIFY` に相当）。調整ループが、状態の変化を受け取るために使う。範囲は P4-2 の個別 ADR で決める。
3. **内容で参照する保存**: コンテナのイメージ（OCI）は、内容の SHA-256 で参照される。リポジトリ管理のオブジェクトの保存は、イメージの層を保存する場合にも使えるよう、**保存層を分けて設計する**。Git のオブジェクト形式の SHA-256 対応は、P4-3 の個別 ADR で決める。
4. **宣言の版管理**: コンテナの望ましい状態の宣言を、リポジトリ管理で版管理し、差分を見られる。P2-5（ADR 0043）の仕様差分と同じ入力の形（二つのスナップショット）を使う。
5. **バックアップと復元**: 保存した状態を、整合した時点で取り出し、復元できる（P4-1 の個別 ADR で最小の形を決める）。

P5 が必要とする効果のカテゴリ（コンテナの操作など）は、ADR 0005 決定 3 のとおり、P5 の ADR で追加する。P4 は新しい効果のカテゴリを必要としない見込みだが、ファイルの同期・原子的な名前変更・ロック・位置を指定した読み書きは、標準ライブラリの追加が要る（「前提と持ち越し」の 1）。

## P4 全体の完了条件

1. P4-1〜P4-4 の成果物が揃い、各段の「完了を確かめる方法」を満たす。参照製品との差は対応表に残る。
2. P1 のクライアントと接続プールが、本データベースサーバーに対して動く。本物の Git が、本リポジトリ管理に対して動く。
3. 各段の個別 ADR が定める安全上の確認と、必要な所有者の承認を完了する。「いまは外部公開しない」は、所有者が変更を決めるまで維持する。
4. 各段の検証の記録（比較試験、復旧試験、ファジング、上限）を残す。

## 決めないこと

- 各段の詳細（SQL の文法の範囲、保存形式、索引の種類、pack の最適化、通信の細部）。個別 ADR で決める。
- P3（Python の置き換え）の範囲。
- 保存データの暗号化の要否、外部の専門家のレビューを加えるか（所有者が公開の前に決める。ADR 0020）。
- 別リポジトリの名前、作成の時期、権限の設定（所有者の操作）。
- 仕様そのものの判断点。ADR の判断点は、判断の手順（理念に照らして考え、typesafe-ai で正式判定し、判定を経ても迷う場合だけ人間へ）に従う。

## 前提と持ち越し

次は、実装前に別の決定または作業が要る。本 PR では修正・再起票しない。

1. **標準ライブラリの不足**（現状の確認を参照）: ファイルの同期・原子的な名前変更・追記・位置を指定した読み書き・ロック・ディレクトリ操作。圧縮と SHA-1（Git の既定のオブジェクト形式で必要。SHA-256 形式のみを対象にするかは P4-3 の個別 ADR で決める）。これらは `std.fs` の拡張または信頼基盤の追加になりうるため、ADR 0005 決定 3・ADR 0016 に従い、P4-1 の個別 ADR より前に別 ADR または別 Issue で扱う。
2. **評価器・ネイティブの速度**。Issue #539 の実測では、評価器の暗号処理が遅い（PBKDF2 4096 回で約 2.7 秒）。データベースとリポジトリ管理は、大量のハッシュと解析を行うため、性能を完了条件に含めるかを個別 ADR で決める。初版の合否にはしない（P2-4 と同様に、記録は残す）。
3. **公開関門 G3 の未達と Issue #547〜#552**。P4 の開始条件ではない。外部公開の検討の再開は、所有者が決める。
4. **ADR 0020 の公開関門を P4 に適用するための改訂**の要否（決定 3）。

## 影響

P4 は、言語の機能ではなく、Sigil で書く大規模なアプリケーションである。ADR 0005 のとおり、ADR 0002〜0004（構文・所有権・効果）の決定を、長く動き続ける実用プログラムで検証する場にもなる。標準ライブラリ（ファイル・暗号）と信頼基盤の追加が前提として見つかっており、言語側の変更は `sigil` リポジトリで ADR を経て行う。P1 の成果物（HTTP、認証、PostgreSQL クライアント、イメージの配布）と P2 の成果物（UI、フルスタック、IDE）を再利用する。

本 ADR は新しい依存・信頼基盤・外部公開の承認ではない。

## 正式判定の記録

2026-11-16 の所有者指示に従い、Gemini Decisions は使わず typesafe-ai のみを使う。

**起草時点では未実施だった。** 起草セッション（claude.ai の Code セッション）には、判定 API（`POST https://api.typesafe.ai/v1/systemone`）の認証キー `TYPESAFE_API_KEY` が設定されておらず、`api.typesafe.ai` への通信がネットワークの許可で遮断されていた（AGENTS.md の「キーが無い環境」。ADR 0042・0043 の起草時と同じ）。そのため起草 PR では判定の節を「未実施」と明記し、採用案を「判定を経ていない起草者の案」として、実行できる 4 つの問いを添えて出した。

### 判定の結果（実施済み）

見張りが、typesafe-ai（モデル `jev-1.13.0`）で判定を実施した（Issue #571 のコメント、2026-11-17）。評価軸は ADR 0001（人間は仕様だけをレビューする原則）、ADR 0005 の段階表、ADR 0020 の公開関門、「いまは外部公開しない」の決定、本 ADR の決定 1〜5。問いは起草時に想定した 4 つで、結果は次のとおり。
