### 3. 上限 — 満たさない

- **確認方法**: ADR 0020 決定 4 の表の各行を、実装の既定値（`src/stdlib/http_limits.sigil`、`src/stdlib/pg.sigil`）とテストに対応づけて実行した。
- **HTTP サーバー（16 行）**: すべて対応するテストが成功。`http_limits_6_3g`（8 件）、`http_conn_6_3g_c`（20 件）、`app_config_460`（25 件）、`bearer_limits_512`（2 件）。既定値は `http_limits.sigil` の `defaults()` が表と一致する（本文 1 MiB、見出し 16 KiB、同時接続 256、backlog 128、各時間 10/30/30/30/60 秒、1 接続 1000 要求、応答本文 1 MiB。符号化本文 2 MiB は ADR 0032 が足した行）。

  | 行 | テスト |
  |---|---|
  | 要求の行・見出し全体・見出し数・本文・分割転送の行 | `limit_http_request_line`・`limit_http_head`・`limit_http_headers`・`limit_http_body`・`limit_http_chunk_line`（`limit_http_encoded_body`） |
  | 見出し・本文・ハンドラ・送信・待機の時間 | `limit_http_head_time`・`limit_http_body_time`・`limit_http_handler_time`・`limit_http_send_time`・`limit_http_idle_time` |
  | 同時接続・1 接続の要求数・応答本文 | `limit_http_concurrent_connections`・`limit_http_requests_per_connection`・`limit_http_response_body` |
  | 問い合わせの欄の数・JSON の深さ 64・トークン 4 KiB | `web_router_478::query_limit_uses_validated_config`・`fuzz_app_json`（深さ 64/65）・`limit_token_payload_audience_subject_key_lifetime_eval_native` |

- **設定で上限を外せない**: `limit_http_setters_reject_unbounded_values`（成功）。`with_*` の `requires` は `1 <= v && v <= 上限の上限` で、0 や負の値（無制限）を受けない。PostgreSQL の `with_*` も上限の上限を超えると `LimitExceeded`（`pool_capacity_and_deadline_configuration_boundaries` 成功）。
- **処理系・言語サーバー**: `depth_limit`（2 件、構文解析の深さ 128 が全段を 2 MiB スタックで通る）、`m6_lsp::lsp_frame_limits_*`、`modules_limits`（8 件）が成功。
- **PostgreSQL（表と不一致）**: 実装の既定値は ADR 0034 の決定に従うが、**ADR 0020 決定 4 の表は改訂されていない**（決定 4 は「既定値を変えるときは本 ADR を改訂する」）。

  | 項目 | ADR 0020 の表 | 実装（`pg.sigil`） |
  |---|---|---|
  | 接続の集まりの大きさ | 10 | **16**（待機 64） |
  | 接続を確立する時間 | 5 秒 | **10 秒**（`connect_ms: 10000`） |
  | 接続を得るまで待つ時間 | 5 秒 | **30 秒**（`acquire_ms: 30000`） |
  | 1 つの結果の全体の大きさ | 16 MiB | **4 MiB**（通信文も 4 MiB） |
  | 通信文の長さ・問い合わせの時間・SCRAM の回数 | 4 MiB・30 秒・4096〜10 万 | 同じ |

  最悪メモリの式（決定 4）もこの値では再計算されていない（実装の方が結果の上限は小さいが、接続数は多い）。テスト名も、ADR 0020 の完了条件の「`limit_` で始まる名前」に PostgreSQL の行は従っていない（`pg_pool_499`・`pg_protocol_463::limits_and_broken_frames`・`pg_scram_473::format_and_bounds` などが相当）。
- **CODEOWNERS（参考）**: `.github/CODEOWNERS` が所有者の対象にしているのは `/src/limits.rs` だが、このファイルは存在しない。既定値の実際の置き場所は `src/stdlib/http_limits.sigil` と `src/stdlib/pg.sigil` で、CODEOWNERS の対象外。ADR 0032 が「人間が行う」と依頼した変更が未実施。
- **中断点のない長い計算**（決定 4 が G3 の報告に求める点）: 要求の処理の時間は中断点でだけ効く。確認した範囲で CPU を長く使う経路は SCRAM の PBKDF2（PR #293 で `task.yield` を入れた）。サンプルのサービスの `/items` は PostgreSQL の問い合わせで、計算の重い経路は確認していない。利用者のハンドラは確認の範囲外。
- **結果**: HTTP・処理系の行は**満たす**。PostgreSQL の行は値が表と不一致で、表が未改訂のため全体として**満たさない**。
- **影響**: 値は表より緩い項目（プール 16、接続 10 秒、待機 30 秒）と厳しい項目（結果 4 MiB）が混在し、ADR と実装のどちらが正かが記録上決まっていない。サービスのメモリ見積り（決定 4 の式）が実装の値で検証されていない。

### 4. 秘密 — 満たす

  3. 試験: `bearer_config_509`（7 件）、`bearer_limits_512`、`bearer_verify_507`、`app_config_460`、`crypto_secret`（9 件）。
- **証拠**:

### 5. 認証 — 満たす

- **確認方法**: `src/stdlib/web.sigil` の `Router` を読み、`web_router_478`（6 件）、`bearer_config_509`、`service_06_integration` の非 Docker 分を実行した。
- **証拠**: `Router.route` は常に `AuthPolicy.Required`。認証を外すのは `public_route` だけ。検証器が未設定の `Router` は必須経路を常に固定の 401 にする（`router_verifier` が `None` のとき `bearer_unauthorized()`）。`public_routes()` が認証を外した経路を `METHOD PATH` の一覧で返す。`registration_rejects_ambiguous_public_and_required_routes`・`hooks_order_short_circuit_and_auth_boundary`・`dispatch_fixed_failures_and_public_routes` が成功。`Authorization` の重複・欠落・形式違反は固定の 401（`direct_dispatch_without_http_normalization_and_request_clock_failure`）。
- **認証を外した経路の一覧（リポジトリ内）**:

  | 場所 | 経路 | 備考 |
  |---|---|---|
  | `examples/11-web-router` | `GET /health`（`public_route`） | 認証検証器 `demo_auth` は固定文字列 `Bearer demo-only` を受け入れるデモ用。製品の検証器ではない |
  | `examples/12-bearer-auth` | `GET /public`（`public_route`） | |

- **結果**: フレームワークは**満たす**。
- **注意**: P1 のサンプルのサービスはフレームワークの既定拒否の振り分け（`Router.dispatch`）を使っておらず、認証を各経路で呼ぶ作り。`/fault` は認証なしで 500 を出せるため、そのまま公開する前に除く必要がある。`service_06_live_integration` は Docker 上の PostgreSQL が要り、このレビュー役の環境では実行できなかった。別のクラウドセッションが同じ対象コミットで実行した結果は、後述の「他のセッションの補助の実行結果」に記録した（本レビュー役は再実行していない）。

### 6. エラーの応答 — 満たす

- **確認方法**: `web.error_response`・`std.http` の `abort_conn` を読み、`http_conn_6_3g_c`・`app_config_460`・`web_router_478` を実行した。
- **証拠**: `error_response` はコードごとの固定の文だけを返し（500 は `internal server error`、未対応のコードも 500）、`std.http` の `abort_conn` は本文なしの固定 500（`content-length: 0`、`connection: close`）を書く。`handler_abort_answers_500_and_does_not_stop_other_connections`（応答が固定の 500 で、標準エラーに記録が出て、他の接続が継続する）と `fixed_error_responses_never_include_diagnostics`・`oversized_content_length_is_413_without_reading_the_body` が成功。`service_06_integration` は `GET /fault` が 500 になり直後の `/health` が 200 になることを確かめるが、この試験は Docker が要り未実行。

### 9. 依存 — 満たす

- **確認方法**: `Cargo.toml`・`Cargo.lock`・`cargo tree --offline -e all` を読み、RustSec の公開の勧告一覧（advisory-db、2026-11-15 10:59 +01:00 の版 `02e2517f`）を取得して `Cargo.lock` の全クレートと照合した。
- **証拠**:
  - `Cargo.toml` の依存は Cranelift の 4 クレート（`=0.137.0`）のみ。`Cargo.lock` は 46 エントリ（本体と、2 版ある `hashbrown` を含む）。`cargo tree -e all` に現れるのは本体を含む 37 名で、現れない 8 つ（`proc-macro2`・`quote`・`serde`・`serde_core`・`serde_derive`・`syn`・`unicode-ident`・`stable_deref_trait`）は、`cranelift-codegen` の任意機能 `enable-serde` と `gimli` の任意機能が引くもので、現在の設定ではコンパイルされない。`Cargo.lock` はほかに作業ツリー全体で 1 つだけ（`runtime/` の独立した lock はない）。
  - 勧告: `Cargo.lock` のクレート名で勧告に当たったのは `anyhow`（RUSTSEC-2026-0190、修正 ≥1.0.103、使用 1.0.104）、`bumpalo`（2020-0006・2022-0078、使用 3.20.3）、`cranelift-codegen`（RUSTSEC-2021-0067、修正 ≥0.73.1、使用 0.137.0）、`hashbrown`（2024-0402、使用 0.16.1/0.17.1）、`smallvec`（2018〜2021 の 5 件、使用 1.16.4）で、**すべて修正済みの版**。残りのクレートに勧告はない。`cargo-audit` は入っていないため、照合は上のスクリプトを使わず勧告ファイルの `[versions]` 欄を手で読んだ。

- **注意**: `serde` 系が `Cargo.lock` に残っているのは任意機能のため。ADR 0020 の「承認した依存のほかがない」の厳密な読みでは、ロックに載る範囲と実際のビルドに入る範囲が違う。
