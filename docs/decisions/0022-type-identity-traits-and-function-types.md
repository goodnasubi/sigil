# 0022: 型の同一性、利用者のトレイト、関数の型をフィールド・戻り値に置くこと（ADR 0018 の PR 2-3）

- **状態**: 提案

## 背景

- [ADR 0018](0018-p1-scope.md) の段階 2 は、モジュール（2-1・2-2）→ 利用者のトレイトと関数の型（2-3・2-4）→ `Bytes`（2-5）の順である。本 ADR は PR 2-3 にあたる。
- [ADR 0011](0011-type-system-scope.md) は、利用者のトレイト（決定 6）と、関数の型をフィールド・戻り値に置くこと（決定 10）を「P1 の前」に送った。P1 のフレームワーク（ハンドラの表）と直列化が、これを要する。
- [ADR 0021](0021-module-unit-and-visibility.md) は、型の名前が平らなことによる衝突を「段階 3 の前に再検討する」とした（未決の点）。案として「取り込み側が曖昧な名前を実際に使った箇所だけをエラーにする。型を修飾名で持つ変更が前提」を挙げた。
- トレイトの実装を探すには、モジュールをまたいで型を区別する必要がある。段階 3 で標準ライブラリを Sigil のモジュールにすると、同じ名前の型が増える。そこで本 ADR は、トレイトと一緒に型の同一性を決める。

### 現状（main `73b38bf`）

- **型の名前**: 検査器（`src/check.rs` の `Ty`）は、型を平らな名前で持つ。
- **取り込み**（ADR 0021 の 2-2b の記録）:
  - 取り込んだ関数のシグネチャに出る公開の型（隠れた依存の型）は、`use` なしで取り込み側に見える。
  - その名前が、自分の宣言や、別のモジュールの同じ名前と重なると、使っていなくても `use` の行で `UseConflict` になる。
- **結合**（2-2c）:
  - 入口でないモジュールの関数は、`<モジュール>.<関数>` に改名する。
  - 型は改名しない。別のモジュールの同じ名前の型は、使っていなくても `Unsupported` で拒む。
- **総称**: lowering は、総称の関数と型を、入口から届く具体的な型ごとに単相化する（`src/lower.rs`）。
- **トレイト**:
  - `trait` と `for` は予約語で、使えば構文エラーである。
  - ADR 0009 の決定 10 に骨格がある（トレイトの関数も 4 節を持ち、本体のない関数は `;` で終わる）。
  - 型引数の制約に書けるのは、標準ライブラリの 7 つの性質（`Copyable`・`Equatable`・`Comparable`・`Numeric`・`Sendable`・`Shareable`・`Displayable`）だけである。
- **関数の型**（ADR 0011 の決定 10）: 引数の型の一番外にだけ書ける。関数の値を入れ物に入れることや、返すことはできない。効果は `of(f)` で引き継ぐ。
- **言語サーバー**（#77 のレビューの低）:
  - hover と、開いていない依存の診断の範囲を作るとき、`text_of` が依存の本文をディスクから読み直す（`modpath::read_source`）。
  - この読み直しは、根の下にあるかを確かめない。検査のときに読んだ本文と、中身が違いうる。

## 本 ADR で決めないこと

- トレイトの値（`dyn` のような動的な呼び分け）・関連型・既定の実装・トレイトの継承・トレイトの型引数・総称のトレイトの関数。P1 では持たない（決定 2 の「持たないもの」）。
- 標準ライブラリの性質（`Equatable` など）をトレイトに置き換えること。段階 3 の ADR（3-1）で検討する。
- `use std.…` の要否（ADR 0021 の未決の点。段階 3 の ADR で決める）。
- `Bytes`（PR 2-5）。

## 評価の観点

重要な順に並べる。

1. **書いたものから意味が一つに決まり、人間と AI が読めるか**: 名前がどの宣言を指すか、どのトレイトの実装が呼ばれるか、呼び出しの効果が何か、が書いた場所から決まること。
2. **P1 のフレームワークと標準ライブラリが書けるか**: ハンドラの表、直列化、総称の数の関数の 0 と 1（ADR 0011 の決定 6 の持ち越し）。
3. **既存の保証を弱めないか**: 効果の宣言と推論の一致（ADR 0004）、契約の 4 節（ADR 0002）、所有権（ADR 0003）、並行処理の性質（ADR 0007）。
4. **実装が小さく、後戻りしないか**: 単相化の上で静的に解決できること。

## 決定 1: 型の同一性と、名前の解決

### 選択肢

- **I1: 平らな名前のまま、衝突を拒む**（今のまま）。
- **I2: 型の同一性を（モジュール, 名前）にする。ソースでは修飾しない名前だけを書く**。
- **I3: I2 に、ソースで型を修飾して書く構文（`lib.a.Config`）を足す**。

### 決定

**I2** を採用する。

- **同一性**: 型（`struct`・`enum`・`type`・`trait`）は、それを宣言したモジュールと名前の組で区別する。名前が同じでも、モジュールが違えば別の型である。
  - 標準ライブラリの型（`List`・`Option` など）は、標準の仮のモジュール（`std`）の型とする。
- **ソースの書き方は変えない**: 型は修飾しない名前で書く。別名も修飾の構文も足さない（ADR 0021 の決定 3 の U1 を保つ）。
- **名前の候補**: モジュール M の中で型の名前 `N` が指しうるものは、次の 2 段に分ける。
  - **明示の名前**: M が宣言した `N`、M が `use` で取り込んだ `N`。
  - **暗黙の名前**: M が取り込んだ関数・メソッド・型のシグネチャに出る、公開の型の `N`（隠れた依存の型）。
  - 標準の前置きの名前は、宣言も取り込みもできない（ADR 0021 のまま）ので、候補が重なることはない。
- **解決の規則**: 候補は同一性で数える。
  - 明示も暗黙も合わせて同一性が 1 つなら、それを指す。
  - 明示の名前が 2 つ以上あれば、その名前は **曖昧** である。
  - 明示の名前が 1 つ（同一性 X）で、暗黙の名前に X と違う同一性があるときは、次の 2 つで分ける。
    - 暗黙の候補が 2 つ以上あり、その中に X があるとき（`use` で暗黙の候補の 1 つを選んだとき）は、X を指す。明示がなければ、この名前はもともと曖昧で書けなかった。そのため、書いてあった箇所の指す先が黙って変わることはない。
    - それ以外（暗黙の候補が 1 つで X と違う、または暗黙の候補に X がない）は、**曖昧** とする。明示の名前を足したことで、それまで暗黙の型を指していた箇所が別の型を指すように黙って変わる（名前の乗っ取り）のを防ぐためである。
  - 明示の名前がなく、暗黙の名前の候補が 2 つ以上あれば、**曖昧** である。
  - まとめると、明示の名前が暗黙の名前に勝つのは、`use` で暗黙の候補から選んだときだけである。自分の宣言は、同じ名前の暗黙の候補を書いた箇所で、常に曖昧になる。この場合は、自分の型の名前を変えて解く（修飾の構文は持たない）。
- **`UseConflict` は、曖昧な名前を実際に書いた箇所でだけ出す**。
  - 報告する位置は、その名前を書いた位置（型の注釈、構造体リテラル、`impl`、`T.f()` の頭など）とする。`use` の行では出さない。
  - 文には、候補を修飾した名前（`lib.a.Config` と `lib.b.Config`）と、明示か暗黙かを並べる。案内は次のとおりとする。
    - 暗黙の候補どうしが曖昧なとき: 使いたい方を `use` で取り込めば解決する。
    - 自分の宣言や `use` が暗黙の候補とぶつかるとき: 自分の宣言の名前を変えるか、取り込む `use` を見直す。
  - 曖昧な名前を一度も書かなければ、エラーにしない。
    - `use` で取り込んだのに書かない名前は、今のとおり `UnusedUse` になる。
    - 暗黙の名前を書かなければ、その型の値は、型を書かずに受け渡せる（例: `let c = lib.a.load();` のように型を書かない `let`）。
  - 関数の名前にも同じ規則を当てる。関数には暗黙の名前がないので、曖昧になるのは明示の名前どうし（自分の宣言と `use`、2 つの `use`）である。
  - 標準の名前を `use` で取り込むことは、曖昧さではなく予約の違反なので、今のとおり `use` の行で拒む。
- **エラーの文の型の表し方**: 1 つの文に、名前が同じで同一性の違う型が 2 つ出るときは、修飾した名前で示す。それ以外は修飾しない名前で示す。
- **結合（2-2c）**:
  - 入口でないモジュールの型を、関数と同じく `<モジュール>.<名前>` に改名する。
  - 同じ名前の型の `Unsupported` を外す。
  - メソッドの実体の名前は、SIR の関数名とネイティブのシンボル（`sigil_f{n}_{名前}`）に出す。次の 2 つの形で区別する。
    - 固有のメソッド（`impl 型 { ... }`）: `<型のモジュール>.<型>.<メソッド>`。
    - トレイトの実装の関数（決定 2）: `<型のモジュール>.<型>/<トレイトのモジュール>.<トレイト>.<メソッド>`。
  - `/` は名前にもモジュール名にも使えない文字なので、固有のメソッドとトレイトの関数、および別々のトレイトの同じ名前の関数は、別の実体名になる。
  - `impl` を置いたモジュール（型の側かトレイトの側か）は、実体名に含めない。（トレイト, 型の頭）の実装は 1 つなので（決定 2）、置き場所がなくても一つに決まる。
  - 総称の実体は、今の単相化のとおり、この名前に型引数の印を足す。
  - 入口のモジュールの宣言は、今のとおりモジュール名を前に付けない。
  - 検査器の中のメソッドの表は、（型の同一性, 由来, 名前）を鍵とする。由来は「固有」か「トレイト（の同一性）」である。
- **仕様の表示**: `sigil spec`・`spec --json` は、書いた名前（修飾しない名前）をそのまま示す。`format` は変えない。
  - hover は、型の名前の上で、解決した先の同一性（修飾した名前と、明示か暗黙か）を示す。名前がどこを指すかを、書いた場所から確かめられるようにするためである。

### 理由

- 観点 1: 明示の名前は、ファイルの先頭（`use`）か自分の宣言で見える。明示が勝つのを「暗黙だけでは曖昧なとき」に限れば、`use` や宣言を足しても、書いてあった名前の指す先は黙って変わらない。変わる場合はエラーになる。
- 観点 1: 曖昧なまま書いた箇所だけをエラーにすれば、無関係な依存の型の名前が、書いていない利用者のコードを壊さない。今の問題（使っていない隠れた依存の型で `UseConflict` になる）は、この場合である。
- 観点 4: ソースの構文を変えないので、構文解析・整形・仕様の表示は変わらない。変わるのは検査器と結合の内部の表現である。
- トレイトの実装（決定 2）を（トレイト, 型）で探すには、型の同一性が要る。

### 選ばなかった案と理由

- **I1**: トレイトの実装を探す鍵が一つに決まらない。段階 3 で標準ライブラリの型が増えると、衝突も増える。
- **I3**: ADR 0021 の U3（常に修飾）の欠点と同じく、`Type.method` の書き方と区別しにくい。曖昧さは `use` で明示すれば解けるので、修飾の構文は要らない。
- **暗黙の名前を書けなくする**（型の名前を書くには必ず `use` を要する）: 規則は単純になる。しかし今のプログラム（隠れた依存の型の名前を書くもの）がすべて壊れ、2-2b の決定を覆す。曖昧でない限り書ける方が、移行が小さい。

## 決定 2: 利用者のトレイト

### 構文

ADR 0009 の決定 10 の骨格を確定する。

```
pub trait Handler {
  fn handle(self: &Self, req: Request) -> Response
    intent "要求に応える"
    requires none
    ensures none
    effects db, console;

  fn name() -> String
    intent "ハンドラの名前を返す"
    requires none
    ensures none
    effects none;
}

impl Handler for Health {
  fn handle(self: &Health, req: Request) -> Response
    intent "常に 200 を返す"
    requires none
    ensures result.status == 200
    effects none
  {
    return Response.ok();
  }

  fn name() -> String
    intent "ハンドラの名前を返す"
    requires none
    ensures none
    effects none
  {
    return "health";
  }
}
```

- `trait` を宣言として使えるようにする。`for` は `impl トレイト for 型` の中でだけ使う（くり返しの構文には使わない。予約は続ける）。
- **`Self`**: トレイトの宣言の中でだけ書ける型の名前で、実装する型を指す。予約名に加える。
  - `impl` の中では `Self` を書かず、実装する型を書く。ADR 0011 の決定 6 の「受け手の型を明示する」を保つ。
  - 整形器は `Self` を書き換えない。
- **トレイトの関数**: 受け手のあるもの（`self: Self`・`&Self`・`&mut Self`）と、受け手のないもの（型に属する関数）を持てる。
  - 受け手のないものは `Type.f()` と、総称の中では `T.f()`（`T: トレイト`）で呼ぶ。これで、総称の数の関数が 0 や 1 を作れる（ADR 0011 の決定 6 の持ち越し。例: `fn zero() -> Self`）。
  - `T.f()` は、型引数を式の中に書くのではなく、ADR 0011 の `Port.check` と同じ「型に属する関数」の形である。
- **4 節**:
  - トレイトの関数は 4 節を持ち、本体を持たない（`effects` 節の後の `;`）。
  - `impl` の関数も 4 節と本体を持つ。
  - 各節の規則は次の 3 つである。
    - `requires`: トレイトの `requires` と同じでなければならない。仕様の表示で、実装の関数だけを読んでも前提が分かるように、同じものを書き直させる。
      - 比較は、トレイトの側の `Self` を実装する型に置き換えたうえでの **α 同値** とする。引数の名前の違いは、引数の位置で対応させて同じとみなす。
      - それ以外（式の並べ替え、`a < b` と `b > a` など）は同じとみなさない。整形の後の構文木が、引数の名前の置き換えを除いて一致すること。
    - `ensures`: トレイトの `ensures` に、条件を足してよい（強めるのは安全）。足す前の条件を消すことはできない。トレイトの `ensures` が `none` なら、何を書いてもよい。検査の時には、トレイトの条件と実装の条件の両方を確かめる。
    - `effects`: トレイトの効果以下でなければならない（少ないのはよい）。「以下」は下の「効果の順序」で定める。
- **効果の順序**（決定 2 と決定 3 で使う）: 効果の集合 E が D 以下（E ⊑ D）とは、E の各要素が D のどれかの要素で覆われることである。
  - カテゴリは、ADR 0004 の階層の部分順序で比べる。同じカテゴリか、D の側が上位（`fs` は `fs.read` を覆う）なら覆う。下位が上位を覆うことはない（`fs.read` は `fs` を覆わない）。
  - `of(p)` は、引数の **位置** で比べる。E の `of(p)` は、D に同じ位置の引数の `of(q)` があるときだけ覆われる。名前の違い（トレイトの `f` と実装の `g`）は問わない。カテゴリが `of(...)` を覆うことも、その逆もない。
  - 比べる前に、両方を ADR 0008 の正規形（畳んだ形）にする。畳み方の違いで結果は変わらない。
- **公開**: `pub trait` のトレイトの関数はすべて公開される（関数ごとの `pub` は書かない）。`impl トレイト for 型` は、トレイトと型の両方が見える所で使える。`impl` 自体に `pub` は書かない。
- **制約**: 型引数の制約に、性質と並べてトレイトを書ける（`T: Comparable + Handler`）。
  - 並べ方は、今の性質の並べ方（名前の文字の順）と同じとする。
  - 性質の名前は予約名なので、トレイトの名前と重ならない。

### 一貫性の規則（コヒーレンス）

- **置ける場所**: `impl トレイト for 型` は、トレイトを宣言したモジュールか、型を宣言したモジュールにだけ書ける。
  - 標準の型（`Int`・`String`・`List` など）は、利用者が宣言したトレイトのモジュールでだけ実装できる。
  - 性質はトレイトではないので、`impl Equatable for ...` は書けない（ADR 0011 のまま）。
- **一意**: 同じトレイトと同じ型の頭（型の構築子。`List<Int>` なら `List`）の組に、実装は 1 つだけである。
  - `impl Show for List<Int>` と `impl Show for List<String>` の両方は書けない。
  - 型引数を持つ型には `impl<T> Show for Tree<T>` の形で書き、型引数に制約を書ける（`impl<T: Displayable> ...`）。
  - 型の頭のない実装（`impl<T> Show for T`）は書けない。
- **重なりが起きない理由**:
  - 実装を置けるのは、トレイトのモジュール A か型のモジュール B だけである。
  - A に置くには、A が型の名前を書ける必要がある。そのため、B は A の依存の閉包（`use` を推移的にたどって届くモジュールの全体）に入る。同じく、B に置くなら A は B の閉包に入る。
  - モジュールの参照の輪は禁じられている（ADR 0021）ので、A と B が互いの閉包に入ることはない。したがって、両方に置くことはできない。
  - 同じモジュールの中の重なりは、そのモジュールの検査で拒む。
  - したがって、プログラム全体で（トレイト, 型の頭）の実装は高々 1 つになる。
- **実装を探す範囲**: モジュール M の中で（トレイト R, 型 H）の実装を探すときは、**M の依存の閉包の全体**（M 自身と標準ライブラリを含む）を探す。
  - R も H も M で名前を書けるので、それぞれのモジュールは閉包に入っている。上の置き場所の規則から、実装は R か H のモジュールにある。したがって、閉包の外を探す必要はない。
  - 単相化の時は、プログラム全体の実装の表を使う。実装は（トレイト, 型の頭）ごとに全体で 1 つなので、M の閉包で見つけたものと同じになる。
  - 言語サーバーの検査（`project::check_project_overlay`）も、コマンドの `sigil check` と同じ読み込み（`modpath::load`）で同じ閉包を作り、その中を探す。開いている未保存の本文は、閉包の中のファイルの本文を差し替えるだけで、探す範囲は変えない。2-4c の試験で、両者の結果が同じことを確かめる。
- **段階 3 の後の標準ライブラリ**: 標準ライブラリを Sigil のモジュールにしても、上の規則はそのまま保たれる。
  - 標準のモジュールは、利用者のモジュールを取り込まない（標準は利用者のモジュールより先に決まり、利用者の名前を知らない。標準は利用者のモジュールの閉包に入るが、逆はない）。段階 3 の ADR で、これを規則として書く。
  - 標準の型に利用者のトレイトを実装するには、トレイトのモジュール（利用者の側）に置く。利用者の型に標準のトレイトを実装するには、型のモジュール（利用者の側）に置く。標準の型に標準のトレイトを実装できるのは、標準の中だけである。
  - 標準を複数のモジュールに分けても、モジュールごとに同じ規則が働き、輪の禁止も保たれるので、重なりは起きない。段階 3 の ADR（3-1）で、この性質が保たれることを確かめる。
- **新しいエラーの種類**:
  - `TraitImplPlacement`（置けない場所の `impl`）。
  - `TraitImplDuplicate`（同じ組の 2 つ目）。
  - `TraitImplMismatch`（関数の欠け・余り、シグネチャ・`requires`・`ensures`・`effects` の規則の違反）。
  - `PolymorphicRecursion`・`InstanceLimit`（下の「単相化の上限」）。
  - 報告する位置は `impl` の行か、違反した関数の行とする。

### 単相化の上限

トレイトの制約で総称の関数を書きやすくなると、型引数が呼ぶたびに大きくなる再帰（多相再帰。例: `fn f<T: Show>(x: T) { ... f(Tree.leaf(x)) ... }`）で、単相化が止まらなくなる。今の lowering の作業の列（`src/lower.rs` の `queue`）には、止める上限がない。そこで次を決める。

- **検査の時に多相再帰を拒む**（`PolymorphicRecursion`）: 総称の関数の呼び出しのグラフで、強連結成分の中の呼び出しが、呼ぶ側の型引数を真に含む型（`Tree<T>`・`List<T>` など。`T` そのものは含まない）を型引数に渡していたら、その呼び出しの位置でエラーにする。
  - `sigil check` と言語サーバーで見つかるように、検査器で行う。
- **単相化の上限**（`InstanceLimit`）: 検査をすり抜けた場合の安全網として、lowering で次の上限を設ける。
  - 実体の鍵の型引数の入れ子の深さ: 32。
  - 実体の数（関数と型の合計）: 10,000。
  - 超えたら、その実体を作らせた呼び出しの位置で `InstanceLimit` を出して止める。`sigil run`・`sigil build` のエラーとして出し、黙って打ち切らない。
  - 上限の値は、ADR 0021 の `ModuleLimit` と同じく定数で持ち、試験で境界（上限ちょうどは通り、1 つ超えると拒む）を確かめる。
- 上限は、トレイトのない今の総称にも働く（今も多相再帰は書けて、止まらない）。入れるのは 2-4c とする。

### 呼び出しの解決

- **静的に解決する**: すべての呼び出しは、単相化の時に具体的な実装に決まる。トレイトの値（`dyn`）は持たない。異なる型のハンドラを 1 つの表に並べる用途は、関数の型（決定 3）で書く。
- **トレイトが見える範囲**:
  - トレイトの関数をメソッドとして呼ぶ（`x.handle(r)`）には、そのトレイトがモジュールで明示の名前として見えていなければならない（自分の宣言か `use`）。ただし、型引数の制約に書いたトレイトは、その関数の中で見える。
  - ファイルの先頭で、使うトレイトが分かるようにするためである（U1 と同じ）。
- **名前の重なり**:
  - 1 つの型の固有のメソッドと、トレイトの関数の名前が同じなら、`impl` の宣言のときにエラーにする（`TraitImplMismatch`）。ADR 0011 の「同じ型のメソッドとフィールドに同じ名前を付けられない」と同じ扱いである。
  - そのため、型のモジュールが後から同じ名前の固有のメソッドを足すと、トレイトのモジュール（下流）に置いた `impl` がエラーになる。これは許容し、記録する（「根拠の限界」）。黙って呼ぶ先が変わるのではなく、検査のエラーとして現れるからである。
  - 見えている 2 つのトレイトが同じ名前の関数を同じ型に与えるときは、`x.m()` を書いた箇所で曖昧のエラー（`UseConflict`。決定 1 と同じく、書いた箇所でだけ出す）にする。
  - 曖昧なときは `トレイト.m(x)` と書いて選ぶ。この形は、受け手を最初の引数に渡すだけで、新しい構文ではない（`Type.f(...)` と同じ形）。
- **効果**:
  - 型が具体的に分かる呼び出しは、実装の関数の効果の宣言を使う。
  - 総称の中の `T: トレイト` を通した呼び出しは、トレイトの関数の効果の宣言を使う。
  - どちらも、推論と宣言の一致の規則（ADR 0004）はそのまま働く。総称の関数は、トレイトの効果を自分の効果に含めて宣言する。実装の効果はトレイトの効果以下（⊑）なので、単相化の後に、宣言より実際の効果が多くなることはない。
- **契約の検査**: 呼び出しの前にトレイトの `requires`（実装も同じ）を、戻る前にトレイトと実装の `ensures` を確かめる。今の関数の契約の検査と同じ時期と方法である。

### 持たないもの（P1）

- トレイトの値（`dyn`）・関連型・既定の実装・トレイトの継承・トレイトの型引数・総称のトレイトの関数（関数ごとの型引数）・型の頭のない実装。
- 必要が分かったら、本 ADR を改めて足す。足しても、今の規則で書いたプログラムの意味は変わらない（どれも今は書けない形なので）。

### 仕様と言語サーバー

- `sigil spec` は、トレイトを型と同じ並びに置き、トレイトの関数を 4 節つきで示す。`impl トレイト for 型` の関数は、その型の項目の下に、どのトレイトの実装かを添えて示す。
- `spec --json` は、項目の種類 `trait` と、関数の欄 `trait`（実装するトレイトの名前）を足す。`format` は上げない（ADR 0019 の決定 1・2）。
- hover は、具体的な型が分かる呼び出しでは実装の関数の仕様を、`T: トレイト` を通した呼び出しではトレイトの関数の仕様を示す。

### 理由

- 観点 2: ハンドラ・直列化・0 と 1 を作る関数は、受け手のある関数と型に属する関数で書ける。関連型や継承がなくても、P1 の用途は足りる見込みである。
- 観点 1・4: 単相化で静的に解決すれば、どの実装が呼ばれるかが型から決まる。実行時の表（vtable）も要らない。
- 観点 1・3: `requires` を同じにし、`ensures` は足すだけにすれば、実装の仕様を読む者は、トレイトの約束を破る実装がないことを、書いたものから確かめられる。`requires` の弱め（実装が前提を緩める）は安全だが、構文での比較では判定できない（同値の判定が要る）。同じものに限る方が単純である。
- 置ける場所と一意の規則は、Rust の孤児の規則の簡単な形で、輪の禁止があるので、モジュールをまたいだ重なりの検査が要らない。

### 選ばなかった案と理由

- **トレイトの値（`dyn`）を P1 で持つ**: 実行時の表、トレイトの値の所有権と性質（`Sendable` など）、効果の上限を決める必要があり、大きい。ハンドラの表は関数の型で書ける。
- **既定の実装を持つ**: 既定の実装の 4 節と、実装の側で上書きしたときの契約の関係を決める必要がある。P1 の用途にない。
- **性質を今トレイトにする**: 性質は導出（構成要素から自動で決まる）で、利用者が実装を書くトレイトと性格が違う。段階 3 で、標準ライブラリを Sigil にするときに検討する。

## 決定 3: 関数の型をフィールド・戻り値に置くこと

ADR 0011 の決定 10 の B を、置ける位置を限って採る。

### 決定

- **書き方**: 置ける位置の関数の型は、効果を必ず書く: `fn(Request) -> Response effects db, console`、効果がないなら `fn(Int) -> Int effects none`。
  - 引数の位置の関数の型は、今のまま効果を書かない（`of(f)` で引き継ぐ）。**P1 では、引数の位置に効果つきの関数の型は書けない**（`FnTypePosition`）。
  - 置ける位置の関数の型の効果には、カテゴリだけを書ける。`of(...)` は書けない（関数の型には引数の名前がないため）。同じ理由で、置ける位置の関数の型の引数に、関数の型は書けない。
- **置ける位置**: 構造体のフィールド、列挙型の値の中身、関数とメソッドの戻り値の型、`let` の型注釈。
- **置けない位置**: 型引数（`List<fn(...) -> T effects none>`）。表に並べるときは、構造体に包んで `List<Route>` とする。
- **効果の規則**:
  - 効果 E の関数の値を、効果の宣言 D の位置に入れるには、E ⊑ D でなければならない（効果の少ない関数はよい。順序は決定 2 の「効果の順序」）。E は、名前の関数なら宣言、クロージャなら本体から推論した効果とする。
  - E に `of(...)` を含む関数（効果が引数で決まる高階関数）と、引数の位置の関数の型の引数（効果が `of(f)` でしか分からないもの）は、置ける位置に入れられない（`FnTypePosition`）。
  - その位置の関数を呼んだ効果は、D とする。
  - 呼んだ側の関数の宣言と推論の一致（ADR 0004）は、D を含めて確かめる。
- **`of(f)` との関係**: 置ける位置の関数の値（効果の宣言 D）を、引数の位置の関数の型の引数 `f` に渡すと、その呼び出しの `of(f)` は D に置き換わる。名前の関数を渡したときに、その関数の宣言に置き換わるのと同じである。
- **呼び方**: フィールドの関数は `s.handler(req)` と書く。メソッドとフィールドに同じ名前を付けられない（ADR 0011）ので、意味は一つに決まる。戻り値の関数は、`let` で束縛してから呼ぶ。
- **入れられる値**:
  - 名前の関数と、`move` のクロージャだけを入れられる。
  - 借用をとらえるクロージャは入れられない。参照は構造体に持てない（ADR 0003）のと同じ理由である。
  - 入れたクロージャは、とらえた値を書き換えられない。呼び出しは何度でもでき、呼ぶたびに同じとらえた値を読む。
- **性質**:
  - フィールドと戻り値の関数の型は、`Sendable` と `Shareable` を持つとする。そのため、入れるクロージャのとらえた値は、すべて `Sendable` と `Shareable` でなければならない（入れる時に確かめる）。
  - 他の性質（`Copyable`・`Equatable` など）は持たない。関数の型の値は移動し、関数の型を持つ構造体は比べられない。
  - ADR 0011 の「関数の型とクロージャはどの性質も持たない」を、この位置について改める。
  - 理由: ハンドラの表は、要求ごとのタスク（ADR 0018 の決定 7）から共有して読まれる。
- **ADR 0011 の決定 10 の他の規則**: 引数の位置の規則（関数の型の変数を `let mut` にできない、など）は変えない。
  - 入れ物に関数の値を入れる禁止は、決定 3 の置ける位置（構造体のフィールド、列挙型の値の中身）の型を通す場合に限って外す。
  - 組・`Option`・`List` に直接入れることは、引き続きエラーとする。
- **破棄**: 入れたクロージャのとらえた値は、入れ物の値と一緒に破棄される。今のクロージャの破棄の規則のままである。

### 理由

- 観点 1・3: 効果を型に書けば、フィールドの関数を呼んだ効果が、宣言から決まる。⊑ の規則で、効果の少ないハンドラを同じ表に並べられる。
- 観点 2: ルーティングの表は、`struct Route { path: String, handler: fn(Request) -> Response effects db }` の一覧で書ける。トレイトの値（`dyn`）なしに、異なる処理を同じ表に並べられる。
- 型引数の位置を許すと、総称の型の性質の導出と単相化に、効果つきの関数の型が入る。構造体に包めば同じことが書けるので、P1 では外す。

### 選ばなかった案と理由

- **効果を書かなくてよい（既定は `none`）**: 書き忘れると、効果のあるハンドラが入らない理由が読み手に見えない。置ける位置では常に書かせる。
- **借用をとらえるクロージャも入れる**: 構造体が参照を持つことになり、ADR 0003 の規則 2（参照は二級）に反する。

## 決定 4: 言語サーバーが依存の本文を読み直すこと（#77 のレビューの低）

- hover と、開いていない依存の診断の範囲は、**検査のときに読んだ依存の本文** を使う。
  - 検査（`project::check_project_overlay`）が `modpath::load` で読んだ本文を、検査の結果（入口ごとの `deps`）と一緒に持つ。
  - `text_of` はディスクを読み直さない。
  - **保持量の上限**: 本文は、パスごとに 1 つを入口の間で共有して持つ。1 ファイルは `modpath::MAX_SOURCE_BYTES`（1 MiB）、1 つの検査で読むファイルは `MAX_FILES`（256）までなので、1 回の検査で持つ本文は高々 256 MiB である。言語サーバーが全体で持つ依存の本文は 64 MiB までとする。超えた分は持たない。その依存の hover は出さず、診断はその依存を取り込んだ `use` の行に出す。超えた分もディスクから読み直すことはしない。
- 理由:
  - 読み直しは根の確認を通らない。
  - 検査の後に書き換わったファイルを読むと、診断の位置と hover の仕様が、検査した中身と食い違う。
- **拾う先**: PR 2-4a（下の「実装の分け方」）に含める。2-4a は検査の結果の形（型の同一性）を変えるので、同じ PR で結果に本文を持たせる。
  - 実装の分割: 2-4a は 2 つに分けた。本決定（本文を結果に持たせる。`check_project_overlay` の `on_text`・`modpath::load_full`・`lsp` の `Checked.texts`）を先に入れ、決定 1（型の同一性と名前の解決）を続けて入れる。
  - 上限の数え方: パスと中身が同じ本文は入口の間で共有し 1 つと数える。再検査する入口の古い本文は数えない（置き換えるため）。試験では `SIGIL_LSP_TEST_DEP_CAP`（バイト数）で上限を下げる。
  - 上限を超えた依存の診断を `use` の行に出すときの探し方は、入口と持っている本文から `use <モジュール名>` で始まる最初の行を探す（見つからなければ入口の先頭）。
- **試験**: 検査の後に依存のファイルを書き換えても、hover と診断の範囲が検査した本文に基づくこと。根の外を指すように差し替えても読まないこと。故障注入として、読み直しに戻すと落ちることを確かめる。

    - 借用をとらえるクロージャを入れる。
    - `Sendable` でない値をとらえるクロージャを入れる。
    - 型引数に関数の型を書く。
    - 引数の位置に効果つきの関数の型を書く。

  - 多相再帰の判定を外す（上限で止まることを確かめる）。
  - 実体名から `/<トレイト>` を外す（固有のメソッドと衝突することを確かめる）。
  - 実装を探す範囲を、直接の `use` の先だけに狭める。
- 2-4a の故障注入:
  - 明示の名前が暗黙の名前に勝つ規則を外す。
  - 名前の乗っ取りの判定を外す（明示が常に勝つようにする）。

  - 結合の型の改名を外す。
  - 依存の本文をディスクから読み直す。
- **2-4a の実装の注記（決定 1 からの逸脱）**:
  - 構文木の `Type` と `Expr` は位置を持たない（位置があるのは宣言・文・`use`・`impl` の単位）。このため、`UseConflict` の位置は、曖昧な名前を書いた **文または宣言** の位置（その名前を含む最も内側の文、文の外では宣言）とし、名前そのものの列までは指さない。決定 1 の「書いた位置」は、この粒度で満たす。式・型への位置の付与は、列まで指す必要が出た時に別に行う。
  - 検査器の中の型の名前は、同じ短い名前が複数の同一性で現れるときだけ `<モジュール>.<名前>` にする（自分の宣言は短い名前のまま）。それ以外のエラーの文は変わらない。結合では、入口でないモジュールの型と関数をすべて `<モジュール>.<名前>` に改める。
  - hover が解決した先の同一性を示すことは、実装済み（cdc7aba。型の名前の上で「解決先: <モジュール>.<型>（明示|暗黙）」を表示し、`lsp_hover_type_identity` で確かめる）。同じ文に同じ短い名前の別の同一性が出るときの修飾表示は、2-4a の後続に回す。

## 影響

## 人間の判断が要る点

- なし。依存の追加・CI の変更・権限の設定・データベースのスキーマに当たる点はない。
- 言語の意味を変える決定（暗黙の名前の解決、トレイトの規則、関数の型の性質）なので、承認は所有者かその委任による。

## 根拠の限界と再検証

- 候補の案出しと採点を、同じ者（Claude）が行っており、偏りがありうる。
- 「P1 の用途は関連型・既定の実装・`dyn` なしで足りる」は、フレームワーク（ADR 6-4）と標準ライブラリの Sigil 版（段階 3）をまだ書いていない段階の見込みである。書いてみて足りなければ、本 ADR を改める。
- 決定 2 の `requires` を同じにする規則は、実装の前提を緩めたい場合を書けなくする。何回これに当たったかを数える。
- 決定 3 の「入れたクロージャはとらえた値を書き換えない」と「`Sendable`・`Shareable` を必須にする」は、ハンドラの表を想定した制限である。状態を持つ関数の値が要る場合は、`SyncShared` を共有する形で書けるかを、ADR 6-4 で確かめる。
- 決定 1 で名前の乗っ取りを曖昧として拒むと、依存に同じ名前の公開の型が増えたとき、自分の宣言と同じ名前を書いていた箇所がエラーになる。黙って指す先が変わるよりよいが、修飾の構文がないので、自分の型の名前を変えるしかない。件数が多ければ、I3（修飾の構文）を改めて検討する。
- 決定 2 で、型のモジュールが固有のメソッドを後から足すと、下流の `impl` が壊れる（`TraitImplMismatch`）。黙った変化ではないので許容する。件数を数える。
- 決定 2 の多相再帰の禁止は、多相再帰を要する正しいプログラム（入れ子の深さで型が変わるデータ構造）を書けなくする。P1 の用途にはない見込みである。
- 決定 3 で、引数の位置に効果つきの関数の型を持たず、`of(...)` を持つ関数を入れられないのは、P1 の範囲を小さくするためである。ミドルウェア（次のハンドラを受け取るハンドラ）が要る場合は、ADR 6-4 で、次のハンドラを構造体に包む形で書けるかを確かめる。
- 次を数える。
  - 2-4a の後に、曖昧な名前で `UseConflict` になった件数と、`use` で解決した件数。そのうち名前の乗っ取りで曖昧になった件数（hover で解決した先を確かめた件数も含む）。
  - 固有のメソッドの後付けで、下流の `impl` が壊れた件数。
  - トレイトを書こうとして、持たない機能（`dyn`・既定の実装・関連型）に当たった件数。
