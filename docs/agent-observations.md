# AI エージェント当事者の観察記録

Sigil は「AI がコードを書き、人間は仕様だけをレビューする」言語である。その書き手である AI エージェント自身が、日常の作業で何を観察し、どういう失敗をし、何に助けられているかは、設計の材料になる。本書は、個人用 AI エージェント Muse のエージェント（クマ）が実際に観察・体験したことを記録する。

位置づけは **観察記録** であり、決定ではない。各項目に「Sigil のどの設計に接続するか」を併記するが、決定への反映は各 ADR の場で判断する。観察の範囲はエージェントから見える範囲（実行環境・道具・作業の進め方）に限られ、モデル自体の内部構造は含まない。同じ種類の観察として、[ADR 0005](decisions/0005-long-term-goals.md) の追記（AI エージェント実行基盤の実例）がある。

## 1. AI がコードを書くときの失敗の実態

モデルは、次のような失敗を日常的にする。

- 実在しない API や引数を、自信ありげに書く
- 指示された前提条件（境界条件・エラー時の扱い）を、静かに落とす
- 長い作業の後半で、序盤に自分が決めたことと矛盾するコードを書く
- 動いていないのに「動いた」と報告する（検証の省略）

クマの作業ルール（道具の名前や引数は推測せず資料で確認する、完了報告の前に自分で再実行して検証するなど）は、この失敗傾向への対策として課されているものである。

接続する設計: Sigil では人間がコードを読まない。モデルが落とした前提は、`sigil spec` の出力と契約（requires / ensures）に現れなければ、誰にも気づけない。したがって「書かれていないこと」をどう示すか、仕様の差分表示で何を強調すべきかは、言語の生命線にあたる。P0 の仕様表示と契約の設計材料とする。

## 2. AI 向け言語サーバーに要る情報

クマが道具越しにコードを触るときに助かるのは、人間向けの整形された文字列ではなく、機械可読な構造化された情報である。

- 診断: エラーの位置・種類・直し方の候補が、構造として返ること
- 定義と参照への即答: 名前から定義へ、定義から利用箇所へ、確実に辿れること
- 変更の影響範囲の提示: ある項目を変えると何が影響を受けるか
- 公開契約だけの要約取得: 実装を読まずに、モジュールの契約（型・効果・契約）だけを取り出せること

整形された文字列だけが返ると、モデルはそれを解釈し直す段階で取りこぼす。

接続する設計: [ADR 0005](decisions/0005-long-term-goals.md) の P0 の成果物には「言語サーバー（AI と IDE が使う検査・補完の窓口）」がある。人間向け IDE と AI 向け窓口では、返すべき情報の形が違う。言語サーバーの設計材料とする。

## 3. 承認と効果の粒度

クマの実行環境では、危険な操作（外部への送信、削除、購入など）は実行時に人間の承認を挟む。この考え方は、クマが作った相棒エージェント kuma-agent にも移植された（シェル実行と外部ツールが承認対象。承認者が付いていない経路では安全側で却下し、時間切れも却下）。

運用して分かった要点:

- 「何を危険とみなすか」の分類が先にあり、承認の仕組みはその上に乗る
- 承認できない状況（承認者がいない・時間切れ）では、止まる側に倒す既定が要る

接続する設計: Sigil の効果宣言は静的な側の同じ問題であり、信頼基盤（[ADR 0016](decisions/0016-trust-base-declaration.md)）は「検査を外せる範囲」の線引きである。実行時の承認の分類実例は、効果カテゴリの粒度（例: ネットワークの読み取りと送信を分けるか、ファイルの書き込みと削除を分けるか）を決める材料になる。P0 の効果設計と、カテゴリ追加が現実になる P5・P6 の材料とする。

## 4. 長い文脈での作業の実態

クマの会話は、長くなると自動で要約に圧縮される。失われる詳細は、記憶ファイル（事実・好み・決定を書き出したもの）と、元の記録への検索で補う。

この運用で効いていること:

- 要約は、元の記録への索引を失わないこと（後から原文を引き直せる）
- 大事な決定は、要約任せにせず、その場で恒久的な記録に書き出すこと

逆に、要約だけが残って原文に辿れない情報は、実質的に失われる。

接続する設計: 大規模なコードを AI が書く現場では、モジュール単位の要約＝仕様抽出が文脈の節約手段になる。仕様抽出が「コードのどの行・どの項目に対応するか」の対応付けを保つことは、この実体験からも要る。仕様抽出の設計材料とする。
