# 0004: 効果（副作用）の扱い

- **状態**: 承認（2026-10-22。所有者の委任を受けて Claude が決定。計測による再検証の条件は末尾を参照）

## 背景

[ADR 0002](0002-syntax-family.md) で、関数は `effects` 節を必ず書くと決めた。人間はコードを読まず仕様だけをレビューするので（[ADR 0001](0001-vision-and-scope.md)）、`effects` 節は「この関数が外の世界に何をしうるか」を人間が知る唯一の手がかりになる。
そこで、効果として何を数えるか、どの粒度で書くか、宣言と実装の一致をどう検査するかを決める。

前提:

- 出力先はネイティブ（サーバー）・WebAssembly / JavaScript（ブラウザ）。Python から呼び出せる（ADR 0001）
- 書き換えは `&mut` 引数としてシグネチャに現れる。共有所有の型を通した書き換えもある（[ADR 0003](0003-ownership-and-borrowing.md)）

## 評価の観点

重要な順に並べる。

1. **仕様として信頼できるか**: `effects` 節に書かれていない効果が、実行時に起こりえないこと。人間はコードを読まないので、宣言が漏れると気づく手段がない。
2. **人間が読んで分かるか**: 仕様に現れる効果の表記が少なく、意味が明快であること。
3. **AI が誤りなく書けるか**: 規則が少なく、検査エラーの直し方が明確であること。
4. **出力先・Python 連携との相性**: ブラウザとサーバーで使える効果の違い、Python との境界を扱えること。
5. **表現力**: 高階関数（関数を引数にとる関数）や、テストでの効果の差し替えを書けること。

## 選択肢

- **A: 代数的効果（Koka など）**: 効果を型の一部とし、効果の多相と「ハンドラ」（効果の実装をその場で差し替える仕組み）を言語に持つ。表現力は最も高いが、規則と概念が多い。
- **B: 静的な効果宣言と一致検査**: 標準ライブラリが定める固定の効果カテゴリを `effects` 節に列挙し、コンパイラが本体から推論した効果と一致するかを検査する。多相は「引数の関数の効果」を引き継ぐ形に限る。差し替えは言語ではなく、テスト用の実行環境で行う。
- **C: 能力（ケイパビリティ）を値として渡す**: ファイルシステムやネットワークへのアクセス権を値として引数で受け取る。効果は引数の型に現れ、`effects` 節は不要になる。

## 比較

| 観点 | A: 代数的効果 | B: 静的宣言 + 一致検査 | C: 能力を値で渡す |
|---|---|---|---|
| 1. 仕様の信頼性 | ◎ | ◎ 推論結果との一致を強制する | ○ 能力を構造体に入れて受け渡すと、どこで使われるかがシグネチャから読みにくくなる |
| 2. 人間が読めるか | △ ハンドラや効果変数は仕様の読み手に説明しにくい | ◎ 「ファイルを読む」「ネットに接続する」のような固定の語彙だけが現れる | ○ 引数として現れるが、意図と混ざる |
| 3. AI の書きやすさ | △ 概念が多く、学習データも少ない | ○ Java の検査例外に似た「呼び出し先の効果を宣言に足す」規則で、直し方が明確 | ○ 依存性注入に近く馴染みはあるが、能力を末端まで引き回す必要がある |
| 4. 出力先・Python | ○ | ◎ 出力先ごとに使えるカテゴリを制限できる | ◎ |
| 5. 表現力 | ◎ | ○ 引数の関数の効果の引き継ぎと、テスト用の差し替えで足りる見込み | ○ |

Java の検査例外は「宣言を書く手間」が批判されてきたが、本言語では書き手が AI なので、その手間は大きな問題にならないと見込む（未検証）。

## 決定

**B: 静的な効果宣言と一致検査** を採用する。

最も重い「仕様の信頼性」と「人間が読めるか」で優れ、規則が少ない。A のハンドラが担う「効果の差し替え」は、テスト用の実行環境で代替する。

### 規則

#### 1. 効果のカテゴリ

効果は、標準ライブラリが定める次のカテゴリで表す。利用者が新しいカテゴリを定義することはできない（読み手が知るべき語彙を固定するため）。カテゴリは `.` で階層をなし、上位を書くと下位をすべて含む（例: `fs` は `fs.read` と `fs.write` を含む）。

| カテゴリ | 意味 | 使える出力先 |
|---|---|---|
| `console` | 標準入出力・ログへの出力 | すべて |
| `fs.read` / `fs.write` | ファイルを読む / 書く | サーバー |
| `net.client` | ネットワークに接続する（HTTP の送信を含む） | すべて |
| `net.server` | 接続を待ち受ける | サーバー |
| `db` | データベースを読み書きする | サーバー |
| `clock` | 現在時刻を読む・待つ | すべて |
| `random` | 乱数を得る | すべて |
| `env` | 環境変数・起動引数を読む | サーバー |
| `process` | 他のプロセスを起動する・自分を終了する | サーバー |
| `dom` | 画面（DOM）を読む・書き換える | ブラウザ |
| `browser.storage` | ブラウザの保存領域を読み書きする | ブラウザ |
| `state` | 共有所有の型を通して値を書き換える | すべて |
| `foreign` | Python など外部から渡された関数を呼ぶ（中身を検査できない） | すべて |

#### 2. 効果に数えないもの

- `&mut` 引数を書き換えること（シグネチャに「書き換える」と現れるため）
- メモリの確保と解放
- 値を返すこと、`Result` で失敗を返すこと

#### 3. 宣言と一致検査

- `effects` 節には、本体が起こしうる効果をすべて列挙する。効果がなければ `effects none` と書く。
- コンパイラは本体から効果を推論し（呼び出した関数の効果の和）、宣言と **完全に一致** しなければコンパイルエラーにする。足りない場合だけでなく、余分に書いた場合もエラーとする。仕様に書かれた効果が実際に起こりうるものだけになり、人間が仕様の差分から効果の増減を正確に読めるようにするためである。
- 効果はカテゴリ単位で扱う。「どのファイルを読むか」のような引数ごとの範囲指定は、検証が難しいため当面は行わない。

#### 4. 関数を引数にとる関数

- 引数の関数 `f` の効果を引き継ぐことを、`effects of(f)` と書く。自分の効果と並べてよい（例: `effects of(f), console`）。
- 呼び出し側では、渡した関数の実際の効果に置き換えて検査する。`effects none` の関数を渡せば、`of(f)` は消える。

#### 5. 出力先による制限

- 関数を含むモジュールの出力先（サーバー / ブラウザ）に対して、表の「使える出力先」にない効果を使うとコンパイルエラーにする。
- 両方で使うモジュールは、両方で使える効果だけを使える。

#### 6. 入口と境界

- プログラムの入口（`main`、サーバーのリクエスト処理、UI のイベント処理など）も `effects` 節を持つ。プログラム全体で起こりうる効果は入口の宣言で分かる。
- Python に公開する関数の効果は、生成する Python 側の説明文（docstring）に記載する。Python から関数（コールバック）を受け取って呼ぶ場合、その呼び出しの効果は `foreign` とする。

#### 7. テストでの差し替え

- テスト用の実行環境では、効果カテゴリごとに実装を差し替えられる（例: `fs.read` を、メモリ上の固定のファイルを返す実装に替える）。
- これは実行環境の機能であり、通常のコードから効果の実装を差し替える構文は持たない。

## 影響

- `examples` の効果の書き方を本 ADR に合わせる。`fs.read(path)` は `fs.read` に、`io.print` は `console` に改める。規則を示すサンプルを [examples/04-effects](../../examples/04-effects/) に追加する。
- 人間向けの仕様表示では、カテゴリを日本語に訳して示す（例: `fs.read` → 「ファイルを読む」）。
- UI の記述モデルの ADR では、イベント処理の入口が `dom` などの効果を宣言する前提で設計する。
- 非同期処理（`async`）を効果として扱うかどうかは、並行処理の ADR で決める。

## 未決として残す点

- 異常停止（配列の範囲外アクセスなど、実行時の検査による停止）を効果として数えるか。契約の静的検査でどこまで排除できるかと合わせて決める。
- 無限ループ（停止しないこと）を効果として数えるか。
- 引数ごとの範囲指定（「この引数のパスだけを読む」）を将来入れるか。

## 根拠の限界と再検証

- 「宣言の手間は書き手が AI なら問題にならない」「代数的効果は AI にとって書きにくい」は定性的な判断で、計測していない。
- 13 個のカテゴリで実用プログラムの効果を過不足なく表せるかは未検証である。
- 候補の案出しと採点を同じ者（Claude）が行っており、偏りがありうる。
- 処理系ができた段階で、次を計測する。結果が本決定と大きく食い違う場合は、この ADR を見直す。
  - AI が書いたコードの、効果の一致検査のエラー率と修正の成功率
  - 代表的なサーバー・UI の課題で、カテゴリが不足して表せなかった効果の数
